# CPU runtime and complete-resource audit, second pass

Updated 2026-11-13 16:08 UTC. This note measures ordinary, benign language-model inference. It extends the [first Qwen3-4B resource pilot](qwen3-4b-q4ks-resource-pilot-2026-11-13.md) and the [CPU runtime review](frontier-cpu-runtime-research-2026-11-12.md). The question is whether a smaller model file also reduces the bytes that must be deployed, peak RAM, and CPU consumed by a complete served task while retaining useful answer quality. Each result below names its denominator. Neither a synthetic token benchmark nor two reused development questions establishes that joint outcome.

## Decision from the new measurements

The public Q4_K_S file is **113,971,200 bytes smaller** than the paired Q4_K_M release. A validated host-dependent local server bundle plus one model shows the same regular-file payload saving, or **4.5169%** of the reference regular-file payload. With repacking disabled, Q4_K_S reduced cgroup `memory.peak` in three admitted cold fixed-token pairs and lifetime server peak RSS in all five fresh-server task pairs. The cold pairs used fixed 128/64 synthetic tokens and favored Q4_K_S by a median 0.641 benchmark-child CPU-seconds. The served-task pilot instead used two complete benign development questions per fresh server and found **more** Q4_K_S CPU in every pair, with a median candidate-minus-reference whole-server difference of **+31.674 CPU-seconds**. Under the default repacking policy, a separate three-pair served-task run likewise found more candidate CPU (**+31.850 s median**) and higher process peak RSS (**+97,714,176 B median**). Nearly all of the measured HTTP CPU difference occurred during the candidate's longer ordered-state response in both policies, but this tiny reused workload does not estimate population task cost or quality. A favorable synthetic CPU result therefore cannot be promoted to a whole-task or default-runtime gain. No held-out quality parity result is available.

## Pinned artifacts and machine

Both GGUF files are from one pinned [Bartowski Qwen3-4B-Instruct-2507 revision](https://huggingface.co/bartowski/Qwen_Qwen3-4B-Instruct-2507-GGUF/tree/ae44f08e1392f39c0e474af10c3ff8355c8b6688). The Q4_K_M reference is **2,497,280,736 B**, SHA-256 `2fde00ce69dd4899c70d020845e2638353015bba0fdf161b3eb965f2bca4464e`. Q4_K_S is **2,383,309,536 B**, SHA-256 `952af947c6aabf7b72f7d8e279e76f7bf4b0d12431eb3abb588ef312865622d8`. These are community releases. Their common repository revision and matching tensor topology do not prove that they were exported from one pinned original BF16 checkpoint with the same calibration data.

All new measurements used Linux `6.18.12+kali-amd64`, an Intel Core i7-12700K with eight exposed logical CPUs, four inference threads, CPU only, and pinned [`llama.cpp` b12283](https://github.com/ggml-org/llama.cpp/releases/tag/b12283) commit `f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a`. Each pair held mmap and one declared repack policy fixed. ## Five-block cold cgroup attempt

Here, cold means that the new model inode had no resident pages at launch. It does not establish a cold storage device, a cold OS boot, or uncached runtime libraries. A zero scope `pgscan` delta also does not measure global reclaim outside that scope.

The [cold harness](../scripts/run_cold_cgroup_gguf_pilot.py) made a new ext4 inode for every arm, copied and SHA-256-verified the file, called `fsync` and `POSIX_FADV_DONTNEED`, and required `mincore` to show **zero resident model bytes before launch**. It then launched a 128-prompt/64-generation-token `llama-bench` child inside a fresh systemd user scope. Odd blocks ran reference then candidate and even blocks reversed them. `wait4` supplied benchmark-child user plus system CPU and process high-water RSS. The fresh scope's `memory.peak` supplied the cgroup high water. The [kernel defines `memory.peak`](https://docs.kernel.org/admin-guide/cgroup-v2.html) as the cgroup maximum since creation; it includes charged memory beyond the benchmark process's RSS. File-copy/hash work, the Python monitor, and scope setup are outside child CPU time.

Admission was frozen before running: successful child and scope exit, initial scope isolation, unchanged controls, zero prelaunch model residency, no swap-charge increase, no `pgscan` increase, no OOM or memory-limit event, and a simultaneous mapped-file charge sanity check. The check compared cgroup `file_mapped` increase with model-mapping RSS and required an absolute gap of at most 16 MiB at **every** sample with at least 256 MiB model-mapping RSS and at least 90% of that arm's maximum model-mapping RSS. The [kernel documents](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-ownership) that a shared memory area stays charged to the cgroup that instantiated it, even if another cgroup later uses it. Its [`file_mapped` counter](https://docs.kernel.org/admin-guide/cgroup-v2.html) is cgroup-wide; this check supports charge ownership but is not an inode-level proof or an error bound. The scope and its ancestors had no configured `memory.max` or `memory.high` cap, so this is a high-water measurement with no container memory limit. A new `--continue-on-reject` switch let the five-block sequence finish after failed arms without changing the admission thresholds.

Across the three admitted pairs, the median **absolute** cgroup peak was **2,695,872,512 B** for Q4_K_M and **2,578,358,272 B** for Q4_K_S. Median process peaks were **2,630,471,680 B** and **2,516,590,592 B**, respectively. These are each arm's median; the paired-difference medians in the table are the comparison statistic.

All six arms in the admitted pairs had zero `pgscan`, `pgsteal`, and workingset-refault deltas. Block 1's reference arm had a 3,716-page scan delta, so a candidate-only result cannot form a valid pair. Its candidate arm was accepted by the declared rule despite 168 file-refault events, because that counter was recorded but was not an admission gate. In block 5, both arms had zero scan delta, but neither met the predeclared simultaneous charge-ownership condition across all near-maximum samples. The largest absolute gap was 386,015,232 B for the reference and 17,235,968 B for the candidate, each beyond the 16 MiB threshold. Their numeric peaks remain diagnostic only. This is a **three-pair signal from a five-block attempt**, not a completed five-pair confirmation. The first stopped [cold no-repack attempt](../data/frontier-cpu-qwen3-4b-q4ks-cold-no-repack-cgroup-round2-2026-11-13.json) had one admitted pair and a later reference reclaim rejection; it is reported separately, not pooled with this retry. The [kernel documents `pgscan`](https://docs.kernel.org/admin-guide/cgroup-v2.html) as scanned inactive-list pages, which is why its increase violates the zero-reclaim admission policy.

An independent [first-party CPU image-pipeline cgroup record](https://ai.satyajit.si/articles/qwen-image-2-1#memory-a-ceiling-i-did-not-know-was-there) shows why mapping policy belongs in an admission test. With the same roughly **9.90 GB model-file set** under a **13.36 GiB memory cap**, a non-mmap Q4_K attempt was killed during VAE decoding after two sampling steps; the author observed **10.27 GiB anonymous process memory**, **413 system CPU-seconds**, and millions of cumulative cgroup limit hits. A subsequent mapped two-step run completed, reporting **12.08 GiB sampled cgroup peak** at half-second intervals and **9.9 system CPU-seconds**. The failed and successful attempts are not a completed matched-request comparison, and the sampled cgroup peak is not a kernel high-water counter. The author did not isolate the proposed page-cache mechanism from cache timing. The observation supports treating mmap, file-page charge, and reclaim as part of the CPU deployment policy rather than inferring admission from GGUF size or process RSS alone.

A different [first-party mixed CPU/GPU server record](https://github.com/jeano76/8G_Qwen3-Coder-30B-A3B/blob/134c8a1cfb10f86c5c2db15bcdcafc8b423e35e4/README.md#what-mtp-did-to-the-ceiling) shows how a memory limit can flatten a high-water comparison. Under `MemoryHigh=24G`, its plain and MTP configurations both reported **24.00 GiB `memory.peak`**, but the latter had **269 versus 113 `high` events**, **1.98 versus 0.66 GB** of trimmed file cache, and **101 versus 9** additional major faults over the load. The arms change the model file and CPU/GPU layer placement, so this is not a same-policy inference or CPU-only comparison. Its narrow lesson is methodological: equal peaks at a binding `memory.high` do not imply equal uncapped memory demand; charge, reclaim, and fault counters must accompany a cold admission result. The uncapped scopes in the local pilot avoid this particular ceiling effect, while their predeclared `pgscan` and mapped-file charge checks address other ways a peak can mislead.

A separate [first-party GGUF memory experiment](https://vrammath.com/gguf-file-vs-runtime-memory/) reports a well-scoped process comparison, with its [raw phase records](https://vrammath.com/measurements/gguf-b7031-m1pro.json). From one pinned SmolLM2-135M release, BF16 and Q4_K_M files occupy **270,885,440 and 101,016,128 B**. On an Apple M1 Pro, three fresh CPU-mmap processes per file used the same two-thread, 512-context policy and completed a 22-token prompt plus 16 decode calls. Median lifetime process peak through the first decode was **323.45 versus 162.47 MiB**, a smaller RAM reduction than the file-byte reduction. The source explicitly leaves OS file-cache coldness unknown; its `getrusage` peak includes load and initialization, but it is not cgroup high water. Its CPU arm also initializes a small Metal resource. The experiment provides no complete-request CPU-seconds, quality comparison, or installed runtime-bundle total. It corroborates keeping file bytes, process RSS, and cgroup charges as separate columns, without supplying a cold-admission result.

A [first-party loader experiment](https://www.bigiron.cc/guides/model-loading-uses-double-the-ram-safetensors-mmap-and-the-fix) illustrates a sharp distinction between process RSS and admission. For one roughly **4 GB** checkpoint, its `load_file()` read-through and ordinary `torch.load()` runs each reached about **5.3 GB** sampled process RSS in unrestricted fresh processes, yet the mapped `load_file()` run completed under a **2.5 GB** no-swap cgroup cap while the ordinary `torch.load()` run was killed. The author dropped host page caches before each load and explains that a read-through verification loop itself temporarily allocated about **1.2 GB**; the 5.3 GB peaks therefore do not represent the minimum resident weight requirement. The article names PyTorch 2.15.0 CPU, transformers 5.22.1, and safetensors 0.8.0, but provides no raw log, pinned code revision, inference request, or cgroup high-water record. It does not quantify a GGUF task result, but it shows why equal unrestricted process peaks cannot substitute for an admitted capped run with file and anonymous charge accounted separately.

## Complete served-task CPU and peak RSS

The [served-task harness](../scripts/run_frontier_cpu_served_task_pilot.py) started a fresh `llama-server` for each arm, with mmap, CPU only, `--no-repack`, four inference threads, one parallel slot, 2,048-token context, 512-token batch and microbatch, and the server's default startup warmup. It served the same reused arithmetic and ordered-state development questions from the frozen [manifest](../data/generated-quality-dev-v4-2026-11-12.json), SHA-256 `55bd65706fc9a907f7e469cf2a675ba62e5474d44f3a810a23c69ef94de1c44b`. Odd blocks used reference first and arithmetic first; even blocks reversed both orders. Each response used temperature zero and a 512-token output cap. All ten servers became healthy, served both requests, and stopped normally. The server reported 52 cached prompt tokens on every second request in both arms, so each pair measures a two-request session with the same prefix-reuse policy, not two independently uncached requests. The host model cache was not evicted, and prelaunch model-page residency was not checked, so these fresh-server trials do not establish a cold-cache condition.

The harness read the server thread group's `/proc/PID/stat` `utime+stime` before and after each complete HTTP request, then used `wait4` for **whole-server CPU through load, warmup, both requests, and exit**. Linux [documents the process CPU fields](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html). `wait4` peak RSS covers the server lifetime. The denominator excludes Python client CPU, operating-system baseline work, model download, and model-file copying. HTTP CPU intervals may include incidental server housekeeping and have 0.01-second tick resolution. The raw host snapshot records CPU affinity and the root cgroup's effective CPU set but does not preserve the served process's full cgroup ancestry. The harness did not lock CPU frequency or isolate the host from all background processes; paired order reversal limits but cannot remove those effects.

Across the five fresh-server served pairs, the median **absolute** whole-server process peak was **2,950,946,816 B** for Q4_K_M and **2,835,845,120 B** for Q4_K_S. Median whole-server CPU was **331.501 s** and **382.306 s**, respectively. The paired CPU difference remains the relevant comparison because each block shares task order and nearby host conditions.

The ordered-state response finished at 398 tokens for the reference and 493 for Q4_K_S in every block. Both visible answers were correct on that one reused item. Arithmetic outputs varied with order; the candidate used 18 fewer tokens in odd blocks and the same number in even blocks. Each response ended with `finish_reason=stop`. The ordered-state request added 30.43 to 81.42 server CPU-seconds across the five pairs; arithmetic ranged from 15.05 fewer to 0.74 more CPU-seconds. Dividing each state request's complete CPU by its own completion count makes Q4_K_S look 2.7% to 8.7% cheaper per token in four blocks, but 11.4% dearer in the remaining block. At 493 versus 398 completion tokens, the candidate's complete-request CPU per completion token would have to be at most 398/493, or 80.73%, of the reference value merely to break even in total request CPU. None of the five pairs reached that arithmetic threshold. Its complete state-request CPU is 13.1% to 38.0% higher in all five blocks. These ratios include prefill and are not isolated decode-kernel timings. The whole-server CPU difference outside the two measured HTTP intervals ranged from -0.146 to +0.504 seconds, so the observed increase was concentrated in that 95-token-longer state response. These are two reused development tasks, including one state instance, so they do **not** estimate population task CPU or quality. A complete task comparison should retain output length and failures as outcomes rather than forcing equal tokens after seeing the result.

The prior [warm synthetic pilot](qwen3-4b-q4ks-resource-pilot-2026-11-13.md) found no-repack Q4_K_S ahead on 128/64 fixed-token CPU and RSS in all five pairs. Its separate default-repack arms had median candidate-minus-reference process RSS **+104,185,856 B** despite a smaller file, while fixed-token child CPU favored the candidate by **0.646 s**. The pinned [server option reference](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/tools/server/README.md#L249-L270) states that weight repacking is enabled by default and distinguishes `--no-repack`. Those policies are distinct comparisons. The cold cgroup and five-pair served trials above both disabled repacking; the next served trial used the server default.

## Complete bytes and packed-weight execution

The measured, complete GGUF reduction is **4.5638%**. The served-run census found 51 regular files and ten symbolic links in the local pinned build directory. The regular files total **58,674,830 B**. Counting the whole directory plus one GGUF yields **2,555,955,566 B** for Q4_K_M and **2,441,984,366 B** for Q4_K_S, a **4.4590%** saving. This is an intentionally broad installed-directory denominator: it includes unused utilities and CPU variants and excludes host operating-system shared libraries, package metadata, and any application outside this directory. A live reference server mapped nine local regular runtime files totaling **25,934,136 B**; the [mapping inventory](../data/frontier-cpu-qwen3-4b-observed-runtime-map-2026-11-13.json) is an observed lower bound.

The [reduced-bundle validation](../data/frontier-cpu-qwen3-4b-minimal-bundle-2026-11-13.json) then copied those nine runtime files plus the 1,078 B `LICENSE` and recreated ten relative symbolic links in an isolated temporary directory. The ten regular files total **25,935,214 B**. It linked each pinned model into that directory without a second physical model copy, launched the copied server with CPU-only mmap and `--no-repack`, and exercised `/health`, `/v1/models`, and one benign `/v1/chat/completions` request. Both arms returned `finish_reason=stop`, and their server processes exited normally. Each process mapped all nine expected local runtime files from the reduced directory, with no file mapped from the original build directory. One model plus this tested local bundle has **2,523,215,950 B** of regular-file payload for Q4_K_M or **2,409,244,750 B** for Q4_K_S, a **4.5169%** saving on that denominator. This byte ledger excludes symlink target strings, directory and inode metadata, allocation rounding, archive headers, and the host library payload discussed next. The [validation script](../scripts/run_frontier_cpu_minimal_bundle_pilot.py) records materialization, checksums, commands, endpoint responses, and process maps. This is a tested host-dependent bundle for the stated endpoint path, not proof of a portable minimum or full server feature coverage.

The same [bundle record](../data/frontier-cpu-qwen3-4b-minimal-bundle-2026-11-13.json) lists **ten additional regular files mapped from the host's `/usr/lib`**, totaling **15,139,000 B** in each arm, including the dynamic loader, C/C++ runtimes, OpenSSL, zlib, and zstd. If these exact host dependencies were charged to an otherwise empty deployment, the observed-file ledger would be **2,538,354,950 B** for Q4_K_M and **2,424,383,750 B** for Q4_K_S, making the same 113,971,200 B difference **4.4900%** of the reference. This is an accounting sensitivity, not a validated portable package: shared base-system files may already be present, and file mappings do not enumerate every service feature or every needed non-mapped configuration file.

A [Microsoft first-party container cold-start experiment](https://techcommunity.microsoft.com/blog/linuxandopensourceblog/dissecting-llm-container-cold-start-where-the-time-actually-goes/4508831) supplies a concrete image-level denominator from a different system. Its AIKit llama.cpp image with Llama 3.1 8B Q4_K_M on an A100 host is **8.7 GB uncompressed**: **4.9 GB** of GGUF weights and about **3.8 GB** of CUDA and system layers. The published gzip image is **6.6 GB**, with the GGUF layer reporting about a 1.00-times gzip ratio. Thus this image's weight file is only **56%** of uncompressed deployed bytes; a weight-only percentage would overstate whole-image saving if the other layers stayed fixed. The authors reset containerd state and drop kernel page caches for each cold run and report a three-run overlayfs comparison: gzip image **138.8 s** versus uncompressed image **102.4 s** to the first response, with pull time **88.3 versus 56.3 s**. These are GPU-backed startup and wall-time measurements under different image compression, not a matched quantization pair, CPU-seconds, or a cgroup-memory result. They show that a complete-image census and cold pull policy can materially change the deployment decision without yielding a transferable percentage for this local host-dependent bundle.

A first-party [CPU image-pipeline file ledger](https://ai.satyajit.si/articles/qwen-image-2-1#the-files) shows that even complete weight files for one named component can be a misleading deployment denominator. On the author's four-core Intel Xeon with one pinned `stable-diffusion.cpp` build, changing only the Qwen-Image-2.1 denoiser from Q4_K to Q2_K shrinks that file from **4,197,494,816 to 2,561,716,256 B**, a **39.0%** saving. The required denoiser, unchanged text encoder, and unchanged VAE together shrink from **9,900,789,304 to 8,265,010,744 B**, or **16.5%**. In the author's single matched 512-pixel, 20-step, mmap CPU comparison, [complete image wall time](https://ai.satyajit.si/articles/qwen-image-2-1#where-the-wall-clock-goes) is **1,822.84 versus 1,656.77 s**, and process peak RSS is **11.40 versus 9.86 GiB**. Its [same-weight memory-policy incident](https://ai.satyajit.si/articles/qwen-image-2-1#memory-a-ceiling-i-did-not-know-was-there) is a separate admission warning: a Q4_K run without mmap was killed at a **13.36 GiB** cgroup cap during VAE decode, while a two-step run with mmap completed at a **12.08 GiB** sampled cgroup peak. Cache coldness and exact cgroup high water are not established in that incident. The matched quantization comparison is one prompt and seed; it has no measured user-plus-system CPU-seconds, admitted cold cgroup high water, or executable/library byte census. Its useful lesson for the present ledger is to count every required model component before calling a changed weight file the deployable saving.

A separate [first-party CPU-only container deployment](https://selfhostmap.com/apps/llama-cpp/#tested-by-selfhostmap) gives a smaller-model example of the same denominator issue. On an eight-vCPU Xeon with the official `llama.cpp:server` Docker image, the operator reports a **310 MB compressed image download**, **1.20 GB unpacked image**, and a separately mounted **491 MB Qwen2.5-0.5B Q4_K_M GGUF**. The image explicitly contains no model. On those rounded numbers, the image plus model occupies about **1.69 GB** before any separately stored data, with the GGUF accounting for only about **29%**. Its [methodology](https://selfhostmap.com/methodology/#our-deployment-tests) says data-folder size after this test was not measured and RAM was sampled from `docker stats` every two to three seconds with inactive page cache excluded. The test page itself notes that the model's cache state changed its reported idle RAM. Accordingly, its **489 MiB highest working `docker stats` reading** is neither a cold cgroup high water nor a basis for a complete installed-byte or CPU-seconds comparison. The rounded CPU-image account strengthens the need to count runtime layers, but it does not transfer to the local stripped host-dependent bundle.

The [MNN-Pocket-0.3B technical report](https://arxiv.org/html/2611.12311v2) calls **173 MB** an INT4 "deployment footprint," but its Table 3 labels the figure **MNN inference file size**. The stated file contents are weights, tokenizer, computation graph, and inference configuration; the report does not include an installed MNN engine or application binary in that byte count. Its **228 MB** peak is Metal resident memory above a pre-load baseline on an iPad Pro M5 at 512-token context, not CPU process RSS or cold cgroup peak. The report also gives CPU prefill and decode throughput with four threads, one warmup, and five runs, but measures the two phases independently from an empty KV cache. It supplies no complete-request CPU-seconds comparison. This is a concrete example of why "deployment footprint" and "peak memory" need their underlying boundaries before they can be compared with the local installed-byte and cold-cgroup measurements.

A newer [first-party browser delivery study](https://arxiv.org/html/2611.04638v1) clarifies a different denominator. Its offline lossless reconstruction of a **4.36 GiB** Qwen2.5-7B Q4_K_M package from another publisher's package saves at least **76.6% of network traffic** across six directions, relative to a level-3 zstd full download. A separate 240-run browser experiment uses four smaller model pairs; each run starts with a same-model, same-quantization public anchor **already stored** by the browser and excludes that anchor's download from measured traffic. The result is still the publisher's complete target file. The authors report a **93.7 MiB** maximum resident reconstruction process in repeated tests over six pairs covering all four model families, plus separately stored manifests, catalogs, and residuals. This can reduce incremental transfer under an existing-anchor policy, but neither the percentage nor the reconstruction memory is a reduction in the installed target's GGUF bytes, complete local bundle, or inference CPU-seconds. Counting the anchor and reconstruction CPU would be necessary for a from-scratch deployment comparison.

The earlier [ZipNN lossless-compression study](https://arxiv.org/html/2411.05239) makes the quantized-format limitation explicit. It restores the original file after decompression, and its authors report that the tested GGUF-quantized models did not compress at all, whereas some tested GPTQ and AWQ models compressed to 85% to 91% of their original sizes. The paper does not identify a Q4_K_M versus Q4_K_S pair or a CPU inference comparison for this claim. Its reported roughly three-second load from a compressed 16 GB BF16 Granite model concerns a high-throughput storage system and GPU serving. Consequently, its BF16 storage savings and load timing cannot be added to the local GGUF byte reduction or credited as a reduction in CPU inference RAM or complete-request CPU-seconds.

That ZipNN result is specific to its codec and sample, not a general impossibility for quantized GGUF. In a pinned [first-party tenz/foldz report](https://github.com/nsiddiqui248/tenz/blob/d17dff7558805e4475644aab6f0c15d7267a14e9/README.md#L185-L261), the author says a GGUF-aware lossless codec compressed nine public Q4_K_M files from **17,094 to 15,614 MiB** in aggregate (**8.66%**) with byte-identical round trips. On one Qwen3.5-2B Q4_K_M file, the reported reduction was **8.43%** with foldz 0.12 versus **2.07%** for `zstd -19 --long=27`; the author reports phone wall times, but the [benchmark script](https://github.com/nsiddiqui248/tenz/blob/d17dff7558805e4475644aab6f0c15d7267a14e9/bench.sh) does not collect process CPU-seconds or cgroup high water. These are unreplicated author measurements on different checkpoints, with no per-file raw log or hash manifest in that repository. The codec reconstructs the ordinary GGUF before inference. It can therefore change compressed transfer or archive bytes under its tested policy, while a usable installed model still needs the full restored GGUF and the decoder adds startup work. No direct inference from its compressed format or complete served-task CPU saving has been shown.

The [tensor descriptor audit](../data/frontier-cpu-qwen3-4b-q4ks-tensor-topology-2026-11-13.json) found identical names and shapes for all 398 tensors and 36 changed type descriptors. Eight attention-value/FFN-down tensors in layers 0 through 3 change Q6_K to Q5_K, saving **3,655,680 B per layer** and **14,622,720 B** total. Another 28 in layers 6, 9, 12, 15, 18, 21, 24, 27, 30, and 31 through 35 change Q6_K to Q4_K, saving **7,096,320 B per layer** and **99,348,480 B** total. The two subtotals equal the observed complete-file difference of **113,971,200 B**. Across all changed layers, FFN-down accounts for **103,116,800 B**, or **90.48%** of the saving; attention-value accounts for **10,854,400 B**. This identifies where packed bytes changed, not which tensor can safely lose precision. The tied Q6_K embedding stays unchanged at **319,065,600 B**. Pure format arithmetic gives **51,658,240 B** of additional payload saving for Q6_K to Q5_K on that one tied matrix; changing the eight early-layer Q5_K matrices to Q4_K would save another **13,762,560 B**. Neither conversion was built or tested here. The [original checkpoint config](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507/blob/1b4199c4f36b0cef378bfb12390c18780c18af4c/config.json) declares tied embeddings, and the [local topology audit](frontier-cpu-static-topology-audit-2026-11-13.md) found no separate output weight in this GGUF; the [pinned quantizer warns](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/tools/quantize/README.md) that requantizing can severely reduce quality. These figures are byte headroom rather than credible task-level wins. Descriptor equality does not prove identical underlying source weights.


An independent [first-party mobile CPU memory profile](https://zenteiq.ai/research/blog/inferencing-dhir-on-edge-devices/) illustrates why a tied matrix's GGUF bytes do not directly predict loaded process RAM. On a Snapdragon 7s Gen 4 with `llama.cpp`, the authors report a **1.21 GB** Q4_0 Dhīr 2B weight file but **2.04 GB** maximum resident memory at a 4,096-token context and **3.47 GB** at 16,384 tokens, with weights read into memory rather than mapped. Their model has a tied embedding, and they attribute roughly **0.2 GB** above their weights-plus-KV-plus-buffer estimate to a second Arm-backend copy of that matrix. Each peak is one `llama-batched-bench` run at a filled context. This is an Arm, no-mmap process peak for a different model, not evidence of a second tied-embedding copy on the local x86 host or of a cold cgroup peak. It reinforces the need to measure resident copies after any embedding-precision change.

The pinned [GGML CPU type table](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/ggml/src/ggml-cpu/ggml-cpu.c#L320-L345) routes Q4_K, Q5_K, and Q6_K to quantized weight by Q8_K vector dot products. The [matrix-multiply path](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/ggml/src/ggml-cpu/ggml-cpu.c#L1282-L1289) selects that trait for the weight tensor and [prepares the matching Q8_K input representation](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/ggml/src/ggml-cpu/ggml-cpu.c#L1340-L1389). This supports direct packed-weight execution for those operations under the tested no-repack CPU path. It does not prove that every kernel and intermediate stays quantized. The live [mapping inventory](../data/frontier-cpu-qwen3-4b-observed-runtime-map-2026-11-13.json) shows `libggml-cpu-haswell.so` loaded. The pinned [repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/ggml/src/ggml-cpu/repack.cpp#L5011-L5075) offers an AVX2 Q4_K route on this host, whereas the Q5_K and Q6_K routes shown there are Arm NEON guarded. The [CPU_REPACK buffer path](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/ggml/src/ggml-cpu/repack.cpp#L5148-L5185) repacks tensor data into an allocated CPU buffer. The Q4_K payload increase between the two files is **216,760,320 B**, and subtracting the model-file saving leaves **102,789,120 B**, near the earlier default-repack fixed-token median RSS increase of **104,185,856 B** and the new complete-task median of **97,714,176 B**. This arithmetic and source path are consistent with an additional packed copy. No per-tensor allocation trace has established the exact source of those RSS differences.

A separate [first-party same-file CPU loader study](https://hrletsgo.me/en/documents/447) shows why checking the *executed representation* matters as much as checking the download. It pins one **491,400,032 B** Qwen2.5-0.5B Q4_K_M GGUF and reports **568.04 MiB** isolated-process peak RSS with a four-thread `llama.cpp` server versus **3,786.91 MiB** with a four-thread Transformers CPU process. The latter loader expands **630,167,424 parameters** into **2,520,669,696 B of FP32 weights** before generation; the study's tensor census finds that only **6.06%** of the nominal Q4_K_M file's tensor payload is actually Q4_K. The two runtimes have different execution stacks and request-timing boundaries, so their wall-time totals are not a matched CPU-speed result. Their outputs also [diverged at generated token 20](https://hrletsgo.me/en/documents/447#where-did-the-outputs-diverge-with-the-same-input) despite matching input IDs, and their suppressed termination-token sets differed. Thus the comparison does not establish behavioral parity. The observation supports inspecting loaded tensor types and the kernel selection path before treating a small GGUF file as a small resident model. It is neither a cold cgroup comparison nor a complete bundle census.

An [experimental `ik_llama.cpp` AMX operator record](https://github.com/RC-CHN/ik_llama.cpp/blob/093dc823d7a53f80ee4476b5ba295c0c9a6b66d9/docs/development/xeon-max-amx-hbm-benchmark.md#pp512-acceptance-result) supplies a stronger example of a quantized file requiring much more resident memory under one CPU policy. On a 52-core Xeon Max with HBM, its **16.806 GB Q4_K_M file** is run with runtime repacking and a 6,144 MiB expanded Q4_K cache budget. The reported persistent AMX prepack is **25.04 GiB**, and GNU `time` records **41.49 GiB process peak RSS** during ten PP512 repetitions inside a 46 GiB no-swap cgroup. The first sample includes prepack construction and runs at 51.45 tokens/s; nine later samples average 222.75 tokens/s. A separate [dialogue smoke check](https://github.com/RC-CHN/ik_llama.cpp/blob/093dc823d7a53f80ee4476b5ba295c0c9a6b66d9/docs/development/xeon-max-amx-hbm-benchmark.md#functional-dialogue-smoke-test) on the same file and backend failed under a 30 GiB cgroup after constructing the compact prepack and succeeded under 40 GiB with **34.22 GiB process peak RSS**. These are self-published operator experiments for a different model, CPU and repack path. Their first-sample label does not establish cold host-page admission, and the record gives no cgroup high water, complete-request CPU-seconds or runtime-bundle bytes. It does show that a smaller packed file cannot by itself certify a memory cap when a fast CPU path materializes a large repack cache.

An independent [first-party LFM2.5 CPU kernel record](https://github.com/MIT-RLX/rlx-models/blob/5e7175a202ed00f802ab57de84a8ca066f8f7363/CHANGELOG.md#L2921-L2972) illustrates a different packed-execution choice. For its **1.67 GB Q4_K checkpoint**, the exact cached-F32 decode path reaches **14.45 GB process peak RSS**, while a fused path that reads packed weights reaches **5.17 GB**, stable within 0.02 GB across three interleaved rounds. On the 2.6B model, that fused path improves decode throughput by **11.1%** relative to the exact default in an interleaved min-of-five comparison, but only **92.2%** of tokens agree with the F32 prefill reference on eight random-ID prompts of eight tokens each. The authors removed that path as their default. Their [on-the-fly exact Q4_K GEMV](https://github.com/MIT-RLX/rlx-models/blob/5e7175a202ed00f802ab57de84a8ca066f8f7363/CHANGELOG.md#L2974-L3000) runs **5.1 tokens/s** against **9.0** for the cached-F32 path and **1.8** for repeated full dequantization on the 2.6B model; its RSS effect is explicitly unresolved. This self-reported, different-runtime experiment shows that bypassing a large dequantized cache can be a real RAM option with a speed or numerical tradeoff. It supplies neither complete-request CPU seconds nor cold cgroup high water, so none of its throughput or process-RSS figures can be added to the local joint result.

A separate [first-party tied-head quantization sweep](https://inboxpraveen.github.io/blogs/blog-1.html#the-tied-lm-head) makes the proposed embedding change more concrete without validating it for this 4B model. Its author built Qwen3-0.6B variants from one BF16 GGUF with one `llama.cpp` b10941 quantizer and importance matrix on a Windows i7-14650HX laptop. The [published ledger](https://github.com/inboxpraveen/ggml-inference-lab/blob/6ef1c7df2a9b5bc31b0aeb2bed75afa820305769/results/kld_table.json) lists **639,447,488 B** for a Q8_0 GGUF and **601,767,648 B** with only its tied output/embedding matrix changed to Q6_K, a **37,679,840 B** or **5.89%** complete-file saving. On about 51,000 scored WikiText positions, mean KL divergence from BF16 rises **0.00274 to 0.003843**, and top-token agreement falls **97.027% to 96.304%**. The author's quiet-window fixed-token CPU decode comparison reports **56.94 versus 59.55 tokens/s**, while other [raw runs](https://github.com/inboxpraveen/ggml-inference-lab/blob/6ef1c7df2a9b5bc31b0aeb2bed75afa820305769/results/bench.jsonl) vary under background load. This is an exact file-byte and logit-proxy result for a smaller, tied model. It has no task-level quality, complete-request CPU seconds, cold peak RAM, or runtime-bundle measurement. It motivates a controlled embedding sweep, but it cannot convert the local Q6_K embedding's arithmetic headroom into an efficiency claim.

Another [first-party CPU-only head-precision comparison](https://github.com/deepgrove-ai/llama.cpp/blob/7e30f3adb34b444c3527f94c3343612d71b47d0d/README.md#L63-L75) reports a larger isolated decode gain for a different model. With the same TQ2_0 matrix weights in Maple Preview, changing the output head from F16 to Q4_K reduces the two [published GGUF file sizes](https://huggingface.co/api/models/deepgrove/maple-preview-GGUF/tree/f5466f918e0c50cdb9d4d47a6f35813509a42a30?recursive=false&expand=false) from **6,349,082,144 to 5,901,782,560 B**, a **447,299,584 B (7.05%)** saving. The repository reports M5 Pro CPU-only `llama-bench`, 16 threads, three repetitions at separate 512-prompt and 128-generation-token shapes: generation rises from **169.81 to 252.74 tokens/s** while prompt throughput falls from **618.57 to 610.48 tokens/s**. The output-head change is therefore a credible layer-specific throughput direction for this model and host, with the same matrix-weight label in both arms. The repository publishes aggregate rates but no per-run CPU-time logs, response-length or task-quality results, cold RAM high water, or installed runtime-bundle bytes. A 1.49-times fixed-token generation rate cannot be treated as a 1.49-times complete-request CPU saving or transferred to this Qwen3-4B comparison.

## Which runtime changes are credible

The observed RAM lead occurred under a **fixed no-repack policy**. The default policy reversed its peak RSS direction, and both policies raised CPU on the reused complete tasks. Neither policy has held-out quality evidence. Selective precision changes are already part of the pinned [Q4_K_M/Q4_K_S quantizer selection logic](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/src/llama-quant.cpp#L613-L683); a changed layer map alone is not a new compression method. The source's [`use_more_bits` rule](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/src/llama-quant.cpp#L471-L473) is a fixed position heuristic for early, late, and every-third interior layer. Its match to this file's changed-layer pattern is an explanation of the export layout, not evidence that those layers are safe or optimal for this task. The pinned [`llama-quantize` options](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/tools/quantize/README.md#L211-L249) include regex `--tensor-type` overrides and a separate `--token-embedding-type`, so a controlled layer or tied-embedding sweep can use the existing exporter. That experiment requires one pinned high-precision source GGUF, the same calibration input and export settings for both arms, and a sealed quality check. No such custom export was built here; requantizing these already-quantized downloads would introduce the quality risk identified by the quantizer's own warning.

Moving CPU packing offline could reduce startup copying under a default packed path. Google's [XNNPack cache design](https://developers.googleblog.com/streamlining-llm-inference-at-the-edge-with-tflite/) stores packed weights in a file and maps them on later loads; it documents the peak-memory cost of in-process repacking. The merged [ik_llama.cpp offline row-interleaved conversion](https://github.com/ikawrakow/ik_llama.cpp/pull/272) and [tensor-name selection option](https://github.com/ikawrakow/ik_llama.cpp/pull/274) are closer GGUF prior art. The fork author explicitly frames the converted format as CPU-only and intended for mmap loading. Its formats and kernels are not shown to be equivalent to this pinned mainline build, and none of these sources demonstrates a Q4_K_M-relative win on this host's complete installed bytes, cold cgroup high water, whole-task CPU, and sealed quality. If an offline packed cache is retained alongside its source GGUF, both byte counts belong in deployment total. A single packed file that can be loaded directly would need an independently verified load and quality test.

[DynaLM's first-party CPU experiment ledger, pinned at `2aeda877`](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/docs/perf/cpu-experiments.md#e1--drop-the-file-pages-of-packed-weights-kept), gives a narrower alternative to retaining both a mapped GGUF page and its packed copy in RSS. Its [CPU packing path](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/dynacore/cpu/cpu_device.cpp#L297-L313) calls [`release_file_pages`](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/dynacore/src/memory/mapped_file.cpp#L156-L177) after copying a tensor into the representation used by its Q4_K/Q6_K kernels. In two back-to-back M4 Pro development runs of a 1.5B model with eight users and 512-token prompts, the authors report process RSS **2,402 to 1,471 MiB** with source-page release, and after-load RSS **2,090 to 1,159 MiB**; output rate remains **44.8 to 45.2 tokens/s** across the two arms. The mapped source file remains required and can fault back in, so this is an RSS mechanism, not a complete-file saving. A later [five-round controlled CPU suite](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/docs/perf/cpu-experiments.md#controlled-cpu-suite-v1-run-with-e10-2026-10-25-17051937) uses the same Qwen3-4B Q4_K_M GGUF in DynaLM and llama.cpp with eight threads, 8 slots, f16 KV, 4,096-token context per slot and 128 forced output tokens. It reports **3,944 versus 11,403 MiB** median peak server RSS, respectively, under AC power. Its [fixed suite](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/docs/perf/cpu-suite-v1.md#memory-gate-b) attributes much of the gap to DynaLM's demand-grown KV pool versus llama.cpp's up-front full-pool allocation; the [harness](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/tools/bench/baseline.sh#L132-L200) confirms CPU-only llama.cpp with default compiled repacking and one warm server per round. Its 1.5B long-prompt whole-request p50 is **1.78 times faster**, but that is a different model and wall latency, not CPU-seconds. The raw suite directory named in the ledger is not present in the pinned repository tree, so its five-round medians cannot be independently recalculated from published run records. None of these measurements gives a fresh-host-page-cache cgroup high-water pair, a complete-request CPU-seconds pair, or a task-quality result. Its Apple runtime result cannot be inserted into this host's cold-cgroup or default-repack measurements. A separate [DynaLM Zen 2 comparison](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/docs/perf/x86-zen2-2026-11.md#avx2-decode-kernels) reports Qwen3-4B Q4_K_M token gaps of **93.7 ms** after AVX2 kernel changes versus **123.4 ms** before and **109.5 ms** for llama.cpp on the same four-vCPU host. Its [archived logs](https://github.com/dynalm-project/dynalm/blob/2aeda8774a16786c8d0cd932a3424f84856c9bb4/docs/perf/data/x86-zen2-2026-11-03/logs.tgz) support the token-gap values, but do not provide whole-request CPU or a full installed-byte census. This supports kernel work as a plausible CPU research path without establishing the joint gate.

An [open upstream llama.cpp proposal](https://github.com/ggml-org/llama.cpp/pull/24156) targets the same mmap-plus-CPU_REPACK residency problem. Its author reports after-load RSS falling from **31,483 to 18,160 MiB** for Qwen3-30B-A3B Q4_K_M on a dual-socket EPYC host, with unchanged pp512/tg128 speed in that test. The proposed Linux `madvise(MADV_DONTNEED)` call runs **after loading**. The author explicitly reports that **peak RSS during load is unchanged** and that the discarded pages remain in the file cache. Thus even if the proposed change is accepted, those after-load RSS numbers do not demonstrate a lower cold admission peak, a lower cgroup memory high water, or fewer deployable bytes. The PR remains unmerged as of this review, is on a different runtime revision, and does not report complete-request CPU seconds. An earlier [upstream issue report](https://github.com/ggml-org/llama.cpp/issues/16761) gives repack versus no-repack RSS on a different model, but was marked `bug-unconfirmed` and later closed as stale; it is corroborating motivation, not validation of this host's paired result.

A [peer-reviewed stage-aware CPU study](https://www.mdpi.com/2076-3417/16/20/10134) shows why implementation savings need a matched denominator. On Phytium FT-1500A/16 with an FP32 Llama-3.2-1B checkpoint, its two-thread self-kernel change reduces measured decode time per output token from **2,471.1 to 1,489.5 ms**. At the same two-thread setting, a tuned BLAS GEMV path reaches **948.8 ms**; with all 16 cores it reaches **141.9 ms**. The paper's **17.2-times** headline compares that final 16-core result with a serial baseline, so it combines a kernel change and additional cores. Its component timers attribute about 99.4% of decode time to matrix-vector multiplication in that setup, and show parallel softmax at two threads regressing to **0.80 times** its serial speed. This is credible evidence for selective CPU kernel work, but it uses FP32 weights and reports token latency rather than complete-request CPU-seconds, cold RAM high water, or installed bytes. It does not predict a saving from further quantizing the local Q4_K_M file.

A [first-party Raspberry Pi 5 same-binary wait-policy test](https://github.com/localai-org/vllm.cpp/blob/82c81b376d1c13de28d2c7fd941cbd4f69d97186/docs/bench-evidence/rpi5-a76-output-wait-c1-main-20260811.md#pmu-result) supplies an unusually clear whole-process CPU counterexample. On four Cortex-A76 cores, the author alternated three separate processes per arm with the same SHA-256-verified Qwen3.5-2B Q8_K_XL GGUF, 17 actual input tokens, 64 output tokens, and identical output-token-file hashes. At four compute threads, a concurrency-one blocking wait reduced median `perf stat` task-clock from **224.842 to 104.801 CPU-s** and complete benchmark E2E wall time from **56.122 to 26.093 s**, with process peaks **2,978,704 versus 2,978,464 KiB** for polling and blocking. At three compute threads, task-clock still fell **108.441 to 81.301 CPU-s**, while E2E wall time was essentially unchanged (**26.999 versus 26.934 s**). These task-clock totals wrap each whole benchmark process, including startup, and are not isolated decode-kernel timings. The report notes a **13.33 to 15.96%** spread in the four-thread polling arm across its performance axes, and keeps blocking limited to a concurrency-one diagnostic. Its 98-file raw archive is described as retained on the author's private Pi, not publicly available for independent recomputation. The test changes a runtime wait policy, not model bytes; it has no cold cgroup high-water pair or installed-bundle census. It demonstrates that CPU-seconds can change substantially with unchanged packed weights and exact generated tokens, but does not provide a transferable compression saving or a served-task quality result.

A separate [first-party CPU KV-cache comparison](https://www.bigiron.cc/guides/kv-cache-quantization-q8-q4-and-turboquant-measured) illustrates a memory and prefill tradeoff under the same Q4_K_M weight file. The author used mainline llama.cpp commit `29c720e` on a six-vCPU Debian 13 VM and reports pre-prompt `RssAnon` at a 32,768-token context falling from **4,300 MB** with f16 K/V to **2,620 MB** with q8_0 K/V. Yet on a 7,421-token prompt the server's reported first-prompt processing rose from **82 to 214 s**. q4_0 K/V lowered pre-prompt `RssAnon` to **1,724 MB**, while a single 16-question numeric lookup trial at that prompt length fell from **12** correct with f16 K/V to **3** correct. The article includes its request script and commands, but no preserved raw run log or repetitions sufficient to estimate variance. It changes KV storage, not deployable model bytes; its pre-prompt anonymous RSS is neither process peak nor cold cgroup high water, and its timings are not CPU-seconds. The result is a reason to measure the same complete requests after any cache-compression change, not a transferable estimate for the local 4B server.

A [same-family CPU measurement study](https://arxiv.org/html/2609.08307v1) provides an independent negative control for using decode speed as complete-workload cost. In its [first-party CSV pinned at repository commit `7214627`](https://raw.githubusercontent.com/UCY-LINC-LAB/Edge-LLM-Inference-Benchmark/7214627eaf57244f38b4998ec40b18b748619ff0/data/results.csv), Llama-3.2-3B-Instruct F16 on an Intel Xeon Gold 6230 CPU has a rounded 6.43 GB model file, 197.83 ms per generated token, 6.71 ms prefill per input token, and 2,332.56 s for the workload. Q4_K_M has a rounded 2.02 GB file and faster 163.28 ms decode, yet slower 8.16 ms prefill and 2,558.80 s total, or 9.7% more workload wall time. The paper says it used 1,531 sequential MMLU multiple-choice requests, ten warmup prompts per model, and five repeated trials; its recorded interval begins just before each request and ends at complete response. Thus the published duration concerns a warmed, short-answer request mix, not model download or load, user-plus-system CPU-seconds, cold peak RAM, exact installed bytes, or dependent-step quality. The result is consistent with a workload break-even between prefill and decode, but its serving stack and model differ from the local Qwen3 comparison.

A [first-party WSL2 quantization comparison pinned at `d174d37`](https://github.com/200lz/llm-inference-optimization-lab/blob/d174d37b7625aa3f3209b6ab592b679853058b54/docs/results/quantization_comparison.md) offers a same-model, same-runtime counterexample to optimizing only decode. Three Qwen2.5-0.5B-Instruct GGUF files from one source revision measure **1,266,425,696 B F16**, **675,710,816 B Q8_0**, and **491,400,032 B Q4_K_M**. On an AMD Ryzen 7 5800H using CPU-only llama.cpp `e3546c7` with mmap and default CPU repacking, the five-run 1,024-prompt/64-generation-token, four-thread case reports Q4_K_M prompt throughput **195.502** versus F16 **304.158 tokens/s**, but Q4_K_M generation **62.438** versus F16 **30.560 tokens/s**. Median complete `llama-bench` invocation wall time is **15.118** versus **11.199 s**. A [separate three-run `perf stat` profile](https://github.com/200lz/llm-inference-optimization-lab/blob/d174d37b7625aa3f3209b6ab592b679853058b54/docs/results/cpu_profiling.md) for the same 1,024/64 shape reports Q4_K_M **1,134.167** versus F16 **723.572 billion** scaled whole-invocation instructions, with a 1.402-times elapsed ratio. The benchmark performs separate fixed-token prompt and generation tests inside each invocation, so these numbers are neither one served request nor task CPU-seconds; the profile's WSL2 virtualized, multiplexed PMU counters also have limited absolute precision. The study did not record peak RSS for the comparison or a complete runtime bundle. Its result nevertheless shows how a much smaller file and faster decode can coincide with a slower combined CPU benchmark under one declared repack policy. The same group's [20-pair CPU kernel experiment](https://github.com/200lz/llm-inference-optimization-lab/blob/d174d37b7625aa3f3209b6ab592b679853058b54/docs/results/phase8d_q8_end_to_end_ab.md) provides a useful application gate: a bit-identical Q8_0 scale-conversion change sped an extracted tile **1.32 to 1.34 times** in its [microbenchmark](https://github.com/200lz/llm-inference-optimization-lab/blob/d174d37b7625aa3f3209b6ab592b679853058b54/docs/results/phase8c_q8_rn2_scale.md), yet the paired complete `llama-bench` prompt change was **-1.571% median**, with a bootstrap interval spanning **-3.538% to +2.252%** and material time drift. Those raw paired records were kept untracked, so the published summary cannot independently establish an application speedup. This is another reason to require measured full-request CPU before crediting a kernel improvement.

A [phone CPU experiment with retained run data](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/README.md#results-at-a-glance) gives a smaller-format counterexample within one model family. For Qwen2.5-3B, importance-aware IQ4_XS reports **1,971 versus 2,320 MiB** of summed llama.cpp model, context and compute allocations compared with Q4_K_M, yet median latency is **7.94 versus 7.54 s** and integrated phone energy is **157.8 versus 151.5 J**. Each configuration has 30 hardware repetitions of the same summary prompt, greedy decoding and [exactly 100 forced output tokens](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/docs/METHODS.md#3-workload). The memory value is an allocation sum rather than measured process or cgroup high water; the reported llama.cpp total timer excludes process startup and model loading. The paper gives neither user-plus-system CPU-seconds nor complete installed bytes. Its IQ4_XS result therefore supports a memory versus elapsed-time tradeoff for that phone and prompt, not a cold deployment or whole-task CPU saving.

A [pinned same-artifact prefix-cache qualification](https://github.com/integrallis/models/blob/83641c1886ae669def8eed5b62901c957cad8e3c/benchmark-results/certified-20260724/rag/native-q8-prefix-cache/smollm2-360m-q8_0/README.md) points to a runtime saving without changing weight precision. On an eight-vCPU EPYC Milan host with the same **386,404,992 B** SmolLM2 Q8_0 GGUF, the Rust/FFM path reused **3,153 of 5,064** prompt tokens across 27 measured grounded-RAG requests. The [uncached](https://github.com/integrallis/models/blob/83641c1886ae669def8eed5b62901c957cad8e3c/benchmark-results/certified-20260724/rag/native-q8-prefix-cache/smollm2-360m-q8_0/smollm2-360m-rust-ffm-grounded.json) and [cached](https://github.com/integrallis/models/blob/83641c1886ae669def8eed5b62901c957cad8e3c/benchmark-results/certified-20260724/rag/native-q8-prefix-cache/smollm2-360m-q8_0/smollm2-360m-rust-ffm-prefix-cache-grounded.json) raw reports give **226.150 versus 134.200 process CPU-s** summed across generation calls, the same **1,161 output tokens**, and byte-identical generated outputs for all 27 pairs. The cached process peak RSS rises **1,258,450,944 to 1,263,542,272 B**. In the [measurement code](https://github.com/integrallis/models/blob/83641c1886ae669def8eed5b62901c957cad8e3c/models-rag-bench/src/main/java/com/integrallis/models/rag/InProcessGenerationClient.java#L114-L170), the CPU clock surrounds `generationLoop.generate` after an input-token count and backend `begin`; it excludes retrieval, tokenizer setup before the clock, model load and process startup. Its **40.7%** CPU reduction is thus for a repeated warm generation-call mix, not complete served-request CPU or cold admission. Prefix reuse is task-dependent and does not reduce the GGUF or runtime bundle.

A [pinned operator trace for a mixed-precision Qwen3.5-2B GGUF](https://github.com/SiliconBadgers/software/blob/13a1e62a3960759e618b247bfdce0c00e2403fa5/experiments/llama-cpp/2026-09-22/REPORT.md#where-the-cpu-time-goes) narrows the plausible CPU kernel target. On an Apple M5 Pro with six CPU threads, two instrumented 2,048-token repetitions attribute **79.9%** of summed prefill operator intervals and **81.8%** of decode intervals to matrix operations. MLP projections account for **49.9%/35.1%** of prefill/decode; attention and DeltaNet projections for **30.0%/21.7%**; the vocabulary head for **0.05%/25.0%**. The [harness description](https://github.com/SiliconBadgers/software/blob/13a1e62a3960759e618b247bfdce0c00e2403fa5/experiments/llama-cpp/2026-09-22/REPORT.md#what-actually-ran) says each prompt is followed by 32 teacher-forced tokens after warmup. The operator intervals include memory service and possible stalls, while load, tokenization, sampling and output checking are outside the timers. The authors exclude an anomalous 8K trace because the instrumented run slowed materially. These percentages identify places to test a kernel improvement, not measured CPU-seconds saved, a transferable speedup bound, or a whole-request result. They also warn against neglecting the output projection when optimizing decode.

A [first-party dual-Xeon CPU runtime campaign](https://retakedata.com/posts/2026/10/cpu-llm-benchmark/) gives a reported same-file counterpoint to format-only optimization. In its matched [public CSV](https://retakedata.com/data/cpu-llm-study-2026/benchmarks.csv), Qwen3-Next-80B IQ4_XS has the same **42,638,492,672 B** reported GGUF size, one NUMA node, 16 threads, f16 KV, flash attention, and requested and reported weight repacking in ik_llama.cpp and upstream llama.cpp `0faee50`. Three warm repetitions average **26.029 versus 12.078 tokens/s** for empty-context 128-token decode and **247.700 versus 109.651 tokens/s** for separate 512-token prefill, respectively. The two aggregate configurations are `9d81c9b3c2baf30747` and `be09e70fc78ec3a8db`; recorded process peaks are **39.933 versus 39.963 GiB**. The [data dictionary](https://retakedata.com/data/cpu-llm-study-2026/README.md) specifies that these are separate pure-phase tests, that `peak_rss_gib` is process RSS, and that `wall_s` is full benchmark-process wall time rather than request latency. It records model identifiers, source revision and byte count but no model-file checksum; the same-file assertion therefore rests on campaign reporting rather than an independently verified hash. The ik build commit is recorded as **unknown**. These data support a large warm throughput difference for two runtime builds under matched tested settings, with no measured model-byte saving. They provide neither whole-request CPU-seconds nor cold cgroup high water, deployable runtime bytes, exact quality parity, or a fully pinned ik runtime revision.

A [first-party 300M protein encoder experiment](https://github.com/AnanyaP-WDW/esmc.cpp/blob/c4b67436d5173eccc51ed2d0d849a8a8580f14a0/lab_manual.md#510-exp-013--milestone-8f-memory-footprint-harness) provides a distinct memory denominator check. On a 16 GiB Apple Silicon host, fresh-process CPU runs for an 850-token embedding input report **7,425.7 MiB** peak RSS for a **664,280,928 B** F16 GGUF and **6,631.9 MiB** for a **248,985,024 B** Q4_K_M GGUF in the [raw 36-row memory CSV](https://github.com/AnanyaP-WDW/esmc.cpp/blob/c4b67436d5173eccc51ed2d0d849a8a8580f14a0/results/memory_Ananyas-MacBook-Pro_20260531_013718.csv). The same fresh-process rows take **3.173 versus 5.131 wall seconds** respectively. The file saving is much larger than the resident-memory saving because this runtime's long-input CPU scratch dominates. Its [separate warmed throughput CSV](https://github.com/AnanyaP-WDW/esmc.cpp/blob/c4b67436d5173eccc51ed2d0d849a8a8580f14a0/results/throughput_Ananyas-MacBook-Pro_20260530_140618.csv) reports F16 at **0.329** sequences/s and Q4_K_M at **0.183** for the same long bucket. This is a bespoke encoder with an embedding task, not the local autoregressive server; the fresh-process figures are process RSS rather than cold cgroup high water, the throughput figures are warm and omit load, and neither source gives a complete runtime bundle or per-request CPU-seconds. Its useful general lesson is that artifact bytes and process peaks can scale very differently with input shape and runtime scratch.

A [new four-architecture compression study](https://arxiv.org/html/2611.00464v1) reports a useful negative control for dense CPU deployment. Its llama.cpp appendix lists five-run generation throughput, within-engine perplexity, and process peak RSS for GGUF exports of Phi-2, Qwen3-4B, Nemotron-Mini-4B, and Qwen2.5-7B. The Qwen3-4B baseline Q4 entry is **12.53** versus Q8 **8.14 tokens/s**, but the reported process peaks are **4,183** versus **4,213 MB**. Its pruned Qwen3-4B INT8 export is **8.15** versus unpruned INT8 **8.11 tokens/s**, both **4,213 MB**; the authors attribute the lack of pruning benefit to dense storage and kernels. These are format and runtime observations, not a CPU-seconds result. The paper does not specify the CPU processor, llama.cpp revision, repack mode, request shape, file sizes, cold page-cache state, or cgroup high water for this appendix, so its speed and RSS figures cannot estimate this project's Q4_K_S break-even or admitted peak. Its stronger transferable lesson is that zeroing weights without sparse storage and sparse execution does not itself remove deployed bytes or CPU work.

A [community CPU-only campaign](https://github.com/Rizzo-AI-Academy/rizzo-flow/issues/25) has [a pinned raw run ledger](https://raw.githubusercontent.com/Axiumine/quillpick/3d0f1f62393bcc5aaddba83a89a5e0b1d53a6eaf/data/ledger.json) that records whole-command child CPU-seconds, including model load, under a matched 16-thread policy. Its [measurement script](https://github.com/Axiumine/quillpick/blob/3d0f1f62393bcc5aaddba83a89a5e0b1d53a6eaf/campaign/run_campaign.py#L654-L708) sums `wait4` child user and system time for each command and takes the maximum child high-water RSS; it does not charge the separate GPU sampler, report extraction, or the ten-second pre-run baseline to child CPU. The tester used base Spark-X2.5-4B GGUF Q8_0 and Q4_K_M with official llama.cpp `b11081` CPU binaries on a Ryzen 9 9950X3D. On its 17-request smoke command, Q4_K_M uses **532.380 versus 601.446 CPU-s**, an **11.48%** reduction; isolated-process peak RSS falls only **5.656 to 5.571 GiB**, or **1.50%**, while categorical accuracy falls **19/20 to 18/20**. The 400-case typed-decision command similarly uses **16,603.840 versus 18,642.014 CPU-s**, a **10.93%** reduction, with reported accuracy **0.5755 versus 0.576**. This supplies a useful opposite sign to the local Q4_K_S CPU result, showing that quantization, model, hardware, and task mix affect the CPU break-even. Each configuration has one campaign run, and each command executes many cases after one model load. The report does not provide fresh-host-cache or cgroup high water, a complete deployable bundle, output-token matching, or the CPU repack mode, so it cannot establish a per-request saving or a joint resource win.

The same [ledger's matched 4B Q8_0 KV-cache runs](https://raw.githubusercontent.com/Axiumine/quillpick/3d0f1f62393bcc5aaddba83a89a5e0b1d53a6eaf/data/ledger.json) make the RAM versus CPU tradeoff concrete. On the long SemIf comparison command, changing only the KV type from f16 to q8_0 lowers isolated-process peak RSS **5.672 to 5.019 GiB** but raises whole-command child CPU **20,195.502 to 27,868.955 s**, a **38.00%** increase. q4_0 lowers that peak further to **4.664 GiB** while raising CPU to **33,172.527 s**, a **64.26%** increase relative to f16. The [campaign issue](https://github.com/Rizzo-AI-Academy/rizzo-flow/issues/25) reports CPU shared-decision throughput falling in the same order and finds significant q4_0 quality losses in other model/configuration pairs. These KV variants use the same deployed weights and do not reduce GGUF bytes. Their process peaks exclude cgroup page-cache high water; these are single whole-command runs with unreported page-cache state, not individual requests or a general speed estimate.

A separate [first-party decision-engine benchmark](https://github.com/AtomicBot-ai/atomic-llama-cpp-turboquant/blob/1937695dc64e73158b74a3ad2943511fc72d10ff/DECISION.md#results-amd-epyc-7v12--rtx-4090-step-7) measures **complete in-process request CPU-seconds**, including request checks, tokenization, inference, calibration and response rendering. It compares F16 and Q8_0 exports of the same Laya multilingual encoder on the same EPYC 7V12 CPU using the same 32-thread ggml `default` kernel policy. Three order-reversed blocks each warm up once and repeat the same suite ten times. For the one-question request, reported process user-plus-system CPU is **2.995 s F16 versus 2.496 s Q8_0**; for the eight-candidate routing request it is **56.933 versus 48.844 s**. The corresponding benchmark process peak RSS is **435 versus 312 MiB**. A separate [diagnostic cross-kernel comparison](https://github.com/AtomicBot-ai/atomic-llama-cpp-turboquant/blob/1937695dc64e73158b74a3ad2943511fc72d10ff/DECISION.md#L1920-L1937) records **40 of 2,578** answer flips for Q8_0 CPU `default` against Q8_0 CPU `blas`; the authors say their parity tier refuses that pair because activation precision differs. Those flips do not compare F16 with Q8_0. The matched CPU figures show a favorable sign for a smaller weight format on this fixed-output classifier, but they do not measure an autoregressive generation task, cold cgroup peak, or full deployment bytes. The [benchmark implementation](https://github.com/AtomicBot-ai/atomic-llama-cpp-turboquant/blob/1937695dc64e73158b74a3ad2943511fc72d10ff/tools/decision/decision-bench.cpp#L360-L445) brackets request parsing through response serialization with `getrusage(RUSAGE_SELF)` and reports load CPU separately. It also times a diagnostic tokenization pass after that bracket; this extra pass is excluded from reported request CPU. Requests run inside one warm process without HTTP or queueing, so request CPU also excludes model load and server startup.

The same [pinned benchmark's backend comparison](https://github.com/AtomicBot-ai/atomic-llama-cpp-turboquant/blob/1937695dc64e73158b74a3ad2943511fc72d10ff/DECISION.md#results-amd-epyc-7v12--rtx-4090-step-7) shows why the CPU kernel policy belongs in each resource claim. On the EPYC 7V12, the *same Q8_0 GGUF and 32 threads* use **2.496 s** for one question and **48.844 s** for eight-candidate routing with ggml `default`, versus **13.342 s** and **170.909 s** with OpenBLAS `blas`. The report's [Apple M4 Max table](https://github.com/AtomicBot-ai/atomic-llama-cpp-turboquant/blob/1937695dc64e73158b74a3ad2943511fc72d10ff/DECISION.md#phase-4-cpu-levers-same-machine-2026-09-30) reports the opposite backend ordering for the same Q8_0 model at 12 threads: ggml `default` uses **0.68 s** for one question and **7.66 s** for four-candidate routing, while Accelerate `auto` uses **0.27 s** and **2.53 s** for those Mac requests. These are self-reported, warmed, in-process classifier measurements, with different hosts and BLAS implementations across the two comparisons. They establish neither a portable backend ranking nor a Qwen3 speedup. On that Mac, mapping `token_embd` read-only and freeing GGUF metadata reduced Q8_0 **after-load RSS 637 to 262 MiB** and `phys_footprint` **764 to 389 MiB**, while leaving the model format unchanged. This was an after-load process measurement, not a cold cgroup peak or deployed-file saving; clean mapped pages can return to the OS under pressure.

A self-published [two-run GGUF reproducibility harness](https://huggingface.co/datasets/CyberNative-AI/gguf-repro-harness/blob/a37a9bc3fa5484cdda20f330594a55f67faaf4a2/RESULTS.md) adds a caution about load-wall comparisons. Its [frozen protocol](https://huggingface.co/datasets/CyberNative-AI/gguf-repro-harness/blob/a37a9bc3fa5484cdda20f330594a55f67faaf4a2/protocol.md) uses one llama.cpp build, eight CPU threads, fresh containers on a shared host, and F16 and Q4_K_M conversions from the same Qwen2.5-0.5B source. The byte-identical GGUF files are **994,157,024 B** and **397,808,096 B**. Q4_K_M's `llama-perplexity` process peak RSS is **1,402.0 versus 1,942.6 MiB** in run one and **1,401.9 versus 1,941.7 MiB** in run two. Yet its reported model-load wall time changes from **772.0 versus 408.7 ms** in run one to **297.5 versus 338.8 ms** in run two, reversing the arm ordering. The authors explicitly reject their preregistered plus-or-minus 2% load and throughput reproducibility claim and point to shared-host contention and page-cache state. Both loads follow conversion and quantization in each run, so their protocol calls them warm-cache loads; it does not isolate a cold admission event. These are two operator executions of one harness, not independent scientific replications. Their process RSS comes from child `getrusage`, and they report neither cgroup high water nor complete-request user-plus-system CPU-seconds or runtime-bundle bytes. The [raw run 1](https://huggingface.co/datasets/CyberNative-AI/gguf-repro-harness/blob/a37a9bc3fa5484cdda20f330594a55f67faaf4a2/evidence/r1/results.json) and [run 2](https://huggingface.co/datasets/CyberNative-AI/gguf-repro-harness/blob/a37a9bc3fa5484cdda20f330594a55f67faaf4a2/evidence/r2/results.json) also show the task-shape problem: Q4_K_M reaches **38.15/51.27** versus F16 **17.45/18.45 tokens/s** in fixed-token decode, yet the complete 200-case HellaSwag scoring commands take **154.671/145.904 s** versus **150.237/124.643 s** in runs 1/2. The Qwen subset scores **50.5%** in both arms and runs, with no equivalence claim. These are whole-command wall times, not served-request CPU-seconds. The stable RSS difference in this setup does not make its load-wall reversal a robust CPU break-even estimate.

A [Google Research cold-start study](https://storage.googleapis.com/gweb-research2023-media/pubtools/1046363.pdf) supplies a useful counterexample to extrapolating from file size or warm token rate. On Cloud Run, LLaMA-3.2-1B Q4_K_M had lower cold request wall time than Q8_0 at both tested tiers (17.9 versus 24.6 s at 1 vCPU; 14.8 versus 20.2 s at 2 vCPU). Yet on the 2-vCPU tier the paper reports Q8_0 at 12.8 versus Q4_K_M at 12.0 generated tokens/s in its quantization sweep, while the 1-vCPU ordering reverses (4.6 versus 8.1 tokens/s). The paper attributes this to a changed balance between memory traffic and unpacking work. It records a roughly 16-token prompt and a 50-token generation cap, not task-success cost. Its nominal cold start comes from a new Cloud Run revision and includes server boot, model load, and inference; it does not establish a cold host page cache, cgroup peak, CPU-seconds, or output-token equality. The 5.8 GB multi-model image includes all GGUF variants, so the paper's per-model file sizes are not per-model deployable bundle sizes. Its single-model image check changes the `llama-cpp-python` compilation environment and reports 12% to 31% slower warm inference, limiting that image-size control.

[PolyQ](https://arxiv.org/html/2607.14618) is credible CPU-only prior art for fine-grained precision with compile-time channel permutation and bit-homogeneous kernel blocks. It reports reduced runtime reorder traffic and measured 256-token prefill latency and batch-one decode throughput on three CPUs. Its advertised peak footprint is a **working-set model** that sums storage, KV cache, activations, scratch, metadata, and a reorder buffer, not a measured process or cgroup high water. The paper gives bit-budget rather than complete installed-file totals, and does not measure complete served-task CPU-seconds or this Q4_K_M GGUF comparator. Its conclusion says throughput is within 2% of the optimized LUT CPU path, whereas its detailed results report up to an 8.2% decode shortfall and 7.3% prefill gap on Ryzen 7840U; those detailed ranges should govern any use of the claim. This is a prospective compiler direction, not a demonstrated joint resource win for the pinned local runtime.

A [first-party CPU-only KV-cache experiment](https://www.bigiron.cc/guides/kv-cache-quantization-q8-q4-and-turboquant-measured) gives a narrow warning about a different compression lever. On one six-vCPU Debian VM with Qwen3-1.7B Q4_K_M weights and mainline llama.cpp `29c720e`, the author reports pre-prompt process `RssAnon` at a configured 32,768-token context of **4,300 MB** for f16 K/V, **2,620 MB** for q8_0 K/V, and **1,724 MB** for q4_0 K/V. With a 7,421-token lookup prompt, the first prompt-processing wall time instead rises from **82 s** for f16 to **214 s** for q8_0 and **212 s** for q4_0, even though the reported generated-token rates improve from **4.1 to 5.8 and 7.1 tokens/s**. On 16 known-answer lookups at that length, q8_0 K/V scores **12/16**, the same as f16, while q4_0 K/V scores **3/16**; shorter prompts did not expose the same collapse. The [inline harness](https://www.bigiron.cc/guides/kv-cache-quantization-q8-q4-and-turboquant-measured#the-test) fixes the prompt and generation cap at 60 but publishes no raw repetitions, complete-request user-plus-system CPU, runtime bundle, or cgroup high water. `RssAnon` was read before the prompt, so it is neither a peak nor a cold admission result. This small self-reported lookup test shows why a lower KV allocation and faster warm decode alone cannot establish whole-task savings or retained quality, and it does not compare the local Q4_K_S weight artifact.

A [peer-reviewed layerwise quantization study](https://arxiv.org/html/2509.23729v3#Sx4) gives a positive CPU throughput example, but a narrower one than its headline memory claim. For Qwen2.5-VL-7B, its [deployment appendix](https://arxiv.org/html/2509.23729v3#SxD2) maps the 12 selected low-bit layers to llama.cpp IQ1_M and the remaining layers to Q4_K_M. Across ten generation runs, the mixed-precision version reaches **9.0 ± 0.3 versus 4.8 ± 0.3 tokens/s** on an Intel i7-13620H and **18.7 ± 0.1 versus 14.1 ± 0.2 tokens/s** on a Threadripper PRO 7965WX. The appendix lists **3.4 versus 4.4 GB** as "Memory Usage," without defining whether this is model storage, process peak, or another metric. Its [quality study](https://arxiv.org/html/2509.23729v3#Sx4) quantizes the backbone with BiLLM and GPTQ in PyTorch on a GPU, whereas the CPU runtime substitutes IQ1_M and Q4_K_M kernels. The paper does not report quality of that exact CPU artifact, prompt length or complete-request CPU-seconds for the generation runs, exact GGUF or runtime-bundle bytes, cold cgroup high water, or a pinned llama.cpp build. This supports a feasible layerwise CPU throughput direction; it cannot establish a joint task-quality and resource win for the deployed surrogate.

A self-published [CPU-only MoE runtime experiment inventory](https://github.com/y0sif/ramvamp/blob/a68b69a70027b369e20fd468d6dcefdf0e262475/docs/experiments.md) illustrates a different way to reduce resident RAM: stream expert weights through `O_DIRECT` instead of charging them to the page cache. Its [pinned model account](https://github.com/y0sif/ramvamp/blob/a68b69a70027b369e20fd468d6dcefdf0e262475/docs/architecture.md) lists an **18,632,183,808 B Q4_K_M GGUF** and an **18,626,213,888 B installed model**, only 5,969,920 B less. On its Core Ultra 9 185H and Micron 2400 NVMe, the reported 3,961-prompt/64-generation-token cold run reaches **2,929.3 MiB cgroup `memory.peak`** under `memory.max=3G` and `memory.swap.max=0`, with three scored runs, proved model-page eviction, positive block reads, and zero reclaim under its published hygiene rules. Its buffered-`pread` control instead reaches the 3G limit and forces about **4.82 GiB of reclaim** during a 13-token generation; a separate run has zero `memory.events max` but 2.4 GiB of `pgsteal`. These observations distinguish *installed bytes* from *resident cgroup peak* and show why an event counter alone cannot certify clean cold admission. They do not compare quantization formats or report whole-request CPU-seconds or a runtime dependency bundle. The repository explicitly [withholds raw logs and harness outputs](https://github.com/y0sif/ramvamp/blob/a68b69a70027b369e20fd468d6dcefdf0e262475/docs/experiments.md), so the figures remain a curated first-party account rather than an independently reproducible resource result.

A [same-GGUF streaming-runtime comparison](https://github.com/ManeeshJupalle/Qwen-3.8-in-Rust/blob/f2b153add3340a25e877cc8e284ecfb59a4037d2/README.md#L187-L205) puts the memory-policy distinction in sharper relief. One Windows 11 i7-9750H laptop with **32 GB physical RAM** ran a verified **17,772,537,440 B Qwen3.8-27B Q4_K_M file** through the author's Rust `aqueduct` engine and official llama.cpp b10827, both with six CPU threads. The author's [raw ladder](https://github.com/ManeeshJupalle/Qwen-3.8-in-Rust/blob/f2b153add3340a25e877cc8e284ecfb59a4037d2/docs/data/ladder.txt#L359-L378) reports **5.057 GB peak process working set** and **13.406 GB disk reads per token** at a 5 GiB Windows job-object cap with three-token self-speculation, averaging **1.894 wall seconds per output token** over three 32-token greedy prompts. The [llama.cpp sidecar](https://github.com/ManeeshJupalle/Qwen-3.8-in-Rust/blob/f2b153add3340a25e877cc8e284ecfb59a4037d2/docs/data/vs_llamacpp.txt#L449-L455) says the shipped repack path cannot allocate its 9.6 GB buffer at that cap. `--no-repack` loads and reports **13.42 s/token**, but the author's [own caveat](https://github.com/ManeeshJupalle/Qwen-3.8-in-Rust/blob/f2b153add3340a25e877cc8e284ecfb59a4037d2/README.md#L197-L205) says the 32 GB host retained trimmed mapped pages in the standby list, making the no-repack speed an optimistic floor for a real 8 GB machine. This is a cross-engine, single-file runtime result with three short fixed-token prompts and divergent output IDs on one prompt. It has no whole-request CPU-seconds, physical small-RAM or Linux cgroup admission measurement, or exact installed dependency bundle. Streaming can trade resident memory for disk traffic without reducing deployable model bytes; the reported per-token wall speed does not establish a task-level CPU saving.

A [same-GGUF CPU runtime A/B](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/results/openllama-7b-v2-ab/SUMMARY.md) shows the cost of a memory-first implementation. On a four-vCPU EPYC 9V74 runner, MemVanta and pinned llama.cpp used one verified **3,825,818,912 B** OpenLLaMA-7B Q4_0 file, four threads, f16 KV, a 512/128 fixed-token shape, and one warmup plus five repetitions. The reported process maximum RSS is **3.80 versus 7.24 GiB**, while prompt and generation rates are **2.92 versus 11.95** and **1.92 versus 7.97 tokens/s**. The [GNU time records](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/results/openllama-7b-v2-ab/memvanta.time.txt#L214-L231) give **4,183.82 CPU-s** for the MemVanta benchmark command versus [**1,347.87 CPU-s** for llama-bench](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/results/openllama-7b-v2-ab/llama-bench.time.txt#L215-L232). Those commands have different benchmark implementations and include repetitions, so their totals are not paired request CPU estimates. A [separate four-vCPU Xeon cgroup sweep](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/results/openllama-7b-v2-ram-constrained/SUMMARY.md) reports repeat-confirmed success at tested limits of 160 versus 3,648 MiB with swap disabled in its [boundary CSV](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/results/openllama-7b-v2-ram-constrained/results.csv). Yet the successful [MemVanta child output](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/results/openllama-7b-v2-ram-constrained/memvanta-confirm-success-1-160.stdout.txt) itself reports **3,728.52 MiB peak RSS**. The [workflow](https://github.com/sauravsingla/MemVanta/blob/66701cae69c03f91efbff8f2f9ecfd6a8ccbb048/.github/workflows/sevenb-ram-constrained.yml#L59-L162) downloads the GGUF outside each transient scope and records limit and exit status, but no `memory.peak`, model-cache ownership, reclaim or prelaunch eviction. Under [Linux cgroup-v2 memory ownership](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory-ownership), mapped file pages can remain charged to the cgroup that first instantiated them. External page-cache charges are plausible, although these records cannot identify their exact share. The 160 MiB result establishes execution under that runner's charged-memory cap, not cold host RAM sufficiency or a cold cgroup high-water saving. Neither comparison counts a deployable runtime bundle or tests task quality. The directly supported conclusion is a measured RSS versus throughput tradeoff in that runtime, with a cgroup admission result that needs its charge denominator.

A [self-published InferBit cross-runtime matrix](https://github.com/demonarch/inferbit-py/blob/7e71d91fcd80261bc8c69347103dbb87e2053225/README.md#L169-L213) initially looks like a smaller-file, lower-RSS, faster fixed-token CPU counterexample. On an Apple M4, its Llama-3.1-8B table lists an InferBit file of **3.75 GiB** versus a llama.cpp Q4_K_M GGUF of **4.58 GiB**, process peaks of **4,306 versus 6,755 MB**, and 128-token decode rates of **4.2 versus 2.4 tokens/s**. The [same README corrects its format label](https://github.com/demonarch/inferbit-py/blob/7e71d91fcd80261bc8c69347103dbb87e2053225/README.md#L169-L175): the rows called PQv2 were actually INT4-blk32 plus INT8, and the v0.4.1 production converter did not emit PQ tensors. The linked [correction](https://github.com/inferbit/inferbit/blob/main/docs/v2/00_CORRECTION.md) and [metrics snapshot](https://github.com/inferbit/inferbit/blob/main/docs/34_METRICS_SNAPSHOT.md) are unavailable in the public repository at this audit, leaving no raw sidecar to check the table. This is a potentially useful **INT4 cross-engine fixed-token** result, not evidence for PQv2. Different runtime builds and memory tools, missing model-file checksums and installed dependency bytes, no complete-request CPU-seconds, no cold cgroup high water, and no task-level quality prevent promotion to a joint deployability result.

A second self-published [llama.cpp CPU streaming report](https://github.com/ggml-org/llama.cpp/discussions/30409) demonstrates how the repack switch can determine *admission* under a memory cap. For one 4,213,512,672 B OLMoE Q4_K_M file on WSL2, its [pinned rows](https://github.com/ahafarag/cpu_inferrence_lab/blob/8b2b2ea450cc0bbd902d329d29b185dc745ddab9/benchmarks/results.csv#L312-L319) report that `--repack 0` completes a 32-prompt/16-generation-token `llama-bench` under a 3 GiB cgroup with swap disabled, while default `--repack 1` exits 137 with `oom_kill=1` at the same cap and 128 KiB block read-ahead. The report gives Q4_K_M anonymous RSS of 57 MB without repacking versus 3,063 MB with it. Under no-repack, its 128 KiB read-ahead result is 4.91 generated tokens/s versus 0.14 at 8,192 KiB, which makes storage policy a major confounder in streamed-weight comparisons. The [published script](https://github.com/ahafarag/cpu_inferrence_lab/blob/8b2b2ea450cc0bbd902d329d29b185dc745ddab9/benchmarks/setup/50_moe_streamed.sh#L319-L403) drops host caches before each streamed run and creates a fresh capped cgroup, but it skips process peak collection and does not publish cgroup `memory.peak`, reclaim deltas, or prelaunch model-page residency. The CSV also identifies earlier mislabeled `--repack 0` rows caused by a script argument-order bug; those rows are excluded here. Its [model inventory](https://github.com/ahafarag/cpu_inferrence_lab/blob/8b2b2ea450cc0bbd902d329d29b185dc745ddab9/MODELS.md#L170-L177) still says the Q4_K_M file was not downloaded, despite later Q4_K_M results, leaving file verification unclear. This is a useful same-file admission counterexample, not a measured cold peak, complete-request CPU, or deployable-bundle comparison.

A recent [first-party Cortex-A53 counter study](https://github.com/FredWen-S/lowbit-decode-a53/blob/08c7d473dc8db3be535528b21fa11b8eab726bba/a53/summary.md) supplies a same-model, same-runtime negative example for assuming fewer weight bits save CPU work. On a Sonim XP8800 with eight Cortex-A53 cores, the author ran Qwen2.5-1.5B-Instruct GGUF variants with llama.cpp `23deec0`, eight threads, `--poll 0 -lm none`, and a warmed page cache. Q3_K_M uses 876 MiB of reported tensor bytes versus Q4_K_M's 1,060 MiB, yet its fixed-token decode rate is 5.38 versus 5.67 tokens/s. The [reported hardware counters](https://github.com/FredWen-S/lowbit-decode-a53/blob/08c7d473dc8db3be535528b21fa11b8eab726bba/a53/counters_result_stat2.json) show about 1.906 versus 1.637 billion user-mode instructions per decoded token; sampled dot-kernel attribution is consistent with greater low-bit arithmetic cost. The author's [run manifest](https://github.com/FredWen-S/lowbit-decode-a53/blob/08c7d473dc8db3be535528b21fa11b8eab726bba/a53/RUNS.md) records forward and reverse passes but says the clean-pass driver script was not retained, and the analysis keeps only runs with decode coefficient of variation below 2%. This self-published result measures warm decode and tensor bytes, not whole-request CPU-seconds, cold cgroup or process peak, full GGUF file and runtime bundle, or task-success cost. It supports a CPU-specific break-even risk rather than a transferable Q3 performance estimate for the local i7.

A [single-checkpoint GGUF quantization study](https://arxiv.org/html/2601.14277) gives a closer format-level counterexample on a dual Xeon Platinum 8488C CPU host. The authors converted one Llama-3.1-8B-Instruct F16 GGUF with llama.cpp `b7600` and varied only the quantization scheme. Their Q4_K_S GGUF is **4,467.80 MiB** versus Q4_K_M's **4,685.30 MiB**, a **217.50 MiB** saving; the fixed 128-token decode benchmark reports **4.65 ± 0.15 versus 5.12 ± 0.37 tokens/s**, so the smaller file is slower on that CPU. In a separate five-benchmark quality aggregate, their rounded averages are **69.17 versus 69.15**, while GSM8K is **77.33 versus 77.41** and WikiText-2 perplexity **7.62 versus 7.56**. These small, mixed score differences do not establish per-task parity. The study does not report process or cgroup peaks, request CPU-seconds, token counts from the scored tasks, or runtime-bundle bytes. Its throughput result is a fixed-token wall-time observation, not a complete-request CPU comparison with the local Qwen3-4B run.

A [peer-reviewed structured-generation CPU study](https://www.mdpi.com/2504-2289/10/5/155) gives a task-level version of that tradeoff on a different checkpoint and host. Its authors merged one fine-tuned Llama-3.2-1B checkpoint before exporting Q3_K_M and Q4_K_M GGUFs, then evaluated a held-out 1,000-example multilingual intent-to-JSON task on a four-vCPU AMD EPYC Genoa virtual machine. Q3_K_M uses **0.93 GB** of reported RAM versus Q4_K_M's **1.04 GB**, but its mean complete inference latency is **1.23 versus 0.82 s**, its P95 is **1.79 versus 1.16 s**, and exact-match accuracy is **0.972 versus 0.984**. The reported CPU table says single-threaded inference. The article does not specify a pinned llama.cpp commit, exact GGUF and runtime bytes, per-case output lengths, page-cache policy, cgroup high water, or user-plus-system CPU-seconds. Its lower-bit artifact loses on both latency and task accuracy despite the lower reported RAM, but the numbers cannot be transplanted to the local Qwen3-4B break-even.

A separate [CrispASR hFT Transformer study](https://github.com/CrispStrobe/CrispASR/blob/967e46d6130e890d614fb6fba46340cca80f41e3/docs/ggml-repack-buft-evaluation.md#5a-end-to-end-whole-model-on-clean-runners) measures complete piano-transcription CLI process CPU on clean CI runners, with one process per arm, interleaved rotating order, a discarded cold repetition, median of three warm repetitions, `getrusage(RUSAGE_CHILDREN)` user plus system time, `MKL_NUM_THREADS=1`, and one ggml thread. The [same model's GGUF exports](https://github.com/CrispStrobe/CrispASR/blob/967e46d6130e890d614fb6fba46340cca80f41e3/docs/music-transcription/HFT_TRANSFORMER.md#sizes) are 21.8 MiB F32, 7.0 MiB Q8_0, and 4.5 MiB Q4_0; only 63 of 157 tensors are quantized. On an AVX2 EPYC 7763, F32 cost **12.88 CPU-s**, generic Q8_0 **14.05 CPU-s**, generic Q4_0 **15.7 CPU-s**, and Q4_0 with repack **9.3 CPU-s**. The smaller GGUFs therefore *raised* complete-process CPU under the generic path on this host, while repack changed the direction. On a different EPYC 9V74 with AVX-512 VNNI, its final corrected run instead recorded F32 **25.56 CPU-s**, generic Q8_0 **21.55**, generic Q4_0 **23.28**, and repacked Q4_0 **18.81**; x86 Q8_0 repack was declined and fell back to mmap. On the arm64 dot-product runner, the same final run measured F32 **102.67**, generic Q8_0 **51.79**, repacked Q8_0 **37.58**, generic Q4_0 **56.92**, and repacked Q4_0 **36.02 CPU-s**. The study reports roughly **233-234 MiB** peak process RSS across hFT arms on its earlier clean run, so model-file bytes did not determine that process peak. Its [MusicNet note F1](https://github.com/CrispStrobe/CrispASR/blob/967e46d6130e890d614fb6fba46340cca80f41e3/docs/music-transcription/HFT_TRANSFORMER.md#note-level-f1-on-musicnets-test-split) is for the quantized generic path; the repack comparison only checks a speech clip passed to the piano model, and [notes differ slightly](https://github.com/CrispStrobe/CrispASR/blob/967e46d6130e890d614fb6fba46340cca80f41e3/docs/ggml-repack-buft-evaluation.md#5b-parity-what-the-repacked-kernel-changes-in-the-output). This is a small non-LLM model, a self-reported CI campaign without a portable bundle or cold cgroup peak; it establishes a same-workload CPU-policy counterexample, not the present language-model joint gate.

An independent [speech-model CPU integration report](https://github.com/CrispStrobe/CrispASR/blob/309830a488172242b72ae39c9959d70a92d94de3/docs/phonon2.md#measured-cpu-profile-2026-09-30) provides a useful, narrower end-to-end counterexample. For the same Phonon-2 recognizer and four-thread EPYC 9V74 runtime, its warmed complete 11/55-second transcription medians are **1.760/9.301 s** with Q8_0 and **2.043/10.878 s** with the smaller Q4_K export; isolated-process peak RSS is **1,614 versus 1,320 MiB**. Its Q4_K export is listed at about **402 MB** against Q8_0's **674 MB** download, but those rounded figures exclude the executable and libraries. The same project's [gated FFN experiment](https://github.com/CrispStrobe/CrispASR/blob/309830a488172242b72ae39c9959d70a92d94de3/docs/phonon2.md#gated-ffn-cpu-experiments-2026-10-01) shows that selective CPU repacking can recover warm Q4_K latency on a separate four-vCPU EPYC 7763: **1.850/10.189 to 1.508/8.401 s**, while model-load wall time rises **0.077 to 0.508 s**. That candidate remains off because it fails the authors' strict stage-magnitude gate despite retaining all words in their 21-clip local check. Their cached F32 FFN path also speeds long F16 transcription while adding **1,536 MiB** of weight storage and slowing short F16 and both quantized shapes on a third host. These are task wall times and process RSS, with shape warmups and different hosts across experiments; they do not provide CPU-seconds, cold cgroup peaks, or a matched deployable bundle. They do show that lower weight precision and a faster isolated layer do not each guarantee lower whole-task cost.

A separate [task-level quantization study](https://arxiv.org/html/2610.32417v3) gives a stronger check on the completion denominator. Its first-party experiments use Q4_K_M and Q8_0 variants of Qwen3-30B-A3B and Devstral Small 2 on A100 GPU hosts, with verifiable agent tasks and repeated attempts. The authors report that 4-bit uses 6% to 16% less energy per output token across conditions but, on three statistically supported tasks in each of three conditions, more energy per verified completion. In the supported disagreements, choosing by the lower per-token energy costs a median 66% more per completion and up to 3.5 times more in one Qwen business-query task. Their measured task window includes model calls, agent tool actions, and waiting, and charges failed attempts through the success denominator. It excludes model load and final research verification, which the authors measure separately. CPU-package and GPU-board energy are read from hardware counters every 0.1 s. This is evidence that extra tokens and failures can reverse a per-token saving. It is **not** a CPU-only result, a CPU-seconds measurement, a cold peak-RAM observation, or a deployable-byte comparison with the local 4B files. Its later expanded-budget and second-model analyses are described by the authors as exploratory, so the 3.5-times example is a task-specific result rather than a general multiplier.

A [first-party 150-run CPU GGUF benchmark](https://github.com/chutapp/locallm-bench/blob/3522cacc510a60f6144bec49e0387228798bc527/README.md#methodology) initially appears to offer a 12/14/15.5 GB cgroup admission comparison with peak RSS and model size. Its [pinned runner](https://github.com/chutapp/locallm-bench/blob/3522cacc510a60f6144bec49e0387228798bc527/scripts/run_single_bench.sh#L80-L109), however, applies `MemoryMax` only below the 15.5 GB tier and uses `--no-mmap`. It fills the output field named `peak_rss_mb` by parsing the first `Host ... =` line from llama.cpp's memory report, [rather than a process high-water or cgroup counter](https://github.com/chutapp/locallm-bench/blob/3522cacc510a60f6144bec49e0387228798bc527/scripts/run_single_bench.sh#L441-L481). For example, its [14B Q4_K_M record](https://github.com/chutapp/locallm-bench/blob/3522cacc510a60f6144bec49e0387228798bc527/results/bench-2/quick_Ministral-3-14B-Reasoning-2512-Q4_K_M_Q4_K_M_llama.cpp_14GB.json) lists a 7,857 MB GGUF but only 2,877 MB under that label, consistent with a partial allocation report rather than total non-mmap resident weights. The run data contain no complete-request CPU-seconds or deployable bundle. Thus its fit and memory summaries cannot supply the cold peak or CPU gate here, regardless of the usefulness of its exploratory throughput results.

The next useful experiment is a controlled, held-out benign workload with a reference that clears an absolute quality floor, run under one declared policy. It should count all required model/runtime files, admitted cold cgroup peak, process high water, warm and cold request CPU, output tokens, retries, and complete task success. The present Q4_K_S control is strong on bytes and no-repack memory, but its two-task CPU result prevents a general joint-efficiency claim.
