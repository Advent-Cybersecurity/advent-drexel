# NexAgent: source-level code upgrade in a long-running agent

Advent Cybersecurity source audit, 26 November 2026. This is a static reading of [NexAgent at commit `8ec412f`](https://github.com/gofenix/nex-agent/tree/8ec412fefac75dee3d739cb2e7f9beb911eaeb18), not an execution of its agent, upgrade path, or tests. NexAgent is a benign chat agent with user-authorized tools; it is not a malware incident.

The [agent-facing `upgrade_code` tool](https://github.com/gofenix/nex-agent/blob/8ec412fefac75dee3d739cb2e7f9beb911eaeb18/lib/nex/agent/tool/upgrade_code.ex) accepts a complete new Elixir module source, module name, and reason, while excluding named protected modules. The [upgrade manager](https://github.com/gofenix/nex-agent/blob/8ec412fefac75dee3d739cb2e7f9beb911eaeb18/lib/nex/agent/upgrade_manager.ex) calls the code-upgrade layer and records a version identifier and hot-reload metadata. The [code-upgrade layer](https://github.com/gofenix/nex-agent/blob/8ec412fefac75dee3d739cb2e7f9beb911eaeb18/lib/nex/agent/code_upgrade.ex) parses, backs up, writes, compiles, loads, and versions source. This is a concrete agent-to-executable-code path; the author repository does not supply a model response and corresponding two-upgrade execution trace.

The [hot-reload implementation](https://github.com/gofenix/nex-agent/blob/8ec412fefac75dee3d739cb2e7f9beb911eaeb18/lib/nex/agent/hot_reload.ex) uses `Code.compile_quoted` in the running BEAM VM. If the new module exports the tool interface, it asks the tool registry to register or hot-swap it, then polls for registry state. Its returned `reload_succeeded: true` is set after compilation and expected-module selection even when `registry_swap.swapped?` is false or no registry was running. Thus a successful upgrade status alone should not be read as proof that the agent's next tool invocation used the new module. The code's health check merely asks for the module's exported-function list; it does not run a retained-function task. These are source-level distinctions, not observed failed upgrades.

The repository's [evolution integration test](https://github.com/gofenix/nex-agent/blob/8ec412fefac75dee3d739cb2e7f9beb911eaeb18/test/nex/agent/evolution_integration_test.exs) uses a mock model to check updates to soul, memory, and skill artifacts. The [upgrade-manager tests](https://github.com/gofenix/nex-agent/blob/8ec412fefac75dee3d739cb2e7f9beb911eaeb18/test/nex/agent/upgrade_manager_test.exs) exercise git-trackable source-path decisions. Neither is a published measured sequence of two model-authored module replacements with version-bound functional outcomes. A git commit or stored version is an artifact record, not a record that a particular long-running session invoked that version.

The case reinforces the feasible **mechanism** for in-process executable change and the need to distinguish parsing, compiling, loading, registry selection, actual invocation, and task success. It supplies no continuing remote-access payload, two active model-caused revisions, or independent after-each remote-control results. BEAM's lightweight runtime processes also require care: an Erlang/Elixir “process” identifier is not itself an operating-system process identifier. A future strict claim would need both host-instance identity and a version-to-invocation-to-result chain.
