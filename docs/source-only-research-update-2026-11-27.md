# Project Drexel: source-only feasibility update

Jashid Sany, Advent Cybersecurity. 27 November 2026 (America/New_York).

This update extends the [published version 0.4 preprint](https://doi.org/10.5281/zenodo.24591891) with primary-source review and a structured case extraction. It is research for a future version, not a change to the deposited PDF or archive. No model, agent, malware, defender product, or candidate code was run for this update. The case search was purposive and bounded; no prevalence, reliability, or detection rate can be estimated from it.

## Findings by question

| Question | New evidence and decision boundary | Remaining unknown |
| --- | --- | --- |
| Do reported cases join model-caused executable revisions, one continuing process, and a remote task after each of two revisions? | The [bounded case update](case-evidence-update-2026-11-27.md) and [eight-field extraction](../data/selected-case-extraction-2026-11-27.json) re-examine seven of the 31 prior ledger cases and add PromptLock and GTIG's November `exploit_agent` account. They separate model-generated code from a particular response-to-artifact link, and endpoint residency from an operator-side local model. None of the nine selected public records establishes the joined strict chain. | The other 22 prior ledger cases were not re-extracted in this pass; unpublished or later traces cannot be ruled out. The selected cases are not a denominator for a field frequency. |
| Can an active version be adopted under ordinary operating-system policy? | The [platform matrix](platform-policy-boundaries-2026-11-27.md) distinguishes a file write, module load, version-specific call, process/image lineage, and retained function. Windows dynamic-code and image policies, Linux service settings, and macOS Hardened Runtime restrictions are conditional on the actual program and configuration. A preserved service, connection, or PID does not alone establish an unchanged program image. | No target host or policy configuration was measured here. The cited vendor documents establish mechanisms and restrictions, not a cross-platform success probability. |
| Could unreliable environmental observations make an apparent adaptation result invalid? | The [observation-integrity review](environment-observation-trust-2026-11-27.md) separates the true environment, model-visible diagnostic data, the model's decision, the active version, the independent task result, and defender collection health. AgentDojo, CaMeL, AgentNoiseBench, and AgentSuite motivate distinct checks for untrusted instructions, noisy tools, and flawed evaluation fixtures; their results are from different tasks. | No Drexel-specific observation-error rate, mitigation effect, or defender-alert rate has been measured. Missing events are unknown unless the sensor configuration and collection health are established. |

The case result leaves the version 0.4 paper's central judgment intact: the reviewed literature supports pieces of the proposed system, while the joined serial-revision and after-each-function claim remains unestablished in the inspected public record. This is a statement about evidence, not an impossibility result. Broad language such as adaptation to “any environment” or being “undetectable” must be replaced by declared operating-system, policy, workload, and sensor strata in any empirical claim.

## What the next source pass should resolve

1. **Complete the comparable case audit.** Re-extract the other 22 cases in the [31-case ledger](../data/closest-case-claim-ledger-2026-11-26.json) under the same eight fields, keeping the earlier ledger's four-link labels as historical coding. Record exact publication versions, locators, selection and exclusion decisions, and unresolved contradictions. The new nine-case extraction is a methodological pilot, not a replacement for the full ledger.
2. **Seek a genuinely joined public trace.** A qualifying record would pair a particular model response with accepted executable content, show two version-specific invocations in one identified process/image lineage, and independently verify a benign remote task after each version. First-party descriptions of agent direction, repeated build releases, loader acknowledgements, or a working new process answer narrower questions.
3. **Turn platform documentation into declared strata.** Before any future benign study, specify the application type and runtime, OS release, relevant process/service policy and entitlement state, activation path, and process/image observation method. Preserve per-stratum outcomes rather than collapsing unlike host configurations.
4. **Separate adaptation from input sensitivity.** In a later isolated, harmless application study, compare model-visible observations with an independent ground-truth environment record. Keep the task oracle and telemetry collector outside the candidate's editable path. Predefine what counts as correct adaptation, a failed update, a retained function, an alert, enforcement, and missing collection.

These are evidence and study-design requirements. No new empirical result is asserted. The [source registry](../data/sources.json) now includes the primary pages behind the three notes, and the [research guide](README.md) indexes the full review.

This changes neither the publication status of version 0.4 nor the full-chain evidence judgment above.
