# Asiel Core: model-generated Python plugins and live reload

Advent Cybersecurity source audit, 26 November 2026. This is a static reading of the author's [public repository at commit `9ccdcce`](https://github.com/asieltechlab/asiel-core/tree/9ccdcce55211b1cd9a11eb1ac2e8414443df2b96), not a reproduction or model test. The project is a benign agent, not a remote-access payload.

## Implemented path

The [application](https://github.com/asieltechlab/asiel-core/blob/9ccdcce55211b1cd9a11eb1ac2e8414443df2b96/asiel_core/asiel_core/app.py#L877-L1131) starts a plugin-evolution loop. It reads an existing plugin, asks an LLM for a complete revised Python version, then calls `self_edit.propose`, `validate`, and `integrate`. After an `integrate` result marked successful, it calls `plugin_loader.reload()` in the same application process. A separate lower-impact `REFINE` path writes generated code directly to a plugin file and calls `reload()` without the proposal validator. The initial `BUILD` path likewise calls `reload()` after integration. Background tasks for the edit and evolution loops are created at startup in the same application module.

The [plugin loader](https://github.com/asieltechlab/asiel-core/blob/9ccdcce55211b1cd9a11eb1ac2e8414443df2b96/asiel_core/asiel_core/core/plugin_loader.py#L97-L168) clears its registry, scans plugin files, checks an AST policy, imports each passing file with `exec_module`, and registers callable hooks. Its tick and chat handlers invoke those registered module functions. This is a concrete mechanism for changing executable Python behavior while the host process continues. It does not preserve a previous module automatically if the replacement fails its import or AST check: `reload()` clears the registry before scanning. The direct `REFINE` path overwrites the file before trying the reload and catches reload errors without a rollback in that branch. These are source-level reliability risks, not observed failures in a measured run.

The [self-edit executor](https://github.com/asieltechlab/asiel-core/blob/9ccdcce55211b1cd9a11eb1ac2e8414443df2b96/asiel_core/asiel_core/core/self_edit_executor.py#L396-L481) snapshots an existing destination, copies an approved workspace file to the codebase, and rolls back on failed *smoke test*. That smoke test invokes only `python -m py_compile`; it does not call the plugin hooks or check any end-to-end task result. `integrated` therefore means a file passed the executor's checks and was copied, not that the active loader imported it, the expected hook ran, or prior functions remained intact. The loader's AST policy is a further separate gate.

## Committed records and their limit

At this pinned commit, the author's committed [proposal registry](https://github.com/asieltechlab/asiel-core/blob/9ccdcce55211b1cd9a11eb1ac2e8414443df2b96/asiel_core/asiel_core/self_edit/proposals.json) contains 23 records: 11 marked `integrated`, 12 `failed_validation`. All 23 identify `self_edit_loop` as the source. The 11 integrated records concern distinct plugin target paths; the registry has **no `evolution_loop` proposal** and no pair of successful integrations to the same target path. Failed candidates followed by an integrated candidate do not establish two active versions. The registry is a committed application artifact, not an independently observed runtime trace; it does not include process identity, module-load result, hook invocation after each version, or a dependent task outcome. These counts describe this checked-in registry only, not a success rate for the agent or for Drexel.

## Feasibility implication

This case joins a model-directed code-revision *mechanism* to a same-process import/reload *mechanism* in one benign codebase. It narrows the engineering gap more than cases that only rewrite prompts or external files. The reviewed public artifact still does not document two distinct model-caused executable revisions becoming active in one identified continuing process. It has no remote-control workload or independent command/result check after either revision. A future claim would need proposal-to-file hashes, process identity across reloads, loader activation for both versions, and fresh version-bound function results, including failure and rollback records.
