# Repeated-revision feasibility: second source pass

Reviewed 2026-11-10. This follow-up to the [repeated-revision audit](repeated-revision-evidence-audit.md) checks additional primary studies and malware analyses against the same question: **did one continuing program apply at least two model-caused payload changes and retain independently verified remote access after each?** It separates a paper's proposed architecture from what its experiment actually ran.

## New evidence

| Source | Study unit and observed result | Boundary for the exact claim |
| --- | --- | --- |
| [You et al., *Tiny Enough to Break In*, August 2026 preprint](https://arxiv.org/html/2608.03009v1) | A local model directed a controller in three short, isolated lab runs against one deliberately vulnerable target. It achieved verified shell-level access on **6 of 55 service-level tasks (10.9%)**. The same two simple paths succeeded in each run. | Despite the “agentic RAT” title, the authors explicitly **built no implant, persistence mechanism, or command-and-control channel**. The model and controller ran on the operator side. They tested no payload rewrite, long-running session, or access after a revision. They also lacked a controller-only baseline, so the model's positive contribution to the successes is unproven. |
| [ESET's PROMPTSPY analysis, February 2026](https://www.welivesecurity.com/en/eset-research/promptspy-ushers-in-era-android-threats-using-genai/) and [GTIG's follow-up, May 2026](https://cloud.google.com/blog/topics/threat-intelligence/ai-vulnerability-exploitation-initial-access) | Analyzed Android malware contains both runtime model-guided user-interface actions and a remote-access module. GTIG's code analysis found that its remote infrastructure settings *could* be updated during execution. | This is closer to the *remote-access plus runtime model use* conjunction, but the model produces actions, **not revisions of the program's payload code**. GTIG attributes potential infrastructure updates to the command-and-control channel, not to model-authored code. ESET reported no infections in its own telemetry at publication, so the articles do not supply a time-ordered field record of access surviving changes. |
| [GTIG's HONESTCUE analysis, February 2026](https://cloud.google.com/blog/topics/threat-intelligence/distillation-experimentation-integration-ai-adversarial-use) | An experimental downloader/launcher requested a model-generated second-stage component. GTIG also saw small iterative changes **across submitted samples**. | Generated second-stage code is distinct from the original program repeatedly rewriting itself. The cross-sample progression is developer-side evolution, with no reported chain of two on-host revisions or independently checked remote-access continuity. |
| [Hortea et al., *The Infinite Mutation Engine?*, October 2026 revision](https://arxiv.org/html/2605.03619v3) | The researchers produced **200 independently generated and validated** offensive-code variants in a local sandbox, using a mock receiver and synthetic files. Some candidates required correction before passing the tests. Their tested cohort still had a shared static signature that covered every generation. Separately, the largest local model they tested produced **126 passing single-stage outputs from 2,480 attempts (5.1%)**. | This strengthens evidence that repeated model generation can yield many functionally checked variants. The **200 units are independent generation runs**, not successive applied changes to one running implant. The mock receiver tested data transfer, not continuing remote control after revisions. The small-model figure is for one stage, not a full payload. |
| [Hortea et al., *From Billion-Scale to Million-Scale Language Models*, October 2026 preprint](https://arxiv.org/html/2610.23534v1) | Seven small models were evaluated on bounded code-generation tasks, including a backdoor task, with execution checks and feedback. The best reported **Pass@5** figures in selected conditions approach 100%. | `Pass@5` means at least one of five candidate generations passed a task check. It does **not** mean a running program survived five code changes. The paper describes an embedded-malware operational scenario, but its measurements are generated task-code correctness in a controlled harness, not deployed model-in-implant behavior or remote-access retention. |

## Attribution and denominators

The [Gen Digital “Promptmorphism” report](https://www.gendigital.com/blog/insights/research/promptmorphism) records rapid changes in loader packaging across days. It explicitly says that the changes could come from LLM assistance, automated build pipelines, or manual refactoring. It therefore supports **variant churn**, not model causation, and its unit is successive distributed samples rather than one running program. This is an excluded candidate for the exact claim.

There is also a [GTIG source inconsistency](https://cloud.google.com/blog/topics/threat-intelligence/ai-vulnerability-exploitation-initial-access): its May 2026 overview describes HONESTCUE as if it requested VBScript self-obfuscation, whereas [GTIG's February technical account](https://cloud.google.com/blog/topics/threat-intelligence/distillation-experimentation-integration-ai-adversarial-use) says HONESTCUE generated a C# second-stage component and explicitly distinguishes it from PROMPTFLUX self-update. The more detailed February analysis is the basis for the HONESTCUE row above. The May overview alone should not be treated as proof of HONESTCUE self-revision.

The studies above count different things: successful service-level tasks, malware capabilities inferred from analyzed code, generated second-stage components, validated independent variants, and best-of-five code generations. None provides a denominator for **successive, model-caused, in-process payload revisions with remote access verified after each**. In particular, a candidate corrected before first use is not a revision of an already working, connected program.

## Updated assessment

The new sources strengthen three component claims: a local model can direct some access-seeking actions in a lab; a malware sample can combine runtime model use with remote-access functionality; and models can generate many test-passing offensive-code variants. They do **not** close the central evidence gap. The reviewed public record still lacks a single time-ordered instance linking two applied model-caused payload revisions to continued, independently verified remote access after both.
