# SilkParasite: plugin loading status versus completed remote task

26 November 2026. Source-only close read of [Bitdefender Labs' full 62-page August report, pinned at commit `08fc949`](https://github.com/bitdefender/malware-ioc/blob/08fc94982f5b27650f7f0e06a9ce7cc4ca0c443d/silkparasite-2026_08/silkparasite-bitdefender-labs-research.pdf) and its [first-party summary](https://www.bitdefender.com/en-au/blog/businessinsights/silkparasite-tracking-china-nexus-apt-across-central-asia). The PDF was text-extracted for this audit; no malware artifact or service was executed.

The report identifies several distinct modular remote-access families, not a single evolving process. Three have especially relevant but different evidence boundaries:

| Family | What the report establishes | Where a version/function claim stops |
| --- | --- | --- |
| **DriveSilkRAT**, pp. 17–25 | The implant polls a Google Drive folder, loads task-supplied .NET assemblies in memory, invokes a common `RunCMD` entry point, and uploads encrypted results. Researchers recovered 12 plugins, analyzed .NET and C++ builds, and counted 37 surviving operator-issued command files as a **lower bound** because files are deleted after execution. | Distinct modules or publisher builds are not successive model-authored revisions of one process. The 37 command files are task observations, not 37 confirmed module activations or successful results; the report does not bind a command/result to each of two active versions. Its roughly 65 identifiers are an upper bound on victim machines because the host identifier can vary and some instances are operator or test systems (p. 3). |
| **CookiETagRAT**, pp. 30–35 | Its design retrieves a requested plugin, maps it into memory, provides a callback for the implant's C2 channel, then invokes an export. | Crucially, `load|success` is emitted **after retrieval/decryption but before mapping or initialization** (p. 34). It is a delivery status, not executable adoption or task success. The authors could not retrieve a plugin, so actual plugin result behavior remains inferred from the callback code. |
| **NomadRAT**, pp. 44–49 | A module is retrieved and reflectively loaded, required exports are resolved, and initialization receives the transmitter callback; the implant then reports `loadsuccess` (p. 48). A separate command can route data to an already loaded plugin. | This status is later in the adoption path than CookiETagRAT's, but it still does not prove the plugin correctly performed a remote task. The report does not publish a two-version same-process lineage or matching post-each-version task/result records. Its local fallback path was not observed in C2 execution and its named fallback plugins were not recovered. |

Bitdefender assesses AI-assisted *development* of this campaign at **medium confidence**, based on indirect code residue and cross-language architecture (summary and report pp. 3, 50, 55). It explicitly says no single clue is conclusive. The strongest clues concern GoginRAT and NodeEdgeRAT rather than a captured model response for the three plugin cases above. The report does not identify a model-generated artifact corresponding to a specific active plugin. Nor does its ability to update or replace components show that two revisions happened inside the same instance; those are architectural options and field components across multiple families.

**Feasibility implication:** field RATs demonstrate that a stable C2 layer can delegate tasks to in-memory plugins, an architecture compatible with later code changes. They also show why an investigator must not accept a generic “load success” event as proof of active code or retained remote function. A future Drexel trace should timestamp the exact artifact, map/initialization result, invoked export, returned command result, and unchanged process identity for **each** accepted revision. The Bitdefender campaign supplies no model-to-two-version chain and no rate for that outcome.
