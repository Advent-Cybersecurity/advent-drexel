# Cloud-written programs and local small-model roles

Advent Cybersecurity source audit, 26 November 2026. Source: [Radovič, Canini, and Pejović, *Should SLMs be in the Driver's Seat?*, arXiv v1](https://arxiv.org/html/2610.14209v1), accepted at the NeurIPS 2026 SLM-Agents workshop. This is a reading of the paper, not a model run. Its role split is relevant because a model *present on an endpoint* need not be the model that writes executable code.

## What was tested

The authors compared a cloud-style ReAct loop, a code-first agent, and a hybrid. In the hybrid, a larger model writes a Python program for each AppWorld task. The program runs on the device and calls a small model only for bounded interpretation of data encountered at runtime. Exceptions may go back to the larger planner, which can write another program, up to five executed attempts. The local small model is **an interpreter of task data, not the code-authoring planner**.

The evaluation has 168 AppWorld Test Normal tasks and 417 Test Challenge tasks, with one run per configuration and bootstrap standard errors over tasks. With Qwen3.6-27B as the planner, the hybrid's Test Normal task success was 60.7% ± 3.8% with a 9B small model, versus 45.8% ± 3.9% for code-first without the local interpreter and 81.0% ± 3.0% for cloud ReAct. On the same Test Normal split, using a 2B local interpreter yielded 61.3% ± 3.7% with that planner, within one reported standard error of the 9B result. This is a narrow-role result; it does not establish that the 2B model can plan or repair executable code itself. Separately, under the paper's full local ReAct setup, models below 5B reached no more than 5.9% on Test Normal and 3.8% on Test Challenge. These are AppWorld outcomes, not Drexel success estimates.

All evaluated models were served with `llama.cpp` on A100 or V100 GPUs. The authors explicitly say token and context counts are resource **proxies** and that edge-device latency and energy remain unmeasured. Thus the result does not provide a CPU-only endpoint memory, time, or energy budget. The five attempts can also leave state from prior executions; the authors reran final programs in fresh environments to bound that effect in their benchmark. That check concerns task-result sensitivity, not continued execution of one resident code image across revisions.

## What it changes in the Drexel argument

Model placement and model role must be separate fields: remote planner, endpoint interpreter, endpoint code author, and evaluator have different capabilities and resource demands. A cloud-written program with a small local interpreter is evidence for a **hybrid architecture**, while the expanded Drexel claim requires exact provenance for two model-caused payload-code revisions active in one identified continuing remote-access process, plus an independent remote result after each. The paper publishes no such process/version/access chain and no endpoint defense telemetry. Its AppWorld figures should not be transferred to that chain or to malware detection.

## Later local security-agent comparator

[Normann et al., *Towards Reliable Local Security Agents*, arXiv v3 (17 November 2026)](https://arxiv.org/html/2603.17673v3) report a post-trained Qwen3 4B agent for Linux privilege escalation from a low-privilege SSH foothold. It can issue shell and credential-tool actions, but is not assigned a coding or self-revision task. On 12 held-out scenarios with ten fresh-container runs each, the trained checkpoint succeeded in 112/120 runs (93.3%) within 20 rounds, versus 95/120 (79.2%) for supervised fine-tuning and 49/120 (40.8%) for the base model. The authors attribute the trained model's remaining failures to one withheld Docker scenario family. Their later prompt audit reports 88.3–91.7% trained success across three prompts on new runs, illustrating sensitivity to the evaluation setup.

The 4B checkpoint is about 8 GB and was served with vLLM on an RTX 5090, so the study does not measure CPU-only endpoint operation. Its reported $0.00213 versus $0.1759 per success comparison is a serving-only estimate under batched concurrency, assumed hardware utilization and lifetime, and electricity cost. It excludes orchestration, container and tool latency, model acquisition, and cold start. The authors' $121.08 post-training estimate additionally excludes trace collection, ablations, tuning, and evaluation. These results show strong narrow-domain local tool-use in the reported laboratory, not local payload revision, resident-image continuity, detection behavior, or a transferable Drexel success/cost rate.
