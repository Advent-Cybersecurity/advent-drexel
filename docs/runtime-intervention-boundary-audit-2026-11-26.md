# Runtime intervention is not necessarily payload-code revision

Advent Cybersecurity source audit, 26 November 2026. These are benign research systems. The audit asks what is changed while work is ongoing and which results can inform a future Drexel study. No model or payload was run for this review.

| Primary source | Intervention and observed unit | What the outcome does and does not show |
| --- | --- | --- |
| [Tan et al., HealBench and HealGuard, v1](https://arxiv.org/html/2609.39086) | An external healing side proposes Python code at an intercepted crash. The execution side runs it inside the paused process and writes back variable bindings; shared mutable objects and external side effects can change even if an attempt fails. The 265 benchmark instances came from 18 repositories after excluding non-resumable errors. | The best tested setting resumed to completion in 38.11% and passed the target test in 28.68% of instances. These are **starting-crash benchmark instances**, and continued runs can encounter later crashes. The healing code primarily repairs *runtime state* and is not shown replacing a retained application-code version. The target test is narrower than general behavior or safety preservation. |
| [Shen and Dong, ARIA, v1](https://arxiv.org/html/2610.20780) | The native integrations may substitute **one pending plain-text agent message per run** after a gate fires. They cannot enact tool-call replacement, multi-event continuation, or historical rollback through that interface. The study trains from verified repair pairs and compares live interventions with paired untreated task runs. | In its in-domain live panel, ARIA reports task success and a task-normalized harmful-intervention rate, including malformed outputs, constraint violations, or score regression against the untreated run. The reported 1.49% and 2.00% harm figures belong to separate Llama-3.1-8B and Qwen2.5-7B panels. A message substitution is neither executable payload-code activation nor a two-change continuity result. |
| [Qi et al., REVISE, v2](https://arxiv.org/html/2609.00643) | “Revision” means a new user instruction or workflow change arriving while a structured agent DAG is still executing. The runtime invalidates affected work and revalidates staged outputs/effects at commit. | The 300 challenging revision/commit executions matched a latest-version oracle under the tested event orderings. The serving-efficiency results use Qwen3-14B on four H100 replicas; they concern workflow recovery and stale effects. No model-authored application-code version is installed in a continuing remote-control process. |

## Implications for the Drexel estimand

1. Record the **object changed**: source/body code, newly loaded module, live state, agent message, workflow requirement, model weights, or configuration. A change to one object cannot silently stand in for another.
2. Record **candidate side effects**, even if the candidate is rejected. HealBench explicitly notes that failed healing code and state-inspection probes may leave mutable state or external effects behind. A future benign two-revision trial would need an independent state snapshot or effect log before the next candidate; rejected does not mean inert.
3. Compare a model-caused change with an **unchanged continuation** at a matched prefix when asking whether intervention helped or harmed. ARIA's harm definition makes a previously passing task that regresses after intervention visible, rather than counting only recovery from failed starts. Its rate does not transfer to Drexel.
4. Test **current-version attribution** and stale effects after each active change. REVISE's commit-time rule is a workflow analogy for this requirement, not evidence that a payload uses it. It also demonstrates why a count of successful revisions needs the target system's actual code and effect provenance.

These sources strengthen the measurement design. They do not change the conclusion that the reviewed public record lacks a joined model-to-two-resident-code-versions-to-after-each-remote-function trace.
