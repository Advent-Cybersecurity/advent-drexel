# Repeated model-caused revisions with retained remote access: evidence audit

Reviewed 2026-11-10. Research question: **Has one running program been shown to make multiple model-caused payload revisions and retain remote access after each revision?** This audit treats that as a conjunction, rather than combining results from different systems. It is a source-based assessment, not an implementation guide.

## What would count

The unit of observation is **one continuing program instance**. The record would have to connect at least two successive model outputs to two applied changes in that instance's payload logic, then independently show remote access still functioning after *each* change. A command generated at runtime, an offline variant, a copied descendant process, and a source edit that is never loaded do not by themselves meet that standard. “Retained access” also needs a measured outcome; a program's assertion that it remained connected is insufficient.

## Evidence by boundary crossed

| [Huang et al., DSC 2024](https://yinminnpapa.com/files/dsc_2024_kou.pdf) | A model rewrote **400** test-malware samples offline; **211/400** compiled and retained the originals' functions on manual verification. In a separate **100-trial** robustness study on a math task, **4%** terminated unexpectedly, **92%** had temporary performance drops, and **14%** finished worse than the initial policy. | Multiple model-driven changes inside live execution are possible; revisions can also destabilize the running system. | The edited logic was an agent's task policy, not a malicious payload. The paper did not test remote access or continuous control across revisions. The robustness percentages are for one math benchmark, not malware. |

The fixed small subset limits generalization. |
| [Darwin Gödel Machine, 2026 revision](https://arxiv.org/html/2505.22954) | The system generated an archive of descendant coding agents, retaining those that compiled and could still edit code. Code-editing ability is not remote access, and benchmark improvement does not show every revision kept every earlier behavior. |
| [EvoCode-Bench, 2026 preprint](https://arxiv.org/html/2605.24110v1) | **13** coding agents were tested on **26** stateful tasks and **227** rounds, with one workspace and agent session per trial for **5–15** rounds and cumulative tests for prior requirements. Best-of-four fail-stop pass rates fell from **46.7%** at round 1 to **21.3%** at round 5 and **7.7%** at round 10. | Preserving previous behavior after serial model-driven software edits is materially harder than passing isolated edits. | The agent edits a benign workspace under externally supplied requirements; it is not itself the continuing edited program. `MT@4` permits four independent attempts, and fewer tasks reach late rounds, so these figures cannot be read as a single-run survival rate. No retained-access chain is reported. |

## Interpretation

The papers support **two separate feasibility components**: live, repeated model-driven self-modification in a benign agent, and model-generated revisions that retain some test-malware functions when produced offline. Persistent coding benchmarks add a measured warning about regression: success on an isolated edit substantially overstates success across successive edits in the same stateful workspace. None of these results measures a remote access channel surviving two applied payload revisions in one continuously running program.

The strongest direct public malware observation remains narrower: Guan et al. report incidental self-code changes with some subsequent task continuation, but neither a quantified serial revision chain nor continued remote access after each edit. PROMPTFLUX is an observed attempt at the idea, not an observed successful end-to-end instance. The existing [feasibility ledger](feasibility-evidence-2026-11.md) covers other nearby prototypes and field claims.

**Current assessment:** the component behaviors make the full hypothesis technically plausible, but the reviewed public evidence does **not establish** that one running program has made multiple model-caused payload revisions while retaining remote access after each. This is an absence of a verified combined record, not evidence of impossibility.

The [second source pass](repeated-revision-followup-2026-11.md) adds a local-model agentic-RAT test, PROMPTSPY, HONESTCUE, and two measured offensive-code-generation studies. It tests their denominators against this same combined claim.

## Evidence still needed

A decisive public study or incident report would identify one continuing process, timestamp at least two applied payload revisions and their model outputs, and independently verify remote access and task function before and after each revision. It would report attempted as well as successful revisions, because a single successful example cannot estimate reliability. A matched record without model-directed changes would also help isolate the model's contribution from the surrounding software. These are criteria for interpreting future evidence, not a proposed build procedure.
