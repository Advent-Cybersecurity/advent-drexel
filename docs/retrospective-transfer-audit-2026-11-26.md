# Retained harness advice and later behavior

26 November 2026. Source-only audit of [Treude and Baltes, *How Do Coding-Agent Harnesses Self-Evolve?*, arXiv v1](https://arxiv.org/html/2610.34938). No agent sessions or code were run for Advent Cybersecurity. This is a study of benign coding-agent harness changes across **fresh sessions**, chiefly context instructions and known-failure files. It does not test a continuing program or remote access.

## Units and selection

Thirty Claude Code task sessions on SWE-bench Verified issues produced 125 retrospective proposals. The researchers and agent implemented 24 eligible proposals, of which 11 produced adaptations evaluable on a later issue; the authors supplied one additional comparison adaptation. Twelve adaptations were evaluated in 13 transfer events. Each event used five fresh original-harness and five fresh adapted-harness sessions on a later issue selected to reproduce the targeted environment problem. Only seven transfer events were *informative* by the authors' rule that at least three original-harness sessions encountered the problem. The sample is selected for transfer relevance, not a random estimate of recurrence or benefit in arbitrary deployment.

The authors separate **encountering** the problem, **coverage** by the retained adaptation, **loading** the change into context, **consulting** a referenced file, and **behavioral recurrence** of the targeted action. Of seven informative events, two adaptations that covered encountered instances eliminated the repeated action; one reduced recurrence, while four did not. A context file was loaded and consulted in the non-improving events too, so exposure to a change does not establish use or effect. On an unrelated control issue, an incomplete known-failure file was associated with extra baseline comparisons in four of five adapted sessions versus none of five originals. Task success differed by at most one session in every event, with no consistent improvement. An adapted SymPy context file removed a failed test command but added a lint instruction; median session time rose from 88 to 156 seconds. These are specific cases with small cells, not general performance rates.

There is substantial human and study-specific mediation. Researchers selected which proposals to implement, chose later issues, and labeled outcomes. The initial 30 tasks included a nonrandom second sample favoring environment problems; 13 of 24 attempted implementations did not produce an evaluable harness change. Two model coders classified proposals, and the first author resolved disagreements. The authors flag incomplete blinding and the possibility that selected later issues overstate usefulness on unselected tasks.

## Relevance to a Drexel paper

This supports a general evidence distinction: *proposal → implemented artifact → loaded state → consulted or executed behavior → measured effect* are separate transitions. For executable revisions, the analogous chain is model output, accepted code, active version in the identified process, and a fresh independent functional result. A task-specific fix may fail to cover a later failure even in the same project, and a retained change can add work. The paper's units are prompts/files and fresh task sessions, so its counts cannot be converted into a two-revision same-process payload probability.
