# Same-base mixed-precision CPU study protocol

Reviewed 2026-11-11. This is a proposed benign model-efficiency experiment, not a completed quantization or quality result. It tests whether a layerwise GGUF representation can reduce complete model-file bytes, peak inference memory, and complete-request CPU work together while retaining a prespecified level of task quality against Q4_K_M on the same CPU host. It does not test broad frontier-model equivalence.

## Why this experiment is next

The [local resource study](inference-resource-study-2026-11-11.md) measured Qwen2.5 0.5B and 1.5B Instruct Q4_K_M files with `llama.cpp` b12283 on a CPU-only VM. It measured synthetic token workloads, not answer quality. The existing Q4_K_M format is already a K-quant mixture: the [pinned quantizer documentation](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/quantize/README.md) says `--pure` disables those mixtures. The experiment therefore tests whether a *different allocation* improves the measured trade-off, not whether mixing is new. A CPU mixed-precision result from [Bhatnagar et al.](https://arxiv.org/html/2509.23729) is a lead, but it concerns a different vision-language model and does not jointly establish preserved quality and complete-request cost for these Qwen files.

The official pinned [0.5B GGUF revision](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/tree/9217f5db79a29953eb74d5343926648285ec7e67) lists an FP16 GGUF of 1,266,425,696 bytes alongside the public Q4_K_M file. The pinned [1.5B revision](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/tree/91cad51170dc346986eccefdc2dd33a9da36ead9) lists FP16 at 3,560,416,288 bytes alongside its Q4_K_M. These exact sizes and the hashes below come from the pinned Hugging Face repository API's file metadata; they still need verification after download. The listings permit same-source construction, but do not disclose the exact recipe used for the published Q4 files. A local read of both public GGUF metadata inventories found `general.quantization_version=2` but no recorded importance-matrix or construction-command key, so that metadata does not resolve the recipe. The new causal comparator must be a *fresh* Q4_K_M made from the same FP16 input, with the same calibration matrix and pinned quantizer as every candidate. Keep the published Q4_K_M as a historical anchor and report any difference from the fresh baseline. Do not requantize the existing Q4 input: the quantizer [warns of severe quality loss](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/quantize/README.md) from that path.

The checked b12283 help and [pinned imatrix examples](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/imatrix/README.md) support this command shape. It is illustrative and has not been run on FP16. Resolve each variable to a recorded absolute path, give `IMATRIX` a `.gguf` extension to match the explicit output format, choose an anchored `TARGET_REGEX` from the fresh reference's tensor map, and add `--parse-special` to the imatrix command if the calibration text contains chat markers. For example, if the fresh map contains a Q4_K `blk.0.ffn_gate.weight`, set `TARGET_REGEX='^blk\.0\.ffn_gate\.weight$'` for a single-tensor diagnostic:

```sh
llama-imatrix -m "$FP16" -f "$CALIBRATION" -o "$IMATRIX" --output-format gguf -ngl 0 -t 4
llama-quantize --imatrix "$IMATRIX" "$FP16" "$REFERENCE" q4_k_m 4
llama-quantize --dry-run --imatrix "$IMATRIX" --tensor-type "${TARGET_REGEX}=q3_k" "$FP16" "$CANDIDATE" q4_k_m 4
llama-quantize --imatrix "$IMATRIX" --tensor-type "${TARGET_REGEX}=q3_k" "$FP16" "$CANDIDATE" q4_k_m 4
```

Freeze the resolved commands and hashes before evaluation. The dry run estimates size; the completed file and its tensor map are the evidence of what was actually built.

The checked local help also offers `--max-buffer-size` to cap rows buffered while quantizing a tensor; if needed, hold that setting constant across the reference and candidates and still measure construction memory.

The same raw inventory groups block tensor payload by role. In the public 1.5B file, `ffn_down`, `ffn_gate`, and `ffn_up` account for 266,434,560, 216,760,320, and 216,760,320 bytes, respectively: 699,955,200 bytes together, or 62.6% of complete file bytes. These are baseline measurements, not attainable savings. `ffn_down` has mixed Q4_K and Q6_K weights, and manual overrides there can shift the default allocation counter. An `ffn_gate` or `ffn_up` group is a more controlled first byte-sensitive probe, subject to the full tensor-map check. All 28 weights in each of those two families are Q4_K in this public file. A one-layer Q4_K-to-Q3_K swap would change only about 1,827,840 payload bytes, or 0.16% of this complete file, based on the [pinned block layouts](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-common.h); this is a format arithmetic estimate, not a measured output-size or performance result. If every `ffn_gate` weight could make that swap with no other change, payload arithmetic gives 51,179,520 fewer bytes, or 4.6% of this file, before container effects. That calculation gives a reason to screen this family but says nothing about quality, RAM, or CPU. The one-layer probe diagnoses sensitivity and tooling; a meaningful file reduction would need an assembled multi-group candidate. The fresh Q4 reference may have a different allocation, so repeat this inventory on that file before fixing groups.

The 0.5B file's 133 `Q5_0` and 13 `Q8_0` tensors all have 896 columns in the GGUF reader; 896 is not divisible by the 256-value K block. The [pinned quantizer source](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-quant.cpp) explicitly falls back from a `Q4_K` target to `Q5_0`, and from `Q6_K` to `Q8_0`, when this divisibility check fails. This explains a plausible route to the observed mixture, but the published file's actual recipe remains undisclosed. It also means a proposed 3-bit K override on those shapes can silently become `Q4_0`; verify the realized type and its CPU cost instead of assigning a bit saving from the requested type. Since embeddings and output account for nearly half of the public 0.5B file, the initial screen that leaves them fixed has a smaller possible file saving than a whole-file bitwidth ratio implies. The pinned official 0.5B tree itself lists Q3_K_M at 432,041,824 bytes and Q4_0 at 428,730,208 bytes, so a lower-bit label does not guarantee fewer complete-file bytes across recipes; those public files have unknown construction details and are not a same-base quality comparison. Use 0.5B as a lower-cost pipeline pilot and test 1.5B separately if construction preflight passes; a 0.5B result alone cannot establish the effect on 1.5B. For each new file, use the [pinned GGUF dump script](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/gguf-py/gguf/scripts/gguf_dump.py) with `--json` to export tensor names, shapes, and types, then verify the map. Its JSON offset is metadata, so compute per-type bytes from the GGUF reader's `tensor.n_bytes` or the script's Markdown tensor table, not from JSON offsets. The pinned `gguf-py` source was staged under `/tmp/drexel-inference-study/llama-b12283-source` for this read-only audit.

The local public-0.5B loader also warned that token 128247, shown as `</s>`, was not marked as a control token and was overridden by the runtime. Record loader warnings and verify tokenizer, chat template, and stop behavior for fresh and public artifacts before scoring their answers. The warning alone does not establish an answer-quality defect.

The [pinned quantizer README](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/quantize/README.md) documents `--tensor-type` regex overrides, `--imatrix`, and output and embedding overrides. The checked local b12283 `llama-quantize --help` also exposes `--tensor-type-file` and `--dry-run`; those two options are not documented in that README. Its examples use per-tensor `q3_k` and `q5_k` names even when the resulting overall file is called Q3_K_M or Q5_K_M. The [pinned source](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-quant.cpp) shows that the first matching manual rule wins, skips that tensor's default mixture heuristic, and may fall back for an incompatible shape. For Q4_K_M, the skipped heuristic advances counters used to assign higher precision to some later attention-V and FFN-down tensors. An override can therefore change types outside its named group, so a one-group sensitivity claim requires a full reference-versus-candidate type-map diff with no unintended non-target changes. If other types shift, use an explicit type-map control that reproduces the reference map, or treat the result as a whole-recipe comparison. Where feasible, hash non-target tensor payloads as an additional check. Explicit token-embedding and output-type options take precedence over general manual rules, except that `per_layer_token_embd.weight` can be named by a manual rule, so freeze these options and avoid overlapping regexes. Q4_K_M does not *require* an importance matrix, but the [pinned GGML kernels](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-quants.c) do use supplied importance weights for Q3_K and Q4_K rows. Audit coverage for the tensors actually changed; missing entries can make those rows take the unweighted path. The shared matrix is a controlled construction input, not a guarantee of quality improvement. These are tool capabilities, not evidence that any recipe will save CPU time or retain quality. The tool documentation says quantization can fully load the source model, so construction RAM and disk may exceed inference costs; report those separately.

## Calibration and candidate selection

Use three disjoint sets: calibration text for the importance matrix, a development set for allocation choices, and a sealed final set for the acceptance decision. Deduplicate exact strings and near-identical templates across them. A mixed-precision result is workload-specific, so record task categories and length distribution; do not call it general capability retention. Freeze the prompt serialization, tokenizer, chat template, and answer checker before testing candidates. [Williams and Aletras](https://aclanthology.org/2024.acl-long.544/) varied calibration data across 1,800 compressed models and found downstream performance differences. Their aggregate quantization ranges were smaller than their pruning ranges: 0.9 to 1.6 percentage points for GPTQ and 0.6 to 1.0 for SpQR, versus 2.4 to 4.8 for SparseGPT and 0.6 to 2.9 for Wanda. These are study-specific ranges, not GGUF imatrix effect sizes. Calibration provenance and a development-only second-corpus sensitivity check are still useful. A second matrix requires rebuilding both Q4 reference and candidate; it cannot be substituted into only the candidate.

The imatrix tool's `--show-statistics` output can diagnose which tensors received observations and summarize activation magnitude, but those statistics are not a validated ranking of complete-task sensitivity. Use actual one-group-at-a-time development outcomes for allocation. In the pinned Qwen public files, the block names distinguish `attn_q`, `attn_k`, `attn_v`, `attn_output`, `ffn_gate`, `ffn_up`, and `ffn_down`; define the intended layer groups from the fresh reference's names and bytes before quantizing them.

First inventory the reference's tensor bytes. Screen reductions only where they can materially shrink the *complete file*. The first controlled probe is a narrow `q3_k` tensor override in one predeclared `ffn_gate` or `ffn_up` layer group of the 1.5B file, chosen from the fresh reference inventory, using `--dry-run` before construction and checking the realized GGUF types after construction. Anchor and escape the tensor-name regex so it matches the declared group alone; the full map, rather than the intended pattern, is the verification record. The pinned Q4_K_M selection logic does not use the gate/up counters to allocate Q6_K tensors, unlike its attention-V and FFN-down counters, but the full tensor-map check remains mandatory. This is a feasibility probe, not a prediction that three-bit tensors will preserve quality or speed. A `Q3_K_S` whole-file option can serve as a broad lower-bit control; per-tensor rules use the actual `q3_k` tensor type named in the pinned quantizer examples, not the whole-file mixture label. Record whether the control uses `--pure`, and inspect its realized type map because shape fallbacks can still prevent uniform tensors. On the 0.5B file, incompatible 896-wide shapes may force `q3_k` requests to `Q4_0`, so keep that model as a pipeline and fallback test. Expand from one group to coarse layer bands or tensor families only after the first result loads and runs, then refine promising bands within a prespecified construction budget. Build and remove temporary candidates sequentially while retaining their hashes, maps, and logs. For each group, measure development perplexity or held-out development task success, complete file bytes, load success, and phase-specific CPU cost. Test a predeclared random allocation of similar measured bytes as another control. Retain sensitive groups at reference precision, or try a higher precision type only when an assembled candidate can still beat reference bytes. Do not assume the most sensitive group from one model or calibration corpus transfers to another.

Use measured size saving and quality change to triage provisional recipes on development data, then build a small prespecified set of assembled candidates. Measure all three resources and task quality on each assembled file before selecting a finalist from the development Pareto frontier; a size-only ranking cannot establish the joint goal. Retest assembled quality because layer effects interact. [MixQuant, a July 2026 preprint](https://arxiv.org/html/2607.23047) reports that layer sensitivity can shift with upstream bit allocation, so a score obtained under FP16 or one isolated swap does not certify the final mixture. [Zhao et al., an October 2026 preprint](https://arxiv.org/html/2610.11226) report 413 of 560 AWQ layer replacements that lowered calibration reconstruction loss nevertheless raised held-out WikiText-2 perplexity in their Llama-3.2-1B-Instruct 3-bit setup. These papers support using proxies for screening, with final assembled quality as the gate. Neither paper measures this GGUF CPU setup.

Choose one finalist using development data and freeze its artifact hash and analysis plan before opening the final set. If multiple finalists are tested on the final set, report the selection and adjust inference for multiple comparisons or run a new untouched final set. If the fresh Q4 baseline is materially worse than the public Q4 on the predefined quality suite, resolve that recipe discrepancy before using it as a practical replacement baseline.

## CPU and memory measurement

Use the same pinned b12283 runtime, host, CPU-only mode, four generation and prompt threads, context size, batch and microbatch sizes, FP16 KV cache type, mmap/load setting, repacking, prompt format, output cap, sampling rule, retry budget, checker, and process lifecycle for reference and candidate. Record exact CLI and build configuration rather than assuming defaults stay fixed. Record CPU model, instruction set, core count, virtualization, kernel, memory, swap, and any CPU affinity or governor setting. The checked b12283 server help defaults `--fit` to on, which can adjust unset resource settings, and defaults GPU-layer selection to auto. Set `--fit off` and `--n-gpu-layers 0` explicitly for both artifacts, set the other resource flags explicitly, and verify the effective context and batch settings in load logs before pairing results. Hold one model process at a time. Interleave model order in paired, randomized blocks, repeat blocks across sessions, and record VM host contention, CPU frequency or thermal state when available, swap activity, page faults, and page-cache policy. Hashing or loading a file warms the cache, so report cold-like starts and warm starts separately instead of claiming a true cold cache without isolation.

The fixed four-thread settings isolate the representation change relative to the previous local study. A separate practical deployment analysis may tune thread count, batch sizes, and mmap policy for each artifact on development workloads, then freeze both configurations before final evaluation. Label that as a different comparison and charge any altered load, memory, CPU, or installation cost; do not silently tune only the candidate on the final set.

The primary regime for this study is a fresh task lifecycle, matching the existing study's one-process-per-run style; the resident-service regime is secondary because it answers a different deployment question. For the primary regime, count from first process launch through model load, prompt processing, generation, checking, and any retries. Freeze whether retries reuse a task's process or relaunch it; with a single-turn CLI, every retry needs another launch, and all launches count. Read `cpu.stat`'s `usage_usec` from a dedicated cgroup before launch and after all descendants exit for the whole-task CPU endpoint; retain per-process user and system time to explain phases. Also report a separate resident-service regime if that matches the intended use. For the resident regime, run serial single-flight requests under one fresh server and cgroup per paired block; record startup and idle intervals separately, use cgroup CPU-time deltas for each request plus its checker, and report the block-level process and cgroup memory peaks. A resident process high-water mark cannot be reset between requests, so do not mislabel its lifetime peak as a per-request peak. Log actual prompt and output tokens and stop reason. Run paired fixed-prompt, fixed-token diagnostics to isolate kernel throughput from candidate-specific answer length. The checked b12283 CLI exposes `--ignore-eos` and `--predict N` for a fixed-length stress run; verify actual token counts and keep this artificial mode separate from natural-task quality and complete-request cost. Report load, prefill, and decode time as diagnostics, but use total CPU-seconds and wall time per assigned task for the main comparison. Do not infer a complete-request gain from generated tokens/s alone.

For a first local harness, the checked b12283 `llama-cli --help` exposes `-ngl 0`, `-t`, `-tb`, `-c`, `-b`, `-ub`, `-ctk f16`, `-ctv f16`, `-lm`, `--repack`, `--no-warmup`, `--seed`, `--temp`, `--single-turn`, and `--no-display-prompt`. Use explicit frozen values for these settings and save the complete command, environment, output, and exit code for every attempt. Its internal warmup is enabled by default, so disable it for the proposed one-shot primary regime or include and report it consistently if the deployment does warm up. A harness must verify that `--single-turn` exits and that captured output separates answer text from diagnostics before any quality score is accepted. The installed binary reports no accelerator in `--list-devices`; still force zero GPU layers and log the runtime backend.

A local one-prompt smoke check on the public 0.5B file confirmed that `--single-turn` exits with code zero, but `llama-cli` stdout includes a banner, prompt, and timing text despite `--no-display-prompt`; its `--output` file contains a labeled user/assistant transcript, not answer-only text. This is a parser warning, not a quality benchmark. Validate answer extraction with deliberately awkward benign formatting cases, or use a structured local server response if the CLI transcript cannot be isolated reliably. The VM lacks `/usr/bin/time`, so use a fresh parent process with per-PID `wait4` for model-process CPU and RSS, plus cgroup counters for all descendant work. A fresh Python parent produced nonzero child CPU and RSS values in the smoke check. Do not silently substitute sampled RSS for a process high-water mark.

The pinned [server API documentation](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/server/README.md) describes `/health` and `/v1/chat/completions`. A local loopback smoke check with the same public 0.5B file, one slot, and CPU-only settings returned structured JSON with assistant content, finish reason, prompt and completion token counts, and timings, then exited cleanly. This supports a reliable quality-harness interface, not answer quality or benchmark readiness. If the server API is chosen, use it for reference, candidate, and public anchor under identical prompt serialization and settings; never compare a server candidate with a CLI reference. Set `--parallel 1`, an explicit `--threads-http` count, and loopback host binding for serial single-flight runs; record their values with the other frozen settings. Record server startup, request, client and checker work in the named lifecycle regime, and verify that API timing fields reconcile with independently measured complete-request CPU and wall time. The smoke output hit its 16-token cap, so no task was scored.

For memory, capture the model process's own peak RSS at exit with a per-PID [wait4 resource result](https://man7.org/linux/man-pages/man2/wait4.2.html), or GNU `time` `%M` wrapped around only that process on hosts where it is installed, plus periodic RSS traces for phase timing. Linux reports `ru_maxrss` and GNU `%M` in KiB; convert before comparing with cgroup byte counters. The [Linux `/proc` documentation](https://docs.kernel.org/filesystems/proc.html) calls `VmHWM` a process high-water RSS and notes approximate asynchronous RSS accounting. A 50 ms sample alone can miss a short peak. Predeclare model-process high-water RSS as the model-RAM endpoint. The [Linux `getrusage` manual](https://man7.org/linux/man-pages/man2/getrusage.2.html) specifies that `RUSAGE_CHILDREN.ru_maxrss` is the largest child's RSS, not a process-tree sum; it cannot identify the model child when client or checker children also run. For whole-task memory, launch the server, client, checker, and descendants inside a fresh dedicated cgroup v2 for each run and record its [memory.peak, memory.swap.peak, and cpu.stat](https://docs.kernel.org/admin-guide/cgroup-v2.html). A fresh group avoids ambiguity from an earlier peak or a file-descriptor-local reset. Cgroup peak includes charged file cache and is a distinct measure from process RSS; label both. Capture `memory.stat` anonymous and file-backed charges at load and request boundaries to explain differences between RSS and cgroup peaks. The [kernel's memory-ownership rule](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-ownership) means a warm model page already charged to a different cgroup need not be charged again to this run's fresh group. Compare cgroup peaks only under a controlled cache-charge regime, or mark that endpoint inconclusive; a fresh group alone is insufficient. A whole-task RAM claim needs a valid cgroup comparison too; if group creation or charge control is unavailable, limit the claim to observed processes. Capture user plus system CPU time, elapsed time, and page faults. If swap activity occurs, separate the runs by swap state and do not claim an unqualified RAM saving caused by paging; a no-swap rerun is the cleaner comparison. Do not use `ru_nswap` as a swap measure; the Linux manual says that field is unmaintained. Include runtime and auxiliary file bytes in an installation total.

On this VM on 2026-11-11, a temporary cgroup under the user `app.slice` was created and removed successfully. A short child launched inside it produced nonzero `memory.peak` and `cpu.stat` values. This verifies the intended isolation primitive, not that the full benchmark harness or its measurements are already validated. The local `llama-cli` reports b12283, commit `f3b407ca1`; its checked SHA-256 is `d6cc36e5fdc2eedd6e052dc7eb1e29d21065331e37e31f57ab2ca4720635dba2`. The local quantizer SHA-256 is `3cb6b1ea8dceca57ae32287b2c91229ff83df127d263becb498d6ee9dd6bdaf1`, the imatrix binary SHA-256 is `4a583e8057e15586b86c30768e61cfb60271031a36bdab9806145af9bb8ec4e4`, and the server binary SHA-256 is `64da0db0262aa9a201b27eccc8fdac336bc42ae990c652d31125c6967665187c`. Recheck these before a later run.

## Final quality gate and decision

Use a prespecified held-out suite of benign, objectively checkable multi-step tasks, such as local code repair against private tests, data transformation with exact outputs, and reasoning problems with fixed answer keys. Keep all execution in a local sandbox without network access. Predeclare task categories, their target mixture, the corresponding final-set sampling fractions, and any category that requires its own quality floor, so a pooled score cannot hide a material loss on an important workload. Record intermediate checks, but define primary quality as correct *final sequence* completion within the same attempt and retry policy for both artifacts. Count failures, timeouts, refusals, invalid outputs, generated tokens, checker calls, and all retries. Use a prespecified absolute success floor and require separate one-sided lower confidence bounds for the baseline and candidate to exceed that floor; a relative noninferiority result is insufficient if either model fails too many assigned tasks. Perplexity and single-step scores are diagnostic, not substitutes for task success.

Prespecify a task-relevant maximum quality loss `δ`, an absolute success floor, the target reductions, and the analysis before final evaluation. Pair candidate and baseline on the same tasks and random seeds. For each artifact's absolute floor, use a one-sided exact-binomial 95% lower bound in the simple unweighted case, and a prespecified task-clustered bound if the design is weighted or has repeated seeds. If final tasks are sampled in the declared target mixture and each task has one scored result per artifact, estimate the candidate-minus-reference full-sequence success difference with a one-sided 95% lower confidence bound using a paired-binomial score method, as reviewed by [Fagerland, Lydersen, and Laake](https://onlinelibrary.wiley.com/doi/10.1002/sim.6148). If the development pilot predicts few discordant task pairs, predeclare an [exact unconditional matched-pair method](https://onlinelibrary.wiley.com/doi/abs/10.1111/j.0006-341X.2001.00478.x) or enlarge the final set rather than rely on the asymptotic score interval. If categories are deliberately oversampled or tasks have multiple seeds, predeclare a weighted, task-clustered interval instead of applying that simple paired-binomial interval to nonindependent or unequally weighted observations. Cluster closely related task templates as well; a hand-picked suite without a defined sampling frame supports only conclusions about that suite. With deterministic decoding, repeated seeds do not create independent answers. Use the development pilot's paired outcome table, especially the two directions of discordance, for a prespecified power calculation under the target task mixture. Lock the final sample size and target power before opening final outcomes; if the required sample is infeasible, label the result underpowered rather than declaring parity. Report paired discordance and raw denominators. A lower bound above `-δ` supports only the specified noninferiority claim. A stricter zero-loss claim would need a margin of zero and enough power; exact output identity is a separate criterion.

File size is exact bytes. Report both the complete GGUF size and the deployed installation total; a smaller GGUF with added auxiliary bytes that erase its installation saving is only a model-file result. For CPU, compare paired total CPU-seconds per *assigned* task, including failed attempts. Define the primary CPU estimand as the arithmetic mean of candidate-minus-reference differences across tasks, averaging prespecified repeated seeds and benchmark blocks within each task first. Use a prespecified stratified paired task bootstrap as the default interval: resample task IDs within each target-mixture category, retain both artifacts and all their repeated seeds and paired benchmark blocks together, recompute the weighted mean difference, and take its one-sided 95% upper percentile. Record the resampling seed and replicate count. Report across-block variation separately; repeated timings are not new independent tasks. If the pilot has too few independent tasks or unstable tails for that interval, enlarge the final set or limit the CPU claim. Report task-level differences and the denominator. Also report CPU-seconds per completed task, with the completed-task denominator visible; this can be unstable or undefined with low success. For peak memory, use the maximum over a predeclared stress set of prompt lengths and **matched realized output-token counts** within each named lifecycle regime; also report peaks from natural task runs. Matched lengths prevent a model that stops early or fails a task from appearing to save KV memory. Report repeated-block maxima without making a significance claim from a single observed maximum. A **full success** requires the same finalist file to beat prespecified meaningful byte, peak-memory, and complete-request CPU thresholds on the same host while passing the held-out relative and absolute quality gates. The RAM gate must name both model-process high-water RSS and whole-task cgroup peak for the chosen regime; a process-only improvement supports only a process-memory claim. For candidate-minus-reference CPU-seconds, the paired interval's upper bound must be below a prespecified negative threshold, `-ε_CPU`, where `ε_CPU > 0` is the smallest worthwhile saving; repeated peak-memory blocks must remain below the reference thresholds in the named regime. Choose these thresholds before opening final data from observed measurement noise and deployment needs. Improvement in only one or two resources is a partial result. Report the resulting Pareto frontier and any quality regression even if the full gate fails. A claim that the finalist is preferable to the currently used public Q4_K_M file must also pass the same resource and quality gates against that public anchor; passing only against a weaker fresh Q4 construction would support a narrower causal claim.

For one finalist and one prespecified all-or-none claim, the four gates act as joint endpoints. The [FDA's 2022 statistical guidance](https://www.hhs.gov/guidance/sites/default/files/hhs-guidance-documents/FDA/MultipleEndpoints_FinalGuidance.pdf) explains why a claim requiring success on *every* endpoint does not create the usual opportunity to choose a favorable endpoint, though this study is not a clinical trial. That logic does not protect a search over many finalists on the sealed set. Specify the candidate-selection rule, analysis family, and any multiplicity correction before opening final data.
