# Project Drexel and adaptive malware: feasibility assessment

Reviewed 2026-11-10; publication wording revised 2026-11-27. This note compares the Project Drexel research hypothesis with published research. It assesses evidence and missing proof; it is not an implementation plan. The [November evidence ledger](feasibility-evidence-2026-11.md) records additional experiment results and their limits. Earlier framing remains recoverable from Git history.

## Scope of the research hypothesis

Project Drexel asks whether a model could cause executable-code changes in a continuing remote-access program while required function persists. The stricter two-revision, same-process chain is an operational research hypothesis, not a claim that such a system has been observed. It is distinct from offline variant generation, model-selected commands, and service continuity across process replacement.

Model placement, environmental observations, change frequency, accepted-version provenance, and after-change function are variables requiring separate evidence. None should be inferred from an “AI-powered” label or an unobserved implementation.

## What public work demonstrates

| Capability in the broader hypothesis | Closest original evidence | What the result leaves open |
| --- | --- | --- |
| Model-requested program changes | [GTIG's PROMPTFLUX analysis](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools) describes an experimental VBScript family requesting rewritten code from Gemini. | The detailed sample's self-update function was disabled. GTIG did not show a deployed program repeatedly applying working revisions. See the [PROMPTFLUX case file](promptflux-case-file.md). |
| Runtime generation of malicious code | [SentinelLABS' MalTerminal analysis](https://www.sentinelone.com/labs/prompts-as-code-embedded-keys-the-hunt-for-llm-enabled-malware/) describes scripts and an executable designed to obtain malicious code from GPT-4. | Investigators found no deployment evidence, and did not show self-revision of a working remote access payload. See the [follow-up](runtime-ai-followup-2026-11.md). |
| Model-gated action within fixed code | [Unit 42's sample analysis](https://unit42.paloaltonetworks.com/ai-use-in-malware/) describes a dropper asking a hosted model whether to proceed after assessing host context. | This changes a decision, not the program's code. The case came from a sample hunt, with no incident telemetry presented for this sample. |
| Model-guided behavior responding to a changing interface | [ESET's PromptSpy sample analysis](https://www.welivesecurity.com/en/eset-research/promptspy-ushers-in-era-android-threats-using-genai/) shows a bounded loop in which updated Android screen state informs another model-chosen action. | The goal is fixed; the sample changes interface actions rather than its own code. ESET had not seen it in production telemetry. |
| Generated code with execution feedback | The [NYU Ransomware 3.0 research prototype](https://arxiv.org/abs/2508.20444) reports model-generated components and a feedback loop that checks whether generated code ran. | The authors say the prototype omits persistence, advanced evasion, privilege-escalation exploits, and lateral movement. It does not establish a field-deployed adaptive remote access tool. |
| Autonomous adaptation across heterogeneous machines | [Guan and colleagues](https://arxiv.org/html/2606.03811v1) report 15 runs in a contained 33-host network, with model-guided propagation across varied systems. They also report several cases of self-code modification after a failed attempt and successful recovery in some cases. | Every test host had an exploitable weakness, and the environment had no endpoint protection or active firewall. The main spread runs used shared inference; a separate test measured setup of a new local model service. The authors do not demonstrate an AI-modified remote access payload in an incident, and the preprint is under peer review. |
| Local inference on constrained hardware | [Anthropic's October 2026 evaluations](https://www.anthropic.com/research/self-replicating-ai) show that small models can complete many component tasks and run on several device types. | The authors say smaller models still make mistakes when composing those tasks and that they have not demonstrated a full rogue replicator. |

The first four rows concern observed malware **samples**; the next three concern **controlled research**. None demonstrates the full Project Drexel chain. The studies also answer different questions: a changed command or interface action is distinct from changed program code, and self-replication is distinct from payload modification.

Earlier HYAS proof-of-concept reports also matter. The developer described [BlackMamba](https://securityboulevard.com/2023/03/blackmamba-using-ai-to-generate-polymorphic-malware/) generating a new component at each launch and [EyeSpy](https://securityboulevard.com/2023/08/eyespy-proof-of-concept/) generating and repairing code in response to its environment. EyeSpy closely resembles the broader hypothesis, but its public article supplies no measured trial results or linked revision artifacts, and HYAS says it was not production-ready. Both are research prototypes, not documented field incidents.

The [VoidLink and PromptLock cross-check](voidlink-promptlock-crosscheck.md) adds two important distinctions. ESET examined a local-model sample that generated scripts but was not seen in attacks. Check Point recovered strong AI-development artifacts for VoidLink version 2.0; Cisco Talos later reported victims using what it assessed as an earlier version 1.0, without observing AI tools in those operations. The family-level link does not establish AI-driven payload revision in those victims.

**New field claim requiring artifacts:** [Mandiant's September 2026 case study](https://cloud.google.com/security/resources/ai-risk-and-resilience-2026) says malware in observed campaigns used embedded lightweight models to alter command-execution strings at runtime. The report provides no named sample, model identification, before-and-after strings, or execution trace. It does not identify the model as an LLM or show repeated source-code revision by a remote access program. The [local-model claim audit](local-model-claim-audit.md) records this as a first-party assertion that cannot yet be independently checked from published artifacts.

## Feasibility judgment

**Partial capabilities have been demonstrated.** Research prototypes have shown model-generated code with feedback and autonomous adaptation in contained environments. Guan and colleagues additionally report self-code changes after failures in several trials. Their result is a stronger controlled demonstration of this particular capability, while still leaving repeated payload revision in an incident unproven. Model placement is a separate Project Drexel condition: reports using hosted inference cannot establish an endpoint-resident custom model. [NYU prototype](https://arxiv.org/abs/2508.20444); [Guan et al.](https://arxiv.org/html/2606.03811v1); [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools).

**The integrated claim remains unverified from published artifacts reviewed here.** A convincing case would connect a running remote access program's observed state, model decision, resulting payload revision, continued function, and deployment in the same incident. A second revision would be needed to support “continuous” adaptation. Mandiant asserts local model-driven runtime change in campaigns but does not publish that chain; PROMPTFLUX and the other cases also do not supply it. The 2026 adaptive-worm study is the strongest controlled demonstration of autonomous adaptation, while its authors explicitly limit the result to an isolated, unusually vulnerable network without active endpoint defenses. [Mandiant](https://cloud.google.com/security/resources/ai-risk-and-resilience-2026); [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools); [Guan et al., limitations](https://arxiv.org/html/2606.03811v1).

The current research question is therefore precise: **has anyone documented AI-caused payload revision, retained remote access function, and repeated operation in one deployed program?** The [runtime-AI evidence audit](runtime-ai-evidence-audit.md) tracks that question across the known public cases. Finding another model-assisted malware sample alone would not resolve it; the causal trace and operational context matter.
