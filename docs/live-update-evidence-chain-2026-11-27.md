# Project Drexel: the accepted-version evidence chain

Jashid Sany, Advent Cybersecurity. 27 November 2026 (America/New_York). Source-only research for a later paper version. No model, agent, malware, defender, or candidate code was run. The four cases below are a purposive subset of the 22 cases in the [31-case ledger](../data/closest-case-claim-ledger-2026-11-26.json) that had not received the newer eight-field extraction. They were selected because they make live executable adoption unusually concrete. The other 18 remain unextracted under that scheme. This is neither a prevalence sample nor an independent reproduction.

## The question behind an apparent successful update

The strict Project Drexel subclaim requires two **model-caused executable revisions** active in one identified continuing remote-access process, with an independent remote task result after each. The four source types reviewed here expose several distinct boundaries:

1. **Proposal to accepted artifact:** A model's suggested text is not necessarily the bytes accepted after validation, human editing, compilation, or file copying.
2. **Artifact to loaded code:** A successful file integration or compile result does not prove the running application loaded it. Loader policy, registry replacement, and later restart can change the result.
3. **Loaded code to selected call path:** A loaded module may not be the module the next request invokes. Cached references, an old module version, or a failed registry swap can leave the old behavior active.
4. **Invocation to retained function:** A version-specific call must produce a fresh, independently checked outcome. A health check that lists exported functions, a service that merely stays alive, or an alert-free candidate does not establish retained remote function.
5. **First to second revision:** The full chain must recur in the same identified process. Two stored versions, two builds, or two sessions are not two accepted active revisions in one process.

This is an **evidence dependency**, not a recipe for constructing the proposed system. Zhu et al.'s [reconstruction-aware authorization study](https://arxiv.org/html/2609.26529v1) empirically shows in a different agent-software setting that a checked object can differ from the version ultimately consumed after reload or rebinding. Its 28 controlled outcomes concern authorization, not Drexel or malware. The transferable methodological inference is narrow: a revision study must identify the exact object/version consumed at the call site, not infer it from an earlier approval or file record. Mattis et al.'s [live-programming position paper](https://www.hpi.uni-potsdam.de/hirschfeld/publications/media/MattisTaeumelBoehmeHirschfeld_2026_LivenessInTheAgeOfAgentsAreWeBackToCompileAndRunCycles_AcmDL.pdf) argues that large agent-generated changes lengthen the generate-and-run feedback cycle. It is a conceptual warning about evaluation latency, not a measured success rate for autonomous live updates.

The evidence is **not uniformly negative**. Asiel and NexAgent disclose concrete executable-code mechanisms, Autopoiesis reports online policy adoption, and Shirudo reports a single live protective effect. The conclusion is narrower: none of these four public records documents the strict two-revision remote-access chain. They also do not establish that a deliberately engineered system could never do so.

## Consequences for the next paper and case audit

The word *active* should require an identified version's behavior to be invoked, not merely copied, compiled, or loaded. For a future benign study, the record would have to join a particular model response, accepted artifact identity, load/selection event, process and image identity, version-specific invocation, and independent outcome **twice in temporal order**. Any failed proposal, fallback, or restart belongs in the same lineage record. This requirement follows from the definition of the claim; the four cases motivate why it matters. It does not imply a field success probability.

These four extractions increase the comparable eight-field coverage of the prior 31-case ledger from seven to eleven cases. The two cases added in the earlier nine-case pilot remain outside that ledger. Eighteen prior ledger cases have not yet been re-extracted; several concern variants, agent configuration, or operator-side builds rather than live code. Completing that audit is the next source-only step. The deposited [version 0.4 preprint](https://doi.org/10.5281/zenodo.24591891) and its archive are unchanged.
