# Project Drexel: platform and policy boundaries for active code revision

Advent Cybersecurity source review, 27 November 2026 (America/New_York). This note extends the [version 0.4 preprint](../paper/drexel-feasibility-v0.4.tex) and the [26 November live-code audit](live-code-activation-boundaries-2026-11-26.md). It examines documented software-update mechanisms and operating-system restrictions. No target application, model, endpoint product, or malware was run.

## Question and method

Which parts of an active-code revision can be supported by documented Windows, Linux, and macOS mechanisms, and which claims require an observed process and policy record? The review is a focused comparison, not a census of all runtimes, kernel configurations, or endpoint products. On 27 November 2026, we searched the official Microsoft Learn, Apple Developer, systemd, and Linux man-pages sites for dynamic-code policy, library validation, executable memory, module loading, and process-image replacement. We checked those results against the primary Kitsune and PROTEOS dynamic-update papers already cited in the preprint. Queries included site-restricted combinations of “dynamic code policy,” “Arbitrary Code Guard,” “hardened runtime,” “library validation,” “MemoryDenyWriteExecute,” “dlopen,” and “execve.” The source inventory below gives the exact pages used. Vendor documentation describes a capability or policy, not its state on a particular host or its empirical success rate.

The strict Drexel subclaim requires an identified continuing application process and image lineage, two distinct model-caused executable revisions invoked in that instance, and an independently checked task after each. Its evidence ladder is therefore:

| Boundary | What a record can establish | What it cannot establish alone |
| --- | --- | --- |
| Artifact written | Exact accepted bytes and their provenance exist. | Compilation, activation, or function. |
| Artifact loaded or installed | A loader or runtime accepted some version. | That the relevant worker called changed behavior. |
| New version invoked | A version-specific behavior ran. | That state and all required functions survived. |
| Process and image continued | Process start, image events, and version calls belong to the same lineage without a qualifying replacement. | Model authorship or a successful independent task. |
| State and function retained | An external oracle observed the required task after activation. | Universal portability or absence of defender telemetry. |

This is a research measurement distinction, not a claim that every legitimate application must update in this way. A service can remain available while a worker is replaced; that useful operational property answers a different question from same-image continuity.

## Cross-platform source matrix

| Platform and path | Documented capability or constraint | Policy scope and status | Consequence for a Drexel evidence claim |
| --- | --- | --- | --- |
| Windows: module load within a process | Microsoft says LoadLibraryW loads a module into the calling process and returns a module handle on success. It may call a DLL initializer. This confirms a load event, not invocation of the particular revised task handler. [LoadLibraryW function (libloaderapi.h)](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryw) | **Documented API, not a default permission guarantee.** Application-specific loader behavior and process image-load policy still matter. | Record the exact module identity and a subsequent version-specific call. A loader return value is insufficient. |
| Windows: dynamically generated executable code | Microsoft's Arbitrary Code Guard (ACG) restricts dynamic executable memory when applied; the dynamic-code process policy can prohibit generating dynamic code or modifying existing executable code. [Exploit protection reference](https://learn.microsoft.com/en-us/defender-endpoint/exploit-protection-reference); [PROCESS_MITIGATION_DYNAMIC_CODE_POLICY structure (winnt.h)](https://learn.microsoft.com/en-us/windows/desktop/api/winnt/ns-winnt-process_mitigation_dynamic_code_policy) | **Optional process/application policy**, with audit and enforce modes; deployed settings take effect when the program restarts. Documentation does not show that ACG is enabled for every process. | A blocked dynamic-code path is a policy-conditioned failure, not a model-quality failure. A no-block observation must be tied to the actual policy state. |
| Windows: image integrity | Code Integrity Guard can restrict which signed binaries a protected process loads; Microsoft also documents image-load policies for certain locations. [Exploit protection reference](https://learn.microsoft.com/en-us/defender-endpoint/exploit-protection-reference); [GetProcessMitigationPolicy function (processthreadsapi.h)](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessmitigationpolicy) | **Optional process mitigation settings**, not a blanket Windows default. CIG's compatibility limits and configured options matter. | Distinguish a failed image mapping from a code-generation or activation failure. Preserve the signed-image and policy context. |
| Linux: dynamic library within a process | The Linux man-pages project documents dlopen as loading a named shared object and returning a handle. Symbol resolution and later application calls are separate from the load result. [dlopen(3) — Linux manual page](https://man7.org/linux/man-pages/man3/dlopen.3.html) | **Documented API, not a default permission guarantee.** Availability depends on the application, library, filesystem, credentials, and configured restrictions. | A library handle does not show that an existing worker switched to the revised function. Version-specific invocation is required. |
| Linux: service executable-memory restriction | systemd's MemoryDenyWriteExecute setting, when enabled for a unit, restricts specified writable/executable memory transitions. The manual notes compatibility limits for JIT-style programs and limits to the protection's coverage. [systemd.exec — execution environment configuration, version 262](https://www.freedesktop.org/software/systemd/man/262/systemd.exec.html) | **Optional service-unit setting, not a Linux-wide default.** Implementation and coverage vary with host architecture and accompanying policy. | Record the service unit, effective policy, architecture, and failure category. The setting's presence does not by itself prove every code-loading path impossible. |
| Linux: image replacement | execve replaces the caller's program image, stack, heap, memory mappings, and other threads. It does not create a new OS process merely by being called. [execve(2) — Linux manual page](https://man7.org/linux/man-pages/man2/execve.2.html) | **Documented system-call behavior.** A preserved PID cannot establish resident-image continuity; some descriptors may persist even though memory state does not. | Record execution/image boundaries in addition to PID and process start. Service or connection continuity after execve must be labeled separately from the strict same-image subclaim. |
| macOS: Hardened Runtime and executable memory | Apple documents Hardened Runtime restrictions and specific entitlements for JIT-compiled or unsigned executable memory. Apple says notarized macOS apps require Hardened Runtime; that does not make every running app notarized or identically entitled. [Configuring the hardened runtime](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime.md); [Allow execution of JIT-compiled code entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit.md) | **Default restriction within an app that has Hardened Runtime; exception entitlements are optional.** The actual signing, notarization, and entitlement state must be known. | Classify a restriction or permission against the app's signed configuration before attributing success or failure to the model. |
| macOS: library validation | Apple says Hardened Runtime enables library validation by default and constrains third-party plug-in/framework loading unless the app has the relevant entitlement. [Disable Library Validation Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation.md) | **Default within Hardened Runtime; exception entitlement optional.** This does not mean every macOS process rejects all dynamic libraries. | A plug-in load failure and a failure to invoke an accepted plug-in are different outcomes. |

The table is deliberately conditional. These primary documents describe mechanisms and policies; they do not measure an AI-generated updater, prove defender invisibility, or establish one universal feasibility result across operating systems.

## Runtime and state are additional boundaries

Operating-system permission to load code is only one gate. The [Kitsune paper](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf) reports live updates in purpose-adapted C programs, including a Tor relay. Its mechanism uses declared update points and data/control migration; its Tor case required application changes and state handling. It demonstrates engineered continuity, not safe arbitrary updates or model-generated revisions. The [PROTEOS paper](https://download.vusec.net/papers/asplos-2013.pdf) evaluated transactional process-level live updates in a research operating system built around state quiescence and transfer. It is a comparator for service and state continuity, not evidence that an ordinary endpoint keeps one resident image unchanged.

Runtime-level adoption can also lag code loading. [Erlang/OTP documentation](https://www.erlang.org/doc/system/code_loading.html) explicitly distinguishes current and old module versions, notes that processes may linger in old code, and describes the effect of introducing a third version. This is a concrete reason that a loader acknowledgement must be paired with a call-path observation at **each** claimed revision. The existing [live-code audit](live-code-activation-boundaries-2026-11-26.md) documents other source-level examples where a reload report, application session, or logical service does not settle active-version or OS-image identity.

## Evidence sheet for a future benign study

The source review identifies fields that should be frozen before any isolated, authorized experiment:

1. **Environment:** OS release and architecture; application runtime and version; whether the program is a service, signed/notarized app, or ordinary user process; relevant policy name, mode, and effective state.
2. **Artifact lineage:** model response or other author, accepted bytes and hash, transformations, rejection history, and whether the change is source, native image, interpreted module, or configuration.
3. **Activation:** write/compile/load result; exact active version bound to a subsequent call; whether an old call frame or handler remained in use.
4. **Instance identity:** process start and end, process identifier plus image-execution events, worker replacements, and any state migration. A single PID or open connection is insufficient.
5. **Function and observation:** a new independent task and result after each version; separate raw events, named alerts, enforcement, and missing telemetry under a declared observation window.

These fields are a measurement specification, not test results. The proper future comparator is a benign client-server application with a deterministic remote task, as the v0.4 preprint proposes. The same application can be studied under explicitly declared policy strata; outcomes must remain per stratum rather than becoming an “any environment” rate.

## Findings and limits

* **Supported:** Deliberately designed live-update systems and ordinary loaders make some active-code revisions technically possible. Documented process protections can constrain particular memory or image-loading paths when they are applied.
* **Conditional:** Windows ACG/CIG, Linux systemd service settings, and macOS Hardened Runtime entitlements differ in scope. Their presence in product documentation is not their effective state on a given endpoint.
* **Unresolved:** No host was inspected, no policy combination was measured, and no defender telemetry was collected for this note. The cited sources provide no probability that a model-authored revision survives two changes or that a defender would or would not alert.
* **Interpretation:** Written bytes, load success, active invocation, same-image lineage, and retained function remain separate proof obligations. Failing one gate may explain a bounded platform outcome without answering the broader feasibility question.
