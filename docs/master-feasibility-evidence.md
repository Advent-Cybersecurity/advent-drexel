# Master evidence: repeated AI-caused payload revision and retained access

Evidence reviewed through 2026-11-27; local experiment status updated 2026-11-25. This is the central, source-linked synthesis for the *Drexel* research question. It aggregates the repository's case files and measured studies; those files retain the detailed source audits. This document is an evidence assessment, not an implementation guide. The [research guide](README.md) indexes the detailed notes.

The [dated search and evidence protocol](source-search-and-evidence-protocol-2026-11-26.md) records the exploratory review's selection rules and limits. The source registry is broad and heterogeneous; it is not a census of independent AI-revising implants.

## The claim under test

**One running program makes at least two model-caused revisions to its own payload code and retains independently verified remote access after each.** This is Project Drexel's stringent serial-revision subclaim. “One running program” means a continuing instance, not separate generated variants, a new replica, or an operator's development process. A model-generated command, interface action, configuration value, or unexecuted source file is distinct from applied payload-code revision.

This review counts an added executable module as a code change only when it becomes active in the same resident process; it identifies module addition separately from replacement of an existing function or program body. The [live-revision note](live-revision-feasibility-2026-11-26.md) gives the operational definition and provenance rule.

To establish the claim, a public record would need to tie together: the same continuing instance; a model output for each of two revisions; evidence each revision was applied; and an independent access/function check after each. The unit of analysis is the **revision chain**, not a count of model calls, candidate programs, or infected hosts.

**Present assessment:** component behaviors are demonstrated, but the reviewed public sources do not document the full chain. This is a limit of the published evidence, not a finding that the chain is impossible or absent in private data.

The [27 November accepted-version audit](live-update-evidence-chain-2026-11-27.md) adds four eight-field re-extractions from the prior 31-case ledger. Across Asiel Core, NexAgent, Autopoiesis, and Shirudo, it separates a proposed or integrated artifact from a loaded version, the selected call path, and a version-bound result. Eleven of the prior 31 cases now have comparable eight-field records; the other 18 remain to be re-extracted. This source-only audit does not change the full-chain judgment or produce a feasibility rate.

**26 November engineering update:** [Live-revision feasibility](live-revision-feasibility-2026-11-26.md) verifies that supported runtimes can replace code inside a continuing program but impose version, state, update-timing, and supported-edit constraints. It separates same-process function from service reachability across restarted workers and identifies the provenance and telemetry needed to decide a two-revision case. These mechanisms do not change the integrated-case verdict.

Endpoint policy is another conditional constraint: [Microsoft's exploit-protection reference](https://learn.microsoft.com/en-us/defender-endpoint/exploit-protection-reference) documents process mitigations that can block dynamically generated executable memory or unsigned image loading when enabled; [Apple's hardened-runtime guidance](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime.md) describes restrictions on JIT and plugin loading with specific entitlements; and [systemd's service-execution reference](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) documents a configurable Linux executable-memory restriction. [Microsoft's script-control guidance](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/script-enforcement) cautions that coverage differs by script host. These are not universal endpoint states or observed Drexel detection results; the [engineering note](live-revision-feasibility-2026-11-26.md) records the mechanism-specific reading.

The same note now distinguishes a fourth model-placement option: a model managed by an eligible browser or OS can be available without a separately shipped model package. A [Chrome-based controlled study](https://arxiv.org/html/2611.25086) used its local model for classification and tool selection, not payload-code revision. [Chrome](https://developer.chrome.com/docs/ai/get-started), [Microsoft](https://learn.microsoft.com/en-us/windows/ai/apis/), and [Apple](https://developer.apple.com/documentation/foundationmodels.md) document different readiness, hardware, distribution, and policy conditions. This is a resource and placement lead, not an observed Drexel chain or evidence that the shared models will produce malicious code.

The strongest benign serial network-continuity example found in this pass is [Hayden et al.'s Kitsune study](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf): successive C program versions were loaded within a running driver process, and several updates to a live Tor relay under load did not break or renegotiate client TLS sessions. This supports a deliberately engineered update mechanism, with explicit update points and state migration. It supplies no model-caused revision or remote-access-payload evidence; [the engineering note](live-revision-feasibility-2026-11-26.md) records the exact scope and limits.

**26 November case update:** [Unit 42's KUKURAT investigation](https://unit42.paloaltonetworks.com/custom-rats-target-southeast-asia-governments/) documents a deployed modular RAT whose core supports runtime capability loading and unloading; [Kaspersky's Emotet monitoring](https://securelist.com/emotet-modules-and-recent-attacks/106290/) observed delivered modules running in the parent process with a response to C2. These strengthen the *non-AI* in-process module precedent. [Zimperium's ArcticRAT analysis](https://zimperium.com/blog/arcticrat-ai-powered-android-rat) reports a live hosted-model query inside a remote-access program, but its output classified harvested data rather than revising code. No one of these sources, and no combination of observations from separate families, establishes the same-process, model-caused two-revision access chain.

A [paired continuous-maintenance study](https://arxiv.org/html/2610.14768) additionally finds that inherited failed behavior, rather than merely the presence of agent-written code, drives much of the measured difficulty of later edits. Its 1,996 later events are Python repository tasks, not implant trials; it reinforces carrying the accepted version and all earlier function checks forward in any serial revision claim.

[WithSecure's GREYVIBE report](https://www.withsecure.com/wp-content/uploads/2026/09/WithSecure_GREYVIBE.pdf) documents operational RAT versions and a watchdog that fetches scripts and launches a stored RAT script when no C2 session is active. It attributes the V2 reconstruction to LLM assistance with high confidence from comments, without a model-to-artifact trace. This is a useful field example of AI-attributed development and script-based recovery, but it does not document two model-caused changes inside a continuing process. See the [case audit](live-revision-feasibility-2026-11-26.md#ai-attributed-revisions-and-fetched-scripts-greyvibe).

**25 November source update:** [Unit 42's campaign review](https://unit42.paloaltonetworks.com/autonomous-ai-agent-threat-campaigns/) documents more than ten July–September agentic campaigns with rapid commands, tailored single-use scripts, and web-shell footholds; the investigators explicitly say they recovered no compiled backdoor or custom C2 framework in that set. Its separate [Cairn campaign analysis](https://unit42.paloaltonetworks.com/cairn-framework-ai-autonomous-attacks/) reports model-directed operations against at least 19 organizations and unauthorized access or data retrieval at ten, without a resident implant revision chain. [GTIG's November report](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold) adds field observations of autonomous frameworks and an exposed `exploit_agent` staging server using both frontier and local models. These strengthen the evidence for external agentic orchestration, not for two model-caused changes within one continuously running remote-access payload. New benign [FeatureLoop](https://arxiv.org/abs/2610.35488) and [multi-turn regression](https://arxiv.org/html/2607.01855v1) studies quantify repair and preservation failures under cumulative coding tasks, but their rates are not implant success probabilities. The [dated audit](feasibility-source-update-2026-11-25.md) records the denominators, additional adjacent sources, and limits. The four-part verdict below is unchanged.

**Fast reference:** [Anthropic's GTG-20006 report](https://www.anthropic.com/threat-intelligence-report-september-2026) documents actor-side modification and redeployment during operations; [Unit 42's C2Agent analysis](https://github.com/PaloAltoNetworks/Unit42-timely-threat-intel/blob/d74de078d0cf3227a97076dbc7b7fc504c49fe7e/2026-10-09-C2Agent-malware.txt) combines a resident model loop, C2, changing builds, and a described upgrade feature; [HYAS EyeSpy](https://web.archive.org/web/20231008233626id_/https://www.hyas.com/hubfs/HYAS_EyeSpy_Proof_of_Concept.pdf) describes in-process generated-module repair; [LLMalMorph](https://arxiv.org/html/2507.09411v2) has the clearest *offline cumulative source lineage*; [Yuan et al.](https://arxiv.org/html/2608.01639v1) check a short remote-control connection for each lab candidate. Each lacks at least one necessary link in the exact claim.

**26 November measurement update:** The [matched-continuation audit](mid-execution-change-audit-2026-11-26.md) shows how to compare a coding agent from the same saved state with and without one *external* workspace change and to verify preservation and fresh evidence. The [failure-detection audit](failure-detection-and-repair-audit-2026-11-26.md) separates missed loss-of-function signals from repair after an experimenter forces recall; the [warrant audit](revision-warrant-audit-2026-11-26.md) checks whether a proposed fix addressed a real failure; and [retrospective transfer](retrospective-transfer-audit-2026-11-26.md) separates an implemented or loaded change from behavior it actually affects. These are adjacent benign studies. None adds a two-revision same-process remote-access observation or a transferable success rate.

[Microsoft Threat Intelligence's 25 November ARTEX review](https://www.microsoft.com/en-us/security/blog/2026/11/25/what-defenders-need-to-know-artex-agentic-ai-framework-threat-actors-abuse/) adds a first-party field characterization: several short-lived, incrementally named web shells can each run a different command while an external agent corrects errors. It separately reports RAT installation as a possible post-compromise action. The model pool can switch providers, but that controller feature says nothing about revisions to an installed payload. This report does not publish the joined Drexel chain; its behavioral hunting guidance is not a measured alert rate for that chain.

[Check Point Research's GearDoor case](https://research.checkpoint.com/2026/silver-dragon-targets-organizations-in-southeast-asia-and-europe/) provides a particularly clear field distinction inside one backdoor: its binary self-update path explicitly **restarts the process**, while its separate plugin path can run an assembly in memory. Neither feature is evidence of two observed, model-caused code versions applied to one continuing instance with remote function checked after each. The report's changing command list is evidence of evolving builds, not an in-process chronology.

[NVISO's 23 November ZQAgent case](zqagent-artex-case-audit-2026-11-26.md) is a closer field pairing of an LLM-driven intrusion framework and a persistent backdoor. NVISO says ARTEX deployed ZQAgent in a Belgian intrusion and analyzes its C2 and remote-action capabilities. The article does not trace the model authoring or revising that code. The documented memory-backed relocation **restarts into a detached process**; it is not an in-place behavioral revision. The report also does not provide an independent command/result sequence after two applied versions. The first-party foothold assessment should therefore be kept separate from the strict four-link claim.

[JFrog's 24 November ARTEX artifact investigation](jfrog-artex-model-artifact-audit-2026-11-26.md) is complementary. Public commits and a leaked operator-container self-test support rapid iteration of malicious model repositories; JFrog attributes the work to an ARTEX task with high confidence but cannot separate model choices from human instructions or map exact model responses to each edit. The self-test was **on the operator's own host**, and the latest second-model configuration would fail under stock `transformers`. Neither repository versioning nor that test is a two-change resident remote-access sequence. The case is also a concrete warning against treating the newest candidate as working merely because it was published.

[AgentWorm v3](agentworm-configuration-persistence-audit-2026-11-26.md) tests a different type of persistence: a model-mediated edit to an agent's instruction/configuration file is reloaded on later single-turn sessions, and one payload category fetches operator-served tasks from a remote URL. Its controlled 2,250-trial success measure joins configuration presence, a fresh-session execution marker, and propagation; a separate 90-trial panel checks the same configuration across five restarts. Neither measure is a two-code-version same-process result. The paper's earlier *ClawWorm* title and changed version details make version pinning important when citing its percentages.

[Asiel Core's pinned source and proposal registry](asiel-core-hot-reload-audit-2026-11-26.md) join an LLM-directed Python plugin revision loop to a same-process loader that imports revised files and replaces hooks. That is a plausible benign implementation path, not just a prompt update. Its 23 committed proposals contain 11 initial integrations and 12 validation failures, all under `self_edit_loop`; none is an `evolution_loop` proposal or a second successful integration to the same target. The executor's post-copy smoke test only compiles Python and the loader's registry is cleared before reload. No public process/version/hook-result trace demonstrates two active model-caused revisions, and the project has no remote-control workload.

[Kujanpää et al.'s production tool-making study](production-tool-versioning-audit-2026-11-26.md) supplies a stronger benign *function-check* precedent: 44 decision-node tools generated against backend traces, a held-out 8,022-case node set, one promoted library, version-tagged production invocations, and a historical 1,500-alarm end-to-end evaluation. Tool construction and repair occur before promotion, with shadow execution and human review. The paper does not disclose two sequential promotions to one resident tool or process identity across them. Its repair example shows that a candidate may fit feedback better while violating the intended calculation, so an independent function oracle matters.

[NexAgent's pinned Elixir code](nexagent-beam-hot-upgrade-audit-2026-11-26.md) implements an agent-facing module-upgrade tool and compiles revised modules inside the running BEAM VM. The hot-reload result can report success even if tool-registry selection did not complete; its health check inspects an exported-function list rather than running a task. The public tests checked in at this commit cover other evolution artifacts and source-path decisions, not a model-authored two-upgrade functional sequence. This supplies another runtime mechanism with a clear **compiled versus callable versus functional** evidence boundary, without a remote-access case.

The [live-code activation audit](live-code-activation-boundaries-2026-11-26.md) adds pinned samizdat and Autolith source as model-callable **mechanism** comparators. Samizdat's checked-in fixture verifies one changed cell through the live registry, while a held-out-pending candidate leaves the old handler active. Autolith's checked-in fixtures verify one changed function and a separate two-layer install/discard sequence; they are human-authored and do not check function after both installs. Its Windows checkpoint exits and boots a saved image. These cases strengthen engineering plausibility without supplying a model-authored two-revision remote-control trace. Poiesis's documented logical job PID with re-exec likewise cannot substitute for uninterrupted resident-image evidence.

[Radovič et al.'s edge small-model study](edge-model-role-split-audit-2026-11-26.md) separates **cloud code authorship** from **local data interpretation**. A 2B local interpreter can help a larger planner's AppWorld program, but the small model does not write or revise executable code in that design. All models were served on A100/V100 GPUs and edge CPU latency/energy were not measured. Its task results cannot be used as evidence that a small endpoint model can cause two resident payload revisions or that such activity evades monitoring.

[Normann et al.'s local security-agent study](edge-model-role-split-audit-2026-11-26.md) provides a different narrow-role comparator: a post-trained 4B model succeeded in 112/120 held-out Linux privilege-escalation runs with shell and credential tools. Its approximately 8 GB checkpoint was served on an RTX 5090; the quoted cost advantage is a serving-only estimate. The agent did not author or revise its own code, and the study measured neither CPU-only endpoint operation nor the serial resident-version and after-each remote-result chain.

[SafeDep's Hermes/LeadStack investigation](safedep-hermes-backdoor-audit-2026-11-26.md) describes malicious npm packages designed to install a general-purpose AI agent as a remotely tasked service. The nine published package versions changed delivery mechanisms at the *publisher*, and the downloaded persona is configuration rather than executable-code revision. SafeDep did not observe a victim installation or recover later downloaded payloads. The source therefore supplies an attempted AI-agent-as-backdoor architecture, not an active two-revision process or access result. It is separate from ThreatDown's earlier CARBONATO campaign, which also installed Hermes Agent without documenting model-caused resident-code change.

A [runtime-intervention source audit](runtime-intervention-boundary-audit-2026-11-26.md) separates three more meanings of “revision.” [HealBench](https://arxiv.org/html/2609.39086) executes model-written recovery code against live state, [ARIA](https://arxiv.org/html/2610.20780) can substitute one pending agent message and measures harm against an untreated continuation, and [REVISE](https://arxiv.org/html/2609.00643) handles new workflow instructions with dependency and stale-effect checks. Their measured units are not resident payload-code versions. HealBench additionally warns that even rejected attempts can leave state or external effects, which a future two-revision cohort must record.

A separate [HARD defense-evolution study](revision-selection-and-transfer-audit-2026-11-26.md) shows that accumulating 97 action-gate rules over five rounds can substantially improve a training split while producing only a small held-out gain on a long-horizon attack benchmark. That is a transfer and collateral-utility warning for any iterative acceptance rule; it is not an implant experiment or a Drexel reliability estimate.

[Pianese et al.'s smaller-model PowerShell study](powershell-model-proxy-audit-2026-11-26.md) reports an 84.5% median overlap and 48.4% exact match of selected triggered Sigma-rule sets for its best native model, conditioned on 212 reference scripts with at least one rule trigger. These are behavior-proxy comparisons in separate restored VMs with endpoint protection disabled, not working remote-control or detection-evasion rates. The reported quantized arm was also inferred on a four-A100 research system, so it does not measure an endpoint CPU revision budget. No two-version same-process trace is supplied.

[OpenAI and Cisco's Shirudo demonstration](shirudo-live-shield-audit-2026-11-26.md) provides a recent, closer **benign single-change** case: a Codex-generated Java guard was reportedly attached to a running Elasticsearch process, with published install/reject log events and continued service operation. The public record does not expose exact model-to-bytecode provenance, process ID, or two accepted active versions. The project's default Java-agent documentation says `JAVA_TOOL_OPTIONS` reaches JVMs when they start, so that path alone cannot explain a live attachment. This is no remote-access payload or C2 test and does not alter the four-link verdict.

A close read of [Bitdefender's full SilkParasite report](silkparasite-plugin-result-audit-2026-11-26.md) shows a field remote-access implementation in which DriveSilkRAT loads task-supplied .NET plugins and returns results via the same Google Drive C2. It also exposes an important **false adoption signal**: CookiETagRAT sends `load|success` after plugin retrieval/decryption but *before* mapping or initialization. NomadRAT's later `loadsuccess` follows initialization, still before a demonstrated task result. Bitdefender's AI-development assessment is medium-confidence inference from indirect clues, not model-to-plugin provenance. The report describes several different families, no two active versions of one model-written module in one process, and no after-each-version access check.

## Four-part evidence check

Here **shown** means the published record identifies an observation or trace for that part; **described** means a first-party account states the behavior without a checkable sequence; **unshown** means the paper does not provide that link. The columns apply to *payload-code* changes in a continuing instance, so parameter changes and fresh candidate executions are labeled separately.

The [structured closest-case ledger](../data/closest-case-claim-ledger-2026-11-26.json) currently encodes 31 selected component cases with source IDs and explicit `not_shown` versus `outside_scope` values. It is a cross-reference for this narrative review, not a sample from which to estimate prevalence. A [27 November bounded re-extraction](case-evidence-update-2026-11-27.md) revisits seven of them and adds two comparators; it does not recode the other 22.

## What the evidence supports

1. **The component mechanisms are feasible under defined conditions.** Offline model-directed test-malware rewrites passed original-function checks, benign agents revised their own running logic, and Kitsune updated a live network service across successive developer-prepared versions while retaining client connections. These are different systems with different acceptance gates; their successes cannot be combined into a measured end-to-end Drexel success rate. [Huang et al.](https://yinminnpapa.com/files/dsc_2024_kou.pdf), [Gödel Agent](https://arxiv.org/html/2410.04444), [Hayden et al.](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf).
2. **Runtime model use can coexist with malware functions.** PROMPTSPY's analyzed code combines model-guided interface actions and a remote-access module; HONESTCUE asks for generated second-stage code. Neither analysis demonstrates repeated model-authored edits to a connected program. [ESET](https://www.welivesecurity.com/en/eset-research/promptspy-ushers-in-era-android-threats-using-genai/), [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/distillation-experimentation-integration-ai-adversarial-use).
3. **Successive edits are a reliability problem.** EvoCode-Bench's persistent-workspace results lag its isolated-round results, and Gödel Agent records temporary drops and unexpected terminations. Tayebati et al. show that even a change which fixes its immediate failure can break behavior that worked before. Those studies measure benign tasks but are directly relevant to the requirement that earlier function survive later edits. [EvoCode-Bench](https://arxiv.org/html/2605.24110v1), [Gödel Agent](https://arxiv.org/html/2410.04444), [Tayebati et al.](https://arxiv.org/html/2609.24130).
4. **Revision counts are not progress counts.** In benign persistent-skill work, many candidates never become a distinct validation best; in evolutionary coding traces, previously discarded lines often return. These studies give concrete reasons to retain per-version outcomes, failures, and rollback history when evaluating any serial-revision claim. [Liu et al.](https://arxiv.org/html/2608.02636), [Pelleriti et al.](https://arxiv.org/html/2605.20086).
5. **The exact combined claim remains unverified publicly.** The closest malware cases have different missing links: model output without applied code (PROMPTFLUX), applied agent edits without a measured serial chain (Guan), runtime AI and remote-access code without payload revision (PROMPTSPY), cumulative offline source lineage without a continuing implant (LLMalMorph), attacker-side redeployment without published access checks (Anthropic), and a field assertion without published artifacts (Mandiant).

## Source-quality cautions

- [COGENT's IEEE conference abstract and the related author thesis repository abstract](cogent-endpoint-claim-audit-2026-11-26.md) describe model-guided code variants and a 45-run bidirectional C2 endpoint matrix, respectively. The full conference methods were unavailable here and the thesis PDF is restricted; the two abstracts do not show that the matrix measured in-process revision cycles. Neither publishes a one-process, two-active-version, after-each-access trace. The thesis's no-relevant-alert result is bounded to its tested controls and run windows; it separately reports ARGUS detection.
- [Prinos and Brush's commercial EDR study](commercial-edr-observability-audit-2026-11-26.md) demonstrates that delayed/throttled telemetry, vendor-specific attribution units, and autonomous-response state can alter alert and block interpretations. Its NodeZero policy-agent outcomes are not Drexel detection probabilities. A future benign study needs product configuration, telemetry coverage, lag window, reset history, and independent application-side function results.
- [Sugio and Ito's fixed Windows analysis](generated-artifact-detection-audit-2026-11-26.md) flagged all six reported baseline/obfuscation conditions for functionally checked model-generated executables under static and dynamic Hybrid Analysis. These are conditions rather than a disclosed independent-trial denominator; the source uses offline wiper/keylogger artifacts and a fixed packaging pipeline, not a live remote-access revision. It refutes an automatic-invisibility claim without supplying a Drexel detection rate or directly contradicting COGENT's different setup.
- [Kan et al.'s trusted-tool update experiment](tool-update-adoption-boundary-2026-11-26.md) scores normal task completion separately from an unauthorized side effect after one researcher-authored implementation update. The updated tool may be adopted through server replacement or reconnection, so logical tool identity and preserved output do not imply process continuity or behavioral safety. Its task percentages are unrelated to a model-authored two-revision remote-access rate.
- [Kim's controlled one-round code-refinement comparison](feedback-directed-revision-audit-2026-11-26.md) keeps each model–task initial candidate identical across two revision protocols and separates repair from regression. Diagnostic feedback improved or held pass rate in all 21 model–benchmark cells in the first run, while feedback-free critique commonly degraded it; diagnostics still missed many final-test failures. These standalone Python tasks and GPU-served local models cannot set Drexel's serial update success or endpoint resource rate.

- [Check Point Research's July 2026 AI Security Report](https://engage.checkpoint.com/state-of-ransomware-q3-2026/items/report--ai-security-report-2026) says LAMEHUG generated its **code** on demand and groups LAMEHUG with PromptLock as runtime-model malware seen “in the wild.” The original [CERT-UA notice](https://csirt.csi.cip.gov.ua/en/posts/apt28-targets-security-and-defence-sector-with-ai-powered-software) says LAMEHUG generated **commands** from text descriptions, and [GTIG's sample analysis](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools) specifies one-line commands. GTIG classifies PromptLock as experimental. The summary does not supply a new code-revision trace; retain the original case classifications rather than converting its wording into evidence of runtime payload rewrite.
- [GTIG's May 2026 overview](https://cloud.google.com/blog/topics/threat-intelligence/ai-vulnerability-exploitation-initial-access) describes HONESTCUE as if it requested VBScript self-obfuscation. Its [February technical account](https://cloud.google.com/blog/topics/threat-intelligence/distillation-experimentation-integration-ai-adversarial-use) instead describes model-generated C# second-stage code and expressly distinguishes HONESTCUE from PROMPTFLUX's intended self-update. [AhnLab's later overview](https://www.ahnlab.com/en/contents/content-center/36185) repeats the VBScript attribution. The detailed account controls this classification; the [PROMPTFLUX case file](promptflux-case-file.md) records the within-publisher and downstream source drift.
- [Gen Digital's “Promptmorphism” report](https://www.gendigital.com/blog/insights/research/promptmorphism) observed rapid loader variation but names AI assistance, automated builds, and manual refactoring as alternative causes. Variant churn alone cannot establish a model-caused change in a running instance.
- “Pass@5” in [Hortea et al.](https://arxiv.org/html/2610.23534v1) estimates whether at least one of five **independent** candidate scripts passed an isolated task check; even a near-100% setting is not sustained control-channel success. Its experimental orchestrator ran generated scripts in separate child processes and bounded repair of failed candidates. It did not embed a model in one continuing implant. Similarly, the **200** validated variants above were separate generation runs.
- [LLMalMorph's](https://arxiv.org/html/2507.09411v2) most relevant result is cumulative *offline* source evolution. Its 618 compiled variants are not 618 confirmed functional variants, and its remote-control sample's reported preservation percentages are API-sequence proxy scores, not verified access continuity.
- [Yuan et al.](https://arxiv.org/html/2608.01639v1) provide stronger function evidence by requiring a short live control connection, but their threat model explicitly places generation and compilation offline. The paper's **630** uploaded samples correspond to 3 × 7 × 30 run instances; each run could include several refinements, and each VM was restored to a clean state after tests.
- [Rigaki and Garcia](https://www.stratosphereips.org/s/Bringing_a_GAN_to_a_Knife_fight_submission_draft.pdf) show that model-driven **behavior** can change while control traffic continues. They modified the RAT code beforehand to accept model parameters; the running model did not generate or apply new payload code. Their tables and prose disagree on whether results aggregate five or ten repetitions.
- [Anthropic's field report](https://www.anthropic.com/threat-intelligence-report-september-2026) blends observed use of Claude to modify and redeploy detected artifacts with descriptions of an agent workflow *designed* to keep iterating. It does not publish a count of successful serial revisions, and “full remote access capabilities” is a feature description, not a measurement of reconnection after changes.
- [Sysdig's JADEPUFFER reports](https://www.sysdig.com/blog/jadepuffer-agentic-ransomware-for-automated-database-extortion) show unusually dense, context-sensitive revision of attack requests, but the agentic attribution is an inference from payload style and timing; investigators say they lacked the agent's prompt or configuration. The [later campaign](https://www.sysdig.com/blog/jadepuffer-evolves-the-agentic-threat-actor-deploys-ransomware-built-to-destroy-ai-models) links an operator through shared contact information, while its six-script iteration is external to any one implant process.
- [Bitdefender MDR's 3AM report](https://www.bitdefender.com/en-us/blog/businessinsights/3am-ransomware-hybrid-ai-attack) is unusually explicit about attribution limits. Its telemetry documents successive artifacts and pacing, but the unmanaged attacker-side host was outside its visibility. The authors present a hybrid AI reading as a working interpretation, not an observed model trace, and acknowledge that a person moving text between a model and shell could look similar.
- [GTIG/Mandiant's ARTEX report](https://cloud.google.com/blog/topics/threat-intelligence/artex-and-friends-enter-agentic-offensive-frameworks) aggregates several incidents. Its webshell correction trace, script redeployment example, and separate C2 observation cannot be combined into a single same-process revision chain. The JSP candidates had different filenames and executed different commands; some corrected prior errors and eventually returned valid output, but the report does not show two successful code revisions of one persistent web shell with access checked after each. The report's maturity-stage summary of HONESTCUE and PROMPTSPY does not add a new serial-revision measurement to those earlier sample analyses.
- [Unit 42's November agentic-campaign review](https://unit42.paloaltonetworks.com/autonomous-ai-agent-threat-campaigns/) describes distinct script payloads and process chains, and expressly reports no recovered compiled backdoor or custom C2 framework among hundreds of scripts. Its Figure 9 caption says scripts execute "under the same process," while the explanation identifies the same **process chain** and the figure shows multiple processes. The [close audit](unit42-agentic-webshell-boundary-2026-11-26.md) also separates five web-shell variants across more than 40 paths from active versions of one instance, and identifies the two WMI-backdoor versions as a comment-language change without functional post-version results. None is proof of same-process code revision.
- [Check Point Research's operator-console access](https://research.checkpoint.com/2026/hacking-on-autopilot-inside-artex-cybercrime-campaigns/) is stronger evidence of actual model control than stylistic attribution from victim-side logs. It still concerns an external framework and has no resident implant lineage. [CrowdStrike's separate ARTEX campaign](https://www.crowdstrike.com/en-us/blog/vapor-panda-uses-artex-to-scale-global-campaign/) demonstrates why observed C2 traffic should not be assigned to model-caused revisions without a link to the specific backdoor version. [ReliaQuest's case](https://reliaquest.com/blog/threat-spotlight-how-ai-agents-turned-one-exposed-endpoint-into-a-server-takeover/) likewise distinguishes code running inside a victim application from code self-revision by an implant.
- [Kaspersky's CyberStrikeAI investigation](https://securelist.com/tr/cyberstrikeai-attacks/121715/) reports one implant version across each observed incident. Its server-side agent can direct commands while the resident program remains unchanged; server version updates must not be counted as payload revisions. This is explicit negative evidence against assuming adaptation of the controller entails self-modification of its implant.
- [Liu et al.](https://arxiv.org/html/2608.02636) separate candidate updates, validation bests, selected skills, and released-test gains. Their benign skill results must not be converted to a per-payload success rate. [Pelleriti et al.](https://arxiv.org/html/2605.20086) count byte-identical line reintroductions; this is a code-change quality indicator, not a direct measure of lost function.
- [Tayebati et al.](https://arxiv.org/html/2609.24130) report **211/383** among replay-decided *rejections*, not among all 2,306 proposed changes. The result quantifies observed conflicts in sampled benign-agent behavior, not the probability that a payload revision will fail.
- [HealBench](https://arxiv.org/html/2609.39086) separates mere execution completion from target-test passage. It also warns that live healing code can affect later behavior even when its immediate test passes. The paper mentions possible successive crashes but does not publish a same-process two-repair access-continuity chain.
- [MOSS](https://arxiv.org/html/2605.22794) preserves agent user-state files across a **container replacement** after one reported evolution cycle. That is service lineage, not identity of one continuously running process.
- The [archived HYAS EyeSpy whitepaper](https://web.archive.org/web/20231008233626id_/https://www.hyas.com/hubfs/HYAS_EyeSpy_Proof_of_Concept.pdf) adds detail absent from short summaries: an in-process retry loop for generated modules. Its “corrected” code is not a measured sequence of successful remote-access payload revisions, and the paper says the demonstrator did not implement a weaponized deployment.
- [Unit 42's browser proof of concept](https://unit42.paloaltonetworks.com/real-time-malicious-javascript-through-llms/) demonstrates functional model-generated code assembled at runtime, but its statement that the final prompt worked “in most instances” has no denominator. Its suggestion that the method could later support a C2 channel is a proposed application, not a measured result.
- The [Symbiont author repository](https://github.com/MathisWellmann/symbiont/blob/3cedf3cced44d1a85e7c8e3cb60afbbe0e41dc6e/README.md) describes hot-loaded model-generated function revisions in a benign running program. Its [own caveats](https://github.com/MathisWellmann/symbiont/blob/3cedf3cced44d1a85e7c8e3cb60afbbe0e41dc6e/CAVEATS.md) warn that revision-scoped state can reset or become incompatible, retained versions accumulate resources, and generated code can hang. These are relevant failure modes for interpreting “same process survived,” but the repository is not an independent C2-continuity experiment.
- [FIRSTCON26's primary abstract](https://www.first.org/conference/2026/program) announces a self-modifying agentic-malware emulation rig, but has no quantitative or trace evidence for this claim. The available [FIRST video listing](https://www.youtube.com/watch?v=K2_ZnEECI7o) restates the abstract; slide and caption content could not be verified from accessible primary material, so third-party demo descriptions are not included as outcomes.
- [Joe Security's NETRYX analysis](https://joesecurity.org/reports/report-a9e404dd7afad8c1a3e176d456ecf293.html) found a compiled model-query feature, but explicitly did not establish a completed query or a path that turns model output into remote commands. A model API reference inside a remote-access program is therefore insufficient evidence of autonomous adaptation.
- [Unit 42's C2Agent analyst note](https://github.com/PaloAltoNetworks/Unit42-timely-threat-intel/blob/d74de078d0cf3227a97076dbc7b7fc504c49fe7e/2026-10-09-C2Agent-malware.txt) distinguishes a described model tool loop, changing binaries seen over 29 days, and an upgrade feature added to a later build. None establishes that the model caused those binary changes or that two upgrades occurred in one running process. The authors explicitly say at least one available feature had not been observed in use, underscoring the difference between capability and field execution.
- [Unit 42's sample analysis](https://unit42.paloaltonetworks.com/ai-use-in-malware/) shows why printed “dynamic adaptation” messages require code-path verification: the purported changes were mostly labels written to logs. In the separate dropper, model output gated execution of a fixed payload rather than revising it.
- [IBM's Slopoly report](https://www.ibm.com/think/x-force/slopoly-start-ai-enhanced-ransomware-attacks) illustrates another false combination: probable AI-assisted development and week-long access occurred together, but IBM expressly found no self-revision in Slopoly. Its title-like code comment calling the client polymorphic was not borne out by the analyzed behavior.
- [Unit 42's CL-UNK-1211 account](https://unit42.paloaltonetworks.com/ai-campaign-targets-linux-infrastructure/) similarly places AI-like scripts and a working RAT in one campaign, but its attribution is based on code comments and style, and the RAT's code is not shown changing. Co-occurrence across a toolkit does not prove that the connected component was model revised.
- [Madani's 2024 paper](https://arxiv.org/html/2410.23894) uses “metamorphic malware” in its framing, but its quantitative experiment is on HumanEval functions. Its variation@10 statistic measures distinct correct candidate solutions per task; it is not a serial revision survival rate.

## Evidence that would change the assessment

An original report would need a time-ordered trace of one continuing instance that links two model outputs to two *applied* payload-code revisions and checks remote access and task function after each. It should count attempted and failed revisions as well as successes and separate model decisions from operator changes. An independent host or controller-side measurement would be stronger than the program's self-report. These are criteria for judging future reports, not a build procedure.

## Compact-model resource feasibility: separate research question

The model-efficiency question is whether file size, active memory, and compute can fall together while measured quality holds. This is distinct from the payload-revision evidence claim above. The detailed [compact-model review](compact-model-deep-research-2026-11-11.md), [new evidence audit](compact-model-evidence-update-2026-11-11.md), [CPU-only local inference study](inference-resource-study-2026-11-11.md), [exact GGUF archival test](lossless-model-compression-study-2026-11-11.md), and [current decision memo](frontier-efficiency-decision-memo-2026-11-12.md) contain methods, measurements, and source limits.

**Later experiment status, 2026-11-21:** A Q4_K_M reference and Q4_K_S candidate were exported from one pinned F16 GGUF, with [source revision, hashes, and file sizes recorded](../data/qwen3-same-source-artifact-provenance-2026-11-21.json). The reference passed a public 32-case benign development screen in both task families, and a [240-case held-out manifest](../data/qwen3-same-source-structural-eval-2026-11-21.json) was frozen before evaluation. The reference run was [interrupted after 73 requests](../data/qwen3-same-source-structural-eval-reference-interrupted-2026-11-21.json) when the study was paused. The candidate was not evaluated on that manifest, and the final paired resource trials were not run. This supplies neither a completed held-out quality result nor a four-gate finding. The community F16 GGUF has not been verified tensor by tensor against the official BF16 checkpoint.

**Measured here:** An earlier zstd/gzip check reduced the two existing Q4_K_M GGUF files by 2.26% to 2.94%, with byte-exact restoration. We also [tested foldz v0.9 on both files](../data/foldz-storage-check-2026-11-11.json): its complete archives saved 5.16% on the 0.5B file and 7.64% on the 1.5B file. High-setting zstd (`-19 --long=27 -T4`) saved 3.03% and 2.49% on those same files; prior zstd level-nine runs saved 2.94% and 2.37%. Every restored file matched its original SHA-256. With four foldz threads and zstd's default restoration settings, foldz restoration took 47.3/17.9 seconds versus zstd's 0.28/1.21 seconds for the two files. foldz archive operations peaked at 0.78 to 1.11 GiB process RSS. The timing and RSS are host-specific archive costs, not inference savings; the tested loader cannot infer from `.foldz`. The [foldz author](https://github.com/nsiddiqui248/foldz/blob/c1b69d5672a2b44440e3487c3d6dd3980837665f/README.md) reports 7.55% to 12.94% savings across nine public files, including a Qwen2.5-1.5B file whose listed size and savings match our 1.5B result; its file hash is not published. On this CPU-only VM, the two existing model files were about 491 MB and 1,117 MB; for the shorter inference-study workload, sampled median peak process RSS was 570 MiB and 1,752 MiB. That study did not measure answer quality. These results do not predict performance on another host.

**New same-base CPU pilot, 2026-11-12:** The [fresh GGUF experiment](same-base-quantization-pilot-2026-11-12.md) verified one official Qwen2.5-1.5B FP16 input, built a fresh Q4_K_M reference, and changed exactly 14 `ffn_down` tensors from Q6_K to Q4_K in a second file. A complete tensor audit found identical payload bytes for every unchanged-type tensor. The candidate saved 49,674,240 complete file bytes, or 4.45%. With the pinned runtime's default CPU repacking, five alternating short synthetic pairs had lower candidate CPU-seconds but **higher peak process RSS in all five**. With repacking disabled for both files, five 128/64 and five 512/128 warm-cache pairs had lower candidate CPU-seconds and peak process RSS in every pair. A separate [cold-cache cgroup pilot](../data/frontier-cpu-cold-cgroup-pilot-2026-11-12.json) admitted all ten 512/128 processes only after zero prelaunch file residency, fresh-scope checks, and model-page charge ownership checks; candidate CPU-seconds, process peak RSS, and cgroup `memory.peak` were lower in every pair. Median paired differences were -1.2645 CPU-seconds, -49,770,496 process-RSS bytes, and -50,946,048 cgroup-peak bytes. These are synthetic measurements on one host, not complete task costs. The [frozen public multistep diagnostic](gsm8k-pair-diagnostic-2026-11-12.md) failed its absolute-quality floor for both models because its exact final-answer format was usually absent. No quality-preservation claim follows. The pilot is a bounded resource observation, not a compression breakthrough or a frontier-model comparison.

**Output-head pilot and closest prior:** We built a second complete GGUF from the same FP16 source, changing only `output.weight` from Q6_K to Q4_K. The [tensor audit](../data/output-head-q4-pinned-map-2026-11-12.json) found the other 338 tensor payloads byte identical. The file is 60,166,656 bytes (5.38%) smaller than the fresh Q4_K_M reference. In five paired 512/128 warm-cache, no-repack runs, it used less full-process CPU time and lower peak process RSS in every pair; the median CPU times were 27.813 versus 25.689 seconds and median RSS values were 1,278,074,880 versus 1,217,818,624 bytes. A direct five-pair comparison also favored this file over the simpler Q4_K_S control on CPU time and process RSS at 512/128. The [accepted cold-cache no-repack cgroup rerun](../data/frontier-cpu-head-cold-cgroup-pilot-2026-11-12.json) favored it over Q4_K_M on CPU time, process RSS, and cgroup peak in all five pairs; its first attempt was rejected for prelaunch page reclaim. The [accepted cold-cache default-repack repeat](../data/frontier-cpu-head-cold-cgroup-default-repack-2026-11-12.json) reversed the cgroup peak result: candidate `memory.peak` was higher in every pair, by a median 73,035,776 bytes, despite lower child CPU and process RSS. The [resource note](output-head-cpu-pilot-2026-11-12.md) and [decision memo](frontier-efficiency-decision-memo-2026-11-12.md) record protocols and limits. The Q4_K_M reference solved only 5/8 arithmetic and 3/8 ordered-state development cases with the best tested prompt in the [generated-quality protocol](generated-multistep-quality-protocol-2026-11-12.md); no sealed candidate evaluation was run. The output-head file therefore fails the default-runtime full-memory gate and has no quality-preservation result. [Muse Glimmer's October 2026 report](https://arxiv.org/html/2610.24628v3) already changes a Q4KM-like output projection from Q6_K to Q5_K and searches Q4_K/Q5_K/Q6_K assignments by calibration loss. [SoftWater](https://arxiv.org/html/2608.12026v1) also allocates output-head rates by token class. This allocation has direct prior art; the local result is a bounded deployment measurement, not a new compression method or a frontier-model comparison.

**New external evidence:** [Tan et al., ISCA 2026](https://arxiv.org/html/2606.15789) show GPU tile-level lossless weight decoding during SGLang serving. Their Table II reports Qwen-14B on one 80 GB A100, sequence length 1,024: GPU weight memory 27.5 to 18.1 GB and throughput 1,131 to 1,217 output tokens/s, while median time per output token worsens from 71 to 81 ms. Freed space is used for a larger KV cache, leaving total GPU allocation around 75 GB. The table does not specify the input weight numeric format, and its maximum-batch result, 47 to 60, conflicts with the abstract's 47 to 75. These GPU figures cannot be transferred to the CPU GGUF setup.

[MINE, a 2026-11-09 revised preprint](https://arxiv.org/html/2611.09424) reports up to 2.52×/1.48× faster steady-state batch-one decode on two NVIDIA GPUs for an already quantized Llama 3.1 8B checkpoint. Its exact entropy coding preserves **that quantized checkpoint**, not the original model; the paper's reported speed excludes startup, its plugin loads uncompressed tensors one by one before encoding, and its reported prefill was slower than vLLM. The authors screened GGUF i-quants and found no useful entropy headroom, but did not build their specialized kernels or test our Q4_K_M files. [Helcig et al.'s 2026-08-09 revised preprint](https://arxiv.org/html/2605.02404) makes the quality boundary explicit: tested task-level parity appeared as low as 3.3 bits per parameter, while a stricter sampled next-token distribution criterion took 4.98 to 6.55. Neither is byte-identical behavior. On one reasoning benchmark, a task-parity variant used more thinking tokens despite similar accuracy, so output work is part of the resource budget.

[ZipServ, ASPLOS 2026](https://arxiv.org/html/2603.17435) adds a lossless BF16 comparison: its GPU-aware format reduced tested stored weights by up to 30% and improved mean end-to-end GPU throughput 1.22× over vLLM. Its prefill path expands weights into GPU global memory, and the paper does not establish peak memory across load and prefill. This is evidence that integrated compression can differ from ordinary archiving, but not a measured improvement for quantized CPU GGUF.

**Closest CPU evidence:** [Bhatnagar et al., TMLR June 2026, Appendix D](https://arxiv.org/html/2509.23729) report Qwen2.5-VL 7B generation on two CPU hosts: a layerwise IQ1_M/Q4_K_M mix reached 9.0 versus 4.8 tokens/s on an i7-13620H and 18.7 versus 14.1 on a Threadripper PRO 7965WX against Q4_K_M. The reported 3.4 versus 4.4 GB “Memory Usage” lacks a definition, and the paper does not establish broad quality parity for that exact mixed file. [Kurt's January 2026 preprint](https://arxiv.org/html/2601.14277) finds a smaller Q3_K_S GGUF faster to decode but slower to prefill than Q4_K_M for one Llama 3.1 8B on a 96-core Xeon server, with worse selected-task mean and perplexity. [BitNet b1.58 2B4T](https://arxiv.org/html/2504.12285) reports a CPU decode gain over a BF16 Qwen2.5 1.5B comparator, with different runtimes and gaps on individual quality tests; it supplies no Q4_K_M CPU comparison. These results justify a controlled CPU test rather than a general win claim.

The LUQ CPU result and its quality result use different artifacts: Appendix D runs a llama.cpp IQ1_M/Q4_K_M mix, while Table 1 scores a PyTorch BiLLM/GPTQ mix. The latter loses 16.5 MMBench points and 15.5 ChartQA points against its GPTQ 4-bit comparator. Neither the CPU file's complete bytes nor a process high-water RAM definition, full-request CPU-seconds, or sealed multistep quality are reported. [Ehsani et al.'s phone study](https://arxiv.org/html/2603.26603v2) provides a second useful Q4_K_M control: in 30 repeated CPU runs of one Qwen2.5-3B summary, IQ4_XS used 1,971 versus 2,320 MiB of reported llama.cpp allocations, yet its median prefill-plus-generation latency was 7.94 versus 7.54 seconds and its measured energy was 157.8 versus 151.5 joules. The [released metric definition](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/data/README.md#columns) sums model, context, and compute allocations rather than measuring process high-water RAM; its latency is parsed from llama.cpp's inference timing and excludes model load. The 30 repetitions improve hardware timing precision, but greedy decoding of the same prompt supplies one distinct quality example per configuration. This shows that lower reported allocation can accompany longer inference latency; it does not establish the four-gate result.

In a narrower same-base [CPU study on e-commerce intent extraction](https://www.mdpi.com/2504-2289/10/5/155), Q3_K_M used 0.93 versus 1.04 GB reported RAM but fell from 0.984 to 0.972 exact-match accuracy and from 19.5 to 13.0 generated tokens/s relative to Q4_K_M. The article does not report complete file sizes or define the RAM peak, so it reinforces the need for a joint measurement rather than proving one.

Two further counterexamples clarify the trade. In [Bathula's 270M-class CPU study](https://arxiv.org/html/2610.22428v1), a separately trained ternary model cut file size and peak memory and increased decode speed against a Q4_K_M float model, but training-path validation loss worsened from 3.155 to 3.439 nats/token and ARC-Easy from 45.9% to 41.0%; the comparison used different runtimes and omitted prefill. Its Table 5 perplexities use different measurement paths, and deployed ternary-artifact quality was checked against PyTorch on only 64 validation tokens, so neither is a deployed-artifact parity test. The paper says the 253 MB Q4_K_M file keeps its embedding in FP16, but inspection of the [released GGUF](https://huggingface.co/QLNI/embeddings-are-overpriced/blob/main/gguf/armA-Q4_K_M.gguf) identifies `token_embd.weight` as Q8_0, occupying 178,257,920 bytes. The [SipLLM author measurements](https://github.com/ankit1057/sipllm/blob/3e501d0dc641fef2a2900bcba3891627ce455576/README.md) streamed the **same** TinyLlama Q4_K_M file at 122 versus 1,323 MB peak RSS on Apple M3, while decode fell to 11.7 versus 88 to 96 tokens/s. Neither result satisfies simultaneous resource reduction with preserved task quality.

**Quality gate:** [Patodiya's October 2026 preprint](https://arxiv.org/html/2609.05881) found seven of 305 eligible GGUF registry tags solved at most six of 164 HumanEval+ coding tasks. Five failing files matched uncalibrated rebuilds tensor for tensor; importance-matrix calibration raised three Qwen2.5-Coder-3B low-bit levels from zero to between 76 and 113 solved tasks, still below a plain Q4_K_M rebuild's 129. This implicates the quantization recipe in those failures, rather than proving the bit budget inherently unworkable. It does not measure paired CPU runtime or RAM and cannot establish general quality outside coding tasks.

[ThinkBit's same-base Qwen3-1.7B comparison](https://arxiv.org/html/2610.34886) reports a 0.52 GB low-bit checkpoint versus a 1.11 GB Q4_K_M file, but its seven-task mean is 53.8 versus 58.7 and sampled MATH-500 is 73.0 versus 90.8; there is no CPU or peak-RAM result. This supports task-aware training as a size-quality lead while showing that its reported file saving does not retain all measured capabilities.

**Whole-task cost:** [Abkin et al.'s October 2026 preprint](https://arxiv.org/html/2610.32417) found Q4_K_M used 6% to 16% less energy per output token than same-base Q8_0 in A100-hosted tests, yet the lower per-token choice used a median 66% more energy per completed task on statistically supported cases where the choices disagreed. Its 29 automatically checked tasks charge failed attempts and retries to completions. This is a GPU-hosted energy result, not a CPU speed or RAM result, but it shows why a quality gate must count complete multi-step outcomes and all attempts.

A [separate Abkin et al. shared-GPU study](https://arxiv.org/html/2610.41672v2) gives a paired fixed-work versus live-work check. For Qwen3.5-9B on A100, W4A16 used 9.8% to 12.3% less CPU-package plus GPU-board energy than W8A8 when replaying the same recorded calls. Across eleven live repetitions of sixteen benign tasks per precision, W4A16 generated 30% more output tokens, used 15% more cohort energy, and completed 96/176 rather than 124/176 tasks. Its energy per verified completion was 49% higher, with a reported paired 95% ratio interval of 1.28 to 1.72. The live denominator includes failed attempts, tool activity, and server drain, but excludes model load and independent verification. This is a GPU concurrency result with W8A8 as control, so it supplies no CPU-only four-gate observation. It supports a paired CPU study that records both fixed-input cost and complete task cost, where additional work or failures can reverse a per-call saving.

**Architecture lead:** [Monea et al.'s October 2026 preprint](https://arxiv.org/html/2610.02383) reports 76% to 79% less context memory and better selected quality for 150M to 1B parameter looped models with shared cache at five recursions, while H100 batch-one decode slowed substantially at that recursion count. The result concerns context memory and a newly trained architecture, with no CPU or full process-RAM comparison.

**Current judgment:** A compact representation can reduce a specified resource on a specified runtime, and a smaller model may preserve a specified set of benign tasks. The cited studies do not establish one tiny local artifact with unchanged broad frontier capabilities and simultaneous reductions in file bytes, RAM, and CPU. The [candidate matrix](compact-model-evidence-update-2026-11-11.md#testable-hypotheses-and-decision-rule) prioritizes a layerwise mixed-precision CPU comparison, then tests entropy-aware runtime compression only if the existing Q4_K_M files have headroom; native low-bit models, structured pruning with retraining, task-focused distillation, and context/KV methods require separate quality and workload checks. Retrieval, tools, and independent verification may help a bounded system meet a quality target, but their indexes, runtimes, retries, and external services belong in the total resource budget. A mixed-precision trial needs the same unquantized base or a trustworthy equivalent, a compatible CPU format and kernel, a calibration set, and a separate held-out quality suite. Compare it with the current Q4_K_M file on one host, including objectively checkable multi-step tasks, full-sequence success, failed attempts and retries, complete request cost, load cost, peak RAM, complete model-file and total installation bytes, and generated-token count. A one-resource gain is a partial lead; the full target requires smaller complete model-file bytes, lower peak RAM, and fewer complete-request CPU-seconds for the same artifact on that host while meeting the held-out quality gate. Any GPU candidate belongs in a separate hardware comparison.

**Concrete next study:** The pinned official [Qwen2.5 0.5B Instruct](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/tree/9217f5db79a29953eb74d5343926648285ec7e67) and [1.5B Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/tree/91cad51170dc346986eccefdc2dd33a9da36ead9) GGUF revisions include FP16 inputs beside the public Q4_K_M files. The [same-base mixed-precision CPU protocol](mixed-precision-cpu-study-protocol-2026-11-11.md) builds a fresh Q4_K_M reference and layerwise candidates from each pinned FP16 file, using one frozen importance matrix per model size and the same `llama.cpp` b12283 quantizer. The published Q4 files remain practical anchors because their calibration recipes are undisclosed. [Calibration-source evidence](https://aclanthology.org/2024.acl-long.544/) supports recording and freezing calibration data, although its quantization effects were smaller than its pruning effects and it did not measure GGUF imatrix. Q4_K_M already mixes K-quant types, so the hypothesis is that a different allocation might win.

**Where to probe:** The [pinned-reader inventory](../data/mixed-precision-baseline-tensor-inventory-2026-11-11.json) found that embeddings plus output consume 48.5% of the public 0.5B file and 28.9% of the 1.5B file. The 0.5B K-quant shape fallback also differs from the 1.5B mixture, so the smaller file is a pipeline pilot, not a substitute for the larger test. The pinned public 1.5B tensor inventory places 699,955,200 bytes, 62.6% of complete file size, in the three feed-forward weight families. This is available payload, not predicted savings. Start with a narrow gate or up tensor probe, then screen assembled allocations on development data. Manual tensor overrides can shift the quantizer's default higher-precision assignments elsewhere, so compare full tensor maps before attributing a one-group effect.

**Acceptance:** Final assembled artifacts must pass a sealed benign multi-step quality gate with full-sequence success, failed attempts, and retries counted. Measure exact model-file and installation bytes, process high-water RSS and separately labeled cgroup peak, and total CPU-seconds per assigned task under a named launch or resident lifecycle. Include checking in the CPU total, and report startup and idle separately for resident runs. A full win requires all three resource reductions for one artifact on the same CPU host, a prespecified noninferiority margin, and an absolute success floor for both reference and candidate. A practical replacement claim must pass the same gate against the currently used public Q4 file as well as the fresh causal reference. The exploratory artifact above exists; calibrated construction and sealed task quality remain open.

**Public quality diagnostic outcome:** A [frozen 200-question GSM8K comparison](gsm8k-pair-diagnostic-2026-11-12.md) of the fresh Q4_K_M reference and the 14-tensor smaller candidate scored 10/200 for each under an exact final-line format rule. The paired difference was zero, but both models failed the prespecified absolute-quality floor. Most invalid outputs stopped normally and gave answers in prose without the required line, so this is primarily a prompt and scorer mismatch. A post hoc last-number check is recorded only as a diagnostic; it cannot pass the original gate. The local resource lead therefore remains unqualified by a valid quality result. A disjoint, newly frozen benign test and the full calibrated study are still needed.

**Simple whole-format control:** A fresh Q4_K_S file from the same FP16 source saved 45,735,936 complete bytes against Q4_K_M, close to the custom candidate's 49,674,240-byte saving. Its [audited tensor map and paired runs](same-base-quantization-pilot-2026-11-12.md) show lower CPU-seconds and peak process RSS than Q4_K_M in both short and longer no-repack synthetic workloads. In five direct 512/128 pairs, the custom candidate used 0.123 to 0.520 more CPU-seconds than Q4_K_S, although its file and process RSS were about 3.94 and 4 million bytes smaller. Thus the custom map does not dominate the simple control, and the size difference alone is not a novel allocation result. Neither smaller file has passed the held-out quality gate.

### Joint model and CPU-runtime design: November 2026 source pass

The [architecture and runtime audit](joint-model-runtime-efficiency-audit-2026-11-11.md) tests whether a newly designed model and its runtime can clear that same four-part gate. Its clearest matched-training CPU architecture lead is a 150M-parameter [convolution-attention hybrid](https://arxiv.org/html/2608.20210). After 5B training tokens per arm, a [directly alternating eight-thread Q4_0 record](https://github.com/unseen1980/daedalus/blob/main/runs/abl-arch/decode-paired.json) reports 656.51 versus 387.65 tokens/s at 2,048 context, a 1.69-fold decode ratio, and rounded file sizes of 101.98 versus 108.34 decimal MB. The paper's 739 versus 420 tokens/s came from per-arm results collected about 12 hours apart, according to that paired record. Its published 95.56 versus 101.62 MiB sizes do not reconcile with the rounded raw file sizes. A separately reported five-task mean was nearly equal, 44.68 versus 44.82, but the paper does not show that suite rerun on the Q4_0 files. The dense file had one tensor requiring fallback quantization, so part of the byte gap reflects tensor shapes and format behavior. The paper does not measure peak process RAM, full-request CPU-seconds, or statistical noninferiority. This is a promising architecture hypothesis, not a joint result against the same-source Q4_K_M reference.

A newer [MNN-Pocket-0.3B report](https://arxiv.org/html/2611.12311v2) offers the closest cross-model tuple found in this pass. Against Qwen3-0.6B in the same MNN INT4 table, its reported MNN inference file was 173 versus 340 MB, iPad M5 peak **Metal** resident memory above the pre-load baseline was 228 versus 427 MB, and four-thread CPU decode was 231 versus 135 tokens/s. Its eleven-benchmark mean was 49.59 versus 44.28, with deficits on some individual tasks. The authors say the MNN deployment footprint includes weights, tokenizer, computation graph, and inference configuration, but do not report complete installed bytes including the runtime. The memory figure is for Metal, while the CPU result is isolated decode; neither is CPU peak RSS or full-request CPU-seconds. This is a different, heavily trained model, not same-base compression or broad-capability parity.

A [MatMoE CPU ablation](https://arxiv.org/html/2611.01704v1) separates two useful design effects on one MoE model and GSM8K-CoT task. On a four-thread Raspberry Pi 5, custom low-bit kernels cut static mixed-precision output-token time from 80.3 to 27.3 ms without changing its 27.7% score; a dynamic nested-bitplane allocation scored 36.5% at 27.6 ms/token under the reported 4-bit memory budget. Its FP16 source scored 41.0%. Thus the kernel accounts for most of the token-speed gain and the allocation improves this bounded task score. The paper does not give complete artifact bytes, peak CPU RSS, full-request CPU-seconds, or held-out multi-step success; its dense-Qwen transfer is untested. This warrants kernel-aware allocation as a hypothesis, not a joint-resource finding.

An author [Muta Compress model card](https://huggingface.co/timiiowolabi/muta-compress-20260920) gives a narrower, Qwen-derived CPU lead: its width-pruned and distilled tutor has a [592,887,552-byte Q4_0 GGUF](https://huggingface.co/api/models/timiiowolabi/muta-compress-20260920/tree/main/refine-final/gguf) versus a [713,654,016-byte dense-parent file](https://huggingface.co/api/models/timiiowolabi/muta-compress-20260920/tree/main/step2-26L-dense/gguf), with reported peak RSS 705.7 versus 809.9 MB and four-thread decode 15.51 versus 13.15 tokens/s. The linked raw benchmark directory was unavailable during this audit, the card does not verify comparable RSS lifecycles or complete-request CPU-seconds, and its small tutor quality tests include disclosed training-set overlap. They do not establish broad parity. It is a candidate for independent replication, not a completed joint result against Q4_K_M.

A released [Kev-4B mixed-precision GGUF](https://huggingface.co/turintech/Kev-4B-Artemis-GGUF) gives concrete same-base file evidence: 2,541,447,616 bytes versus 3,033,489,824 bytes for a stock Q4_K_M, a 16.22% reduction. Vendor tests on an RTX 5090 found equal 66.8% accuracy on 2,000 typed decisions used to select the published file, but 71.3% versus 72.3% on a separate 300-item benchmark sample. Its CPU-only memory test covered only the mixed file, so it establishes no paired CPU peak-RAM or full-request CPU result. The `Q4_K_M` release label describes a size class; its tensors mix other GGUF quantization types. A separate [published per-tensor layout study](https://huggingface.co/blog/bartowski/per-tensor-layout-maps-for-gguf-quantization) supplies reproducible tensor maps: on a held-out same-shape model its computed Q4_K_M was 5.3% smaller, but raw WikiText next-token KL was 0.0230 versus 0.0228 for the standard file. Its advertised 0.66× KL ratio uses an equal-size interpolation, and it has no task-level or CPU resource result. These examples support testing calibrated allocation locally, not a quality-preserving joint resource claim.

A [Kuza Gemma 4 E2B artifact](https://huggingface.co/kuzaai/kuza-gemma-4-e2b) reports a same-source mixed GGUF with 22.7% fewer file bytes, about 20% lower labeled peak RSS, and 10.9% faster six-thread isolated decode than its default Q4_K_M. Its raw hidden reports, however, mark **all 36 outputs empty for both models** while assigning each a 0.479 mean score. Its four smoke prompts are also flagged empty. The published task-quality gate therefore cannot establish parity; its RSS lifecycle and full-request CPU work are unreported. This is a useful resource lead and a concrete reason to verify actual generated answers before accepting a compression result.

A [Fractal64 custom GGUF and CPU kernel report](https://github.com/synchopate/llama-modchip/blob/main/benchmarks/FRACTAL_MOE_QUALITY_GATE.md) gives another same-source lead. Against an official Q4_0 Nemotron3.5-30B-A3B file, it reports 17.59 versus 14.35 GiB on disk, 21.41 versus 15.40 GiB current idle process RSS, and 19.54 versus 25.02 tokens/s on one decode prompt. Its 2,688- and 1,856-wide tensors cannot use the 256-value K-quant blocks, so this does not establish an advantage over our Q4_K_M baseline. Its post-suite RSS is one current `ps` sample, although labeled peak, and the [evaluation script](https://github.com/synchopate/llama-modchip/blob/main/benchmarks/eval_quality_and_tools.py) checks only ten simple visible tasks plus a speed score. No complete-request CPU-seconds or held-out multistep parity is reported. Replication should use an exact runtime and thread setting, true high-water RSS, and the full quality gate before treating this as a joint result.

A [same-base ARM phone artifact](https://huggingface.co/bpmatt/Qwen3.8-2B-Distill-Q4_0-ARM-GGUF) makes the tradeoff unusually concrete: pure Q4_0 was 15.7% smaller than the publisher's Q4_K_M, and two paired `llama-bench` runs reported lower peak RSS and faster isolated CPU stages. Its next-token divergence from the F16 reference roughly doubled, however, and no paired task success or complete-request CPU-seconds was measured. The gain is a resource lead with a known fidelity cost, not a quality-preserving result.

Meta's official [Llama 3.2 model card](https://github.com/meta-llama/llama-models/blob/main/models/llama3_2/MODEL_CARD.md) is a useful same-base ARM CPU control: 1B SpinQuant cut the ExecuTorch file from 2,358 to 1,083 MB and reported RSS from 3,185 to 1,921 MB, while decode rose from 19.2 to 50.2 tokens/s against BF16. Yet BFCL V2 tool-use accuracy fell from 25.7 to 15.9 and GSM8K from 44.4 to 40.6. Its comparator is BF16, RSS is not defined as high-water peak, and full-request CPU-seconds are absent. Smaller and faster therefore did not retain all measured capability in this example.

The closest independently run size-quality-speed comparison is the [WMT 2026 translation shared task](https://aclanthology.org/2026.wmt-main.52.pdf), but its H100 systems lack reliable peak-memory measurements. One [team report](https://aclanthology.org/2026.wmt-main.136.pdf) cut a text-only Gemma 3 12B system from 23.5 to 6.7 GB on disk and 23.2 to 9.7 GB peak **load-time GPU memory**, while raising hot throughput from 4,486 to 5,131 tokens/s. It removed the vision stack and part of the vocabulary, had a residual loss under one translation metric, and did not measure full-request CPU cost. Adding its quality-recovery reranker reduced throughput and added model bytes. These are bounded translation results, not evidence that the original capabilities survive.

CPU counterexamples matter as much as headline compression ratios. A [same-source Llama-3.1-8B GGUF sweep](https://arxiv.org/html/2601.14277v1) found Q4_K_S 4.6% smaller than Q4_K_M and similar five-benchmark mean scores, yet slower at 128-token decode: 4.65 versus 5.12 tokens/s on a dual Xeon server. It had no peak RSS or complete-request CPU measure. In one [Qwen3.5-0.8B pruning study](https://arxiv.org/html/2608.15693), a separate quantization sweep found that 1% physical MLP pruning **increased** Q4_K_M file size from 507.85 to 612.06 MB because 24 of 320 tensors lost 256-value block alignment; its fixed-prompt CPU quality/latency experiment was a different evaluation campaign and also worsened. A [Jetson structured-pruning comparison](https://arxiv.org/html/2610.15781v1) cut wall latency from 117.76 to 97.16 seconds but raised peak memory from 6,135 to 6,748 MB. A [revised spiking-model CPU report](https://arxiv.org/html/2606.03026v2) withdrew an invalid pure-INT4 export; its valid mixed-precision export used less storage and sampled RSS but ran slower than INT8. None supplies a same-artifact Q4_K_M quality/file/RAM/CPU win. A [mobile MoE study](https://arxiv.org/html/2605.27358) likewise shows that fewer active weights can still mean a larger static weight set and worse short-context RAM. A separate [ARM CPU deployment report](https://jacar.es/en/cpu-only-llms-arm64-maple-minicpm5-spark/) measured 3.27 GiB peak process RSS for a 1.45 GiB MiniCPM5 Q4_K_M file at 16K context, partly because CPU repacking duplicated live weight pages on its tmpfs setup; model bytes alone cannot stand in for inference RAM. In a [reasoning-pruning study](https://arxiv.org/html/2611.01133v1), 80% expert pruning needed 1,319 rather than 20 answer candidates and 59.63 times as many generated tokens to reach the same AIME coverage target; that estimate excludes prompts and verification, but shows why retries belong in the resource gate.

An author [Cortex-A53 study of the exact pinned Qwen2.5-1.5B Q4_K_M file](https://github.com/FredWen-S/lowbit-decode-a53/blob/08c7d473dc8db3be535528b21fa11b8eab726bba/a53/summary.md) found that Q3_K_M cut reported tensor weights from 1,060 to 876 MiB but slowed isolated decode from 5.67 to 5.38 tokens/s and raised user-mode instructions per token from 1,637 to 1,906 million. It measured neither complete file bytes nor peak RSS or full-request CPU-seconds, but directly shows why lower bit count is not a CPU-cost guarantee on the target model.

Kernel availability can also reverse a mixed-precision choice. A same-source [Snapdragon 695 study](https://github.com/HUNT-001/adaptive-llm-quantization/tree/7f052c55621c77f3b527ea534fa2f320299e896b) found that its selected Q4_0/Q8_0 allocation improved prefill and slightly improved perplexity against Q4_K_M, but increased the file from 935 to 1,386 MiB and slowed decode from 9.8 to 6.7 tokens/s in one paired session. Strong thermal drift, a restricted allocation search, and missing RSS, complete-request CPU, and task quality prevent a broader conclusion. The local mixed-precision search should therefore test actual CPU kernels and complete artifact bytes, not merely bit counts.

**Why the full-sequence gate matters:** In a controlled synthetic [retrieve-and-add study](https://proceedings.iclr.cc/paper_files/paper/2026/file/3b4e1336f775c3dba16ebbb8d2afd258-Paper-Conference.pdf), most tested models were nearly perfect on the first turn, yet even Qwen3-32B fell below 50% mistake-free completion within 15 turns. The study did not test compression; it shows why isolated step scores cannot substitute for held-out complete trajectories. Similar aggregate scores can also hide *which* tasks fail: in a separate [program-repair quantization study](https://arxiv.org/html/2606.27205v2), Llama-3-8B and a 4-bit Quanto variant solved 61 and 58 of 525 bugs, but only 29 solved bugs overlapped. This GH200/Transformers result is not a CPU or GGUF resource test; it supports reporting paired base-correct/candidate-wrong counts alongside overall success. The Q4 reference also needs its own FP16 quality comparison: a separate [Qwen2.5-1.5B CPU study](https://arxiv.org/html/2608.28652v1) found identical ARC-Easy scores for F16 and Q4_K_M (0.747) but lower CommonsenseQA accuracy at Q4_K_M (0.733 versus 0.807). That result belongs to the authors' artifact and task suite, not our pinned files.

Phase-specific acceleration also needs package and full-request accounting. [Disaggregated quantization](https://arxiv.org/html/2609.26333v1) reduced 8K-prompt time to first token from 12.27 to 6.90 seconds for a Qwen3.8-27B IQ1_S decoder plus an SSD-streamed NVFP4 prefiller on DGX Spark. The added checkpoint increases complete stored bytes even though the implementation reuses device weight memory. On another low-bit decoder in the same study, mean MMLU-Pro output length rose from 2,394 to 3,897 tokens after prefill specialization. Short prompts incurred loading cost; CPU peak RAM, full-request CPU-seconds, and multi-turn quality were not measured. This is a phase-design lead, not a joint improvement over local Q4_K_M.

**Trajectory and allocation controls from the current source audit:** A [November 2026 coding-agent study](https://arxiv.org/html/2611.02368) compared BF16 with 4-bit AWQ and GPTQ on 115 public OJBench problems over three seeds. For Qwen2.5-Coder-7B, BF16 yielded 17 one-shot and 10 execution-loop solves, while AWQ yielded zero one-shot and 25 loop solves. No final-accuracy comparison remained significant after the authors' correction across eight comparisons, but the Qwen-7B solve-path shift persisted at the problem level. The study did not measure end-to-end CPU-seconds or peak memory, and its modest success counts limit broad inference. It shows why matching final success alone cannot establish matching request cost. A separate [matched-precision study](https://arxiv.org/html/2609.01587) found global group-128 quantization more accurate than locally restoring selected layers for all eight compatible tested models, by 21 to 52 points on its CORE metric. Its precision budgets are first-order, weight-only estimates, and its best local selectors use evaluation data. A proposed custom GGUF allocation therefore needs a simple whole-format and equal-complete-byte control before claiming a novel advantage.

**What fused compression proves, and what it leaves open:** [ZipServ](https://arxiv.org/html/2603.17435) losslessly compresses BF16 GPU weights and reports 17.60% lower mean full-output wall latency than vLLM across its tested model, batch, and output settings; its Llama-3.1-8B weight footprint falls from 14.96 to 10.83 GB. Its serving manager uses freed static-weight space for more KV cache, so that figure does not establish lower whole-process peak memory. [MINE](https://arxiv.org/html/2611.09424v2) fuses entropy decode into GPU matrix-vector kernels and reports up to 2.52 times faster steady decode for an EntQuant 2.1-bit checkpoint, but found no entropy headroom in tested GGUF i-quants. Neither establishes a complete Q4_K_M CPU file, peak-RSS, and CPU-seconds gain. For the quality-cost boundary, a same-base [Q4_K_M versus Q8_0 task study](https://arxiv.org/html/2610.32417v3) measured 6–16% less energy per output token at Q4 across 29 GPU-hosted tasks, yet on statistically supported disagreements Q4 used a median 66% more energy per completed task because it needed more tokens and turns. Energy is not CPU-seconds, but the reversal supports counting failed attempts and all generated tokens in our CPU gate.

[ZipNN's lossless-compression study](https://arxiv.org/html/2411.05239v2) supplies a direct check on the Zip analogy. The authors report that their tested GGUF-quantized models did not compress, while selected GPTQ/AWQ files compressed to 85% to 91% of their original sizes. Their roughly three-second load example first decompresses a BF16 Granite model and then loads it to GPU from a high-throughput cluster volume. Lossless storage compression restores the original weights before inference in this example, so the file-transfer gain does not establish lower CPU inference RAM or CPU-seconds. The paper does not identify a Q4_K_M pair for our task; this is a bounded negative result, not proof that every GGUF file is incompressible.

**Ranked research path:** First complete the calibrated same-base Q4_K_M versus mixed-precision CPU study already specified above. If it fails, test modest materialized structured reduction with recovery training, followed by quantization that preserves block-compatible tensor shapes; this has plausible byte and arithmetic effects but high quality risk and training cost. Global low-rank training is another architecture lead: one [functional-subspace study](https://arxiv.org/html/2609.40127v1) reduced BF16 weight allocation and sped GH200 decode, but its Llama-2-7B six-task mean fell from 56.9% to 42.2% at its 70% targeted-linear compression setting. Its long-context latent-cache saving is analytical, and CPU bytes, RSS, and full-request work were not measured. Native low-bit training with fused CPU kernels is a separate architecture program. Integrated entropy coding is worth a CPU implementation only after measuring useful entropy headroom in the actual GGUF tensor mix. For already quantized weights, entropy coding reduces bytes; it reduces CPU work only if decoding is fused with matrix operations and saved memory-transfer time exceeds decode cost. Decode and prefill may have different bottlenecks, so the actual prompt-length distribution and complete-request CPU-seconds decide the result. Looped/shared-cache designs and narrow-task students target context memory or selected tasks, and their extra compute, index, checker, or teacher costs require full accounting. A published gain on GPU, against BF16, in isolated decode, or on a few benchmark averages cannot transfer to the present CPU Q4_K_M files. The joint claim remains unverified until one complete candidate on one host reduces file bytes, measured peak RAM, and full-request CPU-seconds while meeting a sealed benign multi-step quality gate with full-sequence success and retries.

### November 2026 two-agent audit: decision so far

The [architecture audit](frontier-architecture-research-2026-11-12.md), [CPU-runtime audit](frontier-cpu-runtime-research-2026-11-12.md), and [decision memo](frontier-efficiency-decision-memo-2026-11-12.md) distinguish proposed methods from measured results. The local 14-tensor and output-head candidates cut complete GGUF bytes by 4.45% and 5.38%, respectively. Both show lower child CPU time and cold cgroup peak under `--repack 0` on a fixed-token synthetic workload. The 14-tensor map is slower than a simple same-source Q4_K_S control in every direct longer no-repack pair. With default repacking, the output-head candidate raises cold cgroup peak in every admitted pair even though its process RSS falls. A second [100 ms trace](../data/frontier-cpu-head-cold-cgroup-default-repack-memory-trace-2026-11-12.json) repeats the cgroup regression and shows an approximately 131 to 133 MB rise in sampled anonymous charge near peak while file charge falls by about 60 MB. This is consistent with an additional packed copy, but the trace does not identify a per-tensor allocation.

See the [tensor audit](../data/frontier-cpu-output-head-q5-tensor-audit-2026-11-12.json) and [runtime note](frontier-cpu-runtime-research-2026-11-12.md).

This runtime issue has [direct XNNPack prior art](https://developers.googleblog.com/streamlining-llm-inference-at-the-edge-with-tflite/): Google's 2024 CPU cache provider writes packed weights to a file and maps them on reload, reducing measured startup and peak process RSS in its own benchmarks. [ONNX Runtime documentation](https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-models.html) likewise says prepacking can undo peak-memory savings from borrowing model bytes. An offline native-layout file is therefore a plausible engineering control, not a new general compression method. Its complete installed bytes must include any original model and packed cache retained for deployment; neither source supplies the four-way Q4_K_M CPU result.

There is more direct GGUF prior art: [ik_llama.cpp PR #272](https://github.com/ikawrakow/ik_llama.cpp/pull/272), merged 2025-03-21, converts a model to row-interleaved quantization offline so the converted GGUF can be memory-mapped without runtime repacking. [PR #274](https://github.com/ikawrakow/ik_llama.cpp/pull/274), merged the same day, adds regex selection of tensors to convert. This rules out a generic novelty claim for selective single-GGUF offline packing. The fork's format and CPU path are not established as equivalent to our pinned mainline AVX2 Q4_K repack path, and those PRs report no complete installed-byte, cold cgroup peak, whole-request CPU, or sealed multistep result for the local comparison.

Lossless coding has the same resource-accounting trap. Cloudflare's [Unweight technical report](https://research.cloudflare.com/papers/unweight-2026.pdf), Table 8, reduces one Llama-3.1-8B BF16 bundle from 14.97 to 13.07 GB in its inference configuration, or to 11.74 GB for a distribution configuration that must be transcoded before inference. Table 9 measures H100 decode throughput, not whole-request CPU cost: its fused inference configuration falls from 168 to 100 tokens/s at batch one and from 23,464 to 16,520 at batch 1,024 against the uncompressed baseline. The 21.6% distribution saving cannot be paired with the inference timing as if it were one unchanged artifact. This preliminary, Hopper-specific result is a measured counterexample to assuming that fewer stored weight bytes necessarily improve decode speed; it does not establish the CPU Q4_K_M four-gate outcome.

Quality preservation also has a retry-cost denominator. [Song and Zheng](https://arxiv.org/html/2611.01133v1), §4.1, estimate that an 80%-expert-pruned Qwen3.6-35B-A3B needs 1,319 samples to reach 90% of the original model's AIME coverage, versus 20 for the original, and 59.63 times as many generated tokens despite shorter mean individual responses. Their estimate multiplies required samples by mean output length; it excludes prompt processing and checking and is not a measured CPU cost. The MoE pruning result cannot be transferred to this dense Qwen2.5 GGUF. It does show why a fixed-token benchmark and pass@k alone cannot establish lower CPU-seconds per completed task: paired sealed runs must count every permitted attempt through final judgment.

The quality gate remains unresolved. The public 200-item diagnostic failed its prespecified absolute floor for the reference and candidate, and the earlier reference-only generated development prompt failed the ordered-state floor. Later public reference calibrations improved after task and cap changes, but no sealed candidate multistep run was admitted. The four-template generator also cannot demonstrate transfer across task structures. A stronger competent reference, disjoint structural holdout, prospective paired analysis, and full task-level CPU accounting are necessary before claiming quality retention. For a structural holdout, the [iGSM generator](https://github.com/facebookresearch/iGSM/tree/a1ed1d04600add811beb08b58d9912ed30999642) exposes directed dependency graphs. Its [question is selected before unused nodes are added](https://github.com/facebookresearch/iGSM/blob/a1ed1d04600add811beb08b58d9912ed30999642/math_gen/problem_gen.py#L229-L245), so grouping by the **query-ancestor induced graph**, including edge direction and node roles, would avoid treating distracting nodes as new reasoning structures. Reserving whole canonical groups rather than new random seeds on reused templates is our proposed test design, not a published iGSM validation protocol. It would test transfer beyond this project's development structures, without ruling out pretraining overlap. The current result is **no four-gate breakthrough**.

The [peer-reviewed PRISM study](https://link.springer.com/article/10.1007/s10791-026-10580-5), Table 15, reports Qwen2.5-3B fictional three-hop open-book accuracy of 0.912 at FP16, 0.812 at uniform 4-bit, and 0.013 at uniform 3-bit on 80 questions, while its single-hop copy probe stays at a ceiling. Its GPU torchao setting and retained FP16 head cannot predict our GGUF output-head candidate, but the contrast shows why a copy task or perplexity score is insufficient as a dependent-step quality gate. A public bAbI Task 3 screen is another possible reference-only development check: the [pinned Meta archive digest](https://github.com/facebookresearch/ParlAI/blob/a29567f7ce76992fd1f03c51ba9e3b155a37ea51/parlai/tasks/babi/build.py#L265-L275) allows source-byte verification, and public test stories must be clustered for analysis. Passing that screen would still require a separate, structurally disjoint sealed suite; public examples may overlap training data.

Task-specific training is another bounded lead, not a substitute for this quality gate. [Li et al.](https://arxiv.org/html/2610.06404v1) train a 1.5B model on five graph-algorithm and two state-tracking families using intermediate-step subsampling and quantization-aware training. Their Appendix Table 3 reports 80.3% Bellman-Ford accuracy for the 4-bit training setting versus 75.3% for its 32-bit setting, but these are trained task models, not a fixed same-base GGUF conversion. The released [CLRS launcher](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/scripts/train_clrs_text/quantized_training/train_lora_quant.sh#L23-L29) selects BF16 training and LoRA-only quantization; the [pinned implementation](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/src/quantization/quant.py#L438-L458) quantizes adapter matrices, not the frozen base. We have not matched that launcher to every table cell, so its result cannot establish a 4-bit deployed base or a size win. Each family has 200 test examples; the authors report that all five graph families fall below 25% accuracy on inputs 20% longer than training. The paper provides no installed CPU artifact, cold peak RAM, full-request CPU-seconds, or same-base Q4_K_M comparison. Its stronger lesson for our study is to test dependent-step success and length transfer separately, and to count added reasoning tokens in the CPU denominator.

Two newer training and calibration results narrow the quality hypothesis. [Bondarenko et al.](https://arxiv.org/html/2603.16867v2), Table 11, train a reasoning adapter on an INT4 Qwen2.5-7B base: after 1.2 million training examples, the five-task mean is 58.12% against 60.54% for their BF16 comparator, with MATH-500 at 89.6% versus 94.0%. Their result supports training on the quantized representation, but its comparator is BF16 and it lacks a complete CPU package, high-water RAM, full-request CPU, and dependent-step holdout. [CodeQuant2](https://arxiv.org/html/2611.09868v1), Table 6, raises its eight-metric mean from 0.745 to 0.754 when calibration uses the first 256 generated tokens, while AIME25 pass@1 falls from 0.546 to 0.517; the mean includes pass@8. Its CPU deployment and complete-artifact costs are unreported. A calibration gain on an aggregate that mixes single- and repeated-attempt scores therefore cannot stand in for our sealed single-attempt quality gate.

[QATFactory's Q4_K distillation paper](https://arxiv.org/html/2609.39223v2), Table 3, reports GPQA-Diamond/AIME25 mean gains over its post-training Q4_K controls for Qwen3-8B and Qwen3.5-9B. Its later first-party GGUF reproductions expose a mixed result: the [8B release](https://huggingface.co/qatfactory/Qwen3-8B-Q4_K-QAD-GGUF) scores 59.8 versus 60.2 for the same-build PTQ control, and WikiText KL is 0.0377 versus 0.0374; the [9B release](https://huggingface.co/qatfactory/Qwen3.5-9B-Q4_K-QAD-GGUF) scores 65.6 versus 61.0, with KL 0.0452 versus 0.0567. Those card evaluations used GPU llama.cpp and two short-form benchmark families. Q4_K is the trained tensor format, while Q4_K_M is a whole-model mixed preset; no CPU high-water RAM, full-request CPU-seconds, or sealed dependent-step comparison is reported. Training can recover quality in some cases, but the 8B reproduction is a direct warning against treating the paper's mean gain as guaranteed after retraining. See the [release and artifact audit](frontier-architecture-research-2026-11-13-round2.md) for exact file bytes and provenance limits.

**External quality and artifact checks:** [AgentCoMa](https://aclanthology.org/2026.acl-long.380.pdf) supplies 260 expert-written dependent commonsense-to-math items (80 development, 180 test), closer to a composition check than isolated arithmetic. Its [commit-pinned evaluator](https://github.com/lisaalaz/agentcoma-benchmark/blob/5464e3e7cf7261837876f5ea3f12d477579a68f5/eval.py) can assign zero to an otherwise judge-correct isolated commonsense answer when the exact final-answer delimiter is missing. This would attenuate a negative composition-minus-both-isolated gap for affected answers; the prevalence is unknown, so its reported gap is a diagnostic rather than a ready-made quality gate. [CompressionBench](https://arxiv.org/html/2611.06858) verifies complete submitted artifacts and reports 29 of 36 passes, but its resident-weight accounting excludes KV state and temporary workspace, and its quality floor is 80% of a BF16 mean across three short-task sets of 50 items each. Neither study measures the four local CPU gates together. Our next admissible comparison should freeze task structures and exact answer scoring before candidate exposure, count all installed files and runtime charges, and report complete-request CPU-seconds alongside the full-sequence quality outcome.

A [preregistered compression-fragility study](https://arxiv.org/html/2611.11695v1) reinforces this quality design. Its short-answer damage ordering transferred within a model across 18 compression cells (median correlation 0.875), but its long-form ordering met the prespecified stability band in only 10 of 16 task-model positions, below its 75% criterion. It included Qwen2.5-1.5B BF16, but did not test our GGUF CPU candidates. Its separate finding that some strict-answer failures still contain the right content is a reason to report both task correctness and format compliance; it does not justify changing the frozen parser after seeing candidate responses.

**Closest external resource and quality comparisons:** A [TurinTech same-base GGUF report](https://huggingface.co/turintech/Kev-4B-Artemis-GGUF/blob/main/RESULTS.md) lists a mixed-allocation Q4_K_M file at 2,541,447,616 bytes versus a stock Q4_K_M file at 3,033,489,824 bytes, a 16.22% file saving. Both have 66.8% typed-decision accuracy against synthetic labels in its RTX 5090 panel, but those decisions were used to choose the published files. Its CPU-only measurement covers the custom file alone: 3.78 GiB peak server RSS during three short requests, without a stock CPU arm, full-request CPU-seconds, or sealed dependent-step quality. An [Arm Qwen2.5-1.5B ONNX INT4 comparison](https://developer.arm.com/ai/models/hugging-face/Arm/qwen2-5-1-5b-instruct-onnx-genai-int4-kquantlast-emb-int4/qwen2.5-1.5b-instruct-int4-onnx) reports a 1,078.7 MB model, 1,570.45 MB peak memory, 2,235.38 ms p50 request wall time, and 61.03% MMLU against 62.98% for its original-model comparator on a four-core Graviton G4. The portal says 5,000 MMLU items while its [bundled benchmark YAMLs](https://huggingface.co/Arm/qwen2-5-1-5b-instruct-onnx-genai-int4-kquantlast-emb-int4/tree/8a3d1d673acdc70d4b7d10906e59d643376dd6fc/benchmarks) say `sample_count: 9183`, so the exact accuracy denominator is unresolved. Its memory ownership is unspecified, the wall time is not CPU-seconds, and neither comparator is our same-base Q4_K_M GGUF. These studies show credible resource reductions with explicit quality tradeoffs; neither clears the four local gates.

A [WMT 2026 document-translation study](https://aclanthology.org/2026.wmt-main.46.pdf) reports EuroLLM-1.7B BF16 versus W4A16 GPTQ chrF++ of 65.7 versus 63.6 on independent segments, but 35.6 versus 6.3 on 1,500-token document chunks across 27 Ukrainian-to-English documents. At 100-token chunks the scores are 67.6 versus 66.2. Chunking and context length interact with quantization in that experiment, and the quality run used a GPU. The bounded lesson is to stratify the sealed quality suite by input length and count each chunk request in the CPU total; these scores do not predict our GGUF candidates.

### November 2026 4B reference and next architecture test

The [Qwen3-4B development screen](qwen3-4b-development-screen-2026-11-13.md) found a stronger public reference: a pinned third-party Q4_K_M GGUF answered 8/8 inventory arithmetic and 8/8 ordered-state questions with normal stops under the fixed `reasoned_512` prompt. The same repository revision's Q4_K_S release also scored 8/8 in each family. These are 16 reused development questions from four templates per family. The Q4_K_M result clears the predeclared 60% point-rate screen that stopped the earlier 1.5B reference, but neither 4B result is a sealed quality estimate or a controlled scale comparison. Q4_K_S is 113,971,200 bytes, or 4.56%, smaller than Q4_K_M. In [five warm, fresh-process 128/64 synthetic pairs](qwen3-4b-q4ks-resource-pilot-2026-11-13.md) per setting, its median paired CPU difference was -0.646 seconds with default repacking and -2.342 seconds without repacking. Median process-RSS difference reversed from +104,185,856 bytes with repacking to -113,946,624 bytes without it. These are different fixed runtime policies, so their favorable counters cannot be combined into one deployment claim. Both attempted cold-cgroup comparisons were rejected on the first reference arm for page reclaim, leaving no admitted full-memory pair. The quality screen used no repacking, but its tasks and generation lengths differ from the synthetic CPU pilot. Installed bytes, full served-task CPU, and sealed quality remain unmeasured.

The [4B CPU tensor audit](frontier-cpu-static-topology-audit-2026-11-13.md) establishes a deployment constraint: this GGUF has a tied Q6_K `token_embd.weight` and no separate `output.weight`. A one-tensor Q6_K to Q5_K conversion would save 51,658,240 packed bytes by format arithmetic, but its projected complete file would still exceed the released Q4_K_S by 62,312,960 bytes. A pinned quantizer dry run changed only the planned tensor type. No candidate file, resource measurement, or quality result follows from that dry run. Any conversion of the community GGUF would also be postquantization, outside the stricter same-source original-checkpoint protocol.

The [Q4_K_S descriptor comparison](../data/frontier-cpu-qwen3-4b-q4ks-tensor-topology-2026-11-13.json) finds identical names and shapes across 398 tensors. Its 113,971,200-byte reduction comes from 36 changed type descriptors in attention-value and FFN-down matrices: 8 Q6_K to Q5_K and 28 Q6_K to Q4_K. The tied embedding remains Q6_K. This is consistent with a format-dependent repacking effect, but no per-tensor allocation trace establishes the memory mechanism. Descriptor comparison also cannot prove equal underlying source weights or payload equality.

The [composition-conditioned aligned-pruning hypothesis](composition-conditioned-aligned-pruning-hypothesis-2026-11-13.md) proposes physically removing aligned FFN channels while weighting dependent-chain loss above isolated-step loss. This is an untested selector. [RAC](https://proceedings.iclr.cc/paper_files/paper/2026/file/e70ffb3f05096e62b5077d8e1b62e668-Paper-Conference.pdf) already calibrates pruning on generated reasoning, [OBC-Prune](https://arxiv.org/html/2609.17890v1) uses outcome-aware rollouts, and [CSD](https://arxiv.org/html/2610.34336v1) already physically prunes MLP neurons using long and short correct traces. Thus reasoning-guided physical pruning is substantial prior art. The proposed excess-composition signal needs same-width ordinary-pruning and near-byte bit-only controls, equal recovery budgets, sealed unseen dependency structures, and a second base and CPU class before a transferable method claim. The [official Qwen3-4B-Instruct-2507 card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507#model-overview) calls this checkpoint non-thinking, so CSD's literal trace recipe cannot simply be copied onto it. The pinned GGUF loader expects a common FFN width across layers, making a uniform aligned cut the first mechanical export test. Conditional format arithmetic predicts 42,854,400 packed payload bytes saved by a 256-channel cut across 36 layers, but no such model has been built or measured. None of these findings satisfies the four-gate feasibility decision.

[AutoCompress](https://arxiv.org/html/2611.08290v1), posted 5 November 2026, is close prior art for deployment-aware architecture search. It selects global and per-layer structure using serving-engine profiles and a memory model that includes deployed weights, request caches, prefill workspace, runtime buffers, and a calibrated residual. Its measured contracts use GPU vLLM, including 739.7 ms and 3.93 GiB on an RTX 5070 for a 2,048-input/256-output workload. This narrows any novelty claim for a CPU allocator to the CPU-specific export, repacking, full-request cost model, and demonstrated outcome against equally budgeted search controls. The paper does not report complete CPU GGUF bytes, CPU high-water memory, CPU-seconds, or this study's sealed structural quality.

The [Prism ML Ternary Bonsai 4B release](https://huggingface.co/prism-ml/Ternary-Bonsai-4B-gguf/tree/a3eb42bafe873f9686bc97486c43b72ef7d75ec8) demonstrates a complete 1,074,969,344-byte Q2_0 GGUF. Its [first-party card](https://huggingface.co/prism-ml/Ternary-Bonsai-4B-gguf/blob/main/README.md) reports 226 prompt and 56 generated tokens/s on a ten-thread Apple M4 Pro CPU, but these are separate phase rates, without peak RAM or complete-request CPU-seconds. The card's near-lossless packing statement compares Q2_0 with the *already ternary* Bonsai weights, not with the original Qwen3-4B ancestor; its six-task H100 means are 70.7 for ternary Bonsai and 77.1 for Qwen3-4B. Q2_0 requires the author's llama.cpp fork. A packing-only control needs a Q4_K_M export of the same learned ternary checkpoint; an overall model comparison needs the exact ancestor and training history. Neither is the local Qwen3-4B-Instruct-2507 reference, and no four-gate CPU comparison exists.

## 13 November CPU, architecture, and quality evidence

The [second CPU audit](frontier-cpu-runtime-research-2026-11-13-round2.md) separates complete file bytes, cold total memory, warm process memory, and full served-task CPU. Two third-party Qwen3-4B-Instruct-2507 files from one repository revision differ by 113,971,200 GGUF bytes: Q4_K_S is 2,383,309,536 B and Q4_K_M is 2,497,280,736 B. Counting the complete local llama.cpp build directory with the model gives 2,441,984,366 versus 2,555,955,566 B. This is an installed-directory census that includes unused build files and excludes host libraries. The matching tensor names and shapes do not establish identical original source weights or calibration.

The [cold raw record](../data/frontier-cpu-qwen3-4b-q4ks-cold-no-repack-cgroup-continue-round2-2026-11-13.json), [no-repack served-task record](../data/frontier-cpu-qwen3-4b-served-task-no-repack-round2-2026-11-13.json), and [default-repack served-task record](../data/frontier-cpu-qwen3-4b-served-task-default-repack-round2-2026-11-13.json) retain per-arm counters and controls. The served-task denominator is one two-request session per fresh server, with the same 52 cached prompt tokens on the second request in both arms under both repack policies; it is not two independent uncached requests. Under the tested no-repack policy, fewer packed bytes reduced peak memory, while complete-task CPU rose on the reused tasks and the candidate generated a longer state response. The fixed-token CPU gain did not transfer to those complete tasks; these observations do not isolate the cause of the CPU difference. Default repacking also raised process peak RSS on those tasks. The no-repack and default-repack results are separate deployment policies; their favorable counters cannot be assembled into one configuration. Neither this Q4_K_S comparison nor the earlier head-only candidate clears all four gates: the present 4B pair lacks a sealed structural quality comparison, a verified common original checkpoint, and a complete-task CPU win.

The common-checkpoint gap is material. In [Liu and Tsai's GGUF re-derivation audit](https://arxiv.org/html/2610.19498v1), the named quantization type alone did not recover several publishers' per-tensor recipes. With additional build settings and type maps, seven of eight target quantization **tensor payloads** matched on x86. Their comparison excluded GGUF metadata because the quantizer wrote a local imatrix path, so this is not seven whole-file hash matches. This study does not identify the source of our third-party 4B pair; it supports rebuilding both arms from one pinned full-precision file before a quality claim.

A [tested host-dependent runtime bundle](../data/frontier-cpu-qwen3-4b-minimal-bundle-2026-11-13.json) contained ten regular local files totaling 25,935,214 B and ten relative symlinks. One model plus that bundle measured 2,523,215,950 B for Q4_K_M or 2,409,244,750 B for Q4_K_S, a 4.5169% reduction. Both copied-server processes served a benign chat request with normal stops and mapped no file from the original build directory. They still mapped ten host `/usr/lib` files totaling 15,139,000 B; including those files once changes the observed reduction to 4.4900%. The copied bundle was exercised only for this CPU-only endpoint path and is not a portable complete image. This improves the deployment-byte denominator without changing the failed complete-task CPU result.

The [second architecture audit](frontier-architecture-research-2026-11-13-round2.md) adds two concrete compression leads with different missing gates. [OPTIC](https://arxiv.org/html/2610.31309) publishes a Gemma 4 E4B GGUF 43.76% smaller than Google's QAT Q4_0 file through compressed embeddings, but its [raw GGUF runs](https://github.com/VILA-Lab/optic/blob/main/docs/benchmarks/gguf-results.json) change the peak-RSS and process-wall-time ordering with lazy-loading mode. They do not report CPU-seconds, a cold cgroup peak, or sealed benign multistep parity against Q4_K_M. [MNN-Pocket-0.3B](https://arxiv.org/html/2611.12311) has five released MNN model files totaling 174,149,042 B at the audited revision, excluding the MNN engine and application and measured mobile CPU prefill and decode rates. Its 228 MB peak is Metal resident memory, and the released speculative draft adds 130,366,688 B before runtime libraries. Neither CPU process peak nor full-request CPU-seconds is published. Both examples warrant a same-hardware complete-package experiment, not a joint success claim.

The [QuantDiff same-maker comparison](https://www.quantdiff.com/compare/iq4_xs-vs-q4_k_m/) is a concrete paired-quality warning for an IQ4_XS candidate. Its pinned Spark-X2.6-4B GGUFs are 2,338,275,968 versus 2,621,104,768 bytes, a 10.79% file cut; the published 500-question scores are 379 versus 394 for IQ4_XS and Q4_K_M. Re-scoring the publisher's [raw answers and method](https://www.quantdiff.com/data/) gives 20 IQ4-only and 35 Q4-only wins, or a 3.0-point candidate deficit. The companion audit derives a paired bootstrap interval of minus 6.0 to 0.0 points. That interval does not establish even a five-point noninferiority margin. Its M2 Pro Metal generation rates and single-turn tasks do not supply CPU-only whole-request time, peak RAM, or dependent-step quality. The GGUF byte counts also exclude runtime distribution.

[VisionPsy-Nano's same-checkpoint quantization ladder](https://arxiv.org/html/2609.31746v1) reports rounded full VLM model sizes of 393 MB for Q4_K_M and 346 MB for IQ4_XS, with small but nonzero changes in its 17-benchmark normalized aggregate scores. Its phone CPU measurements use a different Q4_0 language plus Q8_0 vision configuration; its large first-token improvement uses separately trained visual-token policies. Neither result measures the Q4_K_M/IQ4_XS pair's peak CPU RAM, complete-request CPU-seconds, or sealed dependent-step quality. The ladder therefore supports a candidate export, not a four-gate outcome.

[MedPsy-4B's same-checkpoint IQ3_M/Q4_K_M comparison](https://arxiv.org/html/2611.02011v1) gets closer to joining quality and deployment: Table 4 gives rounded GGUF sizes of 2.0 versus 2.6 GB and aggregate score changes from BF16 of minus 1.50 versus minus 0.81 points. Appendix A.13 reports 3.66 versus 4.29 GB peak RAM and 8.3 versus 8.75 seconds median answer wall time on the same 30-prompt set. Those device runs use Apple Metal, and the paper does not provide exact complete package bytes, process CPU-seconds, or sealed dependent-step outcomes for the pair. They are a useful replication lead, not a CPU four-gate result.

The [Baarali Edge pinned CPU quantization sweep](https://github.com/benewende-dev/baarali-edge/blob/b8b3bbfe2dbbdf5ea6045593475ae4dcad8d5cdc/bench/resultats.md) is a closer deployment lead: its Qwen3.5-2B IQ4_XS GGUF is 8.42% smaller than the Q4_K_M GGUF in the same pinned repository, and three Apple M1 `-ngl 0` benchmark runs per arm favor IQ4_XS on sampled peak RSS and decode throughput. The reported 512-token prefill field is computed from phase throughput, not observed first-token latency; the RSS sampler covers only the `llama-bench` window. A single public 200-question ARC-Easy screen scores 0.670 versus 0.675. The study lacks complete-request process CPU-seconds and sealed dependent-step quality, so its favorable phase counters do not establish a four-gate result.

The [MERNIK pinned model card](https://huggingface.co/wepiqx/MERNIK/blob/8f9264dbe4cd7f246c51fd8a7233c5a8b07ef605/README.md) reports a custom mixed-bit export smaller than a stock Q4_K_M export from one Ornith-1.5-9B source, with similar public HumanEval outcomes. The custom serving GGUF is absent from the pinned public inventory, so its exact bytes and source-checkpoint hash could not be independently verified. The published evaluation sidecars set GPU offload; they give no paired CPU-only peak RSS, complete-request CPU-seconds, or sealed dependent-step outcomes. This is a reported candidate for reproduction, not measured evidence of the required joint result.

A second [same-source Occamy release](https://huggingface.co/Accio-Lab/occamy-1.0-GGUF/blob/15027de49a5f8bbb5a131ed3fcfc1b54a543089d/VALIDATION.md) reports IQ4_XS at 18,728,777,728 bytes versus Q4_K_M at 21,166,757,696 bytes, an 11.52% model-file saving. I independently recounted its [780 per-question records](https://huggingface.co/Accio-Lab/occamy-1.0-GGUF/blob/15027de49a5f8bbb5a131ed3fcfc1b54a543089d/validation/per_question.jsonl): on the paired 60-case screen, IQ4_XS passed 33, Q4_K_M passed 34, with one Q4-only win; output counts were 12,008 versus 12,017. These few public cases cannot establish dependent-step noninferiority. The speed table is NVIDIA B200 phase throughput, not CPU task cost. The publisher also discloses a tokenizer metadata correction after benchmarking and a different historical Q4 conversion recipe, so the exact released-file bytes and old benchmark scores are not one fully retested configuration.

The [mcpzim same-fine-tune quantization frontier](https://github.com/jasontitus/mcpzim/blob/d15193cf9098c92619790859298f284b22793483/tools/llama-smoke/LFM25_MEMORY_PERF_FRONTIER.md) is a useful near miss for multistep quality. Its LFM2.5-8B-A1B Q4_K_M passes 11 of 13 public tool and three-turn chain scenarios at reported 5.16 GB average peak process RSS; Q3_K_M passes 12/13 at 4.16 GB, and IQ3_XS passes 12/13 in three runs at 3.64 GB. The author calls a one-case difference sampling noise. The files are only approximately 4.80 versus 3.3 GB for Q4_K_M and IQ3_XS. The [pinned harness](https://github.com/jasontitus/mcpzim/blob/d15193cf9098c92619790859298f284b22793483/tools/llama-smoke/eval.py) samples process RSS every 100 ms and uses `ru_maxrss`, but runs on an M2 Max with Metal offload. The reported 136.3 tokens/s IQ3_XS rate is a decode phase. Exact installed bytes, CPU-only high-water RAM, full-request CPU-seconds, and sealed paired quality are absent, so this is a transfer lead rather than a four-gate pass.

[Suram's router-locality experiment](https://arxiv.org/html/2608.18261v1) shows a distinct quality tradeoff for reducing expert-cache misses. On a 137M-parameter MoE, the settings that reduce misses by 59% to 60% worsen validation perplexity by 2.1% to 3.1%, above the paper's declared 1% ceiling; a setting within the ceiling reduces misses by only 15%, short of its 30% target. Its proposed 2 to 7 times cached-serving improvement for a separate large Qwen model is projected from IO and router traces, not a measured end-to-end request. It is not a same-source Q4_K_M comparison or a four-gate result.

[FairyFuse](https://arxiv.org/html/2604.20913) reports 32.43 versus 26.15 generated tokens/s on a Xeon CPU against LLaMA-2-7B Q4_K_M. This is a decode-only comparison. Its [Fairy2i predecessor](https://arxiv.org/html/2512.02901) says the candidate received another 30 billion training tokens after initialization from pretrained LLaMA-2-7B, while the Q4 source revision is unspecified. The reported 3.3 GB model figure conflicts with the paper's 2.24 GB component sum and approximately 3.5 GB runtime budget; none is a measured process high-water mark. The first-party release contains QAT safetensors rather than the benchmarked packed file. It is a replication lead, but the reported advantage cannot be attributed to packing alone and does not establish complete deployable bytes, full-request CPU-seconds, or sealed multistep parity.

[ThinkBit](https://arxiv.org/html/2610.34886v1) gives a useful physical-size counterexample. Its selected Qwen3-1.7B QAT+R-h2 candidate is reported at 0.520 GB against 1.11 GB for a Q4_K_M release of the same named base. On the authors' common scoring harness, the smaller model scores 53.8 versus 58.7 on the seven-task mean and 73.0 versus 90.8 on sampled MATH-500. The selected candidate received 2.1 billion additional reasoning-mixture training tokens, so this is a changed-model comparison rather than a packing-only treatment. The paper verifies bit-exact repacking for related variants, but does not list a separately verified packed file for the selected candidate. Its H100 serving measurements use four-bit containers rather than the packed format; it reports no whole-request CPU-seconds or measured peak CPU RAM. It shows substantial reported size reduction with a measurable quality gap, not retention of all capability.

A [pinned Qwen3.5-0.8B native CPU release](https://github.com/Danmoreng/qwen35-cpu/tree/2f7faac466d7d9c969cb886ef174fe202497b7ee) provides a narrower file-size near miss. Its [model distribution](https://huggingface.co/api/models/danmoreng/Qwen3.5-0.8B-H128-Q4-G32-DOT4/revision/f6cb5cf04a9094670f9041578a3f4e44b94a1395?blobs=true), counting the eleven downloader-named files and `SHA256SUMS`, totals 447,996,060 B against a [pinned 532,517,120-byte Q4_K_M GGUF](https://huggingface.co/api/models/unsloth/Qwen3.5-0.8B-GGUF/revision/6ab461498e2023f6e3c1baea90a8f0fe38ab64d0?blobs=true), 15.87% less before either engine. The author's eight-core Ryzen phase table reports 123.03 versus 99.03 batch-one decode tokens/s but 3,052.57 versus 3,403.18 P512 prefill tokens/s; the engines differ. The candidate's WikiText-2 perplexity is worse, 15.79649 versus 14.77376 on 8,192 scored tokens. Its original BF16 source revision is unavailable, and no matched peak CPU RAM, complete-request CPU-seconds, or sealed dependent-step quality is reported. The observed byte and phase gains therefore do not establish the four-gate result.

[GateTrim](https://arxiv.org/html/2611.00654v1) illustrates why physically pruning a low-rank branch may save little when a dense residual dominates storage. Across five models, residual codes and scales occupy 96.01% to 98.20% of its measured target-matrix export bytes; a large retained-rank reduction shrinks those target files by only 1.50% to 4.25%. Its complete-model component totals are estimates, and its reference implementation decodes packed tensors into floating buffers. On Qwen3-4B, sampled GPU evaluation-process memory is 20.701 GiB versus 12.400 GiB for FP16. This is a GPU/QDQ negative case without a native compact CPU implementation, Q4_K_M arm, complete-request CPU cost, or independent held-out task quality.

[ScaleQ-1.58](https://arxiv.org/html/2608.01078v1) is a closer CPU low-bit lead with a clear quality warning. Appendix F reports Qwen3-4B llama.cpp batch-one, 512-token decode at 19.31 tokens/s and 2.32 GB labeled "CPU Memory" for Q4_K_M, versus 37.35 tokens/s and 1.01 GB for its ternary TQ1_0 model. The paper does not define a sampled peak or specify the CPU hardware there, and it gives no complete package size or full-request CPU-seconds. Its Table 1 compares the 4-million-calibration-token ternary candidate with BF16, not Q4_K_M: MATH-500 falls from 96.80% to 58.40% and HumanEval+ from 85.37% to 53.98%. The decode and memory figures therefore justify a controlled replication, while the published quality gap prevents a retention claim.

[Zhang et al. at ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/file/665654759cdf2114c0cbe2b8e501e00e-Paper-Conference.pdf) protected about 2% of R1-Distill-Llama-8B weights at 16-bit within a 3-bit AWQ model. Table 4's average across AIME 2024, FOLIO, and Temporal Sequences rose from 46.0% to 52.57%, a 6.57 percentage-point gain; MuSiQue is reported separately. This supports testing selective precision as a quality control. The paper gives no exact deployed-byte census, peak CPU RAM, or complete-request CPU-seconds for that mixed-precision variant, and its tasks are not our sealed dependency suite. It does not make the specific final-layer protection a novel proposal here.

A separate [same-family CPU study](https://arxiv.org/html/2609.08307v1) makes the prompt-to-output break-even concrete. Its [first-party CSV](https://raw.githubusercontent.com/UCY-LINC-LAB/Edge-LLM-Inference-Benchmark/main/data/results.csv) reports Llama-3.2-3B F16 at 6.43 GB and 2,332.56 s total wall for 1,531 short-answer MMLU requests, versus Q4_K_M at 2.02 GB and 2,558.80 s. Q4 decodes each output token faster, but its measured prefill is slower and this prompt-heavy workload takes 9.7% longer overall. These are rounded file sizes and workload wall times, not exact deployed bytes or user plus system CPU-seconds; checkpoint revisions, peak RAM, and sealed dependent-step quality are absent. The result supports measuring the complete assigned request mix rather than substituting a decode token rate for total cost.

The [quality audit](frontier-quality-research-2026-11-13.md) shows why the 16/16 public 4B screen cannot support generalization to unseen dependency structures. In a reference-only, 24-case structural development pilot, Q4_K_M scored 10/12 inventory arithmetic and 6/12 ordered-state final answers, with seven 512-token cap stops and two arithmetic prompts whose pooling wording admitted another reasonable reading. A separately versioned prompt, wording, and 768-token-cap repair on the same case IDs scored 11/12 arithmetic and 12/12 state, or 23/24 by the normal-stop last-number rule; a stricter terminal-final-line rule scored 22/24. All 24 second-run responses stopped normally, yet one arithmetic answer regressed, two state responses needed over 700 tokens, and the conditions changed together. The paired public cases had 15 correct in both versions, eight improved, one regressed, and zero wrong in both. These are calibration observations on inspected development structures, not a held-out reference rate, candidate comparison, or evidence that any one repair caused the improvement. The sealed structural grammar, frozen parser, source-matched artifacts, and sample-size plan remain prerequisites. A valid decision must keep reference and candidate on the same prospective tasks, count full-sequence correctness and failures, and require family-level paired uncertainty bounds together with the three resource gates.

Fresh public reference-only [V3 calibration](../data/frontier-quality-reference-structural-dev-v3-score-2026-11-13.json) scored 23/24, with 11/12 arithmetic and 12/12 state final answers and all normal stops under a 1,536-token cap. A subsequent query-dependency audit found that only one of its six nominal seven-event state cases actually required seven dependent events. The separately frozen [V4 long-chain state panel](../data/frontier-quality-reference-structural-dev-v4-score-2026-11-13.json) required all listed events to affect the sampled answer and scored 10/12: 5/6 at seven-event depth seven and 5/6 at nine-event depth at least eight, again with all normal stops. Its independent [displayed-trace audit](../data/frontier-quality-reference-v4-displayed-trace-2026-11-13.json) found wrong written state updates in 3/12 responses, including one whose final answer was correct. The V4 panel has one conditional in a fixed position, just twelve cases, and branch outcome confounded with length. These public development results establish neither a sealed reference rate nor candidate noninferiority. They show why nominal event count, final-answer accuracy, and the model's displayed calculation each need separate checks.

Two primary studies sharpen the prospective quality protocol without supplying a result for this GGUF pair. In [StateBench](https://arxiv.org/html/2611.03094v1), four state-update classes are derived from matched source sequences, and each sequence has six surface forms. The pretrained-model Figure 5 reports the **maximum** score over those six forms and uses five-choice final-state scoring; it is an optimistic format-selection result, not generated-answer retention under one frozen prompt. It motivates dependency-structure and format strata. In [Singh's compression audit](https://arxiv.org/pdf/2608.15046v1), a Qwen2.5-7B GPTQ/AWQ GSM8K cell has a 0.58 percentage-point aggregate gap but 17.66% paired item churn. Its 2,730-item requirement is a planning calculation for a declared plus-or-minus 2-point **equivalence** margin, not our five-point noninferiority rule. The lesson is to publish paired per-item outcomes, disagreement, the declared decision margin, and the achieved sample size, rather than call close aggregate scores identical.

A separate [public paired Qwen2.5-7B F16/Q4_K_M result](https://huggingface.co/datasets/pbhappliedsystems/quant_eval_behavioral_per_case_results/blob/41bca7e40b84c30ec7323c7f35973e4a6144c141/quant_eval_behavioral_per_case_results.csv) illustrates why the exact quality endpoint matters. On 200 sampled JSON multistep cases, the publisher's parse-plus-oracle gate has 69 both pass, 90 neither, two F16-only, and 39 Q4-only. A separately recorded checks-consistent diagnostic has 18 both pass, 168 neither, three F16-only, and 11 Q4-only. That diagnostic is not nested in the published gate: four responses per arm pass consistency while failing oracle equivalence. The result is from another model, contrast, and public case set, so it cannot predict our held-out Q4_K_S comparison. It does support publishing both final-value correctness and separate trace consistency with paired case counts.

A [two-precision error-routing preprint](https://arxiv.org/abs/2611.16478) tested whether disagreement between simulated quantized copies identifies mistakes. On held-out multiple-choice questions, its selected disagreement score changed error-detection AUROC versus an 8-bit entropy baseline by +0.001 [minus 0.009, +0.011] at 0.6B and minus 0.001 [minus 0.009, +0.006] at 1.7B. The additional pass incurs weight traffic, and those intervals include zero. This is not evidence that a second precision can cheaply repair generated dependent-step errors; the prospective gate still needs gold-scored paired task outcomes and complete request cost.

**Decision at the 16:08 UTC cutoff:** No reviewed paper, released artifact, or local candidate jointly demonstrates smaller complete deployable bytes, lower measured peak CPU RAM, fewer full-request CPU-seconds, and preserved sealed benign dependent-step quality against a same-checkpoint Q4_K_M reference. The local 4B Q4_K_S file is 113,971,200 bytes smaller and lowers no-repack process peak RSS on the tested served tasks, but its median whole-server CPU use is 31.674 seconds higher across five pairs. Default repacking reverses the process-RSS result. Public reference-only quality calibration cannot supply a candidate quality estimate. The next decisive experiment is a fresh Q4_K_M and candidate export from one pinned full-precision checkpoint, tested under one declared CPU runtime policy with exact shipped-byte census, cold and warm high-water memory, complete task CPU cost including failures and retries, and a frozen unseen-structure paired quality panel. The current evidence supports a specific experiment, not a breakthrough claim.
