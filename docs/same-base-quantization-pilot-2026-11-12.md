# Same-base CPU quantization pilot

Design recorded 2026-11-12 18:07 EST, before constructing a new candidate. This is an exploratory screen of a general-purpose local model. It is not a test of frontier hosted-model parity or a completed quality result.

## Question and comparison

Can a fresh, loadable Qwen2.5-1.5B-Instruct GGUF with selected MLP down-projection tensors at Q4_K use fewer complete bytes, less peak CPU memory, and fewer CPU-seconds for the same synthetic request than a fresh Q4_K_M GGUF built from the identical FP16 source?

Use the official Qwen FP16 GGUF at revision `91cad51170dc346986eccefdc2dd33a9da36ead9`, expected SHA-256 `fc89e330deb3fd8fa560f1c0f35a1e2b8da96d59e13445559ed190307a6f5649`, and pinned llama.cpp build `f3b407ca1` (b12283). The [official revision tree](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/tree/91cad51170dc346986eccefdc2dd33a9da36ead9) lists the FP16 file. Compare a fresh default Q4_K_M build with a build that requests Q4_K for each `blk.N.ffn_down.weight` that is Q6_K in the fresh reference. Keep output and embedding tensors at reference types. Record the realized type map, since manual rules can alter other default mixture choices. The published Q4_K_M is a historical anchor, not the causal reference, because its construction recipe is not published.

No importance matrix is used in this pilot. This choice reduces setup cost but limits quality inference. The full [calibrated study protocol](mixed-precision-cpu-study-protocol-2026-11-11.md) remains the standard for any quality or joint-win claim. A pilot candidate must not be described as a breakthrough if it merely reduces file bytes or synthetic decode cost.

## Measurements and stop rules

- Hash the FP16 input and each completed GGUF. Record exact bytes, tensor count, tensor names, shapes, types, quantizer command, binary hash, and loader warnings. Reject a mismatched source hash or a failed load.
- Record file bytes for both loadable model artifacts and any deployment companion files. Keep FP16 construction input outside deployed-byte totals unless it is required at inference.
- On one CPU host, alternate reference and candidate order over at least five fresh-process blocks at fixed threads, context, prompt and output token counts. Record `wait4` model-process user plus system CPU-seconds and maximum resident memory, full wall time, swap and page faults, and llama.cpp phase timings. Keep cold and warm page-cache regimes separate. A cgroup `memory.peak` claim requires verified cache-charge control.
- If the candidate is not smaller in actual loadable bytes or has a load failure, stop the resource screen. If it is smaller but slower or more memory hungry, retain the negative result. Do not score a synthetic token benchmark as task quality.
- A later quality decision needs a frozen benign held-out multistep suite, paired same-task outputs, an absolute success floor, a noninferiority margin, and complete-request accounting for retries and checking. Freeze these before final scoring. A pilot resource result alone cannot pass the four-way gate.

## Provenance and status

At design time, the public Q4_K_M tensor census contained 14 Q6_K MLP down projections, 14 Q6_K attention value projections, and a Q6_K output projection. The other 14 MLP down projections are Q4_K. The public file is 1,117,320,736 bytes with SHA-256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e` in the [prior inventory](../data/mixed-precision-baseline-tensor-inventory-2026-11-11.json). The 14 public Q6_K MLP down tensors would save 49,674,240 payload bytes if replaced by Q4_K blocks with identical shapes; this is block-size arithmetic, not a measured candidate. The fresh reference map is not yet known. These facts motivate the probe; they do not predict its quality, CPU time, or memory.

## First artifact and recipe correction

At 18:11 EST, the official FP16 input passed the expected length and SHA-256 check. The fresh reference was produced by `llama-quantize --max-buffer-size 512 FP16 REF Q4_K_M 4` with binary SHA-256 `3cb6b1ea8dceca57ae32287b2c91229ff83df127d263becb498d6ee9dd6bdaf1`. It has 339 tensors, 1,117,320,736 bytes, and SHA-256 `b66e0350b994a95e26e9c41f05410c39f1ec84838b96144f494f87a5aaee8bf5`. Here `FP16` and `REF` stand for the verified cache paths named below; they are not shell variables.

The first candidate used the same command with `--tensor-type-file q4-down-tensor-types.txt`, listing the 14 Q6_K `ffn_down` names from the fresh reference as Q4_K. It has 1,088,935,456 bytes and SHA-256 `4986cb4db669ae343b527e4b2736db13be2e41d183c3a199f46b880c24ffcb77`. The realized map changed all 14 requested Q6_K tensors to Q4_K **and also changed six other `ffn_down` tensors from Q4_K to Q6_K**. Net payload saving was 28,385,280 bytes. This candidate is a whole-recipe comparison, not a clean 14-tensor intervention.

Five fresh-process alternating blocks with pinned `llama-bench` used 128 synthetic prompt tokens, 64 generated tokens, four threads, CPU only, `mmap`, `--poll 0`, and a warm page cache. The [raw runs](../data/same-base-quantization-pilot-runs-2026-11-12.json) include child `wait4` CPU-seconds and peak process RSS. The first candidate was 2.54% smaller than the fresh reference. Its median CPU time was 12.947 versus 13.068 seconds, with paired candidate-minus-reference differences of -0.376, +0.084, -0.018, -0.312, and -0.129 seconds. Its peak RSS was higher in all five blocks by 33.3 to 35.5 million bytes. The resource result does not pass the joint gate, and no quality was scored.

The tensor map confound was found before the resource runs finished. A second exploratory artifact pinned *every* quantized tensor to its fresh-reference type, except those same 14 `ffn_down` tensors set to Q4_K. The [rule file](../data/same-base-quantization-pilot-rules-2026-11-12.txt) is an exact-name list for this quantizer build. A dry run caught a second recipe hazard: putting `output.weight=q6_k` first also matched `attn_output.weight` and promoted extra tensors. Moving that rule to the end produced the intended dry-run counts. This ordering is specific to the quantizer's rule matcher; the realized artifact was audited independently.

At 18:13 EST, the corrected artifact completed at 1,067,646,496 bytes, SHA-256 `6c7476ad9ab6f108f0d28f31601d761ec40e9981a8dd13baa60ac3f66b8077b2`. The [full tensor and payload audit](../data/same-base-quantization-pilot-pinned-map-2026-11-12.json) found the same 339 names and shapes, exactly 14 Q6_K-to-Q4_K type changes, and byte-identical payloads in every unchanged-type tensor. It is 49,674,240 bytes, or 4.45%, smaller than the fresh reference. Both GGUFs loaded successfully in all resource runs.

The [corrected five-block runs](../data/same-base-quantization-pilot-pinned-runs-2026-11-12.json) used an Intel i7-12700K, four CPU threads, 128 synthetic prompt tokens and 64 generated tokens, with alternating process order and no cache flush. Median model-process CPU time was 13.167 seconds for the reference and 12.472 seconds for the corrected candidate. The paired candidate-minus-reference CPU differences were -0.975, -0.703, -0.394, -0.505, and -0.549 seconds. Median peak process RSS was 1,821,437,952 versus 1,880,035,328 bytes; the candidate was higher in every block by 57,806,848 to 64,729,088 bytes. Median wall time was 3.703 versus 3.575 seconds. These are short synthetic runs on one host with no controlled cold-cache measurement, cgroup peak, or task-quality score. The corrected candidate **fails the joint resource gate because peak process RSS increased**. The lower measured CPU time does not establish lower CPU cost for complete real tasks.

This is a useful negative result for the simplest precision change. Lower tensor payload bytes did not imply lower peak resident memory in this implementation. No inference-quality or frontier-parity conclusion follows. The next rigorous decision requires the calibrated and sealed benign multistep study in the linked protocol; this pilot does not substitute for it.

## Follow-up runtime control, declared 18:17 EST

The first two resource screens used the b12283 default `--repack 1`. The runtime reports `repack=true` in their raw benchmark records. Run one new five-block paired screen on the same reference and corrected candidate with `--repack 0`, changing this one runtime setting for both artifacts. This can test whether the observed RSS increase depends on CPU tensor repacking. It is an exploratory mechanism check, not a new model-design claim. Record the same file bytes, CPU-seconds, process RSS, and wall time. If the candidate then saves memory but loses CPU time, retain that tradeoff. Even a joint resource improvement under this setting would require a separate held-out quality gate.

The [completed no-repack runs](../data/same-base-quantization-pilot-pinned-no-repack-runs-2026-11-12.json) found lower CPU-seconds, wall time, and process peak RSS for the candidate in every one of five alternating pairs. Median CPU-seconds were 12.393 for the reference and 11.217 for the candidate; paired differences were -1.062, -0.991, -1.040, -1.132, and -1.594 seconds. Median peak process RSS was 1,211,441,152 versus 1,161,707,520 bytes; paired candidate-minus-reference differences were -49,446,912 to -49,934,336 bytes. Median wall time was 3.250 versus 2.927 seconds. The complete file remains 4.45% smaller. This is a **joint file, process-RSS, and synthetic-request CPU improvement on one host and one short workload**, with no measured quality preservation or independent host replication. It is not yet a full four-way result.

The [pinned repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5078) offers an AVX2 Q4_K path when the row count is divisible by eight, while its Q6_K branch in that section offers Arm paths. This makes a private repacked Q4_K copy a plausible explanation for the default-mode RSS reversal on this Intel host. The paired setting change shows the reversal is mode-dependent; it does not isolate allocation ownership or prove that this code branch caused every byte of the difference.

A one-pair `systemd-run --user --wait -p MemoryAccounting=yes` diagnostic reported cgroup peaks of only 85.4 MB for the reference and 84.4 MB for the candidate, far below their process RSS values. The model files were already page-cached before each transient service and may have been charged to an ancestor cgroup. Those figures are **not comparable total inference-memory measurements** and are excluded from the decision. A future cgroup experiment must control page-cache charging or use a clearly defined process-private metric consistently.

## Longer synthetic request control, predeclared 2026-11-12 18:25 EST

To check whether the short no-repack resource lead survives a larger request, run five alternating fresh-process pairs with the same pinned artifacts, `--repack 0`, four CPU threads, `mmap`, `--poll 0`, no benchmark warmup, 512 prompt tokens, and 128 generated tokens. The revised reproduction script accepts explicit prompt and generation token counts while retaining its original 128/64 defaults. Record exact output counts, model-process user plus system CPU-seconds, process peak RSS, wall time, and faults. Compare paired differences and medians; do not combine this synthetic control with the 128/64 blocks or treat either as final-task quality. Run it only after the quality diagnostic so both screens avoid CPU contention. Its outcome cannot establish a whole-task cgroup or quality claim.

The [completed longer runs](../data/same-base-quantization-pilot-pinned-no-repack-long-runs-2026-11-12.json) used five alternating pairs; all ten processes exited successfully and recorded zero major faults. Median reference versus candidate model-process CPU time was 27.489 versus 25.892 seconds, peak process RSS was 1,278,025,728 versus 1,228,324,864 bytes, and wall time was 6.999 versus 6.596 seconds. All five paired candidate-minus-reference CPU differences were negative, from -1.893 to -1.350 seconds; all five RSS differences were negative, from -49,733,632 to -49,467,392 bytes. The longer synthetic shape therefore preserves the narrow resource lead under the same warm-cache, no-repack setting. The [frozen public quality diagnostic](gsm8k-pair-diagnostic-2026-11-12.md) failed its absolute-quality gate because the strict answer format was usually not followed; this resource screen cannot establish quality retention.

## Simple-format control, declared 2026-11-12 18:55 EST

Before any paired GSM8K correctness was scored, add a fresh `Q4_K_S` control from the same verified FP16 file, pinned quantizer, four construction threads, and no importance matrix. The checked b12283 quantizer help lists `Q4_K_S` as a supported whole-file type. Audit its actual tensor map, payload bytes, complete GGUF bytes, and loader behavior. Compare it with both the fresh Q4_K_M reference and the 14-tensor candidate. Do not infer equal bytes from the format name.

If the control loads and has fewer bytes than the reference, run the same frozen 200-question public GSM8K diagnostic and the 128/64 and 512/128 five-block `--repack 0` synthetic screens. Reuse the fixed prompt, parser, runtime flags, and reference outputs. Run these after the first candidate's quality and longer resource control finish, without concurrent CPU load. This public sample is shared across candidate arms, so any selection among them is exploratory. A successful local result must still beat a sealed quality and full-request resource test; a simple format control that matches or exceeds the candidate weakens any novel allocation claim.

### Whole-format Q4_K_S control, 2026-11-12 19:19 EST

The pinned quantizer produced a loadable Q4_K_S file from the same verified FP16 source with four construction threads, no importance matrix, and the same 512 MiB quantizer row-buffer setting. Its complete size is 1,071,584,800 bytes and SHA-256 is `eee0176b86f95aff2e794f88c13b613a47c13380131ccdf926de8d650e6402d2`. It saves 45,735,936 bytes against the fresh Q4_K_M reference, only 3,938,304 bytes less than the custom candidate's saving. The [tensor audit](../data/same-base-q4ks-control-map-2026-11-12.json) found the same 339 names and shapes and byte-identical payloads wherever tensor type stayed the same. The whole-format recipe changed 29 types: 14 `ffn_down` and 15 `attn_v`. Eleven down tensors changed Q6_K to Q4_K and three to Q5_K; the attention changes included one Q4_K to Q5_K. This is the realized allocation, not an assumption from the format label.

Five alternating, fresh-process no-repack pairs at [128/64](../data/same-base-q4ks-control-no-repack-128-64-runs-2026-11-12.json) and five at [512/128](../data/same-base-q4ks-control-no-repack-512-128-runs-2026-11-12.json) compared Q4_K_S with the fresh Q4_K_M reference on the same host and pinned runtime. At 128/64, median CPU time fell from 11.035 to 10.085 seconds and median peak process RSS from 1,211,588,608 to 1,165,688,832 bytes. At 512/128, median CPU time fell from 26.871 to 25.349 seconds and median peak process RSS from 1,278,046,208 to 1,232,330,752 bytes. Candidate CPU and RSS were lower in all ten paired blocks. These are synthetic warm-cache measurements; they do not score answers or establish cgroup peak for this control.

A separate [direct 512/128 paired comparison](../data/same-base-custom-vs-q4ks-no-repack-512-128-runs-2026-11-12.json) used Q4_K_S as the reference and the custom 14-tensor file as the candidate. The custom file had about 3.6 to 4.2 million bytes less peak process RSS in every pair, but used 0.123 to 0.520 more CPU-seconds in every pair. Median CPU time was 25.901 seconds for Q4_K_S and 26.132 for the custom file; median peak RSS was 1,232,269,312 versus 1,228,279,808 bytes. The custom allocation therefore does not dominate the simple whole-format control on this measured workload. No Q4_K_S quality comparison has yet been completed, and neither file has passed a held-out four-way gate.
