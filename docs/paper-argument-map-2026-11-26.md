# Drexel feasibility paper: working argument map

Advent Cybersecurity research note, 26 November 2026. This is a planning aid for a later paper, not a finished manuscript or a claim that the source search is complete. The [master evidence assessment](master-feasibility-evidence.md), [live-revision analysis](live-revision-feasibility-2026-11-26.md), [search protocol](source-search-and-evidence-protocol-2026-11-26.md), and [source registry](../data/sources.json) retain the detailed support.

## Candidate research question

Can a model cause **two distinct executable payload-code revisions** to become active in **one identified continuing remote-access process**, while independently verified remote-control function persists after each? This is Project Drexel's stringent, operationally testable subclaim. Model placement, runtime, update count, and verification method must be explicitly specified in a study.

The paper should answer two different questions separately:

1. **Mechanism feasibility:** Could deliberately designed software combine model-generated code, runtime activation, state preservation, and a continuing access channel?
2. **Documented occurrence:** Does a public field case or controlled study show the entire joined sequence, rather than individual components in different systems?

The current answer is **yes in principle for the component mechanisms; no published end-to-end sequence established in the reviewed public record**. The second statement is bounded by public disclosure and this exploratory review; it is not a universal negative.

The [cross-case synthesis](claim-ledger-cross-case-synthesis-2026-11-26.md) maps the 31 selected close cases to the four required links. It makes the strongest noninterchangeable components explicit and shows that none supplies a version-bound remote-control result after **each** of two active revisions. Its annotation totals describe the selected evidence record, not a prevalence or feasibility rate.

## Proposed contribution

The paper's contribution should be a claim-level feasibility framework and evidence audit, not a prediction of an attacker's success rate. It can correct a recurring category error: a model producing a command, a one-off script, a new build, a changed prompt, a swapped model, or encrypted/decrypted code is not automatically a new executable version active in the same resident process. It can also show why uninterrupted network reachability alone is weaker than a successful command/result check after each revision.

Avoid calling this “recursive self-improvement” unless the mechanism that proposes the next change is itself revised and then used. A fixed model could author two payload-code versions. [Anthony et al.'s methods review](https://huggingface.co/blog/daicelabs/ri-is-not-rsi) articulates that stricter proposer-change distinction, although its own literature coding has limitations and its counts do not describe malware prevalence.

The [Autopoiesis audit](autopoiesis-live-policy-audit-2026-11-26.md) is a bounded-function counterpart to the full-harness examples: an external model-driven control plane stages two pure policy functions for live data-plane adoption. Its rescheduling counts must not be read as code-swap counts, and no published event sequence joins process identity, two code activations, and function after each.

The [Asiel Core source audit](asiel-core-hot-reload-audit-2026-11-26.md) offers a closer benign mechanism: one application codebase asks an LLM for revised Python plugins and calls an in-process loader after integration. Its committed proposal registry contains initial integrations and failures but no recorded `evolution_loop` proposal or second successful integration of one plugin. Compilation, copying, and a hot-reload call must remain separate observations from loader acceptance and version-specific function. This is a mechanism case, not a Drexel outcome.

The [production tool-versioning audit](production-tool-versioning-audit-2026-11-26.md) provides a concrete logging comparator: a deployed benign agent invokes versioned, model-generated tools and records each version's inputs and outputs. The paper evaluates tool libraries and historical alarms, but its model writes tools before promotion, and it does not publish two serial same-process promotions with after-each function results. A repair example shows lower test error can hide a wrong time-window interpretation; a Drexel oracle must be independently specified.

The [NexAgent source audit](nexagent-beam-hot-upgrade-audit-2026-11-26.md) shows an agent-facing Elixir module-replacement path in a long-running BEAM service. Its `reload_succeeded` flag can be true while tool-registry selection is absent or unsuccessful, and its health check does not call the updated function. This sharpens the paper's evidence ladder: source accepted, module compiled, registry switched, version invoked, and function retained are separate claims.

The [cl-agent trace audit](cl-agent-live-extension-trace-audit-2026-11-26.md) is a stronger benign model-to-live-code near case: its checked-in conversation records two distinct model-submitted versions of one Lisp extension loaded during one logical session, with revised tool functions called after the second. The first load is an addition, the second an edit; there is no OS PID trace or after-first functional check, and the tool has no remote-control workload. The [live-code activation audit](live-code-activation-boundaries-2026-11-26.md) uses SMAXr, samizdat, Autolith, Genesis, Pi, Poiesis, Erlang, and `execve` to distinguish compile/load reports, actual adoption, old-code execution, and program-image continuity. These distinctions should appear in the methods, not be hidden in a generic "hot reload" category.

The [executable-harness selection and state audit](executable-harness-selection-and-state-audit-2026-11-26.md) adds a trained code-patch engineer and an eight-day sequence of proposed/accepted harness rewrites. Both evaluate new candidates on fresh benchmark runs rather than in one resident process. The deployment-contract study shows that saved state and resumed in-flight work are separate guarantees. These results support the feasibility of components and the need for version-bound verification; their percentages cannot be transferred to Drexel.

The [edge small-model role audit](edge-model-role-split-audit-2026-11-26.md) shows why model placement alone is insufficient: a large planner writes programs while a 0.8B–9B model only interprets bounded runtime data. Its AppWorld task results and GPU-based token proxies do not demonstrate local small-model code authorship, endpoint CPU cost, two resident revisions, or retained remote access.

The [agentic C2 execution audit](agentic-c2-execution-boundary-audit-2026-11-26.md) separates a cloud-model-directed endpoint control loop from a researcher-prepared hook that runs around an agent's tool calls. Both help characterize remote tasking; neither supplies model-authored resident code replacement. The first report's no-alert observation is one incompletely specified test, not an endpoint detection rate.

[PluginRSI v2](https://arxiv.org/html/2609.32423v2) suggests a useful selection diagram for the methods section: branch-level plugin candidates screened on small development batches, one recomposed harness scored on a larger development set, then a frozen winner checked on a held-out set. Its separate reuse analysis trains on what was originally held out; those later numbers need a new evaluation-set label. None of these fresh-task scores measures one resident payload's serial revisions.

The [ZQAgent/ARTEX field audit](zqagent-artex-case-audit-2026-11-26.md) is a useful near case: one first-party incident report places an agentic intrusion framework and a persistent backdoor together, but does not give model-to-code provenance or any resident revision sequence. Its `memfd` relocation explicitly starts a detached process. The paper should present this stronger co-occurrence without converting it into the absent four-link chain.

The [JFrog ARTEX artifact audit](jfrog-artex-model-artifact-audit-2026-11-26.md) should sit alongside it as a **different case**: commits show rapid malicious-model package changes and an operator-side self-test, while exact LLM causation for each edit and a victim-side continuing process are unshown. The final broken configuration is a useful negative control for treating a published latest version as an active successful one.

The [AgentWorm v3 audit](agentworm-configuration-persistence-audit-2026-11-26.md) is a separate controlled agent-ecosystem comparison. Its remote task-fetch marker and five-restart configuration retention are actual measured outcomes, but the retained object is an instruction file reloaded in new sessions. This case can clarify why persistence and C2 do not by themselves imply executable-code revision in one process. Pin v3 when citing its 2,250-trial, 63% outcome; older *ClawWorm* summaries describe a prior version.

The [SafeDep Hermes/LeadStack audit](safedep-hermes-backdoor-audit-2026-11-26.md) adds a field artifact at a different model-placement boundary: the would-be implant is a general-purpose AI agent controlled over a chat gateway. Its nine package releases are publisher-side variants; downloaded instructions are configuration. SafeDep has not observed victim installation, so even service access is a design inference rather than a case-specific command/result observation.

## Suggested paper structure

1. **Introduction and scope.** State the Project Drexel hypothesis and why claims about “self-modifying AI malware” need operational definitions.
2. **Methods.** Describe the source-only exploratory search, primary-source preference, dated cutoffs, screening rules, and claim-level extraction. State explicitly that the source registry spans earlier model-resource research and is not a denominator of independent malware cases. No model or malware tests were performed in the present research window.
3. **Mechanism taxonomy.** Separate command/action selection, one-off generated code, author-side builds, service replacement, resident module addition, existing-function replacement, and model-weight/configuration changes. Give each a distinct continuity claim. The [Hyperspace source audit](hyperspace-source-audit-2026-11-26.md) illustrates why a reused *evaluator* process and a newly instantiated *candidate agent* must also be separated.
4. **Software engineering constraints.** Use official runtime documentation and peer-reviewed dynamic-update work to analyze safe timing, active functions, mixed old/new execution, state migration, rollback boundaries, and repeated changes. [Kitsune](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf) is the strongest serial network-continuity anchor; [PROTEOS](https://download.vusec.net/papers/asplos-2013.pdf) illustrates continuity through process replacement, which fails the strict process-identity condition. The [cl-sm-harness author account](https://github.com/browep/cl-sm-harness/blob/0add24563f436eeb796121aa2606ca56d18e389a/harness/docs/sm-harness.md) gives a concrete stale-handler counterexample: a successful reload can fail to update the behavior an already-open session actually invokes.
5. **Model-to-code and field evidence.** Compare the closest cases in the [master matrix](master-feasibility-evidence.md#four-part-evidence-check). Keep first-party observation, code-level capability, analyst inference, and forecast visually distinct. Resolve [GTIG's HONESTCUE wording conflict](promptflux-case-file.md) by privileging the detailed technical account while reporting both statements.
   The [AttackGPT source audit](attackgpt-source-audit-2026-11-26.md) gives a useful near-case: repeated controller-side script generation and an ongoing endpoint stub coexist, but local validation repair and resident-code revision are different events.
   [Amazon's Cairn shell case](aws-cairn-shell-process-boundary-2026-11-26.md) shows a reported agent-written field payload becoming functional in a newly spawned interpreter. [Gambit's retailer campaign](gambit-controller-and-reinjection-boundary-2026-11-26.md) shows externally directed agents and deterministic skimmer reinsertion after a site redeploy. Both sharpen the process and authorship boundaries without meeting the two-revision claim.
6. **Repeated-change reliability.** Explain why a first accepted change does not predict a second. Use the [controlled two-revision harness audit](two-revision-harness-study-audit-2026-11-26.md), [feedback-directed revision audit](feedback-directed-revision-audit-2026-11-26.md), [selection and transfer audit](revision-selection-and-transfer-audit-2026-11-26.md), [SWE-Maintain](https://arxiv.org/html/2610.14768), [Multi-step SWE](https://arxiv.org/html/2611.07166), [BoxBox](https://arxiv.org/html/2611.09218v3), [HSI](https://arxiv.org/html/2608.08466), and [Shah and Kathrotia](https://arxiv.org/html/2611.22299) as bounded benign comparisons. The two-revision study gives 54 substantive changed-source transitions but separately evaluates each frozen snapshot and shows a development-to-held-out gap; its post hoc selector underlines the need to record promotion and abstention. He distinguishes triggering-failure repair from collateral breakage and held-out gain, with different results in retrospective code edits and controlled instruction edits. RRSI, SEAGym, HarnessOpt-Bench, and HARD separate candidate retention, update completion, intermediate regression, and held-out transfer. HARD's accumulation of gate rules is a useful development-versus-held-out warning, but it evolves defense rules rather than a resident payload. HSI's reported Crafter trajectory peaks before its last iteration, illustrating version-selection risk, but mixes prompt/tool/control-logic changes and supplies no one-process remote-access trace. Label differing tasks, budgets, runtimes, and denominators; Multi-step SWE's per-step and whole-chain scores must not be treated as a two-revision live-program rate.
7. **Placement, resources, and observability.** Compare hosted, external-controller, local, distributed, and already-present browser-model options. [Anthropic's contained replication study](https://www.anthropic.com/research/self-replicating-ai?full=1) usefully separates a model running across 15 small devices, a 9B model's inference-setup success, and end-to-end trials driven by a larger externally served model; none demonstrates resident self-revision. [Lin et al.](https://arxiv.org/html/2605.30621v2) separately measure a model's ability to write a harness update and a task agent's ability to use it, though their skill loading is context retrieval rather than executable activation. Keep resource claims tied to the measured hardware and complete request. Treat detection as a separate empirical outcome with named sensor configuration; [Prinos and Brush](commercial-edr-observability-audit-2026-11-26.md) show why telemetry surface, lag, attribution unit, and carried-over autonomous state matter. A catalog of possible signals is not an alert probability.

   [Patodiya's local-code study](local-code-model-energy-audit-2026-11-26.md) makes a file-size/solved-task/energy comparison on one Metal-accelerated laptop, and [Abkin et al.](https://arxiv.org/html/2610.32417) show that per-token energy can favor the opposite precision from whole completed-task energy on dedicated A100 hosts. Together they motivate reporting **full-sequence** cost and failure counts, without transferring either study's task scores or hardware costs to a resident controller. [Unit 42's field campaign review](unit42-agentic-webshell-boundary-2026-11-26.md) separately demonstrates why a high volume of generated scripts through one foothold does not make the foothold a self-revised process.
8. **Decision and limitations.** State what is technically possible, what has actually been observed, what remains unknown, and which new evidence would change the verdict. Propose a future authorized **benign** study only as a protocol, with no operational payload construction in this paper.

The [SWE-Shift audit](mid-execution-change-audit-2026-11-26.md) supplies a matched-prefix Clean/Shifted design and preservation/freshness oracles for one externally imposed coding-workspace change. The [failure-detection audit](failure-detection-and-repair-audit-2026-11-26.md) separately tests whether agent-written checks notice function loss that a forcibly recalled author can repair. The [warrant audit](revision-warrant-audit-2026-11-26.md) adds the prior question of whether the alleged failure was real and the accepted delta necessary. [Retrospective-transfer evidence](retrospective-transfer-audit-2026-11-26.md) separates a proposal, implemented artifact, loaded context, consulted file, and behavioral effect. These are method precedents for a future benign study, not Drexel outcomes or repeated model-authored change estimates.

The [serial-revision estimand](serial-revision-estimand-2026-11-26.md) gives the proposed paper's exact cohort and outcome rule. In one complete cohort, two accepted-and-functional transitions are nested; report both conditional and all-instance rates, all proposals, and missing evidence. No cross-study multiplication is defensible.

The [runtime-intervention audit](runtime-intervention-boundary-audit-2026-11-26.md) supplies a further classification and causal-design check: HealBench executes model-written state repair in a paused process; ARIA substitutes one pending message and measures harm against an untreated run; REVISE treats new workflow instructions as revisions and checks for stale effects. These are useful method analogies, but none installs two executable payload-code versions in one process.

The [trusted tool-update audit](tool-update-adoption-boundary-2026-11-26.md) adds a version-specific collateral-behavior check: a normal task can complete after updated executable code runs while unrelated side effects occur. Its prepared single update is researcher-authored, and adoption may replace a tool server, so its rates do not supply model causation, process continuity, or a serial Drexel outcome.

[Kim's paired one-round refinement study](feedback-directed-revision-audit-2026-11-26.md) offers a useful experiment-design contrast: the same initial candidate is revised with either model-generated critique or preselected diagnostic feedback, with repair and regression reported separately and two fresh-generation replications. Its diagnostic test is a subset of final tests and misses many final failures, so a later Drexel paper should avoid treating a single passing validation check as proof of preserved function.

[Pianese et al.'s PowerShell study](powershell-model-proxy-audit-2026-11-26.md) should be cited only for its conditioned Sigma-rule overlap and generation setup. The paper should not equate a rule-set match to a working remote-control program, an endpoint alert outcome, or a measured local CPU footprint; its experiments used four A100 GPUs and disabled endpoint protection.

[Shirudo](shirudo-live-shield-audit-2026-11-26.md) is a useful single-change counterpoint in the runtime section: its operator-side Codex agent generated a defensive Java guard reportedly attached to a running service, with an install/reject log. Cite it as one controlled live-attachment example and state that the project's standard Java-agent instructions instead reach new JVM starts. Neither path documents two model-caused resident revisions or retained remote control.

[Bitdefender's full SilkParasite report](silkparasite-plugin-result-audit-2026-11-26.md) should anchor the distinction between delivery, mapping, initialization, and remote task result in a real modular-RAT analysis. Its CookiETagRAT `load|success` precedes mapping, making it unsuitable as an applied-version marker. The campaign's indirect AI-assisted development assessment cannot be merged with a different family's observed plugin/C2 mechanism to claim a model-caused chain.

## Guardrails for quantitative claims

- Do not count process presence, a prepared SSH key, persistence artifact, or attempted tunnel as a successful remote-control task. [Microsoft's editor-extension analysis](https://www.microsoft.com/en-us/security/blog/2026/10/30/inside-malicious-claude-code-branded-cursor-extension-persistent-ssh-backdoor/) explicitly separates these states and reports platform-dependent failures; the AI branding of that package does not imply model-authored code.
- Do not infer a Drexel success probability by multiplying unrelated rates from code-generation, endpoint, and dynamic-update studies. For a true serial estimate, count all initial continuing instances and use the conditional second-change outcome after the first accepted version and its retained state.
- Distinguish submitted proposals, changed artifacts, accepted versions, active executions, and functioning access. A “success” figure must name its unit and denominator.
- Do not turn [BypassGym's](https://arxiv.org/html/2611.13684) 71/90 fresh-candidate passes into a two-revision rate or an undetected rate. Its endpoint is restored between submissions and unblocked alerts do not fail its verdict.
- Do not combine the [COGENT conference abstract's](cogent-endpoint-claim-audit-2026-11-26.md) mutation-cycle claim with the related thesis abstract's 45-run bidirectional C2 matrix as though they were one documented process/version experiment; neither accessible abstract provides that link.
- Do not turn [Sugio and Ito's](generated-artifact-detection-audit-2026-11-26.md) six flagged analysis *conditions* into a universal endpoint detection rate. Their artifact classes, packaging, analysis platform, and timing differ from COGENT and the expanded Drexel claim.
- Do not interpret [Sophos's](https://www.sophos.com/en-gb/blog/fake-ai-real-malware-attackers-impersonating-ai-brands) selected MDR case count as prevalence, [Kitsune's](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf) network continuity as a malware success rate, or a single endpoint alert as general detection efficacy.

## Evidence still most valuable

A publication or reproducible benign trace that joins two exact model responses to two distinct accepted code artifacts, shows each becoming active in one process, records intervening state and any rejected candidates, and returns an independently issued remote task result after each version would directly test the expanded hypothesis. Short of that, the paper should present a bounded feasibility judgment and identify which link each source establishes.
