# Autopoiesis: generated code in a continuing serving system

26 November 2026. Source-only audit of [Jiang et al., *Autopoiesis*, arXiv v1](https://arxiv.org/html/2604.07144), posted 8 April 2026. No model, serving system, or payload was run for Advent Cybersecurity. This is a benign LLM-serving-policy design and evaluation, not a remote-access case.

## Code path claimed by the authors

The system separates a data plane that handles requests from a control plane that uses GLM-4.7-Flash to synthesize and select improved policy code. Its editable surface is **two pure functions**, `schedule` and `should_reschedule`, rather than the full serving program. The control plane writes a selected version to shared staging. At the next monitoring point the data plane is described as loading the replacement; subsequent calls use the new functions while an in-flight serving plan continues. This is stronger than merely reporting offline generated candidates because the authors specify a live adoption boundary and continuous serving architecture. It remains an author-described mechanism in the public paper, without a published process identifier, exact version hashes, and ordered per-swap request outcomes.

The evaluation uses three cluster configurations ranging from 32 H100 GPUs to heterogeneous or elastic configurations of up to 64 GPUs. Its workloads derive from ShareGPT, LongBench, and Azure Functions traces, with synthetic fluctuation patterns added; the outcome is trace completion time and throughput. The paper reports policy behavior changing between workload phases and aggregate gains, but does not provide a two-swap event sequence for one identified data-plane process, nor a functional request result keyed to each selected policy version. Rescheduling counts in its tables are **serving-plan changes**, not counts of model-generated policy-code replacements. These percentages and costs do not characterize a small model on an endpoint.

## What it adds to Drexel feasibility

Autopoiesis is an engineering precedent for narrowing the mutable code surface, compiling or evaluating candidates in a separate control plane, staging a selected version, then adopting it only at an explicit monitoring boundary. The stateless pure-function surface avoids much of the state migration demanded by a resident program's general logic. A future benign analogue would still need to record each control-plane model response and artifact hash, each data-plane activation with process identity, and a function check after each of two changes. The source does not report a remote-control workload or show that a policy that improves throughput preserves unrelated service functions. The paper's online-serving vocabulary should therefore be cited for **bounded function adoption**, not as proof of Drexel's integrated chain.
