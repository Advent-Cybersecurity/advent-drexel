# Composition-conditioned, block-aligned FFN pruning: a falsifiable CPU study

**Status, 2026-11-13.** This is a prospective experiment, not a measured four-gate result. No reviewed artifact has jointly demonstrated smaller complete deployment, lower cold CPU RAM, fewer full-request CPU-seconds, and retained sealed dependent-step quality against the same-source Q4_K_M model. The current 1.5B reference failed the ordered-state development floor, so its existing file and resource measurements cannot establish retained multistep quality. A community Qwen3-4B Q4_K_M reference cleared a narrow public development screen described below; no physical-pruning candidate or sealed quality result exists.

## One hypothesis

Physically remove whole 256-channel groups from the feed-forward intermediate dimension, then retrain the narrower model using a **composition-sensitive calibration objective** before Q4_K_M export. The proposed selector would prefer groups whose removal least increases the loss on *dependent chains relative to their isolated primitive steps*. It would optimize that loss jointly with ordinary task loss and a measured CPU cost model. The intended advantage is to save physical matrix rows or columns, hence complete bytes and CPU matrix work, while protecting the features that connect steps. This is an inference to test; the cited work does not establish that such features exist as separable FFN channel groups.

For a public development example with a dependent chain `c` and matched isolated primitives `p1...pk`, let `D(x,m)` be the increase in length-normalized gold-answer negative log likelihood after applying channel mask `m` to the source model. A possible prespecified selection score is

`J(m) = mean[D(c,m)] + λ mean[max(0, D(c,m) - Σ wi D(pi,m))] + μ measured_CPU_cost(m)`

subject to an exact exported-byte ceiling and an aligned, physically removable mask. The second term is an *excess composition penalty*, not a measure of actual task success. Its weights, prompt form, and `λ` must be selected using development data only. It cannot substitute for a sealed, unconditional final-answer success gate. Masking must be followed by actual tensor surgery and export; leaving zeroed channels in a dense GGUF does not realize the proposed resource mechanism. Any recovery or distillation must be counted and given the same token and optimizer budget as the generic-mask control. No longer inference trace or external executor is assumed, because either could erase a CPU-seconds gain.

The closest published overlap is substantial. [QPruner](https://aclanthology.org/2025.findings-naacl.240.pdf) (Findings of NAACL 2025) already combines structured pruning, mixed precision, and recovery, but measures NF4/GPU settings against an equally pruned half-precision control, not this CPU Q4_K_M comparison. [GRASPrune](https://aclanthology.org/2026.acl-long.491.pdf) (ACL 2026) learns physical FFN and KV masks under a parameter budget, so learned channel gates are established prior art. [Reasoning Models Can be Accurately Pruned Via Chain-of-Thought Reconstruction](https://proceedings.iclr.cc/paper_files/paper/2026/file/e70ffb3f05096e62b5077d8e1b62e668-Paper-Conference.pdf) (ICLR 2026, hereafter RAC) already calibrates pruning on on-policy generated reasoning, and [OBC-Prune](https://arxiv.org/html/2609.17890v1) (2026-09-15 preprint) already weights correct and incorrect reasoning rollouts using sentence interventions. Most directly, [Long-Short Contrastive Pruning](https://arxiv.org/html/2610.34336v1) (2026-10-25 preprint, hereafter CSD) **physically removes MLP neurons** selected by contrasting long and short correct reasoning traces, then trains for shorter traces. [LayerTrim](https://arxiv.org/html/2610.19121) (arXiv v1, 2026-10-13) uses reasoning-trace calibration to rank MLP features, but reports GPU resource results and quality loss. [AutoCompress](https://arxiv.org/html/2611.08290) (arXiv v1, 2026-11-05) searches physical architectures against profiled serving cost and distills the student on GPUs. The proposed distinction is the **excess loss on dependent chains relative to matched isolated primitives**, rather than the long-versus-short trace contrast, as a selector for a physically narrower, supported Q4_K CPU artifact. That distinction is only a hypothesis. A positive local result would be a specific CPU/GGUF deployment result, not proof that reasoning-aware calibration, outcome weighting, physical pruning, or hardware-guided selection was invented here. A transferable method claim requires outperforming CSD-like, RAC-like, and OBC-like calibration at identical physical width, a generic-mask selector, and a matched-byte bit-only allocator on at least two base models and CPU classes. The [official Qwen3-4B-Instruct-2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507#model-overview) states that this particular base is **non-thinking** and emits no `<think>` blocks, so the published CSD trace recipe is not directly executable here. A same-base variant would need prospectively elicited and validated long and short *correct solution text*; if those pairs cannot be obtained, report CSD as prior art and evaluate method novelty on a separate reasoning-capable base rather than claiming to have beaten it.

## Quantitative break-even and equal-byte controls

The pinned 1.5B tensor census in the [previous architecture note](frontier-architecture-research-2026-11-12.md) has 28 MLP blocks, hidden width 1536, and intermediate width 8960. Gate and up matrices are Q4_K; 14 down matrices are Q4_K and 14 are Q6_K. A 768-channel trim, aligned to three 256-weight K blocks, removes 8.57% of the intermediate width. From Q4_K's 144 bytes and Q6_K's 210 bytes per 256 weights, the **packed tensor-payload estimate** is

`768 × 1536 × (70 × 144/256 + 14 × 210/256) = 59,996,160 bytes`.

This is an unexported estimate. It is near the **measured** 60,166,656-byte, 5.38% complete-GGUF saving from the separate Q6_K-to-Q4_K output-head export, which therefore supplies a strong bit-only size target. The 768 cut is an implementation diagnostic on the current 1.5B source, not a quality candidate until that reference clears a dependent-step development floor. A stronger chosen base needs its own census and block-aligned cut; copying the 768 value across architectures would be unjustified.

### Qwen3-4B-Instruct-2507 topology correction, 2026-11-13

The [official pinned config](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507/blob/1b4199c4f36b0cef378bfb12390c18780c18af4c/config.json) declares 36 layers, hidden width 2,560, FFN width 9,728, vocabulary 151,936, and `tie_word_embeddings: true`. The pinned [Qwen3 tensor loader](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/src/models/qwen3.cpp#L17-L50) accepts a missing separate output matrix by duplicating the input embedding and expects every layer's gate/up/down triplet to have one `n_ff` width. Its [load-local macro](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/src/llama-model.h#L1092-L1103) calls `hparams.n_ff()` without a layer index; the [function signature](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/src/llama-hparams.h#L472-L478) defaults that index to zero. The [generic metadata loader](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/src/llama-model.cpp#L1539-L1558) can read a feed-forward-length array, but this Qwen3 tensor path still uses the scalar from layer zero. A **different physical width by layer is unsupported by this pinned loader**. The experiment must trim the same *number* of channels in all 36 layers; it may choose different channel identities in each layer. This removes a potentially valuable layer-wise width-allocation option from the unmodified backend. The [pinned converter](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/conversion/base.py#L1909-L1916) emits the source `intermediate_size` as GGUF feed-forward length, so a source-model surgery must update that global config value before conversion. These code paths establish a shape-compatible export design, not that a trained narrow checkpoint will retain quality.

I read only tensor descriptors from the existing 2,497,280,736-byte **community** Q4_K_M GGUF, avoiding inference during the concurrent reference screen. Its 36 `ffn_gate.weight` and 36 `ffn_up.weight` matrices are Q4_K, shape `[2560, 9728]` in GGUF order. The 36 `ffn_down.weight` matrices have shape `[9728, 2560]`: **18 are Q6_K and 18 are Q4_K**. The Q6_K down layers are 0, 1, 2, 3, 6, 9, 12, 15, 18, 21, 24, 27, 30, 31, 32, 33, 34, and 35. There is no `output.weight`; the tied `token_embd.weight` is Q6_K. The [static inventory](../data/frontier-cpu-qwen3-4b-static-tensor-audit-2026-11-13.json) records total types and the embedding; the per-layer down types here were checked directly with `GGUFReader`. This community file is a reference-only screen. A matched candidate and control must both be exported from the **same pinned official BF16 source**, because the community quantizer's selected tensor map cannot be assumed to reproduce automatically.

For a uniform 256-channel trim, the new FFN width is 9,472, exactly 37 groups of 256. Gate/up matrix rows still have 2,560 values, exactly 10 such groups, and down matrix rows have 9,472 values. Thus each matrix dimension required by the observed Q4_K/Q6_K packing is block divisible. The candidate must select a coherent channel set across gate/up rows and down columns within each layer, compact the BF16 matrices, update `intermediate_size`, and *then* quantize. Arbitrarily zeroing channels in an already packed GGUF would save no bytes. The [pinned block definitions](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1bfeeecebf9e9ef19fcd6eed565bd70a/ggml/src/ggml-common.h#L341-L368) give 144 bytes per Q4_K block and 210 per Q6_K block. If the new same-source export reproduced the observed Q4/Q6 map, the **tensor-payload estimate** for one 256-channel step would be `36 × 2 × 256 × 2560 × 144/256 + 18 × 256 × 2560 × 210/256 + 18 × 256 × 2560 × 144/256 = 42,854,400` bytes, or 1.716% of the present community file. Two and three width steps predict 85,708,800 and 128,563,200 payload bytes. Metadata, padding, other tensor-map changes, runtime repacking, and complete deployed bytes remain unmeasured.

This tied model cannot inherit the 1.5B **head-only** precision control. Changing its Q6_K `token_embd.weight` changes both input lookup and output projection. A Q6_K-to-Q5_K tied-tensor control would save a theoretical 51,658,240 payload bytes on the present file, 8,803,840 more than the predicted one-step width trim, a 0.353% whole-file gap. That is a useful *near-byte* simple control, not a matched artifact or the main method comparator. The stronger control is a same-source, supported-format, RAMP-like bit allocation trained or calibrated with the same budget and deliberately bracketed around the **actual** narrow GGUF's complete package bytes. Prespecify a tight tolerance, for example ±0.1% of the reference package; if the allocator cannot reach it, report the nearest above/below complete-byte arms and do not assert an equal-byte method advantage. Keep the tied Q5_K arm and whole-format Q4_K_S as simpler controls with their actual byte gaps reported. A generic physical mask at the same 9,472 width isolates the value of the composition-conditioned selector. All arms use the same tokenizer, runtime build, prompt, task generator, and development allocation. The smallest decisive claim is a four-gate win over the same-source Q4_K_M reference, followed by a resource-and-quality Pareto comparison against both the same-width generic mask and the near-byte bit-only controls. A 256-width cut alone would be a modest storage result; it does not establish a project-level improvement until cold RAM, full-request CPU, and sealed dependent quality also pass.

The **first mechanical falsifier** is a 256-channel, untrained tensor-surgery export from the pinned official weights: update the config, keep tied embeddings untouched, quantify all FFN shapes and types, and require the pinned loader to complete a short benign forward pass. This tests the shape and quantizer path, not retained capability. If the file fails to load or the quantizer silently promotes enough tensors to erase the byte saving, reject this deployment path before training. For a confirmatory resource test with a stronger signal, a **prospectively chosen 768-channel uniform cut** would reduce the FFN arithmetic dimensions by 7.895% and, under the observed type map, predict 128,563,200 fewer packed bytes, about 5.148% of the present file. That remains conditional on a competent reference-only quality floor and a successful development recovery; it is not a measured file or speed result. The 768-width candidate would be compared with a generic mask at the identical 8,960-channel width and a same-source bit-only allocation matched to its *realized* complete package bytes. Freeze that choice before opening sealed task scores. If the larger cut fails the four gates, an exploratory smaller-cut run cannot replace it as a confirmatory success.

For a genuine comparison, define `B` as every deployable model/tokenizer/runtime byte within a fixed packaging boundary, `R` as both fresh-process peak RSS and controlled-charge cgroup peak, and `C` as CPU-seconds for a complete request including prompt prefill, generation, permitted retries, and failures. A candidate must satisfy prespecified positive margins `B0 - B > εB`, `R0 - R > εR` for **both** memory measures, and `C0 - C > εC`, while passing sealed quality noninferiority and an absolute reference-success floor. Shorter matrices do not guarantee smaller `C`: total request work also depends on prompt length, generated tokens, kernel choice, repacking, and retries. Report token counts, per-token rates, and cold-load allocation traces only as diagnostics.

The decisive bit-only arm is a same-source RAMP-like allocation that matches the width candidate's **actual complete package bytes** within a frozen tolerance, uses the same calibration budget, and stays in supported GGUF tensor types. Include whole-format Q4_K_S and any simple one-tensor precision arm with their actual byte gaps. A head-only Q4_K arm applies to the earlier **untied 1.5B** source, not to tied Qwen3-4B. Include a generic physical mask at the identical output width, with the same calibration and recovery budget. Attempt a CSD-like long-versus-short correct-solution comparator only if the non-thinking 4B model yields validated paired solutions on development tasks; hold its rollout, training, and recovery budget equal to the proposed selector. Otherwise, a four-gate 4B deployment finding remains possible, but a method novelty claim needs a reasoning-capable base and a same-base CSD comparator. The published 7B CSD numbers cannot be directly compared with a 4B GGUF. A same-source Q4_K_M reference is necessary for feasibility but too weak alone for a method claim.

## Smallest decisive experiment

1. **Reference-only floor.** Screen one stronger, provenance- and license-checked open checkpoint on public development instances from two benign dependent-step families. Record its complete Q4_K_M package, CPU feasibility, parser, generation cap, and unconditional final success. Require a prespecified absolute floor in both families before any candidate training or sealed evaluation. The current 1.5B ordered-state development result, 3/8 under its best tested explicit-reasoning prompt, did not pass the prior screen. A [community Qwen3-4B Q4_K_M reference-only run](../data/generated-quality-dev-qwen3-4b-reference-2026-11-13.jsonl) subsequently scored 8/8 arithmetic and 8/8 ordered-state on the reused 16-item public development set, with all 16 responses stopping normally and final-line compliance 7/8 in each family. This is a narrow development feasibility signal on four shared templates, not an independent or structural holdout. It does not validate a same-source official export, any pruning candidate, or general quality retention. The 1.5B and 4B sample rates are not population estimates; a new same-source reference and disjoint sealed structures remain necessary before a four-gate claim.
2. **Lock the design.** Use public development tasks to choose one aligned width cut and `λ`; compare the composition-conditioned mask, an ordinary final-task-loss mask, and a generic physical mask under equal width and recovery budgets. If development tasks yield validated long and short correct solution pairs from the same 4B base, add a CSD-like selector under equal total rollout, calibration, training, and recovery budgets. If not, retain CSD as close prior art and defer a method novelty claim pending a reasoning-capable base. Export each actual candidate as a narrow Q4_K_M-compatible GGUF. Audit dimensions, all tensor types, tokenizer, hashes, complete bytes, and any runtime repack. Reject a mask that remains logically sparse but physically dense. Choose a single candidate and a bit-only equal-byte control without looking at sealed outcomes.
3. **Measure costs before quality unsealing.** On one pinned llama.cpp build, alternate fresh-process paired runs under the same repack and threading policy. Use fixed-token workload diagnostics and complete benign requests. Record package bytes, process RSS, cgroup peak, CPU-seconds, wall time, output tokens, and error/retry rates. Stop if the width candidate fails any resource margin. Repeat a passing locked pair on a second CPU class; a first-host-only win is platform-specific.
4. **Seal dependent quality.** Precommit two disjoint families and unseen dependency structures, for example graph-topology groups from the [official iGSM generator](https://github.com/facebookresearch/iGSM) and separately generated ordered-state operation motifs. That topology split is a *proposed design*, not a published iGSM validation. Within each family, include matched isolated primitives and independent batches, but make unconditional final success on dependent chains the primary outcome. Keep format compliance, primitive success, conditional failure, length stops, and token count separate. Freeze generator revision, seeds, prompt, parser, task mixture, token cap, model hashes, and one-sided paired noninferiority margins before scores are viewed. Select sample size from an independent reference/control discordance pilot and allocate simultaneous error across both asserted family bounds. The prior generated arithmetic/state suite was only a narrow development pilot; its shared templates cannot establish broad composition competence.

**Stop rule.** Reject four-gate feasibility if exported bytes fail to fall, either cold RAM peak rises beyond the locked margin, complete-request CPU-seconds fail to fall, or either sealed family misses the paired noninferiority bound. Reject the claimed *selection-method advantage* if the generic same-width mask or equal-complete-byte bit-only control has equal or better sealed success and no worse RAM/CPU on both hosts. For a method novelty claim, also require superiority to an executable same-base CSD-like comparator; failure to obtain valid paired 4B solutions means this particular experiment cannot support that claim. Absence of a statistically significant difference is insufficient to claim noninferiority. If the composition-conditioned mask only wins on public development tasks or one structural family, report an exploratory result. Count search, training, distillation, and teacher compute separately and calculate the request volume required to amortize them.

The next practical milestone is therefore an auditable, physically narrow export plus a competent reference-only quality screen. Without those, an added compression percentage would be a storage observation, not a retained-capability result.
