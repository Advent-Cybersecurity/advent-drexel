# Live-code activation: source-level comparators

Advent Cybersecurity source audit, 26 November 2026. All findings below come from primary documentation or pinned source inspection. No model, agent, malware, or payload was run. These are benign mechanism comparators, not Drexel observations.

## A real same-runtime module replacement and its second-update limit

[SMAXr's `apply_patch` tool at commit `99b360e`](https://github.com/AsmanovLev/SMAXr/blob/99b360e0c217f91b20ae6c254bca2581bdf6a3c2/lib/smaxr/tools/apply_patch.ex) accepts a `.ex` file edited through the agent's tools, calls `Code.unrequire_files` and `Code.compile_file`, and returns the compiled module names. Its [unit test](https://github.com/AsmanovLev/SMAXr/blob/99b360e0c217f91b20ae6c254bca2581bdf6a3c2/test/smaxr/tools/apply_patch_test.exs) loads a test module returning `:first`, edits the file, reloads, and checks that a call returns `:second` in the same BEAM. The [README](https://github.com/AsmanovLev/SMAXr/tree/99b360e0c217f91b20ae6c254bca2581bdf6a3c2) describes use of the new code on the next bot turn; there is no published model-authored two-revision conversation or version-specific remote task record. It also says supervisor-child changes need a restart.

[Erlang/OTP's code-loading documentation](https://www.erlang.org/doc/system/code_loading.html) explains a material constraint: current and old module versions can coexist; a process lingering in old code must make a fully qualified call to switch; loading a third version purges the oldest and can terminate processes lingering in it. Thus a compile success or module-name report cannot alone establish that a continuing worker invoked the new version or survived the next replacement. This is a language-runtime rule, not an observed SMAXr failure.

## A guarded cell mutation with a pending state

At pinned [samizdat commit `53e1bfe`](https://github.com/samizdat-code/samizdat/tree/53e1bfe06182ee6ffb418e7ba4f396950e95fdb2), the author's [mutation protocol](https://github.com/samizdat-code/samizdat/blob/53e1bfe06182ee6ffb418e7ba4f396950e95fdb2/src/samizdat/mutation.clj) describes checkpoint, in-image cell reload, workflow validation, dry run, per-definition probes, held-out battery, and commit or rollback. Its [unit tests](https://github.com/samizdat-code/samizdat/blob/53e1bfe06182ee6ffb418e7ba4f396950e95fdb2/test/samizdat/mutation_test.clj) include one human-authored change from `+1` to `+10` that commits and returns `10` through the live registry. They also check that a battery-pending candidate leaves the prior handler active until an acceptance callback. These are source and checked-in test assertions, not tests run for this audit. The same tests cover syntax/wiring/soak failure and rollback; none is a recorded two-edit model conversation or a remote-access result.

The repository calls itself a live image, but its evidence unit matters. A successful one-edit unit test establishes a possible in-process replacement and a post-edit function result, while a `:pending` report explicitly does **not** mean the new version is active. The mutation code's effects checks and dry-run stubs are additional engineering conditions; they are not evidence that arbitrary new code is harmless. No OS process trace or repeated model-to-version lineage is published in the inspected files.

## A model-callable active-image definition installer

[Autolith at commit `afa99ad`](https://github.com/lambda-symbolics/autolith/tree/afa99ad208d0bea276ac71305c175f856aa3b92c) exposes `self.define` as a tool. Its pinned [implementation](https://github.com/lambda-symbolics/autolith/blob/afa99ad208d0bea276ac71305c175f856aa3b92c/src/self/tools.lisp) journals the proposed definition, compiles/installs it in the active Common Lisp image, then journals installed or failed status and retains an undo action. In its [self-tool tests](https://github.com/lambda-symbolics/autolith/blob/afa99ad208d0bea276ac71305c175f856aa3b92c/tests/self-tool-tests.lisp), one fixture changes a function from returning `0` to `42` and checks the changed call; another installs two exploratory definitions returning `1` and `2`, then discards the second and checks that the first is restored. These are author-written test fixtures, not model-output transcripts. The two-install fixture does not independently check the function after each installation or involve remote tasking.

The [architecture document](https://github.com/lambda-symbolics/autolith/blob/afa99ad208d0bea276ac71305c175f856aa3b92c/docs/architecture.org) separates exploratory in-image mutation from durable private publication and checkpoint/recovery. It says that on Windows a checkpoint uses `save-lisp-and-die`, exits, and boots the saved core; that path does not preserve an uninterrupted resident program image. Autolith therefore supports a credible model-callable **mechanism** for in-process function replacement, while its published tests and docs do not supply a two-model-revision, same-image, after-each remote-control record. We inspected source and test text only.

## A success log that can precede successful adoption

The pinned [Genesis `HotReloader`](https://github.com/Garrus800-stack/genesis-agent/blob/557b4947326d09093155adbf5aa6191afefe8c29/src/agent/capabilities/HotReloader.js) can return `{success:false}` when Node cannot load changed source. The pinned [self-modification pipeline](https://github.com/Garrus800-stack/genesis-agent/blob/557b4947326d09093155adbf5aa6191afefe8c29/src/agent/hexagonal/SelfModificationPipelineModify.js) awaits `hotReloader.reload(targetFile)` but does not inspect that returned success field before recording `CODE_MODIFIED` with `success:true`; callback failures are caught and logged within the reload path. This is a **static source-path inference**: the implementation permits a successful modification event despite failed activation. It is not a measured failure in a published run. A version-specific callable-result check is needed before treating such a log as active code.

## Reload timing and process identity

The [break-away agent README at commit `9ef8b45`](https://github.com/2389-research/breakaway-agent/blob/9ef8b4589155f3e845787a512db73fd9725f4fe6/README.md) advertises same-process hot reload of its tools, policy, and system prompt, with a separate wrapper restart for core files. The pinned [entry point](https://github.com/2389-research/breakaway-agent/blob/9ef8b4589155f3e845787a512db73fd9725f4fe6/src/index.ts) does cache-busted imports and updates all three `currentRefs`, but its task runner passes the tool array and policy as arguments into a [single `run` call](https://github.com/2389-research/breakaway-agent/blob/9ef8b4589155f3e845787a512db73fd9725f4fe6/src/agent.ts). Within that active call, the loop resolves tools from the passed array, not the later `currentRefs.tools`; an in-flight signal-triggered reload therefore does not establish in-flight adoption. The REPL reads `currentRefs.tools` for its next task, but builds the next policy from the captured `basePolicy` and retains the existing system message. Static inspection finds no later read of `currentRefs.policy` or `currentRefs.systemPrompt` in those task paths. The checked-in [reload tests](https://github.com/2389-research/breakaway-agent/blob/9ef8b4589155f3e845787a512db73fd9725f4fe6/tests/reload.test.ts) assert signal-listener registration, not changed tool/policy/prompt behavior across two model turns. This is a **source-path inference**, not a measured failure or a run performed here. It illustrates why a reload acknowledgement must be tied to the specific subsequent call path and version; core-file restart is a different process lineage.

The [Pi extension documentation at commit `9a4dcac`](https://github.com/earendil-works/pi/blob/9a4dcacb77e6103b4b096380ab5f2e35cb99368b/packages/coding-agent/docs/extensions.md) says `ctx.reload()` replaces extension resources for future calls, while the handler that requests reload continues in its old call frame. A model-callable tool cannot reload while Pi is actively running the agent; the documented pattern defers the request to `agent_settled`. Runtime survival, turn continuity, and immediate execution of the new version are therefore distinct.

The [Linux `execve(2)` manual](https://man7.org/linux/man-pages/man2/execve.2.html) supplies a separate identity caveat. An `execve` call preserves the OS process identity and PID but replaces the program image, stack, heap/data, mappings, and other threads. A PID/start-time match alone cannot prove uninterrupted resident image or in-memory state continuity; an evidence protocol must record image-execution boundaries. This does **not** mean `execve` starts a new OS process.

The author [Poiesis README pinned at `8b0bfa9`](https://github.com/china-nyx/poiesis/blob/8b0bfa9b5b57cc9357114035e9356092a9bf1a6b/README.md) uses an application-level `pid` for a durable conversation/job and separately describes stopping work, promoting a rewritten image, and re-executing the node, which wipes RAM and resumes from stored notes. This is an architecture description, not an observed serial-success trace. Its logical process continuity cannot be silently substituted for uninterrupted OS program-image continuity. The README explicitly treats Erlang-style module hot-loading as a later possible optimization rather than its default path.

## Relevance to the proposed paper

These sources support a five-step evidence ladder: edited bytes, successful compilation/loading, adoption by the target registry or call path, invocation of the new version, and independently observed retained function. The last two steps must be repeated after each claimed revision. None of the examples above publishes the full model-to-two-active-payload-versions-to-remote-command/result chain in one identified remote-access process.
