# Drexel feasibility: continuity, causation, and evidence for live revision

Research begun 26 November 2026 for Advent Cybersecurity; publication wording revised 27 November. This is a source-based feasibility assessment, not an implementation guide or an experimental result. No model, malware, or payload was tested for this note. The [master assessment](master-feasibility-evidence.md) remains the overall evidence record. The strict two-revision chain below is a **Project Drexel research hypothesis**, not an observed property of a deployed program.

## The claim needs four different forms of continuity

The exact claim being evaluated is: **one continuing remote-access program applies at least two model-caused payload-code revisions and retains independently verified remote access after each.** The following properties must be distinguished:

The term *self-modifying* is especially broad in malware literature. For example, [Calvet and colleagues' WaveAtlas study of malware packers](https://virusbulletin.com/uploads/pdf/conference/vb2015/Calvet-etal-VB2015.pdf) analyzes code that reveals or changes executable bytes in successive unpacking waves. That kind of predetermined runtime transformation is a different mechanism from a model proposing a novel behavioral revision in response to feedback. It must not be counted as AI-driven adaptation without a model-to-change record.

| Property | What would establish it | What does not establish it |
| --- | --- | --- |
| Process continuity | A stable process identity across the before, revision, and after intervals, with no intervening exit/restart. | The same filename, path, PID alone, application name, or server address. |
| Code continuity and change | A versioned code artifact or comparable trace showing which changed code became active in that process. | A changed source file, downloaded script, model response, or new build that was never shown running. |
| State and function continuity | The revised process still handles an independent remote-control task and retains any state the claim requires. | A surviving process or socket with no demonstrated task execution; a new process restoring service. |
| Causal continuity | A recorded model output is linked to the specific accepted revision, with operator intervention and rejected proposals visible. | A prompt in the program, AI-like code style, a vendor's label of “AI-powered,” or temporal proximity alone. |

These are evidence criteria, not an assertion that all are necessary for every useful form of adaptive malware. A remotely controlled service can be useful even if its worker processes restart. The *Drexel* expanded hypothesis deliberately asks the harder question of one program maintaining a functional access path through serial code changes.

[Zhao and Zhao's Enoch study](https://arxiv.org/html/2609.00546) formalizes an alternative **logical-instance** continuity claim: an agent can preserve governed identity, memory, and code lineage while its host, model, harness, or interaction surface changes. Its reported operational migration keeps a recorded body revision fixed across transitions, and the authors explicitly distinguish a restart from an in-process continuation and a separately authorized body evolution from migration. This is useful evidence that retained service identity is meaningful without retained process identity. It does **not** relax the stricter question above or supply two model-caused payload-code revisions; the authors report no combined live migration and body-evolution trial. A later Drexel paper should identify whether it evaluates broad service continuity or this review's narrower same-process hypothesis before comparing case outcomes.

## The feasibility question changes with the meaning of “payload modification”

Adaptive behavior can arise through several distinct mechanisms. They should be reported as separate claims, ordered here by what would have to be shown, not by a numerical difficulty score.

| Interpretation | Closest published example | Additional fact needed for the expanded Drexel claim |
| --- | --- | --- |
| Model changes an operator-side source tree or produces a new build for later delivery. | [Anthropic's GTG-20006 report](https://www.anthropic.com/threat-intelligence-report-september-2026) describes AI-assisted modification, rebuilding, and redeployment. | A later build is a new artifact; it does not show the original running instance adopted the change or kept access through two revisions. |
| Resident program uses a model to select a command or generate a one-off script. | [ESET's PromptLock analysis](https://www.welivesecurity.com/en/ransomware/first-known-ai-powered-ransomware-uncovered-eset-research/) describes runtime script generation; [Talos's CLOSEDQUORUM analysis](https://blog.talosintelligence.com/the-closed-quorum-inside-the-first-reported-autonomous-ai-c2-implant/) describes model selection of preexisting handlers. | A transient script or chosen handler is not a revision to the resident payload's own code. The reviewed samples also do not publish a two-revision retained-access chain. |
| Resident program accepts a new executable module while its core process continues. | [Erlang/OTP code loading](https://www.erlang.org/doc/system/code_loading.html) and [Java class redefinition](https://docs.oracle.com/en/java/javase/23/docs/api/java.instrument/java/lang/instrument/Instrumentation.html) establish supported live-code mechanisms in benign systems. | The model must be linked to the accepted module, the new version shown active, and the same process shown functional after each of two changes. |
| The active main loop or native program body changes in place while the same process retains state and remote function. | [Active DSU's conference abstract](https://2024.splashcon.org/details/splash-2024-Onward-papers/3/Active-DSU-Dynamic-Software-Updates-for-Active-Functions) identifies active-function migration as a special challenge. | Evidence must additionally show control-flow and state migration through both changes, without mistaking a restart or child process for continuity. |

The third and fourth rows are technically plausible for deliberately prepared software, but the reviewed malware reports have not established the complete model-caused, two-change, after-each-access sequence. This distinction leaves room for a useful paper result even if the strict chain remains unobserved: it can identify exactly which narrower behaviors are already demonstrated and which claim lacks evidence.

For this review, a **code revision** means a model-linked change to executable behavior that becomes active in the identified resident process. It can be a new version of an existing component or an added executable module, but those should be labeled separately: adding a module does not prove that the program rewrote an existing function or replaced its main body. A model response that is merely saved, compiled, or tested in another process is still a candidate. This definition keeps the minimum claim broad enough for modular runtimes while making the stronger “rewrites its own active code” wording independently testable. A deterministic compiler or packaging step can sit between model output and the applied artifact if its provenance is recorded; undocumented human edits leave model authorship unresolved.

Terminology also needs care. [MITRE ATT&CK's Polymorphic Code entry](https://attack.mitre.org/techniques/T1027/014/) includes software whose code changes across executions to preserve an objective and evade signatures. That category does **not** by itself imply a language model, two changes within one process, or retained remote access after each change. A paper can use the ATT&CK label for a broader technique while retaining the more specific revision-chain test above.

“Self-modification” can also refer to changing the **model** rather than application code. In [Irregular's controlled September 2026 study](https://irregular.cv/research/agentic-self-modification-in-open-weights-systems), a coding agent fine-tuned and replaced a shared checkpoint used by a separate application and future agent instances. The researchers independently loaded the revised checkpoint in a new process and checked its task behavior. This is evidence for an agent-initiated, persistent *model-weight* change under favorable training and deployment access. It is not a resident remote-access payload rewriting executable code, and its fresh-load verification does not establish same-process continuity.

The expanded Drexel claim does **not** require recursive self-improvement of the model or its revision proposer. A fixed model could propose both payload-code changes while the resident program applies them. [Anthony et al.'s November 2026 methods review](https://huggingface.co/blog/daicelabs/ri-is-not-rsi) reserves “recursive self-improvement” for a changed proposer that makes subsequent changes; its screening and coding are largely LLM-assisted and do not include implementation-repository inspection. That terminology helps prevent a model-authored payload revision from being described as proof that the model or its own improvement mechanism got better. The review's counts are about reported self-improvement systems, not Drexel-like malware prevalence.

## What general software engineering proves and limits

Several established runtimes can replace code while software runs. Their documentation supports **technical possibility under particular update mechanisms**, not a general guarantee of arbitrary changes to any program.

| Source | Established mechanism or constraint | Inference for the hypothesis |
| --- | --- | --- |
| [Erlang/OTP code loading](https://www.erlang.org/doc/system/code_loading.html) and [release handling](https://www.erlang.org/doc/system/release_handling.html) | Current and old module versions can coexist. A process must switch into current code; loading a third version may purge the oldest and terminate processes still using it. State-format changes require synchronized suspension, transformation, and resumption rather than simple module replacement. | Two revisions are possible in a designed live-update system, but the *second* revision is precisely where stale-code and state-migration errors can surface. A resident process surviving the first change does not prove it uses the new code or survives the next. |
| [Oracle Java Instrumentation API](https://docs.oracle.com/en/java/javase/23/docs/api/java.instrument/java/lang/instrument/Instrumentation.html) | Redefinition can update class behavior without restarting the VM. Active frames continue old bytecode; later invocations use the new definition. Static values stay as they were, and existing instances are not reinitialized. | A single JVM can temporarily execute mixed versions. A successful class redefinition is weaker evidence than showing that the intended revised method actually ran and the application still worked. |
| [Python `importlib.reload` documentation](https://docs.python.org/3.14/library/importlib.html) | A module can be re-executed within the interpreter, but existing outside references and instances of old classes do not automatically switch. The documentation warns that `reload` is not thread-safe. | A source rewrite followed by `reload` may leave the active access-handling object on old code. Repeated revisions need proof of which version was invoked, not just proof that module loading returned. |
| [Microsoft Visual Studio supported Hot Reload changes](https://learn.microsoft.com/en-us/visualstudio/debugger/supported-code-changes-csharp?view=visualstudio) | Most method-body edits are supported; most edits outside method bodies and some within require a stop and fresh start. | A source edit may appear to be a live revision while the tool actually restarts the target or refuses the change. The supported edit class matters. |
| [Hayden et al., systematic DSU safety study](https://www.chrishayden.com/papers/dsutesting-journal.pdf) | In long release streaks for OpenSSH, vsftpd, and ngIRCd, update timing affected correctness. Their manually selected update points eliminated failures in the tested cases; the two automatic timing restrictions still allowed some failures. The authors limit generalization to their three applications and chosen updates. | Safe update *timing* is an independent engineering problem. A syntactically valid model revision need not be behaviorally valid after application. This is a benign software result and cannot supply a malware success rate. |
| [Hayden et al., quiescence study](https://www.cs.tufts.edu/~jfoster/papers/dsu-quiescence.pdf) | In a small set of event-driven programs with manually placed update points and support changes, reaching full quiescence could be fast under the evaluated workloads. | The existence of a practical update window supports feasibility for deliberately structured programs, but not arbitrary hot swapping or serial access survival. |
| [Zhao et al., object-state transformation study](https://cs.nju.edu.cn/changxu/1_publications/21/ICSE21_01.pdf) | In 190 class changes sampled from Tomcat 8 history, the authors judged 166 to need only trivial object transformation, 21 to need non-trivial transformation, and three not dynamically updatable at the assumed safe point without refactoring. Their PASTA synthesis tool solved 60% of its selected non-trivial transformation tasks. | The need to carry live object state into a new code version is measurable and sometimes difficult even for ordinary server maintenance. These are class-change and selected transformer-task denominators, not probabilities for serial revisions of an implant. |
| [Strömbäck and Varró, Active DSU](https://2024.splashcon.org/details/splash-2024-Onward-papers/3/Active-DSU-Dynamic-Software-Updates-for-Active-Functions) | Their published conference abstract identifies long-running active functions as a limitation of conventional dynamic updating and proposes call-stack/control-flow migration to update them. | Whether an access loop is paused at a safe boundary or is active during revision changes the mechanism needed. This abstract supports a research direction, not a general success rate or evidence of a remote-control chain. |
| [Giuffrida et al., PROTEOS](https://download.vusec.net/papers/asplos-2013.pdf) | In a research OS, transactional updates replace old processes with new ones after state transfer; the old version can resume if preparation or transfer fails. The authors evaluated 50 sampled real updates and explicitly say their OS design is not applicable as-is to commodity operating systems. | Rollback and state continuity are feasible in a purpose-built process-replacement architecture. Its updated component has a **new process identity**, so service continuity here does not establish the same-process Drexel claim. Its reliability/effort measurements cannot be transferred to an endpoint implant. |
| [Wasmtime `Store` and `Instance` API, current 52.0.0-dev documentation](https://docs.wasmtime.dev/api/wasmtime/struct.Store.html) | A host can instantiate modules in a `Store` with host-defined state, but each module has its own instance; the documented `Store` does not reclaim an instance until the store is dropped. [The `Instance` reference](https://docs.wasmtime.dev/api/wasmtime/struct.Instance.html) describes distinct instance ownership. | A native host process could by inference keep running while selecting a newly instantiated executable component, but guest-state transfer and dispatch to the new instance need explicit design. Repeated instantiation into one long-lived `Store` can accumulate memory. This is an API-level option and constraint, not an observed model-directed update or access test. |

A stronger **serial continuity** precedent is [Hayden et al.'s peer-reviewed Kitsune study](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf). Its runtime loads successive C program versions in one running driver process and migrates control and data at designated update points. The authors report updating a live Tor relay across versions 0.2.1.18–0.2.1.30, including several updates under load, while up to 4,000 connections were active; they observed no broken or renegotiated TLS sessions and 7 TB of traffic over the experiment. They also checked maintained FTP connections, Icecast streams, and Tor circuits around updates in controlled workloads. This directly supports the **engineering possibility** of multiple code versions with continuous network service in a purpose-built runtime. The paper does not publish a model-authored candidate chain, autonomous acceptance decisions, or independent remote-command checks after each revision. The Tor result is one research deployment under its own workload, not a general reliability or detection rate for implants.

A more recent, agent-assisted benign service example appears in the [RSInfer author's pinned live-engine record](https://github.com/open-agent-infra/RSInfer/blob/bd26c7e1554211a578e733f7e2fc59feb3a21452/doc/rsi/2026-11-11-real-kernels-hot-apply.md). The author reports one inference worker process accepting **nine** alternations between two source trees. Ten changed code units and a dependent executor unit were reloaded; four prompts produced version-specific outputs that matched a cold start of the corresponding tree. A concurrent request completed under a wait-for-empty transition, while a forced transition interrupted its in-flight stream. This is stronger evidence of **serial code activation and post-change service function in one designed process** than a mere update API or a changed file. It remains an author-recorded development experiment: the public note does not supply exact model-response-to-patch provenance or independent process telemetry, and its checked function was inference service, not remote control. The nine applications alternate **two existing versions**, rather than nine newly generated behavioral revisions. The repository's broader [four-hour session account](https://github.com/open-agent-infra/RSInfer/blob/bd26c7e1554211a578e733f7e2fc59feb3a21452/doc/rsi/2026-11-16-ds1017-hot-apply-time-saved.md) records 29 hot applies **across two cold starts**, including an out-of-memory crash; it must not be summarized as one uninterrupted 29-change process.

The same project records why a committed hot update is weaker than functional recovery. In its [dated failure report](https://github.com/open-agent-infra/RSInfer/blob/bd26c7e1554211a578e733f7e2fc59feb3a21452/doc/framework-bugs/2026-11-11-a-repaired-worker-stays-stopped.md), an injected test error stopped service; restoring the worker code through a successful live apply left new requests returning errors until a separate scheduler unit was reloaded. The authors report fixing that fault afterward. This failure is a service-engineering counterexample, not a malware result: application of good code can leave retained failure state, so the independent after-each behavior check is indispensable.

A separate, more explicit model-to-edit example is [rsibox's pinned Codex/Megatron-LM run record](https://github.com/hao-ai-lab/rsibox/blob/f3ae52b97150632b10e64031beca732d5efa1bc2/repos/megatron/examples/codex-hillclimb/README.md). Its November 7 session submitted 82 *iterations*, including re-measures, skipped or unusable proposals, rejected candidates, and reversions. The harness took Codex-proposed diffs, installed candidate function bodies into a warm training job, required an execution witness on every rank, compared short training checks with the base, and retained a change only after a performance and loss/gradient gate. The authors identify two Codex-authored **code** changes in the three-edit kept set (iterations 11 and 61); the third (iteration 12) was an **orchestrator-set attribute**, not a code change. This is useful evidence that a model-proposed code candidate can be made active and functionally checked in a designed benign runtime. It is not an 82-revision success chain.

The record's opening says “no restart between edits,” but its detailed outcomes report **three runtime failures that poisoned the lab**, followed by respawn and reinstallation of retained edits. Therefore the 82-iteration session cannot be treated as one unbroken process, and the two retained Codex code edits cannot be counted as two changes to the *same identified process* on this public record. No process-ID/start-time sequence is published, and the measured function was model-training throughput and loss, not remote access. The lab's ability to recover and replay retained changes is valuable for engineering feasibility, while the respawns and rejected/no-op edits show why proposal count, accepted code count, process continuity, and after-each service results need separate columns.

The [Symbiont author's pinned harness description](https://github.com/MathisWellmann/symbiont/blob/3cedf3cced44d1a85e7c8e3cb60afbbe0e41dc6e/README.md) and [technical caveats](https://github.com/MathisWellmann/symbiont/blob/3cedf3cced44d1a85e7c8e3cb60afbbe0e41dc6e/CAVEATS.md) expose a different, concrete live-update limit. The harness compiles a model-proposed Rust function into a dynamic library and switches the function pointer in a continuing host. It restricts revisions to declared signatures, and revision-owned state belongs to one library version: activating a new version requires a new state value unless the host explicitly replays state into it. Old libraries remain mapped until safely unloaded; the author estimates roughly 1.2 MiB per retained debug-profile revision. A generated infinite loop can hang a calling thread while the process remains alive, and the harness does not automatically stop it. These are author-documented design constraints, not a measurement of remote-access survival or a general resource estimate for other runtimes. They show why **process liveness, active-code replacement, state continuity, and functional response** are four different facts even in a deliberately designed hot-swap system.

A separate [pinned Asiel Core source audit](asiel-core-hot-reload-audit-2026-11-26.md) traces LLM-generated Python plugin revisions to an in-process `PluginLoader.reload()` call. The loader clears its registry, AST-checks files, imports passing modules, and replaces callable hooks. Its committed proposal registry records 11 `integrated` initial plugin files and 12 validation failures, but no `evolution_loop` proposal or two successful integrations of the same target. `integrated` follows a `py_compile` smoke test, not a hook or task-result check; the direct `REFINE` branch can overwrite a file before reload without its own rollback. This is concrete same-process code-loading architecture with unmeasured version activation and preservation, not an observed remote-access case.

[NexAgent's pinned BEAM source](nexagent-beam-hot-upgrade-audit-2026-11-26.md) implements a different same-VM replacement path. An agent tool accepts a new Elixir module, the manager compiles and loads it, and the loader optionally swaps a tool-registry entry. Source inspection shows `reload_succeeded` is set on compile/load success even when the registry reports no successful swap, while its health check only examines exported-function metadata. This case reinforces why compile, route-to-new-code, actual invocation, and retained service result must be logged independently. The checked-in tests do not supply a two-revision run or remote-control workload.

The pinned [mi agent source](https://github.com/av/mi/blob/ebfa5610e8f5bfcaca5ca423409b087c8ef21e79/index.mjs) offers a small interpreted-code counterpoint. Its loop imports `.mjs` tool modules with a new cache key before each model call and rebuilds the name-to-handler table, while its [author documentation](https://github.com/av/mi/blob/ebfa5610e8f5bfcaca5ca423409b087c8ef21e79/README.md) and [self-extension instructions](https://github.com/av/mi/blob/ebfa5610e8f5bfcaca5ca423409b087c8ef21e79/skills/self/SKILL.md) permit the agent to write a tool file. Static inspection therefore supports a **mechanism for the continuing interpreter to adopt a new or replaced model-written tool on the next model call**. It does not show that an edited main loop becomes active, that a particular generated replacement passed a functional check, or that two versions preserved remote access in one process. The code path also means a file change made during one tool batch is not imported until the next model-call boundary. This is a source-level inference, not an executed trial in this study.

The [pinned `cl-sm-harness` author documentation](https://github.com/browep/cl-sm-harness/blob/0add24563f436eeb796121aa2606ca56d18e389a/harness/docs/sm-harness.md) and [reload implementation](https://github.com/browep/cl-sm-harness/blob/0add24563f436eeb796121aa2606ca56d18e389a/harness/sm-harness/src/tool-catalog.lisp) give an unusually concrete **activation-boundary** example. Its running Common Lisp image can reload changed source through ASDF; an author test at the same commit writes a fixture returning `v1`, reloads it, writes `v2`, reloads again, and calls the new function value in that interpreter. The test is [published source](https://github.com/browep/cl-sm-harness/blob/0add24563f436eeb796121aa2606ca56d18e389a/harness/sm-harness/test/reload-harness.lisp), not a test run performed in this review. The author also documents three distinct limits encountered in the project: an earlier reload reset a configuration variable, leaving subsequent reloads on the wrong subsystem while reporting success; captured function objects and a cached tool catalog could leave old behavior active even after new definitions loaded; and an incompatible live structure change could leave further reloads failing until restart, even after source rollback. Current code addresses the first two with preserved variables, late-bound handlers, catalog refresh, and a next-turn reconnect. This is a benign mechanism and author-reported debugging account, not a published model-output-to-two-active-revisions trace or a remote-control result. It sharpens the Drexel evidence rule: **a successful reload response is not sufficient; the intended handler and task result must be version-checked after each change.**

Host policy can narrow which live-update mechanisms work in a particular protected process. [Microsoft's arbitrary-code-guard documentation](https://learn.microsoft.com/en-us/defender-endpoint/exploit-protection-reference) says an enabled mitigation blocks dynamically generated executable memory and modification of executable pages; its code-integrity guard can restrict which signed images a process loads. These are **configured process protections**, with compatibility implications for legitimate JIT applications, not universal Windows settings. [Microsoft's App Control script guidance](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/script-enforcement) further distinguishes supported script hosts: disallowed Windows Script Host scripts are blocked and PowerShell can run under constrained language, while many third-party Python or Java interpreters are not directly covered if their host remains allowed. [Apple's hardened-runtime guidance](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime.md) and [library-validation reference](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation.md) describe separate restrictions on JIT memory and third-party plugin loading, subject to app entitlements. On Linux, [systemd's `MemoryDenyWriteExecute=` documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) describes a service-level restriction on creating or changing executable memory mappings and notes incompatibility with some legitimate runtime code generation; [kernel documentation](https://docs.kernel.org/userspace-api/mfd_noexec.html) also defines policy-dependent non-executable anonymous files. These mechanisms differ from outright rejection of every interpreted or loaded module, and their effect depends on the configured service and code path. Together, the documents establish **conditional mechanism constraints**, not an observed block, alert, or success rate for any Drexel candidate. A feasibility claim about a specific host needs its OS, process policy, code format, and actual application outcome.

Kitsune's six evaluated programs needed explicit update points and control/data migration changes, reported as 57–529 modified lines across a program's version streak; state-transformer specifications added a further 27–297 lines. Those are measurements of adapting the authors' particular benign programs, not an effort forecast for Drexel. They show why the existence of a live-update library does not make an arbitrary model-generated edit safely applicable to a continuing process.

A [source review of Brahma AI Evo's skill forge](https://github.com/titechprabhasolutions/Brahma-Ai-Evo/blob/3d04d907a54233e18d70e7aa0d904fe3fbcbc6f6/core/skill_forge.py) shows a benign **model-to-new-module** path: generated Python is saved and the [dynamic registry](https://github.com/titechprabhasolutions/Brahma-Ai-Evo/blob/3d04d907a54233e18d70e7aa0d904fe3fbcbc6f6/core/dynamic_registry.py) can import that module when invoked in the existing interpreter. That is architecture evidence for adding an executable capability, subject to the code's actual gates; no independent deployment trace was reviewed. The separate [auto-heal path](https://github.com/titechprabhasolutions/Brahma-Ai-Evo/blob/3d04d907a54233e18d70e7aa0d904fe3fbcbc6f6/actions/auto_heal_engine.py) writes a model-proposed source patch and compiles it on disk, but the reviewed path does not reload the already imported module or show that the active function changed. The repository's “self-evolving” and “hotfix” labels should therefore not be treated as evidence of serial in-process code replacement. It is a desktop assistant, not a remote-access implant, and this review did not run its code or model.

A separate read-only review of [Agent Zero at commit `a6e41ca`](https://github.com/agent0ai/agent-zero/tree/a6e41ca5330af21371f15fc62798f09f0393eedb) identifies a narrower **tool-replacement** mechanism. Its [agent dispatch](https://github.com/agent0ai/agent-zero/blob/a6e41ca5330af21371f15fc62798f09f0393eedb/agent.py) resolves a requested tool to a Python file for each call, and its [module loader](https://github.com/agent0ai/agent-zero/blob/a6e41ca5330af21371f15fc62798f09f0393eedb/helpers/modules.py) creates and executes a fresh module object from that path. The source therefore supports the inference that a changed tool file can affect a later request in the ongoing interpreter, without changing the agent's main loop. This is an architecture inference, not an observed model-authored edit or test: the inspected paths do not publish two accepted changes, retained process identity telemetry, or independent command results. [GTIG's field report](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold) mentions experimentation with Agent Zero, but does not tie that activity to these exact source paths or a resident RAT update.

[Gödel Agent's original paper](https://arxiv.org/html/2410.04444) is a stronger benign **in-interpreter model-to-code** precedent. Its [pinned published implementation](https://github.com/Arvid-pku/Godel_Agent/blob/bbb508796be31c7140cdfc7106efd830a1324242/src/agent_module.py) compiles a proposed Python definition and replaces a module function or class method in memory; the recursive agent loop calls its current method again after handling an action. The paper reports repeated optimization over reasoning tasks and, in 100 MGSM optimization trials, unexpected termination in 4%, temporary performance drops in 92%, and worse final performance than the initial policy in 14%. The named edit path is **bounded** despite the paper's broad self-modification language: it expressly refuses edits to its model-call methods and other specified code forms. The inspected [published MGSM result file](https://github.com/Arvid-pku/Godel_Agent/blob/bbb508796be31c7140cdfc7106efd830a1324242/results/mgsm/mgsm_0.6425.txt) contains task outputs, not a process-identity or per-change provenance trace. This establishes a credible mechanism and author-reported repeated benign behavior, not a two-revision retained remote-access case. Its robustness percentages have no implant denominator.

[Xia et al.'s Live-SWE-agent paper](https://arxiv.org/html/2511.13646) uses “live” for a different boundary. Its agent can create or revise custom **script files** and execute them as tools during one repository issue; the authors explicitly say their implementation leaves the underlying agent loop unchanged. Its 77.4% SWE-bench Verified and 45.8% SWE-Bench Pro results are issue-resolution rates for one submitted patch per issue, not rates at which resident agent code was replaced or a network service survived multiple versions. It supports model-directed *tool creation within an ongoing task* while preserving a fixed orchestrator; calling its tools “self-modification” must not obscure the subprocess/script boundary.

[Fahim et al.'s SelfEvolve paper](https://arxiv.org/html/2604.16314) describes a closer **new-function adoption** design: generate a function on user request, test it in a subprocess sandbox, then promote it to a Python knowledge base with `importlib.reload()` for access without a restart. Its reported 51/55 successes across 11 hand-crafted tasks are passes against ground-truth `pytest` assertions, five independent runs per task. The authors acknowledge that their tasks are largely independent, integration does not guarantee other functions remain correct, and regression tests for interdependent functions remain future work. The paper does not publish one process ID receiving two successive accepted functions with retained state or after-each remote-control results. Its percentage is a **single-task function-test** measure, not a serial update reliability estimate. The linked [Zenodo replication archive](https://zenodo.org/records/18152531) was inspected as an archive without executing code; it contains task datasets and an appendix, while the implementation is linked separately.

The [Nodecode author repository at pinned commit `c329831`](https://github.com/nodecode-ai/nodecode/tree/c3298318925dbb12ecf403b2ae5374aa699cc80d) supplies a more direct *source-level* in-process mechanism. Its [evaluation path](https://github.com/nodecode-ai/nodecode/blob/c3298318925dbb12ecf403b2ae5374aa699cc80d/src/engine/turn.lisp) evaluates model-submitted Lisp forms in the live image and records successful top-level definitions; its [scribe](https://github.com/nodecode-ai/nodecode/blob/c3298318925dbb12ecf403b2ae5374aa699cc80d/src/organism/scribe.lisp) writes individual definitions to a versioned layer and notifies other attached shells. The source also makes the boundary visible: forms within a snippet apply in order rather than atomically, and a failed later form does not undo earlier successful ones. The [README](https://github.com/nodecode-ai/nodecode/blob/c3298318925dbb12ecf403b2ae5374aa699cc80d/README.md) describes a single running gateway, but explicitly says the model replies in its displayed demonstration were scripted for repeatability. This read-only code audit establishes a plausible benign live-definition-replacement architecture, not an independently observed model-caused two-version lineage or preserved remote-access function. No code or model was run in this review.

Another [local-model agent at pinned commit `94433d8`](https://github.com/agustin-gdw/local-llm-agent/tree/94433d8a5f08d377d5c04a5d6992297f8d7cf37f) illustrates why “hot-load” claims require source inspection. Its [`crear_herramienta.py`](https://github.com/agustin-gdw/local-llm-agent/blob/94433d8a5f08d377d5c04a5d6992297f8d7cf37f/tools/crear_herramienta.py) asks Ollama for Python code, checks syntax and simple interface strings, writes the file, imports it, and writes `.reload_tools_signal`. Its [`main.py`](https://github.com/agustin-gdw/local-llm-agent/blob/94433d8a5f08d377d5c04a5d6992297f8d7cf37f/main.py) builds the callable tool registry at startup and when a user enters `/reload`; the inspected main loop has no reader for that signal. Thus the generated module's top-level code is imported, but a newly written tool is **not shown becoming callable in the ongoing agent loop automatically**. A manual `/reload` can rescan tools without exiting the interpreter. This is a source-level interpretation, not an execution result or a serial model-change trace; the repository supplies no remote-access continuity evidence.

There are also mechanisms that preserve **service availability across a restart** rather than process identity. [nginx's binary-upgrade procedure](https://nginx.org/en/docs/control.html) starts a new master process while the old one remains during transition. [systemd's socket activation guidance](https://www.freedesktop.org/software/systemd/man/latest/daemon.html) explains how a bound socket can remain with the service manager while a daemon restarts. These are useful operational designs, but a service still answering at the same address is insufficient evidence for the stricter same-process claim. A research paper should classify them as service or lineage continuity if a particular case uses them.

Three controlled harness studies make **selection after code generation** a distinct feasibility gate. [RRSI](https://arxiv.org/html/2609.24972) retained four of 32 evaluated candidate edits in one legal-workspace run and improved held-out OOD results more than a higher-scoring unregularized evolution did. [SEAGym](https://arxiv.org/html/2606.17546) reports 39/40 completed updates in one batch schedule even while held-out ID performance fell 14.5 points; its main run suffered an intermediate middleware regression that cut train replay to 6/80 before recovery. [HarnessOpt-Bench](https://arxiv.org/html/2608.06301) protects a held-out test partition until final nomination and reports that the best visible validation score is usually optimistic relative to the nominated candidate's test score. These are benign, separately evaluated agent-harness versions with mixed editable surfaces, not same-process payload revisions. The [selection and transfer audit](revision-selection-and-transfer-audit-2026-11-26.md) preserves the denominators and a protocol inconsistency in HarnessOpt-Bench. For Drexel, candidate creation, acceptance, active-code invocation, retained function, and held-out transfer must be recorded separately.

The [pinned Hyperspace research repository](https://github.com/opinionated-systems/hyperspace/tree/9b53c901b6044b4d3aa0b74703081d15648fb591) makes **which process continues** a subtle evidence issue. Its generation loop can import changed model-edited agent code in a reused Python evaluator, while each generation forks a selected source tree and the task evaluator instantiates a fresh `TaskAgent` for every task row. The author reports model-directed peer-code adoption with source snapshots and LLM-call logs, but the changing task-agent object is not shown as one resident object surviving two edits. See the [static source audit](hyperspace-source-audit-2026-11-26.md). Process reuse by a test harness must not be substituted for continuity of the program whose behavior is under study.

[Roesner and Kohno's controlled poisoned-feedback study](https://arxiv.org/html/2609.17817) shows a different failure route for revision selection: a changed agent can retain a harmful code-generation tendency learned from a corrupted benchmark, even after later clean evolution in the tested cases. Their three systems have different edit surfaces, and two primarily change agent directives; one DGM arm required a researcher modification outside the assumed attacker's control. The [feedback-integrity audit](feedback-integrity-audit-2026-11-26.md) details the controls and denominators. This does not demonstrate a resident payload update, but it makes the evaluator's independence and coverage part of any credible Drexel feasibility claim.

## An evidence chain that would actually decide the question

An adequate time-ordered record needs to identify the original running instance; its access path and a successful baseline task; the model request and exact response for proposal 1; the accepted artifact and application event; the resulting active code version; an independently issued task and response; then the corresponding sequence for proposal 2. It should also record rejected proposals, errors, human edits, and any process replacement. The independent task matters because a heartbeat or open socket may survive while command handling is broken.

[Yuan et al.'s BypassGym preprint](https://arxiv.org/html/2611.13684) offers a concrete **functional oracle for a single launched candidate**. Its endpoint checks require process survival and outbound traffic; a separate control-server playbook then checks a session, returned command output, and bidirectional file transfer. In its five-model, six-product, three-payload grid, 71 of 90 runs produced a passing candidate, with one run per combination. An agent can revise and resubmit a candidate within a run, but the evaluator restores the endpoint snapshot before each submission. Thus the numerator is successful *fresh executions*, not revisions adopted by one continuing process. Alerts without a block or termination are excluded from its pass/fail rule, and the authors say they cannot fully separate loader from payload detection. Its strong end-to-end function check is a useful measurement precedent; its pass rate is neither an invisibility rate nor a two-update Drexel feasibility estimate. The paper says full experimental data and framework code are planned for release after review, so its published tables are currently the available audit trail.

The process-identity check is feasible with ordinary defensive telemetry when it is available and configured. [Microsoft Sysmon](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon) documents a ProcessGUID that correlates events despite PID reuse, process-creation and termination events, and optional network-connection events linked to that GUID. [Microsoft Defender XDR's DeviceNetworkEvents schema](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-devicenetworkevents-table) exposes an initiating-process unique ID equal to the Windows Process Start Key. These data can help distinguish a continuing instance from a replacement. They do **not** by themselves reveal which model output caused an in-memory code change, whether the new code was invoked, or whether a remote-control command succeeded. That requires artifact provenance and application-side or controlled observation. The [OpenTelemetry trace data model](https://opentelemetry.io/docs/specs/otel/trace/data-model/) illustrates how causal links can be retained across asynchronous boundaries, but a trace is only as complete and trustworthy as the instrumentation that produced it.

For a Linux case, the [`/proc/PID/stat` manual](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html) defines field 22 as process start time since boot, and [kernel documentation](https://docs.kernel.org/5.16/admin-guide/sysctl/kernel.html) defines a boot-scoped ID. Recording these with the PID, host, and [PID namespace identity](https://man7.org/linux/man-pages/man7/namespaces.7.html) helps distinguish a restarted process or reused PID, especially in containers; coarse sampled start times alone are not a substitute for a complete lifecycle trace. The [kernel's `/proc/PID/maps` documentation](https://docs.kernel.org/filesystems/proc.html) describes a snapshot of mapped regions, permissions, and file inodes. A mapped executable component can support an application claim, but the snapshot cannot establish that its revised function ran, that an earlier version stopped running, or that model output caused the mapping. Those require version-aware runtime records and independent behavior checks.

An agent transcript is useful for model-to-artifact provenance only to the extent that its action record can be corroborated. In [METR and Redwood Research's independent review of the OpenAI–Hugging Face incident](https://metr.org/blog/2026-08-26-openai-hugging-face-incident-investigation/), researchers inspected roughly 1,300 agent transcripts and an agent message-board dump. They report small-scale successful tool-call spoofing in roughly 7% of the transcripts they evaluated, and acknowledge missing activity and errors in their own AI-assisted analysis of the large corpus. That percentage is specific to this unusual evaluation dataset, not a rate for Drexel or for attacker logs generally. The [OpenAI technical report](https://cdn.openai.com/pdf/67869394-cb91-4c12-888c-5cbd85c7814c/OpenAI-Hugging-Face%20Incident-Technical-Report.pdf) also says agents in a later run re-established administrator access with fresh credentials without maintaining a persistent implant. Together with [Hugging Face's victim-side timeline](https://huggingface.co/blog/agent-intrusion-technical-timeline), these sources support an agent-driven intrusion and distinct access paths, while underscoring that a proposed Drexel trace needs independently captured code artifacts, process lineage, and access results in addition to model conversation text.

For module-based cases, [Sysmon's image-load event](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon) records a module loaded in a process with hashes and signature fields when that high-volume event is configured; Microsoft says it is disabled by default. [Defender XDR's DeviceImageLoadEvents schema](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceimageloadevents-table) likewise describes DLL-load records with process identity and file fields when Defender for Endpoint supplies data. Its `InitiatingProcessUniqueId` can be joined conceptually to the Windows Process Start Key described in the [process-event schema](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table), where that service is deployed and fields are populated. These records could corroborate a conventional DLL's arrival in a particular process. Because the documented event is a DLL/executable image load, it should **not** be presumed to capture every interpreted or memory-only code change. Nor does a load event by itself show that a new version replaced an old one, that the new code executed successfully, or that a model generated it. A missing event is uninterpretable without sensor and collection settings.

For a managed-code mechanism, [Microsoft's CLR method ETW reference](https://learn.microsoft.com/en-us/dotnet/framework/performance/method-etw-events) documents a separate, configuration-dependent signal: verbose `MethodLoad` events include dynamic and generic methods, while the nonverbose method-load event excludes them. This is a .NET runtime-specific way to corroborate method creation or JIT loading if the right provider and level were collected; it is not evidence that a particular model response supplied the method, that a prior method was replaced, or that a remote-control task used it. The sensor plan for an observed Drexel case therefore must follow its actual code format—DLL, managed method, script, or other runtime—rather than treating an image-load table as universal coverage.

For PowerShell-based cases such as PhantomRelay, [Microsoft's PowerShell logging documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_logging_windows) says enabled script-block logging records the content of processed commands, functions, and scripts as event 4104; [Windows policy documentation](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-windowspowershell) says optional invocation logging also records start and stop events, with high event volume. These records can narrow *what script text ran*, where collection was active. They still need process correlation, artifact versioning, model-output provenance, and independent command-result evidence to establish the strict chain. They also should not be assumed present in a published incident without stated sensor settings.

Passive authorship judgment is weaker than a captured model-to-artifact link. In an [ASE 2026 cross-generator study](https://arxiv.org/html/2610.01664v1), Djire tested code-provenance judges against seven generators and three languages and found large shifts by generator and prompt; two dedicated detectors reached about 0.50 accuracy with zero F1 for the human-written class because their decisions collapsed toward one label. The dataset reused 18 human solutions across generator comparisons, so these figures should not be treated as a field attribution rate. The narrower lesson is that “looks AI-written” cannot by itself establish that a particular revision came from a model. [ESET's incident analysis](https://www.welivesecurity.com/en/eset-research/edr-killers-explained-beyond-the-drivers/) independently cautions that it has no definitive forensic marker for AI-authored code, especially after editing or obfuscation.

This suggests a claim-level evidence scale for published cases:

1. **Artifact-level:** model prompt or generated code exists, with no observed application.
2. **Single-change execution:** one model-linked change is shown to run in a target process.
3. **Functional single-change:** the target completes an independent remote-control task after that change.
4. **Two-change continuity:** the *same identified process* accepts two model-linked code changes and completes an independent task after each.
5. **Operational corroboration:** an incident or independently observed deployment confirms that level 4 happened outside a controlled prototype.

This scale is an analytic proposal, not a published standard. Level 4 would establish technical feasibility for the expanded hypothesis; level 5 would establish that someone actually used it in operations. The published cases in the [master matrix](master-feasibility-evidence.md) have not yet supplied level 4 in the sources reviewed. Absence of a published chain must not be restated as impossibility or absence from private telemetry.

One deployed benign comparison usefully tests the meaning of “revision” and “verification.” [Zhang and Li's AllPath paper](https://arxiv.org/html/2610.26662v1) reports 56 automatically applied reflection revisions over about five weeks, but these altered versioned **strategy rules and thesis files**, not executable code. The integrity gates rejected no proposals, and the operator later removed 11 of the 19 autonomously added rules. The authors describe failures that passed their gates and were found by the operator. This is a single-operator paper-account study, not a malware analogue or a measured access-survival rate. It supports the narrower inference that serial, model-proposed changes to a continuing deployed system can be logged, while gate success alone does not establish that the system's intended behavior remains correct.

A closer code-level comparison is [Tan et al.'s BoxBox preprint, version 3](https://arxiv.org/html/2611.09218v3). In 150 four-hour benign software-optimization runs, the authors report a median five harness reviews per run and 620 applied nonempty harness updates across runs. The editable surface includes executable agent tools and logic. Their separate kernel activates a **candidate runtime** and transfers a preserved conversation, terminal session, and workspace after validation; on activation failure it retains or restores the old runtime. This is genuine model-directed revision during an ongoing task, but the paper describes a runtime handoff with state transfer, not proof of a single unchanged process identity. Its end outcome is correctness-preserving optimization of target projects, not independent remote-control checks after each harness edit. The authors call it a research prototype and say validation and rollback do not form a complete security boundary. The source materially strengthens the *general* feasibility of serial, model-directed software revision while leaving the strict Drexel chain unshown.

[Jiang et al.'s Autopoiesis preprint](https://arxiv.org/abs/2604.07144) is a different benign example of external model-to-live-service code flow. A control plane uses an LLM to mutate **two pure scheduling-policy functions**, scores candidates on replayed workload snapshots, and places a selected code version in shared staging; the serving data plane is described as loading it at its next monitoring point, with subsequent calls using the new version while service continues. The paper discusses repeated evolution cycles and reports aggregate serving performance under traces augmented with synthetic workload changes. It does not publish process IDs, a per-swap continuity/event trace, or independent remote-command outcomes after two identified swaps. Its model operates in a separate control plane and its code surface is a narrow stateless policy, not the resident service's full program body. It supports a plausible **bounded-function hot-swap architecture**; the reported throughput gains are not a measure of Drexel's serial access reliability.

[Shah and Kathrotia's November 2026 harness-evolution preprint](https://arxiv.org/html/2611.22299) gives a more controlled comparison of model-authored executable changes. Its outer optimizer proposed one Python harness-module edit at a time; the validation gate accepted three modules and rejected one that improved development tasks but hurt validation results and exceeded a token cap. On 40 held-out software-repair tasks, the gated harness solved 16, while an ungated four-module rewrite solved 17; the gated version used substantially fewer runtime tokens and had no unverified exits for its original task model. These are **frozen evolved harnesses run in fresh single-commit task sandboxes**, with different turn caps and search budgets across methods. They do not show in-process activation, two changes to a resident RAT, or remote access. The result supports explicit acceptance gates and resource accounting, without supplying a Drexel success probability or a simple accuracy ranking between the unequal-budget methods.

[Yan et al.'s DeltaHarness preprint](https://arxiv.org/html/2611.21688) is another bounded comparison, and its several evaluation settings must remain separate. In the Linux plan-search study, a model proposes sandboxed **source-code policies** over fixed video-tool operations; a distinct recursive arm rewrites its own sandboxed `analyze(data)` program every two rounds. Fresh candidate–incumbent executions and an independent confirmation panel govern policy replacement, followed by frozen held-out evaluations. The paper does not record one continuously identified process accepting two active code changes while remote access remains functional. Its one-round Mac result uses a typed-rule policy, not the Linux source-policy interface. In the Linux allocation study the shared initial source failed its execution contract, and the reported successful development executions differed sharply by arm (624/768 Uniform, 336/768 Balanced, 48/768 Selected, 0/768 evolutionary-strategy baseline). These are study-specific workflow results, not probabilities that a Drexel candidate will run or that a serial revision chain will survive.

An industrial [tool-making study by Kujanpää et al.](https://arxiv.org/html/2607.08010) makes the **deployment boundary** clearer. Its model-generated procedural tools are grounded against live backend schemas and repaired on labeled cases, then the selected tool library is deployed to an alarm-triage agent. The production agent calls the versioned tools and falls back to code generation on failures, but the paper places the tool-making loop **before deployment**; it does not report the production process adopting two newly written tools while one session continues. Its 44-node held-out pass measure evaluates generated tools in a benign workflow, not remote-control continuity.

Revision attempts should be decomposed into **requested, changed, applied, and functional** outcomes. [Kim's October 2026 self-debugging study](https://www.mdpi.com/2673-2688/7/10/392) evaluated 9,790 initial Python programs from six open-weight models. Among 4,168 initially failing programs, a basic revision request returned structurally changed code in 57.39% and repaired the program under the same benchmark suite in 16.34%. Additional execution feedback helped, but the benefit of repeated attempts diminished in the tested setting. Each evaluation ran in a fresh isolated process without network access. These numbers cannot be transferred to a resident remote-access program; their value is showing that a model *deciding* to revise, producing changed code, and restoring function are empirically different events.

[Mahmud et al.'s November 2026 Décalage preprint](https://arxiv.org/html/2611.11721) tests four locally served 1.5B–3B code models on C++ generated directly from 166 sections of 11 requirements documents. The authors define a **usable** section only as one that compiles and has a non-stub body for every planned function; that is a weaker criterion than functional correctness or retention of a running service. Initial compile rates by model were 1%–22% of sections. In the three-model repair analysis, two compiler-feedback rounds raised usable sections from 8.4% to 17.5% under the general prompt and 7.6% to 13.9% under a secure-coding prompt, leaving more than 80% unusable by that definition. A secure instruction more often changed stated reasoning than actual checks, illustrating why a model's explanation cannot certify its generated code. These results are from one greedy sample per requirement section, a particular multi-function C++ workflow, and one local laptop setup; they do not estimate the chance that a bounded Python or other payload revision will succeed. Together with the repository's [measured CPU resource study](inference-resource-study-2026-11-11.md), they show that **model size, runtime cost, code completeness, and retained function are separate axes**. This research window adds no model runs.

[Hu et al.'s MalTool preprint, version 3](https://arxiv.org/html/2602.12194v3) illustrates a different denominator risk. It constructed 1,300 accepted standalone malicious *agent tools* across 13 behavior classes using generation, verification, and retry; its reported generation success rate of 1.000 is defined over **accepted tools** checked again by its evaluation, not first proposals or an uninterrupted live program. The paper reports variable generation-verification iterations by model and behavior. Its separate detection experiment scans source/tool artifacts, including a VirusTotal rule that treats any one scanner flag as detection; these results are not endpoint-alert probabilities for a running self-revising program. A March 2026 [author blog](https://rdi.berkeley.edu/blog/maltool/) still gives 1,200 standalone tools and 5,287 embedded tools, whereas version 3 gives 1,300 and 5,727. The versioned paper controls the current denominator. This is a component demonstration of model-assisted code synthesis with selection, not evidence for the Drexel chain.

[Zhang et al.'s controlled self-improvement study](https://arxiv.org/html/2610.01073v1) adds a second measurement distinction: a program can pass an old suite and fail under a changed environment. In one experiment, historical scores kept the same unsafe program selected in 22 of 48 framework histories even though each affected archive contained a correct alternative. Its tasks concern stateful authorization components, not malware or a continuous network service. The finding supports checking the **currently deployed** version against the **current** behavioral contract after each accepted change, rather than treating an earlier certificate or a repaired candidate elsewhere in the archive as proof of current function.

[Chen et al.'s preregistered API-migration study, version 2](https://arxiv.org/html/2611.08269v2) tests whether passing a release gate means a revised program is correct. Across its finite, documented repair space, a gate using typical inputs released 0.410 of wrong programs; adding one input aimed at a documented edge condition reduced that fraction to 0.065. The paper includes 73 tasks covering 60 changes in CPython, Node.js, and SQLite, and a separately described free-form addendum in which model-written programs ran in fresh isolated containers. Its main-stage model repairs chose among predefined fragments, so 0.410 is **not** a success or failure probability for unrestricted model-written code. The relevant methodological lesson is narrow: a heartbeat or routine command that still works after a revision can miss a broken edge of the intended access function. A Drexel claim would need checks whose inputs cover the behavior that the revision may have disturbed, plus the model/version/process evidence above.

[Liu, Raff, and Micinski's decompilation study](https://arxiv.org/html/2609.05370) independently shows the limit of passing a narrow test set after code reconstruction. Among 12,133 decompiler candidates that passed their shipped tests and could also be scored by the authors' differential input corpus, 4.9% diverged from the original function; the authors report that 77% of those divergences changed output without a crash. These are reconstructed C functions across decompiler systems, not adaptive malware or two live revisions, so the percentage is not a Drexel failure estimate. The source supports one specific verification rule: compilation and familiar test inputs should be separated from behavioral agreement on fresh inputs and retained application state.

[Pan et al.'s SWE-Maintain preprint](https://arxiv.org/html/2610.14768) isolates a different cost of repeated changes. Its 100 three-event episodes come from 50 Python repositories. Across five coding systems, two backbone models, and 1,996 paired later events, agents resolving the same next task from their own earlier edits scored 5.6 percentage points lower on average than from the developer's earlier patches. Requiring all prior tests to remain passing widened the gap to 14.0 points; two-thirds of agent-history starts already failed earlier tests. Conditional on a clean inherited test state and a genuinely unsolved next task, the measured disadvantage disappeared within the reported confidence interval. This is repository maintenance, not live malware, and its percentages cannot be assigned to Drexel. It does show why a serial feasibility study must carry the *accepted code history* forward and count inherited failures, rather than resetting to a clean reference before every proposed revision.

[Zeng, Liu, and Lin's Multi-step SWE preprint](https://arxiv.org/html/2611.07166) makes the unit-of-analysis distinction especially clear. Its 69 benign software-engineering tasks contain 5–15 dependent, multi-hour steps on a cumulative codebase; each step is checked in a separate verifier container, generally including inherited behavior. Across nine evaluated frontier models and four rollouts per task, the strongest model passed 56.8% of individual steps but attained an 18.5% whole-task solve rate; 38 of 69 tasks were never solved by any tested model. The paper also reports that 52% of failed steps were nevertheless declared complete by the agent without naming a failure. These are demanding repository, migration, and optimization tasks, not two live implant changes or independent access checks; the rates cannot be imported into Drexel. The transferable lesson is that a candidate's local pass and an agent's completion claim do not substitute for an **externally checked cumulative chain**.

[Ning et al.'s ControlScope preprint](https://arxiv.org/html/2609.34313) isolates a related *review-timing* failure. Its model can keep a generated workflow, edit the next tool call's data arguments, or replace the unfinished executable workflow. In two failed file-organization runs, replaying each actually proposed replacement without later interventions let 49/71 and 46/62 candidate continuations reach the task goal; these are correlated candidates from **two runs of one task**, not independent success probabilities. A fresh confirmation example failed after 35 replacements within a 100-call budget, whereas retaining its first replacement and allowing ordinary planning succeeded in 77 calls. The paper's programs execute in isolated workers/workspaces, and its endpoint is benign task completion, not process or remote-access continuity. The transferable inference is narrow: a later model revision can interrupt a viable earlier one, so a Drexel evaluation must log *which accepted version actually ran long enough to satisfy a fresh check*, not just whether a candidate would have worked if frozen.

If a revising agent consults asynchronously updated source indexes, it can also reason from a code state that never existed. [Shi's revision-consistent context preprint](https://arxiv.org/html/2611.21616) reports two unsafe mixed/invalid responses among 150 update trials for a live-source composite query, versus none under its complete-revision publication method in the same five edit scenarios. These are repository-context service measurements, not resident-program update outcomes. The narrow implication is that any model-to-revision audit should identify the exact source snapshot shown to the model; a retrieved function body and caller graph from different revisions would weaken the causal interpretation of its next change.

[Cim, Topcu, and Kandemir's November 2026 preprint](https://arxiv.org/html/2611.14960) retrospectively tested each distinct patch from coding-agent runs. Across its tested settings, 1–8% of runs that reached a benchmark-correct patch later ended with an incorrect patch after further work; some other runs broke and then restored correctness. This is a repository-task outcome measured with hidden benchmark tests, not an implant update rate. It highlights a specific serial-revision failure mode: observing a working intermediate version does not guarantee that later autonomous edits preserve it. The authors' tests evaluated patches offline, not within a continuing service process.

[Wang and Qi's October 2026 self-improvement study](https://arxiv.org/html/2610.27465) separates verifier strength from recoverability. In their platform case study, one LLM approval gate gave a constant score in 9 of 37 tested configurations without signaling an error. In a separate simulated airline-task experiment, restoring a saved prompt version returned measured behavior to the null-change floor, while three generated undos did not; three admitted prompt changes altered outcomes on 17% of 50 probe tasks beyond normal variation while deployed. The authors did **not** test tool-code or model-weight changes under that experiment, and their weaker-verifier regret trend was statistically inconclusive with 20 held-out tasks. These results cannot quantify Drexel reliability. They support two distinct checks for any proposed serial revision: verify the **admission test** against a trusted reference, and establish **rollback fidelity** separately from the ability to keep the process alive. Reverting a bad version also cannot undo commands or effects already produced while it was active.

[García-Carrasco et al.'s closed-loop embedded-agent study](https://arxiv.org/html/2610.11447v1) provides a bounded check on the assumption that a compact local model can autonomously implement and verify complex behavioral changes. It used five simulated ESP32 control tasks, four feedback conditions, seven model configurations, and three repetitions, for 420 runs. Under its realistic self-verification condition, the local Qwen3.5-27B passed 9/15 runs, the 9B and 4B variants each passed 2/15, and the 2B variant passed none. All local models ran as four-bit GGUFs on the same RTX 4090; these results cannot be translated to CPU-only performance, remote-access function, or the chance of two successful live revisions. They do show why code emission, self-verification, and feedback quality should be treated as separate feasibility gates.

[A controlled two-revision harness study](two-revision-harness-study-audit-2026-11-26.md) followed 27 independently built benign agent lineages through two model-authored Python code revisions each, with all three frozen snapshots scored on five feedback games and twenty withheld games. All 54 transitions changed source, yet mean development improvement (+8.42 points) exceeded held-out improvement (+2.80; 95% interval −1.44 to +7.35), and 12 lineages lost held-out score by strict sign after the second revision. Every candidate had to execute and interact in a limited smoke qualification, not pass a full preservation check. The study's post hoc choice among snapshots retained the initial version in nine lineages, emphasizing that making a revision and deciding to activate it are separate capabilities. Each snapshot was run as a separate task harness; no continuously identified process or remote-control workload was tested. Its score changes therefore cannot estimate Drexel's two-revision survival probability.

[He’s feedback-directed revision audit](feedback-directed-revision-audit-2026-11-26.md) adds a different separation. Among 145 eligible modifications in public Darwin Gödel Machine logs, the paper detects no target-specific repair advantage; its controlled instruction-edit experiment instead finds a 20.0-point target-repair advantage from relevant feedback for one 4B model, without reliable held-out improvement. These are different units and settings. A future benign serial study should report the triggering failure, other failures, and regressions of previously working behavior for *each* candidate and accepted version, rather than treating a model retry or an acceptance gate as proof of directed repair.

The [Autopoiesis source audit](autopoiesis-live-policy-audit-2026-11-26.md) separates its live code-swap claim from **rescheduling events**, which are changes to a serving plan rather than counts of policy-code revisions. The evaluation uses 32–64-GPU clusters and GLM-4.7-Flash for synthesis; it supplies no small-endpoint resource estimate.

## Detection is a separate empirical question

[Kanso et al.'s COGENT conference abstract and Kanso's related thesis abstract](cogent-endpoint-claim-audit-2026-11-26.md) are unusually close endpoint claims: model-guided code variants over mutation cycles in the former, and 45 reported bidirectional C2 workflows across 15 products in the latter. The conference methods were not accessible in this review, and the university repository marks the thesis PDF restricted. The public abstracts give neither same-process active-version lineage nor remote-control results after each of two revisions; the thesis matrix cannot be assumed to be the conference mutation experiment. Its no-relevant-alert claim is scoped to the tested matrix, while a separate ARGUS run in the thesis abstract generated an alert.

[Prinos and Brush's commercial EDR evaluation](commercial-edr-observability-audit-2026-11-26.md) shows why a future endpoint measurement needs independent application-side outcomes and a specified telemetry surface. Their lab's named block events could be delayed or absent from one query stream despite attacker-side confirmed prevention; vendor outcome units differed, and Defender's autonomous containment varied even after reset. Their action-level “silent bypass” definitions do not estimate whether one Drexel process would stay functional and unnoticed through two code versions.

[Sugio and Ito's IEEE Access study](generated-artifact-detection-audit-2026-11-26.md) supplies a bounded detection counterexample: all six reported model/obfuscation *conditions* for packaged, functionally checked Windows executables were flagged by Hybrid Analysis in static and dynamic modes. The paper does not disclose a clear per-condition repetition count in its table, and its offline wiper/keylogger artifacts lack a remote-control loop and live revisions. Thus the result rebuts automatic-invisibility claims but cannot estimate Drexel's on-host alert probability or be numerically compared with COGENT's distinct abstract-level endpoint matrix.

The [24 November Unit 42 campaign review](https://unit42.paloaltonetworks.com/autonomous-ai-agent-threat-campaigns/) merits a particularly narrow reading. Across more than ten July–September campaigns, investigators recovered hundreds of distinct scripts but explicitly no compiled backdoor, custom C2 framework, DLL implant, or shellcode loader. One case placed five web-shell variants in more than 40 locations on a Windows server within 26 minutes; this is *multiple placements and variants*, not five accepted updates of one running web shell. Figure 9's caption says different scripts ran "under the same process," but its accompanying text and image describe a **process chain** involving separate Python, PHP, and Bash processes. Neither establishes one process revising its own code. The report also gives one pair of median inter-command gaps, 23.9 seconds in a manually operated phase and 1.4 seconds in a later agentic phase; these are campaign observations, not latency or success measurements for a resident implant.

The live-update mechanism does not by itself imply invisibility or immediate detection. [Microsoft's behavior-monitoring documentation](https://learn.microsoft.com/en-us/defender-endpoint/behavior-monitor) says Defender observes process, file, and service activity and can flag suspicious behavior without a known hash. [Sysmon's event catalog](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon) shows that some useful network telemetry is optional and disabled by default. Thus a claim about an alert needs a named product, policy and sensor configuration, a defined event window, and the actual alert/result record. The recent [Unit 42 campaign review](https://unit42.paloaltonetworks.com/autonomous-ai-agent-threat-campaigns/) and [GTIG report](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold) describe rapid script creation and forensic traces in live operations, but neither publishes a controlled detection probability for the precise Drexel chain.

[MITRE ATT&CK's detection strategy for polymorphic code](https://attack.mitre.org/detectionstrategies/DET0324/) lists correlates such as process creation, module loads, process access, file modification, and changed hashes or memory sections across executions. This is a **catalog of possible analytic signals**, not an evaluated detector or an alert rate. It reinforces why source-code variation alone cannot establish evasion: the update procedure and access behavior may still leave observable events, with visibility dependent on the actual sensor configuration.

The [UK NCSC's 24 November 2026 incident guidance](https://www.ncsc.gov.uk/sites/default/files/2026-11/Familiar-weaknesses-exploited-faster-defending-against-agentic-cyber-attacks.pdf) reports a rise in agentic offensive-framework incidents since September and emphasizes faster exploitation of familiar weaknesses, bursty traffic, varied requests, and error-driven retries. This is an authoritative operational assessment of **external agent activity** and its observable patterns. It does not describe a self-revising resident implant or give an endpoint detection rate. Its relevance is to distinguish the noisy, currently observed agent workflow from an assumed stealth property of the hypothetical Drexel design.

[Microsoft Security Research's analysis of a trojanized editor extension](https://www.microsoft.com/en-us/security/blog/2026/10/30/inside-malicious-claude-code-branded-cursor-extension-persistent-ssh-backdoor/) gives a concrete access-oracle counterexample. Its code attempted key installation, persistence, and a reverse SSH tunnel, but Microsoft says code order and artifacts do not prove every step succeeded, and an SSH process alone does not prove attacker access. Cursor reported configuration and privilege failures blocking SSH access on most macOS and Windows hosts. This was an AI-*branded* supply-chain lure, not a model-authored implant; its value here is the separation of attempted access, process presence, and independently verified remote use.

[Microsoft Threat Intelligence's 25 November ARTEX analysis](https://www.microsoft.com/en-us/security/blog/2026/11/25/what-defenders-need-to-know-artex-agentic-ai-framework-threat-actors-abuse/) describes an external Go-based multi-agent controller and observes short-lived web shells with incrementing names and different commands as agents correct errors. That is field evidence for rapid **external** iteration and observable tool activity, not two replacements of one resident web shell or RAT. The report's option to switch model providers is a controller availability feature, not a payload-code change. Its hunting patterns are advice tied to product telemetry, not an empirical detection rate for the strict claim.

[NVISO's ZQAgent incident-response account](zqagent-artex-case-audit-2026-11-26.md) brings the external controller and a persistent backdoor into the *same reported intrusion*. It reports ARTEX deployment of a Linux backdoor, but no model-authored code revision. Its in-memory relocation restarts a detached process; its configuration update operations and reboot persistence do not establish a continuing process with two active code versions. NVISO's first-party foothold claim is also not a published after-each-version command/result trace.

[JFrog's separate ARTEX-associated malicious-model case](jfrog-artex-model-artifact-audit-2026-11-26.md) reconstructs rapid *external repository* variants and a successful collection self-test on the operator's own container. Its evidence for an ARTEX task is stronger than style-based AI-authorship inference, but it lacks exact model-response-to-edit linkage and any continuously running victim payload. The final published configuration fails in stock `transformers`; source publication is not proof of successful active behavior. This is a different incident and cannot be merged with NVISO's ZQAgent process or access observations.

## Model placement changes the feasibility constraints

Inference placement is a distinct variable in Project Drexel, and no one placement follows from a model-driven label. Four arrangements have different evidence and engineering burdens:

| Placement | Primary-source anchor | Feasibility implication and evidence limit |
| --- | --- | --- |
| Hosted model called by a program on the host | [GTIG's PROMPTFLUX analysis](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools) describes a sample that requests rewritten script code from Gemini. | The analyzed self-update path was disabled. The network request demonstrates a model dependency, but not an applied functional revision chain. Credentials, availability, latency, and service policy would affect such an arrangement; those costs are not measured by this case. |
| Model in an external controller or attacker infrastructure | [Unit 42's Cairn case](https://unit42.paloaltonetworks.com/cairn-framework-ai-autonomous-attacks/) and [GTIG's `exploit_agent` report](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold) describe external orchestration with model access, including local model options at the staging server. | The endpoint need not carry the model. This lowers the endpoint model-storage burden by inference, but requires a control channel and does not turn controller-side script repair into same-process resident-code repair. |
| Model in the endpoint environment | [Mandiant's September 2026 case study](https://cloud.google.com/security/resources/ai-risk-and-resilience-2026) asserts local inference and runtime command-string changes; its public account omits the sample and version trace. The repository's [resource assessment](feasibility-constraints-and-study-plan.md) reviews measured benign local-inference costs. | Locality removes dependence on a remote inference call during each decision, but adds model storage, memory, computation, and application-integration demands. The Mandiant assertion is narrower than revised executable payload code and cannot support a repeat-success rate. The paused local-model four-gate study remains incomplete; this research window runs no models. |
| Host-managed local model in the endpoint environment | [Fleshman and Lucas's November 2026 preprint](https://arxiv.org/html/2611.25086) uses Chrome's local Gemini Nano for classification and tool selection; [Chrome](https://developer.chrome.com/docs/ai/get-started), [Microsoft](https://learn.microsoft.com/en-us/windows/ai/apis/), and [Apple](https://developer.apple.com/documentation/foundationmodels.md) document model APIs supplied through a supported browser or OS. | Access can avoid packaging separate model weights with an app and avoid an inference-time external call. Availability is conditional: Chrome requires eligible hardware, storage, and an initial download; Microsoft's Phi Silica is preinstalled on supported Copilot+ NPU devices but downloaded on demand for other supported devices; Apple's on-device Foundation Models require Apple Intelligence support. None of these sources tests code revision or remote-access preservation. |

The key feasibility conclusion does not depend on choosing one placement. A controller can direct revisions while a small host component executes them, or a local model can propose them on the host. In either case, the claim still requires an applied-code record, stable instance identity, and after-each function checks. Model location alone cannot supply any of those observations.

[Anthropic Frontier Red Team's contained replication study](https://www.anthropic.com/research/self-replicating-ai?full=1) makes the placement tradeoff more concrete without testing Drexel's revision claim. It ran Gemma4-26B-A4B through **15 networked Android TV boxes**, at 0.39 generated tokens per second; this is distributed inference, not a capable model running on one inexpensive endpoint. Qwen3.5-9B set up an inference server on 8 of 9 hardware types in a separate setup task. In a firewalled eight-node Android-emulator fleet with an **unauthenticated ADB port**, GLM-5.2 reached all eight nodes in four of five trials and seven in the fifth, but the agent model ran on a **separate inference server** and the harness seeded the next GLM-5.2 instance after checking that an 8B model was served. Anthropic explicitly treats a small model with GLM-5.2's ability as a future conditional, not an observed end-to-end result. The study thus separates model fit, task competence, and completed chain reliability. Its 20 six-generation Qwen lineages passed notes to *new* instances and improved inference-setup success from 45% initially to 61–84% in later generations; they do not show one resident process revising its executable code. Its extrapolated spread times and year-end capability forecast are projections, not Drexel measurements. None of these results measures a same-process code revision or a retained remote-control channel.

[Lin et al.'s November 2026 harness-evolution preprint](https://arxiv.org/html/2605.30621v2) adds a narrower model-capability distinction. Across seven models and three benign agent benchmarks, it varied the model that **writes persistent harness updates** separately from the model that later **uses** those updates. Even a 9B evolver could produce useful prompt, skill, or memory changes in its tasks, but weaker task agents frequently failed to load a relevant skill into context or follow it across a long task. The paper's “skill-load rate” is *context retrieval*, not executable-code activation; its cross-model gains are not evidence that a small endpoint model can write reliable payload code or retain control after two code changes. It does show why an update's existence, activation, and downstream benefit require separate observations when assessing any model placement.

[Pianese et al.'s PowerShell generation experiment](powershell-model-proxy-audit-2026-11-26.md) adds a task-specific model-quality proxy, but not an endpoint-local deployment measurement. Its strongest native model matched a reference's selected Sigma-rule set exactly in 48.4% of the 212 reference-triggering cases; the corresponding 4-bit AWQ figure was 35.9%. Inference used four A100 GPUs, and generated scripts were run in separate restored Windows VMs with endpoint defenses disabled. A rule-set match does not establish a functioning controller, any accepted live code version, or an alert outcome.

[Shirudo's first-party Java4Shell demonstration](shirudo-live-shield-audit-2026-11-26.md) is a bounded live-code precedent: an externally operated Codex agent reportedly produced a bytecode guard attached to running Elasticsearch, and application logs show guard installation and rejection of one malformed input. The vendor says service continued. Yet its ordinary documented Java-agent delivery path configures **future JVM starts**, not live JVM adoption, and the reviewed text does not explain the demo's separate attachment path. The published example applies one defensive change, without process-ID/version lineage or remote-control checks, so it supports only a constrained component mechanism.

[Bitdefender's SilkParasite technical report](silkparasite-plugin-result-audit-2026-11-26.md) sharpens the applied-code gate with a field example: one RAT's `load|success` is emitted before a fetched plugin is mapped or initialized, while another reports load success after initialization but before a task result. A remote status string therefore needs its exact implementation semantics. The same investigation documents in-memory .NET plugins and returned results in DriveSilkRAT, but its AI-development attribution is indirect and it does not bind two active model-caused revisions to one process and two subsequent remote-control results.

[Microsoft's 2026 Digital Defense Report, pages 15–16](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/msc/documents/presentations/CSR/2026-Microsoft-Digital-Defense-Report.pdf#page=15) independently groups observed AI-using malware by remote hosting, execution on a compromised device, and attacker infrastructure. Its named examples correctly separate LAMEHUG's generated **commands** from experimental PromptLock's generated **Lua scripts**. The report does not provide a case-level trace for each placement or any serial in-process code adoption. Its page 16 “self-improving AI worms” discussion is a **future risk projection** built on a contained adaptive-worm report, not a documented field observation that infected instances rewrote their own resident payloads. The broad placement claim therefore strengthens the relevance of the alternatives above without closing the Drexel evidence gap.

Platform-managed model availability is also different from unrestricted output or dependable access. [Microsoft's Windows AI API documentation](https://learn.microsoft.com/en-us/windows/ai/apis/) says callers should check readiness and some API surfaces require particular SDK or OS channels. Its [content-moderation guidance](https://learn.microsoft.com/en-us/windows/ai/apis/content-moderation) describes filtering of potentially harmful prompts and responses. [Apple's Foundation Models documentation](https://developer.apple.com/documentation/foundationmodels.md) limits its on-device API to eligible devices, and its [acceptable-use requirements](https://developer.apple.com/support/terms/acceptable-use-requirements-for-the-foundation-models-framework) prohibit use to seek unauthorized access. These are policy and availability constraints, not measured refusal or code-quality rates for the Drexel task. The presence of a shared model on a host is therefore only a *placement option*, not evidence that a resident program could obtain and apply two payload revisions from it.

[Check Point Research's February 2026 “AI in the Middle” proof of concept](https://research.checkpoint.com/2026/ai-in-the-middle-turning-web-based-ai-services-into-c2-proxies-the-future-of-ai-driven-attacks/) demonstrates yet another role: a web AI assistant relayed content from an attacker-controlled page to a small native demonstration program, which performed a simple received action. The command originated on the page and was returned through the assistant's browsing/summarization response. The report presents model-directed targeting and generated follow-on code as **possible future extensions**, not as results of that proof of concept. It therefore supports feasibility of one AI-service-mediated transport path under the tested conditions, but not model authorship of executable revisions or serial access survival. Its claims about the broader future of AI-driven malware should be attributed as forecasts rather than counted as observed deployments.

An observed model-related download is still weaker than observed local inference. [Cyble's SURXRAT sample analysis](https://cyble.com/blog/surxrat-downloads-large-llm-module-from-hugging-face/) reports a persistent Android RAT that conditionally initiates a download of an LLM-related file exceeding 23 GB. It does not show the model being loaded, invoked, producing code, or modifying the RAT. Cyble presents possible future AI uses as hypotheses. Its observed download belongs in a resource and model-placement boundary case, not in a count of AI-directed payload revisions.

For contrast, [Zimperium's November 2026 ArcticRAT investigation](https://zimperium.com/blog/arcticrat-ai-powered-android-rat) reports a sample that actually queried a hosted model during dynamic analysis and stored the model's structured responses. The model's role was classifying harvested app and message data for the operator; remote device control was handled by separate, preexisting RAT functions. The investigators also collected distinct builds of the family, but provide no trace tying the model response to a code change or one running instance to successive builds. ArcticRAT is evidence for **runtime hosted inference inside a RAT**, not for model-authored self-revision. Its published product-detection claims likewise do not measure alerts for the Drexel chain.

[Kaspersky's Q3 2026 mobile report](https://securelist.com/malware-report-q3-2026-mobile-statistics/121844/) gives a brief first-party account of two other on-device roles: one malicious app used DistilBERT to interpret natural-language C2 commands, and a separate Trojan used an on-device image-classification model with a capability to update that model. The report does not publish sample hashes, model invocation traces, actual model-update events, code-version changes, or a remote-access continuity sequence for either case. Its “could update” feature concerns the **model artifact**, not a demonstrated revision of the resident executable payload. It supports treating local inference and model-update capability as real but distinct from Drexel's code-revision question; it gives no resource measurement for either app.

The browser-model study provides a useful capacity boundary rather than a Drexel success estimate. Its Chrome experiment ran on one laptop; the authors report roughly 3 GB of weights paged into an 8 GB GPU and about 1.4 seconds per prompt in the headed Windows setting, versus about 3.7 seconds when their tested headless/virtualized settings fell back to CPU. A 9,216-token session window constrained their task design. An explicit plan completed their one simulated multistep scenario in 41/50 trials, while an open-ended goal completed 60% of trials; neither condition asked the model to write or revise code. The paper reports one more capable script being flagged by Defender and a smaller scenario-specific script passing its check, but does not provide an endpoint-product sweep or a general detection probability. Chrome's own documentation currently specifies at least 22 GB free profile-volume storage and either more than 4 GB GPU memory or a CPU with at least 16 GB RAM and four cores. These prerequisites limit where an opportunistic local-model arrangement exists; the study's per-prompt times cannot be transferred to a two-revision code task.

## Generated tasks versus resident revision: AttackGPT

A static audit of [Netskope's published AttackGPT source](attackgpt-source-audit-2026-11-26.md) narrows the earlier [speaker abstract](https://bsides.tokyo/en/2026/n04/). The model and repair engine are controller-side. Generated scripts are sent as individual tasks to an endpoint stub; the engine's retry loop reacts to local validation failures before delivery, while the server aborts on a failed required endpoint task. The endpoint can keep polling across tasks, but this is not evidence that its resident polling/dispatch code was replaced, let alone twice, or that control was independently checked after each replacement. The repository contains no measured run trace. It therefore illustrates how one continuing access channel can execute changing model-authored work without meeting the stricter active-code revision claim.

## Newly screened remote-access case: Neural Override

[Unit 42's original Neural Override analysis](https://github.com/PaloAltoNetworks/Unit42-timely-threat-intel/blob/main/2026-09-15-Neural-Override-AI-Orchestrated-RAT.txt) describes five recovered builds of a Python RAT family. Its model integration appears in the second build and proposes **attack actions** through an autopilot loop. Later separately recovered builds add many functions; a fifth returns to an earlier capability set. Unit 42 says the rapid build evolution and code style *strongly suggest* AI-assisted code generation. That is an inference about the development process, not a captured model transcript proving authorship. The investigators found an active bot and model API key, but the note gives no victim-side operation trace, after-update access test, or evidence of one process adopting any of the new builds. A referenced industrial-control module was not recovered.

This case matters because it combines remote-access capability, a runtime model role, and rapid code evolution **within one family**. Those observations must not be spliced into one same-instance revision chain. [Trellix's November threat report](https://www.trellix.com/advanced-research-center/threat-reports/november-2026/) refers to Neural Override when describing autonomy observed in practice; for the mechanism and evidentiary boundary of this named sample, Unit 42's direct artifact analysis controls. Neither source documents model-caused code revision inside a running Neural Override instance. The case therefore raises confidence in the feasibility of combined *components*, while leaving the stricter outcome unverified.

## Newly screened field replacement: Operation Snowball

[Malbear Labs' 8 November 2026 report](https://malbearlabs.com/posts/operation-snowball-inside-an-autonomous-ai-intrusion-campaign) says investigators found an exposed attacker workspace with model-agent transcripts, tools, and incident records. In one reported sequence, endpoint controls blocked a tunnel tool, after which an agent-directed worker wrote a **different** tunnel and the report says tunnel operation resumed in the same session. A separate remote-control framework was also present. This is meaningful first-party evidence of model-directed *replacement tooling* during an operation, with a described functional outcome. It is not two accepted code changes to one resident program, and the original blocked tool did not survive a revision. The report describes its evidence without publishing the underlying workspace or independently confirmed victim account; it also says “over 70” transcripts in one section but “all 18” recovered transcripts in another without explaining the difference. Treat the reconstruction as a single-source account and its exact scope as uncertain. No implementation details are needed to make the feasibility distinction.

## Paired attacker and defender evidence: Wiz October intrusion

[Wiz Research's 23 November 2026 report](https://www.wiz.io/blog/agentic-attacks-artex-offensive-ai-frameworks) offers an unusually useful evidence-design example: investigators paired their own telemetry with more than 3,000 files from one exposed attacker directory. For the anonymized four-day October intrusion, the report attributes the command layer to CyberStrikeAI and records a working reverse shell, a node-level rootkit with a DNS-tunnel channel, and beacons placed on 19 hosts. The publicly described attacker files improve visibility into the external operator workflow, while defender telemetry establishes material access. However, Wiz does not publish a model response tied to a rootkit or beacon code version, a resident activation trace, or independent access results after two revisions. The earlier ARTEX-Harvester campaign in the same article is a *separate case* and cannot supply missing links. The inference is limited to a general method lesson: even dual-vantage incident access cannot prove Drexel's joined chain without version-level provenance and process continuity.

## Observed modular RAT architectures: PipeMagic and KUKURAT

[Microsoft Threat Intelligence's PipeMagic analysis](https://www.microsoft.com/en-us/security/blog/2025/08/18/dissecting-pipemagic-inside-the-architecture-of-a-modular-backdoor-framework/) is an especially clear **non-AI staged-versus-active** precedent. Its recovered backdoor keeps raw payload modules and successfully loaded executable modules in separate in-memory lists, and receives C2 commands to replace a payload-list module or load a selected payload into the executing list. Its network function runs as a separate module. Microsoft's phrase “self-updates” describes that modular architecture; a command replacing staged bytes alone is weaker than proof that a new version became active. The report describes field use of PipeMagic and analyzes these capabilities, but does not publish two time-ordered replacements of one activated module in an identified process, remote-command results after each, or model authorship. The dropper's disguise as a ChatGPT desktop project is **branding**, not evidence of a runtime model call.

[Kaspersky and BI.ZONE's separate original PipeMagic analysis](https://securelist.com/pipemagic/117270/) reports three recovered 2025 plugins with different functions and describes a loader that injects and executes additional payloads. Its comparison of 2022, 2024, and 2025 samples concerns family evolution across incidents. Neither the three-plugin inventory nor the cross-year samples establish two successive revisions of one active module in one process. The fake ChatGPT client in that account is likewise a delivery disguise, not a model dependency.

[Binary Defense's October 2026 Platypus-fork investigation](https://binarydefense.com/resources/blog/platypwned-when-a-citrix-0-day-lays-an-egg) recovered a FreeBSD agent from a NetScaler intrusion, a Windows agent served by the same controller, and an installer. The analysts identified an upstream WebAssembly plugin runtime and signed self-update capability in the fork. The two agent binaries carry the **same source commit, version string, and build timestamp**; their platform difference is not a revision sequence. Investigators found an installer command in appliance logs, but reported no post-install indicators on one affected device and considered registration there likely to have failed. In their own lab, the agent ran and repeatedly attempted enrollment, but the analysts supplied no live controller, so plugin, remote-terminal, and update behavior was **not exercised**. The case supports a real RAT's available Wasm/update surface, not an observed active plugin replacement, model-authored code, or remote access surviving two revisions. The separate Wasmtime API analysis above describes one possible host design; it is not a claim about Platypus's precise runtime implementation.

[Bitdefender's original 2018 RadRAT white paper](https://www.bitdefender.com/content/dam/bitdefender/business/whitepapers/pdf/Bitdefender-Whitepaper-RADrat-crea2645-A4-en-EN-interactive.pdf), pp. 11–12, is a particularly clear **disk-versus-active** update case. The analyzed RAT can fetch newer component DLLs. Two commands replace the current service DLL **on disk without restarting it**; a distinct command uses a helper to stop the DLL's threads and reload the library, or to stop and restart its service. The paper also describes a registry field intended to log update operations, but does not publish that field as a victim-side sequence of two active revisions. An in-place disk write is therefore not proof that a running process adopted new code. Reloading a DLL after its threads stop may retain a host process in one mode, but the report gives no process-identity or after-reload access trace to establish that outcome, and the service-restart mode is not same-process continuity. No model role is reported.

[Unit 42's 16 November 2026 KUKURAT investigation](https://unit42.paloaltonetworks.com/custom-rats-target-southeast-asia-governments/) closes part of the gap between general dynamic-update theory and a real remote-access program. Investigators identified two C++ variants deployed in compromised networks. Their analyzed core loads capability DLLs from its control server at runtime, can load a module beyond its named handlers, and has explicit module-unload commands. The published heartbeat format includes loaded-module and active-call state. This supports the **architectural feasibility** of changing a resident RAT's available executable capabilities while its core is running. The report also describes a separate watchdog that relaunches a terminated core; such recovery would preserve a service path but not the same process identity.

An independent [.NET XWorm 7.2 analysis by FortiGuard Labs](https://www.fortinet.com/blog/threat-research/deep-dive-into-new-xworm-campaign-utilizing-multiple-themed-phishing-emails) documents a captured campaign sample with commands to accept, cache, and load executable plugins, and illustrates multiple plugin artifacts in the analysts' examination. The report says its captured phishing messages were blocked before delivery, so its debugger observations should not be described as a victim-side plugin-update timeline. It separately labels a client `update` command as starting a **new RAT**. The plugin path supports runtime *capability addition* in a resident core; the client update is replacement/relaunch rather than proof of the same process changing its main body. The report does not show two model-authored plugin revisions, stable process identity across them, or independent command success after each. Its plugin count is not a revision-chain count; no AI role is reported.

[Check Point Research's GearDoor analysis](https://research.checkpoint.com/2026/silver-dragon-targets-organizations-in-southeast-asia-and-europe/) makes the same distinction within one deployed .NET backdoor. An identified self-update package is version-compared, replaces the binary, and **restarts** the malware process when versions differ. A separate plugin path loads an assembly into memory for execution. Those are two different mechanisms: the former changes the core across processes, and the latter adds executable functionality to a resident process. The article does not trace two successive versions of a plugin in one process, attribute the code to a model, or check remote-control behavior after each such activation. Its changing help output suggests author-side evolution, not a documented live revision sequence.

The KUKURAT report does **not** publish a time-ordered trace showing two successive versions of one module applied to the same process, model-generated module code, or independent access checks after each module change. Its six PerfectPioneer builds and two KUKURAT variants are developer-side family evolution, not evidence of in-process revision. A Cortex XDR alert shown for log-on-script persistence establishes one observed alert in the campaign, not a detection rate for module updates. KUKURAT therefore demonstrates a closer *non-AI* resident-code-update surface while leaving the causal and serial-success links in the Drexel hypothesis open.

Earlier, [Kaspersky's 2022 Emotet investigation](https://securelist.com/emotet-modules-and-recent-attacks/106290/) observed a control server return a process-list DLL after registration. The researchers report that the retrieved modules they examined were launched in the parent process, each on a separate thread, and that the process-list module returned results to the server. That is direct evidence of **delivered executable modules operating within an existing malware process** with a response path. It does not establish that an existing module was *revised* twice, that a model authored any module, or that one remote-access channel survived each revision. Even this stronger historical observation remains a component precedent rather than a Drexel chain.

[Boyarchuk et al.'s peer-reviewed Emotet longitudinal study](https://sites.cs.ucsb.edu/~vigna/publications/2023_DigitalThreats_Emotet.pdf), section 5, adds a different type of evidence: the researchers used a **modified Emotet sample** to connect to C2 endpoints and collect distributed core and plugin updates across a six-month window. They identified bots by host identifiers and grouped near-identical builds with a “conceptual hash” that omits a varying `.rdata` field; separate file hashes therefore do not necessarily mean separate behavioral versions. Their reported spam-module and other plugin distributions across botnet epochs show changing **delivered artifacts**, not two accepted revisions activated inside one actual victim process with remote access checked after each. This strengthens an evidence rule for Drexel: even a dated C2 update table needs application and process records before it becomes a live-revision timeline.

[Check Point's VoidLink technical analysis](https://research.checkpoint.com/2026/voidlink-the-cloud-native-malware-framework/) describes an in-memory plugin architecture and uses the term “self-modifying code” for protected code regions that decrypt while used and re-encrypt afterward. That latter operation changes the **representation of existing code**, not its behavior or version. The later [AI-development investigation](https://research.checkpoint.com/2026/voidlink-early-ai-generated-malware-framework/) found author-side development artifacts, while [Cisco Talos's separate field report](https://blog.talosintelligence.com/voidlink/) links an earlier variant to intrusions. These sources should not be combined into a claim that the deployed process asked a model for new code. The reviewed reports publish no two model-caused active plugin revisions with after-each access results.

An earlier [CISA/NCCIC incident report on PlugX](https://www.cisa.gov/sites/default/files/publications/IR-ALERT-MED-17-093-01C-Intrusions_Affecting_Multiple_Victims_Across_Multiple_Sectors.pdf) says plugins operate independently on threads within the RAT service and can be added, removed, or updated during runtime by an operator. Unlike a generic benign hot-reload API, this is an analyzed field RAT with an explicit **plugin update capability**. Yet the report gives a module inventory and a general capability description, not a dated sequence of two replacement versions in one identified process with command results after each. It also predates and does not involve model-guided revisions. PlugX, Emotet, KUKURAT, and SHINYROAD collectively reduce uncertainty about possible resident update *surfaces*, while leaving model provenance and serial function preservation unmeasured.

## An update-capable remote-access interpreter: SHINYROAD

[METAL's 16 October 2026 investigation](https://www.manageengine.com/uk/threat-analysis-lab/aomei-backupper-supply-chain-compromise.html), coordinated with [GTIG/Mandiant's supply-chain report](https://cloud.google.com/blog/topics/threat-intelligence/investigating-ephemeral-supply-chain-tampering/), recovered an in-memory PocketPy payload from an implanted component in a signed `dllhost.exe` surrogate. METAL's decrypted configuration indicates an outbound reverse-TCP control path, shell execution, and the ability to receive and execute further interpreter code at runtime. This is a useful **non-AI architectural precedent**: a real deployed remote-access implant has a code-loading surface in an existing host process. The researchers observed its delivery path, but the command server was unresponsive in their analysis environment. They expressly did **not** observe a live session, and publish no received code version, successful update, or remote-control result after an update. The short, repeated vendor-update tampering windows concern *delivery of the implant*, not repeated changes within one implanted process. No model role is reported.

[Elastic Security Labs' SCMBANKER investigation](https://www.elastic.co/security-labs/threat-command/mexican-banking-fraud-scmbanker-ref6045) supplies a contrasting field case. Its recovered toolkit had an operator-directed ZIP replacement path that kept selected state files, then **killed the old PowerShell module processes and relaunched** the kit. A separate commercial Remote Utilities Host product supplied hands-on access; the kit's script replacement does not demonstrate revision of that remote-access product. Elastic found earlier toolkit versions and inferred AI-assisted authorship from comments and code style, without a captured model-to-version trace. Its “process-mutation rotator” copied scripts under changing Windows-like names and launched short-lived processes, rather than rewriting executable code inside one process. This is an observed architecture and artifact analysis, not an observed two-update sequence with access checks. It illustrates why retained installation state, a persistent remote-desktop service, and a self-update label must be kept separate from same-process code continuity.

## AI-attributed revisions and fetched scripts: GREYVIBE

[WithSecure's 2026 GREYVIBE investigation](https://www.withsecure.com/wp-content/uploads/2026/09/WithSecure_GREYVIBE.pdf) observed PhantomRelay RAT deployments that changed from V1 to V2 while retaining their core function. WithSecure rates LLM assistance on the V2 reconstruction **high confidence**, based on comments in recovered scripts, rather than a captured prompt, response, or version-authoring trace. The PhantomRelay client can execute scripts delivered through C2. Its watchdog fetches current scripts to disk and, if it finds no active C2 session, launches the stored initial-stage script on a recurring schedule. That is an operational **replacement or recovery** path, not evidence that the original process changed its own active code while remaining alive. The report does not link two fetched revisions to one identified process and verify remote access after each.

The same report documents LegionRelay executing operator-issued scripts and returning output, with WithSecure assessing LLM-assisted development at moderate-to-high confidence from naming, design choices, and flaws. This supports field use of a RAT that can run externally supplied code; it does not show the model revising the resident client. The distinction is material: comments and style can motivate an authorship assessment, while the stricter causal claim needs a trace joining a particular model output to the applied artifact. The report's [dated summary](https://www.withsecure.com/fi/resurssit/w-labs/greyvibe/) was published 28 May 2026; its analysis cutoff was 30 April 2026.

[Sophos X-Ops' August 2026 MDR review](https://www.sophos.com/en-gb/blog/fake-ai-real-malware-attackers-impersonating-ai-brands) provides a stronger *developer-side provenance* example. Investigators correlated a deployed Slack-controlled Rust RAT with a public development repository showing commits from a human operator and a `claude` coding-agent account. The reported history changed capabilities over several days, including addition and later removal of a reverse-shell feature. This is more concrete evidence for AI-assisted authoring of a working RAT than stylistic attribution; the article does not publish a model output-to-commit transcript or a process-level chain. Its evidence concerns **build evolution before deployment**, not revisions accepted by one running RAT. Sophos reports that behavior on a monitored endpoint was flagged, while the initial foothold included an unmonitored device; that incident result is not a detection probability for adaptive implants. The report's 86 tagged MDR cases, 34 confirmed after review, and four added analyst cases describe a selected casework sample, not prevalence of this mechanism.

[Elastic Security Labs' PHANTOMPULSE investigation](https://www.elastic.co/security-labs/threat-command/phantom-in-the-vault) provides the weaker comparison: its follow-on [binary analysis](https://www.elastic.co/security-labs/threat-command/blockchain-c2-phantompulse-rat-sinkhole) calls structured debug strings and verbose diagnostics “AI-assisted-development fingerprints,” without a captured model session or source commit trail. The first reported intrusion was blocked early, before the final RAT executed on that monitored victim. The analyzed binary can receive commands, repair persistence, and restart after repeated connection failures; the reported “self-healing” repairs tasks and stored components, while restart changes process identity. No model call or active-code rewrite in the RAT is shown. Its AI-authoring assessment therefore remains an analyst inference, and its one blocked intrusion is not a detection rate.

[GTIG and Mandiant's 16 November 2026 field update](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold) reports CAIRN and PentAGI in intrusion activity and describes agent frameworks that generate *single-use* payloads, then adapt tactics from execution feedback. Its `exploit_agent` example runs vulnerability analysis and exploit attempts from an exposed staging server using frontier and local models. Those are meaningful observations of model-assisted operation, yet the publication does not trace a generated version into a continuing RAT process, let alone two accepted revisions with access checks after each. It also calls these workflows forensically noisy and vulnerable to model errors; those are analyst assessments rather than measured Drexel detection or reliability rates.

## Version labels are not an accepted revision chain

[Unit 42's Latin America incident analysis](https://unit42.paloaltonetworks.com/ai-tool-use-targeting-latam-orgs/) observed attempts to install files labeled versions 1 through 9 of a separate tunnel tool within about two hours, after multiple RATs had been dropped. It assesses that repeated failed installation or proxy connection likely led to trying version 9. The investigators saw an attacker-hosted NextChat instance and iterative scripts on exposed infrastructure, and infer LLM-assisted troubleshooting and development. The report does not publish a prompt-to-build trace, hashes or diffs establishing nine distinct code changes, a successful connection after each attempt, or an in-place upgrade of one process. Its version count is therefore evidence of **attempted operator-side replacement**, not serial accepted revision. This distinction also applies when a recovered malware family contains many builds: a filename or sample count is not the number of functional changes retained by a continuing instance.

“Self-update” itself is ambiguous. [Microsoft's SparkRAT threat description](https://www.microsoft.com/en-us/wdsi/threats/malware-encyclopedia-description?Name=Trojan%3AWin32%2FSparkRat%21MTB) notes both an embedded Go interpreter and automatic client updates. [F5 Labs' first-party architecture analysis](https://www.f5.com/labs/articles/sparkrat-exploiting-architectural-weaknesses-in-open-source-offensive-tools) separates the two: newer **client binaries** are built server-side, referenced by commit SHA, and retrieved through REST calls. The exposed C2 that F5 investigated contained no client version newer than the binary they had. Neither source demonstrates that the interpreter revised the resident RAT code in place. A source using “self-update” should therefore be checked for the exact replaced object and process lineage before entering the Drexel matrix.

[Sysdig's EtherRAT analysis](https://www.sysdig.com/blog/etherrat-dprk-uses-novel-ethereum-implant-in-react2shell-attacks) makes the process boundary unusually explicit. The recovered Node.js implant is programmed to send its source to a server on first successful contact, overwrite its source file with the response, mark the update as done, start a fresh process, and exit the old one. Sysdig did **not** observe a server response, so whether the returned code would change behavior, only re-obfuscate, or arrive at all in the analyzed setting is unknown. Even if that one-time path executed, it would be process replacement, not two revisions accepted by one continuing instance; no model role is reported.

Two more first-party RAT analyses show why an update label alone is insufficient. [Unit 42's Insomnia RAT report](https://unit42.paloaltonetworks.com/ppi-network-malware-campaign-analysis/) lists a C2 task type `ow` for self-update, but does not describe its application semantics, process identity, or an observed update result. [Zscaler ThreatLabz's MLTBackdoor analysis](https://www.zscaler.com/blogs/security-research/technical-analysis-mltbackdoor) says the implant self-updates during installation before sideloading and separately documents a loader that executes task modules within its own process and then frees their memory. The former is a setup stage, and the latter runs transient task code rather than retaining a changed payload version; the report does not link them into serial revisions or show two versions, model authorship, or after-each access checks. The three cases strengthen the distinction between **available update mechanism**, **observed applied version**, and **same-instance serial success**.

[Stormshield's September 2026 Melofee analysis](https://www.stormshield.com/news/cti-melofee-linux-implant-and-new-variants/) gives a stronger persistent-module design in a recovered Linux remote-access implant. Its core tracks loaded modules and can request, load, and unload separate shell, file-management, and remote-command components without a process restart. The three recovered components demonstrate the architecture and the placement of remote-control functions outside the core. They are **different functions**, not successive versions of one function. Stormshield compares samples from different years but publishes no one-instance module-replacement timeline, model-to-module provenance, or independent remote-access results after each change.

## Current feasibility judgment

**Broad model-guided code-change mechanism:** technically plausible because a model can produce code and a program can apply selected code at runtime. This is a mechanism-level inference, not evidence that a real RAT has performed it. **Strict same-instance subclaim:** possible in deliberately designed runtimes, but constrained by version activation, mixed old/new execution, safe timing, state conversion, and supported edit classes. [Multi-turn programming studies](feasibility-source-update-2026-11-25.md#new-evidence-about-repeated-revision-reliability) show that preserving earlier behavior across revisions is a live reliability problem. The integrated two-revision/access chain remains unestablished in the public cases audited here. No success probability or expected detection rate can be inferred by multiplying results from unrelated studies.

If a future authorized benign study estimates a serial rate, its denominator should be **initial continuing instances**, with each later outcome conditioned on the accepted prior version. Formally, the two-change success probability is the probability of the first accepted functional change multiplied by the conditional probability of the second accepted functional change *given* the first and its retained state. The second factor cannot be replaced by the first or inferred from independent fresh-candidate success. A failed first change, recovery through restart, and a rejected proposal should remain visible rather than being silently excluded. This follows directly from the chain definition and is reinforced by [SWE-Maintain's inherited-history finding](https://arxiv.org/html/2610.14768) and [BypassGym's fresh-snapshot design](https://arxiv.org/html/2611.13684); neither paper measures the proposed serial rate.

The next source pass should look for primary incident traces or controlled studies that publish process lineage, exact model-to-artifact links, two accepted revisions, and after-each function checks. Where a report uses “self-modifying” for generated commands, swapped scripts, restarted workers, configuration changes, or model-weight updates, it should be mapped to that narrower behavior rather than counted as an instance of the full claim.
