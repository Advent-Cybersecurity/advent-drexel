# Production tool versioning: generated code, promotion, and function evidence

Advent Cybersecurity source audit, 26 November 2026. Source: [Kujanpää et al., *Tool-Making and Self-Evolving LLM Agents in Low-Latency Systems*, arXiv v2, 24 August 2026](https://arxiv.org/html/2607.08010). This is a paper reading, not a reproduction. The system is a benign fulfillment-center alarm-triage service.

The authors separate **build-time code synthesis** from **production use**. A tool-maker observes a backend trace and writes a deterministic Python tool for each of 44 decision nodes. A reflector and tool-maker may revise the candidate for up to three rounds against labeled training cases; the candidate with the highest training-set pass rate is selected. A separate held-out set totals 8,022 node cases. The reported 94.5% pass@1 for GLM-4.7 is the mean over nodes of whether one complete pipeline run produces a tool correct on *all* held-out cases for that node, not the fraction of individual alarms solved by a live revision process. Across 30 runs, generated libraries have 39–43 fully passing tools; one deployed library has 42 of 44. [Method and results](https://arxiv.org/html/2607.08010).

The production agent calls the prebuilt tools directly or through a sub-agent, with a code-generating fallback on tool error. Before promotion it runs in shadow, with human review of discrepancies. The paper reports use across more than 5,000 production alarms, a 42% p50 latency reduction in a same-model production comparison, and held-out 1,500-alarm end-to-end evaluations. These are meaningful functional observations for **deployed generated tools**; the 53% relative error reduction is calculated for GLM-4.5-Air on historical alarms and remains an alarm-triage result, not a remote-control rate. [Deployment and evaluation](https://arxiv.org/html/2607.08010).

Each tool invocation reportedly logs tool version, inputs, and outputs; a monitoring agent reviews drift in batches. The authors describe regenerating and promoting a corrected version after a held-out set and manual review. They do **not** publish a time-ordered record of two replacements to one tool, process identity across such promotions, or outcomes immediately after each promotion. The promotion is a configuration change in a versioned tool library, and the build-time model is not part of a resident payload. [Production insight](https://arxiv.org/html/2607.08010).

This case offers a **measurement pattern** for Drexel: version-tag every invocation, pin the expected input and output, hold out cases, and inspect discrepancies before claiming retained function. It also documents a failure mode: one repair reduced test failures by replacing the specified five-minute averaging window with a wrong ten-minute average. The correct target behavior had to be clarified independently of the repair signal. [Repair example](https://arxiv.org/html/2607.08010). None of these figures estimates Drexel success or proves two active model-caused revisions in a continuing remote-access process.
