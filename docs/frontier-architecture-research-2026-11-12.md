# Architecture and training routes to a smaller CPU model

Research note, started 2026-11-12 17:52 EST. Scope: general model efficiency on benign tasks. Source audit completed 2026-11-12 22:48 EST. This note is a companion to `master-feasibility-evidence.md` and the two 2026-11-11 efficiency notes. It does not claim a working compression breakthrough.

## Decision standard

The comparator is the **same base model** in a working llama.cpp CPU `Q4_K_M` deployment, with the same prompts, context policy, thread count, host, and sealed benign multistep evaluation. A candidate must lower complete deployable bytes `B`, both process high-water RSS and fresh-cgroup peak memory `R`, and full-request CPU-seconds `C`. The task success rate `Q` must meet a prespecified noninferiority margin and an absolute floor. Do not substitute BF16 or GPU numbers for this comparator.

This relative gate does not by itself establish that a model fits an intended local device. Before selecting a stronger reference, record separate **absolute** maximums for installed bytes, cold cgroup peak, and full-request CPU-seconds on the target CPU class. A candidate can improve all three against a larger same-base reference and still exceed those device limits. The current study has no user-specified numerical device limits, so it cannot certify deployability from relative percentages alone.

Useful accounting identities:

```
B = serialized tensor payload + container/tokenizer metadata + runtime and libraries + auxiliary files
R = resident weights + KV and state + temporary buffers + runtime + parallel workers
C = CPU-seconds for prefill + decode + checks + retries, over the entire task
```

These sums are bookkeeping, not assumptions that each term is independent. For a change in decode steps, use the observed full request. If a method increases step count by `r`, a decrease in CPU-seconds requires per-step CPU cost to fall below `1/r` after accounting for prefill, checks, and retries. `Q` should be scored on the same held-out tasks and paired seeds where stochastic decoding is used. Report uncertainty and a failure taxonomy, including errors that appear only when steps are combined.

The local [same-base quantization pilot](same-base-quantization-pilot-2026-11-12.md) shows how runtime settings can reverse a resource result. Against a fresh Qwen2.5-1.5B-Instruct Q4_K_M reference, a pinned map changed exactly 14 MLP down projections from Q6_K to Q4_K and saved 49,674,240 file bytes (4.45%). In five alternating 128-prompt/64-generation synthetic runs on one i7-12700K with default CPU repacking, candidate CPU-seconds were lower in every pair but peak process RSS was **higher in every pair** by 57,806,848 to 64,729,088 bytes. With repacking disabled for both artifacts, five further paired runs had lower candidate CPU-seconds and peak RSS in every pair; median CPU-seconds were 12.393 to 11.217 and median peak RSS was 1,211,441,152 to 1,161,707,520 bytes. A later [cold-cache five-pair cgroup pilot](../data/frontier-cpu-cold-cgroup-pilot-2026-11-12.json) under `--repack 0` also lowered child CPU-seconds and both process and cgroup peaks on fixed synthetic 512/128-token loads. These measurements do not include complete benign tasks or quality, so they do not establish the four-way gate. The realized tensor map was checked after export; an earlier rule recipe had changed six other tensors in the opposite direction. Architecture claims should audit the actual serialized map and measure every gate under a pinned runtime setting.

The changed tensors hold 108,380,160 Q4_K payload bytes in the candidate. Subtracting median no-repack RSS from median default-repack RSS gives 609,996,800 bytes for the reference and 718,327,808 for the candidate, an overhead difference of 108,331,008 bytes. That is within 49,152 bytes of the changed tensors' Q4_K payload, consistent with an added repacked copy under this runtime. It remains an inference from separate run groups, not an allocation trace or proof that the same relationship holds on another CPU.

**Simple-control result.** The pinned whole-format [Q4_K_S control](same-base-quantization-pilot-2026-11-12.md#whole-format-q4_k_s-control-2026-11-12-1919-est) from the same FP16 source is 1,071,584,800 bytes, only 3,938,304 bytes larger than the custom 14-tensor file. In five direct alternating [512/128 no-repack pairs](../data/same-base-custom-vs-q4ks-no-repack-512-128-runs-2026-11-12.json), the custom file used 0.123 to 0.520 **more** CPU-seconds in every pair, while its peak process RSS was 3.6 to 4.2 million bytes lower. Median CPU-seconds were 25.901 for Q4_K_S and 26.132 for custom. This makes the simple control a serious falsifier of any claim that the 14-tensor selection has a novel or dominant CPU tradeoff. Neither file has a valid held-out quality comparison, controlled-charge cgroup peak, or cross-host result, so it does not yet rank the candidates by the full `B/R/C/Q` gate.

**Closer released mixed-GGUF comparison.** [TurinTech's Kev-4B Artemis results](https://huggingface.co/turintech/Kev-4B-Artemis-GGUF/blob/main/RESULTS.md) (27 to 28 October 2026 protocols) publish a per-tensor mixed file of 2,541,447,616 bytes versus a 3,033,489,824-byte stock Q4_K_M file from the same BF16 tensors, a 492,042,208-byte or 16.22% complete-GGUF reduction. On an RTX 5090 its 2,000 typed decisions have the same displayed 66.8% accuracy as stock Q4_K_M, and its GPU peak is 7.6 versus 8.0 GiB over the reported suite. The authors explicitly say the test decisions selected the published files; the 300-item Decision Index panel is only 30 items per benchmark. Its CPU-only Ryzen 9 5900X memory check reports 3.78 GiB peak resident memory for the Artemis file over three 112-token short requests, **without** the stock Q4_K_M CPU arm or CPU agreement check. It reports no full-request CPU-seconds or sealed dependent-step success. This artifact is stronger evidence that mixed native GGUF can save substantial *file bytes* than our 14-tensor probe, but it does not establish the joint CPU and quality gate or a new allocator method here.

The pinned [llama.cpp `repack.cpp` selector at commit `f3b407ca1`](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5076) supplies a specific mechanism to test. For `GGML_TYPE_Q4_K`, AVX2 returns the `q4_K_8x8_q8_K` repack trait when `cur->ne[1]` is divisible by eight (lines 5011 to 5015). The `GGML_TYPE_Q6_K` branch in that revision offers repack traits only for NEON integer-matmul or dot-product paths (lines 5066 to 5076). The [model buffer list](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model.cpp#L1230-L1285) places CPU extra buffers, which include CPU_REPACK in the [CPU backend](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/ggml-cpu.cpp#L59-L83), ahead of the ordinary CPU buffer; the [loader](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model-loader.cpp#L1151-L1173) chooses the first buffer whose test operation the device supports. The [CPU_REPACK buffer code](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5148-L5185) calls the selected trait's `repack` method while setting a tensor. Thus changing an eligible Q6_K tensor to Q4_K on the pilot's AVX2 host can switch on a resident repacked representation, rather than smoothly reducing RAM with serialized bits. The 14 changed down-projection tensors have `[8960, 1536]` GGUF shapes, so `ne[1]=1536` passes the selector's divisibility test; the separate `[1536, 151936]` output head also passes it, so the proposed Q6_K-to-Q4_K head arm may trigger the same branch. These shapes come from the [audited pilot tensor map](../data/same-base-quantization-pilot-pinned-map-2026-11-12.json). This code-path reading predicts a **possible** head RSS penalty, not its size or even its realized buffer lifetime. An allocation trace, realized trait census, and fresh paired process and cgroup peaks with repack enabled and disabled are required to attribute the observed RSS difference. The precise result is revision- and CPU-feature-dependent.

**Whole-task cost can reverse a token-level saving.** [Abkin et al.](https://arxiv.org/html/2610.32417) (arXiv v3, 2026-10-30) ran Q4_K_M and Q8_0 files of the same released Qwen3 and Devstral models through a pinned llama.cpp agent harness on bare-metal A100 servers. Their 29 verifiable SQL, data, function, and repository tasks use hidden final checks and repeated attempts. Four-bit used 6% to 16% less measured energy per output token on average, but on tasks with statistically supported disagreement between per-token and per-completion choices, the per-token choice cost a median 66% more energy per completed task, up to 3.5 times as much. The conditional 66% figure must not be read as an all-task average: the main Qwen condition's geometric-mean Q4/Q8 task-energy ratio was 1.17, while two exploratory conditions were 0.92. For the disagreeing tasks, extra tokens per completed task had a median factor of 1.6 to 2.0, far above the 6% to 19% extra tokens that their per-token energy savings could cover. Their main task suite and protocol were fixed before the experiment; expanded budgets, second model, and held-out task analyses were added after early results and are exploratory. This is evidence for charging retries and failures to completed work. It is **not** evidence that a sub-Q4 candidate loses or wins our CPU-seconds gate: all weights were GPU resident, the compared quantizers and kernels differ, model loading was excluded from task energy, and no same-base smaller-than-Q4 CPU file, process peak RAM, or complete installed-byte result was tested.

**Parser sensitivity in that result.** The [paper's trace analysis](https://arxiv.org/html/2610.32417#S5.SS3) says one business-query variant had 20/20 correct *eventual* answers, but 6/10 Q4 attempts first submitted the numerically correct result with one missing closing JSON brace; the parser rejected it and the model resubmitted. A separate Devstral regression task had the same missing brace in 6/10 Q4 attempts. The [released harness at commit `8e10a85`](https://github.com/stephen122204/mantra-energy/blob/8e10a855d4509837c09f0678d0c972bc8b4ddb70/studies/energy_diagnosis/agent_protocol.py#L125-L165) uses strict `json.loads`, rejects malformed calls, and only repairs a missing final `</tool_call>` tag, not JSON syntax. Its [turn loop](https://github.com/stephen122204/mantra-energy/blob/8e10a855d4509837c09f0678d0c972bc8b4ddb70/studies/energy_diagnosis/local_run.py#L342-L359) returns a parser error to the model and charges a turn. This is a real cost under that machine interface, but its magnitude is protocol-sensitive; a separately prespecified lenient-JSON arm could change it. The 3.5-times maximum is the **8,192-row** business query, while the explicit missing-brace trace described above is the **one-million-row** variant, so it does not by itself explain the maximum. The 66% is conditional on supported disagreements selected from the same repetitions. In the authors' exploratory split-repetition retest, the Qwen median extra cost falls to 31% and 45%; this is more useful for judging selection sensitivity than presenting 66% as a prospective effect. Recompute on saved traces under alternative parsers before generalizing to another agent protocol; the repository says large actual measurements live outside Git, so this audit did not independently replay those attempts.

## Ranked, falsifiable hypotheses

No source below proves a joint `B/R/C/Q` win against the same-base Q4_K_M CPU reference. The ordering ranks experimental value, not the probability that a breakthrough already exists. Apply the prespecified meaningful saving thresholds and the paired statistical plan in [the existing CPU study protocol](mixed-precision-cpu-study-protocol-2026-11-11.md): exact installed bytes; both process high-water RSS and task-cgroup peak in a named lifecycle; a one-sided 95% upper bound on the paired mean candidate-minus-reference CPU-seconds below `-ε_CPU`; a one-sided 95% lower bound on paired success difference above `-δ`; and one-sided absolute-success floor checks for each artifact. Here `ε_B` and `ε_CPU` denote the minimum worthwhile absolute reductions in installed bytes and CPU-seconds. Use a matched-token memory stress set so early failed completions cannot masquerade as RAM savings. These thresholds, `δ`, the RAM reduction, and the absolute floor must be locked before final outcomes. A literal zero-quality-loss claim requires `δ=0`, adequate power, and still does not mean identical outputs.

**Runtime qualification for rank 1.** The Q4_K head is the larger measured file-byte opportunity, but its accepted [default-repack cold cgroup pairs](../data/frontier-cpu-head-cold-cgroup-default-repack-2026-11-12.json) raised cgroup peak in all five pairs. It is viable under the tested `--repack 0` policy only if that policy is part of the frozen deployment and the eventual quality and full-request gates pass. The simpler [Q5_K head-only arm](../data/frontier-cpu-head-q5-cold-cgroup-default-repack-retry-2026-11-12.json) saves 30,994,944 complete GGUF bytes (2.77%) and lowered cgroup peak, process RSS, and child CPU-seconds in four admitted default-repack synthetic cold pairs; a fifth planned pair failed the prespecified admission checks. Q5_K is therefore the more plausible *default-runtime resource screen*, but neither precision has a sealed quality result. Its mechanism is also directly anticipated by Muse Glimmer, so it cannot support a new algorithm claim on its own.

The smallest common screen uses one model, one pinned CPU runtime build, one host, the same prompt/context/thread settings, and a few public development tasks for error diagnosis. It records per-tensor bytes, model load, prefill, decode, full-request CPU-seconds, process and cgroup peaks, token counts, and retry counts. The final sealed suite is a single-use decision gate, with categories and sample size fixed from development data. A candidate that wins only on nominal bits, GPU latency, perplexity, or tokens/s is a partial result.

### Novelty and cost audit for the ranked ideas

The mechanism in each rank has prior art. A same-host, same-base four-gate result would be valuable evidence because those sources do not measure it; it would not by itself prove a new compression algorithm. The local 14-tensor candidate is a **baseline probe**, not a learned allocator. A genuinely new *method* would need a documented selection rule that beats a faithful RAMP-like mixed-GGUF allocator, an AutoCompress-style measured-cost architecture selector, and simple controls at matched complete bytes. RAMP does not publish an artifact or code link in its paper, so a local reimplementation would have to state its differences and cannot establish superiority over the unreleased original.

The separate [ik_llama.cpp offline-conversion PR #272](https://github.com/ikawrakow/ik_llama.cpp/pull/272) and [regex-selection PR #274](https://github.com/ikawrakow/ik_llama.cpp/pull/274), both merged 2025-03-21, also rule out claiming selective, memory-mapped, single-GGUF offline packing as a new mechanism. Their CPU-oriented row-interleaved quants are not shown to match the pinned mainline AVX2 Q4_K_8x8 layout, and the PRs do not measure our four gates. A new CPU/GGUF packing method would need a specified format or kernel advance and a matched resource and quality result beyond this implementation precedent.

## Output-head compression against an already Q6_K reference

The local [tensor inventory](../data/mixed-precision-baseline-tensor-inventory-2026-11-11.json) shows a separate Q6_K `output.weight` with 151,936 rows by 1,536 columns and 191,439,360 packed payload bytes in a 1,117,320,736-byte Qwen2.5-1.5B-Instruct Q4_K_M GGUF. Its Q4_K `token_embd.weight` has the same shape and 131,272,704 payload bytes. If the output head alone can use Q4_K without changing other tensors, the payload difference is 60,166,656 bytes, or 5.38% of that GGUF. The arithmetic predicted the later measured byte saving in the pinned export, but it does not establish full-request CPU performance or safe quality. Since the reference head is **Q6_K rather than BF16**, BF16-to-INT4 comparisons cannot be counted as additional savings here.

The closest direct precedent is Muse Glimmer's Q6_K-to-Q5_K output projection. It makes a plain head-bit downgrade an incremental engineering test. A method claim would need a source-matched Q5_K arm, the unshifted Q4_K head, and matched-budget calibration/assignment controls, not only a BF16 comparison.

[Softmax Reparameterization for Output-Head Quantization](https://arxiv.org/html/2609.31291) (arXiv v2, 2026-09-28) exploits the exact full-precision softmax invariance of subtracting the same hidden-state-dependent scalar from every logit: `W_t = W - t 1 μᵀ` for a linear-softmax head. It fits `t` by validation KL after W4 quantization, adding no new inference operation to the tested shift-compatible deployment. On Phi-4-mini with W4 AW-MSE packed vLLM and an A10G GPU, held-out WikiText perplexity is 31.65 unshifted versus 15.40 shifted, still above BF16 at 11.65. For W4 GPTQ, the same comparison is 13.67 versus 12.23, compared with BF16 11.65. The warm batch-one 64-token Phi AW-MSE latency is 1,014.8 versus 1,013.4 ms, which supports near-zero *shift overhead* in that implementation, not a shift-driven speedup. Its 10.8% latency advantage is W4 against BF16, with the decoder kept BF16. The Qwen3.5-4B auxiliary A10G timing has 516.6 ms BF16 versus 467.2 ms W4 for 25 tokens, a 9.6% difference with the same limitation. The paper uses group size 128, 128 WikiText fitting articles with separate validation/test slices, then an untouched 26-article holdout after a development test split was seen. Some heads have little baseline W4 error and barely benefit from the shift. For tied Phi-4-mini, keeping BF16 input embeddings while adding a separate packed W4 head raises resident weights from 7.17 to 7.47 GiB. That is a direct memory warning, although our inventory is untied. The paper promises code and evaluation records upon publication, so the exact result is not independently reproducible from a released implementation as audited here. It reports no Q6_K-to-Q4_K GGUF, CPU RAM, CPU-seconds, complete package, or benign multistep quality.

[ARCHead](https://arxiv.org/html/2608.02703) (arXiv v1, 2026-08-03) uses an activation-metric low-rank correction for a compressed head. For Qwen3-8B it reports 1,188 to 304 MB of **persistent head state** for a BF16 versus INT4-plus-correction head, relative WikiText perplexity 1.007, and 93.05% top-1 dense agreement versus 76.95% with plain group-INT4 on a 16,384-token holdout. The storage-matched GPTQ relative perplexity is 1.0093 at 8K calibration, averaged over three seeds. RTX Pro 6000 throughput is 4,468 tokens/s dense versus 4,467 ARCHead, effectively unchanged within those reported numbers; no CPU speed win is established. The paper separates persistent state from backend peak memory. Its [released code](https://github.com/suayptalha/archead) uses PyTorch, Hugging Face, and Triton, with CUDA recommended, so adaptation to a native Q4_K GGUF path would be new engineering and might erase the byte gain. Its BF16 comparator, calibration data, short holdout, and GPU runtime do not establish a win over the local Q6_K head.

[SoftWater](https://arxiv.org/html/2608.12026) (arXiv v1, 2026-08-12) already performs class-aware output-head rate allocation using a softmax-KL surrogate and entropy-coded lattice quantization. In its head-only experiments, the body is FP16 and calibration uses 128 WikiText sequences of 1,024 tokens. It reports better head-induced next-token KL than the released WaterSIC baseline without finetuning at 59 of 60 matched-rate points; at a nominal two-bit head rate the reported KL reduction spans 6.5 to 8.3 times across five models. Its fully quantized tied Llama-3.2-1B table compares a two-bit GuidedQuant body with an FP16 tied head at 737.3 MiB against the same nominal body with a two-bit SoftWater head at 297.0 MiB, while WikiText-2 perplexity changes 26.81 to 27.80 and C4 perplexity 38.54 to 42.39. That reported model-size reduction is 59.7% relative to a **tied FP16 head/embedding** comparator, not an already Q6_K GGUF or a complete CPU deployment. The four-bit-body comparison similarly reports 962.6 to 532.5 MiB, with WikiText-2 perplexity 16.53 to 17.01 and C4 24.54 to 26.60. The paper does not report CPU latency, peak memory, full-request cost, or sealed multistep quality. Domain-targeted calibration changes cross-domain KL; its large domain-calibration experiment uses 1,024 sequences of 1,024 tokens per domain. Native K-quant blocks do not directly express SoftWater's per-class variable rates and entropy code. A CPU implementation could need new storage and kernels, so the candidate must account for complete bytes and runtime overhead rather than import the paper's bit-rate claim.

The [Muse Glimmer 30B technical report](https://arxiv.org/html/2610.24628v3) (dated 2026-10-19, Section 7.1) is a closer prior than the specialized head papers for a simple K-quant change. Its Q4KM-derived variant changes the output projection from Q6_K to Q5_K while also increasing group sizes for Q6_K and Q5_K in an MLX/ExecuTorch affine representation; the authors state the two changes have negligible quality degradation but do not isolate the projection effect. Their Greedy-KL and EvoPress per-weight-unit searches allow Q4_K/Q5_K/Q6_K, including the output projection. EvoPress selects a Q5_K head and Q4_K token embedding at 19.65 GB of model weights, versus a Q4KM profile chosen as their smallest footprint. On 15 downstream benchmarks, Table 3 reports 75.7% BF16, 75.6% EvoPress, 75.3% Greedy-KL, and 74.8% Q4KM mean accuracy. These are a different, multimodal 29.6B-parameter model, format conversion, and runtime, with no isolated Q6_K-to-Q4_K head or comparable CPU process/cgroup peak and full-request CPU-seconds. The report is primary technical evidence, not an independent replication.

**A direct head-bit caution from released GGUF measurements.** [Praveen Kumar's single-laptop experiment](https://inboxpraveen.github.io/blogs/blog-1.html) (2026-09-07) exports a Qwen3-0.6B Q4_K_M GGUF and a source-matched variant with its tied `token_embd.weight` changed from Q6_K to Q4_K. That file has no separate `output.weight`; the shared tensor serves as both input embedding and output projection. The [export script](https://github.com/inboxpraveen/ggml-inference-lab/blob/master/scripts/make_quants.sh) uses `--output-tensor-type` for this tensor and declares the same BF16 source and importance matrix; the [released result table](https://github.com/inboxpraveen/ggml-inference-lab/blob/master/results/kld_table.json) records complete files of 396,705,504 and 356,594,400 bytes, a 40,111,104-byte or 10.11% reduction. On 200 WikiText-2 chunks of 512 tokens, approximately 51,000 raw-text scored positions, mean KL divergence to BF16 rises from 0.074071 to 0.091351 and BF16 top-1 agreement falls from 86.118% to 84.369%. The result is a reason to test head sensitivity before celebrating our 5.38% measured file saving, but it is not a task-success loss estimate. Its smaller **tied** 0.6B model, different quantizer revision and Windows laptop cannot predict the quality change of our **untied** Qwen2.5-1.5B head. KL was computed with GPU-offloaded `llama-perplexity`; the reported 391 versus 351 MB per token describes tensor bytes read per token, not complete package bytes. That head-only Q4_K arm has no paired cold CPU process/cgroup peak, whole-request CPU-seconds, or sealed multistep result. The measurements are a reproducible engineering blog and released raw table, not independent replication. The laptop also ran other applications during timing. Our ranked arm therefore remains prospective on quality despite a verified GGUF byte reduction.

The predeclared minimal arm is **output.weight Q6_K to Q4_K only** from the same original source checkpoint and pinned quantizer used for the reference, with a Q5_K head-only intermediate control motivated by Muse Glimmer. Verify every tensor type after export, hash complete packages, and reject immediately if the realized map changes another tensor or if actual `B` does not beat the 49,674,240-byte pilot plus the declared extra margin. On public development data, compare naive head-only Q4_K first. If it loses quality, use disjoint calibration, validation, and development test splits to compare ordinary centering, validation-selected softmax shift, and a storage-accounted correction; any extra tensor bytes must be subtracted from the 60,166,656-byte opportunity. Lock a single head treatment before the sealed benign multistep suite. The same-host CPU reference and candidate need identical context/thread and repack policies, fresh paired processes, process RSS and task-cgroup peaks, and whole-request CPU-seconds. The experiment fails if quality, actual complete bytes, either peak, or CPU-seconds misses its prespecified gate. No model-heavy runs are launched from this note while the paired quality screen is active.

## Physical pruning plus native low-bit recovery

**Claim to test.** Remove complete CPU-kernel-aligned channel, head, or block structures, preserve dense executable tensors at smaller dimensions, then train the surviving network with a simulation of its target quantizer. This is an inference from several sources, not an achieved result. Physical removal can lower weight bytes and matrix work; recovery training might restore multistep quality lost by pruning. Metadata-only or irregular sparsity cannot be credited with CPU savings without a matching sparse kernel.

**Quantitative gate.** Let the removed parameter fraction be `p`, quantized bytes per retained parameter be `q`, package overhead change be `ΔO`, KV/state saving be `ΔK`, and CPU work saved be `ΔW`. Require `p*N*q > ΔO` for bytes, `p*N*q + ΔK >` new temporary memory for peak RAM, and measured `ΔW >` conversion, dispatch, longer responses, and extra verification/retry CPU. A rough roofline prediction can screen candidates, but the three inequalities must be measured on the complete deployment. Quantizer block shape matters: pruning one scalar from a 256-weight Q4_K block need not remove its scale or fixed-size packed block. Width changes should remove complete compatible groups and retain kernel-friendly dimensions.

**Pinned packed-width arithmetic, before any pruning run.** The [same-source GGUF tensor census](../data/same-base-quantization-pilot-pinned-map-2026-11-12.json) has 28 MLP blocks, intermediate width 8,960, hidden width 1,536, and complete reference size 1,117,320,736 bytes. Every `ffn_gate` and `ffn_up` is Q4_K; 14 `ffn_down` tensors are Q4_K and 14 are Q6_K. The pinned [ggml block definitions](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-common.h#L2647-L2730) use 256 weights per block, 144 packed bytes for Q4_K and 210 for Q6_K. If an identical set of intermediate channels could be removed from all three projections in every layer, while retaining these exact tensor types and 256-element alignment, each 256-channel width cut would remove `28 × 1,536 × (2 × 144 + (144 + 210)/2) = 19,998,720` packed tensor bytes. Cuts of 512, 768, and 1,024 channels imply 39,997,440 (3.58%), 59,996,160 (5.37%), and 79,994,880 (7.16%) packed bytes relative to the current complete file. These are **counterfactual payload calculations**, not exported GGUF or measured CPU savings. A 512-channel cut cannot by this arithmetic alone exceed the 49,674,240-byte MLP bit-map pilot; the first listed width cut that could is 768 channels, or 8.57% of intermediate width. Re-export may alter tensor types, metadata, padding, or kernel routing. The width and model configuration must actually be changed and recovered, and no quality retention is assumed. A decisive arm must report the new complete GGUF census and bytes before any runtime or quality claim.

**Near-equal-byte adversary for that width cut.** The 768-channel calculation is only 170,496 bytes below the **measured complete-GGUF saving** of the head-only Q6_K-to-Q4_K export (60,166,656 bytes). Thus the already built head-only file is a particularly strong, same-source, nearly equal-byte control for an aligned-width candidate on this checkpoint. The match is provisional because a real width export could change padding or tensor types. If its complete bytes land outside the locked tolerance, build a same-source bit-only arm matched to its *actual* bytes. Reject a claim that width selection improves the deployment tradeoff if the head-only or matched-byte bit-only arm is quality noninferior and has equal or lower cold process/cgroup peak and full-request CPU-seconds under the same repack policy. This comparison would test the added value of physical shape changes; it would not make either compression mechanism new.

**Source and limit.** [QATFactory](https://arxiv.org/html/2609.39223) (arXiv v2, 2026-10-01) implements simulated llama.cpp Q4_K blocks, including 256-weight blocks and 32-weight subblocks, and exports to a native deployment format. Its training uses H100 GPUs and BF16 fake-quantized matrix operations. Q4_K is not the same tensor-wise mixture as `Q4_K_M`. The paper reports score recovery within Q4_K: Qwen3-8B mean of GPQA-D and AIME25 rises from 59.37 after PTQ to 61.21 after quantization-aware distillation, versus 63.39 BF16; Qwen3.5-9B rises from 57.64 to 64.57, versus 69.93 BF16. These are two knowledge/reasoning benchmarks, not sealed multistep task success, and the paper does not give deployed file bytes, CPU peak RAM, or full-request CPU-seconds. Thus QATFactory supports a recovery mechanism, not a joint gate win. Its LoRA training-memory reduction is training GPU memory, not inference RAM.

**Smallest decisive experiment.** Choose one same-base model already deployed as Q4_K_M. Profile per-layer CPU time and packed tensor sizes. Remove one conservative, whole-block-aligned fraction of MLP channels, keeping dimensions supported by the CPU kernels. Compare original Q4_K_M, pruned PTQ, pruned plus target-format-aware distillation, and unpruned plus the same distillation budget. Export each to a complete distributable package. Verify actual tensor types and no unexpected fallback; measure bytes, peak RSS/cgroup memory, energy if available, prefill, decode, full task CPU-seconds, and sealed paired multistep success. Repeat on a second host only after a local joint win. If Q4_K_M-aware training is unavailable, label the Q4_K result as an exploratory arm rather than claiming comparator equivalence.

**Likely failure.** At a modest pruning ratio, multistep failures may worsen even if aggregate short-form accuracy recovers. An ill-shaped width may route to a slower CPU kernel. A recovery model may need more tokens, checks, or retries and lose the `C` gate. If the dense Q4_K_M baseline is already dominated by runtime or KV memory, parameter removal may not reduce measured peak RAM enough.

**A quantizer-block counterexample.** [Das et al.](https://arxiv.org/html/2608.15693) (arXiv v1, 2026-08-16) physically remove 1% of Qwen3.5-0.8B MLP channels and report that its FP16 checkpoint shrinks from 1,446.48 to 1,441.42 MB, yet the Q4_K_M GGUF grows from 507.85 to 612.06 MB. The authors attribute this inversion to breaking 256-element K-quant superblock alignment; 24 of 320 Qwen tensors fall back to a larger representation. In a separate internally controlled CPU campaign, Qwen SQuAD evaluation rises from 0.7826 to 0.9150 **wall seconds per sample** while F1 falls from 86.30 to 68.49. The GGUF byte table also shows TinyLlama-1.1B Q4_K_M growing 637.81 to 933.30 MB after 3% pruning and Gemma-3-1B growing 768.72 to 1,020.14 MB after 1% pruning. These campaigns cannot be merged into one verified artifact-level `B/C/Q` observation. A rank-8 LoRA recovery using 100 optimizer steps, each with an effective batch of eight 256-token WikiText-2 sequences, did not restore the Qwen quality. These are public short-form tests over 100 items per dataset, not sealed multistep success or measured CPU-seconds and process/cgroup peak. The Raspberry Pi arm changed prompt templates between campaigns, so it is unsuitable for a causal latency ratio. The paper's 18 matched prefill/decode logging pairs are **all GPU-offloaded**, despite the adjacent discussion of CPU decoding, and cannot be used as CPU per-token data. The [public repository](https://github.com/Arnavvvkumar/deployment) supplies summary tables and a minimal client but omits the full pruning pipeline, scoring harness, and per-sample raw logs; independent replay is therefore limited. The result is a direct counterexample to inferring packed file savings from removed FP16 parameters; it does not rule out whole-block-aligned pruning with stronger recovery. Inspect tensor dimensions, tensor types, and complete file bytes before any performance claim.

**A CPU speed-versus-RAM split even with hardware-aware pruning.** [Barker et al.'s Heterogeneous Structured Pruning](https://arxiv.org/html/2610.15781) (arXiv v1, 2026-10-11) searches per-sublayer dense, head/channel, and block-sparse choices with a profiled latency or analytical memory constraint for a Jetson Orin Nano Super. In its **FP16 ARM CPU** on-device OPT-2.7B mixed workload of fixed 1,024-token prefill and 128-token decode, the latency-optimized candidate's measured end-to-end time improves from 117.76 to 97.16 seconds versus dense and the first-32-window WikiText-2 perplexity moves from 15.66 to 15.50, but peak process physical RAM grows from 6,135 to 6,748 MB. The memory-optimized candidate is also above dense on measured peak RAM, at 6,640 MB, despite its analytical budget; its mixed latency is 100.02 seconds. The model counts FP16 weights, sparse metadata, and KV but excludes temporary activations, allocator overhead, and workspaces. The measured peaks therefore expose an unmodeled cost or implementation effect, though the paper does not isolate its cause. The CPU has no supported 2:4 kernel, so the GPU's favorable 2:4 points are not CPU evidence. This is a direct counterexample to assuming that a latency-constrained structural search automatically lowers peak RAM. It uses custom FP16 ARM kernels, three timed CPU executions, public perplexity and seven short zero-shot tasks, and no Q4_K_M complete file, task-cgroup peak, CPU-seconds, or sealed multistep test. The [project page](https://cameronbarker.me/publications/hsp/) still lists both pruning and kernel code as coming soon, limiting independent reproduction. A local adaptation should profile **actual Q4_K_M CPU paths** and constrain both measured RAM and full-request CPU instead of transferring the Jetson proxy.

**CPU cache-targeted physical pruning is already published.** [Ochilov et al.](https://www.mdpi.com/2673-2688/7/10/408) (AI, 2026-10-05) derive a compression target from each operator or layer weight working set and an effective L3 budget, physically remove functionally similar FFN channels with compensation, then apply per-channel INT8 GPTQ and a task-level quality stopping rule. On a single i7-11850H running ONNX Runtime 1.28, their Whisper-medium Uzbek encoder removes 17.1% of FFN channels and shrinks its serialized encoder from 300 to 267 MiB beyond GPTQ-only. The paired 300-utterance WER difference from GPTQ-only is -0.0014, 95% CI [-0.0115,+0.0096]; the paper's actual accept/reject rule requires the upper quality-loss bound to fit a prespecified budget, not merely a nonsignificant difference. The whole 705 MiB cascade is 4.14 times smaller than FP32, so that headline denominator is not an already quantized artifact. On six recordings, eight-thread end-to-end transcription wall time falls 14,457 to 6,134 ms against FP32; a separate 1.91-times execution measure covers one encoder forward plus one decoder step. The authors' decoder recomputes its prefix without KV cache. Their 30/18/12/10 MiB L3 settings are hypothetical inputs on the same processor, not measured second hosts. Its cross-architecture diagnostic is a specific warning for our ranked width hypothesis: the Qwen2.5-0.5B SwiGLU sample had only 0.04% to 0.14% near-collinear channels at its stated threshold, versus 17.1% for Whisper; that sample is a different size and cannot prove a null for Qwen2.5-1.5B. At matched 267 MiB encoder size, the proposed selection and FLAP had WER 0.1833 and 0.1838 with a paired difference whose interval includes zero, so method superiority is unresolved. This is strong prior art for hardware-derived targets, physical width reduction, quantization ordering and a quality gate. It does not establish native Q4_K_M GGUF alignment, complete installation bytes, cold process/cgroup RAM, full-request CPU-seconds, or benign dependent-step quality. A new claim here must exceed that precedent with an artifact-realized Q4_K CPU allocation and matched-byte controls, not just reuse its cache-aware framing.

**Adversarial null and ordering check.** [Compression Technique Interactions in Small Language Models](https://arxiv.org/html/2611.00464) (arXiv v1, 2026-10-30) tested 72 factorial configurations on four 2.7B to 7B models, plus 48 ordering trials. With bitsandbytes NF4 applied **before** 30% or 50% unstructured L1 pruning, all 16 combinations collapsed under its perplexity criterion. The ordering study found viable NF4 results when pruning preceded quantization, so the result is not a universal low-bit-plus-pruning impossibility. Its 200-step LoRA recovery on 256 short C4 samples improved severely degraded FP16-pruned perplexity; an ablation with cross-entropy and no teacher gave comparable recovery. This disputes any assumption that an expensive teacher is necessary for basic perplexity recovery, though it does not test multistep quality. Appendix D reports Nemotron-Mini-4B attention-head pruning at 30% with perplexity 4,775 versus 52.69 for unstructured pruning; 50% collapsed. This is a warning against naive head removal, not evidence that informed block pruning always fails. Three other architectures were incompatible with the external head-pruning method due to fused projections. Its CPU llama.cpp Appendix Table 11 lists **19 selected configurations**, including only three 30%-pruned-plus-recovery q8 rows, rather than the entire 72-cell factorial sweep. Those rows show no consistent RSS or tokens/s benefit from retaining unstructured zeros in dense GGUF; they do not directly isolate pruning from recovery. CPU q4 was 46 to 54% faster than q8 for four baseline models, but the paper does not specify a `Q4_K_M` comparison, a complete package, the CPU processor or full-request CPU-seconds. Its CPU perplexity and short-form GPU benchmark accuracy do not establish sealed benign multistep success. Its GPU factorial NF4 and CPU GGUF q4 are different quantizers; one cannot transfer the NF4 collapse rate directly to Q4_K_M.

**Informed pruning precedent.** [Minitron](https://arxiv.org/html/2407.14679) (arXiv v2, 2024-11-04) physically trims attention, MLP, embedding, and depth dimensions from a 15B base and retrains with distillation. In its 8B search, a width-pruned 7.74B model reaches validation loss 2.049 after 1.8B recovery tokens, versus 2.155 for a 9.39B depth-pruned variant. The authors emphasize that width can look worse before retraining yet better afterward, and search rankings stabilize only after lightweight retraining. A 4B distillation comparison uses roughly 100B recovery tokens, with 4B MMLU 37.81 after direct 15B pruning and 42.45 when pruned through 8B, versus 24.57 for a conventionally retrained pruned 4B at a stated iso-compute setting. This supports physical dimensional change and staged recovery as feasible at high training cost. It reports no Q4_K_M artifact, CPU peak RSS, or full-request CPU-seconds; 4B and 8B descendants are not quality-equivalent to their 15B parent on all tasks. Its finding that teacher distillation helps a long, aggressive retraining regimen does not negate the factorial study's narrower result that a 200-step LoRA recovery can improve perplexity without a teacher.

**Mask selection with a smaller training budget, and a size-dependent null.** [Deterministic Differentiable Structured Pruning](https://arxiv.org/html/2603.08065) (arXiv v2, 2026-05-11) learns structural masks on 30M FineWeb-Edu tokens without updating pretrained weights. At 20% target pruning, its nine-task Qwen3-32B mean falls from 72.12 to 71.09, while Qwen3-4B falls from 65.38 to 62.99; MathQA on the 4B falls 46.50 to 38.36. At 50%, 4B mean falls to 47.63. This is a useful warning that pruning tolerance observed at 32B may not transfer to a smaller local base. A vLLM experiment reports LLaMA-7B GPU request throughput 10.88 to 14.75 requests/s at 20% sparsity on RTX 5090, using 1,000 ShareGPT prompts. The source does not inventory exported tensor bytes or CPU RSS/CPU-seconds, and its public zero-shot means do not establish sealed multistep quality. The smallest adaptation is to keep the same 30M-token mask search as one rank-1 candidate arm, export the resulting physical tensor shapes into Q4_K_M, then compare its package and task metrics against both the reference and a simpler ranking method. Reject mask optimization as an added expense if it does not improve the quality bound at the same measured bytes.

**Where to prune.** [LayerTrim](https://arxiv.org/html/2610.19121) (arXiv v1, 2026-10-13) uses 24 AIME2024 reasoning traces to rank block influence, then physically trims MLP gate/up/down widths while retaining attention and depth. On Qwen3-14B, removing about 1.5B parameters by MLP trimming leaves an AIME25/GPQA-D average of 58.8, versus 48.3 when that budget includes 25% attention trimming, 0.7 for attention-only trimming, 0.4 for attention-layer removal, and 8.8 for MLP-layer removal. The dense model's five-benchmark mean is 76.7; LayerTrim is 68.3 at 7/40 layer-equivalent removal and 65.1 at 9/40. Thus MLP-only is a more credible first physical trim than naive attention or depth removal, but it still loses substantial quality. The paper's RTX 6000 Ada BF16, batch-one Qwen 9/40 run reports 588 to 474 ms prefill, 38.0 to 31.3 ms per decode token, and 28.1 to 22.6 GiB peak memory. Model loading is excluded, and its output-token comparisons condition on different successful subsets. It gives neither Q4_K_M CPU measurements nor a full benign task cost. Add a conservative MLP-only arm and an attention-pruning counter-arm to the decisive experiment above, with identical recovery training. Check physical GGUF tensor shapes and kernel routing before attributing any CPU saving to the nominal parameter reduction.

**Prune or train the target size.** [Small LLMs: Pruning vs. Training from Scratch](https://arxiv.org/html/2606.14150) (arXiv v3, 2026-06-29) compares a Llama-3.1-8B parent trained for 200B tokens, 50% pruned descendants given 50B recovery tokens, and target-size models trained from scratch on either 50B or the full 250B pipeline budget. On its eight-benchmark average, a width-pruned Minitron descendant scores 66.3 versus scratch-50B 59.9, but scratch-250B reaches 67.5. A depth-pruned descendant scores 64.4 versus 60.7 and 66.2. This supports reuse of a trained parent when the available incremental training budget is small; it does not show that pruning is intrinsically superior to training a small architecture with equal total tokens. At 81.3% pruning, the initialization advantage disappears in the paper's study. Its TPU v4-256 50% pruning step-speed table gives 1.9 times for depth, 1.4 times for width, and 1.0 times for unstructured or 2:4 sparse pruning relative to the 8B parent, illustrating that nominal sparsity need not translate into implemented speed. These are TPU training-step speeds, not CPU inference. A project-level break-even must include the cost of acquiring or training the parent, the recovery data, and whether the saved deployment CPU-seconds amortize that work at the expected request volume. The smallest fair training comparison uses a target-size scratch model and a physically pruned same-parameter descendant with equal **total** data and compute budgets, then applies identical Q4_K_M packaging and sealed evaluation. Likely failure is attributing gains from the inherited 200B-token parent to the pruning method.

**Additional source and caveat.** [Quantization-Aware Healing](https://arxiv.org/html/2608.20953) (arXiv v1, 2026-08-21) distills an MXFP4 compressed GPT-OSS student from the original uncompressed teacher and reports that 4-bit training recovers or exceeds its compressed BF16 source on seven of nine benchmark scores. It uses a second training stage and an expensive original teacher; the authors explicitly note the absence of a direct head-to-head baseline that distills the compressed student from its compressed BF16 version. The apparent gain therefore cannot be attributed to quantization-aware healing alone. Its format and GPU setting do not establish Q4_K_M CPU efficiency.

**Joint architecture and precision allocation.** [TOGA](https://arxiv.org/html/2606.07819) (arXiv v1, 2026-06-05) searches structural masks and per-channel bit allocation jointly. Its Llama-2-7B ablation is a striking sensitivity check: uniform W4A4 round-to-nearest gives WikiText-2 perplexity 1,753 versus FP16 5.12; retaining an average 12.5% of salient weight and activation rows in W8A8 lowers it to 6.03, then reordering/GPTQ to 5.38, and INT4 KV to 5.48. The table labels this step as upgrading weights to INT8, while its caption specifies both weights and activations in W8A8; it should not be treated as a weight-only comparison. This is a warning that one uniform low-bit representation can destroy quality while selected high-precision channels preserve it. The runtime result uses custom CUTLASS kernels on an NVIDIA L40, 2,048-token contexts, and 100-run phase measurements: up to two-times prefill speedup versus FP16 and up to 6.5-times peak decode-memory reduction, not a joint improvement versus Q4_K_M. The paper defines its compression budget as theoretical memory, such as 50% sparsity times 4/16 bits = 0.125 of FP16, which omits full package and runtime overhead. Its structural-mask equations imply dimension selection, but it does not publish an exported tensor-size inventory; actual physical savings must be verified in a deployed file. A testable local extension is to search only quantizer-supported **whole tensor or whole block** precision choices together with physical MLP widths. Require observed `B`, `R`, `C` below the Q4_K_M reference, with a sealed task-quality bound. If a mixed-bit choice creates extra CPU unpack passes or high-bit copies, it may increase `C` or `B` despite lower theoretical bits. The smallest decisive experiment is a two-dimensional grid of a few physical width cuts and a few Q4_K_M-compatible precision maps, each exported and executed in the same CPU runtime, including sequential prune-then-quantize and quantize-then-prune controls with equal calibration and recovery budgets.

**Fine-grained mixed precision is already prior art.** [SFMP](https://arxiv.org/html/2602.01027) (arXiv v2, 2026-06-03) assigns 2/3/4-bit rates to weight blocks, reorders rows and columns by Fisher salience, and runs them in one CUDA one-bit-LUT kernel. Its 512 by 128 block option estimates 0.006 bits per weight of metadata on Llama-3.1-8B. At a reported 3-bit/4,501-MB budget for Llama-3.1-8B, its WikiText-2 perplexity is 8.65 and six-task zero-shot mean 69.92, versus AMQ 9.38 and 68.78; at 4-bit/5,333 MB, SFMP reports 6.84 and 74.15 versus AMQ 6.86 and 73.46. These are matched *reported model-memory budgets* with public perplexity and short tasks, not complete runnable packages or a same-base Q4_K_M comparator. All main experiments use A100-80GB GPUs; its 128-token generation throughput and CUDA kernel cannot establish full-request CPU-seconds. The paper notes that group-wise SliM-LLM can be 30% to 50% slower than GPTQ at similar average bits in its GPU tests, a direct warning that rate flexibility can cost execution time. The [released code](https://github.com/Nkniexin/SFMP) is a source for replication, but no independent CPU/GGUF reproduction was found in this audit. A new CPU method would need to beat source-matched simpler per-tensor allocation and a rate-matched SFMP-style control on *actual* package bytes, process/cgroup peaks, full task cost, and sealed success. Merely proposing block-wise bit selection, Fisher salience, or a unified kernel would repeat existing work.

**Phase-aware precision and a runtime counterexample.** [AlignQuant](https://arxiv.org/html/2610.07457) (arXiv v1, 2026-10-05) allocates W4/W8 precision to 64 by 64 tiles from both prefill and decode loss observations, packs one selected weight copy, and uses distinct GPU Tensor Core and DP4A execution paths. Its default has 60% W4 tiles and **5.61 packed bits per quantized weight**, compared with 4.01 in its all-W4 arm. On A100 Llama-3.2-3B-Instruct, the 128-input/512-output batch-one table reports 132.28 tokens/s and 2.72 GiB peak VRAM for the default, versus 138.96 tokens/s and 2.17 GiB in its **own all-W4 runtime**. The default's headline 2.27-times throughput and 5.99 to 2.72 GiB resident-memory comparison are against BF16, not a same-base Q4_K_M CPU deployment. Its higher precision preserves quality on short public tasks, but the primary 128-token peak is worse than all-W4, and an isolated **byte or memory win over Q4** is not shown. At 16K prompts the paper reports 4.44 GiB peak versus 5.72 GiB for its separate W4A8 implementation, which shows runtime-lifetime interactions can reverse a short-context ordering; it does not establish a smaller installed file. The A100 results use matched CUDA Graph, attention and KV settings, but the external SFMP backend dequantizes to floating-point multiplication, so the cross-method speed gap is partly a kernel comparison. The source uses 64 Multi-News summary pairs for deterministic calibration and public short-form/long-context tests, no sealed benign multistep tasks. A prospective CPU architecture must beat the same-runtime all-W4 control at *complete bytes*, process and cgroup peaks, and full-request CPU-seconds. A mixed W4/W8 map without a compensating physical width reduction cannot be assumed to beat a Q4_K_M file merely because it speeds GPU decode.

**A CPU route for the precision map.** [PolyQ](https://arxiv.org/html/2607.14618) (arXiv v1, 2026-07-16) uses activation-aware allocation across 2/3/4/8/16-bit input channels, then groups equal-bit channels into compiler-generated CPU blocks. Its Llama2-13B at a 3-bit target has WikiText-2 perplexity 4.88 versus 5.29 AWQ and 5.75 GPTQ under its calibration setup, and at a 2.6-bit target has 5.96 after a severe 2.5-bit collapse to 44.78. The 2.6-bit point is **not** quality-equivalent to its own 3-bit point, let alone a Q4_K_M reference. On Ryzen 9950X and 7840U, its measured 256-token prefill is respectively within 4.7% and 5.8% to 7.3% of AWQ on the same T-MAC backend at integer budgets; decode throughput is 0.2% and 8.1% to 8.2% lower. Thus mixed-bit execution can be near a uniform low-bit CPU path, but the paper does not show it is faster at equal quality. Its headline 4.98 GiB peak for 2.6-bit Llama2-13B is a **modeled** maximum of a 256-token prefill and a one-token decode with 256 cached tokens, not measured process RSS/cgroup peak. Its 70.8% reorder-traffic saving is also a model of A16 shuffle bytes, not an end-to-end CPU-time saving. It reports no complete distributable package, Q4_K_M comparator, or benign multistep completion. Use its quantizer/compiler co-design as an engineering lead, then reject any local map that loses full-request `C` despite lower packed bits.

**A nearer CPU Q4_K_M comparator, with a quantizer fidelity gap.** [LUQ](https://arxiv.org/abs/2509.23729) (TMLR June 2026, arXiv v3, 2026-06-22) selects language-backbone layers by output-activation entropy for lower precision. Appendix D maps 12 selected Qwen2.5-VL-7B layers to llama.cpp IQ1_M at roughly 1.75 bits per weight and the remaining layers to Q4_K_M. Across ten generation runs, reported CPU generation throughput is 9.0 ± 0.3 versus 4.8 ± 0.3 tokens/s on an i7-13620H, and 18.7 ± 0.1 versus 14.1 ± 0.2 on a Threadripper Pro 7965WX. Its table reports 3.4 GB versus 4.4 GB of "Memory Usage," a 22.7% difference, without defining whether that is artifact size, resident model memory, process RSS, or another denominator. Only the language backbone is quantized. The main VQA quality table, however, uses **BiLLM at 1.08 bits plus GPTQ at 4 bits in PyTorch**, not the appendix's IQ1_M plus Q4_K_M export. On Qwen2.5-VL-7B, the main-table LUQ configuration scores 63.7 ± 0.6 versus GPTQ4's 80.2 on MMBench, and 68.6 ± 0.5 versus 84.1 on ChartQA, even though MME perception is close at 1640 ± 10 versus 1638. The paper does not report quality on the exact exported CPU artifact, packed tensor census, whole installed bytes, process/cgroup peak, prompt processing, or full-request CPU-seconds. Thus LUQ makes entropy-guided native mixed precision a strong **screening control**, not a joint-gate demonstration. The smallest decisive local check is to produce and hash the exact IQ1_M/Q4_K_M artifact for the same base as its Q4_K_M control, audit every tensor type, replay the same sealed benign tasks on the same CPU, and count full-request CPU-seconds, both memory peaks, and complete installed bytes. Reject the route if the exported model's quality falls outside the locked noninferiority margin or any resource gate fails.

**A same-size CPU model has a useful but weaker comparator.** The first-party [Arm AI Portal Qwen2.5-1.5B-Instruct INT4 page](https://developer.arm.com/ai/models/hugging-face/Arm/qwen2-5-1-5b-instruct-onnx-genai-int4-kquantlast-emb-int4/qwen2.5-1.5b-instruct-int4-onnx) reports a 1,078.7 MB ONNX model, 1,570.45 MB peak memory versus 6,117.85 MB for its original-model baseline, and 2,235.38 versus 7,514.74 ms p50 end-to-end wall time on a four-core Graviton G4. Its MMLU five-shot scores are 61.03% versus 62.98%. These are promising CPU deployment measurements for an INT4, dynamic-INT8-activation, INT8-head artifact, but the comparator is the original model, not a native GGUF Q4_K_M file. The portal lists 5,000 MMLU items while the linked benchmark YAMLs specify `dataset.sample_count: 9183`; the denominator needs clarification. Publication date and peak-memory accounting are unstated, and the timing uses 127 input and 60 generated tokens over 30 runs with two warmups. The displayed wall time is not CPU-seconds, the model size excludes a verified installed bundle, and MMLU is not sealed dependent-step quality. This is a CPU control to reproduce under a common task and artifact census, not evidence for our four-gate claim.

**A multi-team blind benchmark reinforces the comparator problem.** [Gowda et al., WMT 2026 model-compression shared-task findings](https://aclanthology.org/2026.wmt-main.52.pdf) (ACL Anthology, October 2026) evaluated 41 runnable submissions from 13 teams on held-out translation inputs on one H100. In its constrained Gemma-3-12B track, Table 2 gives the BF16 organizer baseline 22.74 GiB on disk, 626 net characters/s and Czech-to-German COMET-Kiwi-XXL 56.26; its bitsandbytes Q4 baseline is 7.78 GiB, 838 net characters/s and 55.47. A Tahoma FP8 system reaches 12,670 net characters/s at 10.72 GiB and 56.24, while a pruned/AWQ Vicomtech variant reaches 23,580 net characters/s at 4.27 GiB but drops to 26.47. The 20-times speed headline is **Tahoma FP8 versus BF16** at a throughput-optimal batch and a different serving engine, not a speed gain over Q4 or lower CPU-seconds per request. The paper's own table also has a 25% FFN-pruned AWQ variant at 5.71 GiB and 53.70, so its warning about severe structural loss pertains to the aggressive settings tested, not every physical trim. The authors report divergent directions between two reference-free quality metrics, do not report reliable peak GPU memory, and say host RSS is incomparable across runtimes. Their net throughput subtracts a one-sentence warmup that includes initialization and decoding. This is an unusually useful blind, multi-team negative control for claims based solely on size and speed, but it is translation-specific, GPU-based, and compares to a BF16 baseline. It cannot settle the same-base Q4_K_M CPU four-gate question. The methodological lesson is to compare the *same deployed runtime and quality denominator*, report both quality metrics or task success, and include load and complete-request cost.

**Global structured-mask learning has a stronger precedent than manual MLP cuts.** [Wang et al., GRASPrune](https://aclanthology.org/2026.acl-long.491.pdf) (ACL, July 2026) jointly learns FFN-channel and KV-head masks under a parameter-count budget, then folds calibrated scales into a physically smaller dense checkpoint. On LLaMA-2-7B, its four epochs on 512 WikiText-2 sequences took about six A100 minutes. At 50% parameter retention, WikiText-2 perplexity is 12.18 versus 5.49 for the original; the paper's five-task zero-shot average is 0.4654 versus 0.6896 original. Even at 80% retention, that average is 0.6139. At batch four and 2,048-token prefill, reported GPU peak memory is 21,889.8 MiB dense versus 17,822.5 MiB at 80% retention. Its throughput figure uses 2,048 prompt plus 256 generated tokens and batch scaling, but does not isolate per-request CPU-seconds. This is already a learned joint FFN/KV allocation method, so merely replacing hand-selected masks with learned gates is not novel. Its paper explicitly uses parameter count rather than hardware-exact cost and lacks quantized GGUF CPU deployment, instructions, code or multistep evaluations. The distinct test is whether a **prospective, artifact-realized allocator** that includes K-quant block alignment and measured CPU repack/lifetime effects can beat GRASPrune-style parameter-budget masks, simple MLP-only masks, and a target-size quantizer at the same complete package budget. Kill the idea if its allocation fails the four deployment/quality gates or does not improve against those source-matched controls.

**Hardware-aware structured allocation is also prior art.** [Barker et al., Heterogeneous Structured Pruning](https://arxiv.org/html/2610.15781) (arXiv v1, 2026-10-11) uses a multiple-choice knapsack to select dense, unstructured, 2:4, block-sparse, or physically narrowed head/channel options per sublayer under either profiled latency or analytically encoded memory. It profiles and tests on a Jetson Orin Nano Super, including its ARM CPU, so a claim that hardware-aware physical-mask allocation is new would be false. The paper's OPT-2.7B CPU Table 1 shows dense peak memory 6,135 MB and latency 117.76 s versus the latency-optimized candidate **6,748 MB and 97.16 s**. Thus its own measured CPU result improves one resource while worsening the other. Its analytical memory model counts FP16 weights, sparse metadata, and final KV but excludes temporary activations, allocator overhead, and kernel workspaces; CPU perplexity uses only the first 32 WikiText-2 windows, and seven public zero-shot tasks form the rest of its quality evidence. It has no Q4_K_M GGUF package or sealed benign multistep test. The credible remaining distinction is a *prospective* allocator trained on actual exported K-quant block sizes plus measured CPU repack and allocation lifetime, scored simultaneously on complete bytes, both memory peaks, whole-request CPU-seconds, and task success. Even this is a hypothesis until it beats an HSP-style allocator at equal installed bytes and quality on two CPU classes and two base models.

**Long-input quality can invert a short-input impression.** [Zhao et al., WMT 2026](https://aclanthology.org/2026.wmt-main.46.pdf) evaluate EuroLLM translation on 27 DocHPLT documents with bootstrap intervals. For EuroLLM-1.7B UK-to-EN, a W4A16 GPTQ model scores 63.6 chrF++ on independent segments versus 65.7 at BF16; at a 1,500-token document chunk threshold, it scores **6.3 versus 35.6** at BF16. At a 100-token threshold, the scores are 66.2 versus 67.6. This is a strong reason to stratify sealed quality by input length and dependent context, and to count all chunk requests in full-task cost. It is a 27-document, translation-specific GPU comparison on RTX 4090, not a same-base Q4_K_M CPU artifact or a general multistep result. The paper's serving Pareto curves use A100/H100 vLLM and random token IDs, so they cannot be combined with the document quality row as one four-gate observation. Its document segmentation changes both context and the number of requests; the study does not isolate a quantization-only causal effect at fixed long-input behavior.

**Pipeline composition has an unusually direct negative control.** [Yu and Shen, Budget-Aware Compression Pipeline](https://aclanthology.org/2026.groundlm-1.66.pdf) (GroundLM workshop, 2026-10-29) combine AWQ, 10-of-80 depth pruning, PyramidKV, and INT8 KV on a single A40. Table 10 gives a 33 GB artifact for both the pruned model without KV compression and the INT8-KV version, while measured peak GPU memory falls 44,170.07 to 42,174.54 MB; **decode slows from 9.49 to 8.59 tokens/s** and prefill from 748.23 to 539.77 tokens/s in those same rows. The KV choice is a memory tradeoff, not a joint speed win. Table 9 separately reports 39,029 MB and 57.21 tokens/s for PyramidKV INT8 at 11,427 input tokens, while Table 10 reports 42,174.54 MB and 8.59 decode tokens/s at 10,240 input and 256 output. These figures come from different reported protocols or stages and cannot be combined into a single four-gate observation; the paper does not provide enough detail to reconcile them. Its approximately 33 GB artifact is compared with a 132 GB FP16 file and a 38 GB AWQ file, not a Q4_K_M CPU baseline. The evaluation is public QA/reasoning, scripts and YAML are available on request, and no process/cgroup CPU peak or sealed multistep completion is reported. This limits both a blanket claim that combining compression modes is new and any claim that long-context KV savings automatically lower total CPU work.

**A target-size allocator is a useful control, not a validated solution.** The author's [llama.cpp PR #15550](https://github.com/ggml-org/llama.cpp/pull/15550), opened 2025-08-24 and still open at this audit, proposes `--target-size` and `--target-bpw` per-tensor allocation. It samples quantization error under an importance matrix, builds per-tensor size-error frontiers, and solves a global bit budget. The author's latest summary counts 195 KLD wins, 26 ties, 16 losses, and one unavailable result across 238 comparisons on 34 models at matched bit rates, about 93% wins or ties; that denominator is **KLD versus a standard quantization at similar bits**, not sealed task success or improvement on `Q4_K_M` while also reducing bytes. Its own description says quantizer search can take 5 to 10 times the standard conversion time and that sampled tensor error is only a proxy for model behavior. It reports no paired whole-request CPU-seconds or process peak RAM. Use a pinned copy only as a strong same-byte control for hand-picked maps, if the PR's exact revision is reproducible. To seek a meaningful joint win, first set a target below the measured Q4_K_M complete file bytes, then evaluate the actual exported tensor census, full package, RSS/cgroup peaks, total CPU-seconds, and sealed multistep success. Reject any map that wins KLD yet misses a deployment or task gate; do not treat the PR's unmerged state as native support in a pinned standard build.

**CPU runtime version is part of the experiment.** Two merged llama.cpp changes make static quantizer speed rankings fragile. [PR #27402](https://github.com/ggml-org/llama.cpp/pull/27402), merged 2026-08-31, adds an AVX2 decoded `int8` panel for IQ formats at sufficient prompt batch size. In the author's 24-thread EPYC 9654 benchmark on a pure Qwen3.6-27B IQ1_M artifact, prompt-processing throughput at microbatch 512 rises from 14.36 to 73.70 tokens/s across runtime revisions; at microbatch 8 it rises from 12.08 to 17.16. This is an **old-runtime versus new-runtime IQ1_M comparison**, not IQ1_M versus Q4_K_M. [PR #27851](https://github.com/ggml-org/llama.cpp/pull/27851), merged 2026-09-26, adds tiled CPU matrix multiplication for K-quants. The author's eight-thread AMD 9950X3D matrix microbenchmark reports Q4_K throughput of 1.064 to 4.973 TF/s for a large matrix product, but 0.263 to 0.238 TF/s for a 32-row input; the implementation avoids the tiled path when it expects too little work. Neither PR measures complete installed bytes, model-process peak RSS, cgroup peak, task quality, or paired full-request CPU-seconds. The LUQ report predates both merges and does not pin the exact runtime in its Appendix D; its generation-only rate cannot be assumed for a current full request. A decisive local study must pin one CPU runtime revision and its repack, batch, and thread settings for both artifacts, record phase times and full task cost, and repeat a promising result on a later revision before treating it as portable.

**Cold deployment cost needs its own protocol.** [Hu and Adatiya, Cold Start Latency of Quantized Small Language Models on Serverless CPU Infrastructure](https://storage.googleapis.com/gweb-research2023-media/pubtools/1046363.pdf) (Google Research, 2026; month not stated) tests llama.cpp GGUF on CPU-only Cloud Run, with five models, 4 and 8 GiB service tiers, 13 model/quant combinations and 25 feasible tier configurations. Each timing uses the same roughly 16-token prompt with a 50-token cap, with 30 or 60 trials per configuration; quality is WikiText-2 perplexity over roughly 50,000 tokens. Model loading is 55 to 70% of reported cold end-to-end wall time, and the Llama 3.2 1B Q4_K_M versus Q8_0 8 GiB cold comparison is 14.8 versus 20.2 seconds. This supports measuring cold load separately from warm request execution, but the multi-model container is about 5.8 GB, so individual GGUF sizes in Table I are not complete installed packages. The 4 GiB tier has one vCPU and the 8 GiB tier two vCPUs, preventing a memory-tier contrast from isolating RAM capacity. The paper reports no measured process or cgroup peak, CPU-seconds, or dependent-step success. It also contains an unresolved within-paper inconsistency: Table II reports 15.2 tokens/s for Llama 1B Q4_K_M at 8 GiB, while Section V.A says 12.0 tokens/s for that same model/quant/tier when comparing with Q8_0 at 12.8 tokens/s. That ambiguity and the short fixed prompt limit any claim about quantizer speed ranking. Its fitted cold-latency model uses 25 configurations from this same platform, with correlated model parameters and file size, so its coefficients are a planning prior rather than a portable causal byte-to-latency rule.

**A direct pruning-plus-quantization precedent, with a weaker denominator.** [QPruner](https://aclanthology.org/2025.findings-naacl.240.pdf) (Findings of NAACL, April 2025) combines LLM-Pruner physical structures, 4/8-bit per-layer allocation, Bayesian optimization, and LoftQ recovery training. Its LLaMA-7B at 50% pruning reports 16.65 GB peak memory and 48.37% BoolQ for a selected mixed-precision arm, versus 23.89 GB and 43.76% for a **half-precision, equally pruned** LLM-Pruner control. The unpruned model's BoolQ is 73.09%; the mixed arm remains far below it. Its 30% memory reduction is therefore relative to an already pruned half-precision GPU model, not to the unpruned Q4_K_M CPU deployment. The experiments use an NVIDIA L20 GPU, BitsandBytes NF4, 50,000 public Alpaca recovery samples, and seven zero-shot classification tasks, with no CPU timing or packaged-file measurements. Table 1 does not specify the exact peak-memory measurement stage or process accounting, so the GPU figure is not a cold total-RAM measurement. The study also compares quantized arms with LoftQ recovery against half-precision arms with LoRA recovery, so training recipes differ along with precision. The paper itself acknowledges pruning-related quality loss. It supports testing the order prune, quantize, then recover, while making same-base Q4_K_M, exported tensor maps, and sealed multistep quality indispensable controls. In the local pilot, record **realized** tensor types after export: the requested precision override need not equal the produced map if the quantizer's allocation changes other tensors.

**An apparently joint allocator can still lack a deployment test.** [Dehghani et al., SQuaRE](https://spice.cs.umd.edu/2026_papers/SQuaRE.pdf) (MICRO, October 31 to November 4, 2026) formulates sparsity and precision as joint layer choices under a resource budget, so the idea of simultaneous allocation is prior art. Its experiments cover DeiT-Tiny, Swin-Tiny, and ResNet-18, not LLMs. The abstract's 92.7%, 94.7%, and 84.3% mean energy reductions are an **unweighted per-layer proxy** equal to bitwidth divided by 32 times retained density, subject to each layer's isolated one-point accuracy-drop bound. The methods section explicitly omits sparsity metadata, activation traffic, memory hierarchy, hardware utilization, and execution overhead, and says the numbers are not measured hardware energy or total network energy reduction. Jointly applying selected configurations and measuring cross-layer quality interaction are future work in this paper. SQuaRE therefore constrains novelty but offers no CPU Q4_K_M `B/R/C/Q` evidence. A legitimate extension must include the realized whole model, not infer joint success by summing isolated layers.

**Ternary plus pruning can have a misleading speed denominator.** [Tropeano et al.](https://aclanthology.org/2026.climatenlp-1.5.pdf) (ClimateNLP, October 28, 2026) find that under 5% pruning yields up to 21% less reported time/energy and up to 13% less memory across six ternary models, with small changes on seven public zero-shot tasks. Their methods define inference time as the sum of **GPU FP32 matrix-multiplication proxy timings** on activations sampled from 128 C4 sequences. Memory savings are computed from layer parameter counts and assumed bitwidth; energy is tracked during the FP32 GPU matrix operations. Neither packed ternary CPU inference, installed bytes, process peak, nor full-request CPU-seconds is measured. The authors explicitly leave end-to-end bitnet.cpp decoding to future work and note that neuron-level shape changes break its optimized kernels. This is a useful negative check against importing ternary-pruning headline numbers into the proposed CPU test.

**A same-byte alternative to 2:4 sparsity deserves a control.** [Qin, Is 2:4 Sparsity Still Worth It?](https://arxiv.org/html/2610.28947) (arXiv v1, October 20, 2026) compares 2:4 masks with a lower dense quantization at equal stored bits, counting mask indices and scales, and at equal nominal tensor-core tiers. In its GPU transformer-operand grid, the lower dense precision is generally more accurate and faster while a lower precision is available. At a hardware precision floor, retrained 2:4 FP8 serves 27% more H100 prefill throughput than dense FP8 at similar GSM8K accuracy; reaching that quality draws on a 13-billion-token Sparse-Llama retraining precedent. Perplexity recovered before reasoning in its shorter retraining runs. The result applies to NVIDIA semi-structured tensor-core paths, not physical width pruning or llama.cpp Q4_K_M CPU kernels. The prospective CPU study should still include an equal-**complete-byte** dense lower-bit arm when testing sparse formats, and should treat public perplexity recovery as insufficient for multistep quality.

**Broad hardware audit strengthens the runtime caution.** [Hildebrand, Kiefer, and Zell](https://link.springer.com/article/10.1007/s10462-026-11614-6) (Artificial Intelligence Review, published 2026-07-12) evaluated pruning and quantization across GPU servers, a PC, an 8 GB Intel i5-8350U CPU laptop, and a phone. On Llama 3.0 8B, most structured pruning approaches fell below random-guessing MMLU by 25% removal; limited recovery used only 256 WikiText samples and did not restore the public MMLU gap. Their cluster GPU 50%-structured-pruning example reduced measured memory 39% and increased throughput 80%, below nominal 50% and 100% expectations; those are **GPU**, not CPU, numbers. On the CPU laptop, the pruning variants loaded but generated at most 2.4 tokens **per minute** in that implementation. The paper's uncompressed Qwen3-1.7B nearly reached four tokens **per second**, but this is a different model and cannot be taken as a pruning speed ratio. The laptop results expose backend support limits, not a universal CPU pruning law: the study uses PyTorch/Transformers rather than a physically reduced Q4_K_M GGUF in pinned llama.cpp, and its short public benchmarks and 256-sample recovery cannot settle the proposed rank-1 test. Score comparability is limited too: the paper's MMLU option to abstain excludes those questions from evaluation, and its flexible GSM8K score accepts the gold number anywhere in the generated text, unlike its strict delimiter score. Its quantization discussion also notes that unquantized embedding and output layers and unquantized activations dilute nominal weight-bit savings.

## Priority hypothesis: train on multistep errors after quantization

**Artifact functionality is a separate prerequisite.** [Patodiya, *Broken on Arrival*](https://arxiv.org/html/2609.05881v3) (arXiv v3, 2026-10-29) screened all 305 eligible code-capable official Ollama GGUF tags in 15 selected model lines, plus 22 popular community files. Seven official tags (7/305, or 2.3%) scored at most 6/164 on HumanEval+ after a 15-task screen; the seven are three model-variant incidents, all low-bit files of at most 4B models. Five suspect files were rebuilt from source and matched the published tensors, so reproducible conversion did not establish task function. For Qwen2.5-Coder-3B, a same-checkpoint, same-toolchain, same-tensor-mix importance matrix raised three failing Q2/Q3 levels from 0/164 to 76–113/164; the fourth Q3_K_S rose only to 30/164 and did not meet the paper's rescue rule, which was added after initial rebuild results. The authors' healthy Q4_K_M rebuild scored 129/164. This is a useful artifact-level smoke-test and calibration precedent before comparing subtler size gains. The 15 tasks were selected from problems solved by 23 Qwen healthy configurations, so they are a coarse failure screen, not a sealed multistep quality gate. Generation and replication used CUDA/Metal, the census is restricted to one registry and code tasks, and the work reports no complete installed bytes, cold CPU peak, or full-request CPU-seconds. Its own scorer initially failed one HumanEval task across artifacts and required serial rescoring, underscoring the need to retain raw responses and scorer versions.

**Claim to test.** A training curriculum that starts from actual failed benign multistep trajectories and applies localized teacher corrections may preserve combined-step success better than ordinary next-token distillation. This addresses the prior observation that small models can perform individual steps yet fail at composition. It must be evaluated on sealed tasks because training on near-duplicate trajectories could inflate success.

**Quantitative gate.** Let `S0` be paired success under Q4_K_M and `S1` success after compression and recovery. Require a prespecified one-sided confidence bound on `S1-S0` above `-δ` and `S1` above the absolute floor. For efficiency, compare paired `C1/C0`, including failed attempts and recovery loops. A shorter average successful trajectory is not enough when the methods succeed on different subsets.

**Source and limit.** [SteerDistill](https://arxiv.org/html/2611.13410) (arXiv v1, 2026-11-10) trains with locally corrected failed trajectories, then deploys the student without a teacher. Across five agentic benchmarks, the reported Qwen3-8B W4A16 mean is 53.18, versus 46.36 GPTQ and 53.54 BF16; Qwen3.5-4B is 60.95, versus 54.22 GPTQ and 61.68 BF16. These are agentic-task scores and a meaningful recovery signal. But W4A16 uses group size 64, BF16 activations, and an eight-A100 training setup; there are no complete bytes, CPU peak RAM, or CPU-seconds. The paper's 4.0k versus 4.1k to 5.2k output-token comparison on tau2 success traces is conditioned on each method's own successful subset, so it does not prove lower cost on a fixed task set. The Qwen3-8B W2A16 mean is 42.97 versus 53.54 BF16, a warning that more aggressive quantization can overwhelm the recovery method.

**Reproducibility and transfer boundary.** The [released implementation at commit `937744a`](https://github.com/air-embodied-brain/SteerDistill/tree/937744a4003eb96078ebe852f023d1249c2466b4) contains training launchers, configs, pinned dependencies, and evaluator guidance, but its [model setup](https://github.com/air-embodied-brain/SteerDistill/blob/937744a4003eb96078ebe852f023d1249c2466b4/docs/benchmarks.md) still marks checkpoint download links `TODO`. The main experiments start from task-specific BF16 checkpoints obtained by GRPO; the same task data or environments are used for initial BF16 post-training and subsequent low-bit training. The paper also reports a no-initial-GRPO Qwen3-8B control, but that does not supply the missing main checkpoints. Exact main-score reproduction is therefore not established from the public repository alone. This is a **training recipe candidate**, not a byte-saving architecture: apply failure-localized corrections to a fixed compressed same-base candidate, compare against ordinary equal-budget distillation on the same training trajectories, and assess an independently sealed task family with no teacher examples, prompts, or environment seeds from that family in training. Log teacher tokens, GPU-hours, verification attempts, and reference-trajectory construction separately, then amortize that offline cost across a stated deployment volume; the reported 67% fewer GPU-hours is relative to QeRL within their eight-A100 setup, not a free or CPU-local training path. The method requires successful teacher references, state restoration, and reliable local verification, and the authors say a locally accepted correction need not yield final task success.

**Smallest decisive experiment.** On a fixed Q4_K_M compressed architecture from the first hypothesis, collect benign training trajectories disjoint by task family and data source from the sealed test. Train equal-token-budget arms using standard distillation and failure-localized corrections. On the same held-out task seeds, report success, step count, retries, full-request CPU-seconds, and per-error-category paired changes. Keep all teacher use offline; count training cost separately from deployment.

**Likely failure.** Corrections can overfit the training workflow, increase output length, or shift errors from local steps to orchestration. Student-only inference does not by itself save inference bytes when compared with a student-only Q4_K_M baseline.

**Quantization-aware reasoning is already a strong precedent.** [Bondarenko et al., *Efficient Reasoning on the Edge*](https://arxiv.org/html/2603.16867v2) (arXiv v2, 2026-06-03) trains rank-128 reasoning adapters on a quantized Qwen2.5-7B base, then INT8-quantizes adapters; the base uses INT4 linear weights including the output head, INT8 embeddings and KV cache, and INT16 activations. Table 11's full 1.2M-example OT3 arm averages 58.12% over AIME24/25, MATH500, GPQA Diamond, and AMC23 versus 60.54% for its same-training BF16 arm; MATH500 is 89.6% versus 94.0%. Its 50k-example naive quantized base plus full-precision adapter scores zero across all five tasks, while quantization-aware retraining restores 39.25% mean before the paper's stronger base quantizer lifts it to 41.72%. The table is a useful warning that a BF16-trained adapter cannot be assumed to work after base quantization. It compares with BF16, **not an already Q4_K_M GGUF reference**. The budget-forced RL arm reports 2.38 ± 0.07 times shorter completions on MATH500, but its 32k-token accuracy is 92% versus 95% for the unforced SFT baseline; the 1k/2k/4k/6k caps favor budget forcing and do not establish unbounded parity. Training uses eight H100s for RL, and the quantized-base transformation uses one H100 for under 24 hours. The paper describes Qualcomm GENIE/ONNX mobile export and NPU-oriented parallel decoding, yet gives no complete installed bytes, measured cold RAM, full-request CPU-seconds, or sealed dependent-step quality. This sharply narrows novelty: local quantization-aware recovery or trace shortening alone is a reproduction; a new contribution must clear a same-base, equal-complete-byte CPU/GGUF comparator and an independent held-out composition gate. [Quantization protocol and Table 10](https://arxiv.org/html/2603.16867v2#S7.SS2), [Table 11 and deployment path](https://arxiv.org/html/2603.16867v2#S7.SS3), [budget results](https://arxiv.org/html/2603.16867v2#S5.SS3).

**Calibration is part of the hypothesis.** [UniComp](https://arxiv.org/html/2602.09130) (arXiv v6, 2026-08-28; accepted at EMNLP 2026 Main) evaluates seven compression methods across over 40 datasets and finds that retained factual recall can mask steep reasoning losses. Its LLaMA-3.1-8B example falls from 76.80 to 36.92 on GSM8K with SparseGPT under default C4 calibration, then reaches 55.04 when pruning calibration uses reasoning examples, a 49% relative improvement over the default-calibrated pruned model but still well below the 76.80 original. For the tested AWQ quantizer, that calibration substitution did not provide a comparable gain and could harm knowledge scores. These are public reasoning benchmarks on GPU-oriented compression, not sealed multi-step tasks or a CPU Q4_K_M deployment. The decisive test is a paired, equal-size pruning-calibration comparison: general text versus task-family-matched but test-disjoint benign multistep examples, followed by the same recovery budget and exact Q4_K_M export. Measure whether calibration improves the lower confidence bound on `Q` without hurting other held-out categories, while all three resource gates are assessed separately. A likely failure is improving one benchmark family by sacrificing transfer or consuming too many calibration examples from the sealed distribution.

**Depth is a high-risk quality lever.** [What Breaks and What Comes Back](https://arxiv.org/html/2611.00877) (arXiv v1, 2026-10-31) block-prunes 12.5% to 25% of layers from four 1.2B to 1.7B instruction-tuned families. Across those families, post-pruning function-calling score retention is only 0 to 0.05 and math retention 0 to 0.07 relative to the unpruned model, although other categories are less damaged. In a 1M-token recovery comparison, all-layer LoRA is better than tuning only the final three blocks; the latter loses 0.05 to 0.18 in the authors' capped mean on three of four models. Their pilot-based selection consumes 3.48M additional tokens for a nominal 1M-token recovery and is matched or beaten when a uniform recovery receives the same 4.48M total token budget. This strengthens the case for testing small MLP width trims before layer removal and for accounting for search cost. The study is GPU-oriented, uses public and benchmark-aligned recovery data, and has only 150 to 300 examples per test category, so it cannot establish the precise loss rate on sealed tasks or the CPU resource gate. A minimal countercheck can remove one shallow or deep block from the local same-base model, then compare its failure categories and Q4_K_M CPU measurements with a parameter-matched MLP trim; stop the depth route if the sealed multistep lower confidence bound collapses. The likely failure is preserved surface fluency concealing damaged task orchestration or tool use.

## Output-head and vocabulary routes: useful counterexamples

### Approximate output retrieval

[Loretz and Hochreiter](https://arxiv.org/abs/2608.27460) (arXiv v1, submitted 2026-07-01; ICML 2026 AdaptFM Workshop preprint, [PDF](https://openreview.net/pdf?id=nYQVHA4prY)) replace dense output projection with HNSW nearest-neighbor search for top-k sampling. They report up to 82% higher batch-one CPU decoding throughput for Gemma 3 270M. The test uses FP32 on an i7-10750H CPU, short questions, and 128-token continuations. The paper reports that the index **adds 5 to 10% static output-layer memory** relative to its vectors; it does not report complete package bytes or peak process RAM. Its AlpacaEval pairwise win rates of about 45.9 to 49.1% are below 50%, despite the authors' characterization of negligible quality impact. There is no Q4_K_M, full-request CPU, or sealed multistep result. The workshop status matters: a main ICML PMLR listing was not verified in this audit.

**Break-even.** As a standalone proposal, an added graph index does not satisfy the bytes and RAM gates unless some other structure is removed. If combined with a smaller output head, let `H` be removed head bytes and `I` added index bytes plus metadata. Require `H>I` and a measured peak RSS reduction. If HNSW search cost per token is `c_i` and exact projection cost is `c_p`, the net CPU test is `(c_p-c_i)*T >` graph loading, token-count changes, and retry/check overhead for the request. Retrieval recall must be checked against exact top-k on task prompts because its approximate errors can alter a multistep trajectory. A small decisive test is to instrument the existing CPU Q4_K_M output head with exact and HNSW top-k on identical hidden states, then run the full sealed suite and package-size/RSS measurements. If the index requires FP32 copies of quantized head weights, reject it at the bytes gate before further quality work.

For the [local untied head census](../data/mixed-precision-baseline-tensor-inventory-2026-11-11.json), `|V|=151,936`, `d=1,536`, and its Q6_K payload is 191,439,360 bytes. Applying the paper's [FP32 index formula](https://arxiv.org/html/2608.27460#S3) with `M=32` gives 933,494,784 vector bytes plus 38,895,616 graph bytes, or 972,390,400 before metadata. Replacing only that Q6_K payload with this form would add about 780,951,040 bytes to the serialized package. This is **prospective arithmetic**, not an exported index or measured runtime result. A packed-vector HNSW would need a new search kernel and byte census. Even if it could reuse Q4_K vectors without FP32 copies, the nominal graph alone would consume 38,895,616 of the measured 60,166,656-byte Q6_K-to-Q4_K head saving, leaving at most 21,271,040 bytes before metadata. The released FP32 implementation therefore cannot be treated as a compression result for this GGUF reference.

### Extreme vocabulary reduction

[One Byte, One Token](https://arxiv.org/html/2611.13607v1#S4.SS2) (arXiv v1, 2026-11-10) replaces a 248,320-row embedding/output vocabulary with 384 byte/special entries in a Qwen3.8-27B hybrid model. The authors report that language-model parameters fall from 26.9B to 24.4B while the backbone remains untouched. Continued training on 4.77 GB of supervised bytes takes 178.6 hours on eight H200 GPUs, about 1,430 GPU-hours; the authors separately estimate corpus generation at about 760 local GPU-hours or 2,190 GPU-hours when external API calls are converted and included. Their [same-stack FP8 GPU efficiency table](https://arxiv.org/html/2611.13607v1#S5.SS6) reports 3 to 5 times more decode steps for comparable output, roughly one-quarter Chinese-character throughput, and 6.5 times slower prefill for 65,536 bytes of Chinese input. The paper attributes part of the prefill gap to less-tuned byte-model kernels, so 6.5 times is a deployed-stack observation, not an intrinsic tokenization constant. It also reports losses of roughly 4 to 6 points on some Chinese or instruction metrics despite gains on character-level tasks. The result has no CPU or Q4_K_M artifact and no sealed benign multistep score.

**Break-even.** Reducing vocabulary from `V` to `V'` can save roughly `(V-V')*d*b/8` bytes per untied embedding/head matrix at `b` bits, subject to GGUF metadata, tensor packing, and tying. For a token expansion `r=3...5`, decode cost per emitted step must drop by more than `1-1/r`, about 67 to 80%, just to match decode CPU time, before prefill and checks. The paper reports no such per-step reduction. A less extreme vocabulary change should be tested at matched **semantic bytes and tasks**, not equal token counts. The smallest decisive trial is an exportable same-base Q4_K_M model with a moderately reduced vocabulary, a retrained tokenizer/head, and measurements of whole-package size, peak RSS, total token inflation, full-request CPU-seconds, and sealed quality. Likely failure is that shorter head vectors save weight bytes but longer sequences enlarge KV memory and compute, while retokenization harms multilingual or rare-token tasks.

**Dynamic output-vocabulary selection has a different denominator.** [VocabTailor](https://aclanthology.org/2026.findings-acl.1418.pdf) (Findings of ACL, July 2026) keeps the full tokenizer and full input embeddings, places embeddings in CPU memory or disk-backed LMDB, and selects task-specific plus input-dependent output-head rows for GPU execution. Its headline up-to-99% reduction concerns **vocabulary-related resident components**, not the whole installed model; the full embeddings and candidate head rows still require storage. In its Qwen3-0.6B efficiency test on 100 English-to-Chinese prompts, peak accelerator memory falls from 1.17 to 0.91 GB on A100 and Jetson Orin, and from 1.11 to 0.85 GB on M1 Pro, while time to first token rises on all three. The tested information-extraction output vocabulary is just 105 dynamic tokens, a particularly narrow extractive setting. Code completion retains 11.18% of output vocabulary with 53.87% Pass@1 versus 54.10% original on its public set, but these are separate from the Qwen efficiency timings. No Q4_K_M CPU-only implementation, full installed-byte saving, host peak RSS, full-request CPU-seconds, or sealed multistep quality is reported. A CPU-only port would have no accelerator memory tier to offload from; it must demonstrate actual physical head removal or compressed storage to pass `B` and `R`, then account for per-prompt selection and cache I/O in `C`. The likely failure is that merely relocating weights saves VRAM while increasing host RAM or disk footprint.

**Withdrawn output-codebook lead.** The [arXiv record for VQ-Logits](https://arxiv.org/abs/2505.10202) says the authors withdrew it on 2026-09-18 for lack of sufficient experiments and detailed format alignment. Its earlier 99%-of-output-layer parameter and 6-times-logit-computation claims are not evidence for this study. Its mechanism of mapping several output tokens to a shared code vector also needs an explicit test of how token identity is recovered, especially on rare tokens and multistep tasks. Exclude it from candidate ranking unless a new reproducible implementation resolves that concern and passes the same CPU gate.

## Parameter sharing and adaptive compute: a strict compute warning

Looping uses one set of weights repeatedly. It can lower stored bytes compared with a model that stores separate layers for the same effective depth, but each invocation still consumes CPU work. A direct result from [Shared Memory in Looped Transformers](https://arxiv.org/html/2610.02383) (arXiv v1, 2026-10-01) makes this tradeoff unusually clear. Its 150M to 1B models with five recursions reduce context-memory use by 76 to 79% and improve FineWeb-Edu validation perplexity by 1.12 to 1.82 relative to same-parameter standard Transformers. In the paper's H100 BF16 Appendix F, a batch-one decoding step of the ordinary looped model takes approximately 2.3, 3.4, and 5.7 times as long as the standard model for two, three, and five recursions; the shared-memory version is another 8 to 12% slower than ordinary looping at equal batch. Its high peak batch throughput comes from fitting more concurrent sequences, not from making a single request cheaper. These are GPU latency data, but the repeated-compute obligation is architectural. The paper does not report Q4_K_M CPU-seconds, complete deployed bytes, or sealed multistep task quality.

**Break-even and decisive test.** If a looped model stores `1/r` as many backbone weights but runs `r` repeats per token, it can pass `B` and possibly `R`, while `C` requires a per-repeat CPU cost below `1/r` of the unshared equivalent, or enough saved tokens/retries to overcome the repeated work. A direct trial should use a native CPU runtime, same-base Q4_K_M-equivalent stored weight budget, batch one, complete prompts and outputs, and paired task outcomes. Compare loop counts 1, 2, and 3 plus a no-loop model that uses the same stored bytes. Measure actual whole-process memory at the task's context, rather than analytic KV alone. The likely failure is repeated weight reads and KV attention causing CPU-seconds to rise despite lower resident weights.

[How to Loop Your Transformer](https://arxiv.org/html/2610.40325) (arXiv v1, 2026-10-29) explicitly separates stored-parameter, training-compute, and inference objectives. Its Parallel Loop Transformer variant rearranges loops so their inputs can be processed as a batch, but the paper says it does not remove loop computations and does **not measure wall-clock decoding latency or throughput** for this variant. It also reports MMLU and MMLU-Pro near chance at its 1B scale and excludes them from the eight-task headline mean. Hence it cannot establish quality or CPU efficiency against the proposed reference. [LoopSpec](https://arxiv.org/html/2609.17184) (arXiv v1, 2026-09-15) reports up to 6.83 times faster decoding than ordinary looped autoregressive generation on an RTX PRO 6000 GPU in BF16, with prompt prefill excluded. This is a useful runtime idea for an already-looped model, but there is no CPU experiment or comparison with a same-base non-looped Q4_K_M reference. [LoopFold](https://arxiv.org/html/2610.35556) (arXiv v1, 2026-10-26) moves some recurrent stages into parallel work and explicitly reports higher FLOPs and KV requirements, so lower sequential latency alone is not evidence of lower CPU-seconds or peak RAM.

[Improving Test-Time Scaling with Adaptive Looped Transformers](https://arxiv.org/html/2609.35748) (arXiv v1, 2026-09-28) finds that fixed-depth looping spends iterations on tokens that often do not benefit and trains a token-level iteration decider. It reports an AIME accuracy-compute slope improvement and a roughly 3.4 point peak advantage at matched decoding FLOPs in its comparison. This leaves open whether the control overhead, prefill, output length, and retries permit a smaller **full-request CPU-seconds** total on benign multistep tasks. A smallest test is to replay the same prompts with a fixed maximum-depth loop and an adaptive decider, logging actual iteration counts, total CPU-seconds, and paired task success; it must also compare the non-looped Q4_K_M reference. Failure risk is gating errors on rare, consequential steps and compute spent deciding to skip compute.

**Early exit is not free model compression.** [Diminishing Returns of Early-Exit Decoding](https://arxiv.org/html/2603.23701) (arXiv v1, 2026-03-24) evaluates 100 prompts per benchmark and reports very small oracle skip fractions at a maximum five-point accuracy loss for current dense models: on Qwen3-8B, 0.10% for MMLU and 0.62% for GSM8K, versus 7.26% and 4.48% for GPT-OSS-20B. Its oracle computes the final-layer logits to choose the exit, so the skip fractions are hypothetical work savings, not measured speedup of a deployable predictor. An early-exit head also retains the full backbone and therefore cannot by itself pass package-byte and resident-weight gates. A valid paired test would train a deployable exit predictor, include its CPU cost, and show fewer actual layer operations without worsening sealed multistep success. It would have to be combined with physical model reduction to lower stored bytes. Likely failure is that hard steps need late layers, while false early exits cause downstream errors and retries.

## Low-bit kernel caution from an alternative architecture

**Lossless archives do not yet solve the resident CPU problem.** [Rothstein and Rothstein](https://ijcaonline.org/archives/volume187/number120/rotem-ijca-2026-a71cdd2650e6.pdf) (International Journal of Computer Applications, June 2026) measured byte-exact coding of BF16 and Q4_K_M files with source-model train/test splits. Their five complete GGUF test files achieve a reported 1.041 to 1.045 times ratio with a five-stream transform plus zstd-19, versus 1.022 times for whole-file zstd-19; the ratios are labeled *per-model amortized* in Table 8. This is roughly 3.9% to 4.3% fewer archive bytes, **not** a resident Q4_K_M model that llama.cpp can execute directly. The paper reports single-core x86 decompression throughput around 110 MB/s for the transformed GGUF and defers the full multi-model inference-sanity sweep; it does not measure cold total RAM or full-request CPU-seconds after restoration. Its 1.076-times Q4_K tensor-stream “ceiling” applies to a specified within-superblock coding class, not all lossless codecs or complete GGUF files, while its adjacent-layer correlation null covers only scalar-affine same-role BF16 pairs in two Qwen2.5 models. Its public reproduction URL returned an authorization error in this audit, so the released code and raw rows were not independently replayed. The useful next check is an exact roundtrip plus a cold-load benchmark on our pinned GGUF and host, including decoder bytes and peak RAM. Any archive that must be fully unpacked before inference can lower distribution bytes without lowering the steady resident weights or CPU work; a fused runtime would need its own four-gate result.

**Same-model GGUF control and phase reversal.** [Which Quantization Should I Use?](https://arxiv.org/html/2601.14277) (arXiv v1, 2026-01-11) quantizes one Llama-3.1-8B-Instruct checkpoint into 13 GGUF formats with llama.cpp b7600 and measures quality and CPU throughput on dual Xeon Platinum 8488C processors (96 physical cores). Its Q4_K_S file is 4,467.80 MiB versus 4,685.30 MiB for Q4_K_M, a 4.64% reduction against the Q4_K_M file. The unweighted five-benchmark means are 69.17 and 69.15, respectively, but individual scores differ: IFEval 80.26 versus 79.06 and TruthfulQA MC2 53.40 versus 54.49. WikiText-2 perplexity is 7.62 versus 7.56. Those means cannot establish multistep noninferiority. More tellingly, Q4_K_S processes a 512-token prompt at 92.52 versus 87.70 tokens/s but generates 128 tokens at 4.65 versus 5.12 tokens/s. A two-objective file-size/mean-score Pareto claim in the paper omits this decode reversal. Under the *illustrative* linear phase-time model `T=P/pp+G/tg`, Q4_K_S only has lower phase time when prompt/generated-token ratio `P/G` exceeds about 33.2; the paper's 512/128 setting has ratio 4. This calculation is a screening heuristic, not a measured whole-request result. The source does not provide complete installed bytes, process or cgroup peak RAM, CPU-seconds, output-token changes, or sealed multistep tasks. It motivates including Q4_K_S and Q3_K_M as inexpensive format controls before crediting a new architecture with compression gains.

**Phone CPU Q4_K_M versus IQ4_XS is a direct tradeoff, not a four-gate win.** [Ehsani et al.](https://arxiv.org/html/2603.26603) (arXiv v2, 2026-05-20) run eight models in both formats with `llama.cpp` CPU-only, eight threads, on one Samsung Galaxy S25 Ultra. Their [pinned aggregate table](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/data/aggregated/final_results.csv) gives Qwen2.5-1.5B-Instruct Q4_K_M versus IQ4_XS: 4.37 versus 4.61 s total inference latency, 1,373 versus 1,162 MiB reported peak memory, 92.87 versus 93.42 J, and comparative Overall G-Eval 0.69 versus 0.66. The smaller format is slower on seven of eight model pairs in this table, while its reported peak memory is lower on all eight. This is a useful counterexample to equating fewer model bytes with lower compute or energy. The [pinned method](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/docs/METHODS.md#L60-L66) uses one fixed summarization prompt, exactly 100 generated tokens, a warm-up and 30 timed repeats; these are hardware repeats, not 30 independent quality tasks. The [memory statistic](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/docs/METHODS.md#L167-L172) is parsed from `llama-cli`'s `total = model + context + compute` line, not process RSS or cgroup peak; its 1,059 versus 848 MiB `model_weight` values are not complete GGUF file sizes. [Quality scoring](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/docs/METHODS.md#L180-L210) uses a single evaluated output prefix per configuration and one GPT-5.2 comparative call per criterion across all 16 responses in fixed order. Wall latency is not CPU-seconds. The [reproduction guide](https://github.com/eziyoo/LLMs-on-Devices/blob/4090c3a3687fa4e3ea6fb1c1bea45dafeb1f704c/docs/REPRODUCE.md#L198-L233) describes same-source quantization as an option, but the aggregate rows do not identify checkpoint and artifact hashes. This one-phone, one-prompt result neither measures sealed dependent-step success nor verifies all four gates on the same artifact.

**Sub-3-bit codebooks have a CPU result, but the comparison is FP32.** [AQLM](https://arxiv.org/html/2401.06118) (arXiv v4, 2024-09-11) reports a 2-bit additive-codebook runtime on an eight-core Intel i9: generating 128 tokens from scratch on Llama 2 7B is 6.961 tokens/s with two 8-bit codebooks versus 3.106 tokens/s for FP32, and a single `gate_proj` matrix-vector multiply is 2.75 times faster. Its average bit count covers quantized weights and excludes parameters retained in floating point; Appendix H models codebooks, codes, and scales, rather than a complete installed package. The paper's strongest fine-tuned 2.02-bit 7B still scores 5.3 on eight-shot GSM8K versus 14.6 for FP16, while 13B scores 13.8 versus 24.3. This is a concrete quality warning even before comparing with Q4_K_M, whose behavior may differ. AQLM provides no Q4_K_M CPU throughput or package/RSS/full-task measurement and does not show quality noninferiority. Its smallest useful replication is a 2-bit AQLM arm in the same-host format sweep, but kill it if its exported file fails the byte gate or the early public math screen fails before expensive sealed testing.

[Spike-Aware INT8 Execution for Spiking Language Models on Commodity CPUs](https://arxiv.org/html/2606.03026) (arXiv v2, 2026-09-07) reports a native C++ runtime for a bespoke 874M spike-gated language model. On an early checkpoint, INT8 weight storage was 1,087.4 MiB versus 3,355.2 MiB FP32 and single-thread decode was 23.31 versus 9.82 tokens/s. Yet applying INT4 to its dense projections saved another 17.4% of weight storage while **reducing decode throughput by 46.6%**. This is a direct counterexample to assuming fewer bits automatically lower CPU work. It has no same-base Q4_K_M reference, complete package comparison, or sealed multistep quality result, and the model architecture differs from the proposed reference. The useful experiment is a per-tensor low-bit sweep with real CPU kernels, recording packed bytes, effective bytes read, unpack cost, and full-task CPU-seconds before choosing a precision solely by its nominal bit width.

**CPU kernel gains can leave memory unchanged or worse.** [CodeQuant](https://arxiv.org/html/2604.10496v2#A5) (ICLR 2026; arXiv v2 revised 2026-08-14, first posted 2026-04-12) combines MoE outlier smoothing, weight clustering and a T-MAC lookup-table kernel. Its Appendix Table 9 uses a Xeon w7-3445 with 20 threads. Against a quantized llama.cpp A8W4 control, CodeQuant's reported memory and latency are 4.1 GB/13.3 s versus 4.1 GB/15.0 s for Phi-mini-MoE-Instruct, 8.9 GB/14.2 s versus 8.8 GB/17.1 s for DeepSeek-V2-Lite, and 16.5 GB/15.9 s versus 16.2 GB/20.1 s for Qwen3-30B-A3B. Thus latency improves but **memory does not fall** in any of the three quantized-control comparisons. Its advertised 4.15-times CPU speedup is against BF16, not A8W4. Section 4 specifies 512-token prefill, 128-token decode and batch 16 for the GPU simulator, then separately introduces the real CPU benchmark; Appendix A.5 does not establish that this workload also governs its CPU latency. Nor does it define the memory statistic as a cold process or cgroup peak. Latency seconds are wall time, not full-request CPU-seconds, and no complete installed bytes or sealed dependent-step quality are supplied. The [released repository](https://github.com/SAI-Lab-NYU/CodeQuant) describes fake-quantization task evaluation, so its public accuracy path should not be assumed to validate the T-MAC artifact end to end. CodeQuant is useful kernel precedent, but its own quantized-control table is a counterexample to inferring a four-gate win from speed alone.

**A laptop working-set study cannot close the joint gate.** [Song et al.](https://arxiv.org/html/2505.15030v5) (arXiv v5, 2026-03-16) measure Windows process peak working set with `psutil` on an i7-1360P laptop, but run five capability benchmarks on a separate GPU workstation and report warm prefill/decode throughput for synthetic 1,024-token outputs rather than completed-request CPU-seconds. Their Table 1 gives Qwen2.5-1.5B GSM8K 60.80% in FP16 and 52.77% under `q4_k`; this is a short-task comparison, not a Q4_K_M same-base noninferiority test against our deployed file. No complete artifact hashes or file sizes are reported. The source also contains unresolved denominator inconsistencies: five selected formats in Section 3.1 versus eight Table 1 columns, 1,024 output tokens in the method versus 1,000 in Figure 5, and conflicting q2_k/FP16 throughput ratios between Table 2 and its explanation. Its 7B `q4_0` peak working set of 6,910 MB exceeds its `q5_0` 4,837 MB, an explicitly noted anomaly rather than a basis to assume monotone resident memory. The linked anonymous code host returned an access challenge during this audit. Exclude its aggregate efficiency claims from any four-gate conclusion; the useful lesson is to measure the exact deployed artifact on one CPU host.

**Reasoning-aware calibration has a single-sample caveat.** [CodeQuant2](https://arxiv.org/html/2611.09868v1#S4) (arXiv v1, 2026-11-06) extends CodeQuant with learned rotation/scaling, matrix-level cluster allocation, and calibration from the first 256 tokens that a full-precision model generates on GSM8K *training* questions, mixed 9:1 with WikiText2. Its Qwen3-4B-Thinking A4W4 [cumulative ablation](https://arxiv.org/html/2611.09868v1#S4.SS3) raises a six-benchmark average from 0.664 to 0.770; this is an ablation within its own GPU representation, not a Q4_K_M comparison. More cautionary, its separate calibration-segment Table 6 raises an eight-metric average from 0.745 without decoding samples to 0.754 with first-segment samples, while **AIME25 pass@1 falls from 0.546 to 0.517**. The average includes pass@8 for AIME25 and AIME26, so it can improve even when one attempt gets worse. Calibration on all 768 available decoded tokens lowers the average to 0.708. The final A4W4 AIME25 pass@1 remains 0.563 versus the BF16 model's 0.688; its AIME25 pass@8 0.800 versus BF16 0.733 is a different, eight-sample statistic with additional inference cost. A single H100 is used for roughly 75 minutes of reported fine-tuning stages, and speedups use a custom CUDA lookup kernel on A6000, L40s, and A100 against BF16. The system evaluation profiles GPU *decode* latency using representative prompt/decode lengths, not CPU-seconds for completed requests. The [official release at commit eaf112c](https://github.com/SAI-Lab-NYU/CodeQuant2/blob/eaf112cb1da3a7e6010006c7f5341307c2c9768b/README.md#L220-L302) writes a dense Hugging Face checkpoint for evaluation and runs vLLM with an activation fake-quantization plugin. Its standalone packed CUDA kernel handles 16 centroids per channel, while adaptive cluster allocation can choose 8, 16, or 32; the README says 8 and 32 require a separate representation or kernel. Thus the released task evaluation and packed-kernel path do not demonstrate performance and quality on one deployable low-bit artifact. This is a reproducibility limit of the release, not evidence that the paper's experiments used the same scripts. No complete GGUF package, cold CPU peak, same-base Q4_K_M cost, or sealed dependent-step success is reported. For a local calibration hypothesis, freeze a single-attempt quality gate and full-request CPU accounting before selecting early-token data; reject a method that improves pass@8 or perplexity while failing that gate.

**Search-budget accounting.** [Capability Scaling-Down Laws](https://arxiv.org/html/2610.02462) (arXiv v1, 2026-10-01) fits capability-loss curves across pruning, quantization, and distillation. On Pythia and OLMo-2 panels, a compact pruning curve fitted on half the measured densities stays within 0.020 nats per token of the full-grid fit on math/code, with coefficients refitted for each model setting. This could reduce the number of expensive exploratory builds, but its prediction target is token loss, not multistep task success or CPU cost. Its detailed byte audit shows why exact accounting matters: changing from nominal parameter ratios to stored byte budgets alters candidate feasibility in 176 of 272 selection cells, largely because sparse indices and small-model embedding shares were omitted from nominal ratios. These figures concern the authors' FP16 and grouped-rounding formats, not Q4_K_M. The smallest local replication is to fit a small loss curve on half of a physically pruned Q4_K_M grid, predict held-out loss, then test whether its candidate selection actually chooses a `B/R/C/Q` winner. Reject this surrogate if it misses a quality cliff or selects a candidate whose exported package breaks the byte budget.

## Native ternary packing: a genuine CPU result with a quality gap

**Sparse activation can lose the deployment budget.** [Alfarizy et al.](https://arxiv.org/html/2606.21428) (arXiv v3, 2026-07-09) compare one Q4_K_M OLMoE-1B-7B (1.3B active, 6.9B total parameters) with three *different* dense models through llama.cpp on an M2 Pro and an 8 GB Jetson Orin Nano. Each device/model cell pools 15 prompts with three repetitions (45 runs); the reported generation throughput, GGUF file size, and polled process-tree peak RSS are all on the same artifacts. The MoE file is 4.21 decimal GB versus 0.81 GB for Llama-3.2-1B; median generation rates are 116.2 versus 130.7 tokens/s on M2 and 23.0 versus 33.0 on Jetson; peak RSS is 4.49 versus 0.98 GiB on M2 and 8.01 versus 1.87 GiB on Jetson. The paper says the Jetson completes above its physical 8 GB ceiling by using default zram swap, so this is not proof of an acceptable unswapped RAM footprint. Sparse *active* parameter count did not translate into a smaller or faster artifact in this comparison. These are Metal/CUDA-offloaded runs (`-ngl 99`), not CPU-only; the dense controls differ in training and capability; the paper measures output throughput and wall time including load, but not completed-request CPU-seconds or paired benign quality. Its result is a deployment warning against equating active parameters with installed bytes or cold RAM, not a general disproof of MoE or a same-base four-gate comparison.

[Sherry](https://aclanthology.org/2026.acl-long.513/) (ACL 2026, published July 2026) combines 3:4 structured ternary weights with a five-bit code per four weights, giving 1.25 nominal bits per weight. Its temporary training residual anneals away before deployment. On an Intel i7-14700HX using BitNet.cpp, its 3B variant is 712.40 MB and decodes at 45.55 tokens/s, versus a 1.67-bit TL2 variant at 846.01 MB and 38.80 tokens/s. At 0.7B, the comparison is 205.50 versus 233.44 MB and 148.27 versus 116.83 tokens/s. These are reported artifact and decode gains **against other ternary formats**, not against Q4_K_M. The 3B file saving is 15.8% while the nominal bit saving is 25%; scales, non-ternary tensors, and packaging dilute the headline. An Apple M4 Pro llama.cpp test also beats TQ1_0 decode speed but falls below TQ2_0, indicating that its kernel advantage depends on the comparison and execution engine.

The quality experiments are on LLaMA-3.2 1B and 3B, trained for 10B tokens and scored on five zero-shot short-form benchmarks. Sherry's mean is 0.519 for 1B versus 0.558 BF16 and 0.567 for 3B versus 0.636 BF16. The CPU speed table uses 0.7B and 3B **BitNet variants**, so the quality and speed rows do not jointly evaluate one complete deployed model. It reports no peak RSS, whole-request CPU-seconds, or sealed multistep quality. The value is proof that a CPU-aligned low-bit representation can improve both stored bytes and decode throughput within a ternary family; it does not show that a same-base Q4_K_M deployment can be beaten on all four gates.

**Break-even and smallest decisive test.** Let `f` be the fraction of the Q4_K_M package occupied by tensors eligible for Sherry-like packing, `q` the mean Q4_K_M bits per eligible weight including its scales, `h` the extra packing/runtime overhead as a fraction of the current package, and `r` the semantic output-token inflation. Byte improvement requires `f*(1-1.25/q) > h`. CPU improvement requires measured full-task per-step CPU cost, including unpacking, to fall below `1/r` of baseline after prefill and retries. Build one same-base Q4_K_M reference and a 3:4 ternary-trained candidate with the same tokenizer and executable runtime on one CPU; report complete package bytes, peak resident RAM, full-task CPU-seconds, and paired sealed multistep success. Add native 1.67-bit ternary as a mechanism control. Likely failure is a quality deficit versus Q4_K_M or unpack overhead that reverses the decode gain on another CPU; Sherry's tables do not rule either out.

**Export fidelity is a separate gate.** [Lost in the bf16 Cast](https://arxiv.org/html/2610.07853) (arXiv v3, 2026-10-27) audits three ternary fine-tuning and export paths. At particular low-learning-rate endpoints, the documented export drops strict greedy GSM8K accuracy from 58.79% to 0.78% for Falcon-E-1B-Base and 36.13% to 0.39% for BitCPM-CANN-0.5B. Capturing the training quantizer's codes directly or projecting inputs so the exporter produces those codes meets the authors' four-point noninferiority criterion in their tested settings. The failure is recipe-dependent: the paper reports a Falcon-E rate and longer recipe without a detected export loss. The CPU bitnet.cpp replication covers two models, 512 development rows, and a shared host, with no throughput or memory claim. This is not evidence that ternary compression fails in general. It is a strong requirement to compare the **actual serialized candidate** with the online training model, including code census and sealed task replay, before recording a recovered quality score. A smallest check records trained codes, exported codes, and task outcomes for each checkpoint; reject a candidate if the deployed file silently reverts gains. The likely failure is quantization-threshold rounding during a BF16 export even when online validation looks good.

**Post-training ternary packing can disappoint on whole-model bytes.** [Scaling Post-Training Ternarization to Qwen3-8B](https://arxiv.org/html/2609.09240) (arXiv v1, 2026-09-08; a single-team technical report) targets Qwen3-8B's 252 attention and MLP projections and reports about 1.64 effective bits per targeted linear weight. Embeddings, output head, norms, activations, and KV remain FP16. The packed artifact is 8.24 GiB after a 16.9 GB fake-quantized checkpoint, and eight short-form tasks average 64.6% versus 72.4% FP16. Its direct packed execution reaches 15.52 tokens/s in 7.35 GiB on an RTX 5070, while one prototype packed GEMV is 4.6 times slower than cuBLAS FP16. There is no Q4_K_M artifact, CPU implementation, or sealed multistep comparison. The report is valuable for accounting: 1.64 bits on selected weights does not imply a 1.64-bit complete file, and a fake-quantized checkpoint is not a deployable compression result. A decisive test would include all tensor dtypes in the packed byte inventory and compare the *same model* as Q4_K_M before further investment. Likely failure is uncompressed embeddings/head or metadata erasing theoretical savings while quality still drops. Its single-seed, 500-row-per-task design and local FP16 perplexity mismatch versus its external reference limit generality.

**Native training is real, but the reported CPU comparator is too weak for this gate.** [BitNet b1.58 2B4T](https://arxiv.org/html/2504.12285) (arXiv v2, 2025-04-25) trained a 2B ternary model from scratch on 4T tokens and released a CPU GGUF and bitnet.cpp. Its table reports 0.4 GB of *non-embedding* memory and 29 ms CPU time per output token; the [released GGUF file](https://huggingface.co/microsoft/bitnet-b1.58-2B-4T-gguf/tree/main) is 1.19 GB. The file is roughly three times the headline non-embedding figure, a reminder that the table's denominator omits large tensors. In the paper's three-task INT4 comparison, BitNet averages 55.01 versus 52.15 for Qwen2.5-1.5B GPTQ INT4 and 51.17 for AWQ INT4, but MMLU is 53.17 versus 58.06 and 57.43. These are different bases, model sizes, training corpora, activation schemes, and runtimes, so they cannot establish a same-base Q4_K_M noninferiority result. The related [bitnet.cpp CPU report](https://arxiv.org/html/2410.16144) (arXiv v2, 2024-10-23) gives large speedups versus **FP16 llama.cpp**, not Q4_K_M; its lossless token-sequence check uses a separate 700M BitNet model. Thus native low-bit training merits a route to test, but the published memory, per-token latency, and public short-task score do not prove lower complete bytes, process/cgroup peak RSS, and full-request CPU-seconds at retained multistep quality against the target comparator. The 4T-token training budget is also a substantial feasibility cost that must be stated separately from inference resource savings.

**Runtime correctness must be checked before speed comparisons.** An independent October 2026 [lowbit-atlas audit](https://github.com/matheus-c-feitosa/lowbit-atlas) pins model file hashes, runtime commits, CPU classes, flags, and exact token IDs in its [method](https://github.com/matheus-c-feitosa/lowbit-atlas/blob/main/METHOD.md). On the official BitNet-b1.58-2B-4T GGUF, its x86-64 AVX2 run of bitnet.cpp `0b341e5` gives WikiText-2 perplexity 113.33 versus 18.79 for a float32 Transformers reference on the **same token IDs**; changing the FFN activation from SiLU to the model's ReLU squared yields 18.87. The underlying graph mismatch was independently filed as [BitNet issue #588](https://github.com/microsoft/BitNet/issues/588) on 2026-07-19, with a separate pinned reproduction. The atlas also observes that a smaller PTQ1_0 Ternary-Bonsai-2 27B file processes prompts about four times slower than PQ2_0 in Prism on AVX2, where the former lacks a fast path. These are important implementation confounds, not quality or CPU superiority claims for a new model. The atlas is a volunteer, non-peer-reviewed test of selected files, short WikiText-2 windows and `llama-bench` phases, not complete installed bytes, peak RAM, full requests, sealed tasks, or a same-base Q4_K_M reference. Its own method notes a missing tokenizer preprocessor in the GGUF that changes token count by about 16% relative to default Transformers tokenization; the matched-ID comparison is what makes the cited perplexities interpretable. Any rank-3 candidate should first establish native runtime semantic parity on identical tokens, then test its complete resource and task gates.

**A faster low-bit kernel needs a contemporary comparator.** The author of [llama.cpp Q2_0 VNNI PR #26348](https://github.com/ggml-org/llama.cpp/pull/26348) initially reported roughly threefold gains in Q2_0 `llama-bench` prompt and decode phases against the then-scalar x86 path on an EPYC 9645. After [AVX2 Q2_0 dot product commit `0a731cc`](https://github.com/ggml-org/llama.cpp/commit/0a731cced9ed826349838333a767ccae63164c2c) landed in upstream llama.cpp, the author's October 21, 2026 clean revision comparison found VNNI plus VBMI versus AVX2 at 1.30 to 1.33 times prompt throughput across four Bonsai sizes, and 0.97 to 1.22 times decode throughput. The 1.7B decode mean was slightly lower, with large run variance. The PR remained open at the November 12 audit. This is a useful near-counterexample to treating an early 3-times CPU kernel gain as durable: much of that gain disappeared when the baseline gained a different optimized kernel. These are author-reported phase rates for Q2_0 on one host, with no Q4_K_M comparator, complete package, peak RAM, or full-task quality measurement. Pin both runtime revisions and compare against the *best available* CPU path for the reference and candidate.

**The 2-bit quality cliff is largest on generation, even after a better representation.** [Sukthanker et al.](https://arxiv.org/html/2610.28537) (arXiv v1, 2026-10-20) evaluate vector-codebook quantization at 2.26 to 2.31 effective bits per weight, including codebook overhead, against scalar and trained baselines. Their Table 4 selects the best calibration recipe separately for question answering and generation. Phi-4-mini's average QA is 71.0 BF16 versus 63.3 YAQA, while its generation mean is 73.2 versus 37.4; Llama-3.1-8B is 73.1 versus 65.7 QA and 42.9 versus 26.6 generation. Qwen3-MoE is a more favorable generation case, 61.8 BF16 versus 62.4 YAQA, showing that the loss is model dependent. These are **best-of-grid public scores**, not a prespecified same-base Q4_K_M task comparison. In a separate 40-problem Qwen3-30B-A3B MATH-500 analysis, BF16, 4-bit, and 2-bit accuracy are 0.675, 0.650, and 0.450; mean thinking-token counts are 4,928, 5,265, and 5,900. More tokens can erase a per-token cost advantage. Short codebook-only recovery improves some models but Llama-3.1-8B's QA falls in every long-recovery arm in Table 8. Their prospective calibration/recovery interaction check held on Qwen3-8B, but on prompt-independent MBPP and MATH-500 the interaction is clear only for Phi-4-mini. Screening `k` calibrated bases requires `k` quantizations, `2k` recoveries of about 100 PFLOP each for a 4B model, and `3k` evaluations. The preprint promises code, Hessian mixtures, and checkpoints upon acceptance, so the present paper alone cannot reproduce its exact quantizers. It reports neither a native GGUF CPU kernel nor complete package bytes, process/cgroup peak, full-request CPU-seconds, or sealed multistep quality. A low-bit route should first beat a Q4_K_M CPU reference on the **deployed** representation and count generated tokens and retries, not infer task efficiency from effective bits per weight.

**Sub-1-bit factorization is a useful quality stress test, not a retained-capability result.** [LittleBit](https://arxiv.org/html/2506.13771) (NeurIPS 2025; arXiv v5, 2026-02-05) replaces dense matrices with binarized low-rank factors. Its Llama2-13B 0.1-bit footprint is estimated at 0.84 GB versus 26.06 GB FP16, with the embedding and output head left FP16; the paper's 11.6-fold speedup is an A100 CUDA MLP-kernel comparison with FP16, not a CPU Q4_K_M request. [LittleBit-2](https://arxiv.org/html/2603.00042) (ICML 2026; arXiv v2, 2026-05-03) improves factor initialization with latent rotation and Joint-ITQ at no stated change to the inference graph. Its table makes the quality loss visible: for Llama-3 8B, average accuracy on five zero-shot tasks is 72.97% FP16, 57.33% at 1.0 bit, and 41.64% at 0.1 bit. At 0.1 bit, its stated model-body footprint is 0.1 GB, but the total with fixed FP16 embedding/head is 2.2 GB; for Gemma-3 27B, the same five-task average is 79.48% FP16 versus 47.06% at 0.1 bit. These are estimates of model-weight footprint and public short-form scores, without a released CPU runtime that establishes process/cgroup peak RAM, full-request CPU-seconds, or sealed multistep quality. The large measured quality gaps make 0.1-bit a poor immediate choice for a strict noninferiority gate despite the impressive body compression. A less extreme rank and a native CPU kernel would be separate hypotheses to test.

## New checks on trajectories and equal-byte controls

[Li et al.'s dependent-step stability study](https://arxiv.org/html/2610.06404v1) is a bounded training lead, not a deployment result. Its Qwen-1.5B experiments use five 10-node CLRS-Text algorithms and two 8-variable LEGO variants, each with 2,000 training, 200 validation and 200 test examples, averaged over three seeds. Table 1's trained method beats the best listed baseline by 2.61 **percentage points** on the unweighted seven-task mean; the paper states 3.5% average, which is consistent with an aggregate *relative* improvement but does not name that denominator. Table 3's Bellman-Ford 4-bit 80.3% versus 32-bit 75.3% is task-specific training, not evidence that post-training Q4_K_M or arbitrary low bits improve reasoning. All five graph tasks fall below 25% final-answer accuracy at 20% longer inputs. The claimed Jacobian error bound is poorly calibrated across architectures: roughly 8 times the measured loss gap for Qwen-1.5B and 10^5 to 10^6 times for Llama-1B/Gemma-2B. The released [DFS](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/scripts/train_clrs_text/quantized_training/train_lora_quant.sh#L23-L29), [BFS](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/scripts/train_clrs_text/quantized_training/train_lora_quant_v2.sh#L23-L29) and [LEGO](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/scripts/train_lego/train_cyclic_ours.sh#L8-L20) quantized-training launchers select `--quant_training_mode lora` with BF16 training. In that [pinned code path](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/src/quantization/quant.py#L438-L458), only `lora_A` and `lora_B` linear layers are replaced by simulated quantizers; [full-model quantization](https://github.com/VirtuosoResearch/Multi-step-reasoning-experiments/blob/0dbd4f415bac7df5d989f4696938c4198113d08d/learning-algorithms/train_clrs_text.py#L432-L442) is a separate mode. These examples do not prove which exact command produced every reported table cell, but they prevent interpreting the released LoRA recipe as a 1–4-bit full-weight package or a measured CPU deployment. A decisive local test would hold the base, complete exported bytes, training tokens and task split fixed; compare training with quantized adapters plus step subsampling against each component alone on isolated primitives, independent batching and dependent chains, then measure cold complete-package bytes, process/cgroup peak and full-request CPU-seconds. A gain limited to its seven synthetic task families, or a failure on held-out topology groups, would reject a general composition-retention claim.

[Alimaskina et al.](https://arxiv.org/html/2606.02011v1) provide a direct warning against judging low-bit inference by tokens per second. Their 2-bit process-degraded regime generated far longer reasoning traces than FP16. Their Table 4's 0.23/0.22-times FP16 batch-1/batch-8 speed estimates combine measured A100 decode throughput with trace lengths. They are not measured whole-request CPU timings. Loop rescue can recover some quality and speed, but a fallback that loads FP16 weights must charge the extra checkpoint to complete bytes and peak memory. A local experiment should report generated tokens, loops, stop failures, retries, final success, and CPU-seconds for the entire request.

[Mehboob et al.](https://arxiv.org/html/2611.02368v1) show that similar final coding-agent scores can hide changed solve paths. They test 115 Easy and Medium OJBench Python problems over three seeds with a vLLM/executor scaffold; Hard problems are excluded because every arm solves zero. For Qwen2.5-Coder-32B, BF16 final success is 13.91% versus 10.72% AWQ and 11.01% GPTQ, with no statistically significant difference under their tests. This absence of significance does not establish noninferiority to BF16 or Q4_K_M. The paper does not measure full-request latency or memory. Our sealed test therefore needs a prespecified noninferiority margin, power, per-step failure taxonomy, and cost per completed task.

[Hu and Ramachandran](https://arxiv.org/html/2609.01587v1) are a difficult control for selective high-bit protection. In eight compatible models, the +0.146 effective bits/weight group-128 global RTN arm recovers 21 to 52 percentage points more of the 4-bit-to-8-bit CORE score gap than the best whole-layer 8-bit repair at a matched first-order *weight-only* budget. Qwen3-8B is 76.6% versus 54.9% gap recovery. This is neither a 21 to 52 point raw accuracy gain nor an exact complete-package comparison. The layer choice is oracle-ranked on the same scoring set, and the paper uses one A100 MIG, public short tasks, and no GGUF CPU measurement. A proposed local allocator must beat a globally finer granularity or uniformly lower-error quantizer at matched **serialized complete bytes**, not only a crude uniform-bit baseline.

[Hu and Adatiya](https://storage.googleapis.com/gweb-research2023-media/pubtools/1046363.pdf) supply a CPU-only llama.cpp check on the **request lifecycle**, including serverless cold starts. On Cloud Run, loading is 55% to 70% of cold-start wall time for five small Q4_K_M models; for LLaMA-3.2-1B, Q4_K_M versus Q8_0 cold start is 14.8 versus 20.2 s on 8 GiB. The 4 GiB and 8 GiB tiers have one and two vCPUs, so tier differences cannot isolate a RAM effect. On the 8 GiB tier, the paper reports Q8_0 warm throughput of 12.8 tokens/s versus Q4_K_M 12.0, an example where denser weights can decode faster because kernel cost matters. The quality comparison is WikiText-2 perplexity over about 50K tokens, while requests use about 16 prompt tokens and at most 50 output tokens. The 5.8 GB multi-model image contains all GGUF variants, so its complete installed-byte denominator is not the per-format file. The study measures wall time, not full-request CPU-seconds or process/cgroup peaks. For our first-host protocol, report both cold and warm CPU-seconds and bytes for the actual single-model package, then keep the lifecycle fixed between candidates.

[RAMP](https://arxiv.org/html/2603.17891) is a closer GGUF precedent than a generic mixed-precision paper: it maps learned layer bits to Q3_K_M, Q4_K_M, Q5_K_M, and Q6_K presets and reports 3.68 GB and 5.54 WikiText-2 perplexity versus 3.95 GB and 5.61 for Q4_K_M on Llama-2-7B. Its four short commonsense-task mean is 63.6% versus 62.4%. The paper's CPU platform table is explicitly representative data from public llama.cpp benchmarks, not paired CPU measurements on the exported candidate and reference. It reports no exact tensor census, full package inventory, process/cgroup peak, full-request CPU-seconds, or sealed multistep result. No code or candidate artifact link appears in the paper. A recipe name is not an exact tensor type: [llama.cpp's quantizer](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-quant.cpp) maps the Q4_K_M file preset to a default Q4_K tensor type and can promote selected tensors. This is an additional reason to inventory the actual exported tensors before matching bytes. Thus RAMP establishes a substantive prior bit-allocation hypothesis and a reported size/short-task result, not the four-way CPU result. A local method must differ in **its objective and choices**, such as selecting physical width and repack policy from directly measured whole-request CPU/RAM response while using exact serialized bytes, and must beat a matched-byte RAMP-like bit-only allocation. This remains a proposed discriminator until implemented and tested.

Its formal constraint averages assigned nominal bits **equally across 224 linear layers**, excluding embeddings and the output head, whereas complete GGUF bytes weight every tensor by its actual shape and block metadata. This distinction matters even if the paper's reported 3.68-GB file size is correct: the policy objective does not itself enforce a serialized-byte target. Section 4.2 also labels Q3_K_M/Q4_K_M/Q5_K_M as per-layer GGUF types, while llama.cpp defines those names as file-level quantization presets. A local RAMP-like reproduction must translate each decision to legal per-tensor types and disclose the resulting tensor census; without the authors' export artifact or implementation, this cannot be claimed as an exact replication.

[MixQuant](https://arxiv.org/html/2607.23047) further weakens a claim that accounting for cross-layer precision interactions is itself new. It marginalizes module distortion over random quantized upstream contexts and calibrates on allocation-induced activations. At a reported 1.25-GB AWQ budget on Llama-3.2-3B, its seven-group public score mean is 55.6% versus 47.8% for a Hessian-based scoring control. The quantization is simulated by dequantizing to FP16, and its constraint is only `sum(P_l*b_l)/8`, explicitly excluding scale overhead. Neither the 1.25 GB nor its gain is an equal complete-GGUF-byte, CPU peak, full-request CPU-seconds, or sealed-task result. Our novelty test should give a RAMP-like control MixQuant-style upstream-context scoring if feasible, so that any joint selector win cannot be attributed simply to a weaker quality proxy.

**Measured serving-cost architecture search is already published.** [AutoCompress](https://arxiv.org/html/2611.08290) (arXiv v1, 2026-11-05) selects global and per-layer dimensions with cost models fitted to its serving engine, including measured layer latency, weights, KV/recurrent state, prefill workspace, runtime buffers, and an allocation residual. It validates the selected architecture against end-to-end GPU latency and peak VRAM under fixed deployment workloads: 2,048 input plus 256 output tokens on RTX 5070, and 262,144 cached plus 16,384 new input plus 1,024 output tokens on RTX 5080. Its selected models measure 739.7 ms/3.93 GiB and 11.1 s/13.61 GiB, respectively, against those deployment budgets. Appendix B finds that weights plus KV plus recurrent state underpredicts measured memory by 31% to 43% across six RTX models; accounting for workspaces and other runtime allocations reduces error by roughly an order of magnitude in those GPU measurements, not by a transferable CPU correction factor. At matched targets and matched 30B or 10B recovery tokens, the eight-public-benchmark averages are 26.67 versus 20.10 for Minitron++ on RTX 5070 and 68.90 versus 66.55 on RTX 5080. Search alone uses 4.18B or 2.85B tokens, on 8 or 32 H100 nodes. These are substantive evidence that actual serving costs can guide physical architecture selection, so a CPU/GGUF proposal cannot claim this basic idea as new. AutoCompress keeps precision fixed for each target and does not search native K-quant tensor types, repack settings, complete installed bytes, CPU process/cgroup peak, or full-request CPU-seconds. Its fixed-token GPU latency and public benchmark means do not establish a sealed task-level cost or multistep quality gate for a Q4_K_M CPU export. A local method claim would need to beat a feasible, explicitly documented AutoCompress-style measured-cost architecture control as well as RAMP-like bit allocation; if their full algorithms cannot be reproduced, limit the claim to the local controls actually run.

Its [Appendix B.1](https://arxiv.org/html/2611.08290#Sx1.SS1) makes the cost-model lesson quantitative: a conventional estimate using deployed-precision weights, request KV cache and recurrent state underpredicts measured vLLM memory by 31% to 43% across six served RTX models. Adding the stated activation buffer and other runtime allocations reduces error by roughly one order of magnitude in those GPU measurements. Figure 12 includes two illustrated architectures, while the six-model range is stated in the text. The paper profiles vLLM 0.27.1 with NVFP4 experts/head, FP8 Mamba projections, BF16 attention, and FP8 KV cache; its results cannot supply a correction factor for llama.cpp CPU RSS or cgroup memory. A CPU cost model should therefore fit and validate residual runtime allocations on held-out exported GGUF architectures and distinct prompt lengths, then still measure the final cold process/cgroup peaks directly. The 120B-to-74B case retains 95% of its parent's nine-metric mean, which is a remaining average loss against a different model, not a quality-preserving joint resource win against Q4_K_M.

**GGUF phase-model prior and negative transfer.** [Qiu et al.](https://arxiv.org/html/2609.14864) (arXiv v1, 2026-09-14) fit a quantizer-specific roofline predictor from GGUF file size, activated-parameter fraction, and per-layer KV metadata. Its 53 scored host-file configurations span 22 files on two M4 Max systems and an RTX 5080; held-out host-specific decode errors are 13.1%, 14.4%, and 36.1% MAPE on only four, five, and two configurations, respectively. Prefill prediction is weaker, reaching 108.2% MAPE on the RTX held-out pair. The three depth rows per configuration are correlated. Its `llama-bench` trials are separate 512-token prefill and 128-token decode phases at prefixes 0, 4,096, and 16,384, with maximal GPU offload requested; physical RTX residency was not instrumented. The authors do not select an added output-projection timing term because its held-out improvement is inconsistent across tested hosts and loss functions. Thus GGUF metadata and host-fitted phase modeling are established prior work, while even the fitted model does not predict complete CPU requests or cold memory. A proposed selector must profile its actual exported candidates and validate on held-out CPU shapes and request lengths rather than use this paper's coefficients as a universal cost oracle.

**Agent-directed compression under an executable package budget has also been tested.** [CompressionBench](https://arxiv.org/html/2611.06858) (arXiv v2, 2026-11-09) gives six coding agents eight hours each on six source-model/storage settings, with one H200 NVL and vLLM 0.32.0 for each run. Twenty-nine of 36 frozen submissions pass independent checks. Its saved-package allowance includes weights, inference code and tokenizer, and it separately limits resident *model* storage, including persistent reconstructed weights. KV cache, recurrent state and temporary workspace are excluded from that resident allowance; Appendix Table A8 separately samples actual peak device memory for two released controls. The principal score is held-out source-continuation likelihood, with a minimum mean answer accuracy of only 80% of BF16 on 50 each of GSM8K, HumanEval and TriviaQA. The lowest-PPL artifact per setting averages 77.33% across those tasks versus 79.56% for freshly measured BF16. Critically, complete-model feedback reverses 17 of 79 prior local candidate rankings, while a dense-model sequence improves PPL as GSM8K drops 88% to 72%. This supports complete-model and generated-answer checks rather than local reconstruction alone. A four-run fresh repeat in [Appendix Table A6](https://arxiv.org/html/2611.06858) keeps PPL within 0.81% of the corresponding original designs, yet the GLM dense-model mean answer accuracy moves from 80.67% to 68.67% on the same three 50-question tasks; this small repeat cannot estimate a search-success distribution, but shows PPL stability does not ensure answer stability. Speed is reported as batch-one warm decode from first to last of 128 tokens after a 2,048-token prompt, and it is excluded from reward; for the 12-GiB dense setting, the published release reaches 74.6 tokens/s while the Sonnet artifact reaches 16.7 despite its lower PPL and higher mean answer accuracy. These are GPU observations on 27B/120B/122B parents, not proof that agent search improves complete CPU bytes, cold process/cgroup peak, full-request CPU-seconds, or dependent-step success against our 1.5B Q4_K_M. Its 80%-of-BF16 mean threshold can mask a large loss in one component, and 50 questions per component cannot support a narrow noninferiority claim. The closest reusable method is its frozen executable-artifact verification protocol, not any particular compressed representation.

**Nominal sparsity can be a false storage comparator.** [Zhou et al.](https://aclanthology.org/2025.findings-emnlp.645/) (Findings EMNLP 2025) evaluate five small models in their main 1B-to-3.8B study, plus an appendix 0.5B model. At nominally matched 50%/INT8 and 75%/INT4 compression, GPTQ and AWQ generally retain more activation fidelity and public-task accuracy than SparseGPT and Wanda, although some individual tasks reverse that ordering. This is a reason to demand an already quantized control, but its primary pruning comparison uses unstructured zeros. The paper explicitly assumes no mask-storage overhead, labels a 50%-pruned 1B model as “0.5B effective size,” and borrows theoretical device speed figures for Table 3. Its own evaluations use a single A100 and an FP16 parent. Thus it does not measure the deployed byte or CPU benefit of a physically narrower tensor after recovery, nor does it supply a same-base Q4_K_M four-gate test. It also does not justify claiming that all pruning is inferior to quantization.

**Temporary overcomplete recovery is established prior art.** The peer-reviewed [OverRep paper](https://aclanthology.org/2026.emnlp-main.278/) (EMNLP 2026, October) trains two temporarily overcomplete recovery blocks after structured layer pruning and anneals them into a projection that can be folded into an ordinary layer. Its six-backbone controlled study keeps pruning criterion and FineWeb-Edu recovery subset fixed at 120,000 training and 4,000 test samples. Its 10 reasoning and three generation tests are public benchmark tasks, not a sealed dependent-step holdout. Table 1 uses retained performance, the pruned model mean divided by its dense parent mean. The LLaMA3-3B 25% pruning setting has 90.2% retained performance versus LoRA 84.7%, while its 50% setting has 72.3% versus RankAdaptor 63.9%; the advertised 5.5- and 8.4-point gains are maxima across settings, and the latter model still loses 27.7% of the dense mean. Figure 3 reports *training* memory, TFLOPs and throughput on two RTX 3090 GPUs. The authors say channel-wise and hybrid pruning are preliminary, with lower recovery budgets and narrower model coverage. Thus overcomplete recovery and exact post-training fold-in cannot be claimed as new. The open deployment question is whether an aligned, format-aware physical-width candidate recovers enough quality while beating equal-byte Q4_K_M and simple controls on complete GGUF bytes, cold CPU peaks and completed-task CPU-seconds. The paper does not supply such an artifact or a sealed integration-quality result.

**Quantized physical pruning with an output-head change is also published.** The peer-reviewed [UniQL paper](https://arxiv.org/html/2512.03383) (ICLR 2026, arXiv v3 2026-02-26) sorts channels, applies masked LoRA recovery and GPTQ 4-bit quantization in one cloud pass, then physically prunes eligible channels on an edge device. Its implementation unpacks INT4 weights, removes channels, and repacks for its kernel. Unlike TAO-HQQ and TRT-AWQ comparators, UniQL also quantizes embeddings and the output head to 4 bits. Therefore, its Qwen2.5-7B 3.9-GB unpruned size versus TAO-HQQ's 6.0 GB combines a head/embedding precision change with other implementation differences. A cleaner within-UniQL comparison at 35% pruning is 3.9 to 2.7 GB and fixed 512-plus-512-token Orin Nano TTLT 39,795.3 to 28,185.8 ms. The same model's five-public-task mean falls from 72.4% to 58.1%, so those large gains do not meet a quality-retention claim. Even 15% pruning changes that mean to 68.1%. The Nano has a GPU and the warm fixed-token timing does not equal variable-completion full-request CPU-seconds. The reported model sizes are not installed GGUF bytes or peak process/cgroup RAM. UniQL is a strong closest prior against any claim that physical pruning, low-bit head compression, and edge latency are a new combination. The open question here is narrower: whether a source-matched candidate in native CPU GGUF passes the exact four resource/quality gates against already-Q4_K_M and equal-byte controls.

**Multi-hop quality deserves its own gate.** The peer-reviewed [PRISM paper](https://link.springer.com/article/10.1007/s10791-026-10580-5) (2026-10-06) supplies a precise warning: its Qwen2.5-3B-Instruct fictional-entity two-hop test has `n=160` and open-book accuracy 0.98 at FP16, 0.74 at uniform 4-bit, and 0.15 at uniform 3-bit. Its harder three-hop `n=80` test moves 0.912 to 0.812 to 0.013, while long-context multi-hop `n=100` moves 0.75 to 0.54 to 0.00 at those precisions. All three have zero closed-book accuracy by design, so they test composition of supplied facts; the long-context test has a high invalid/other-response rate of 0.31 to 0.59 and a small denominator. The apparent safety of short, single-hop verbatim retrieval is a ceiling and does not transfer to multistep tasks. PRISM also shows that capability-specific mixed precision is not a free resource win: its calibrated GPTQ attention-8/MLP-3 allocation averages 3.6 bits and reaches 0.99 open-book accuracy versus 1.00 for uniform 4-bit, but closed-book recall falls to 0.07 versus 0.78 on a 96-item anchor. It explicitly reports that calibrated GPTQ removes a sharper early-MLP sensitivity seen under RTN. These distinctions argue for separate task-family floors and error categories, not a universal claim that any particular tensor class is safe to compress. Every PRISM experiment uses an RTX 5060 GPU; its GGUF Qwen2.5-7B sweep offloads all layers to GPU, and its head stays FP16. There is no tested transfer to a 1.5B Q4_K_M CPU artifact, no Q6_K-to-Q4_K output-head arm, and no complete deployed-byte, CPU RAM, or CPU-seconds result. The paper claims to release its pipeline and per-item records, but its cited GitHub URL returned HTTP 404 on 2026-11-12; independent replay was not possible in this audit.

[Bajwa's WMT26 COMET-guided allocator](https://aclanthology.org/2026.wmt-main.133.pdf) is closer prior art for *task-outcome sensitivity plus serialized-byte costs*: it independently fake-quantizes each of 48 decoder layers, measures development-set translation COMET drop, reads tier costs from safetensors headers, and solves a BF16/INT8/INT4 knapsack. Its single-layer drops are assumed additive and INT8 drop is estimated as half the INT4 drop. The 9-GB decision target excluded embedding, output head, tokenizer, and config, so the exported directory is 9.15 GB. On an L40 GPU its fresh-subprocess 456-sentence WMT25 source timing is 259.4 seconds versus 401.6 seconds for the vLLM BF16 engine control; the 550.5-second Transformers BF16 reference uses another engine. The 9.15-GB mixed package is also larger than the 8.0-GB GPTQ/AWQ controls. Reference-scored chrF is a single run on a public WMT25 set, and the speed source set is publicly provided without references. Thus exact tier costs, task-guided allocation, and load-inclusive time are published precedents, while a **complete-package-constrained physical-width/type/repack selector with measured CPU-seconds, process/cgroup peaks, and sealed benign multistep quality** remains an untested combination. The paper does not establish a CPU or equal-byte four-gate win.

The [organizers' official WMT26 findings](https://aclanthology.org/2026.wmt-main.52.pdf) supply an independent check on that submission. On the common H100, the submitted CometCut mixed model has 8.53 GiB on disk versus 7.90 GiB for the same team's uniform GPTQ, a median one-sentence warmup of 58.6 versus 50.1 seconds, and 10,820 versus 6,690 net Czech-to-German source characters/s. Its reference-free Czech-to-German COMET-Kiwi-XXL is 55.98 versus 56.29; on English-to-Chinese it is 76.98 versus 76.55, and on English-to-Arabic 60.19 versus 60.58. The pattern is a genuine speed-size-quality trade-off, not a uniform improvement. The organizers subtract one warmup sentence from full-set wall time and select a reliable batch for peak throughput; neither warmup nor that net rate is a full-request CPU-seconds measure. They explicitly caution that serving runtime heavily affects speed and that aggressive structured removal often damages translation quality. Their blind set has no available references in the paper, so quality comes from two reference-free estimators. This further weakens any claim that a task-guided allocator alone will beat a uniform low-bit CPU control.

[La et al.](https://arxiv.org/html/2606.04063) are an even closer *joint architecture and precision search* precedent. Their differential supernet selects hidden/intermediate/head widths, block count, weight bits, and activation bits together, with a probability-weighted per-choice latency lookup and expected **parameter-count** constraint. It uses Llama-3.1-8B and A100 Marlin/ABQ-LLM GPU profiling; the paper's quantized Pareto figure gives up to 1.4 times faster inference than sequential NAS then fixed quantization at about 40% public seven-task mean accuracy, or about six accuracy points better at 30 ms. The 30-ms and 1.4-times comparisons are GPU latency points, not full-request CPU-seconds or complete-byte matched results. Training uses approximately 52,000 Alpaca instructions, LoRA and distillation after supernet convergence, with the supernet runnable on one A100 80GB according to the paper. No native K-quant export, process/cgroup peak, exact package accounting, sealed multistep suite, or second host is reported. The proposed CPU/GGUF contribution cannot claim joint width/precision allocation itself as new; it must show that measured repack and whole-request CPU/RAM objective terms select a better deployment artifact than a source-matched La-style joint search under the same complete-byte and quality constraints. This is a method proposal, not a literature-proven win.

[Lian et al.](https://arxiv.org/html/2606.25519) directly test token inflation in reasoning models and report Qwen3-4B BBH taking 285 seconds in BF16 versus 292 seconds in INT4 despite a separate W4A16 per-token kernel advantage of 1.2 to 1.4 times. Their Table 2 gives Qwen3-4B RTN4 an average 42.5% reasoning-token inflation across six tasks. The 285/292 seconds are a GPU wall-time comparison, while the per-token test uses specified 512 input and 128 maximum new tokens, so they are not a single CPU cost decomposition. All experiments use H100 GPUs; the accuracy suite samples 100 questions per task except AIME25's 30. The paper supports recording the complete generated trajectory and CPU cost, not imputing a fixed token-count speedup. Its BF16 comparator also differs from our already-quantized Q4_K_M reference.

The result is method-dependent, not a universal low-bit penalty. In the primary [Liu et al. quantized-reasoning study](https://arxiv.org/html/2504.04823), W4G128, W8A8KV8 and KV4 output lengths stay near BF16, whereas more aggressive W3G128 and W4A4KV4 can lengthen outputs, especially for 1.5B models. Its reported latency in the reasoning analysis is generated token count multiplied by official Qwen time per output token, not a measured paired full request. Lian et al. likewise give Qwen3-4B six-task mean chain-of-thought inflation of 12.0% for GPTQ INT4, 8.2% for AWQ INT4 and 4.7% for ParoQuant INT4, with much larger 3-bit cases. These are means of reasoning tokens relative to BF16, not total CPU cost against Q4_K_M. The design consequence is to predeclare complete-request CPU-seconds and stop/failure counts as gates, then let measurements determine whether any particular compressed artifact helps.

### Independent task batching versus dependent step integration

**Program synthesis as a narrow integration intervention.** The [ClosureBench arXiv v2 report](https://arxiv.org/html/2608.18242v2) shows a Qwen3-4B LoRA model emitting executable Ein programs for graph tasks, with 1,226/1,300 correct and 1,295/1,300 executable on fresh held-out instances; the [released Ein summary](https://github.com/egolabs-ai/closurebench/blob/main/experiments/ein-sft/summary.json) reproduces those counts. Its reported 59.2% direct-answer SFT comparator is a promising same-base task-specific contrast, but not an equal-cost deployment result. The test draws fresh instances from the same 26 categories and graph sizes 4 to 10, rather than withholding program structures. The paper says both SFT arms train for three epochs in §3.4, while §4.1 gives the answer result after five epochs; Table 6 specifies matched LoRA configuration, not a reconciled training budget. The public experiments directory inspected on 2026-11-12 contains the Ein summary but no direct-answer SFT summary, so the 59.2% denominator could not be checked from raw outcomes. The paper describes Ein output as about 128 tokens in one passage and about 200 in another; its 600-token syntax prompt and executor cost are not included in a CPU package comparison. A valid local variant must use the same base model, data, training tokens/steps, and frozen graph instances for direct answer and program arms, include interpreter, schema and retry bytes/RAM/CPU in the installed and full-request totals, and test fresh program structures as well as fresh instances. Reject any general model-efficiency claim if this narrower system fails the four deployment gates or loses on the independent held-out family. The paper is an unreplicated preprint and does not imply frontier-model parity.

For the user's concern about correct isolated steps failing when combined, the closer primary precedent is [Press et al.](https://aclanthology.org/2023.findings-emnlp.378.pdf). On 8.6k templated two-hop Compositional Celebrities questions, their Davinci-002 Table 6 assigns 41.8% of all cases to correct subanswers and correct final answer, and 33.4% to correct subanswers but wrong final answer. Thus 44.4% of cases with both isolated subanswers correct still fail the two-hop answer. This conditional ratio diagnoses integration failure; it is not unconditional task accuracy. Their 125 manually judged Bamboogle cases improve from 17.6% direct to 46.4% chain of thought and 57.6% self-ask, but extra generated reasoning and any external search must be charged in a full-request CPU study. Older models and factual QA do not establish a repair for our Q4_K_M model or quality retention after compression. [Dziri et al.](https://arxiv.org/html/2305.18654) provide a separate executable-graph warning across multiplication, logic-grid and dynamic-programming tasks, testing 500 examples per task and model; their out-of-domain failures as graph complexity grows support measuring dependency depth, not a universal claim that transformers cannot compose. A prospective local gate should sample all sealed compound tasks without selecting for isolated correctness, use final-answer success as the primary metric, and report the both-isolated-correct conditional failure rate as a secondary diagnostic. Match single-step and compound primitives, stratify by dependency depth, and count every prompt, retry and verification step in CPU-seconds. A prompt or training intervention should be rejected if it only narrows the conditional gap by increasing total CPU-seconds beyond the predeclared resource gate.

[AgentCoMa](https://aclanthology.org/2026.acl-long.380.pdf) is a newer, direct dependent-step diagnostic: a commonsense selection supplies an operand to a math operation. Its 260 expert-written cases comprise 80 development and 180 test items; Table 2 reports 16 representative models with mean 80% success when both steps are tested separately and 51% when composed. The paper benchmarks 61 open-weight models under a two-shot chain-of-thought prompt, greedy vLLM generation up to 2,048 tokens, and four A100 GPUs. The [official evaluator pinned at commit 5464e3e](https://github.com/lisaalaz/agentcoma-benchmark/blob/5464e3e7cf7261837876f5ea3f12d477579a68f5/eval.py) calls `check_text` only for commonsense-only answers. In that function, the `try` branch splits on the exact string `So the final answer is:`. If the delimiter is absent, the `except` branch asks GPT-4o whether the full response matches a gold answer, but assigns `is_correct = 0` even when that judge returns true. Math-only and composed answers instead use numeric `accuracy`; the reported gap is `comp_acc - both_steps_acc`. Hence an affected semantically correct commonsense response is falsely scored zero, lowering `both_steps_acc` and making a negative gap less negative. This is a verified code-path property, not a measured estimate of how often the defect occurred or how much it changed any reported result. The paper's requested answer format may limit exposure. AgentCoMa motivates a dependency-specific suite but is not a substitute for our format-audited, sealed same-base CPU gate.

[Wang and Bagci](https://arxiv.org/html/2611.11695) provide a caution against selecting compression by a convenient proxy task. Across eight BF16 instruction models, including Qwen2.5-1.5B, they apply four random damage mechanisms plus Wanda, SparseGPT and GPTQ. Each of sixteen short-answer tasks has 300 items scored in choose, answer, JSON and repeated-answer formats. The within-model task-failure order under random damage versus compression has median correlation 0.875 across eighteen model-method cells. Yet their preregistered long-form extension failed its transfer criterion: only 10 of 16 task-model positions stayed within the specified band, below a 75% target, and multi-step reasoning became more fragile under pruning. That extension uses four models and 200 items each of GSM8K chain of thought, HumanEval/MBPP code, IFEval and function calling, under Gaussian noise and Wanda only. Format itself changes measured fragility: at intermediate damage, 83% of repeated-answer errors violate the template, while 79% of those still contain the correct answer. The study supports separate content and format scoring, and it explicitly weakens any claim that short-answer or perplexity screening predicts sealed dependent-step success. It reports neither Q4_K_M GGUF artifacts nor cold CPU RAM or full-request CPU-seconds.

**Coverage can conceal request-cost failure.** [Song and Zheng](https://arxiv.org/html/2611.01133) (arXiv v1, 2026-10-31) compare original and structurally pruned models using pass@k on 30 AIME-2026, 272 Minerva, 164 HumanEval+ and 175 LiveCodeBench-v6 problems, with up to 2,048 math and 512 code samples per problem and an 8,192-token generation cap. For Qwen3.6-35B-A3B on AIME, their 80% expert-pruned arm requires an estimated 1,319 attempts and 59.63 times the original's generated tokens to reach the same 90%-of-original-coverage target; mean tokens per attempt fall from 4,923.5 to 4,451.4. This is a striking counterexample to treating retained pass@k coverage or shorter individual traces as an efficiency win. The paper's token-cost estimate is `attempts × mean generated tokens`, not a measured CPU-seconds, cold RAM, or complete-file result; it excludes prompt processing and verification. Its MoE expert-pruning comparison does not transfer to the current dense Qwen2.5-1.5B Q4_K_M artifact. Use a fixed retry policy and include every unsuccessful attempt in full-request CPU-seconds, with unconditional first-attempt success and eventual success reported separately. A candidate that needs retries to recover the reference's task success fails the CPU gate unless its measured total request cost still clears the locked reduction threshold.

**Screened-out quality-risk result.** [Oladri et al.](https://arxiv.org/pdf/2607.09999) (arXiv v2, 2026-07-23) study FP32, FP16 and bitsandbytes NF4 on five 3B-to-14B models, 500 questions per benchmark and 2,000 outputs per model-precision combination on A100 GPUs. Their proposed reasoning-failure taxonomy could motivate an exploratory trace audit, but the quantitative tables cannot presently support our gate. Table III calls 71.4% ±1.8 percentage points on 500 GSM8K items a 95% bootstrap interval; a standard item-level Bernoulli 95% approximation at that rate is about ±3.96 points. Table IV reports 15.9%, 10.6%, and 10.6% Hollow Convergence for Qwen2.5-7B at the three precisions with chi-square 1.43, whereas a balanced 2-by-3 Pearson calculation at 2,000 observations per precision is about 34.6. The actual taxonomy denominator may exclude some outputs, but the paper does not provide the counts needed to reconcile the result. Its LLaMA-3.1-8B change is mainly FP32 to FP16 (29.9% to 13.8%), with only 13.8% to 13.6% from FP16 to NF4. No raw outputs or evaluator are linked in the paper. Do not use its significance or claimed NF4-specific effect as evidence of a compression-induced reasoning shift without a reproducible correction; use independently checked final-task success and a bounded, blinded error audit instead.

The 2026-10-19 [Li et al. preprint](https://arxiv.org/html/2610.27190) isolates a different composition failure from our ordered-state examples. It concatenates **independent** questions from one dataset into one prompt and grades each answer, rather than requiring one step's output to feed the next step. Its eight models are Qwen3 4B Thinking, 8B and 14B; Qwen3.8 27B; three DeepSeek-R1-distilled 7B/8B models; and Claude Opus 5. The eight source pools are 1,000 generated integrals, 1,548 OneWordQA questions, 1,406 MMLU-Redux, 196 GPQA-Diamond, 1,319 GSM8K, 500 MATH-500, 60 AIME 2024/2025, and 687 StrategyQA. For the isolated-ability analysis, a model-specific question enters only after **three of three** correct isolated attempts, then isolated accuracy is measured again on independent runs. The paper tests composition sizes 3, 6, 10 and 20, except 20 on GPQA and AIME due context overflow, usually estimating accuracy over five trials. This conditioning isolates the act of independent-task batching; it does not estimate unconditional deployment accuracy or dependent-chain reliability.

Their measured-fragility policy uses ten isolated trials and ten trials at each composition size per task, then selects a per-task batch size by cross-fitting under a 0.5-percentage-point mean accuracy-loss budget. Averaged across all eight models and seven datasets excluding AIME, it saves **43% generated output tokens per task** relative to solving each task separately while reporting **+0.6 percentage points** mean accuracy. The deployable predictor version encodes each question with a separate **Qwen3 Embedding 8B**, fits a model-specific linear head from repeated trial labels, and saves **31.0% output tokens on average**. This does not include encoder package, training queries, encoder inference, input/prefill, CPU-seconds, or memory. Its transfer is uneven: on Claude Opus 5 GPQA, measured-fragility batching saves 24.3% tokens with a 0.4-point accuracy drop, whereas the predictor saves 0.5% and loses 2.0 points. Section 4.2's blanket statement of predictor losses no worse than 0.5 point conflicts with that Table 1 row; retain the row rather than generalize the prose. A nominal output-token saving cannot satisfy our complete-bytes, CPU-peak, full-request CPU-seconds, and sealed-quality gates. Adding an 8B predictor to a local 1.5B deployment would likely increase installed bytes and peak RAM unless a smaller predictor is independently validated and all auxiliary costs are counted.

**Falsifiable composition test, separate from head compression.** Build two disjoint sealed benign suites after development calibration finds a reference with an adequate absolute floor. Axis A holds independent items fixed and randomly assigns them prospectively to isolated requests or groups of 3 or 6, with stable item order, answer slots, parser, context and token limits. Report per-item correctness, whole-group correctness, output and input tokens, full-request CPU-seconds per correct item, process/cgroup peak, and all extra classifier or retry costs. No sealed item is selected because the reference already solved it. Reject an adaptive-batching efficiency claim if paired accuracy falls outside the predeclared bound or **total** CPU-seconds per correct item fails to fall, even when output tokens fall. Axis B uses independently generated **dependent** chains from matched single-step primitives, with executable gold for each intermediate state and final state; stratify by chain length and dependency depth, and score the final answer and the first failing step. Compare each model's composed success with its same-item single-step controls and a preregistered expectation from those controls, while retaining an absolute success floor and paired candidate-versus-reference bound. Reject a dependent-integration claim if compound accuracy falls below that bound even when isolated steps pass. Keep these axes separate: Li et al.'s batching result motivates Axis A and a possible token-cost covariate, but supplies no evidence that Axis B or output-head Q4 compression passes.

**Conditional step errors are a secondary diagnostic.** [Firke and Kannan](https://aclanthology.org/2026.emnlp-main.1976.pdf) (EMNLP, 2026-10-24 to 29) programmatically label 18,969 greedy-decoded reasoning chains across GSM8K (5,412), MathQA (4,729), BBH Tracking (3,342), ProofWriter (3,185), and MMLU-Pro (2,301), using seven models from 3B to 70B or API access. Their parametric Weibull fit places the first-error hazard above a constant-risk shape in 34/35 dataset-model cells. The nonparametric Mann-Kendall table is much weaker: only five of seven ProofWriter cells have a significant positive trend after correction, while GSM8K Llama-3B and MMLU-Pro Llama-70B have significant **negative** trends. Weibull is AIC-preferred in only 4/35 cells, and the authors acknowledge that late steps may simply be harder, so neither the 34/35 count nor a depth trend identifies a causal model-aging mechanism. Their fan-in correlation is based on only five dataset means (`rho_s = 0.90`, exact `p = 0.083`); it is a hypothesis, not a demonstrated driver. In a 70/30 split repeated 100 times, checking the last one step detects 94% of ProofWriter error-containing chains versus 23% from a uniform random one-step check, but this is simulated **error detection**, not corrected final answers or reduced total CPU. For the proposed dependent-chain suite, preregister unconditional final-task success as primary and score time to first objectively verifiable state error, later-step recovery, depth, and fan-in only as secondary diagnostics. Hold step difficulty and parser behavior as constant as possible across depth, report unparseable steps separately rather than coding them correct, and include any checker and retry cost before claiming a resource gain. This paper supplies no Q4_K_M GGUF, complete bytes, cold CPU memory, or full-request CPU comparison.

**Short-answer fragility does not certify composed answers.** [Wang and Bagci](https://arxiv.org/html/2611.11695v1) (arXiv v1, 2026-11-08) include Qwen2.5-1.5B-Instruct among eight BF16 models and test 16 short-answer tasks, each with 300 evaluation and 40 calibration items, in four answer formats capped at 32 generated tokens. Short-answer task-fragility order correlates within a model across Wanda, SparseGPT, GPTQ, and four random perturbations; the median correlation with random-damage order is 0.875 over 18 compression cells. But GPTQ's order does not transfer across models (median 0.095 over six model pairs). Their separate 200-item-per-task long-form extension covers GSM8K chain of thought, code, instruction following, and function calling in four models: only 10 of 16 task-model positions remain within the preregistered band across noise and Wanda, below the required 12 of 16, and GSM8K becomes more fragile under Wanda in three models. The result supports holding answer format constant and measuring long-form and dependent-step tasks directly. It cannot predict our local Q4_K_M head or width change: its checkpoints are BF16, quantization is GPTQ rather than native K-quant, and it reports neither deployable GGUF bytes nor cold CPU memory or full-request CPU-seconds. This is an unreplicated preprint; its failed transfer tests are as relevant as its short-answer correlations.

**Public, bounded development-screen leads.** [Roy and Roth's Commoncore corpus, commonly used as MultiArith](https://cogcomp.seas.upenn.edu/papers/arithmetic.pdf) has 600 problems, 100 in each of six two-operation categories; their own six-fold evaluation holds out an entire category per fold. The paper uses an A6000, temperature 0.7 and top-p 0.9, and does not identify that Qwen checkpoint as the *Instruct* variant or measure Q4_K_M CPU. Therefore, run a **reference-only** local development screen with a locked few-shot chain-of-thought prompt and count every generated token and the complete request CPU cost. Do not adopt the paper's 95% as a local baseline or use its test rows as an untouched final set after viewing them. **A stronger structural composition family, still prospective.** [CLUTRR](https://aclanthology.org/D19-1458.pdf) builds short kinship stories in which the answer requires composing `k` supporting relations. The EMNLP 2019 paper defines `k` as the number of required reasoning steps and evaluates length transfer from `k = 2,3` or `2,3,4` to `k = 2..10`. Its experiment generated 5,000 training stories and 100 test stories per `k`, repeated 10 times, holding out 20% of paraphrases and 10% of logical clauses during training. These are **published training/evaluation denominators**, not a local Q4 result. [The official generator](https://github.com/facebookresearch/clutrr/tree/d045fae289d3746503677ceed7631c999202501e) exposes relation length, template splits, and logical-pattern holdouts; its README describes a same-pattern, same-placeholder default, although the pinned CLI default for `--template_split` contradicts that description. A reference-only development screen should use `k = 2,3` and check a predeclared absolute floor before freezing a disjoint `k = 4` set. The published study found that text-model performance improved when train and test reused the same paraphrases, so score stable-language and held-out-language conditions separately to distinguish relation composition from parsing difficulty. Verify held-out relation-pattern and paraphrase configurations in the pinned generator before treating either as a clean internal split. On this pretrained checkpoint, withholding patterns from our prompt and development set does **not** establish that the model never saw CLUTRR's public rules or templates during pretraining. Even an internally clean split remains a narrow kinship task. The pinned code has three implementation traps: [`--template_split` is `store_true` with default `True`](https://github.com/facebookresearch/clutrr/blob/d045fae289d3746503677ceed7631c999202501e/clutrr/args.py#L59-L65), so the documented easy/no-template-split configuration cannot be selected through the CLI as written; [synthetic rendering overrides the loaded train/test template sets with the same relation templates](https://github.com/facebookresearch/clutrr/blob/d045fae289d3746503677ceed7631c999202501e/clutrr/generator.py#L41-L56), so template separation requires the AMT renderer; and [the generator forces pattern overlap for `k = 2` even when `--holdout` is set](https://github.com/facebookresearch/clutrr/blob/d045fae289d3746503677ceed7631c999202501e/clutrr/generator.py#L126-L145). Verify disjoint pattern/template IDs in the **rendered** development/evaluation manifests, hash every input and gold label, and keep answer parsing, normal stops, token counts, and full-request CPU-seconds separate. The repository's `LICENSE` is CC BY-NC 4.0, which also matters before reuse. The published human check exceeds 70% at `k <= 3` for time-constrained annotators but falls to 40–50% at `k > 3`; trained annotators with unlimited time reach 100%. This difference shows that language comprehension, attention and composition can confound one another, and it warns against assuming a local 60% four-step floor without reference-only screening. It is not a reason to retune against a frozen set. No quality, CPU, RAM, or file-byte result for the current artifact exists on CLUTRR.

**State-emission training as a bounded quality lead.** [Nadgir, Balasubramanian and Chaudhari, arXiv v2, 17 October 2026](https://arxiv.org/html/2610.09186v2) fine-tuned **Qwen2.5-1.5B-Instruct**, the same named base family as our local reference, on generated equations and dependent story questions. Its algebra experiment used 50,000 training and 1,000 distinct test problems for each of three replicates, with depth mostly 3 to 10 operations. On unperturbed algebra, the reported final-answer accuracy was 0.973 with a state after every step, versus 0.587 with operation traces but no emitted states and 0.564 for direct answers. A fixed-token comparison reduced the every-step training count to 24,536 because state traces are longer, and reported the same qualitative ordering. The story experiment used a 479-story generated corpus, with 375 train and 63 test stories per replicate, four questions per story, three independent splits and 252 held-out questions per split. It reports 0.866 accuracy and median 852 reasoning tokens for state tracking, 0.438 and 648 tokens for length-comparable local narration, and 0.694 and 38 tokens for key-sentence reasoning. The story task includes first- and second-order belief updates over 20 actions. These are **BF16 LoRA fine-tunes**, about 2.3% trainable parameters, not measurements on our GGUF or a quantized CPU engine. The test sets separate stories or exact equations, not operation grammars or story dependency structures. The paper describes a 479-story corpus but allocates only 375 training and 63 test stories per split; it does not explain the remaining 41 in Appendix C. Frequent state emission also made the algebra model less robust to answer-preserving perturbations, and longer traces can increase full-request CPU-seconds. The medians imply 22.4 times as many reasoning tokens as key-sentence prompting; at equal prefill and no retries, state traces would need per-token decode CPU cost below 38/852, or 4.46% of the key-sentence arm, merely to make the decode stage cheaper. That arithmetic is a cost warning, not an equal-quality comparison: the paper's state arm has higher accuracy. The paper is unreplicated and reports no complete file bytes, cold process/cgroup RAM, or CPU request time. Thus it suggests a training and evaluation arm for dependent-step integration, not a four-gate compression result. A falsifiable follow-up would hold the compressed and Q4_K_M artifacts fixed, train matched-budget adapters on development-only state traces versus key-sentence and length-matched narration controls, then export complete quantized packages and test unseen dependency motifs with task accuracy and trace-token cost. Reject if the state-trained compressed arm fails the locked paired quality margin, if the byte/RAM/CPU gains disappear after adapter merge and longer decoding, or if it only wins on the paper's same-grammar instances. This is closest prior for intermediate-state supervision, so using state traces alone would be a reproduction rather than a new method.

**A state-task selection trap.** [ExploreToM, ICLR 2025](https://arxiv.org/html/2412.12175) supplies a [released symbolic belief tracker and generator](https://github.com/facebookresearch/exploretom/tree/6a9372870ddc1c7b9b9ce1f3ee1641dbbdb56760) that could provide a third benign dependent-state development family. Its Table 9 finds that only 5.6% to 8.6% of randomly sampled story/question/answer triples in the reported two- to four-person, two- to four-movement settings require a false-belief answer different from the world state. A fresh-instance set could therefore look broad while mostly grading easy direct-state questions. Sample by a **gold-defined dependency property**, balance answer classes and action motifs before either model is queried, and freeze whole action motifs between development and evaluation. The paper's A* search instead explicitly finds stories missed by a target model; the official README says its released sample targets Llama-3.1-70B and should be regenerated for another target. Using a reference-error-selected set as the sealed absolute-floor gate would bias that floor downward, and it might be too hard for the current 1.5B artifact. The tracker is a task-design lead, not evidence for a compressed CPU model, and the reported 0%/9% worst-case Llama-3.1-70B/GPT-4o scores must not be read as performance of our artifact.

**Prompt-budget sensitivity is a separate development variable.** [Qi's April 2026 preprint](https://arxiv.org/html/2604.02155) compares two-stage reasoning budgets on 200 contiguous BFCL v3 Multiple tasks with BF16 Qwen2.5-1.5B-Instruct in Transformers: no reasoning scores 44.0%, a hard 32-token reasoning stage scores 64.0%, and hard 256 and 512-token stages score 25.0% and 22.5%. A separate fine-grained sweep on only 100 tasks reports 69.0% at 16 tokens, while its later matched 200-task table reports 71.5% at 16 tokens. These denominators should not be mixed. The paper's 88.6% short-budget oracle result uses 148 of 167 tasks solved at any budget, not all 200. Its single-call function-routing setting does not measure dependent-step integration, and the hard two-stage protocol, BF16 runtime and task selection cannot explain our separate 512-token state-development failure. It does show why the next **reference-only** development screen should compare a small prespecified set of prompt and output budgets and log completed answer, format compliance, generated tokens and full-request CPU-seconds before locking one policy. The paper's claim that prompted function routing structurally guarantees no hallucination is too strong: its own Table 5 reports invalid routing in 0.5% of 1.5B and 1.5% of 7B traces, with zero observed final hallucinations on 200 tasks each. That observation is not a guaranteed property of future requests. No complete GGUF, cold CPU RAM or sealed composition quality is tested.

**What structural holdout means.** The [official pinned iGSM README](https://github.com/facebookresearch/iGSM/blob/a1ed1d04600add811beb08b58d9912ed30999642/README.md) exposes `problem.G`, a layered structure graph, and `problem.template`, a directed dependency graph; [`setup_template`](https://github.com/facebookresearch/iGSM/blob/a1ed1d04600add811beb08b58d9912ed30999642/math_gen/graph_gen.py#L832-L849) constructs that directed graph. The [exact generator path](https://github.com/facebookresearch/iGSM/blob/a1ed1d04600add811beb08b58d9912ed30999642/math_gen/problem_gen.py#L222-L245) calls `setup_template`, `reasonable_sort`, `design` and `fill_all`, then sets `ques_idx` from the last topologically ordered required parameter *before* calling `design_unused`. The [`design_unused` code](https://github.com/facebookresearch/iGSM/blob/a1ed1d04600add811beb08b58d9912ed30999642/math_gen/graph_gen.py#L423-L440) subsequently adds unused or independent parameters to the full template. A prospective structure key must therefore use the query's ancestor-induced subgraph, rather than the full `G` or template, so distractors do not make the same solution topology appear new. Canonicalize that subgraph with edge direction, parameter-node class and queried node preserved. Predeclare graph-depth and branching strata and assign *whole canonical topology groups* to development or sealed evaluation. Reusing a topology with new names, numbers or seeds is only an instance holdout. For an independent ordered-state family, similarly group operation sequences or dependency motifs, reserve whole motif groups for evaluation, and retain matched primitive controls. Freeze the graph canonicalizer, assignment rule, accepted strata and manifest hash before evaluating either artifact. Report the number of distinct held-out groups and a group-aware uncertainty analysis. The existing locally generated pilot uses only four fixed templates per family, so many generated seeds do not give many independent structures; item-level intervals cannot support broad composition generalization. This ancestor-topology split is **our proposed protocol**, not a holdout validated in the published iGSM work; this project has not run it. It would establish a holdout relative to this project's development process, not prove that a pretrained checkpoint never saw related structures.

Both the Q4_K_M reference and 14-tensor candidate scored 10/200 under a required generated `####` final line, far below the locked 60% absolute floor. Most normally stopped responses lacked that line; a post hoc last-number check was exploratory and cannot replace the frozen scorer. The 200 evaluation rows and their outputs are now exposed to the project and should be quarantined from a future confirmatory gate. A future prompt change, longer output cap, or parser repair on these rows would produce only another exploratory result. The source [GSM8K answer file](https://github.com/openai/grade-school-math/blob/3101c7d5072418e28b9008a6636bde82a006892c/grade_school_math/data/test.jsonl) uses `####` in gold labels. The authors' [GSM-Symbolic evaluation recipe](https://github.com/apple/ml-gsm-symbolic/blob/main/README.md) instead prompts generated answers with `The final answer is ...` in eight examples, illustrating that the gold delimiter is not automatically a suitable generated-answer contract for every model or prompt.

The [fresh generated two-family pilot](generated-multistep-quality-protocol-2026-11-12.md) was also stopped before a sealed evaluation. Reference-only development on eight cases per family scored arithmetic/state 4/8 and 0/8 with two 192-token prompts, 0/8 and 1/8 with a numeric-only prompt, then 5/8 and 3/8 with explicit reasoning at a 512-token cap. The last run stopped normally on all 16 cases but met its requested final-line format on none. Its state point rate missed the predeclared 60% development screen, and eight cases are too few for an inferential floor. No candidate was queried on this suite and no evaluation manifest was frozen. The next attempt needs a stronger checkpoint used as a new same-base Q4_K_M reference/candidate pair or an independently sourced multistep suite whose reference development performance supports a format-blind primary scorer and prospectively powered gate. Further prompt changes on these same 16 cases remain development only. A 300-per-family sealed run would have limited power for a five-point noninferiority margin even if the reference were adequate: equal outcomes with ten discordances in each direction produce a conservative paired lower bound near minus 5.88 points.

The peer-reviewed [StructureBench study](https://ijcai.org/proceedings/2026/267) (IJCAI 2026, August) reinforces why a delimiter or grammar fix alone cannot repair this floor. It tests 11 on-device 0.5B-to-8B models across 13 structured datasets and separates structural validity from conditional semantic correctness. For Qwen3-0.6B with XGrammar, its Table 4 reports a 94.8% conditional structural fix rate and 70.5% conditioned semantic bonus in schema-aligned tasks, but only 16.0% and 1.5% for meaning-bound AMR/PDDL/SQL; hard Python constraints have 97.6% constraint-induced repetition in its designated pattern. Those are heterogeneous task-pattern diagnostics, not a forecast for our arithmetic or ordered-state tasks. A future grammar-assisted scorer or constrained decoder must be frozen before the sealed test, charge its full package and CPU costs, and pass unconditional semantic success; parseability and answer correctness remain separate outcomes. The study does not compare same-base Q4_K_M versus a compressed GGUF on cold CPU memory or full-request CPU-seconds.

A replacement gate should use **fresh hidden seeds and disjoint task instances**, with its prompt, parser, output cap, and baseline absolute floor frozen after a *different public development set*. One family can use the released [iGSM dependency-graph generator](https://github.com/facebookresearch/iGSM) to vary numbers, entities, graph depth and query nodes while keeping executable ground truth; sample strata where the uncompressed same-base reference clears a predeclared public-pilot floor, then seal new seeds and instances. A second family should test multistep state or data transformations with an executable final-state checker, such as an independently implemented subset of the [BFCL V3 multistep tool scenarios](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html); avoid known public benchmark questions as the sole confirmation. Include matched single-operation controls and compound tasks built from the same primitives, so the excess *composition* failure rate is measured rather than assumed from an aggregate score. The checker must reject malformed, incomplete, timed-out and unverified outputs under one frozen rule while reporting format failures separately from semantic wrong answers. No unblinded model-specific parser choices should be made on sealed outputs. The same prompts and validator apply to every exported artifact, and a small independent manual audit should check that the validator accepts semantically correct answers and rejects wrong ones before unsealing.

**Concrete prospective replacement protocol.** Use a public development pool that excludes every one of the exposed 200 GSM8K diagnostic rows. Before generating sealed items, choose the iGSM difficulty band and a small sandboxed state-transformation task grammar using **reference-only** development performance, without filtering individual sealed questions by reference success. Freeze generator revisions, task mixture, prompt, chat template, stop rule, maximum generation, deterministic decoding, evaluator code, and an inaccessible evaluation seed list; hash this manifest before any finalist answer is scored. Generate one independent set of numeric iGSM problems and one independent set of new state tasks, with matched single-operation and composite strata in each family. iGSM's [official generator documentation](https://github.com/facebookresearch/iGSM#quick-example) exposes a reproducible `fix_seed` example, the problem/answer pair, and difficulty controls. Use its integer ground truth, but score the model's **last numeric token in a normally completed response** after removing thousands separators, an extraction convention explicitly documented by the [GSM-Symbolic authors](https://github.com/apple-aiml-research/ml-gsm-symbolic/blob/main/README.md#answer-extraction-heuristic). Convert both extracted and ground-truth numbers to exact decimal values; missing numbers, non-finite values, length stops, timeouts and requests errors are incorrect. Keep a separate secondary format-compliance rate for a requested `The final answer is <number>` line, plus truncation and extraction-error categories. Do not require a gold-data `####` delimiter in generated text. The last-number convention can mistake an incidental trailing number for an answer, so audit a blinded sample of public development outputs, settle ambiguous patterns there, and freeze the validator before sealed runs. For the state family, compare the simulator's state after every turn with the expected state, and use a response-path check for read-only actions, matching the two validation modes in the [BFCL V3 primary description](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html#evaluation-metrics). This is a newly generated benchmark inspired by BFCL, not a BFCL leaderboard reproduction; keep JSON or tool-call parse failures as a separate reported metric while counting them incorrect for the primary task result.

**Cache state belongs in the frozen protocol.** [Patodiya's controlled serving study](https://arxiv.org/html/2609.04748v3) (IEEE Access early access, arXiv v3 on 2026-11-05) found that Qwen2.5-7B Q4_K_M on CUDA-offloaded llama.cpp b10434 diverged between cache-hit and recompute trajectories on a mean 82.5% of 80 BFCL episodes across ten fresh server histories, versus 37.4% at F16. This is emitted-token or trajectory **disagreement**, not an accuracy drop. In its separate default-prompt-cache single-history grid, repeating the Q4_K_M cache-enabled arm changed 77.5% of 80 episode trajectories; disabling the server-level prompt cache reduced that to 1/80, with the residual due to an empty versus warm prefix cache. A sealed paired comparison should disable cross-request prefix and server prompt reuse, or explicitly freeze and reproduce cache state, then log the realized cache path for each arm. This GPU result does not establish that our CPU build has the same rates or any resource saving. It identifies a measured inference-state confound that a same-request quality comparison should control.

For this pilot's **decision rule**, require both the fresh Q4_K_M reference and the locked finalist to have a conservative one-sided exact-binomial lower bound above **60% success in each multistep family**, and require a conservative paired lower bound for finalist minus reference to exceed **minus 5 percentage points in each family**. The per-family rule prevents a gain on arithmetic from hiding a collapse on state composition. Allocate total one-sided alpha 0.05 across the two families and three asserted bounds in each, giving alpha 0.05/6 per bound. For each paired bound, use the exact lower limit for the candidate-only proportion minus the exact upper limit for the reference-only proportion, giving each direction half its bound alpha. Fix the independent task count from development diagnostics and expected runtime before generating the sealed seed list. At 300 tasks per family, zero discordances yield a paired lower bound near minus 1.81 points, ten candidate-only and ten reference-only discordances yield near minus 5.88 points, and 15 in each direction yield near minus 7.02 points. Thus a 10% total discordance rate with equal wins has an illustrative expected-count bound that fails the five-point gate at n=300; this is **not** the actual probability of passing. At 400 per family, ten in each direction yield near minus 4.44 points, but twenty in each yield near minus 6.03 points. Determine n from a disjoint pilot estimate of both discordance directions, a predeclared target power, and simulation or enumeration of the locked six-bound rule rather than an arbitrary runtime target. These bounds assume independent items; the four shared templates in each generated family make them optimistic if template clustering is material. Treat the result as a bounded pilot, not a general quality conclusion, and use a prespecified cluster-aware or independent-suite analysis for a stronger claim. Publish both discordance directions, family denominators, format compliance, truncations, and exact bounds. If the public reference cannot clear the intended floor on the chosen grammar, redesign the grammar using development data before freeze or report that this base model cannot support the intended quality claim. Never repair the sealed parser, floor, or sample size after seeing candidate outcomes.

The paired difference bound above is intentionally conservative. [Newcombe's 1998 paired-binomial interval study](https://www.eiti.uottawa.ca/~nat/Courses/csi5388/Newcombe.1998.pdf) finds better coverage behavior for score-based methods than several older paired intervals, and [Tango's 1998 paired-sample paper](https://pubmed.ncbi.nlm.nih.gov/9595618/) derives a score interval for a paired risk difference. A future, **prospectively** revised gate could use one of these methods to improve power, but only after fixing its software implementation and checking simultaneous one-sided coverage and power under the intended family counts and structure clustering. Neither paper validates this project's clustered generator or licenses switching intervals after seeing sealed outcomes; the current exact conservative rule remains the frozen pilot proposal.

Size the sealed paired sample from the public reference and reference-versus-control discordance rate, fix a one-sided noninferiority margin and absolute success floor before any sealed run, and publish the paired contingency counts and confidence bound. Low absolute success can make a zero paired gap meaningless: the present 5%/5% result illustrates that failure. A public benchmark can remain a development diagnostic, but the final method claim needs a freshly generated multi-family task gate plus task-level CPU cost through any permitted retries. iGSM measures a narrow synthetic arithmetic distribution and BFCL measures tool use; neither alone establishes broad model capability or frontier parity. [GSM-Symbolic](https://proceedings.iclr.cc/paper_files/paper/2025/file/663865ea167425c6c562cb0b6bcf76c7-Paper-Conference.pdf) specifically finds accuracy varies with changed numeric instantiations, which motivates new seeds rather than treating one public sample as stable generalization evidence.

The proposed contribution is **allocation using actual packed tensor bytes, runtime repack behavior, and whole-request CPU and RAM observations together**, under a sealed benign quality constraint. QPruner already joins physical pruning and mixed precision; GRASPrune learns physical masks; HSP uses CPU latency and memory models; SQuaRE formulates joint sparsity/precision. A new allocation objective or positive Q4_K_M deployment result would have to beat those closest controls where reproducible. It would not establish a new principle merely by showing a smaller GGUF. The first host's corrected 14-tensor pilot is a measured warning that repack policy can reverse the RSS sign.

**Adversarial novelty test.** The corrected 14-`ffn_down` tensor map is a checkpoint-specific probe, not an algorithm or evidence of transfer. Reproduce it, a RAMP-like bit-only allocation, and whole-format Q4_K_S from the same source checkpoint and pinned quantizer. Give the RAMP-like arm the same calibration budget and per-layer bit search, then match the finalist's *complete* bytes within a locked tolerance. Q4_K_S is a fixed whole-format control: record its actual complete-byte gap, and call it byte matched only if it falls within that same tolerance. Report if a faithful RAMP reproduction is unavailable and label the arm an approximation. Evaluate every arm under the same repack setting and sealed benign quality bound on two CPU classes. The proposed shape/type/repack selector has a distinct method claim only if it picks a better `R/C/Q` tradeoff than the matched-byte RAMP-like arm and Q4_K_S where size comparable, then reproduces the selection on a second base model. If either matched-byte control is quality noninferior with equal or lower process/cgroup peaks and full-request CPU-seconds on both hosts, the method claim fails even if the 14-tensor probe saves 4.45% of its GGUF. Failure to reproduce an external method limits any claim to beating the *documented local control*, not the published method.

1. **Lock artifacts and budgets.** Choose one source checkpoint and tokenizer, the same llama.cpp commit, a Q4_K_M reference, aligned physically trimmed MLP widths, and quantizer-supported tensor maps. Serialize every candidate, hash it, parse its full tensor census, and record all installed runtime/tokenizer/auxiliary bytes. Select the proposed allocator only from disjoint public development tasks and profiled runs. Hold candidate recovery tokens, optimizer steps, teacher tokens, and training hardware budget equal to the sequential controls, or report an explicit compute-adjusted comparison. Do not tune on the sealed tasks.
2. **Use two kinds of baseline.** For feasibility, compare with the same-base Q4_K_M reference. For method novelty, compare with (a) same-source whole-format Q4_K_S and untrimmed target-size mixed quantization, including a RAMP-like per-layer bit allocator, (b) globally finer quantizer granularity when the runtime supports it, (c) sequential physical trim then quantize and quantize then trim, (d) a source-matched QPruner-style mixed-precision search or Mosaic-style projection prune, and (e) GRASPrune/HSP-style mask or hardware selection when an exact reproduction is possible. Give the RAMP-like allocator a quality calibration budget and upstream-context scoring comparable to the proposed selector where feasible; report every difference from RAMP because its paper does not link a released implementation. Equal-byte arms target the finalist's **complete package**, not nominal or effective bits per weight, within a preregistered tolerance such as ±0.5%; if matching is impossible, include the nearest *smaller* control and report the byte gap. The 14-tensor pilot and simple head-only Q4_K arm are lower-cost controls. A method claim requires improvements beyond these controls; unavailable source code limits the claim to an internal ablation, not a superiority statement about the published method.
3. **Measure the whole lifecycle.** On the first host and on a second CPU class with a different instruction set, for example the local x86-64 AVX2 host and a documented ARM64 NEON host, run the **same exported weights** in independently pinned builds of the same runtime revision. For each host, fix thread count, batch, context, cache policy, repack setting, and prompt/output policy for both artifacts. Alternate fresh-process paired requests, record full CPU-seconds from launch through final verifiable answer including retries, process high-water RSS, task-cgroup peak with a documented charge lifecycle, page faults/swap, total bytes and actual token counts. Separately report prefill and decode. Use fixed-token memory stress cases so a candidate that fails early cannot appear to save RAM by shortening work.
4. **Seal the quality decision.** Predeclare benign multistep task categories, success rubric, sample size/power from a public pilot, seeds, noninferiority margin `δ`, absolute floor, minimum worthwhile byte/RAM/CPU reductions, and a one-sided paired confidence procedure before generating final outcomes. Evaluate the exact CPU exports once on the sealed set. Keep completed-task CPU cost, parser failures, invalid outputs, retries, and step-composition errors in the denominator; report task-level uncertainty and category breakdowns.

A nonsignificant quality difference is not proof of noninferiority; require the prespecified one-sided paired bound. If only the first CPU passes, report a platform-specific observation. If external QPruner/GRASPrune/HSP implementations cannot be reproduced, describe the tested approximate controls exactly and avoid claiming to beat those papers. Count all search and recovery compute separately from deployment cost, and give a request-volume break-even for amortizing it.

For that amortization calculation, put one-time search, calibration, teacher, recovery, and export costs in the same measured cost unit as deployment, such as energy or money. If their incremental total is `K` and the finalist saves `s > 0` per completed request against the Q4_K_M reference, the earliest cost break-even is `ceil(K/s)` requests, before extra maintenance or distribution costs. There is no finite break-even when `s <= 0`. Keep this accounting separate from the four deployment gates: a large future request count cannot repair failed sealed quality, higher cold peak RAM, or a slower full request. ## Three next experiments that can beat the 4.45% pilot

The pilot's 49,674,240-byte (4.45%) reduction is the measured file-size hurdle, not proof of a quality-safe deployment. None of these experiments has passed the four-way gate. Use the same base model, pinned CPU runtime, held-out task design, and complete-package baseline for every arm. Keep the sealed suite closed until one candidate and all thresholds are locked. These are falsifiable proposals derived from the source audit, not reported results.

**First decision to make.** Test the physical-width mechanism with one preregistered, K-block-aligned cut against a bit-only arm at the same *realized* package bytes. On the current 1.5B tensor map, a 768-channel MLP cut is the first 256-channel increment whose calculated packed-payload saving exceeds the 14-tensor pilot, and its 59,996,160-byte payload estimate nearly matches the head-only Q4 file's measured 60,166,656-byte complete-GGUF saving. Build that width export once, record its actual dimensions, tensor types, complete bytes, and runtime support, then stop the current 1.5B line if the export inflates or the reference-only dependent-step floor remains unmet. Treat that line as an implementation and cost-model diagnostic only. For a quality claim, select a stronger same-base Q4_K_M reference through the prospective reference-only screen above, recompute an aligned width cut for **that** architecture, and match a head-only or RAMP-like bit-allocation control to its exported complete bytes within a locked tolerance. Give all trained arms the same recovery token and optimizer budget, report any teacher cost, and select one finalist on disjoint development tasks. Freeze new structural templates, instance seeds, parser, prompts, runtime settings, absolute floor, paired noninferiority margin, and sample size from an independent discordance pilot before its sealed evaluation. Measure both cold process/cgroup peaks and full-request CPU-seconds including failures and retries on matched CPU requests; then repeat a passing locked comparison on a second CPU class. Stop the four-gate claim at the **first** failed byte, RAM, CPU, or sealed-quality bound. If the bit-only control is quality noninferior with equal or better RAM and CPU at matched bytes, stop the distinct-width-method claim even if the width file is smaller than Q4_K_M. This test is an incremental, falsifiable deployment experiment until an allocator itself beats faithful prior controls and transfers to another base.

1. **Weight-only gain: compress the separate output head.** The [pinned same-source head-only export](../data/output-head-q4-pinned-map-2026-11-12.json) measures a 60,166,656-byte (5.38%) complete-GGUF reduction from 1,117,320,736 to 1,057,154,080 bytes; exactly `output.weight` changes Q6_K to Q4_K. Compare four prespecified arms from one source: Q4_K_M reference, the corrected 14-MLP-tensor pilot, output-head Q4_K alone, and output-head Q4_K plus the corrected map. Hash complete packages and inspect every realized GGUF tensor type; the combined arm's saving is still a prediction until exported and audited. On disjoint public development data, use unshifted Q4_K as the first control; only if it misses the quality screen, fit a validation-selected softmax shift or a storage-accounted correction. Lock one candidate before sealed evaluation. Reject if another tensor changes unexpectedly, if correction bytes consume the gain, or if sealed quality fails. Then measure process/cgroup peak and full-request CPU-seconds under identical repack settings; the measured file result alone does not pass the joint gate.

2. **Runtime-aware physical-width and precision allocator.** This is the proposed method contribution, separate from published hardware-aware sparsity and mixed-bit methods: choose aligned MLP width, the realized K-quant tensor map, **and** repack policy by exact exported GGUF bytes plus measured CPU allocation and whole-request cost. The smallest useful search is two aligned width cuts, three supported maps, and two repack policies on one source checkpoint and pinned build. Run calibration and any recovery only on disjoint public development data, using the same budget for each arm; record training GPU-hours, teacher tokens, and every complete package. Compare the prospectively selected finalist against the same-source whole-format Q4_K_S, equal-byte sequential pruning then quantization, target-size mixed quantization, a globally finer-granularity control if supported, an HSP-style latency/memory allocator, a Mosaic-style projection prune, and GRASPrune-style parameter-budget mask where reproducible, and the untrimmed Q4_K_M reference. Inspect every realized tensor and allocation trace, then use alternating fresh-process fixed-token diagnostics and public benign multistep tasks before locking one finalist for a sealed suite. Require package-byte saving greater than the pilot's 49,674,240 bytes, both process RSS and controlled-charge cgroup peak below the reference under the **same** runtime policy, a paired full-request CPU-seconds win, and the locked quality bound. Repeat the locked comparison on a second CPU class and base model. Reject if no searched candidate passes all gates, the winning selection disappears on replication, kernel/repack effects are mispredicted, or stronger equal-byte controls match it. A first-host grid result would be a feasibility observation, not a new general method.

3. **Long-context gain: lower KV storage without length or success shortcuts.** Apply one runtime-supported lower-precision KV format to the best byte-saving artifact from experiment 1 and the same Q4_K_M reference. Keep model weights, tokenizer, context window, prompt bytes, generated-token allowance, and memory lifecycle identical. Compare 4,096- and 16,384-token matched-length stress cases, then long benign tasks with objective final checks; record actual tokens, complete CPU-seconds, process high-water RSS, controlled-charge cgroup peak, and swap. Approximate the available raw KV saving at context `T` as `2 × layers × KV_heads × head_dim × T × (bytes_per_element_base - bytes_per_element_candidate)`, before scale metadata and runtime buffers. The necessary break-even is measured RAM saved above those overheads **and** measured whole-request CPU saved after KV dequantization, attention, and any extra retries. Reject if longer contexts are silently truncated, if only the KV allocation estimate improves, if CPU-seconds rise, or if sealed quality falls outside the locked margin. KV compression alone cannot beat the 4.45% model-file hurdle; its combined file must inherit and preserve the experiment-1 saving.

## Current decision

**No breakthrough yet.** The 14-tensor and Q4_K head-only GGUF exports have measured complete-file savings of 4.45% and 5.38%. On this host, their `--repack 0` cold synthetic pilots lowered child CPU-seconds and fresh-cgroup peak against the same-base Q4_K_M reference. The Q4_K head instead raised cgroup peak with default repacking. A Q5_K head-only control saved 2.77% of complete GGUF bytes and lowered process RSS, cgroup peak and child CPU-seconds in four admitted default-repack synthetic cold pairs, with one planned pair excluded under the prespecified checks. These are workload- and runtime-specific resource observations. The exposed GSM8K diagnostic failed its absolute floor under a strict generated-answer delimiter, and the generated two-family reference-only development screen failed the ordered-state floor. No candidate has passed a sealed, adequately powered dependent-step quality test on a competent reference, and no one CPU artifact has demonstrated all four gates on completed benign tasks. The next decision is a reference-only development screen on a stronger, license-compatible same-base Q4_K_M checkpoint, followed by a disjoint structural holdout and the predeclared paired gate above. Until then, the measured resource gains are engineering leads, not retained model capability.
