# AttackGPT: source audit of a near case

26 November 2026. Static review of the [Netskope open-source repository at commit `da274296`](https://github.com/netskopeoss/AttackGPT/tree/da274296de3f7124d264725635eac617c0260bc1), alongside the [BSides Tokyo speaker abstract](https://bsides.tokyo/en/2026/n04/). No code, model, or payload was run. This audit evaluates published evidence for the [Drexel four-link claim](master-feasibility-evidence.md#the-claim-under-test), not the safety or effectiveness of the prototype.

## Observed design in the published source

The [README](https://github.com/netskopeoss/AttackGPT/blob/da274296de3f7124d264725635eac617c0260bc1/README.md) assigns model integration and repair to a controller-side engine and describes a lightweight endpoint stub that receives generated tasks. The [orchestrator](https://github.com/netskopeoss/AttackGPT/blob/da274296de3f7124d264725635eac617c0260bc1/AttackGPT/orchestrator_agentic.py) generates a script for each campaign phase and yields it to the [server](https://github.com/netskopeoss/AttackGPT/blob/da274296de3f7124d264725635eac617c0260bc1/AttackGPT/server.py). The server queues that script as a task, awaits a result, and stores successful output for later phases. A failed required endpoint task aborts the sequence in the reviewed code; that result is not fed into the engine's script-repair loop.

The [engine](https://github.com/netskopeoss/AttackGPT/blob/da274296de3f7124d264725635eac617c0260bc1/AttackGPT/engine_agentic.py) can generate a replacement script after a **controller-side validation failure**, up to five attempts by default in the simple-objective path. The [validator](https://github.com/netskopeoss/AttackGPT/blob/da274296de3f7124d264725635eac617c0260bc1/AttackGPT/sandbox.py) runs the main PowerShell script in a local subprocess and treats exit code zero as success; its separate verification script is ignored there. Python validation is explicitly unimplemented. The engine can skip validation, and its microtask assembly path returns a generated result without calling the validator. Therefore “self-healing” in this source chiefly describes pre-delivery regeneration after local validation errors, not demonstrated automatic repair after a failed endpoint task. The name “sandbox” does not by itself establish security isolation or independent functional verification.

The [stub](https://github.com/netskopeoss/AttackGPT/blob/da274296de3f7124d264725635eac617c0260bc1/AttackGPT/stub.py) keeps polling after tasks. Its Python task path evaluates each received snippet in the stub interpreter with fresh local dictionaries; its PowerShell path starts a separate child process for each task. The published dispatch path does not replace the stub's polling loop or install versioned resident handlers. A received script could in principle have arbitrary side effects, but the source and accompanying documentation do not show it being used to revise the resident stub twice. Consecutive generated tasks are not automatically two revisions of one active payload component.

| Necessary link | Finding from this source |
| --- | --- |
| Continuing identified process | The stub source contains a continuing poll loop; the repository supplies no process-identity run trace across revisions. |
| Model-caused executable resident revision | The controller generates executable task scripts, but no published path or trace links a model output to replacement of the stub's resident code. |
| Two active revisions | The engine can regenerate candidates before delivery; there is no published two-version activation record for one resident component. |
| Independent remote-control result after each | The server accepts task results, but no published run record ties successful remote-control checks to two accepted resident-code revisions. |

The repository tree at this commit contains source, README, and dependency list, without a test suite, execution transcript, or measured trial table. Its speaker abstract promises a demonstration; the source clarifies the architecture but is not an independently observed outcome. This case supports feasibility of **controller-side generation with transient endpoint execution** and a local candidate-repair path. It does not establish Drexel's stricter continuing-process revision chain. These are limits of the reviewed public artifacts, not a claim that the prototype cannot be extended or that an unpublished demonstration did not occur.
