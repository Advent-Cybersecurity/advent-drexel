# Project Drexel: bounded primary-source case update

Advent Cybersecurity, 27 November 2026 (America/New_York). This is a source-only research update. No model, malware, defender product, or candidate code was run. The companion [machine-readable extraction](../data/selected-case-extraction-2026-11-27.json) records every selected case against the same eight fields with a source locator and an explicit `null` for public-record unknowns.

## Question and scope

The strict feasibility claim examined here is: **two distinct model-caused executable-code revisions become active in one continuing remote-access process, and an independent remote-control task succeeds after each revision**. This is an evidence requirement for the proposed research outcome, not a statement that such a system is impossible. In particular, model placement, executable-code authorship, activation, process identity, repeated function, and defender observation are separate facts.

This update **re-extracts nine cases**: seven chosen from the prior 31-case [closest-case ledger](../data/closest-case-claim-ledger-2026-11-26.json), plus the first-party PromptLock announcement and the November 2026 GTIG `exploit_agent` account. The other **22 prior ledger cases were not re-extracted** here. Selection was purposive: one proposed self-rewrite sample, one model-generated task-script sample, a model-directed remote agent with an upgrade feature, a recent field agent operation that spawned a new process, one operator-side multi-agent field account, a controlled defense-evasion benchmark, and three benign live-update comparators. This gives contrary and near-positive examples for each link without treating heterogeneous reports as a prevalence denominator.

The prior [search and evidence protocol](source-search-and-evidence-protocol-2026-11-26.md) and paper v0.4 set the baseline. We used the [PRISMA-S reporting guidance](https://doi.org/10.1186/s13643-020-01542-z) only as a reminder to preserve platforms, dates, exact search strings, and source selection. **This targeted update is not a completed systematic review, a PRISMA-S-conformant corpus, or a census.** There was no preregistered protocol, comprehensive database search, independent dual screening, deduplication flow, or exhaustive full-text assessment.

## Uniform extraction and evidentiary rule

For each selected case, the [JSON](../data/selected-case-extraction-2026-11-27.json) records: (1) inference placement relative to the endpoint; (2) whether model-generated executable content is reported; (3) whether a particular model response can be paired with accepted artifact content; (4) activation of changed code; (5) continuity of the target process and image; (6) two distinct active revisions; (7) a remote-control result after **each**; and (8) defender telemetry. The status vocabulary distinguishes case-specific documentation, a first-party report, an unexercised mechanism, a field not reported in the public source, and a design outside the tested claim. `not_reported` means **unknown from the source**, never “did not happen.” The model-generation field is broader than exact response-to-artifact lineage. A compile or load acknowledgement does not by itself demonstrate an invoked changed function. A PID alone also would not exclude image replacement.

The concise case readings below emphasize the decisive link; the extraction file contains the field-by-field locator.

### Analyzed samples and reported operations

**PROMPTFLUX.** [GTIG's first-party analysis](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools), section “Experimental Malware Using Gemini for Self-Modification to Evade Detection,” describes a sample querying the hosted Gemini API for replacement script code and logging responses. In the examined sample the self-update function was commented out, and GTIG assessed its then-current state as unable to compromise a device or network. The source also describes variations and a requested whole-source rewrite; that does not establish an applied active version in a continuing process. The important negative observation is the **disabled activation path**, not a universal claim about future versions.

**PromptLock.** [ESET's first-party announcement](https://www.eset.com/us/about/newsroom/research/eset-discovers-promptlock-the-first-ai-powered-ransomware/), opening bullets and body, says a locally accessible model provides generated Lua task scripts to the device through an API and calls the sample a proof of concept. “Locally accessible” does not locate the inference server on the infected endpoint. Generated task scripts are meaningful model-produced executable content, but this account does not publish two versions of the resident Go program, an identified continuous process, or after-each remote-access results. This case was absent from the prior 31-case closest-case ledger and is added here as a placement/code-role comparator, not as a Drexel match.

**C2Agent.** The [pinned Unit 42 case report](https://github.com/PaloAltoNetworks/Unit42-timely-threat-intel/blob/d74de078d0cf3227a97076dbc7b7fc504c49fe7e/2026-10-09-C2Agent-malware.txt), sections “AI CAPABILITIES,” “TIMELINE,” and “IMPACT,” reports an LLM-directed host tool loop, a chronology of recovered builds, and an in-memory upgrade capability in version 2.4. These are three distinct observations. The report does not connect a particular model response to a deployed upgrade, trace two active versions through one identified process, or show an independent remote result after each. Runtime acquisition of skills or tools is also not necessarily revision of the implant's own executable code. The model-serving location is not established in the inspected report.

**Cairn field operation.** [AWS's first-party account](https://aws.amazon.com/blogs/security/chinese-nexus-actors-cairn-ai-agents-found-a-zero-day-on-their-own/), “Discovery” and “Zero-day discovery,” describes operator-side agents and a placed Python payload. A **new Python process** imported the payload and established one remote shell. This is strong evidence of an agent-associated remote-control result, but the new process is a categorical boundary: it is not a second active revision in the prior resident process. AWS does not publish a model-response-to-payload-byte chain or a two-revision result sequence.

**GTIG November `exploit_agent`.** [GTIG's 16 November field report](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold), agentic exploitation section, reports an exposed staging server hosting a multi-agent framework that integrates both frontier and local models and drafts/executes exploit candidates. The locality claim refers to an option within **operator-side infrastructure**; the report does not place the model inside an endpoint implant. It supplies no two-revision target process or after-each remote-control trace. Its significance for Drexel is the separation of local inference from endpoint residency.

### Controlled and benign comparators

**BypassGym.** The [author preprint](https://arxiv.org/html/2611.13684), §§4.2–4.3, records model-guided candidate refinement and a credible two-vantage function oracle: endpoint execution plus server-side remote-command and transfer checks. Yet the controller restores a clean endpoint snapshot before **each** submission. Successive candidates are therefore not code revisions in one continuing instance. The authors explicitly exclude detection alerts from the pass verdict; a candidate can pass while being logged or flagged. Its reported pass rates cannot support “undetectable” or an in-process serial-revision probability.

**Kitsune.** The [author paper](https://www.cs.tufts.edu/~jfoster/papers/toplas-kitsune.pdf), §6.1, PDF p. 28, reports a Tor relay updated through versions 0.2.1.18–0.2.1.30 while carrying traffic, including updates under load with no disrupted client TLS connections. This is substantial evidence that carefully engineered live executable updates and connection preservation are possible. The updates were developer-prepared, no model response is tied to them, and Tor traffic continuity is not an independent remote-control command/result after every version. The cited passage does not itself provide OS process telemetry.

**RSInfer.** The [pinned author experiment record](https://github.com/open-agent-infra/RSInfer/blob/bd26c7e1554211a578e733f7e2fc59feb3a21452/doc/rsi/2026-11-11-real-kernels-hot-apply.md), supplementary hot-apply experiment, says one worker accepted nine applies alternating old and new code trees. Its change table and version-specific inference outputs support more than a mere compile claim. The author also describes a failure mode where a committed change later stopped service, showing that acceptance need not imply retained function. No model-response-to-patch chain or independent PID/image trace is published, and the checked service is model inference rather than remote access.

**cl-agent live extension.** The [pinned author conversation](https://github.com/echawk/cl-agent/blob/e6aa53d2b868c9e3fe7b2bfe88bcae3fe0c997be/successful-runs/memory-proposal-chat.txt) contains two byte-distinct model-submitted `memory.lisp` versions and two successful load reports in one logical chat; the contemporaneous [loader](https://github.com/echawk/cl-agent/blob/e6aa53d2b868c9e3fe7b2bfe88bcae3fe0c997be/src/extensions.lisp), `load-extension-file`, calls `load` in the running Lisp image. The transcript functionally exercises the extension only **after the second load**. Thus the record supports two reported in-image loads, but not a version-specific function result between them, an independently identified continuous OS process, or any remote-access result. The relevant static audit is [here](cl-agent-live-extension-trace-audit-2026-11-26.md).

## Synthesis, negative evidence, and limits

The nine cases distribute across different partial links. PromptLock and C2Agent show model-generated or model-directed actions in malware; Cairn shows an agent-associated remote shell but in a newly spawned process; BypassGym shows independently checked remote function after **fresh** candidates; Kitsune and RSInfer show repeated live updates in benign systems; cl-agent approaches model-submitted in-image revision but lacks a function check after its first load. None of the inspected public sources establishes all strict links **in the same unit of analysis**. The result is a public-evidence gap, not an impossibility proof.

There is also no evidentiary basis here for the universal phrase “adapts to any environment” or the outcome “undetectable by defenders.” BypassGym's pass rule omits alerts, GTIG reported detectable/forensically noisy agentic activity, and the other selected reports do not publish comparable alert traces after each revision. A future study should specify an environment distribution and defender observation window before measuring adaptation or visibility; without them, those claims have no testable denominator.

This review inherits publication bias, incomplete public telemetry, heterogeneous source genres, and intentionally selective case choice. The sources may omit events that occurred privately. Conversely, a named mechanism or author summary cannot be promoted to an observed two-change lineage. The exact case extraction is a reproducible **reading of these sources at this cutoff**, not a measured probability of feasibility.

For the next source-only update, seek a primary record that joins version-specific model output to changed-code hashes, successful activation and invocation, stable process/image identity, and a distinct remote-control result after each of two changes. Record defender alerts separately from execution survival. Those are evidence requirements, not directions for building or testing malware.
