# Evo agent: reload mechanism versus model-caused revision evidence

26 November 2026. Static source audit at [rn7s2/evo-agent commit `88af303`](https://github.com/rn7s2/evo-agent/tree/88af30375972a18a05875fec708ca72c3e51f437). This is a benign agent runtime, relevant as an engineering analogue for replacing executable behavior while an interpreter remains alive. We did not run the project or a model.

The [self-extension documentation](https://github.com/rn7s2/evo-agent/blob/88af30375972a18a05875fec708ca72c3e51f437/docs/self-extension.md) describes writing a Common Lisp extension file, loading it into the live image, and invoking a newly registered tool on a later turn. A load is journaled for replay after restart; a bare evaluation is not. The [design](https://github.com/rn7s2/evo-agent/blob/88af30375972a18a05875fec708ca72c3e51f437/design.md) says function redefinition takes effect on the next call, not in an already executing frame. Its `/reload` command is restricted to an idle session, disposes the old extension generation before loading the new one, and can leave old extensions withdrawn if the new build fails. These are important conditions on what “live revision” means: a stable interpreter does not imply stable in-flight execution or uninterrupted plugin function.

The committed [`test-reload-generation-ordering`](https://github.com/rn7s2/evo-agent/blob/88af30375972a18a05875fec708ca72c3e51f437/tests/unit.lisp) writes one fixed probe extension, boots userspace, then reloads it twice by calling `boot-userspace` in the same test process. It checks for exactly one live probe task after each load, no accumulating hooks, and two unloads. The test comment says the earlier incorrect ordering let an old stop closure kill the newly loaded task. This is concrete regression coverage for repeated in-process reload mechanics, but the probe file is unchanged across loads. It does not exercise an LLM-generated edit, distinguish version hashes, or check application functionality after two distinct code revisions. We inspected test text, not test results.

The project therefore supports architectural plausibility of a persistent process accepting future model-authored extension code. It does not supply an observed two-version lineage or a remote-control result after each version. Its own task-liveness check illustrates why an acceptance signal should be paired with an independent function check. No claim is made here that this runtime is deployed as malware or that its test outcome transfers to Drexel.
