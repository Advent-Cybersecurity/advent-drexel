# Architecture and compression source audit, round 2

**Audited 2026-11-13 through 16:08 UTC.** This note supplements [the master evidence](master-feasibility-evidence.md) and [the prior architecture audit](frontier-architecture-research-2026-11-12.md). Scope is benign, general local deployment. The test proposition is one physical model that beats a Q4_K_M export of the same frozen source on complete shipped bytes, peak CPU memory, and user plus system CPU-seconds for completed requests while preserving sealed dependent-step task quality.

## Result

The new sources supply useful mechanisms and close partial comparisons, but no audited source establishes all four gates on one CPU artifact. The strongest physical-byte candidate is [OPTIC's deployed Gemma 4 E4B GGUF](https://github.com/VILA-Lab/optic/blob/main/docs/gguf.md): 2,899,237,408 versus 5,154,941,280 bytes for Google's official Q4_0, with a working direct decoder. Its peak RSS and process wall direction reverse under matched lazy-loading modes, and its GGUF quality evidence is one GSM8K run. [Baarali Edge](https://github.com/benewende-dev/baarali-edge/blob/b8b3bbfe2dbbdf5ea6045593475ae4dcad8d5cdc/bench/resultats.md) has a smaller same-repository IQ4_XS file, lower benchmark-window RSS, and higher CPU decode rate than Q4_K_M on an M1, but no complete-request CPU-seconds or dependent-step gate. [FairyFuse](https://arxiv.org/html/2604.20913) is an informative CPU Q4_K_M lead, yet its ternary candidate received 30B additional QAT training tokens after the common LLaMA-2-7B ancestor and lacks a published packed serving file.

Two negative controls are especially instructive. [Das et al.](https://arxiv.org/html/2608.15693v1) pruned 1% of Qwen3.5-0.8B MLP channels and exported a *larger*, slower Q4_K_M CPU model with lower accuracy when quantization block alignment changed. [Licardo et al.](https://www.mdpi.com/2504-2289/10/5/155) report Q3_K_M using less rounded memory but 50% more end-to-end elapsed time and 12 fewer exact JSON matches than Q4_K_M on 1,000 synthetic requests. Those papers report elapsed time, not full process CPU-seconds. The [multilingual expert-pruning study](https://arxiv.org/html/2611.12240) and [reasoning-length study](https://arxiv.org/html/2606.25519) show why output length, cap hits, and retry cost belong in the denominator, not only decode tokens/s.

[AutoCompress](https://arxiv.org/html/2611.08290) already optimizes physical architecture against profiled serving memory and latency, so a generic hardware-guided architecture search is not novel. Separately, [Das et al.](https://arxiv.org/html/2608.15693v1) report 18 matched GPU prefill/decode pairs and a CPU Table 3 whose pruned artifact grows in GGUF bytes. [LUQ](https://arxiv.org/html/2509.23729) reports CPU llama.cpp Q4_K_M versus mixed IQ1_M/Q4_K_M decode throughput, but its quality scores come from a different PyTorch BiLLM/GPTQ artifact. These are hypotheses to test with one exported file and one pinned CPU harness.

## Selected primary-source audit

The measurements below retain their reported hardware, artifact, workload, and timing denominators. `CPU seconds` means process user plus system time; `wall` means elapsed time. A decode or prefill rate alone is neither one. Model weight bytes, package bytes, high-water RSS, GPU residence, and cgroup peak are separate quantities.

## Falsifiable same-source CPU test

1. Pin a frozen source checkpoint, tokenizer, quantizer, runtime revision, and target CPU. Export its Q4_K_M reference and each candidate from that source. Record every shipped file's SHA-256 and exact bytes, including tokenizers, adapters, routers, indexes, scales, and unpack tables. A separately retrained candidate is an architectural or training comparison with its training cost reported.
2. Freeze two or more benign task families with independent tests and dependent steps. Keep calibration and selection rows disjoint. Predeclare a Q4_K_M absolute success floor, a candidate noninferiority margin, per-family floors, output contracts, and retry/cap policy. Report paired full-sequence outcomes, output tokens, stop reasons, cap hits, and confidence intervals. Repeat calibration draws for a finalist because a row-level interval does not cover compression variability.
3. Interleave paired cold starts and warm requests with GPUs disabled. On identical inputs and caps, record complete packaged bytes `B`, high-water process RSS, fresh-cgroup `memory.peak` under a stated page-cache policy, process user plus system CPU-seconds `C`, wall seconds, load, prefill, decode, checker, router, and retry work. Record actual token counts and failures. A packed candidate must run from its packed representation or include unpack time and buffers. A factorized candidate must include reconstructed matrices in peak memory.
4. Accept only if `B_candidate < B_Q4`, `RSS_candidate < RSS_Q4`, `E[C_assigned,candidate] < E[C_assigned,Q4]`, and the paired sealed quality difference exceeds the predeclared negative margin on the whole suite and each required family. This is a proposed decision rule, not a measured result. Total CPU per assigned task includes failed attempts; CPU per solved task is secondary and must be accompanied by solve rate.

Start with a same-frozen-checkpoint mixed-bit or per-tensor layout sweep plus a same-byte bit-only control. It can fit within the existing small-model cache, avoids training as a first variable, and tests whether the published CPU phase wins survive full requests. If that fails the size or quality gate, proceed to architecture or QAT candidates with their additional training and artifact denominators explicit. Test prompt/output mixtures, because CPU prefill and decode can move in opposite directions.
