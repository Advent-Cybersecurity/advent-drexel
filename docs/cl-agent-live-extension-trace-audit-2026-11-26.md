# cl-agent: two loaded extension versions in one recorded conversation

Advent Cybersecurity source audit, 26 November 2026. This is a static reading of the author's [checked-in conversation transcript](https://github.com/echawk/cl-agent/blob/e6aa53d2b868c9e3fe7b2bfe88bcae3fe0c997be/successful-runs/memory-proposal-chat.txt) and the corresponding [extension tool](https://github.com/echawk/cl-agent/blob/e6aa53d2b868c9e3fe7b2bfe88bcae3fe0c997be/src/tools/extensions-tool.lisp) and [loader](https://github.com/echawk/cl-agent/blob/e6aa53d2b868c9e3fe7b2bfe88bcae3fe0c997be/src/extensions.lisp) at commit `e6aa53d`. The trace is a benign agent-development example, not a remote-access program. No model or code was run for this audit.

## Observed sequence and mechanism

The transcript contains two `write-extension` calls for `memory.lisp` in one recorded conversation. The submitted source strings differ: the second changes the in-memory session table to use weak keys on SBCL and adjusts related code. Both tool results report that the file was written and loaded, enabled for future sessions, and compiled successfully. The tool's then-current implementation writes the file, calls `load-extension-file`, and reports `Wrote and loaded` only after that call returns; the loader calls Common Lisp `load` in the running image. This supports two consecutive successful in-image loads without a recorded agent restart, although the transcript does not log an OS process identifier or image boundary. A later repository version uses a different mutation transaction, so interpretation of this trace must use the pinned historical code.

After the second load, the same transcript records `eval-lisp` checks: `list-tools` includes `remember`, `recall`, and `forget`; calls through `call-tool` store and retrieve entries and then remove a test entry; a hook check observes a one-time memory digest. These are concrete functional outcomes for the second version. The trace does not show a version-specific tool invocation or output between the first and second loads. A successful load report is therefore stronger than a mere file write but weaker than an after-each functional result. Under the paper's qualification rule, the untested first load does not count as a demonstrated active-and-functional revision.

## Relevance and limits

This is one author-committed conversation trace of a model-mediated agent extending its own executable code and revising that extension while its logical session continues. It is a useful near case for model-to-source provenance and live activation. It does not establish independent repeatability, stable OS process identity, remote-control capability, a remote command/result after either version, or a rate of serial revision success. The first installation adds a new extension; the second changes that same extension. The case cannot be treated as a Drexel outcome.

The [current Pi extension documentation at commit `9a4dcac`](https://github.com/earendil-works/pi/blob/9a4dcacb77e6103b4b096380ab5f2e35cb99368b/packages/coding-agent/docs/extensions.md) supplies a contrasting boundary: `ctx.reload()` replaces extension instances for future calls while the current handler still runs old code, and model-triggered reload is deferred until `agent_settled` because Pi does not reload during an active agent run. "Hot reload" does not alone specify when an updated version becomes callable.
