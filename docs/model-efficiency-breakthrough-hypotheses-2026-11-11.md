# Model efficiency: independent evidence audit and testable hypotheses

Reviewed 2026-11-11. This companion note asks whether one deployable model artifact can reduce **complete file bytes, peak inference RAM, and complete-request CPU time together**, while preserving a declared level of benign multi-step task quality. It complements the [master evidence record](master-feasibility-evidence.md) and the [same-base CPU study protocol](mixed-precision-cpu-study-protocol-2026-11-11.md). The search covers publicly available primary work through the review date. A promising single metric is a lead, not a joint result.

## Decision standard

The causal baseline is a fresh Q4_K_M file built from the same verified FP16 source, calibration corpus, quantizer, and runtime as any candidate. The already published Q4_K_M is a separate deployment anchor. Include runtime libraries, codebooks, entropy tables, routing networks, indexes, and any teacher needed during operation in the installed byte total. For RAM, report both process high-water RSS and whole-task cgroup peak in a named cold or resident regime. For CPU, report user plus system seconds per *assigned task*, including model startup when the declared regime is cold, prefill, all generated tokens, verifier calls, failures, and retries. Task quality is correct final sequence completion under the same harness and budget, with a prespecified absolute floor and noninferiority margin. The protocol gives the paired uncertainty analysis. A study that reports only tokens per second, a matrix kernel, a batch throughput gain, perplexity, or an isolated benchmark cannot clear this gate.

The Q4_K_M baseline itself needs a quality check against its FP16 parent. In [Dasari et al.'s *A Generalized Optimization Engine (GOE) for Edge AI Inference Acceleration*, CPU Table 8](https://arxiv.org/html/2608.28652v1), Qwen2.5-1.5B CommonsenseQA accuracy is 0.807 for F16 and 0.733 for Q4_K_M, although its ARC-Easy score is unchanged at 0.747. The four named multiple-choice tasks are not a broad capability evaluation, but this measured gap is enough to prevent assuming that every Q4 baseline has already retained the parent model's capabilities.

## Decision shortlist

1. **Measure, then possibly stop, direct Q4 entropy coding.** Characterize the exact Q4_K_M baseline's tensor and whole-file entropy before building a decoder. Existing whole-file lossless gains are modest and no reviewed CPU system has cleared the joint gate.
2. **Test quantizer-aligned physical pruning.** This is the most direct route to fewer stored bytes *and* fewer CPU operations, but retraining must recover final-task quality and the actual GGUF layout must be checked for format fallback.
3. **Test vocabulary and output-head co-design in a newly trained small model.** A frozen code table plus ternary body has a released 46.2 MB artifact and measured low CPU process RSS, but loses held-out quality. Header inspection shows the paper misstates the comparator GGUF's embedding precision.
4. **Treat a newly trained looped or sparse architecture as a longer-term experiment.** It can reduce stored parameters at matched modeled FLOPs, but early-exit and cache overhead, CPU runtime support, and full-task accuracy remain open.

Task-specific distillation and verified retries are alternatives only if the accepted capability target is narrowed. Neither currently supports a claim of broad model-quality parity at lower file, RAM, and total CPU cost.

A concrete verification result shows both the opportunity and its cost. In [Kang et al., ICLR 2026, Tables 1 and 10](https://openreview.net/pdf/67c8f4a64019d336d7c4fa91e802f7bb4b7c791a.pdf), Llama-3.2-1B-Instruct solves 27.0% of MATH500 with one answer and 53.2% when selecting among 64 sampled answers with a tool-based filter and distilled process reward model. The paper compares that latter score with roughly 51% for Llama-3.1-8B under one greedy sample. The 1B result requires generating and checking many candidates, not a single compact inference; for its generative-verifier route, the authors count a mean 574 solution, 4,431 verifier, and 611 code tokens **per candidate**, then rescale the plotted compute budget by 1.14 for the added code stage. The process-reward route has a different cost, which the authors describe as roughly doubling the per-candidate compute when tool verification is added. The study reports no deployed file bytes, CPU peak RSS, or complete-request CPU-seconds. It supports tool verification on math problems, while leaving the three-resource CPU claim and broad multi-step capability untested.

A concrete bounded-task check is the [tiny-search-reader-60M release](https://huggingface.co/ahkamboh/tiny-search-reader-60M). Its 62M-parameter model answers 206 of 258 supplied-search-result questions correctly in author CPU evaluation, versus 207 of 258 for zero-shot Qwen3-0.6B in a separate Colab BF16 evaluation. The release's 70.2 MB Q8_0 GGUF has a reported 174 MB peak RSS and takes 317 ms for a fixed 449-token prompt plus 24-token answer on a four-thread M1 Pro CPU. The smaller 41.0 MB Q4_K_M file reports 123 MB peak RSS and 205 of 258 correct, but the same request takes 354 ms, so reducing file and RAM alone does not reduce request time even on this narrow workload. The source does not publish user-plus-system CPU-seconds or its peak-RSS collection code. The model requires externally supplied search results, has only 512 tokens of context, and the author reports about one in five test answers wrong; some test mistakes guided later training data, so the 258-item score is not fully blind. The accuracy comparison is not a CPU comparison of identical quantized artifacts and says nothing about broad multi-step capability. It supports specialization as a *bounded* design choice, not full capability preservation.

The reader card's separate 0.28-second Q8_0 `llama-bench` result below is faster than its 317-ms real-prompt run because `llama-bench` measures writing from an empty context; these are different timing campaigns.

An independent [preregistered capability-fragility study](https://arxiv.org/html/2611.11695v1) applied random perturbations, Wanda, SparseGPT, and GPTQ to eight instruction-tuned models across 16 tasks in four answer formats. Within a model, the task-failure order under those compression methods correlated with random-damage profiles at median 0.875, but the authors explicitly found the order did not generalize to long answers; multi-step reasoning became more fragile under pruning. At intermediate damage, 68.4% of induced function-calling errors were format failures, and strict scoring made that task 2.3 times more fragile than content-only scoring. This is opposing evidence to treating a stable aggregate or multiple-choice score as retained final-task capability. It does not itself measure deployed file, CPU RAM, or CPU time.

### Cross-source adjudication of the three near-term mechanisms

| Mechanism | Strongest positive evidence | Strongest opposing evidence and decision |
| --- | --- | --- |
| Lossless coding of an existing Q4 file | The [IJCA Q4_K_M decomposition](https://ijcaonline.org/archives/volume187/number120/rotem-ijca-2026-a71cdd2650e6.pdf) reports byte-exact 1.041 to 1.045 times whole-file compression. [ZipServ](https://home.cse.ust.hk/~weiwa/papers/zipserv-asplos26.pdf) shows that a codec designed with its GPU kernel can reduce BF16 storage and output wall time together. | The Q4 gain is small and has no live CPU result; [MINE](https://arxiv.org/html/2611.09424v2) finds no entropy headroom in the GGUF i-quants it considered, which are **not** Q4_K_M. [Unweight](https://research.cloudflare.com/papers/unweight-2026.pdf) saves BF16 GPU weight bytes but slows batch-one decode from 168 to 100 tok/s. **Decision:** measure the exact Q4 baseline's compressible bytes first; build a decoder only if its measured headroom justifies the CPU and RSS risk. |
| Physical pruning aligned to deployable quantizer blocks | [Muta Compress](https://huggingface.co/timiiowolabi/muta-compress-20260920) shrinks a Q4_0 file 16.9% and reports lower peak RSS, faster CPU decode, and similar or better bounded ARC/GSM8K scores after width pruning, distillation, and partial QAT. [HAP-E](https://openreview.net/pdf/7b49b49ba997c64d5a325d7ab1f2689415522a98.pdf) nearly retains its seven-benchmark mean while meeting a 1.3-times CPU latency-speedup target in an INT8 ExecuTorch pipeline. | Muta omits full-request CPU-seconds, and its tutoring behavior and judged quality do not improve. HAP-E omits deployed bytes, peak RSS, CPU-seconds, and a Q4 result. [GOE](https://arxiv.org/html/2608.28652v1) cuts a Q4 GGUF from 770 to 627 MB and raises CPU decode 58.6 to 72 tok/s, but ARC-Easy falls 0.613 to 0.440 and CommonsenseQA 0.587 to 0.193. [LayerTrim](https://arxiv.org/html/2610.19121v1) and [OverRep](https://arxiv.org/html/2609.06974v1) show task losses despite recovery; [Das et al.](https://arxiv.org/html/2608.15693v1) show a Q4 file growing under misaligned pruning in a separate quantization sweep. **Decision:** test only physically removed, block-aligned structures with recovery and final-task quality; do not combine the quality from one paper with the bytes and speed from another. |
| New vocabulary and output-head design | [Bathula](https://arxiv.org/html/2610.22428v1) reports a released 46.2 MB artifact, 62 MB process high-water RSS, and 615 to 740 CPU decode tok/s against a 253 MB, 446 MB, 130 tok/s learned-table arm. [Amazon Science's vocabulary-pruning study](https://cdn.amazon.science/48/65/6b5c8db74362a04d3ad234831320/scipub-approval152134-50035824-which-tokens-can-a-device-afford-to-score-vocabulary-pruning-by-logmass-maximization.pdf) reports 0.43 versus 0.53 GB of Q4_K_M weight memory after selecting 128k rather than 248k vocabulary rows of the same Qwen3.5-0.8B-Base, with six-language chrF 11.12 versus 11.23. | Bathula ARC-Easy falls 45.9% to 41.0%, its validation loss rises 3.155 to 3.439 nats, and training/runtime differ. Amazon gives no CPU RSS, full-request CPU-seconds, or multi-step outcome for the Q4 pair; its speed results use separate runtime paths. More fundamentally, the paper says it keeps the tokenizer and input computation fixed while pruning only output scoring, but Appendix H counts the tied input/output embedding as physically smaller. It does not explain how excluded input tokens are embedded or whether a full input matrix remains, so its 0.43 GB cannot yet be credited as complete deployment bytes. An independent [vocabulary-grid classifier](https://huggingface.co/mp-juuuns/qwen3.5-4l-vocab40k-en-ko-headless/blob/main/benchmark/README.md) shrinks Q8 file 159 to 98 MiB but increases tokenized document length 1,264 to 1,629 and four-thread CPU document latency 1.346 times. **Decision:** test a same-base Q4 physical vocabulary ablation with full-request CPU accounting and held-out final-task success. |

[ZipServ Section 6.5](https://home.cse.ust.hk/~weiwa/papers/zipserv-asplos26.pdf) clarifies the storage-versus-residency distinction: its GPU prefill path first expands compressed weights into global memory, and its serving manager reallocates static-weight savings to KV cache. Its shorter full-output wall time and smaller weight representation therefore do not establish lower whole-process peak memory. The same section gives 10.83 GB for compressed Llama 3.1 8B weight footprint in its model summary but 11.18 GB of static weights in the RTX4090 Figure 17 breakdown, without reconciling these denominators in the surrounding prose.

No reviewed positive row measures all four of complete file bytes, true process or cgroup peak inference memory, full-request CPU-seconds, and held-out multi-step success on the same CPU artifact. Bathula measures the first two and decode throughput, but its quality declines and it omits whole-request CPU work. This is an evidence gap, not proof that the joint target is impossible.

**Memory streaming exposes a different tradeoff.** A [Qwen3.8-27B Q4_K_M CPU engine's same-file ladder](https://github.com/ManeeshJupalle/Qwen-3.8-in-Rust/blob/main/docs/data/ladder.txt) reports 17.961 GB peak memory and 1.170 seconds per decoded token with all weights resident, versus 5.103 GB and 4.305 seconds per token under a 5 GiB memory cap. Its reported peak is the maximum of job-object committed memory, process working-set high-water mark, and 250-ms sampled working set, so it is not a Linux RSS measure. It reads 13.406 GB from SSD per token in the capped case. The author checked identical greedy token IDs for only three prompts of 32 tokens and used a Windows job-object cap on a 32 GB host, not an 8 GB machine. This is evidence that moving the same Q4 file out of RAM can preserve short deterministic outputs while adding large I/O and wall-time costs; it does not shrink installed bytes, establish final-task quality, or measure complete-request CPU-seconds. Speculative verification improves capped wall time in that engine, but changes the computation and still leaves those gates open.

**A same-base pruned Q4_0 artifact is a qualified positive lead.** The [Muta Compress release](https://huggingface.co/timiiowolabi/muta-compress-20260920) compares a dense 26-layer Qwen2 parent with a width-pruned, distilled, 100-step quantization-aware-trained descendant. The published [parent GGUF](https://huggingface.co/timiiowolabi/muta-compress-20260920/tree/main/step2-26L-dense/gguf) is 713,654,016 bytes and the descendant is 592,887,552 bytes, a 16.9% file reduction. The author's four-thread GCP scalar llama.cpp `b10175` comparison reports 809.9 versus 705.7 MB peak RSS, 13.15 versus 15.51 decode tokens/s, nominally held-out ARC-Easy-500 70.0% versus 73.4%, and GSM8K-100 exact-answer accuracy 49% versus 53%. The capability differences are individually statistically inconclusive, and its blind-judge answer quality is level or lower. The card's later audit discloses one GSM8K test item in training and near-duplicates in both test subsets, so these evaluations are only nominally held out. A separate 50-dialogue tutor probe scores both near 3.25/10 and finds the descendant tells the answer or states a falsehood in 33 to 40 of 50 turns. The linked raw GitHub repository was unavailable at review time, so the RSS collection method and exact paired execution cannot be independently audited; the release gives no complete-request CPU-seconds or held-out multi-step success. The result supports trying structure removal with recovery for a bounded task, but does not clear the joint gate or show broad capability preservation.

**An apparent same-source win fails output inspection.** The [Kuza Gemma 4 E2B release's screening data](https://huggingface.co/kuzaai/kuza-gemma-4-e2b/blob/main/screen/results.json) compare a default Q4_K_M GGUF with a tensor-override Q4_K_M variant from the same BF16 source: file 3.416 versus 2.641 GB, reported CPU benchmark peak RSS 3,797,492 versus 3,040,628 KB, and `tg128` 15.63 versus 17.33 tokens/s with six threads and zero GPU layers. Its reported 0.479 hidden-set score is identical across both artifacts, but the linked [default](https://huggingface.co/kuzaai/kuza-gemma-4-e2b/blob/main/screen/hidden_q4_k_m_default.json) and [override](https://huggingface.co/kuzaai/kuza-gemma-4-e2b/blob/main/screen/hidden_q4_k_m_ud_style.json) reports mark **all 36 responses empty** and assign partial credit to empty outputs; even the Q8_0 control has all 36 empty. The smoke logs contain zero bytes. Thus its quality gate cannot establish retained capability. The source also reports phase throughput rather than complete-request CPU-seconds, and does not publish the RSS collection method. The physical tensor-override gain may be real, but a repaired generation/evaluation harness is a prerequisite for using it as evidence.

**A CPU packing gain has a narrow transfer condition.** The [Fractal64 Nemotron 30B Q4_0 report](https://github.com/synchopate/llama-modchip/blob/main/docs/NEMOTRON_OPTIMIZATIONS.md) gives 17.59 to about 14.35 GiB of file, 21.71 to 17.27 GiB of post-suite current `VmRSS`, and 19.54 to 25.02 decode tokens/s on its CPU comparison. The [benchmark script](https://github.com/synchopate/llama-modchip/blob/main/benchmarks/eval_quality_and_tools.py) collects RAM with one `ps ... -o rss=` sample after a speed request, so the figure is not a high-water peak; the speed result is a server-reported decode rate, not full-request CPU-seconds. Its 80/80 non-speed points come from a small scripted gate for tool formatting, code, retrieval, and arithmetic, not held-out multi-step completion. The packing opportunity comes from Nemotron expert dimensions 2,688 and 1,856, which cannot use standard 256-value K-quant blocks and otherwise fall back to Q4_0. A Qwen Q4_K_M file already using K-quantized tensors may have no analogous space to save. Replicate on the exact target architecture before treating this as a general Q4_K_M method.

**Fewer quantization bits can cost more CPU work on the exact pinned target model.** [Wen's primary Cortex-A53 counter study](https://github.com/FredWen-S/lowbit-decode-a53/blob/main/a53/summary.md) compares five official Qwen2.5-1.5B-Instruct GGUF formats on one Sonim XP8800, using llama.cpp commit `23deec0`, eight threads, page-cache warming and hardware counters. Its Q4_K_M SHA-256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e` matches our pinned 1.5B inventory. Q3_K_M reduces reported weight bytes from 1,060 to 876 MiB but decodes at 5.38 rather than 5.67 tok/s and executes 1,906 rather than 1,637 million instructions per token. A [separate desktop CPU accuracy evaluation of the same GGUF hashes](https://github.com/FredWen-S/lowbit-decode-a53/blob/main/accuracy/README.md), using llama.cpp commit `42916d8`, reports WikiText-2 perplexity 11.64 versus 10.80 and MMLU 33.9 versus 35.9. The authors corrected an earlier, noisier speed sweep that incorrectly showed Q3 faster. Their `Weights` measure is tensor bytes from `llama-bench`, not complete installed bytes; their speed is decode phase only, and there is no process peak RSS, whole-request CPU-seconds or held-out multi-step quality. On this specific older ARM CPU, dropping to Q3 fails the CPU and measured-quality gates even before those missing metrics. The [same project's speculative-decoding arm](https://github.com/FredWen-S/lowbit-decode-a53/blob/main/spec/README.md) cuts target decode from 3.55 to 1.81 or 1.77 tok/s with a 0.5B draft, despite 65.7% or 71.8% acceptance, another warning that adding conditional inference can increase CPU work.

The exact tensor inventory matters even when a file is named Q4_K_M. Our [pinned local GGUF inventory](../data/mixed-precision-baseline-tensor-inventory-2026-11-11.json) confirms that Q4_K tensors occupy only 6.06% of the Qwen2.5-0.5B file's 485,452,288-byte tensor payload; Q5_0 and Q8_0 occupy 54.95% and 30.10%. An independent [inspection of the same SHA-256 file](https://hrletsgo.me/en/documents/447) agrees. By contrast, Q4_K occupies about 68.1% of the 1,111,370,240-byte tensor payload in our pinned Qwen2.5-1.5B file, with about 31.9% Q6_K. Thus the 0.5B distribution is not a general Q4_K_M property. The first entropy screen must count bytes and quantizer types for **every** tensor, including output weights, before forecasting a whole-file saving from Q4 nibble statistics.

For scale only, if the IJCA paper's sample-specific 1.076-times Q4-tensor ratio applied to **only** the Q4_K payloads in our pinned files, the implied whole-file reductions would be about 2.08 MB (0.42%) for 0.5B and 53.45 MB (4.78%) for 1.5B, before a live decoder or index is added. This is a conditional arithmetic illustration, not a measured compression result or a bound for other quantizer types. It makes the target artifact's tensor mix a go/no-go input rather than a minor implementation detail.

The IJCA entropy source has a provenance discrepancy: its [publisher record](https://www.ijcaonline.org/archives/volume187/number120/practical-limits-of-lossless-compression-for-bf16-transformer-llm-weights-with-companion-measurements-on-q4_k-tensors-in-gguf-q4_k_m-files/) names Nimrod and Ariel Rothstein, while the [DOI registry entry](https://api.crossref.org/works/10.5120/ijcaa71cdd2650e6) names Nimo and Ariel Rotem. The title and Q4 whole-file figures match, but the advertised reproduction repository was unavailable at review time. Section 5.3 adds a useful denominator check: its five-stream zstd-19 decomposition reaches 1.0422 times whole-file compression, while substituting the slower mixture-CDF coder for the nibble stream reaches 1.0416 times. The custom coder's tensor-stream advantage does not improve the complete artifact in this setup. The 1.041 to 1.045 times ratio is therefore a published measurement to test against our own artifact, not an independently replicated bound.

**Full-request cost can reverse a per-token gain.** [Lian et al., arXiv v2 (2026-06-29)](https://arxiv.org/html/2606.25519) compare BF16 and GPTQ-INT4 versions of Qwen3-4B on BFCLv4-Multiturn: mean reasoning tokens rise from 6,556 to 7,425 (13.3%), tool calls from 7.56 to 7.85, while success slips from 52.12% to 50.88%. The same paper reports 292 versus 285 seconds for a BBH INT4 versus BF16 vLLM run, despite a separate W4A16 Marlin microbenchmark giving 1.2 to 1.4 times the token throughput. These are GPU-serving results, and the BBH line does not identify the quantizer well enough to pair it with the GPTQ multiturn row. They report neither complete deployed bytes, process high-water RSS, nor CPU-seconds. The transfer to our CPU question is a falsifiable *risk*, not an observed CPU penalty: count generated tokens, all attempts, final success, and user plus system CPU time on each identical task.

**Similar aggregate success can hide lost individual capabilities.** In [Vallecillos-Ruiz et al., arXiv v2 (2026-07-03)](https://arxiv.org/html/2606.27205v2), Llama-3-8B-Instruct's Quanto 4-bit weight variant solves 58 of 525 single-function Defects4J bugs under pass@10 versus 61 for the base model, but only 29 solved bugs overlap. The quantized arm therefore gains successes elsewhere while losing many bugs the base arm solved; near-equal totals do not demonstrate behavioral preservation. Their experiments use Nvidia GH200 GPUs, a Transformers stack, ten sampled patches per bug, and allocated GPU memory rather than complete deployable GGUF bytes or CPU process RSS. This is a quality-gate warning, not a CPU resource result. On our paired held-out task set, report both aggregate final-task success and the per-task disagreement matrix, especially baseline-correct/candidate-wrong cases.

**Local correctness can survive while completed reasoning fails.** In a [recursive puzzle-model study, arXiv v1 (2026-06-25)](https://arxiv.org/html/2606.26488v1), a 6.82M-parameter Maze teacher distilled to an 855K-parameter one-cycle student yields 87.25% cell accuracy but 0% exact puzzles (Appendix K, Table 14). In the same paper's structured-pruning Table 13, the dense Maze model scores 99.52% cells and 86.80% exact puzzles, whereas its 25%-pruned arm scores 86.40% cells and 0% exact puzzles. This is a specialized recursive puzzle model, not an autoregressive language model, and cannot supply our CPU resource comparison. It also shows recovery is possible in a particular architecture and quantizer: under one 256-puzzle Sudoku harness with 16 recursive steps and no test-time augmentation, calibrated per-channel INT4 yields 71.9% exact puzzles versus 73.8% for FP32, while naive per-tensor INT4 yields 10.2% (Table 9). The study's on-device tests use Qualcomm AI Hub and report step latency; they do not measure a complete CPU-only request's user-plus-system time. The applicable experimental lesson is to gate compression on *completed tasks* and test calibration against the same artifact, not to infer broad model parity from cell or token accuracy.

## Ranked hypotheses and kill tests

Ranking reflects plausible value **for the declared CPU joint gate**, not certainty that the intervention works. A separate [CompressionBench verification study, arXiv v1, 2026-11-04](https://arxiv.org/html/2611.06858v1) reinforces the final-task gate: on its Qwen3.8-27B 8 GiB sequence, distillation improved held-out perplexity increase from 5.89% to 5.00% while GSM8K accuracy fell from 88% to 72% across trained revisions. It counts package and resident GPU weights, but its speed is steady GPU decode excluding prefill, not complete-request CPU work.

1. **A fast go/no-go screen for direct entropy-coded Q4 inference.** Measure empirical per-tensor entropy of the actual fresh Q4_K_M payload, including scales and metadata, and bound *complete-file* savings after the tile index and tables. Only build a direct CPU tile-decode kernel if that bound exceeds the prespecified byte target. The candidate must consume compressed tiles without materializing all Q4 weights. Kill it if complete-file savings are negligible, resident RSS rebounds to Q4 size, total CPU-seconds rise, or decoded weights differ. The IJCA PDF reports 1.041 to 1.045 times whole-file lossless compression on five Q4_K_M artifacts, but its author metadata conflicts with the DOI registry and its named reproduction repository is unavailable. Its 1.076 times Q4 tensor ceiling applies to a modeled coder class and sample, not all possible compressors. Tan, MINE, and ZipServ show GPU mechanisms, not a Q4 CPU win; ZipServ is the strongest positive systems example because it reports both lower BF16 weight footprint and shorter full-output GPU wall latency against vLLM. MINE reports little headroom in the GGUF i-quants it examined. In this repo, generic zstd/gzip saved 2.26% to 2.94% on two Q4_K_M files; the more specialized foldz archive saved 5.16% and 7.64%, but its loader cannot infer directly and its restoration was much slower than zstd. These results justify measuring actual headroom, not predicting live inference savings.
2. **Quantizer-aligned physical structured pruning with recovery training.** Remove entire layers, heads, or matrix dimensions that the CPU runtime can skip as contiguous dense work, while keeping all changed dimensions compatible with the target Q4 super-block layout. Requantize a verified same-base source, inspect every tensor's actual GGUF type, then evaluate full-sequence quality under the same training and calibration budget. [AutoCompress, arXiv v1 (2026-11-05)](https://arxiv.org/html/2611.08290v1) is a methodological lead for measuring the target serving engine while searching physical architectures: on RTX 5070, two architectures with the same total and active parameter counts differ 35% in latency. Its actual benchmarks are GPU-only, with no CPU or Q4 comparator. S-SALAAD supplies a training-time structural mechanism, but its CPU result is FP32 prefill only, uses a constructed memory measure, and loses quality at the largest compression budgets. [FineGates, AISTATS 2026](https://proceedings.mlr.press/v300/svirsky26a.html) reports up to 25% lower CPU-only MRPC classification validation wall time for a pruned LLaMA-3.2-1B with about 4% accuracy loss, but gives no CPU model, Q4 artifact, file bytes, RSS, or complete generative-task CPU work; its separate 21%-sparse Llama-2-7B C4 perplexity is 11.75 versus 7.76 pretrained. HAP-E supplies a near-dense seven-task average while meeting a 1.3-times Jetson CPU latency-speedup target, but does not report file or inference RAM. [GOE, arXiv v1 (2026-08-19)](https://arxiv.org/html/2608.28652v1) gives a sharp CPU counterexample on an Intel Core Ultra 7 265U with 14 llama.cpp threads: Llama-3.2-1B pruned Q4 shrinks from 770 to 627 MB and single-stream decode rises from 58.6 to 72.0 tok/s relative to dense Q4_K_M, while ARC-Easy falls from 0.613 to 0.440 and CommonsenseQA from 0.587 to 0.193. GOE does not measure inference RSS or whole-request CPU-seconds. Hildebrand's broad modified-MMLU study finds severe structured-pruning quality loss under its limited recovery budget; MoP's GPU latency gain comes with a large score loss at 40% pruning; HSP's Jetson CPU latency gain raises peak process RAM; and Das shows that only 1% unaligned MLP pruning can make Q4 files grow. Song and Zheng show that retained pass@k can mask a much larger number of generated tokens per correct final task. Kill the hypothesis if recovery fails the task floor, any fallback expands the complete file, or CPU time rises after counting all retries. Include compute-matched and parameter-matched references so extra training or passes are visible.
3. **Frozen-code vocabulary and output-head co-design.** The released comparator Q4 GGUF embeds its learned table in Q8_0, not FP16 as the paper says. Train matched float-body arms with learned and frozen tables at equal total data exposure, including the pretrained embedding source used to construct the frozen codes. For any low-bit-body candidate, measure installed bytes including runtime and tokenizer, high-water process and cgroup RSS, prefill plus decode CPU-seconds, and paired final-task success. Bathula's released 46.2 MB ternary artifact and true peak-process-RSS measurement show a large physical saving at 270M architecture scale, but quality is lower and decode uses a custom runtime. For a post-training vocabulary ablation, verify how every original input token is embedded and count any retained input table: the Amazon output-pruning paper claims an unchanged tokenizer and input computation while counting a reduced tied embedding in Appendix H, without explaining that path. Kill this route if matched task quality cannot recover without a larger code table/body, if the code scorer erases full-request CPU savings, or if source-model licensing and build dependencies erase the installed-byte gain. This is primarily a new-model research path, not a demonstrated compression of the current checkpoint.
4. **Shared weights with conditional passes and loop-state reuse.** Train a compact looped model with a learned exit policy, then test whether selective passes and KV reuse give a smaller artifact and lower full-request CPU work. A direct retrofit of an already trained checkpoint is a weak default: [Sukthanker and Cameron, arXiv v1 (2026-10-30)](https://arxiv.org/html/2610.42030) compare equal-parameter and equal-inference-FLOP controls from 0.8B to 9B. Only the 0.8B learned loop improves both controls on GSM8K and MATH-500. At 4B, matched short-fine-tune macro accuracy is 82.7% unlooped versus 82.3% looped; at 9B it is 86.5% versus 85.9%. Their H100 serving test shows the loop increases batch-one decode latency 20.6 to 25.3 ms/token at 0.8B, 29.2 to 36.8 at 4B, and 29.4 to 36.0 at 9B, with no reduced batch-one peak GPU memory. The paper gives no CPU benchmark, complete file measurement, or multi-step agent outcome. This strengthens the requirement that any shared-weight candidate be trained for recurrence and be evaluated against both equal-parameter and equal-compute controls. Marchenko shows 36% of dense parameters at equal inference FLOPs but slightly lower task quality. [RecurrentGPT, arXiv v1 (2026-08-15)](https://arxiv.org/html/2608.15062v1) gives a more controlled tradeoff: a newly trained 288M model versus a 774M dense twin at matched modeled forward FLOPs, both trained on about 9.8B tokens, scores 42.08% versus 42.05% across nine zero-shot tasks. Yet compiled GPU generation takes 3.67 versus 3.33 ms/token at batch four and 1,024-token prompt, while measured peak GPU memory falls 1,570 to 639 MB. The paper does not report deployed file bytes, CPU work, or final multi-step outcomes. Its recurrent KV cache erodes memory savings at batch 32 unless K/V is shared, which itself needs a task-quality check. [Lee et al.](https://arxiv.org/html/2605.09165v2) show a 216M-parameter looped MoE versus 246M dense comparison at matched training FLOPs, with 39.6% versus 38.7% Core-9 mean, but their exit savings are modeled FLOPs and they report no real throughput or final-task outcomes. Monea shows that training a shared context cache can raise quality while shrinking that cache, but the 1.01B five-loop point costs 3.75 times the decoder FLOPs of a same-parameter standard model. TaH2 raises ten-task quality from the same 1.7B base, but its same-checkpoint artifact adds 2.6% parameters and its served AIME26 latency rises 30 to 34%, despite an improved quality versus compute frontier. [Ekbote et al. (2026-10-29)](https://arxiv.org/html/2610.40325v1) find that independently parameterized depth generally beats specialized loops at comparable training FLOPs for 70M to 300M models; their GSM8K, MATH, and code evaluations are teacher-forced likelihood, not final-answer or passing-program accuracy. [Mu et al., TACL 2026](https://aclanthology.org/2026.tacl-1.30.pdf) give a useful denominator check for a different sharing scheme: sixfold compression of LLaMA3-8B Q/K matrices saves only 3.74% of total parameters, while GSM8K chain-of-thought falls from 51.71% to 45.94%; their A800 full-generation wall latency falls from 35.43 to 33.69 s in one batch-8 setting. These are GPU measurements, not CPU work. FlashLoop and LoopDuet show GPU runtimes can reduce existing looped checkpoints' KV or serving time, while their weight files stay unchanged. Kaplan's early-exit study is the critical task-quality warning: a gate that appears faithful on individual tokens can fail most final arithmetic answers. Kill the combined approach if extra passes or KV state erase RAM/CPU savings, or final-task quality fails. A retrofit loop on the same checkpoint is not weight compression.
5. **Task-bounded distillation, conditional on a narrower product objective.** Train a smaller student for a declared benign workflow and score whole tasks. The 62M search reader nearly matches a 596M general model on 258 snippet-answer questions with a ninefold smaller Q8_0 file and 5.4-fold shorter fixed CPU benchmark wall time, but no comparator peak RSS or total CPU-seconds, and its capabilities are deliberately narrow. NanoVDR demonstrates a narrow text-query path with large model-byte and query-latency savings but loses image-query capability and relies on an 8.2 GB offline index. CHOP shows standard on-policy distillation can worsen final task resolution despite local-step learning. SCoRe gives a stronger positive composition result: a 7B student matches a tool-prompted 72B teacher's mean over eight reasoning tasks after training on the student's earliest errors, but both rely on tools and no deployment resources are measured. Gan's same-size ALFWorld comparison suggests that short task-stage labels can help subgoal transitions when demonstrations are limited, but it scores three times as many candidates per decision and does not measure full latency. [Kang et al., ICLR 2026 T1](https://proceedings.iclr.cc/paper_files/paper/2026/file/776a5f2c7d6dd4b0d83145fc044e2726-Paper-Conference.pdf) improves a 1B verifier on MATH500 with executable checks, but the reported 8B comparison uses up to 64 candidate solutions for the 1B system against one greedy solution for 8B. At 64 candidates, the 1B tool plus PRM arm scores 53.2% versus 47.4% without tools; its reported per-candidate average includes 574 generation, 4,431 verifier, and 611 tool-code tokens. The paper reports no file, RSS, or total CPU comparison. Test stage supervision and verifier use against matched training and **total inference CPU** budgets. Include any runtime teacher, index, verifier, and failed attempt in bytes/RAM/CPU. Kill the hypothesis if final-task quality falls below the absolute floor or full-system resource savings disappear. This does not answer the original broad-capability question unless the accepted objective explicitly narrows.

**Conditional verified-retry alternative.** Galanti et al. show that a smaller code model can recover a larger one's one-shot accuracy with two to eight attempts while using less memory and, on some GPU and Apple Silicon workloads, less wall time and energy. Their Apple 7B versus 14B HumanEval+ two-attempt result is a useful practical lead; the B200 7B versus 32B eight-attempt result is stronger on speed but uses a high-end accelerator. This is conditional on accessible executable checks and sufficient hardware parallelism. The same study has a counterexample: eight attempts from 3B on MBPP+ lose the Apple wall-time advantage. Test two- and four-attempt caps on a CPU-only same-base or predeclared model-size comparison, with the verifier packaged and all candidate generation and test execution counted as full-task CPU-seconds, peak RSS, and installed bytes. Kill it if verification cannot distinguish good candidates, retries erase CPU savings, or a larger model solves tasks the smaller one never reaches within the cap. Neither benchmark-visible tests nor accelerator batching justify a general frontier-quality claim.

**A composition-focused quality gate.** [Sinha et al., ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/file/3b4e1336f775c3dba16ebbb8d2afd258-Paper-Conference.pdf) explicitly provide the plan and a key-to-integer dictionary, then ask Qwen3 4B to 32B and Gemma3 4B to 27B models to update a running sum, one key per turn. Over 100 constructed samples, all but the two 4B models have near-perfect first-step accuracy, yet even Qwen3-32B falls below 50% mistake-free task accuracy within 15 turns. Counterfactual histories show later accuracy worsens when prior model answers contain errors, beyond the effect of context length. This isolates a failure mode that isolated step benchmarks miss. The paper's thinking mode reduces this effect in its synthetic setup but uses additional generated tokens, and its simple self-verification prompt does not fully resolve it. There are no file, RAM, or CPU measurements. Use its controllable retrieve-and-compose task as an additional held-out quality gate, alongside representative real tasks; count every thinking or checking token in total CPU.

## Evidence still needed

No reviewed paper here demonstrates one self-contained artifact that is smaller on disk, lower in peak CPU inference memory, lower in *complete-request CPU-seconds*, and noninferior on held-out benign multi-step task success versus a same-base Q4_K_M file on the same generic CPU. A joint win remains an experimental question. The closest actionable next measurement is the same-base CPU protocol linked above, followed by entropy characterization of that exact fresh Q4 file. Broad parity with a frontier hosted model is a separate and unsupported claim.
