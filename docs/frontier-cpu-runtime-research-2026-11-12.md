# Frontier CPU runtime and representation study

Updated 2026-11-13 03:48 UTC (2026-11-12 22:48 EST). Companion evidence note for `master-feasibility-evidence.md`. This note asks whether a local language model can reduce complete deployed bytes, **both** high-water process and cold cgroup RAM, and CPU-seconds per complete benign request while preserving held-out multistep task quality against a same-base Q4_K_M baseline. All reported CPU papers below are narrower than that joint test. The findings are generic model-efficiency research.

**Current decision.** No artifact has passed the joint deployment, memory, complete-request CPU, and held-out quality gate. The output-head Q4_K candidate saves 60,166,656 GGUF bytes and improves synthetic CPU and both memory measures with repacking disabled, but default repacking raises cold cgroup peak in two accepted five-pair runs. The Q5_K head has only four admitted favorable default-repack cold pairs, and no candidate has a valid held-out quality result. The reference itself failed the absolute point-rate screen on the current generated development tasks. The next decisive step is a competent, frozen benign task suite, followed by direct paired full-request comparisons under declared deployment flags; a packed-cache prototype or another codec would be premature without that gate.

## Original whole-artifact entropy audit

The [raw results](../data/frontier-cpu-runtime-entropy-2026-11-12.json) are complete enough to recompute the totals and inspect each of 339 tensors. Input was the official [Qwen GGUF release](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF) at revision `91cad51170dc346986eccefdc2dd33a9da36ead9`, `qwen2.5-1.5b-instruct-q4_k_m.gguf`, SHA-256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`. The complete file is 1,117,320,736 bytes; tensor data begins at byte 5,950,496 and occupies 1,111,370,240 bytes. A Linux 6.18.12 Kali x86_64 VMware guest with 8 virtual CPUs and 15 GiB RAM ran Python 3.13.12, `gguf==0.19.0`, NumPy 2.3.5, and `zstd` 1.5.7. The parser read every raw tensor byte in 8 MiB chunks and counted all 256 byte values. For tensor byte frequencies \(p_b\), the diagnostic \(H_8=-\sum_b p_b\log_2 p_b\) is a zeroth-order marginal entropy. It includes quantization scales and metadata embedded in tensor payloads. It does not predict the achievable rate of codecs that exploit within-block structure.

The large F32 percentage is economically small because those tensors are only 0.052% of the complete file. Q6_K occupies 31.8% of tensor bytes and has little generic lossless compression headroom. The whole-file `zstd` result includes the header, tensor payloads, and codec framing. The 1,092,102,183-byte archive was decompressed and its SHA-256 matched the input exactly. The temporary model and archive were removed after measurement. The raw JSON is retained; no model data was committed by this agent.

A second full census partitions the two K block types by the fixed fields in the [pinned GGML definitions](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-common.h). Q4_K's 144-byte block comprises four fp16 scale bytes, twelve packed min/scale bytes, and 128 packed weight-nibble bytes. Q6_K's 210-byte block comprises 128 low-nibble bytes, 64 high-two-bit bytes, sixteen signed scale bytes, and two fp16 scale bytes. Pooled zeroth-order byte headroom across those separate field streams is **4.2728% of Q4_K bytes** and **2.9213% of Q6_K bytes**. Their packed weight streams are less compressible: 3.3909% for Q4_K nibbles, 0.4041% for Q6_K low nibbles, and 5.9534% for Q6_K high two-bit fields. Field partitioning reveals correlations hidden by a whole-tensor byte histogram, but these figures still omit coding overhead and within-block context. They are neither a realized codec ratio nor a universal information bound. The raw JSON includes field byte counts, entropy values, and method. The code read every block of every Q4_K and Q6_K tensor, and the field counts sum back to the original tensor bytes.

**Interpretation.** Ordinary lossless compression of this already-quantized artifact appears unlikely to deliver a large installed-byte reduction. This says nothing decisive about structured coding with bespoke inference kernels or a fresh requantization from higher-precision weights. An archive-size win is also not a runtime win. Standard GGUF execution would have to decompress before loading, increasing startup time and potentially high-water memory, or use a new indexed decoder whose per-token cost has to be measured.

The field-wise census gives 32,335,830 bytes, or 4.2728%, of ideal marginal headroom within its 756,781,056 Q4_K tensor bytes, and 10,341,732 bytes, or 2.9213%, within 354,009,600 Q6_K bytes. Their sum, 42,677,562 bytes, is 3.82% of the complete GGUF before any codec metadata; it is not a proven achievable archive size because field-wise marginal entropy omits correlations and practical coding overhead. Conversely, the 7.6374% measured whole-file `foldz` archive saving exploits a different representation but still has no loadable CPU kernel. [MINE v2](https://arxiv.org/html/2611.09424v2) reports that GGUF **i-quants** it considered had no entropy headroom, but that is a different quantizer family from the Q4_K and Q6_K bytes measured here. MINE's strongest single-stream result uses a 2.1-bit EntQuant checkpoint on NVIDIA GPUs; its documented serve path loads uncompressed checkpoint tensors and then encodes them on the GPU. It does not resolve complete deployed bytes or peak loading RAM for a CPU Q4_K_M replacement. The measured storage headroom warrants a bounded CPU microkernel research branch, but the absent fused CPU backend keeps it behind directly loadable same-base format controls in the near-term experimental order.

The existing [foldz raw record](../data/foldz-storage-check-2026-11-11.json) gives a stronger archive on the **same SHA-256 and 1,117,320,736-byte complete GGUF**: 1,031,986,988 archive bytes, or 85,333,748 bytes saved, **7.6374% of the complete original**. Its byte-exact four-thread restoration took 17.863 wall seconds and 71.341 user-plus-system CPU-seconds, with 1,069,432 KiB process maximum RSS in that archive operation. This is a measured storage result with substantial restoration work, not an inference result. It prevents treating this `zstd -3` test as a maximum lossless compression bound. `foldz` has no compatible inference loader in the tested setup, and the existing restoration measurement does not tell us whether an indexed fused decoder would win or lose on a complete request. The byte-entropy table is a diagnostic for packed GGUF data, not an impossibility proof for structured codecs.

For a naive archive-to-GGUF startup path that performs this same restoration before every request and otherwise leaves inference unchanged, the measured restoration would add 71.341 CPU-seconds per request, before any loader cost. If restoration is performed once for N requests, its measured contribution is 71.341 divided by N CPU-seconds per request; this still provides no CPU saving. These are accounting consequences of the observed restore operation under that explicitly assumed path, not measured end-to-end request times. An indexed decoder fused into a kernel is a different implementation and needs its own measurements.

A related [June 2026 IJCA paper](https://ijcaonline.org/archives/volume187/number120/rotem-ijca-2026-a71cdd2650e6.pdf) reports a **conditional, modeled** 1.076 times Q4_K tensor-stream compression ceiling from a joint within-superblock entropy model on 530 test tensors from three held-out models. Its measured mixture-CDF coder reaches 1.052 times on that tensor stream, decompressing at 38 MB/s in a single-core Sapphire Rapids experiment; a five-stream whole-GGUF method reports about 1.042 times on its own files. These are distinct denominators from our full 1,117,320,736-byte artifact, and the paper's Qwen2.5-1.5B GGUF is listed as 986 MB, so it is not a direct replication. The 1.076 times figure is a ceiling **under the paper's coding model and test corpus**, not a universal limit: the independently measured 7.64% `foldz` saving on our pinned full file is larger and does not create a contradiction. There are provenance limits. The paper points to `github.com/NimoRotem/llm-compression-limits`, which returned 404 on 2026-11-12, and a [separate manuscript mirror](https://www.knowva.ai/) presents different author names and review status from the IJCA page. The publisher PDF is available, but the authors' implementation could not be rerun from that claimed repository. Its 38 MB/s decompression figure is a codec microbenchmark, not inference CPU-seconds.

Tan et al. report 0.6 to 1.0 bits of empirical entropy per weight for generic INT4 symbols and use tile-addressable ANS coding on GPUs. That estimate is not interchangeable with Q4_K_M's mixed tensor payload, which embeds scales and uses groupwise quantization. Their own design discussion says small batches can be decoder-bound, whereas large batches overlap decoding with tensor-core multiplication. The audited GGUF byte census and the GPU paper thus answer different questions. A direct Q4_K_M tile codec would need its own bitstream, loadable implementation, and same-host CPU test.

The [MINE version 2 preprint](https://arxiv.org/html/2611.09424v2), posted 2026-11-09, offers a more relevant *mechanism* than archive-only compression: its GPU kernel fuses entropy decode with matrix-vector multiplication, tunes codec choice per layer and GPU, and falls back to native kernels where coding does not help. The paper states that the maximum 2.52 times and 1.48 times single-stream decode speedups occur on a specially entropy-regularized 2.1-bit EntQuant checkpoint, at effective rates of 2.24 and 3.43 bits per decoder-linear weight on RTX 4060 Ti and RTX 5090. Its bits-per-weight metric covers decoder linears rather than the complete deployed checkpoint. The reported throughput uses the 64-versus-128-token timing difference after a random 512-token prompt, so it removes prefill and startup by construction. The paper also reports 94% of vLLM prefill rate on a 4096-token RTX 5090 test. Its authors say GGUF i-quants they considered showed no useful entropy headroom for their fused kernel, but those formats are not the Q4_K_M tensor mix measured here. The authors also state that MINE selects no new entropy-decoding kernel for many RTX 5090 checkpoints; their reported improvement in those cases comes from selecting existing kernels and compressing the output head, and tighter memory budgets can trade throughput for footprint. A CPU implementation would need its own coding, vector kernel, and complete-request benchmark; the GPU result supplies no quantitative CPU speed or RAM prediction.

Two implementation sources sharpen this screening criterion. The [Fujitsu CPU export guide](https://fujitsuresearch.github.io/OneCompression/user-guide/cpu-inference/) distinguishes bit-exact direct GPTQ-to-GGUF conversion for supported 4/8-bit legacy types from re-quantized 2/3-bit K-format and Q4_K_M fallback paths. Therefore an experiment claiming both a specific GPTQ error correction and a lower-bit GGUF must check the exported tensor map and verify that the correction actually survives. The [DECA paper](https://iacoma.cs.uiuc.edu/iacoma-papers/micro25_4.pdf) models memory supply, vector decompression, and matrix compute separately. Its simulated gain requires new hardware, but its software analysis supports measuring decoder instruction work rather than inferring CPU speed from byte reduction alone. A matched experiment should record memory traffic and vector/instruction counters along with complete-request CPU time where host performance counters are available; any counter result remains diagnostic until the full request gate is measured.

Two phase-aware papers point to different adjuncts, with important accounting boundaries. [Sandwich](https://arxiv.org/html/2507.18454) changes CPU core allocation and kernels at the prefill/decode boundary while keeping one weight copy. Its reported 2.01 times mean end-to-end serving speedup on full-precision Llama models is a runtime effect, not a smaller-file result; phase switching should be considered as an additional factor only after the weight candidate is fixed, so it cannot hide a quantization-specific CPU regression. [Disaggregated Quantization](https://arxiv.org/html/2609.26333) uses one set of weights with phase-specific compute formats, or separately trained prefill weights. The shared-weight form is a possible way to regain quality at unchanged storage for an ultra-low-bit decoder, but its evidence is GPU-based and requires training. The separate-prefiller form stores two checkpoints. Streaming the prefiller from SSD can keep device weight residency flat at long prompts, yet the complete installed bytes increase and the paper's 8K time-to-first-token gain does not include full CPU inference. Its authors explicitly leave multi-turn cache-policy robustness untested, relevant to any retained-capability claim.

## Packed weights, arithmetic, and CPU bottlenecks

The pinned llama.cpp [GGUF block definitions](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-common.h) make the relevant format arithmetic explicit: `block_q4_K` stores 256 weights in 144 bytes, or 4.5 bits per weight; `block_q6_K` stores 256 in 210 bytes, or 6.5625 bits per weight. The audited artifact uses 29 Q6_K tensors occupying 354,009,600 bytes. If each of those same element arrays were instead represented in Q4_K blocks, their static payload would be 242,749,440 bytes, an arithmetic reduction of 111,260,160 bytes, about 9.96% of this whole artifact. This is **not an achieved model**: the original higher-precision checkpoint and a controlled calibration are needed for fresh quantization, the byte count could change with alignment and metadata, and quality may regress. In particular, the output projection is among the Q6_K tensors, so indiscriminate conversion would be a poor assumption.

BITCOS gives a useful constructive case for representation and kernel co-design. For ternary weights with zero fraction \(z\), it stores a presence bitmap plus signs for nonzeros, \(2-z\) bits per weight before scales and framing. Against a five-trit packing at 1.625 bits per weight, the representation wins on weight bits when \(z>0.375\). This is a **different model family** from Q4_K_M and does not preserve an existing Q4 model's behavior. Its authors explicitly separate two regimes: fewer bytes can improve bandwidth-limited decode, while decoding instructions can erase that benefit on a compute-limited small CPU. Their Lunar Lake result is the counterexample. Arm's 64-core Graviton3 result and PolyQ's Ryzen slowdown give independent cautions that the dominant bottleneck changes with machine, thread count, format, and prompt/decode phase.

The simplest useful break-even model for one complete request is:

\[
T_{\mathrm{wall}} = T_{\mathrm{load}} + T_{\mathrm{prefill}} + T_{\mathrm{decode}} + T_{\mathrm{unload}},\qquad
T_{\mathrm{decode}} \gtrsim N_{\mathrm{out}}\max(B/\beta,\, I/\rho).
\]

Here \(B\) is bytes moved per output token, \(\beta\) sustained effective memory bandwidth, \(I\) required compute and unpack instructions, and \(\rho\) their effective issue rate. This is an **analytical wall-time lower-bound model, not a measured prediction of CPU-seconds**. For on-the-fly compression with saved transfer time \(\Delta B/\beta\) and added decode time \(\Delta I/\rho\), a necessary approximate decode win in a bandwidth-limited regime is \(\Delta B/\beta > \Delta I/\rho\). A complete-request CPU-seconds win requires directly measured user plus system CPU time to fall after load, prefill, decode, and codec work are included; shorter wall time alone is insufficient. The peak-memory condition is separate: \(\max_t[\mathrm{weights}(t)+\mathrm{KV}(t)+\mathrm{codec\ scratch}(t)+\mathrm{page\ cache\ charged}(t)]\) must actually fall. A compressor that holds compressed and decompressed copies together may fail it even when installed bytes fall.

A 2026 [GGUF-metadata throughput predictor](https://arxiv.org/html/2609.14864) is a useful falsification check on the simple roofline, although it measured Metal and CUDA offload rather than CPU inference. In a 53 host-file scored cohort, separate `llama-bench` 512-token prefill and 128-token decode runs at three prefix depths produced held-out decode mean absolute percentage errors of 13.1%, 14.4%, and 36.1% on two M4 Max systems and one RTX 5080 when active parameter counts, per-layer KV geometry, and host-format fitted efficiency were used. The zero-prefix prefill model instead missed by 18.7%, 22.2%, and 108.2%; at 16K context it missed by 76.2%, 68.1%, and 133.3%. Each host had only four, five, or two held-out configurations, GPU layer offload was requested but physical residency was not established, and the MacBook runtime revision was not recovered. Thus metadata and byte size may screen decode hypotheses but cannot substitute for measured full-request CPU-seconds, especially for prefill, context growth, or a new CPU backend.

Two systems studies help define the load and offload boundaries. [FlexInfer, EuroMLSys 2025](https://2025.euromlsys.eu/pdf/euromlsys25-38.pdf) tested 4-bit Llama-2 models on a 512 GB AMD 7995WX server with cgroup-imposed memory limits. Its 36.4 GB Llama-2-70B mmap baseline delivered 0.08 to 0.24 decode tokens/s across 10 to 35 GB available memory, versus 0.40 to 1.25 for its direct-I/O/prefetch scheme at the same limits. That is a relevant warning that shrinking resident memory by faulting model pages from storage can impose a large decode penalty. The experiment did not shrink installed model bytes or report complete-request CPU-seconds, measured peak RSS, or task quality. [MAIO, FAST 2026](https://www.usenix.org/system/files/fast26-liu-yubo.pdf) cut model-loading latency by up to 79% among its compared solutions on four Kunpeng CPUs and Ascend NPUs, using a programmable page-cache policy. It also found that eager prefetch can thrash a 64 GB constrained cache. Its gain concerns model loading and service startup on an NPU system, not CPU inference or compressed GGUF. Together these studies motivate reporting cold load, warm compute, cache ownership, and full request separately; they do not establish any candidate for the three-resource gate here.

A closer CPU precedent is [Hu and Adatiya, *Cold Start Latency of Quantized Small Language Models on Serverless CPU Infrastructure*](https://storage.googleapis.com/gweb-research2023-media/pubtools/1046363.pdf), whose PDF metadata is dated 2026-02-26. On CPU-only Google Cloud Run, they report model loading as 55 to 70% of cold request wall time for Q4_K_M across five 270M to 3.8B models. This is conditioned on a roughly 16-token prompt, at most 50 output tokens, and 1 or 2 vCPUs. Their LLaMA 3.2 1B quantization sweep says Q8_0 reaches 12.8 warm tok/s versus Q4_K_M at 12.0 on the 2-vCPU tier, illustrating that more compact weights need not decode faster on every CPU. However, their Table II lists 15.2 tok/s for the same named Q4_K_M model/tier and 6.4 on 1 vCPU, while the sweep prose gives 12.0 and 8.1 respectively; the released [research repository](https://github.com/mingwho/slm-research) contains code and a perplexity CSV, but no raw timing CSV to reconcile these denominators. Treat the Q8_0 reversal as an unresolved reported contrast rather than a calibrated speedup. The authors separately show that changing to a single-model container changed warm inference by 12 to 31%, which they attribute to different runtime compilation. Their quality measure is WikiText-2 perplexity on roughly 50,000 tokens, not completed multistep tasks. They do not give process/cgroup peak RAM or user plus system CPU-seconds for full requests. Their longer 200-max-token Gemma check lowers the cold/warm ratio, reinforcing that a 55 to 70% load fraction is workload-specific. The useful transfer is the need to measure cold and warm requests and actual compilation on the same host, not a predicted resource result for the pinned artifact.

A less mature CPU architecture study, [Poperszky, *Pipeline-Native Transformers*](https://arxiv.org/html/2608.23841), reports that disabling an explicit prefetch thread raises its own 30.9B MoE runtime from 2.58 to 4.96 steady decode tokens/s on an Ice Lake server; removing per-matmul index allocation then reaches 5.94. This is useful evidence that a plausible prefetch mechanism can impose more CPU work than it saves. Its 5.94 versus 4.75 tokens/s comparison with llama.cpp uses a different dense 32B model and is not quality matched. The paper's claim that llama.cpp reads every expert before routing is contradicted by the [pinned llama.cpp CPU `MUL_MAT_ID` implementation](https://raw.githubusercontent.com/ggml-org/llama.cpp/f3b407ca1/ggml/src/ggml-cpu/ggml-cpu.c): it groups routed IDs, skips an expert when its row count is zero, and only then forms that expert's weight pointer. Mapping an entire file at load does not imply reading every expert's weight bytes during each token. This source therefore does not establish an advantage over the pinned Q4_K_M runtime. It gives no complete-request CPU-seconds, high-water RAM, installed-byte comparison, or benign multistep quality. Its 9 to 4.5 MB/token critical-path result is an analytic schedule calculation on a small TinyStories architecture, not measured whole-model byte traffic.

## Why the selective pilot can use more RAM

The [pinned llama.cpp repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5075) supports AVX2 repacking of Q4_K tensors with a compatible output dimension, while the Q6_K selector at this revision lists only Arm NEON branches. Its [CPU_REPACK buffer path](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5148-L5185) allocates through the CPU buffer type, then repacks from the supplied source tensor into that allocation. The [pinned loader](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model-loader.cpp#L1793-L1832) reads from the file mapping and calls `ggml_backend_tensor_set` for tensors already allocated outside that mapping, so the source code permits both the mapped input and repacked output to be resident during load. The pilot host reports an Intel Core i7-12700K and its raw benchmark metadata says `repack: true` and `mmap`. Converting 14 Q6_K down projections into Q4_K can therefore create a resident repacked CPU tensor buffer while the GGUF file remains mapped. This is a **mechanistic hypothesis**, not a measured allocation trace. The observed 55.1 to 61.7 MiB process-RSS increase cannot be assigned entirely to repacking without observing tensor allocation and mapped-page residency.

An [older official llama.cpp issue](https://github.com/ggml-org/llama.cpp/issues/17035), opened 2025-11-05, reported some Q4 models with more CPU RSS than larger Q5/Q6 models; a contributor suggested repacking and the author reported that `--no-mmap` changed the behavior. It is labeled `bug-unconfirmed`, uses a different 2025 build and model, and gives no paired full-request accounting. A [February 2026 Arm issue](https://github.com/ggml-org/llama.cpp/issues/19578) logs about 1,552 MiB CPU_Mapped plus 1,513 MiB CPU_REPACK and reports about 3.2 GB process memory with both versus 1.7 GB with mmap and no repack; it is also labeled unconfirmed and involves Gemma Q4_0. A [May 2026 Intel issue](https://github.com/ggml-org/llama.cpp/issues/23603) reports a Q4_K CPU_REPACK allocation failure and names no repack as a workaround. These reports are not matched to our artifact. A [2026-10-12 author experiment](https://github.com/ggml-org/llama.cpp/discussions/30409) on an OLMoE Q4_K_M model reports a large private-memory difference between repack modes during mmap streaming and separately shows that disk read-ahead can dominate when the model exceeds its cgroup cache budget. That experiment used WSL2 and a native Linux repeat on an EC2 m6id.xlarge x86 instance, both different from the pinned dense Qwen pilot.

The [completed same-host `--repack 0` control](../data/same-base-quantization-pilot-pinned-no-repack-runs-2026-11-12.json) held both artifacts, binary, short synthetic workload, threads, and mmap mode fixed while changing repack mode for both arms. In five alternating pairs, candidate-minus-reference process peak RSS ranged from -49,934,336 to -49,446,912 bytes, CPU-seconds from -1.594 to -0.991, and wall time from -0.423 to -0.262 seconds. The medians are 12.393 versus 11.217 CPU-seconds and 1,211,441,152 versus 1,161,707,520 bytes process peak RSS. These measurements strengthen the repack explanation, but there was no allocation trace or matched cgroup `memory.peak`, and the process totals alone cannot assign the entire memory difference to repacked tensors. As a three-resource **synthetic** screen, the candidate has a smaller GGUF file, lower process RSS, and lower benchmark-child CPU-seconds with repack disabled. Complete installed bytes, quality, longer requests, cold-cache operation, cgroup peak, and second-host transfer remain untested. A complete-request follow-up must record those observables and prespecify the runtime mode, because the same model candidate fails process RSS under `--repack 1`.

The pinned GGML [CPU type-trait table](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/ggml-cpu.c#L292-L328) maps Q4_K and Q6_K to native quantized dot products against Q8_K activations. Thus the no-repack configuration has implemented CPU arithmetic for both formats; a claim that the candidate's lower CPU-seconds comes from lower weight traffic remains a **testable hypothesis**, not a hardware-counter finding. A falsifiable three-resource systems hypothesis is that changing just the 14 down-projection tensors and disabling repack cuts file bytes, avoids the additional repacked copy, and reduces full-request CPU work enough on this i7 guest to clear prespecified margins. It fails if any matched cold or warm complete-request block has a nonpositive practical reduction in process RSS, verified cgroup peak, or CPU-seconds, or if the sealed multistep quality gate fails. Repeating on Arm can test transfer, but a positive i7 result alone would remain host-specific.

**Fresh Q4_K_S format control, preregistered by the parent study.** The [pinned quantizer](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-quant.cpp#L645-L729) defaults both Q4_K_S and Q4_K_M to Q4_K, but applies different promotions: Q4_K_M may use Q6_K for selected `ffn_down` and attention-V tensors, while Q4_K_S uses Q5_K for the first one-eighth of `ffn_down` and the first four attention-V tensors in the relevant branches. Thus the same-FP16 Q4_K_S artifact is a standard-recipe control for the selective 14-tensor candidate, but it is not a one-bit-depth substitution. Its actual tensor map and file bytes were audited, and five matched 512/128 no-repack CPU/RSS runs are reported above. That resource screen showed Q4_K_S using less child CPU than the custom 14-tensor candidate in every pair; it did not measure cold cgroup peak or benign task quality. Q5_K and Q4_K CPU kernels exist in the pinned build, but measured effects remain specific to the host, workload, and repack setting.

**Output-head novelty boundary.** [Muse Glimmer 30B, §7.1](https://arxiv.org/html/2610.24628v3#S7.SS1) directly starts from a llama.cpp Q4_K_M schedule and lowers its untied output projection from Q6_K to Q5_K. Its authors also change the Q6_K and Q5_K group sizes to 128 in their MLX/ExecuTorch conversion, so their statement of negligible degradation does not isolate the head precision change. Their 15-task aggregate is 74.8% for this static Q4KM-derived variant versus 75.7% BF16, with mean response lengths of 10,774 versus 11,070 tokens. Its separate EvoPress allocation selects Q5_K for the head. The pinned [llama.cpp quantizer guide](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/quantize/README.md#L56-L66) already exposes `--output-tensor-type` and tensor-specific quantization, including a [Q5_K output-head example](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/quantize/README.md#L104-L112). **Novelty ranking:** the head-selective idea and implementation mechanism have low novelty because both published prior art and standard tool support exist; the narrower evidence contribution is an exact same-FP16 Q6_K-to-Q4_K GGUF head intervention with one-host paired synthetic CPU, process-RSS, and admitted cgroup measurements. This does not establish an unprecedented format, a new kernel, or any held-out complete-task quality result. [ARCHead](https://arxiv.org/html/2608.02703v1) and [Kadav et al.](https://arxiv.org/html/2609.31291) are additional direct head-compression/repair work, but neither starts from a stock Q6_K GGUF head with the present CPU measurement gate.

**Exact Q5_K output-head control, 2026-11-12 20:23 EST.** The [frozen tensor rules](../data/frontier-cpu-output-head-q5-rules-2026-11-12.txt) quantized the same official FP16 source with the same pinned llama.cpp build and changed only `output.weight` from the fresh Q4_K_M reference's Q6_K to Q5_K. The [tensor and metadata audit](../data/frontier-cpu-output-head-q5-tensor-audit-2026-11-12.json) confirms 339 matching names and shapes, all metadata fields equal, and the other 338 tensor payloads byte-identical. The resulting GGUF is 1,086,325,792 B, SHA-256 `df706338ea8bfa4008fafa9aa27f38060981cbe012939ce4ebb5892cedf76f6f`. Its 160,444,416-byte Q5_K head replaces a 191,439,360-byte Q6_K head, saving exactly 30,994,944 B, or 2.774% of the 1,117,320,736-byte reference GGUF. This is a model-file difference; the runtime and linked libraries are identical for these trials, but a full installed package was not measured. The [pinned CPU repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5075) lists x86 AVX2 Q4_K repacking but does not list x86 Q5_K repacking. That source makes the absence of the Q4_K-head anonymous duplicate a testable prediction on this i7, not an allocation trace for Q5_K.

**Runtime packaging inspection, 2026-11-13.** The pinned `/tmp/drexel-inference-study/llama-b12283/llama-server` executable is 17,864 B. `ldd` resolves six unique libraries inside that build directory totaling 24,127,688 B and ten host-system libraries totaling 15,139,000 B after symlink resolution. The directory also contains fourteen CPU backend `.so` variants totaling 20,695,016 B; `ldd` alone does not identify which are loaded dynamically at inference. The [raw directory inventory](../data/frontier-cpu-runtime-directory-inventory-2026-11-13.json) counts 51 unique regular files excluding symlinks, totaling 58,674,830 B, but includes unrelated tools, so this is neither a minimal package nor a measured install. The runtime files are common to the GGUF arms in the local comparisons. Their **absolute model-file byte differences** therefore persist if deployed with an identical runtime set; the percentage reduction of a complete installed bundle is smaller than the GGUF-only percentage and remains unmeasured until a concrete package is assembled and inventoried.

The [cold-cgroup default-repack retry](../data/frontier-cpu-head-q5-cold-cgroup-default-repack-retry-2026-11-12.json) preserved four fully admitted counterbalanced 512-prompt/128-generation synthetic pairs on the i7-12700K, four threads, `mmap`, `--repack 1`, and the same pinned `llama-bench` binary. ## KV cache and long context

The official [Qwen2.5-1.5B-Instruct configuration](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct/blob/main/config.json) has 28 layers, 2 KV heads, hidden size 1536, and 12 attention heads, so head dimension is 128. At an assumed 2-byte F16 key and value representation, the **logical KV payload** is `2 × 28 × 2 × 128 × 2 = 28,672 bytes` per token, or 28 KiB. It is 448 MiB at 16,384 tokens and 896 MiB at 32,768 tokens, before allocator alignment, index structures, graph scratch, and other runtime costs. These are architectural byte counts, **not observed RSS**. The backend may reserve ahead, touch lazily, or use a different KV type. Long-context measurements therefore need the requested and actual context size, cache type, token count, and high-water RAM. KV compression can reduce runtime RAM, but it does not shrink weight files; a joint candidate must also change deployed weights or packaging, and must test quality at long context.

There are several materially different cache paths to screen. The FAST 2026 [SolidAttention control](https://www.usenix.org/system/files/fast26-zheng.pdf) shows severe task-quality collapse under naive INT4 KV on a related Qwen model; that is a warning against using cache byte savings as a proxy for retained capability. [MetaKV](https://arxiv.org/html/2609.07966) reports a different failure mode: its 4-bit KVQuant path cuts average peak KV allocation to about one-third of FP16 on one GPU stack, yet has over ten times the average request latency and a lower benchmark accuracy. This is specific to its implementation and four-dataset workload, but it makes the CPU-time gate essential. The November 2026 [GAAC preprint](https://arxiv.org/html/2610.38210) instead codes BF16 KV bit-exactly in completed blocks and releases the raw blocks, with a fused GPU attention kernel and a raw fallback for outliers. Its reported roughly 26% resident-KV saving includes fixed-capacity slots. This is an architectural proof of possibility for lossless cache coding, not a CPU result or a ready implementation for the pinned F16 cache. The first transfer check is to sample actual F16 key and value tensors across prompt lengths on the pinned runtime, measure block-level lossless rates and encode/decode CPU cost, and include the uncompressed tail and allocator slots in peak RAM.

Verification can recover exact generated outputs from a lossy cache, but it must be costed at the correct tier. [VeriCache](https://arxiv.org/html/2605.17613) drafts with compressed GPU KV and verifies against a retained full KV cache in CPU memory or storage. Its output-identity claim concerns greedy decoding, apart from hardware nondeterminism. It is an example of preserving output by moving information and work, not by eliminating them. A CPU-only analog cannot claim lower process or cgroup high-water RAM if it retains the full KV in host memory alongside a compressed copy; a disk-backed analog must account for complete deployed storage and load or verification CPU time. This is an accounting inference from the authors' documented design, not a measured CPU result.

The official [llama.cpp server documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) exposes cache-type options and load modes including `mmap`; these describe current code and may differ from the pinned `b12283` test build. A direct `--help` check of the local pinned `b12283` `llama-bench` binary on 2026-11-12 confirmed `-ctk`, `-ctv`, `-lm` with `none`, `mmap`, `mlock`, `mmap+mlock`, and `dio`, plus `--poll` and `-lzm`. Its default `--poll 50` makes a recorded poll setting necessary when comparing CPU-seconds; this command did not test memory behavior. Mapped file pages make process RSS, OS page cache, and cgroup `memory.peak` distinct observables. The [Linux cgroup v2 guide](https://docs.kernel.org/admin-guide/cgroup-v2.html) defines `memory.peak`; Linux [`getrusage(2)`](https://man7.org/linux/man-pages/man2/getrusage.2.html) defines `ru_utime`, `ru_stime`, `ru_maxrss`, and page-fault counts. For the proposed study, isolate each run in a fresh cgroup where possible, record both process high-water RSS and cgroup `memory.peak`, include user plus system CPU-seconds for loading through final token, and report major and minor page faults. Repeated warm-cache and cold-cache runs should be labeled as separate conditions, because file-backed paging can dominate launch behavior.

The cgroup number needs a narrower interpretation when file pages are shared. The [kernel's Memory Ownership rule](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-ownership) says a memory area remains charged to the cgroup that instantiated it, even if another cgroup later uses it. Consequently a fresh request cgroup can report a low `memory.peak` while its process maps and touches a much larger model already cached and charged elsewhere. The pilot's separate diagnostic cgroup peak of about 85 MB alongside process RSS above 1.1 GB is consistent with this mechanism, but does not itself identify which page owner produced the gap. For paired warm-cache trials, treat the new cgroup peak as **incremental charged memory**, not the complete resident model footprint. Record `memory.stat` `anon`, `file`, and `file_mapped` when feasible, along with process VmHWM and page-fault counts. A cold-cache run needs a defined page-cache preparation and the same ownership conditions for both arms; otherwise cgroup peak differences cannot be interpreted as a model-memory comparison.

**Proposed cold-cache cgroup protocol.** For each paired arm and repetition, make a fresh regular-file inode containing a byte-identical, hash-verified GGUF using an explicit read/write copy rather than a reflink or hard link; record its device/inode and file size. This is a measurement copy, excluded from the installed-artifact numerator. Finish writes with `fsync`, close all mappings, then issue page-aligned `POSIX_FADV_DONTNEED` over the file. The [Linux manual](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html) says this only *attempts* to free cached pages and does not discard unwritten dirty pages, so a successful return is insufficient. Immediately before launch, probe the copy's resident pages with [`mincore`](https://man7.org/linux/man-pages/man2/mincore.2.html) without touching their contents, close the probe mapping, and log resident bytes; `mincore` is a momentary snapshot, so run with no other reader of that trial inode. For the first same-host pilot, freeze the acceptance limit at **zero resident file pages** immediately before launching each arm, then reject or repeat any trial above it. If zero residency proves infeasible, predeclare a nonzero tolerance in a new pilot version and label that condition explicitly. The two arms need the same page-residency tolerance. A global [`drop_caches`](https://docs.kernel.org/admin-guide/sysctl/vm.html#drop_caches) can evict clean cache, but it affects the whole host and the kernel warns of performance costs, so it should be reserved for an isolated test machine rather than used during concurrent work.

Create a fresh empty cgroup v2 leaf with the memory controller available for each accepted trial, place the workload process in it **before** model loading or execution, and record its initial `memory.current` and `memory.stat`. The [kernel guide](https://docs.kernel.org/admin-guide/cgroup-v2.html) defines `memory.peak` as the high-water charged usage and `memory.stat` `file_mapped` as mapped cached-file bytes. Record `memory.peak` after completion plus `memory.current`, `memory.stat` (`anon`, `file`, `file_mapped`), `memory.events`, and process VmHWM, RssAnon, RssFile, and per-model mapping RSS at load and during the request. The [proc guide](https://docs.kernel.org/filesystems/proc.html) defines those process fields and notes that `smaps` is a more precise but slower snapshot than `status`. As an ownership sanity check, reject a trial if model mapping RSS is large but its fresh cgroup's `file_mapped` remains far below it; predeclare a quantitative gap tolerance from page size and the intended effect size. Also reject a trial if the model inode was already mapped, the cache-residency check fails, cgroup membership begins after loading, memory controller data are unavailable, an OOM or significant reclaim event occurs, or another workload accesses the trial inode. If these controls cannot be met, report only process high-water RSS for the cold comparison and label cgroup memory unverified. Randomize or counterbalance paired arm order and keep the cold and warm populations separate; repeating on the same inode without renewed eviction can transfer file-page ownership to the earlier cgroup.

**Single-artifact packed-weight hypothesis.** The [XNNPack mapped-cache implementation](https://developers.googleblog.com/streamlining-llm-inference-at-the-edge-with-tflite/) is direct CPU prior art: persist a kernel-ready layout and map it on subsequent starts rather than repacking into anonymous memory. Its [first-party README](https://github.com/tensorflow/tensorflow/blob/master/tensorflow/lite/delegates/xnnpack/README.md) explicitly says a different cache file is required for each model and hardware architecture. More directly, ik_llama.cpp merged [offline row-interleaved GGUF conversion](https://github.com/ikawrakow/ik_llama.cpp/pull/272) and [regex tensor selection](https://github.com/ikawrakow/ik_llama.cpp/pull/274) in March 2025; its [later discussion](https://github.com/ikawrakow/ik_llama.cpp/discussions/323) reports selective `Q4_K_R4` GGUF mmap loading with no runtime repack. This establishes the generic one-GGUF selective offline-packing approach as implemented prior art, although its DeepSeek MoE mixed CPU/GPU report did not measure our four gates and its format is not the pinned mainline AVX2 Q4_K_8x8. The [ONNX Runtime loading guide](https://github.com/microsoft/onnxruntime/blob/main/docs/Model_Loading_Performance.md) independently documents borrowing aligned, mapped CPU initializer buffers, while also showing that eligible kernels may create a separate `PrePack()` layout. Current [llama.cpp OpenVINO documentation](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-openvino/README.md) is a practical caution: its cache-only mode can skip reading source weight pages and import compiled dense CPU graphs, but compiled blobs contain weights and can approach model size **per graph**. The original GGUF remains necessary for metadata, tensor descriptors, and cache identity; the guide says loader prefetch can still request GGUF pages. These separate cache paths can avoid source-weight copying on a later start, but do not establish smaller installed bytes or a direct path in the pinned CPU_REPACK backend. A GGUF-specific experiment would serialize the output head in the exact AVX2 packed layout, make the pinned kernel consume that mapped layout, and deploy **one** loadable model artifact rather than an original GGUF plus a packed cache. The format, loader, and backend compatibility are engineering work, and the test must audit CPU feature variants, packing-version invalidation, tensor metadata, startup faults, and all installed files. Shipping both source and cache could erase the byte saving.

The pinned AVX2 layout has a useful byte-level property. Its [source declares `block_q4_Kx8`](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.h#L48-L55) as 8 scales, 8 minimum scales, 96 scale bytes, and 1024 quant bytes, totaling 1152 bytes. The [ordinary Q4_K block](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-common.h#L323-L338) is 144 bytes, so eight original blocks and one repacked block have the same byte count. The [pinned conversion](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L3572-L3601) groups eight rows and requires `ne[1]` divisible by eight; the audited `output.weight` shape is `[1536, 151936]`, satisfying its row and block divisibility conditions. Thus a correctly serialized, alignment-compatible version of this exact layout could in principle keep the output-head payload at 131,272,704 bytes while avoiding a runtime anonymous repack. This is a struct-size and shape argument, **not** a loadable artifact or runtime measurement. The packed bytes cannot simply be labeled ordinary Q4_K in GGUF and interpreted by the existing loader: the row order and quant layout differ. The pinned [GGUF reader derives row sizes from tensor type](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/gguf.cpp#L726-L760), and [model loading derives tensor strides from type](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model-loader.cpp#L1391-L1416). A new type or explicitly versioned packed segment, mapped loader, and matching CPU kernel/fallback are required; metadata, alignment, executable changes, and fallback bytes belong in the deployment numerator.

There is concrete portability prior art in the same pinned tree. Older hardware-specific prepacked `Q4_0_4_4`, `Q4_0_4_8`, and `Q4_0_8_8` [types are marked removed](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/include/ggml.h#L423-L425), and the [type table instructs use of Q4_0 with runtime repacking](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml.c#L909-L924). This does not disprove a mapped Q4_K layout, but it shows that prepacked-file compatibility has been reversed before. The [Q4_K repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5031) chooses the same `Q4_K_8x8` layout for x86 AVX2 and Arm NEON with integer matrix multiply, while Arm dot product selects `Q4_K_8x4` and other paths differ. The identical layout name is a compatibility lead, not proof that one artifact and kernel work on both machines. The [CPU_REPACK buffer path](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5148-L5184) invokes repack during tensor insertion and allocates a CPU buffer; it has no documented direct mapped-prepacked-head path. Cross-ISA results require an actual second-host load and output audit.

A selective head bypass is not an existing per-tensor CLI switch in this pinned path. The loader [selects a separate output buffer list](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model-loader.cpp#L1211-L1225), but its [CPU tensor-override branch](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model-loader.cpp#L1228-L1259) reselects from the CPU list of extra buffer types. The [model constructs that list](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model.cpp#L1630-L1637) and assigns the output list from device placement. Consequently, merely overriding `output.weight` to CPU does not demonstrate that it avoids CPU_REPACK on this CPU-only host. A per-tensor ordinary-buffer policy or mapped packed-head loader would be a code change requiring its own tensor-map and output-equivalence audit. This is a source-level inference, not a runtime test of an override.

The present data give a falsifiable bound, not a predicted win. The original head change reduces the GGUF by 60,166,656 B, so a replacement packed head can grow by **less than** that amount beyond the current 131,272,704-byte Q4_K head, after incremental format, runtime, and companion bytes are counted, and still beat the reference on installed bytes. Keeping both head representations would fail this particular byte test if the packed copy is head-sized. The traced default-path cgroup difference is about +73 MB, composed largely of about +132 MB `anon` and -60 MB `file` at sampled maxima. If an offline layout truly removes one full anonymous head-sized copy without increasing other peak charges, it could reverse the sign. This condition has not been measured, and the maxima are not synchronized between arms. Instrument the actual output-head `CPU_REPACK` allocation and lifetime first, then implement a one-head mapped-layout prototype and repeat admitted cold pairs. Reject if it still keeps the anonymous copy, requires both on-disk representations, increases peak cgroup charge, or worsens complete-request CPU or sealed quality. The idea combines established packed-cache and mapped-buffer mechanisms with a specific measured failure mode; it is not a new compression algorithm or a demonstrated four-axis result.

**Exact packed-layout break-even to preregister.** Let (B_R=1,117,320,736) B be the reference GGUF, (B_Q=1,057,154,080) B the current candidate, and (H=131,272,704) B its Q4_K head payload. Let (P) be the new on-disk packed-head payload, (I) the incremental format/index/metadata and any required extra installed files, and (D) the new runtime-binary byte delta. If the packed layout *replaces* the Q4_K head rather than accompanying it, the total-install test is (B_Q-H+P+I+D < B_R), equivalently (P+I+D <191,439,360) B. The right-hand threshold equals the [audited original Q6_K head payload](../data/output-head-q4-pinned-map-2026-11-12.json), so the packed replacement and all incremental installed components must fit inside the original head byte budget. Report the actual complete installed closure and any CPU-feature-specific variants rather than relying on this arithmetic alone. A versioned `Q4_K_8x8` artifact might serve both the pinned x86 AVX2 and Arm integer-matrix selection, but this is untested; if a different layout or second binary is needed for a target CPU, count both, and verify that each declared CPU executes its intended kernel. On the resource side, compare the predeclared full-request fresh-cgroup peak and process VmHWM with the same artifact under the same CPU-feature selection. The current default-path candidate is roughly 73 MB *above* the reference on cold cgroup peak. Removing the suspected 131,272,704-byte anonymous allocation would be sufficient only if any new mapped-page, scratch, metadata, allocator, or page-cache charges plus changed timing do not consume that margin. The observed 100 ms components are diagnostic, not an algebraic prediction of a new peak. For CPU, measure user plus system seconds for cold start, page faults, prompt processing, every generated token, output handling, and shutdown or all retries through a complete benign answer. Decode tokens/s alone cannot establish the sign. Use matched controls in counterbalanced blocks: reference Q4_K_M at `--repack 1` and `--repack 0`, current Q4_K head at both settings, and the mapped packed-head prototype on its declared path. Keep separate cold fresh-inode/cgroup and warm repeated-service analyses, freeze practical byte, peak-memory, CPU, and sealed-task quality margins, and reject the packed hypothesis if any declared gate fails. Byte-equivalent tensor decoding tests are necessary for implementation correctness, but do not substitute for paired held-out dependent-step quality against Q4_K_M.

**Streaming source-page reclamation as a separate backend hypothesis.** The current Q4_K-head GGUF plus its default repacked buffer may be able to retain the existing 60,166,656-byte file saving and packed-kernel CPU path without a new serialized tensor type if repacking processes the head in bounded chunks and releases **already consumed** source-file pages before the anonymous destination fills. The [Linux `posix_fadvise` manual](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html) says `POSIX_FADV_DONTNEED` only attempts to free cached pages and ignores partial-page requests; the [Linux `madvise` manual](https://man7.org/linux/man-pages/man2/madvise.2.html) says `MADV_PAGEOUT` may ignore inapplicable pages. Neither call guarantees that pages leave the cgroup charge. Eager prefault or readahead may also charge the head before conversion. Calling either operation **after** the cgroup high-water point cannot undo `memory.peak`. The current [repack setter asserts one full-tensor write](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5153-L5164), so true bounded-chunk loading requires a backend API and conversion change, not just an I/O flag. A decisive instrumented prototype would log page-aligned source ranges, check `mincore` and cgroup `file`/`anon` as destination chunks fill, and verify complete-request logits, faults, wall time, and user-plus-system CPU against the same Q4_K_M and current candidate controls. A screening target would be to avoid more than the worst observed +73,777,152-byte default-path excess *before the high-water event*, with a practical margin; only a directly lower admitted cgroup `memory.peak` and unchanged four-axis quality/resource gates establish success. This could be simpler than shipping an ISA-specific packed model, but reclaim attempts, extra page faults, and changed loading order may erase CPU gains. It is an untested alternative, not an inferred win.

**Direct I/O is not an automatic repack-memory fix.** The pinned CLI [offers `--load-mode dio`](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/common/arg.cpp#L2662-L2678), and its Linux file reader [attempts `O_DIRECT` with a logged buffered-I/O fallback](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-mmap.cpp#L407-L445). Bypassing weight page-cache charge might seem to remove the mapped source half of the Q4_K-head cold peak. The pinned [CPU_REPACK buffer reports no host predicate](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5238-L5254), which [defaults to non-host](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-backend.cpp#L221-L226). In non-mmap loading, [that path allocates a transient read buffer for the entire aligned tensor and then calls `ggml_backend_tensor_set`](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-model-loader.cpp#L1896-L1920). The Q4_K output head alone has a 131,272,704-byte payload, so this staging buffer can replace the source-page charge with anonymous memory during repack. The Q6_K reference head can instead take the direct host-buffer path. This is a source-level reason not to predict a cold cgroup win from DIO alone; a same-mode two-arm cold test would be needed to know its net effect and full-request CPU cost. A streaming, bounded read-and-repack change is distinct engineering work.

Mapped storage can also change the translation and fault path even when the packed payload byte count is unchanged. The [Linux transparent-hugepage guide](https://docs.kernel.org/admin-guide/mm/transhuge.html) documents separate anonymous and file-backed large-page accounting, and the [kernel proc guide](https://docs.kernel.org/filesystems/proc.html) defines `AnonHugePages`, `FilePmdMapped`, page sizes, and mapped-file RSS in `/proc/PID/smaps`. Record those fields for the output-head mapping, major/minor faults, and CPU page-walk or TLB counters where available in each paired run. This is a measurement control, not a prediction that a mapped head will use smaller pages or run slower: file-backed hugepage behavior depends on kernel, filesystem, alignment, and active policy. The CPU acceptance test remains full-request user plus system seconds, regardless of the page mechanism.

For a *screening calculation only*, write the proposed cold cgroup-peak delta as the existing default-path delta minus the actually eliminated anonymous allocation A, plus the incremental mapped-file charge F and all other peak-charge or timing changes S: \(\Delta M_{\mathrm{proposed}}\approx\Delta M_{\mathrm{current}}-A+F+S\). If A were exactly the 131,272,704-byte head, the largest observed \(\Delta M_{\mathrm{current}}=73,777,152\) B leaves a nominal 57,495,552 B for F + S before the sign reverses. This is **not** a measured memory allowance: the peaks occur at different times, anonymous charge is not assigned to a tensor, and a mapped packed format can change page faults and high-water timing. A prototype must show a full-request cgroup peak below the matched reference directly, without relying on this subtraction. A successful cold CPU result must also survive the same request set under a warm server and on a CPU lacking AVX2, with the latter using an explicitly counted compatible artifact rather than silently falling back to a different format.

The pinned `llama-server` binary (build 12283, commit `f3b407ca1`, SHA-256 `64da0db0262aa9a201b27eccc8fdac336bc42ae990c652d31125c6967665187c`) exposes `--repack, -nr, --no-repack` in its own `--help`, with repacking enabled by default. This establishes that the no-repack configuration used in the resource pilot can be selected at the server command line. It does not establish server-level CPU, memory, or answer quality under that setting; the paired resource evidence still comes from `llama-bench`.

**Current quality-screen status.** The parent's pinned reference-only v4 generated dev run reported 5/8 arithmetic and 3/8 ordered-state correct, with 0/16 outputs satisfying its exact final-line format rule and 16/16 stopping normally; [raw reference outputs](../data/generated-quality-dev-reference-reasoned-v4-2026-11-12.jsonl) are a development diagnostic. This reference misses the proposed 60% absolute point-rate screen. No paired output-head candidate v4 result or frozen 300-per-family quality result exists at this point, so the resource pilot remains a resource-only lead. A failed or ill-posed reference screen should prompt development of a solvable, parseable benign task and a frozen rubric before a noninferiority claim; it does not justify loosening the final threshold after inspecting candidate outputs.

**Measurement validity checklist.** A claimed joint resource and quality result needs all of the following in the same report:

1. Pin and hash the shared FP16 source, each complete loadable GGUF, any companion decoder/index files, and the executable; audit the realized tensor map and count all installed bytes. State the runtime flags and CPU topology.
2. Define the request population and complete interval before seeing results. Record prompt, output, retries, and final answer for each benign task; keep cold and warm populations separate. The synthetic fixed-token case is a resource screen only.
3. For a cold cgroup comparison, require a distinct ext4 inode per arm/run, zero model-page residency at both `mincore` checks, workload membership before model load, and a simultaneous `file_mapped` charge consistent with model-mapping RSS. Reject the pair if either arm fails, reclaims pages, hits a memory limit, or has an invalid output. If ownership cannot be established, report process RSS and leave cgroup peak unverified.
4. Report complete-request child user plus system CPU-seconds, child `ru_maxrss` or VmHWM, fresh-scope `memory.peak`, and wall time as different denominators. Record faults, token counts, arm order, and raw paired runs; identify monitor and copy work excluded from child CPU time. Check competing host load and repeat anomalous blocks.
5. Freeze practical byte, process-RAM, cgroup-RAM, and CPU reduction thresholds, plus a paired sealed-task noninferiority margin and absolute success floor, before final task outcomes are inspected. Reject the four-way claim if any resource threshold or quality gate fails. Repeat on a second CPU class before claiming transfer.

## Ranked runtime hypotheses and decisive experiments

The 14-`ffn_down` candidate has a measured synthetic resource advantage over Q4_K_M under `--repack 0`, but a direct same-base Q4_K_S control uses less CPU in all five longer synthetic pairs despite being about 3.94 MB larger. The output-head-only Q4_K candidate is the stronger measured **no-repack** resource lead: it beats both Q4_K_M and Q4_K_S on file bytes, process RSS, and child CPU in the paired synthetic screens, and beats Q4_K_M on admitted cold cgroup peak when repacking is disabled. Under default repacking it loses to Q4_K_M on cold cgroup peak. Its quality is still open. The ranking prioritizes the shortest path to a **complete loadable CPU artifact** under the [mixed-precision protocol](mixed-precision-cpu-study-protocol-2026-11-11.md). None is a demonstrated four-way result. Define prespecified positive practical reductions \(\epsilon_B\), \(\epsilon_R\), and \(\epsilon_C\) for complete installed bytes, **both** process VmHWM and fresh-cgroup `memory.peak`, and user plus system CPU-seconds per complete request. Define a sealed-task noninferiority margin \(\delta\) and an absolute success floor. The candidate passes only if all resource reductions clear their margins on the declared workload and the paired lower confidence bound on candidate-minus-reference final-sequence success exceeds \(-\delta\), with both arms clearing the absolute floor. The thresholds and final task sampling frame must be frozen before final outputs are inspected; observed savings do not set the margins.

The existing paired resource screens hold the repack flag *equal* between arms. If the intended deployment uses a candidate with repacking disabled against a reference that ordinarily runs with default repacking, those exact two configurations need their own counterbalanced paired cold and warm comparisons. The separate no-repack and default-repack sessions cannot be combined into a measured cross-configuration effect, even though their marginal medians look favorable. A full artifact-by-repack factorial would also reveal whether the flag's effect differs by artifact; task quality and complete-request CPU remain independent gates.

**Q5_K control changes the next screen, not the four-gate verdict.** The newly built output-head Q5_K artifact is an existing quantizer-supported format and a direct analogue of the Muse Glimmer head choice. On the pinned i7 with default repacking, its four admitted cold pairs favor it on file bytes, process RSS, cgroup peak, and fixed-token child CPU. This is a useful control to put beside the Q4_K head under both repack settings before developing a new codec or packed format. It is still 29,171,712 B larger than the Q4_K-head artifact, and the planned five-pair Q5_K confirmation was interrupted by cgroup reclaim. Neither candidate has a held-out quality result. The next gate should compare their complete-request CPU and quality on the same benign items, with prespecified practical margins and a sound absolute reference success floor; the i7 synthetic result does not rank their completed-task performance.

The four admitted Q5_K pairs are a directional signal only. Even if their signs were independent under a symmetric null, the one-sided probability of four favorable signs is (1/16=0.0625); the resource axes share the same runs and cannot be treated as independent confirmations. The two rejected fifth-pair attempts provide no favorable or unfavorable sign, and repeated reclaim limits the host-state population to which the accepted result applies. This calculation is illustrative rather than a preregistered significance test.

**Token inflation is a separate CPU break-even hazard.** Let \(n_0,n_1\) be the actual generated tokens needed to reach a completed benign task, and \(c_0,c_1\) be measured average decode CPU-seconds per token on the same request population. Even if \(c_1<c_0\), decode CPU falls only if \(n_1/n_0<c_0/c_1\); load, prefill, extra turns, tool calls, and retries tighten the total-request condition. [Lian et al.](https://arxiv.org/html/2606.25519v2) give a GPU example: on sampled BBH, Qwen3-4B GPTQ INT4 retains 87% answer accuracy while mean reasoning length rises 27.8% against BF16, and the reported whole BBH run takes 292 instead of 285 seconds. Its separate 1.2 to 1.4 times W4A16 Marlin tokens/s is a fixed-token GPU kernel comparison, not the same paired CPU work denominator. The paper uses H100/vLLM and a different model, quantizer, and baseline, so the ratio cannot be transferred to the current GGUF. The decisive local record is achieved tokens and user plus system CPU-seconds through final judgment for every paired sealed task, including failures and retries.


**Prospective quality power and runtime feasibility.** The current [frozen evaluator](../scripts/run_generated_multistep_quality.py) has two families, `arithmetic` and `state`, so 300 tasks per family require at least 1,200 model responses for two arms before retries. Its `BOUND_ALPHA=0.05/6` allocates the joint 5% error budget across two families and three asserted bounds per family, then divides the paired-difference tail budget between the two discordance directions. In a *constructed*, equal-accuracy example with 15 candidate-only and 15 reference-only successes among 300 tasks in one family, its exact-binomial difference lower bound is about -7.02 percentage points. That would miss a 5-point noninferiority margin despite an observed zero-point difference. Under the same constructed 10% discordance proportion and equal successes, the first multiple of 20 to clear the 5-point lower-bound margin is 580 tasks per family: 29 candidate-only and 29 reference-only successes yield -4.964 percentage points. Across the present two families, that design would need at least 2,320 two-arm responses before retries. These are planning illustrations, not observed quality, a power guarantee, or a reason to change the margin after scoring; development discordance and the frozen final design determine the needed sample size. The [reference-only v4 development record](../data/generated-quality-dev-reference-reasoned-v4-2026-11-12.jsonl) contains sixteen completed requests totaling 181.584 seconds of recorded per-request wall time, with arithmetic median 9.812 seconds (range 8.612 to 14.722) and ordered-state median 12.112 seconds (range 10.901 to 13.254). This small development sample excludes model/server startup and supplies no candidate or final-suite time distribution. Budget model loading, prefill, generation, grading, timeouts, and retries using recorded medians and tail times rather than extrapolating `llama-bench` fixed-token rates. Complete-request service CPU-seconds, including server and checker work in the declared lifecycle, have not been measured by the synthetic child-process screens and remain a separate gate.

The next dependency is a valid quality reference. On the best tested generated v4 development prompt, the Q4_K_M reference scored 5/8 arithmetic and 3/8 ordered-state cases, with 0/16 exact final-line format despite 16/16 normal stops; it did not clear the absolute point-rate floor. The public strict-format GSM8K diagnostic also failed its absolute floor. Those failures invalidate a four-gate claim on the present task setup before a candidate comparison. Improve and independently validate a benign dependent-step task family and competent reference, then freeze its absolute floor and sealed holdout without selecting a prompt by candidate outcomes. The smallest subsequent joint experiment is rank 1: evaluate the already-frozen same-FP16 Q4_K_M, output-head-only Q4_K, and Q4_K_S artifacts under the corrected, frozen protocol. Q4_K_S is a simple-format control and beat the 14-`ffn_down` custom candidate on child CPU in every warm 512/128 pair, but lost to the output-head-only candidate in the five direct warm pairs. Pin the source revision, quantizer/build commit, realized tensor map, runtime build, CPU topology, memory configuration, thread count, context, batch size, prompt/output caps, and sampling seed. Hash the complete loadable artifacts and inventory runtime, libraries, and companion files. The output-head map is frozen already; freeze the quality and resource thresholds and task sampling frame before scoring final outputs. Measure a cold launch through final response, a warm repeated request, and a prespecified longer-context condition separately. For each run record achieved token counts, user plus system CPU-seconds, wall time, prefill/decode split, major/minor page faults, process VmHWM, fresh-cgroup `memory.peak`, and complete installed bytes. Repeat each condition in matched blocks, report raw runs and dispersion, and perform paired sealed benign full-sequence evaluation with a fixed rubric. A second CPU class is needed before claiming hardware generality, because BITCOS, Arm, and PolyQ show platform reversals. Perplexity, isolated decode tokens/s, or wall-time gains cannot replace the full gate.

An independent CPU [study](https://arxiv.org/html/2607.20806) illustrates why the quality protocol matters: its Ollama `qwen2.5:1.5b` run reports 53.5% on a 200-item GSM8K subset, but its published [grader](https://github.com/tharada0126/llm_ptme/blob/6309e9ee4d1f6a357cbea9ba030ae72aa75c1f4a/scripts/test_gsm8k.py#L37-L42) accepts a `####` answer and otherwise falls back to the last number anywhere in the response. The model artifact, backend, prompt, and scoring differ from this study's pinned GGUF and strict final-line gate. Its result cannot repair our failed reference gate or establish a candidate effect; it does show that our 10/200 strict-format diagnostic should be labeled a protocol failure rather than an estimate of intrinsic mathematical capability.

A restrictive serial bandwidth model makes rank 2's hurdle explicit. If a decoded token reads \(B_w\) weight bytes at effective bandwidth \(\beta\), the compressed representation uses ratio \(r\), and a separate decoder processes compressed input at \(d\) bytes/s, then \(rB_w/\beta+rB_w/d<B_w/\beta\) requires \(d>r\beta/(1-r)\). Applying the **whole-file storage ratios only as a hypothetical proxy** gives \(d>12.09\beta\) for measured foldz's 7.6374% saving and \(d>43.31\beta\) for zstd's 2.2571%. Actual per-layer weight traffic, cache reuse, compression ratio, overlap, and fused kernels can violate this simple model. The archive restoration times do not measure the needed on-the-fly decoder throughput, and a wall-time inequality does not establish lower full-request CPU-seconds. This calculation is a screening bound, not a predicted speedup.

## Open questions and next source checks

- Identify CPU implementations that keep compressed weights loadable without a duplicate decompressed resident copy, and establish exact decoder instruction overhead on AVX2 and Arm NEON. BITCOS is a ternary proof of principle, not a Q4_K_M retrofit.
- Audit BITCOS source and supplemental test settings, especially prompt length, thread counts, and scale/metadata bytes. Compare actual CPU-seconds for a complete request if source data permits.
- Verify the pinned `llama-server` no-repack configuration under actual served requests. The binary exposes the flag, but the server's complete-request CPU, cold high-water memory, and output quality under it remain unmeasured.
- Find primary studies with **measured** cgroup/process peak, total installed bytes, full-request CPU-seconds, and task quality on the same candidate. Existing evidence in this note does not yet meet that conjunction.
