# Compact-model evidence update: compression, memory, compute, and quality

Reviewed 2026-11-11. This note adds recent primary-source findings to the broader [compact-model review](compact-model-deep-research-2026-11-11.md). The question is whether a model can use fewer file bytes, less active memory, and less CPU work while preserving its measured quality. External study figures below are author-reported; we have not reproduced those experiments. The local measurements in this repository use a CPU-only VM and Qwen2.5 Q4_K_M GGUF files, so GPU results and different quantizers are research leads rather than predicted local gains.

## Define what “preserve” means

Three distinct standards are often called lossless:

1. **Byte-exact restoration:** a compressed file can reconstruct identical model weights. Ordinary archive compression meets this standard, but the restored model still needs storage and work at inference time. Our [GGUF archival test](lossless-model-compression-study-2026-11-11.md) saved 2.26% to 2.94% of the already quantized files and did not measure active inference savings.
2. **Task-level parity:** a changed model scores within a chosen statistical tolerance on selected tests. [Helcig et al.'s 2026 preprint](https://arxiv.org/html/2605.02404) reports this as low as 3.3 bits per parameter for one tested model. This does not establish identical outputs or quality outside the tests.
3. **Next-token distribution fidelity:** Helcig et al. use an expected acceptance rate of at least 0.99, calculated from probability-mass overlap over the top ten candidate tokens at sampled positions. Their tested models needed roughly 5 to 6 bits per parameter on average, with table values from 4.98 to 6.55. Even this stated threshold permits differences and is not byte-exact equivalence. The paper was first posted 2026-05-04 and revised 2026-08-09.

The user's goal of retaining *all* inference behavior is therefore stricter than the task-level parity shown in quantization studies. No cited study establishes that a tiny local model matches a frontier model across every capability. A narrower, held-out quality specification can be tested; universal parity cannot be inferred from a few benchmarks.

**Memory and latency can move in opposite directions.** In [Tan et al.'s Table II](https://arxiv.org/html/2606.15789), SGLang serving of Qwen-14B on one 80 GB A100 at sequence length 1,024 changed GPU weight memory from 27.5 to 18.1 GB. The table reports KV memory rising from 44.1 to 56.3 GB, maximum batch from 47 to 60, throughput from 1,131 to 1,217 output tokens per second, and median time per output token from 71 to 81 ms. The total GPU allocation is about 75 GB in both columns. At sequence length 2,048, the maximum batch changed 23 to 30, throughput 548 to 651 tokens per second, and median time per output token 112 to 125 ms. The paper's abstract and prose instead say 47 to 75 for the first maximum batch; Table II says 47 to 60. We use the table and flag the discrepancy. The table does **not** identify the input weight numeric format for this Qwen-14B comparison; its starting 27.5 GB is not enough to infer one. The paper's broader entropy estimates across formats should not be read as a measured whole-file compression ratio for our Q4_K_M GGUF.

**Lossless compression can save storage and GPU weight memory when the runtime understands the format.** [Fan et al.'s ZipServ, ASPLOS 2026](https://arxiv.org/html/2603.17435), encodes BF16 weights and reports stored weight footprints of 14.96 to 10.83 GB for Llama 3.1 8B, 43.92 to 31.30 GB for Mistral 24B, and 131.56 to 93.52 GB for Llama 3.1 70B. Its GPU tests used one RTX 4090 for 8B and two or four L40S GPUs for larger models, at batches 8 and 32. Mean end-to-end throughput was 1.22× vLLM across its tested cases. This is a distinct result from archive-only compression because the serving engine loads the compact representation. The decode path expands weights in registers, but the prefill path expands them into global memory before matrix multiplication. The paper's separate runtime breakdown gives 11.18 GB of static weights for the 8B case rather than the 10.83 GB storage figure, so those quantities should not be equated. It reports resident weight savings, not a measured peak allocation through load and prefill. It starts from BF16, so neither the compression ratio nor the GPU speedup applies to our already quantized CPU files. Its abstract's “up to 30%” is a maximum across tested models, not a general bound.

**GGUF-aware archiving saved more bytes on both local files, but still needs a runtime.** We compiled [foldz v0.9](https://github.com/nsiddiqui248/foldz) from commit `c1b69d5672a2b44440e3487c3d6dd3980837665f` and compared it with zstd 1.5.7 at `-19 --long=27 -T4` on the same two Qwen2.5 Q4_K_M files. Every restored file matched its original SHA-256 and byte count. One run per method and file produced:

| Input | foldz complete archive / saved | High-setting zstd complete archive / saved | Compression wall seconds, foldz / zstd | Restoration wall seconds, foldz / zstd |
| --- | ---: | ---: | ---: | ---: |
| 0.5B, 491,400,032 bytes | 466,043,596 / 5.16% | 476,500,491 / 3.03% | 49.8 / 43.6 | 47.3 / 0.28 |
| 1.5B, 1,117,320,736 bytes | 1,031,986,988 / 7.64% | 1,089,521,127 / 2.49% | 15.4 / 93.8 | 17.9 / 1.21 |

The prior single-thread [zstd level-nine check](lossless-model-compression-study-2026-11-11.md) saved 2.94% and 2.37%, so the higher four-thread setting changed the byte result only modestly on these files. foldz classified 260.1 MiB of the smaller file as “other” and attributed most of that run's work to one such segment; we did not independently audit its tensor labels. foldz archive operations peaked at 0.78 to 1.11 GiB process RSS across these runs, while high-setting zstd compression peaked near 1.14 GiB. Restoration used 132.5/70.6 user CPU-seconds for foldz versus 0.39/1.56 for zstd on the 0.5B/1.5B files. Timings include file I/O and can vary with host load and cache; these are one-run observations, not an inference result. These are archive-operation costs, **not inference RAM or CPU**. The [measurement record](../data/foldz-storage-check-2026-11-11.json) gives hashes, commands, source revision, and run conditions. The archives and restored copies were deleted after verification.

The [foldz README](https://github.com/nsiddiqui248/foldz/blob/c1b69d5672a2b44440e3487c3d6dd3980837665f/README.md) separately reports byte-identical in-memory tests for nine Q4_K_M GGUF files, with complete-file savings of 7.55% to 12.94% and aggregate 17,094 to 15,614 MiB, or 8.66%. Its percentages use original file size as denominator, and [the source code's total](https://github.com/nsiddiqui248/foldz/blob/c1b69d5672a2b44440e3487c3d6dd3980837665f/foldz.c#L818-L855) includes the container header, index, unchanged bytes, and coded segments. Rounded table values account for hundredth-point arithmetic differences. Its “about 19 MiB/s” is a **combined compression and decompression round-trip** on an eight-thread Android phone, not a measured inference rate or isolated decode rate. Our 0.5B result, 5.16%, is below the author's nine-file range, so that range does not generalize to every Q4_K_M file. The author has not published paired `zstd -19 --long` and `xz -9` results for those nine files. The [pinned source](https://github.com/nsiddiqui248/foldz/blob/c1b69d5672a2b44440e3487c3d6dd3980837665f/foldz.c#L693-L750) indexes independently coded segments by input offset and compressed offset, which makes selective decoding a plausible design question; its shipped command reconstructs the whole GGUF, and no inference-time selective-decode result is reported. The current llama.cpp loader does not read `.foldz` files directly, so this remains a storage-only result until live-format CPU decoding is built and measured. Its file format is explicitly pre-1.0.

**Fast GPU decoding has a setup and a baseline.** [MINE](https://arxiv.org/html/2611.09424), first posted 2026-11-06 and revised 2026-11-09, reports up to 2.52× steady-state batch-one decoding speed on an RTX 4060 Ti and 1.48× on an RTX 5090 against its fastest tested baseline for an EntQuant checkpoint with 2.1 bits of weight entropy. The corresponding effective GPU weight rates were 2.24 and 3.43 bits per weight. The timing subtracts 64-token from 128-token generation after a random 512-token prompt, runs three times, and excludes startup. In its reported 4,096-token prefill on RTX 5090, MINE reached 12,860 tokens per second versus 13,650 for vLLM. The authors screened GGUF **i-quants** and EXL3 and found no useful entropy headroom with their method; they did not build the specialized fused kernels that those formats would require. Those formats are not the Q4_K_M files in our local study. This recent preprint does not demonstrate that CPU inference or complete request latency improves, or that the specific 2.1-bit checkpoint retains original-model quality.

**Extreme compression can lose substantial measured quality.** In [Putzky et al.'s ICML 2026 paper, Appendix E Table E.1](https://arxiv.org/html/2601.22787), one Llama 3.1 8B Instruct EntQuant 2.2-bit setting had a four-task mean of 34.2 versus 64.4 for BF16; its 4-bit setting scored 64.3. The tested tasks were GSM8K chain of thought, GPQA, MMLU, and IFEval. MINE's 2.1-bit speed result used a different checkpoint and quantization recipe, so Putzky et al.'s quality scores cannot be assigned to it. The juxtaposition is a reason to require a quality gate for each compressed artifact, not evidence that every roughly two-bit model fails.

**The quantization recipe can matter as much as the nominal bit level.** [Patodiya's October 2026 preprint](https://arxiv.org/html/2609.05881) audited 305 eligible Ollama GGUF tags across 15 model lines on program-generation tasks. Seven tags, all low-bit variants of models at most 4B parameters, solved six or fewer of 164 HumanEval+ tasks. Five of the failing files matched uncalibrated, recipe-matched rebuilds tensor for tensor, so the failures were not file corruption. On Qwen2.5-Coder-3B, adding an importance matrix while holding the source checkpoint, toolchain, and tensor mix fixed raised three failing levels from zero to between 76 and 113 solved tasks; the study's plain Q4_K_M rebuild solved 129. The fourth level remained weak. This is evidence for testing calibration before rejecting an entire bit budget, and for testing the final artifact rather than assuming that a format name implies preserved quality. The paper did not measure full file size, process RAM, or CPU generation for those calibrated builds, and its code-task results do not establish broad capability retention. Its 15-task screen was tuned on Qwen2.5-Coder configurations, so the reported registry frequency should not be extrapolated to all models or tasks.

**Same score can conceal more inference work.** [SLQ Appendix G](https://arxiv.org/html/2605.02404) evaluated Qwen3-8B on 1,319 GSM8K questions with three seeds. A BF16 baseline averaged 2,051 thinking tokens and 94.1% accuracy; its task-lossless variant averaged 2,097 tokens and 94.7% accuracy. This token-count test used fake-quantized weights that were dequantized before inference, so it is not a throughput result. It shows why output length and total CPU-seconds must be measured alongside task accuracy. The SLQ paper also reports that calibration can be costly: its Shapley procedure for an 8B model and six bitwidths took about 15 hours on one A6000 in Appendix E.

**A CPU lead exists, with an unsuitable comparator for our current files.** [AQLM Appendix I Table 14](https://arxiv.org/html/2401.06118) reports Llama 2 7B generation on an Intel Core i9-13900K using eight CPU cores, batch one, 128 tokens from scratch, and compiled graphs: FP32 reached 3.106 tokens per second, while one AQLM 2×8-bit codebook setting reached 6.961. The 13B comparison was 1.596 versus 4.180, and the 70B comparison 0.297 versus 0.966. These are not comparisons with a tuned GGUF Q4_K_M runtime. AQLM also reports costly preparation, about one day for 7B and 10 to 14 days for 70B on one A100 in the cited setup. It remains a CPU experiment candidate only if quality, complete memory, and full request time are measured on the same host.

**Native low-bit training has a measured CPU result, but its comparator matters.** [Ma et al.'s BitNet b1.58 2B4T technical report, Table 1 and Appendix B](https://arxiv.org/html/2504.12285) reports 0.4 GB of non-embedding weights and 29 ms per output token for its 2B model, versus 2.6 GB and 65 ms for Qwen2.5 1.5B in BF16. Its unweighted selected-benchmark mean was 54.19 versus 55.23; MMLU was 53.17 versus 60.25 and HumanEval+ 38.40 versus 50.60, so the mean should not stand for identical capability. The CPU timing generated 128 tokens with eight threads on a Surface Laptop Studio 2 i7-13800H, using bitnet.cpp for BitNet and llama.cpp for the comparators. The study's Table 2 compares BitNet quality with GPTQ/AWQ INT4 Qwen files, but gives no CPU timing for those quantized files. It does not measure full artifact bytes, peak process RAM, or complete request cost against this repository's Q4_K_M baseline. BitNet was trained from scratch on a reported four trillion tokens, so this is a different model-development path, not lossless recompression of an existing checkpoint.

**A joint CPU resource reduction can still fail the quality condition.** [Bathula's October 2026 preprint, Tables 2 and 5](https://arxiv.org/html/2610.22428v1) trains a Gemma-shaped 270M-class float model with a learned vocabulary and a separate ternary model with a frozen vocabulary. On one Xeon W-11955M laptop, eight threads and a 128-token decode context, the float model at Q4_K_M was a 253 MB file, reached 446 MB peak process memory, and generated 130 tokens/s. The ternary model used a 46 MB file, 62 MB peak, and 615 to 740 tokens/s in the author's custom CPU kernel. Paired validation loss worsened from 3.155 to 3.439 nats/token, while ARC-Easy accuracy fell from 45.9% to 41.0%. Table 5's 23.97 and 31.2 perplexities use `llama-perplexity` on the GGUF and exponentiated training-script loss for the ternary model, so they are not directly paired. The paper says the 253 MB GGUF retains an FP16 vocabulary, but independent inspection of the [released artifact](https://huggingface.co/QLNI/embeddings-are-overpriced/blob/main/gguf/armA-Q4_K_M.gguf) finds its `token_embd.weight` in Q8_0, 178,257,920 bytes or 70.4% of the file. The paper reports one training seed and excludes prefill from the CPU timing. Because the models and runtimes differ, this establishes a possible three-resource trade, not quality-preserving compression of the existing Q4_K_M model or a frontier-capability result.

**Same-base low-bit QAT narrows the file-quality gap but does not close it.** [ThinkBit's October 2026 preprint, Table 7](https://arxiv.org/html/2610.34886) compares repacked 0.52 GB Qwen3-1.7B with 1.11 GB Unsloth Q4_K_M of the same base, using one scoring harness after dequantization. The selected low-bit model scored 53.8 versus 58.7 on the seven-task mean, 25.6 versus 33.5 on HumanEval, and 73.0 versus 90.8 on strictly scored sampled MATH-500. The authors' reasoning-data QAT uses 2.1 billion training tokens for the 1.7B model, a real development cost. Reported GPU decode instead uses 4-bit training containers, not the smaller repacked distribution file; no CPU time or peak process RAM is given. This is a credible size-quality frontier point, not evidence that compression retained the Q4_K_M model's full quality.

**Streaming the same weights lowers process RSS by spending time on I/O.** In the [SipLLM author repository](https://github.com/ankit1057/sipllm/blob/3e501d0dc641fef2a2900bcba3891627ce455576/README.md), the same 669 MB TinyLlama Q4_K_M file on an Apple M3 CPU reached 122 MB peak process RSS at 11.7 tokens/s with layerwise streaming, versus llama.cpp's 1,323 MB and 88 to 96 tokens/s. The README says the warm-cache, four-thread comparison used medians of three to five runs, and its phone comparison also shows slower prefill and decode at low RSS. Process RSS alone does not count all system page-cache use or storage traffic. The file itself is unchanged; output checks are limited, and full request latency was not established. This is a useful memory-versus-I/O negative control for any proposal that streams compressed or uncompressed layers.

**Low-bit performance depends heavily on the kernel and runtime.** [Georganas et al., revised August 2026, Section III-D](https://arxiv.org/html/2508.06753) measured batch-one, 128-output-token CPU runs with optimized PyTorch-TPP 2-bit kernels. For a real 2-bit QAT MobileLLM-1.5B, reported decode throughput was 3.9× its BF16 implementation on an Intel Core Ultra 9 285K, 3.8× on an Ultra 7 255H, and 3.5× on an Ultra 7 258V. The paper did not report a quality evaluation for those exact timed runs or compare them with Q4_K_M. Falcon3-1B and Llama 3.1 8B 2-bit performance runs used dummy weights, so their speedups are kernel evidence only. Its optimized 4-bit PyTorch-TPP run was faster than bitnet.cpp ternary inference for the 1B shape and about equal for the 8B shape on the 285K. The last comparison uses different runtimes and model weights, but directly cautions against assuming fewer bits always means faster CPU inference.

**Closer CPU comparisons expose a quality and phase trade-off.** [Kurt's January 2026 preprint, Tables 2 and 3](https://arxiv.org/html/2601.14277) converted one Llama 3.1 8B Instruct FP16 GGUF into several formats with llama.cpp commit b7600, then ran them on a dual-socket Xeon Platinum 8488C server with 96 physical cores. Relative to FP16, Q4_K_M reduced file size 69.41%; Q3_K_S reduced it 77.23%. Q4_K_M processed a 512-token prompt at 87.70 tokens/s and generated 128 tokens at 5.12 tokens/s, versus 57.39 and 9.91 tokens/s for Q3_K_S. The smaller version was faster for decoding but slower for prefill. Its unweighted five-task mean fell from 69.15 to 65.49, and WikiText-2 perplexity rose from 7.56 to 8.96. The study did not measure process RAM, and one model plus five tasks cannot establish general quality retention.

**A second same-base CPU sweep also shows a cost below Q4_K_M.** The [Qwen3-4B community GGUF benchmark](https://huggingface.co/nikkikaelar/qwen3-4b-lowram-bench), with [public result TSV](https://huggingface.co/nikkikaelar/qwen3-4b-lowram-bench/blob/main/data/results.tsv) and [harness](https://huggingface.co/nikkikaelar/qwen3-4b-lowram-bench/blob/main/bench/run_bench.sh), reports Q4_K_M at 2.497 GB, WikiText-2 perplexity 13.7304, and 6.50 ± 0.15 generated tokens/s. Q3_K_M was 2.076 GB, perplexity 15.6641, and 6.56 ± 0.27 tokens/s on the same 16-thread CPU setup. File bytes fell about 17%, while this language-modeling quality measure worsened; the small throughput difference does not establish a speedup. The model card says five throughput repeats but the published harness uses three. There is no peak process RAM or held-out task-success result, so this is corroboration of a trade-off, not a complete resource-quality comparison.

**A narrow held-out task shows a similar trade-off in CPU RAM and speed.** [Licardo et al.'s peer-reviewed May 2026 study, Table 3](https://www.mdpi.com/2504-2289/10/5/155) fine-tuned one Llama 3.2 1B model for multilingual e-commerce intent extraction and compared its GGUF quantizations on a 4-vCPU AMD EPYC Genoa VM. On 1,000 held-out synthetic examples, exact-match JSON accuracy was 0.984 for Q4_K_M and 0.972 for Q3_K_M. Reported RAM fell from 1.04 to 0.93 GB, while generation slowed from 19.5 to 13.0 tokens/s; mean complete-request latency rose from 0.82 to 1.23 seconds. The article does not provide complete file sizes or define whether its RAM figure is a process peak. Its Table 3 calls inference single-threaded while the host description gives four vCPUs, without clarifying thread settings. This is good evidence that a lower bit level can lose speed as well as accuracy on a specific task, but not a broad-quality or complete four-resource test.

**A mixed precision format beat Q4_K_M on CPU in a vision-language study.** [Bhatnagar et al., TMLR June 2026, Appendix D Table 5](https://arxiv.org/html/2509.23729) mapped selected Qwen2.5-VL 7B layers to IQ1_M, about 1.75 bits per weight, and retained Q4_K_M for other layers in llama.cpp. Across ten generation runs, Q4_K_M versus mixed precision reached 4.8 ± 0.3 versus 9.0 ± 0.3 tokens/s on an i7-13620H and 14.1 ± 0.2 versus 18.7 ± 0.1 on a Threadripper PRO 7965WX. The table lists “Memory Usage” as 4.4 versus 3.4 GB, but does not say whether this is file size, peak RSS, or another measure. The paper's main quality tables use vision-language benchmarks and other 4-bit quantization comparators; they do not prove identical capabilities for the exact mixed GGUF file in Appendix D. This is a strong candidate for a controlled local trial, not a measured gain on our VM.

**CPU mixed precision needs a matching compiler.** [Oh et al.'s PolyQ, July 2026 preprint](https://arxiv.org/html/2607.14618) combines per-channel bit allocation with CPU layout planning and reports real batch-one decode throughput for Llama 2 13B on a Ryzen 9 9950X, Ryzen 7 7840U, and Intel N250. Its runtime comparator is uniformly quantized AWQ on the same T-MAC backend at two, three, and four bits, not GGUF Q4_K_M. At matched integer budgets, Section 5.5 reports PolyQ decode throughput shortfalls of about 0.2%, 8.1% to 8.2%, and 1.2% to 6.1% on those hosts, respectively. This conflicts with the conclusion's claim of measured throughput within 2%. The paper's 3-bit perplexity gains against selected quantizers support investigating finer allocation, but its cited peak-memory figures come from a working-set model, not a measured process peak. The missing Q4_K_M comparator and modeled memory keep it a design lead rather than evidence of a local resource win.

**Adaptive depth is a work-saving lead with a demonstrated correctness hazard.** [Kaplan's September 2026 preprint](https://arxiv.org/pdf/2609.14144), Tables 4 and 5, attaches a confidence-gated readout midway through three frozen 1.5B to 8B models. It estimates 1.13× to 1.38× generation speedup for Qwen2.5-7B across seven prompt sets from layer-equivalent counts. Appendix C checks this accounting on an M5 MacBook Air's integrated GPU with half-precision Qwen2.5-7B: 7.45 to 10.09 tokens/s at an imposed 60% exit rate, with two timed repetitions after warm-up. Those imposed decisions test timing cost, not the quality of that timed run, and there is no CPU-only or Q4_K_M measurement. On a disjoint set of 60 arithmetic problems, each full model answered all 60 correctly, while the gated versions at threshold 0.7 answered only 10, 12, and 28; token-level agreement had rated the arithmetic traffic highly suitable for early exit. The paper did not establish task quality for its other six prompt sets. Full weights must remain resident or available for fallback, so this method cannot by itself shrink the file or weight-memory floor. Treat it as a conditional CPU-work hypothesis only after a task-correctness gate is met.

**Lossless cache coding addresses a different bottleneck.** [Guo et al.'s GAAC, revised 2026-11-04](https://arxiv.org/html/2610.38210), reconstructs BF16 KV entries exactly while keeping completed cache blocks compressed during attention. On DGX Spark with 4-bit AWQ weights, the authors report about 26% less resident KV memory and 1.04× to 1.15× faster complete decode steps at 32K to 128K contexts; measured equal-budget serving throughput rose 13% to 29% as more sequences fit. The Apple M4 result is for the attention kernel, not complete inference, and neither study measures CPU-only execution. Weight-file bytes do not change, and the benefit should be small when the KV cache is a minor fraction of peak memory. Exact KV reconstruction alone does not prove bit-identical final outputs under different attention kernels.

**Dense zeroing is not a resource reduction by itself.** [Nema et al.'s October 2026 preprint](https://arxiv.org/html/2611.00464), Appendix F, reports no CPU throughput or RSS gain from unstructured 30% pruning when the zeros remain in dense llama.cpp format. That is consistent with the representation still storing and multiplying dense tensors. Its q4 versus q8 throughput comparison is against q8, not the current Q4_K_M baseline. The reported q4 and q8 peak RSS values are unexpectedly close for multibillion-parameter models, for example 4,183 versus 4,213 MB for Qwen3-4B and 2,848 versus 2,957 MB for Phi-2. The paper gives neither GGUF artifact sizes nor enough memory-accounting detail to resolve that discrepancy. We therefore do not use its RSS figures as evidence of a quantization memory ratio.

**Shared cache can change the memory frontier, but recursion raises compute cost.** [Monea et al.'s October 2026 preprint](https://arxiv.org/html/2610.02383) trained looped transformers with a common full-context cache and short local windows. Across 150M to 1B parameter models at five recursions, its hybrid used 76% to 79% less context memory than a same-size standard transformer while improving FineWeb-Edu validation perplexity by 1.12 to 1.82 and selected five-task accuracy by 3.1 to 5.6 percentage points. This is **context memory**, not total process RAM or model-file bytes. At matched recursion count, cache sharing added under 1% FLOPs versus the unshared looped baseline, but the looped architecture itself repeated layers. On an H100 at 4,096-token context, the paper reports batch-one decode at five recursions taking roughly 5.7 times the standard transformer's step time for the **non-hybrid** looped model; sharing added another 8% to 12% versus that looped baseline. The five-recursion **hybrid** retained 81% to 88% of the standard transformer's throughput at each model's maximum batch, a different operating point. The GPU speed study used random weights in one research implementation, and no CPU result or frontier-scale quality test is given. This supports a memory-versus-compute architecture hypothesis, not a drop-in Q4_K_M compression method.

**Low-rank compression is not a demonstrated three-resource win here.** [SigmaScale, June 2026 preprint](https://arxiv.org/html/2606.07098), decomposed selected weight matrices in Llama 3.1 8B Instruct and Qwen3-8B and then fine-tuned them. At its 0.90× retained-parameter setting for the selected matrices, Llama WikiText-2 perplexity changed from 7.21 to 8.95 and HellaSwag normalized accuracy from 80.12% to 75.98% for SigmaScale without distillation. The paper does not measure complete model-file bytes, peak RAM, or CPU inference time for the compressed versions. Its reported preparation averaged 45.5 hours on two H100s plus two hours on two MI300X GPUs per experimental condition. These figures constrain it to a lower-priority research lead for this CPU deployment, especially where parity with the original is required.

**A closer Q4_K_M CPU claim needs reproduction before use.** [FairyFuse, April 2026 preprint](https://arxiv.org/html/2604.20913), reports LLaMA-2-7B ternary decoding at 32.43 versus 26.15 tokens/s for llama.cpp Q4_K_M on a 48-core Xeon 8558P, with WikiText-2 perplexity 5.52 versus 5.68 and selected five-task mean 66.0% versus 65.1%. That is a useful same-base hypothesis, but its resource accounting is unclear: Table 5 labels 3.3 GB as memory, Appendix H totals weights at 2.24 GB, Appendix K lists model size as 2.2 GB, and Appendix J's 3.5 GB runtime-memory estimate adds 0.5 GB embeddings to 2.24 GB of weights that Appendix H says already include embeddings. These figures may describe different quantities, but the paper does not reconcile them. The llama.cpp build shows a placeholder commit hash; its baseline runs `llama-bench -p 0 -n 128`, so prompt processing and complete-request cost are unmeasured. The paper also does not explain how its stated 174 KB packed working set relates to the full 11008 × 4096 two-bit matrix, whose packed values alone require roughly 11 MB. We therefore do not treat its memory or speed claim as a verified improvement over this repository's Q4_K_M files.

**Whole-task cost can reverse a per-token gain.** [Abkin et al.'s 2026-10-30 revised preprint](https://arxiv.org/html/2610.32417) compared Q4_K_M and Q8_0 GGUF files of the same Qwen3-30B-A3B and Devstral Small 2 base models using one llama.cpp revision on dedicated A100 hosts. Across 29 automatically checked benign tasks, Q4_K_M used 6% to 16% less energy per output token on average, but on the statistically supported tasks where the per-token and per-completed-task choices disagreed, choosing by per-token energy used a median 66% more energy per completed task, up to 3.5 times as much in one task. The paper charged failed attempts and retries to completions; its main all-task ratio was 17% more task energy for Q4_K_M, while two exploratory conditions averaged 8% less. The finding is task- and budget-dependent, and its energy boundary covers CPU packages and GPU board while excluding loading, DRAM, storage, and cooling. This is a measurement-design reason to track complete multi-step success and all attempts; it is not evidence for CPU-only speed or RAM on our VM.

These are hypotheses, not additive gains: each candidate changes a different bottleneck and must be measured against the same Q4_K_M file and workload.

The most useful next local test is an **apples-to-apples benign quality versus resource comparison** on the CPU-only VM. A mixed-precision trial first needs the same unquantized base model or a trustworthy equivalent, a CPU format and kernel that support the proposed layerwise mix, a calibration set, and a separate held-out quality suite. Use the same tasks, prompt lengths, output limits, and deterministic settings for each locally supported representation of that base model. Include benign multi-step tasks with objectively checkable final outcomes, because success on isolated steps does not establish success after combining them. Record step-level and full-sequence success, failed attempts and retries, complete model-file bytes, total installation bytes including any custom runtime and auxiliary files, load-time and steady-state memory, CPU-seconds, complete-request latency, and generated token count, with uncertainty across tasks and repeated runs. Count the resources consumed by every attempt, including any retrieval index, tool, or checker. Include the current Q4_K_M file as baseline on the same host. If a candidate needs decompression or specialized startup preparation, count that overhead. If it needs a GPU, report it as a separate hardware class.

Memory accounting needs more than a periodically sampled process RSS. The [Linux `/proc` documentation](https://docs.kernel.org/filesystems/proc.html) defines `/proc/PID/smaps_rollup` with proportional anonymous, file, and shared memory fields and `/proc/PID/status` with RSS and its high-water mark. The [cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) defines `memory.peak` for peak charged memory and `memory.stat` for anonymous versus file-backed cache. An isolated trial should record these at startup, after model load, after prefill, and during decode, plus swap use and page faults where available. This would distinguish a smaller file or mmap page cache from a genuine reduction in live anonymous memory, while also exposing temporary decompression buffers. Measurement support and cgroup permissions should be checked on the VM before treating any one counter as complete.

Three hypotheses remain open: (1) an entropy-aware inference representation might save active memory beyond ordinary archival compression; (2) a CPU kernel designed for a compact representation might reduce memory traffic enough to offset decode work; and (3) a narrower model might match a *defined* benign task set with less resource use. Each requires a runnable artifact and quality measurements. A candidate that meets the predefined quality threshold and improves one target resource earns further study as a **partial lead**, with every regression reported. Claiming the requested **joint success** requires smaller file bytes, lower measured peak RAM, and fewer complete-request CPU-seconds on the same artifact and host, with no failure of the held-out quality gate. Broad frontier parity would require a separate, much wider evaluation and cannot be claimed from this experiment.
