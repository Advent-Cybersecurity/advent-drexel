## Purpose and claims

Compare one frozen candidate GGUF against the same-source Q4_K_M reference on new, objectively scored benign multistep questions. The two families are (1) grouped inventory arithmetic with multiplication, addition, and subtraction and (2) ordered transfers and updates among three reading rooms. A deterministic Python state calculation gives each gold integer. The runner sends only the question to the model. A pass applies only to this generated distribution, artifact pair, prompt, parser, and CPU setup. It cannot prove general capability retention or frontier-model parity.

The two families have different failure opportunities but share simple arithmetic. The state family requires the model to follow an ordered transfer through all three rooms: the second room sends half its current books to the third, which then sends half or one third of its current books back to the target room. They are not independent tests of all reasoning. Four numeric/story variants per family remain a narrow template distribution. Templates and random seeds must be disclosed. Since examples within a template can be correlated, item-level binomial bounds are optimistic if correlation is material. Treat the scored run as a pilot until template-cluster dependence is assessed or the generator is expanded and a cluster-aware analysis is frozen prospectively.

## Freeze sequence

1. Run `prepare-dev` with a recorded seed and small development count, for example eight questions per family. The v4 manifest contains questions, deterministic gold, traces, one fixed `reasoned_512` prompt, and a 512-token cap. It refuses overwrite. The v4 development seed may equal the v2/v3 development seed to compare configurations on the same development questions; the later evaluation seed must differ.
2. Run the reference model on the v4 development manifest once. The v4 prompt asks for explicit intermediate quantities and an arithmetic check, ending in `The final answer is N.`; its 512-token cap lets reasoning continue beyond the 192-token truncation seen in v2. This tests a **joint prompt-and-budget change**, so any improvement cannot be attributed to either component alone. The longer completion may raise full-request CPU cost and must be included in later paired resource measurements. Use `dev-summary` for reference development success, normal stops, and final-line compliance. Do not use the candidate or evaluation cases for calibration. The eight-item-per-family development rate is only a feasibility screen: even 8/8 would not establish the evaluation gate's simultaneous exact lower bound above 60%. If the development point rate is below 60% or responses frequently truncate, do not freeze an evaluation manifest merely to report a favorable candidate difference.
3. Run `freeze-eval` with a different seed, selected reference development run, selected prompt ID, candidate model SHA-256, and fixed count per family. It verifies the reference development run is complete, the reference development point rate is at least 60% in each family, its prompt matches the choice, and generated evaluation questions do not overlap development questions. The current 1.5B run fails this check, so the command cannot freeze its evaluation. The frozen manifest records both model hashes, the development evidence hashes, prompt, parser, gold, seed, maximum output tokens, and decision rule. The scorer checks those frozen settings against its implementation. Record and preferably commit the manifest SHA-256 before either evaluation run. Do not edit or replace it after a model is queried.
4. Start each GGUF in a separate pinned `llama-server` process with identical chat template, context, thread, batch, sampler, and `--no-repack` flags. Use `run` once per model on the frozen manifest. The runner hashes each supplied model file, checks the frozen hash, requires the server's `/v1/models` ID to match the supplied file path, records that server response, requests `/v1/chat/completions` at temperature zero with 512 maximum output tokens, and writes raw response, stop reason, usage, timing, error, and wall time in append-flushed JSONL. It refuses overwrite. Keep the server logs and exact startup commands; a matching path is still not cryptographic proof of the weights already loaded in memory.
5. Run `score` once, preserving raw JSONL. It verifies complete case IDs and hashes and writes paired counts, exact bounds, secondary format counts, normal stops, and errors. A transport error, truncated response, or missing numeric answer counts as incorrect. No manual answer repairs or post-outcome parser changes are permitted.

## Parser and simultaneous decision rule

The primary answer is the **last numeric token** in a normally stopped response, parsed as an exact decimal and compared with the integer gold. This follows the same general last-number extraction convention discussed by the [GSM-Symbolic authors](https://github.com/apple/ml-gsm-symbolic/blob/main/README.md), but this implementation and generated test are ours. Format compliance is secondary and does not drive primary correctness: v4 requires a final-line pattern `The final answer is N.` Any response stopped by a token limit is incorrect, even if it contains the right number.

The frozen exploratory gate has **three assertions per family**: reference success above 60%, candidate success above 60%, and candidate minus reference success above minus five percentage points. Each success lower limit uses the one-sided exact Clopper-Pearson bound. The paired lower bound is the one-sided exact lower limit for candidate-only wins minus the exact upper limit for reference-only wins. To cover the two families and all six asserted bounds simultaneously at at least 95% under the stated independent-item binomial assumptions, each asserted bound gets alpha `0.05/6`; the two discordance-direction components of each paired bound get half of that. Pass requires all six strict inequalities. Report `both correct`, `reference only`, `candidate only`, and `neither` for each family. Failure to pass is not proof of inferiority; the intervals can simply be too wide.

The sample count must be set before freeze from independent development diagnostics and runtime, not from evaluation outcomes. The script default of 96 per family means 384 evaluation requests for two models. The prior 424-request GSM8K run took about 2,793 wall seconds, or about 6.59 seconds per request, so 384 requests would take roughly 42 minutes if this task distribution had the same latency. That is a scheduling estimate, not a measured runtime for this suite. A 300-per-family run is 1,200 requests, roughly 2.2 hours at that prior rate. At 96 per family, the conservative simultaneous paired lower bound is already about minus 5.55 points with **zero** discordances, so the default pilot cannot clear the five-point gate. At 300 per family, it is about minus 1.81 points with zero discordances, minus 5.88 points with ten candidate-only and ten reference-only items, and minus 7.02 points with 15 in each direction. A larger 400-per-family run is 1,600 requests, roughly 2.9 hours; ten candidate-only and ten reference-only items give a lower bound near minus 4.44 points, while twenty in each direction give about minus 6.03 points. These are illustrative **fixed-count bounds**, not the probability of passing. In particular, if an independent pilot suggests 10% total paired discordance and equal success rates, 15 wins in each direction are the expected counts at n=300, which would fail the five-point margin under this conservative procedure. The actual pass probability also depends on the full joint outcome distribution, so choose n using an independent pilot estimate of both discordance directions, a predeclared target power, and a simulation or exact enumeration of the locked six-bound rule. Do not recommend n=300 merely because it fits a runtime window.

The current synthetic families' shared templates may violate item independence. A confirmatory claim would need either a prespecified cluster-aware uncertainty procedure with enough independent templates or an independently sourced held-out suite, plus a sufficient task count. [GSM-Symbolic](https://proceedings.iclr.cc/paper_files/paper/2025/file/663865ea167425c6c562cb0b6bcf76c7-Paper-Conference.pdf) shows sensitivity to changed numeric instances; [BFCL V3](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html) uses state-based multi-turn evaluation, but our reading-room questions are not BFCL tool-use cases.

### Prospective sample-size stress test

The [reproducible planning script](../scripts/plan_paired_quality_sample.py) applies the exact six-assertion rule above to 10,000 simulated two-family evaluations per scenario; its [raw output](../data/paired-quality-sample-planning-2026-11-12.json) records seed `20261113`. This is **scenario analysis**, not a power estimate fitted to the present models. It assumes independent cases and families, equal true reference and candidate success rates, and symmetric candidate-only/reference-only errors. Under an illustrative true success rate of 80% and 10% total discordance, the simulated chance of passing all six gates is 1.87% at 300 items per family, 28.30% at 600, 70.35% at 900, and 91.31% at 1,200. At 20% discordance, even 1,200 per family passes only 37.05% of these simulations. The Monte Carlo standard error is at most 0.5 percentage points per reported fraction. These assumptions are unverified, and the four-template generator makes independence particularly doubtful. A new reference development pilot and independent template or benchmark sampling must inform the actual sample size before freeze. At 1,200 items per family, the two-arm, two-family evaluation would require 4,800 model responses, before repeats or resource measurements. Applying the earlier GSM8K run's 6.59 seconds per response only as a scheduling proxy gives about 8.8 hours, so a rigorous gate would need a separately budgeted run.

## Independent sensitivity checks before a broader claim

The candidate changes only `output.weight`, so a next-token distribution check is especially relevant. On a separately frozen, benign set of ordinary, multilingual, code, and low-frequency-token contexts from a licensed corpus, record reference and candidate logits under the same tokenizer and CPU runtime. Predeclare token-frequency bins using a corpus disjoint from evaluation. Compare token-level negative log likelihood, top-1 and top-k rank changes, reference-tail mass, and probability distortion by bin. Follow any detected drift with objective generation tasks that require those token classes. Keep this secondary check separate from the generated arithmetic gate. The [SoftWater preprint](https://arxiv.org/html/2608.12026v1) motivates heterogeneous output-head sensitivity, but its reported KL/perplexity controls and BF16-head denominators do not establish this GGUF candidate's behavior. The exact per-token audit requires a pinned logits extraction path and was not implemented in this pilot window.

For a genuinely independent multistep check, prospectively freeze a subset of the [BFCL V3 multi-turn test](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html) and its released executable state checker, using the same two artifacts and a prompt calibrated only on BFCL development examples. Count parse failures, tool errors, retries, and completed task success, with process CPU and cgroup memory across the whole interaction. This is a different task distribution with stateful tool calls; it cannot be replaced by more reading-room arithmetic. It likely requires a separate adapter and several hours of validation and was not run in this window. If the 1.5B reference cannot satisfy an absolute development floor, report that limitation instead of lowering the gate after seeing test outcomes.
