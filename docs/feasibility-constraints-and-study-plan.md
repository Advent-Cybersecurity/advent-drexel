# Feasibility constraints and study plan

**Last reviewed:** 2026-11-26. **Status:** Research plan, not a demonstrated implementation.

## Question and boundary

The [Drexel assessment](drexel-feasibility-assessment.md) asks whether one deployed remote access program has been observed making at least two model-caused changes to its own payload code while retaining independently verified access after each change. The [master evidence map](master-feasibility-evidence.md) finds no published case that establishes this whole chain. This document turns the main obstacles into testable questions. It does not treat a model-generated command, an offline variant, or an operator-installed update as a code revision by the same running program.

The research can use ordinary, authorized applications and isolated test machines to measure model cost, generated-code reliability, and endpoint observability. No malicious payload or evasion mechanism is needed to answer these questions.

## 1. Resource cost and detection

The concern is real, but its wording needs care. Local inference has costs in model storage, memory, computation, latency, and sometimes energy. The size of those costs depends on the model, runtime, task, and hardware. A 2025 [mobile measurement study](https://arxiv.org/abs/2504.00002) reported that its tested models below 4 billion parameters could run on powerful phones, with quality and latency limits; it reported more than 30 seconds for meaningful on-device output in its application. A 2026 [CPU tool-calling benchmark](https://arxiv.org/html/2609.07370) reported **process** resident memory of 3,637 MiB and 10.627 seconds mean generation latency for its 0.5-billion-parameter checkpoint, and 7,960 MiB and 30.782 seconds for its 1.5-billion-parameter checkpoint. That resource probe loaded unquantized FP32 models sequentially in a **shared notebook process**, recorded RSS after loading, timed three capped 50-token generations after warm-up, and did not capture the CPU model or full software revisions. The authors themselves caution that notebook allocator and history contribute to RSS. These figures are neither isolated model-weight requirements nor directly comparable to the [repository's Q4 GGUF fresh-process runs](inference-resource-study-2026-11-11.md), whose wall time includes process startup and a different prompt/output workload. Neither study measured malicious code generation or an endpoint alert probability.

Local inference is also **not a requirement of the research claim**. The [existing evidence ledger](feasibility-evidence-2026-11.md) records that Guan et al.'s main propagation trials used shared inference. A separate 32-attempt test reported 68.8% success for full local inference setup versus 93.8% for ordinary replica launch under its test conditions. That comparison identifies an additional setup failure mode; it does not measure detection or establish feasibility in field operations.

The [local inference resource study](inference-resource-study-2026-11-11.md) now measures two Q4_K_M models on one CPU-only VM. Its [lossless compression follow-up](lossless-model-compression-study-2026-11-11.md) found only 2.26% to 2.94% storage savings from standard ZIP-like compression settings, while preserving each GGUF file byte for byte after restoration. Archival compression did not test a lower-memory inference runtime.

Inference-only memory and latency do not measure the **complete code-revision loop**. In [Zheng et al.'s AgentCgroup characterization](https://arxiv.org/html/2602.09345), 111 SWE-rebench tasks with a locally GPU-served GLM model and a 33-task overlapping subset with cloud Haiku ran in Podman on one 24-core, 128 GB Linux machine. The authors attribute 55–60% of end-to-end task time to container/agent initialization and tool execution in that setup; a roughly 185 MB framework baseline was punctuated by tool-driven memory spikes, including one 15.4-fold peak-to-average case. These are **sandboxed coding-agent workload measurements**, with large repository images and a different model/runtime, not an estimate of Drexel's endpoint requirements. They establish why a future benign feasibility study must measure the full propose–validate–apply–check path, including compiler/test subprocesses and failed attempts, rather than projecting from a model file or one inference call. The 33 Haiku tasks overlap the 111 GLM tasks, so the 144 executions are not 144 independent problems.

[Zhou et al.'s November coding-agent study](https://arxiv.org/html/2611.24324) further limits what “small model” cost claims can mean. Its best sub-40B model resolved 61.2% of SWE-bench Verified issues under a fixed agent scaffold, but the entire experiment served models on AMD MI300X GPUs, allowed up to two hours and 250 agent steps per issue, and ran each model–issue pair once. Its cost-saving cascade is a **trace-driven simulation** over 466 tasks with complete paired traces; escalation starts a fresh large-model attempt from the original repository state rather than preserving the small model's live process or edits. Its 16.4% all-task reduction uses an exclusive-allocation GPU-hour accounting convention, not measured endpoint CPU, RAM, storage, or battery use. The result supports task-dependent model selection for a separate coding service, while leaving local tiny-model payload revision, serial state retention, and remote-control continuity unmeasured.

A [2026 PowerShell generation study](powershell-model-proxy-audit-2026-11-26.md) fine-tuned roughly 7–9B open-weight models and compared generated scripts against triggered Sigma-rule sets. It describes a 4-bit configuration as a resource-constrained scenario, but the reported training **and inference** used four A100 64 GB GPUs. Its rule-set overlap on 212 reference-triggering cases is neither a measure of working remote-control code nor a CPU endpoint resource measurement. The distinction matters when considering a locally hosted Drexel controller.

A [local code-model energy study](local-code-model-energy-audit-2026-11-26.md) does measure a joint correctness/energy tradeoff on a 16 GB laptop: 3B q4_K_M solved 366 of 542 independent Python tasks at 69.4 rail joules per solve, versus 363 and 141.2 for 7B q2_K. The repeated anchor pair supports the relative energy gap on HumanEval+, but the runtime used Apple Metal, the file budget omits runtime memory, and the tasks do not include a dependent second revision. These numbers inform candidate resource accounting, not a Drexel reliability or CPU-only estimate.

The second part of the concern, that inference *immediately* causes detection after download, is unproven. [Microsoft's behavior-monitoring documentation](https://learn.microsoft.com/en-us/defender-endpoint/behavior-monitor) says Defender observes process, file, and service activity and looks for suspicious behavior. It does not publish a rule that model size or CPU usage alone triggers an alert. **Inference:** resource spikes may make an application conspicuous in a monitored environment, but the probability and timing of an alert require measurements under a specified security configuration. A download, model load, inference run, code change, and network operation must be recorded as separate events.

[Huntress EDR's November support note](commercial-edr-observability-audit-2026-11-26.md) reports an observed local AI session with over 90,000 process events in one minute and occasional EDR-agent resource pressure on agentic workloads. It does not establish that the model inference was local, that inference alone caused those events, or that an alert fired. This reinforces the need to count process events and monitoring overhead separately from model compute and security decisions.

**Research test:** Benchmark approved local inference applications on specified, instrumented machines. Record hardware and OS, model and runtime versions, model artifact size, peak memory, CPU and accelerator use, latency, energy where available, and application failures. Keep endpoint protection enabled and record the product/version, policy, alert, and time of any alert. Specify the queried telemetry surface, named alert versus block outcome, observation window, autonomous-response setting, and between-run state reset; [Prinos and Brush's commercial EDR study](commercial-edr-observability-audit-2026-11-26.md) documents why these can change the interpretation. Use an ordinary non-AI application as a baseline. Report all runs, including failures, instead of selecting the quietest or fastest run.

**Resolution criterion:** A resource claim is supported only for the measured model, task, and device class. A detection claim needs an actual alert trace tied to the relevant event; absence of an alert in one setup does not show general invisibility.

## 2. Other constraints that could defeat the full claim

| Constraint | What is known or unknown | Evidence needed to resolve it |
| --- | --- | --- |
| Model capability at the available budget | The [CPU benchmark](https://arxiv.org/abs/2609.07370) found a reliability and resource tradeoff on structured tool calls. Its results do not measure safe code revision. | Measure task success and resource cost together on benign code-editing tasks. Count invalid outputs, regressions, and timeouts. |
| Repeated revision reliability | The [Guan paper audit](guan-2026-paper-audit.md) records adaptation in a controlled worm study, but not two serial revisions of one continuing remote access program. | Preserve a complete, ordered record of every proposed and applied benign revision, including failed attempts and post-change functional checks. Report the joint two-revision success rate. |
| Continuity of one instance | Separate binaries or fresh executions can look like adaptation without establishing an uninterrupted instance. | Use stable instance identifiers and time-stamped state records that distinguish a continuing process from replacement or redeployment. |
| Code validity after change | A plausible generated patch may fail to compile, run, or preserve earlier behavior. | Apply candidate changes only to a benign test application; run the same independent regression checks before and after each change and count breakages. |
| Access or service continuity | A working changed component does not prove that its surrounding service stayed reachable. | In a benign lab service, record independent health checks before and after each revision, with failures and gaps shown. Do not substitute a process-running check for a functional check. |
| Host diversity | A result on one OS, hardware profile, or protection setup may not transfer. | Repeat the same benign tests across a declared matrix of devices and security configurations; report results by cell rather than a pooled success claim. |
| External model dependence | Hosted inference adds service availability, latency, authentication, cost, and network dependencies. Local inference adds storage and compute costs. | State which dependency each cited case actually used. Measure availability and latency only with authorized services and benign requests. |
| Feedback quality and control | An agent can mistake noisy observations for success or accept untrusted instructions in its environment. [Poisoned-benchmark experiments](feedback-integrity-audit-2026-11-26.md) show that a selected harness can carry a learned unsafe coding tendency into later neutral tasks under specific conditions. A [separate detection-gap study](failure-detection-and-repair-audit-2026-11-26.md) shows that an agent can repair some task failures when called while its own checks stay silent. A [warrant micro-lab](revision-warrant-audit-2026-11-26.md) shows that a benign pattern can prompt an unnecessary guard that a score-only accept rule cannot distinguish from no change. | Keep human-labeled ground truth and independent checks that the candidate cannot edit. Record whether a triggering failure existed, whether it was noticed, what repair was proposed, whether revised code became active, and whether function passed; do not count forced recalls as autonomous detection. |
| Detection and evidence visibility | Security products can observe several behaviors, but a published case may omit event timing or policy details. | Preserve instrumented event timelines and product settings; distinguish an observed alert from a researcher's assessment of detectability. |
| Field evidence and attribution | A lab demonstration, analyzed sample, and observed intrusion answer different questions. Attribution and source claims can conflict. | Follow the [methodology](methodology.md): primary source, exact locator, evidence basis, confidence, and independent corroboration where possible. |

## 3. Research sequence

1. **Source audit:** For each candidate, classify the control point, AI role, observed setting, and whether a time-ordered same-instance revision chain is published. Keep claims about design separate from observed execution.
2. **Benign resource study:** Measure inference costs and endpoint events on authorized devices as described above. Include both successful and failed runs and document the denominator.
3. **Benign revision study:** Use a small, non-networked test application with independent functional tests. Measure how often model-proposed changes pass validation twice in sequence, including regressions and failed proposals. This tests revision reliability without building a remote access tool.
4. **Evidence reconciliation:** Compare the controlled measurements with incident and sample reports. State which parts of the original claim remain untested in public evidence. Do not extrapolate lab success to field deployment.

## 4. Minimum record for each experiment or external case

- Source or experiment ID, date, hardware and OS, software/model versions, and research setting.
- Exact unit of analysis: proposal, applied revision, process instance, sample, host, or incident.
- Ordered event times for model output, proposed change, applied change, validation result, and functional health check.
- Resource measurements with collection method, baseline, and complete attempt/failure counts.
- Security product and policy, plus the actual alert record if a detection claim is made.
- Clear statement of what the evidence does **not** establish.

The [serial-revision estimand](serial-revision-estimand-2026-11-26.md) defines the full `S0`–`S2` lineage, the all-instance and conditional denominators, and treatment of unshown links for a prospective benign analogue or a detailed external case.

## 5. Decision rule

The narrow claim is supported only by evidence for **two applied model-caused code revisions in one continuing deployed remote access program, with independent access verification after each revision**. Controlled benign experiments can establish feasibility of component tasks and their costs. They do not by themselves establish that the integrated behavior has occurred in an intrusion.
