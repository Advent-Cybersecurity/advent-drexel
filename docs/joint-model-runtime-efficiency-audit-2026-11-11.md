# Joint model and CPU runtime efficiency audit

Status: source review completed, 2026-11-11. This note tests a narrow proposition: one deployable local model artifact should use fewer complete file bytes, less peak inference RAM, and fewer CPU-seconds per complete request than the current Q4_K_M reference, while meeting a prespecified benign task-quality gate. A gain in one metric is a useful lead but not the joint result. The [mixed-precision CPU protocol](mixed-precision-cpu-study-protocol-2026-11-11.md) defines the local comparator and measurement procedure. Same-base changes need a fresh reference built from the same unquantized checkpoint; newly trained architectures additionally need a matched training-budget control where feasible. No candidate in this note has been built or measured locally.

## What a convincing result must contain

| Dimension | Required observation | Common substitute that is insufficient |
| --- | --- | --- |
| Deployable bytes | Hash and byte count of the complete model file, required sidecars, and any custom runtime executable or library | Bits per weight for selected tensors; parameter count; archive before restoration |
| Peak RAM | Peak process RSS for a complete load, prefill, and generation request, with page and cgroup context | Static weight size; GPU weight allocation; RAM after excluding load buffers |
| CPU work | Total CPU-seconds for the same complete request, including load/decode where applicable, tokenization, prefill, generation, checking, and retries | Tokens per second; isolated matmul speed; elapsed latency on a different core count |
| Quality | Prespecified noninferiority and absolute success floor on sealed benign multi-step tasks, with full-sequence success and retries | Perplexity alone; average of a few isolated benchmarks; next-token agreement |

The same complete artifact, host, workload, runtime version, thread budget, and lifecycle must support the joint claim. Count new runtime bytes when a custom kernel requires them; a shared, unchanged runtime can be reported separately. Training and search cost should be reported separately from deployment cost, especially for methods that require distillation or new architecture training.

### Independent system evaluation and counterexamples

The [WMT 2026 model-compression shared task](https://aclanthology.org/2026.wmt-main.52.pdf) is useful because organizers ran 41 submitted systems from 13 teams under one interface on an H100. Its constrained track derived from Gemma 3 12B. The organizers report that INT4 systems at 6.0–6.6 GiB, 26–29% of the 22.7 GiB base, stayed within ±0.01 COMET-Kiwi of the base on selected translation directions; the smallest 2.3–4.6 GiB structural systems lost substantial translation quality. The reported 20× throughput extreme compares a custom C++/CUDA runtime with the uncompressed baseline, so it is not a precision-only gain. Translation quality is not general task parity. Crucially, the organizers state that peak GPU memory could not be measured reliably across the heterogeneous runtimes, and their net throughput subtracts a one-sentence warmup from full-set wall time. The study therefore has complete submitted artifacts and an independent quality-size-speed comparison, but no joint memory or full-request CPU result, and it has no CPU Q4_K_M comparator.

A [WMT26 team report](https://aclanthology.org/2026.wmt-main.133.pdf) is a useful calibration and cold-start control. From one Gemma 3 12B source, it measured single-layer INT4 translation sensitivity on a development split, then assigned BF16, INT8, or INT4 to 48 decoder layers under a size budget. On one L40 GPU, its serialized mixed checkpoint occupied 9.15 GB against 8.0 GB for uniform GPTQ INT4 and 23 GB for BF16. Three fresh-process runs over 456 blind translation inputs took 259.4 seconds for mixed precision, 315.8 for GPTQ, and 550.5 for the Transformers BF16 baseline. The mixed version scored 43.23 macro-average chrF across three directions against GPTQ's 43.03 and BF16's 43.53; quality was evaluated once per system and direction, apart from the speed runs. This supports task-guided bit allocation and counting model-load work, but the allocation assumes additive layer effects and estimates INT8 sensitivity rather than measuring it. It reports neither peak resident memory nor CPU-seconds or broad task parity, and its mixed file is larger than uniform INT4. The L40 result cannot predict whether a GGUF Q4_K_M CPU candidate improves all three resources.

One [WMT26 team report](https://aclanthology.org/2026.wmt-main.136.pdf) measures a more nearly joint GPU result in one runtime. For three translation directions on an H100, its text-only Gemma 3 12B BF16 baseline is 23.5 GB on disk, 23.2 GB peak **load-time** VRAM, and 4,486 hot steady-state tokens/s. The INT4-weight/FP8-activation system reports 6.7 GB, 9.7 GB, and 5,131 tokens/s. It scores 65.40 versus 65.33 on WMT25 CometKiwi-XXL but 5.570 versus 5.493 on MetricX24-XXL, where lower is better; the authors explicitly describe a small residual loss under the latter metric. The WMT26 blind set has only reference-free scores in this report. The stack removed the vision encoder and 25.5% of vocabulary pieces, so it does not preserve the original model's complete capability set. Its load-time VRAM and hot throughput do not establish peak process RAM or complete-request CPU-seconds. Adding a 420 MB best-of-four selector improves translation metrics but drops reported throughput to 1,456 tokens/s and costs about four generations per retained output. This is useful evidence for a narrow GPU workload and for counting quality-recovery overhead, not a CPU Q4_K_M win.

Two bounded specialization results further limit a broad-capability inference. [NanoVDR](https://aclanthology.org/2026.emnlp-main.71.pdf) reports a 69M-parameter float32 **query encoder** at 274 MB and 51 ms per query on one AMD EPYC 9474F thread, compared with a different 2.209B encoder at 8.8 GB and 2,539 ms. Its mean retrieval-score retention is 95.1% relative to a *different* Qwen3-VL teacher, and its offline document encoder and 8.2 GB index for one million documents remain necessary. It gives neither generative parity nor complete system RSS/CPU. In a long-horizon coding evaluation, [CHOP](https://aclanthology.org/2026.aacl-long.167.pdf) reports 13.2% resolved on SWE-bench Verified 500 versus an 11.8% off-the-shelf baseline; its stated interval, 10.5–16.1%, overlaps that baseline. Standard online policy distillation scored 6.5%. These outcomes caution against inferring complete-sequence gains from improved components, and the study does not measure our resource tuple.

A controlled synthetic [retrieve-and-add study](https://proceedings.iclr.cc/paper_files/paper/2026/file/3b4e1336f775c3dba16ebbb8d2afd258-Paper-Conference.pdf) provided a fixed dictionary and one-key-per-turn plan. Most tested 4B–32B models had near-perfect first-turn correctness, yet even Qwen3-32B fell below 50% mistake-free task completion within 15 turns across 100 sampled trajectories. The authors also tested sensitivity to induced error histories. This directly motivates scoring entire held-out trajectories and retries rather than isolated steps; it is neither a compression experiment nor evidence that any particular compression method caused the failures.

A separate [program-repair quantization study](https://arxiv.org/html/2606.27205v2), revised 3 July 2026, shows why aggregate success needs a paired disagreement check. Llama-3-8B-Instruct solved 61 of 525 Defects4J bugs with ten candidates per bug; its Quanto 4-bit weight variant solved 58, but only 29 solved bugs overlapped. The reported solved set is based on plausible test-passing patches, not proven semantic repairs, and the authors used GH200 GPUs with Transformers rather than CPU GGUF. Record base-correct/candidate-wrong, candidate-correct/base-wrong, and overlap on the same sealed local task set; do not infer resource behavior from this study.

A separate [GGUF contextual-faithfulness audit](https://aclanthology.org/2026.groundlm-1.16.pdf) reinforces the quality gate. Under counterfactual passages, Llama-3.2-3B Q4_K_M fell 2.9 percentage points against FP16 (95% item-clustered interval for the difference: −5.2 to −0.8 points), while Qwen2.5-3B Q4_K_M fell 1.1 points with an interval crossing zero. At Q3_K_M, Qwen fell 12.8 points, and its Q2_K output was largely degenerate. The 300 SQuAD-derived items and three templates per item were evaluated on a T4, with no resource measurements. This does not estimate the current 0.5B or 1.5B models, but shows that a quality gate should test context use and should not treat repeated templates as independent tasks. The authors explicitly say non-detection at higher precision is not equivalence.

The [GOE CPU study](https://arxiv.org/html/2608.28652v1), dated 19 August 2026, also cautions against treating the Q4_K_M reference as fully capability preserving. On its Qwen2.5-1.5B artifacts, Table 8 reports F16 and Q4_K_M ARC-Easy both at 0.747, but CommonsenseQA falls from 0.807 to 0.733. The authors used an Intel Core Ultra 7 265U, 14 threads, and llama.cpp/GGUF; they report file size and decode throughput, but not peak process RSS, complete-request CPU-seconds, or held-out multi-step quality. Their Q4 construction is not the pinned local artifact, so the local protocol should measure its own FP16-to-Q4 quality gap before judging a mixed-precision candidate against Q4 alone.

Repeated sampling can conceal a large deployment penalty. In the 31 October 2026 [Song and Zheng preprint](https://arxiv.org/html/2611.01133v1), 80% expert pruning of Qwen3.6-35B-A3B required an estimated 1,319 candidates per AIME problem to reach 90% of the original model's observed coverage, versus 20 for the original, and 59.63 times as many generated tokens. The authors count candidate outputs at fixed sampling settings; they exclude prompt processing and verification and do not measure CPU. This is not evidence that the local Q4_K_M model would incur that ratio. It is direct evidence that a high pass@k or retained solved set can coexist with poor per-attempt reliability and greater complete-task cost. The local gate should record success at the allowed attempt budget, outputs and retries per task, and CPU-seconds per completed task.

The [CyberNative GGUF reproducibility harness](https://huggingface.co/datasets/CyberNative-AI/gguf-repro-harness/blob/main/RESULTS.md), dated 17 September 2026, supplies a measurement caution for the proposed CPU trial. Two operators reran one frozen llama.cpp b10991 pipeline in fresh containers on a shared CPU host, using eight threads, two small models, and five alternating `pp512`/`tg128` replicates per run. The F16 and Q4_K_M artifacts had identical hashes and bytes across runs; peak RSS differed by at most 0.13%, but Qwen Q4_K_M load time differed by 61.5% and decode throughput by 34.4%. Its Qwen load-time difference against F16 even changed sign. This is repeat execution of one harness, not independent reproduction, and its 200-item HellaSwag subset does not establish task parity. It reinforces exclusive CPU allocation, controlled warm/cold page-cache conditions, paired repeated runs, and CPU-seconds alongside wall time before accepting a small CPU gain.

A [Google Research cold-start study](https://research.google/pubs/cold-start-latency-of-quantized-small-language-models-on-serverless-cpu-infrastructure/) adds a lifecycle warning. On CPU-only Cloud Run, five Q4_K_M models and a Llama-3.2-1B quantization sweep used a roughly 16-token prompt and at most 50 generated tokens. The authors attribute 55–70% of cold-request wall time to model loading; their 8 GiB tier also has two vCPUs instead of one in the 4 GiB tier, so the faster warm runs do not isolate RAM capacity. The [released harness](https://github.com/mingwho/slm-research) measures client wall, server-side model-constructor wall, and server-side generation wall, but does not measure process peak RSS or CPU-seconds. Its reported infrastructure boot time is a residual, not a directly instrumented interval. The repository inspected on 11 November had a perplexity CSV but no raw timing CSV, and the paper gives inconsistent 8 GiB Llama Q4_K_M warm throughput figures of 15.2 and 12.0 tokens/s in Table II and Section V-A. Treat its cold-load proportion as an author-reported workload-specific warning, not a portable performance or joint-resource result.

A September 2026 [ARM CPU deployment study](https://jacar.es/en/cpu-only-llms-arm64-maple-minicpm5-spark/) makes live memory overhead concrete. On a Linux ARM64 VM, one `llama-server` request at 16,384 context produced `/proc` `VmHWM` of 3.27 GiB for a 1.45 GiB MiniCPM5 Q4_K_M file and 5.56 GiB for a 2.42 GiB Spark Q4_K_M file, with three warm-cache starts per model. Its reported allocation breakdown includes 1,340 and 2,474 MiB of CPU-repacked weights respectively, alongside mapped weights and KV cache. The files were on tmpfs, which kept mapped pages resident; this ratio should not be transferred to a normal disk or x86 host. The models differ, the host was contended, the quality check was five Spanish prompts, and full-request CPU-seconds were not measured. For our study, inspect runtime repacking and record true high-water memory under the intended file placement instead of predicting RSS from GGUF bytes.

The October 2026 [lowbit-atlas runtime audit](https://github.com/matheus-c-feitosa/lowbit-atlas) is a correctness check for custom packed kernels. With the same published BitNet b1.58 2B4T GGUF and identical token IDs, the author reports WikiText-2 perplexity 113.33 on the tested current bitnet.cpp x86-64 build versus 18.79 in a float32 Transformers reference; an activation fix brings the CPU result to 18.87. The wrong runtime still generated plausible short text. Its [method](https://github.com/matheus-c-feitosa/lowbit-atlas/blob/main/METHOD.md) pins hashes, commits, CPU classes, and flags, but uses eight 512-token windows, short prompts, and no complete file/RSS/CPU-seconds comparison. For a new packed representation, inspect the actual kernel path and compare logits or perplexity on identical token IDs against a trusted reference before judging task quality or speed. This does not establish a resource gain.

The published [IJCA Q4_K_M entropy study](https://ijcaonline.org/archives/volume187/number120/rotem-ijca-2026-a71cdd2650e6.pdf) used five Bartowski GGUF builds. Our pinned Qwen GGUFs are official builds, with different complete-file sizes even where model names overlap. Its reported 1.041 to 1.045 times whole-file ratios and our foldz savings are therefore separate artifact observations, not a paired codec comparison. The study's [publisher](https://www.ijcaonline.org/archives/volume187/number120/practical-limits-of-lossless-compression-for-bf16-transformer-llm-weights-with-companion-measurements-on-q4-k-tensors-in-gguf-q4-k-m-files/) and [DOI registry](https://api.crossref.org/works/10.5120/ijcaa71cdd2650e6) disagree on author names, and its reproduction repository was unavailable at review time. Treat its scoped ratios as lower-confidence evidence, not a universal Q4 compression limit.

Our one-run-per-file [foldz storage check](../data/foldz-storage-check-2026-11-11.json) is a direct archive-only negative control. On the existing 1.5B Q4_K_M GGUF, foldz saved 7.64% of complete file bytes, but restoring the model required 71.34 child CPU-seconds and 1,069,432 KiB maximum child RSS; zstd `-19 --long=27 -T4` saved 2.49% and restored in 1.79 child CPU-seconds with 136,856 KiB maximum child RSS. Both restored hashes matched the source. The loader cannot infer from the foldz archive, and these are archive-process rather than inference measurements. The result does not predict a fused entropy kernel, but it demonstrates why extra stored-byte savings cannot be credited as a RAM or CPU gain without measuring the complete load and request.

## Hypotheses to test, in order

1. **Calibrated same-base mixed precision on the present CPU runtime.** This is the lowest-cost falsifiable step because the b12283 quantizer supports per-tensor overrides and the existing protocol already fixes the reference, calibration, held-out gate, and full-system measurement. Bartowski's released tensor maps provide a concrete construction example, while the local sensitivity ranking and sealed task quality must be measured on our own base model. It may improve file and RAM, but CPU-seconds can rise if the lower-bit kernel is less efficient or quality causes more output and retries. The local result must decide.
2. **Materialized structured reduction with modest recovery training, then CPU-aware quantization.** Fewer actual dense dimensions can reduce serialized weights and arithmetic simultaneously. Search or sensitivity scoring should optimize measured CPU request cost plus complete bytes and memory rather than parameter count alone. Keep widths compatible with the target quantizer's block layout and verify the exported tensor map before benchmarking. GRASPrune, Yu et al., and Das et al. show that unrecovered pruning can lose substantial quality or even enlarge a GGUF; MobileLLM-Flash and AutoCompress show a recovery route but also substantial training cost. This is a research program after the simpler mixed-precision gate, not an observed solution.
3. **Custom packed representation with a CPU kernel, then native low-bit training if needed.** First replicate the Fractal64 size and decode result on its Q4_0-compatible source. Test transfer against Q4_K_M only on a separate model whose tensors support that reference format, with true high-water RSS and complete-request CPU-seconds. Its small visible quality suite cannot justify a parity claim. Train or recover a model for a low-bit representation only if a same-base codec/kernel path cannot pass the joint gate. A viable kernel must compute from the packed representation without full-weight expansion. BITCOS and T-MAC support kernel potential, but speed is device- and format-dependent. Preserve required full-sequence capabilities; selected benchmark parity cannot establish broad parity.
4. **Entropy coding inside the inference kernel.** It can reduce packed weight bytes without changing an already quantized checkpoint if decoded tilewise, but a separate archive or whole-model expansion does not guarantee live RAM or CPU savings. The CPU break-even condition is that saved weight-transfer work exceeds entropy-decode and control overhead. Prefill and token-by-token decode can have different bottlenecks, so test the actual prompt-length mix rather than only a warm decode loop. Measure entropy headroom on the actual Q4_K_M tensor mix, then measure complete-request CPU-seconds and peak load/prefill RAM. A negative headroom test should end this path.
5. **Context-state reduction and bounded-task specialization.** Hybrid recurrent state or a small student can help on a known long-context or narrow workload. Neither shrinks a general weight file by itself. Include the student, index, checker, runtime, cache, and retries in total system bytes/RAM/CPU; test exact retrieval and multi-step completion, not only average benchmark accuracy.

### Decision rule

Call a candidate a **partial lead** when it improves at least one target resource with acceptable quality. Call it a **joint deployment result** only when one verified artifact is smaller in complete file bytes, lower in peak RAM, and lower in complete-request CPU-seconds than the current public Q4_K_M reference on the same host and workload, while passing the prespecified held-out noninferiority margin and absolute success floor. For same-base interventions, also compare against a fresh Q4_K_M file built from the identical unquantized checkpoint. For a newly trained architecture, a matched training-budget control helps attribute a gain but does not replace the deployment comparison. Report effect sizes and uncertainty for paired task outcomes and CPU measurements. No cited source above establishes that result for the current baseline, and no local candidate exists yet.
