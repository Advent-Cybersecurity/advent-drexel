# Does failure feedback actually direct a revision?

26 November 2026. Source-only audit of [He, *Does Failure Feedback Direct Agent Self-Modification?*, version 1](https://arxiv.org/html/2610.14662). The study is relevant to Drexel's proposed repair loop because a revision can alter code yet fail to address the error that prompted it, or fix that error while breaking existing behavior. This is a benchmark comparison, not an experiment on malware or a continuing remote-access process. No model was run for this audit.

## Three distinct outcomes

The paper separates **target repair**, **other-failure repair**, and **new breakage of previously correct behavior**. Its retrospective analysis draws on public Darwin Gödel Machine coding-agent logs. Of **145 eligible child modifications**—restricted to cases with a task entry, a working child, and evaluation on the target—**12 repaired the named target**. The target repair rate was **8.3%**, versus **11.6%** on the parent's other failures; the estimated difference was **−3.3 percentage points** with a 95% interval of **−8.2 to +2.0**. The authors found no detectable target-specific advantage in these records. This is a conditional comparison inside selected DGM logs, not an overall probability of repair or proof that feedback has no causal value. [Retrospective methods and results](https://arxiv.org/html/2610.14662).

The paper's second, controlled study deliberately varies which failure the editor sees for the *same target*. In one instruction-editing setting, Qwen3-4B-Instruct-2507 repaired the target **20.0 points** more often when shown that target's failure rather than a matched failure in the same task category (95% interval **+8.5 to +31.8**). Phi-4-mini's **+6.7-point** contrast was not statistically significant. The models ran in **bf16 with vLLM on an RTX 4090**, and this result concerns revisions to a modular instruction playbook, not executable payload code. In a separate tool-using setting, the agent changed Python helper code, but a matched same-family failure could reveal the same underlying bug, so the corresponding feedback contrast was near zero. [Controlled design and results](https://arxiv.org/html/2610.14662).

Target repair did not reliably translate into held-out improvement. The paper reports that one-module edit restrictions lowered some breakage in the Qwen instruction setting but increased it for Phi and the tool-using agent. Its eight-step loops and GEPA comparison were confined to one model and a small number of trajectories; similar mean held-out outcomes there do not establish equivalence across agents or tasks. The controlled study's plan and amendments were recorded before most data, but one method-comparison correction followed the data; children were scored once, and small effects are comparable to prompt-perturbation variation. [Limitations](https://arxiv.org/html/2610.14662).

## Repair budget is a separate experimental choice

[Kim's peer-reviewed one-round refinement study](https://www.mdpi.com/2673-2688/7/9/353) makes the *decision to revise* measurable. Across seven models and three Python benchmarks, each Self-Refine and Self-Debug arm began from the **same exact initial candidate** for a model–task pair. In the first full run over 11,683 model–task cases, diagnostic-feedback Self-Debug had positive final-test gain in 16 of 21 model–benchmark cells and zero gain in five; feedback-free Self-Refine had negative gain in 16 cells, positive in four, and zero in one. Two more runs regenerated initial candidates over the same tasks: Self-Debug had no negative cell in either, whereas Self-Refine still had negative gain in 16 and 14 cells. These are paired **one-round** results, not repeated edits in a resident process. The four initially positive Self-Refine cells had confidence intervals including zero.

The mechanism is narrower than “tests solve repair.” The Self-Debug protocol usually retained a candidate after its diagnostic tests passed, preserving 99.95% of initially final-test-correct candidates; the same rule left 1,828 diagnostic-pass but final-test-failing candidates—34.1% of initial final-test failures—unrepaired in the first run. When diagnostics failed, only 1,623 of 3,519 such initially failing candidates changed; 363 of those changes passed the complete final test suite. Diagnostic tests were fixed in advance but were subsets of final tests. Thus a test pass can justify abstention and still miss a real fault; a revised candidate can pass diagnostics and fail broader tests. The study used standalone Python tasks in isolated Ubuntu executions, local open-weight models on two RTX 4090 GPUs, and no live service, endpoint product, or C2. Its linked replication package is identified by the authors but was not run or independently reanalyzed here.

[Kiecker et al.'s arXiv v1 repair-loop study](https://arxiv.org/html/2607.05197) tracks task-completion curves through ten repair steps in code generation, test generation, and translation across six tool–dataset combinations and three model backbones. The reported completion curves flatten after early repairs; the authors place most of the achievable gain in the first three to four steps, while acknowledging later successes. The actual initial and marginal gains vary strongly by workflow: an OCI variant with tests in its first prompt differs sharply from one that receives tests only after failure. The researchers modified some tool interfaces for newer models, did not repeat every configuration, and used task-specific automated checks that need not establish semantic correctness. Completion by a repair budget is not a record of two accepted code versions running in one process. For Drexel, fix and report the candidate budget, feedback exposure, rejected attempts, and total inference and verification cost before interpreting a retained-version rate. These study percentages are not a payload-revision estimate.

## Consequence for a later benign Drexel test

The [DDBench diagnostic-context audit](distributed-debug-context-audit-2026-11-26.md) provides a complementary check on *what information a repairer receives*. Its matched symptom-only and context-augmented runs over distributed-system bugs show a substantial aggregate gain from short, curated bundles, alongside 13 pass-to-fail reversals among 310 tier-1 model–case pairs. A faithful observed symptom can steer the editor toward the wrong layer. This is a final-patch benchmark, so it does not measure accepted serial versions or live access retention.

For each proposed revision, report whether the specific triggering failure was repaired, whether other failures improved, and what previously working function was lost. Record candidate quality **before** screening as well as after acceptance, because a gate can improve the returned artifact by rejecting bad candidates without making the generator more accurate. These are measurement requirements motivated by the study, not a claim that its rates transfer to model-guided payload revision or endpoint access continuity.
