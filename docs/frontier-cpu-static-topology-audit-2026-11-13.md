# CPU deployment audit: tied embedding in the current 4B reference

2026-11-13 05:26 EST. This is a static tensor and source audit. No model was built or benchmarked in this round. The reference-only quality screen was running separately, so the GGUF inspection read tensor descriptors and metadata without comparing payloads or running inference. The [machine-readable inventory](../data/frontier-cpu-qwen3-4b-static-tensor-audit-2026-11-13.json) records the exact arithmetic.

## Decision-relevant finding

The current local `Qwen3-4B-Instruct-2507` Q4_K_M GGUF is 2,497,280,736 bytes with 398 tensors. It has **no `output.weight`**. Its `token_embd.weight` is a Q6_K matrix of shape `[2560, 151936]` in GGUF order, with a 319,065,600-byte payload. The [official Qwen checkpoint config at its 2025-08-05 upload](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507/blob/1b4199c4f36b0cef378bfb12390c18780c18af4c/config.json) declares `tie_word_embeddings: true`. The source topology and this GGUF inventory are consistent with the same matrix serving input lookup and output projection. The config alone does not establish the GGUF's tensor types; those came from the local descriptor audit. Conversely, the missing `output.weight` is not by itself a numerical equivalence check against the source checkpoint.

This changes the intervention implied by the earlier [1.5B output-head experiment](frontier-cpu-runtime-research-2026-11-12.md). That earlier model had a separate Q6_K `output.weight`, so reducing its precision left the Q4_K input embedding untouched. In the current 4B artifact, changing `token_embd.weight` changes both roles. It is a **new tied-embedding candidate**, not a larger-model replication of the output-head-only result. A [released Qwen3-0.6B same-source experiment](frontier-architecture-research-2026-11-12.md) already explored the shared-tensor idea and reported a perplexity and top-token agreement cost when changing Q6_K to Q4_K; it did not demonstrate preserved dependent-step quality. The current 4B artifact needs its own matched evaluation.

## Exact static byte budget

The GGUF reader found 216 Q4_K tensors totaling 1,765,048,320 payload bytes, 37 Q6_K tensors totaling 725,491,200 bytes, and 145 F32 tensors totaling 784,384 bytes. The 398 tensor payloads sum to 2,491,323,904 bytes; the difference from file size is 5,956,832 bytes of header, metadata, alignment, or other nonpayload content. All 216 Q4_K descriptors are two-dimensional with their second dimension divisible by eight, which satisfies one [pinned AVX2 repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5031) condition. It does not prove every tensor is repacked, allocated concurrently, or resident at the cgroup high-water mark.

The tied matrix has 388,956,160 values, or 1,519,360 blocks of 256. The [pinned GGML format definitions](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-common.h#L341-L368) give 210 bytes per Q6_K block and 176 bytes per Q5_K block. A hypothetical Q5_K encoding of this one tensor therefore has `1,519,360 × 176 = 267,407,360` payload bytes, exactly **51,658,240 bytes below** the present Q6_K payload. That equals 2.0686% of this GGUF. If every other byte, tensor type, alignment, and metadata field were unchanged, file size would be 2,445,622,496 bytes. This is format arithmetic, not a realized GGUF size. The candidate's full tensor map must be checked, since a quantizer's mixed-format heuristic can shift unrelated tensor types when overridden. A strict same-source comparison also requires constructing the candidate and reference from the same original checkpoint.

On the pinned x86 AVX2 backend, the [repack selector](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/ggml/src/ggml-cpu/repack.cpp#L5011-L5075) has a Q4_K path and no x86 Q5_K path. Thus Q5_K is a *plausible control* for avoiding the specific Q4_K anonymous repack route. The current Q6_K embedding also lacks that route, so Q5_K cannot be credited with a runtime-memory advantage over the reference without measurement. Five-bit decoding may change full-request CPU either way. Precision loss may alter answers or token counts in both embedding roles. The Q4_K theoretical payload saving is 100,277,760 bytes, but its pinned AVX2 repack eligibility makes the earlier cold-memory regression a direct concern, and it further changes precision. Neither candidate arm has been built here.

The log enumerates all 398 tensors and reports one type change: `[2/398] token_embd.weight`, Q6_K 304.28 MiB to Q5_K 255.02 MiB. Its 2,375.91 to 2,326.65 MiB summary is a tensor-payload estimate; it does not measure a completed GGUF or its metadata, alignment, or installed footprint. The named output file does not exist, as expected from [`--dry-run` in the pinned quantizer](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-quant.cpp#L1260-L1328). The dry run does not prove actual conversion succeeds, the output loads, only one payload changes, or any CPU, RAM, or quality benefit. A future actual build must compare all 398 payload hashes and metadata against the reference before resource testing. The pinned quantizer warns that [`--allow-requantize` can severely reduce quality compared with quantizing from 16/32-bit weights](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/tools/quantize/README.md).

This is a **postquantization sibling** of a third-party GGUF, not a strict same-source BF16/FP16 candidate. It starts from Bartowski's already quantized Q6_K embedding, so any Q5_K output would have sequential quantization error. The quantizer [copies source metadata and changes quantization fields](https://github.com/ggml-org/llama.cpp/blob/f3b407ca1/src/llama-quant.cpp#L1090-L1100); the source includes imatrix provenance strings, but this dry run did not supply an imatrix. A future artifact must audit or correct metadata that might suggest an imatrix was used for its new Q5_K tensor. It would be conditionally admissible for a separate paired postquantization experiment against this exact third-party reference if only the intended tensor changes, its provenance is explicit, and held-out quality is measured. It is **not admissible under the study's strict same-source original-checkpoint protocol**. For that protocol, quantize both arms from the same pinned original BF16/FP16 checkpoint with matched tool, calibration data, and settings.

The [pinned Bartowski repository API](https://huggingface.co/api/models/bartowski/Qwen_Qwen3-4B-Instruct-2507-GGUF/revision/ae44f08e1392f39c0e474af10c3ff8355c8b6688?blobs=true) lists its Q4_K_S file at 2,383,309,536 bytes (SHA-256 `952af947c6aabf7b72f7d8e279e76f7bf4b0d12431eb3abb588ef312865622d8`). It is **62,312,960 bytes smaller** than the hypothetical Q5-embedding file above. This is artifact byte metadata from the same repository revision, not evidence of equal quality, runtime, or RAM. The Q5 intervention remains a distinct precision allocation to test, but it has no file-byte advantage over that Q4_K_S control on these numbers.

## Source and measurement boundary

The most relevant CPU prior art remains selective offline packed layouts and mapped packed-weight caches, already reviewed in the [2026-11-12 CPU note](frontier-cpu-runtime-research-2026-11-12.md). The pinned GGML selector is format and hardware specific; a prepacked file for one CPU may require a different layout or a fallback on another. The [recent UMLoad paper](https://arxiv.org/html/2611.04253) reports a GPU unified-memory loading result after subtracting file-cache growth from its cgroup memory estimate, and the [Ingestion Tax paper](https://arxiv.org/html/2608.12114) compares GPU-mapped and copied weights. Neither provides a same-artifact CPU result on complete installed bytes, raw cold cgroup peak, full benign request CPU-seconds, and held-out task quality. There is no newly verified four-gate result in this audit.

If the reference clears an absolute benign multistep quality floor, the smallest useful Q5_K test is a frozen one-tensor candidate built from the same BF16 checkpoint with the reference's other 397 tensor payloads and metadata audited for identity. First compare both artifacts on the same host with the same pinned default-repack runtime, input prompts, output limits, and CPU features. Count all installed model, executable, library, tokenizer, and required sidecar bytes. In separate admitted cold and warm blocks, record whole-child user plus system CPU-seconds through loading, prompt processing, all generated tokens, and cleanup; the actual request end point also needs an application-level measure. Record process VmHWM and fresh-cgroup `memory.peak`, including file cache and anonymous memory, with prelaunch residency and page-charge ownership gates from the existing protocol. Inspect `anon` and `file` traces when peaks disagree. Finally compare paired outcomes and token counts on sealed tasks that the reference itself can solve. Reject the candidate if any prespecified gate fails or the quantizer changes unplanned tensors. This is a proposed experiment only; an embedding byte saving alone does not establish a CPU, RAM, or quality improvement.

The static audit did not independently hash the 2.5 GB file because that would read its whole payload during the separate quality run. Its SHA-256 in the inventory is attributed to that runner's metadata and is not a hash check performed here. No system-wide cache operation or CPU benchmark was performed.
